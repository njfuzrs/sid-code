# 否决「把状态栏的目标轮次与 API 调用数统一成同一个数」，只补口径说明

## 决定了什么

**不改任何计数，只在官网补一段口径说明**：`website/use/interactive.md` 新增「内置状态栏读法」，
`website/use/plan-mode.md` 的 goal 进度段加一句交叉引用与站内锚点。

两个数回答的是不同问题，各有各的消费方：

| 数字 | 数据源 | 回答什么 | 口径 |
| --- | --- | --- | --- |
| `◎ 目标 N/M 轮` | `goal.turnsUsed`，`packages/core/src/query/loop.ts:2724` 每轮**发请求前** +1 | goal 推进到第几轮、离轮次上限还有多远 | 按**轮**计：含被中断的轮，轮内重试不额外加轮 |
| `⟳N` | `SessionState.getTotalRequests()`（`packages/core/src/session/state.ts:1119`） | 实际打了多少次 API、花了多少钱 | 按**记账请求**计：含作废重试、子代理、`maxTurns` 强制总结轮 |
| `✘N` | `getDiscardedRequests()`（`packages/core/src/session/state.ts:1137`） | 其中多少次是白烧的 | `⟳N` 的**子集**，不是相加 |

## 放弃了什么（以及为什么不选）

**1. 放弃「统一成 goal 轮次」。** `⟳` 的消费方是成本与重试归因：`✘` 后缀、`/stats`、
`SessionEnd` 轨迹读的是同一个 getter。改成轮次后「这一轮花了多少钱」「重试白烧了多少」
就没有分母了——作废重试与子代理请求都不占 goal 轮。

**2. 放弃「统一成 API 调用数」。** `◎ 目标 N/M 轮` 的分母 `M` 是 `maxTurns` 轮次预算。
改用请求数会让 `M` 与预算单位对不上，且轮内重试会把进度推向上限——用户按 ESC 反而加快
耗尽预算。这会制造新的「轮次上限」误解，正是本方案要修的东西。

**3. 放弃在 Footer 里加 hover / 帮助说明。** 终端 TUI 没有 hover；`/statusline` 无参输出是
**自定义脚本协议**说明，不是内置列口径说明。为这件事新造 UI（弹层、提示条）的成本高于收益，
方案本身给了「没有就只改文档，不为这件事新造 UI」的出口。

**4. 放弃「写进代码注释就算完」。** 注释已经写清楚了（`session/state.ts:96-104`、`1127-1136`），
缺的是用户侧入口——用户看的是官网与状态栏，不是源码。
