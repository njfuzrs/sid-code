# 否决「给 goal 等待放行加一个配置开关」

## 决定了什么

方案 §5 的 D8 原文：

> 等待放行的开关：加 `GoalConfig.enableWaitSuspend`（默认 true）还是不加？
> 结论：**不加**。连续放行上限是防旁路的下限，不是业务偏好。

结论：等待挂起判据（`collectGoalWaitingFacts` → `decideWaitSuspend`）**无条件生效**，
没有开关，也没有「关掉它就退回旧行为」的分支。判据只看**事实**：
registry 里有没有显式声明、且未被释放的外部等待源（monitor / `wait_until` 后台 shell /
待投递通知）。

## 放弃了什么（以及为什么不选）

**放弃 `GoalConfig.enableWaitSuspend` 开关**，四条理由：

1. **它不是业务偏好，是下限**。连续放行上限（`MAX_CONSECUTIVE_WAIT_PASSES = 3`）
   防的是「模型挂着等待源无限放行、目标永远不评估」这条旁路。做成开关之后，
   一旦有人遇到「goal 卡住不动」，最省事的处置就是把它关掉——等于把防旁路的锁
   拆了去修另一个 bug，而那个 bug 的真实成因（等待源没被正确识别 / 释放）就被永久掩盖。
2. **开关会分裂出两条行为路径，测试面翻倍**。开 / 关各要一套「等待期该不该评估」
   的断言，而关掉那条路径实际上就是**修复前的缺陷行为**（end_turn 被打回、模型空转）。
   仓库不应该为「保留缺陷行为」维护一条受支持的配置。
3. **判据没有灰区**。与 `enableBlockedDetection` 不同：后者判的是「相同阻塞原因重复几次
   算卡住」，阈值是经验值，不同项目接受度不同；而「有没有一个还没释放的显式等待源」
   是纯事实，没有可调参数。没有灰区的策略不需要开关。
4. **配置面越小越好**。`GoalConfig` 已经承载了轮次、预算、评估模型、超时等多个旋钮，
   每加一个都要在配置文档、`website/ref` 参考页、SDK 类型里同步一遍；
   这次加开关的收益是「让用户能回到坏行为」，收益为负。

## 拿什么证明它生效了

- 单测 `packages/core/tests/goal/goal-waiting.test.ts`（11 例）锁三种组合：
  有显式等待 → 放行；只有派生任务 / 普通后台 shell → 不放行（宽口径被否决）；
  待投递通知 → 放行。判据是纯函数，开关不存在这件事由「函数签名没有开关参数」直接保证。
- 冒烟 `tests/smoke/cases/S-goal-wait`：挂 monitor → end_turn → `GoalGateDecision{reason:"waiting"}`
  恰好 1 条、`continue` / `satisfied` 各 0 条（评估器一次都没跑）。
- 冒烟 `tests/smoke/cases/S-goal-wait-achieved`（本 PR 新增）：等待挂起 → 释放 → 续跑 →
  评估器判 `satisfied` → `goal.status="complete"`。覆盖「放行之后目标真的能收尾」，
  证明放行不是「永远不评估」。
