# 否决「去掉 L2（`backgroundRunning`）早退来治等待期空转」，改用等待期专属判据

## 决定了什么

**不动 L2 的任何判据**，另加一条**正面判据**（P5，本 PR 已实现）：有声明等待源时，
前台连续执行状态查询这件事本身是信号 —— 第 5 次提示、第 15 次起硬拦（`WaitPollEscalated`
带 level 1/2），硬拦排在 P1 的 120s 探测窗口之前。

L2（`StagnationLevel.backgroundRunning` 的早退）是按「工作区没有进展」判的；
等待期它**必须**继续早退，见下一节。

## 放弃了什么（以及为什么不选）

提议的替代方案是：等待期空转的根因是 L2 早退把「没进展」拦掉了，那就**把早退去掉**，
让停滞判据在等待期也生效。

否决理由（一条就够）：

- **L2 判的是「工作区没有进展」，而等 CI 时工作区本来就不会有进展。** 去掉早退 →
  等待期**必然**被判定为停滞 → 强停。这正是 W2 修之前的老问题（「等待中强停」），
  改回去等于用一个新的错误替换旧的错误。
- 等待期的空转需要**等待期专属**的判据：判「有等待源还在查」而不是「没进展」。
  两件事的观察对象不同（一个看工作区，一个看查询行为），共用一个判据必然在其中一侧失真。
- 同样的错误还有一个变体：把 P5 的第一档（5 次提示）直接做成 `end_turn` 强制结束。
  这会让「模型确实需要看一眼才决定下一步」的合法轮次也被掐断，且与 G2（等待放行判据）
  的职责重叠。所以两档都做成「提示 → 硬拦」，不做强制结束 —— 结束本轮是模型的动作，
  由 G2 放行，不是 harness 替它决定。

## 拿什么证明它生效了

- L2 的既有单测未改动、全绿（`bun run affected-tests:run` 5767 pass / 0 fail）：
  说明本 PR 没有碰到停滞判据。
- 等待期硬拦只在「有声明等待源 + 命令被 `matchStatusQuery` 识别 + 次数 ≥ 15」三条同时成立时触发：
  `wait-poll-escalation.test.ts` 的「不传 escalation 时 P1 行为逐字节不变」与
  「等待源全部释放 → 计数清零」两条守住了「没有等待源时一次都不会拦」。
- G2 `S-wait-poll-pr-list` 在 20 次前台轮询下 `gh-overflow.log` 不存在（≤ 14 次执行），
  且 `WaitPollEscalated level:2` 恰好 1 条 —— 硬拦生效且不重复落事件。
