# 否决「在 P1 拦截回执前面加一句 P5 计数前缀」

## 决定了什么

方案 §4.10 第 4 条对「P5 的 ≥5 次提示」和「P1 的『结果与上次相同』回执」重叠时的处理是：

> 两者可以各说一次，但同一轮的 tool_result 末尾不要叠两段近似文案——
> 实现时若 P1 已给出回执，P5 的提示**改成一句前缀**即可。

按字面实现就是给拦截回执加一行 `[等待期第 N 次查询]`。**这条被否决。**

## 放弃了什么（以及为什么不选）

放弃「给拦截回执加前缀」，原因是它会打掉一个已上线能力的核心埋点：

- `query/unchanged-observation.ts` 的整条判据，以及 G2 用例 `P1-intervened-true`
  （`tests/smoke/cases/P1-intervened-true/case.ts`），都靠「**连续相同的工具返回值**」计数：
  同一工具同参连续返回相同内容，`run` 递增；达到阈值时若该次被 P1 拦截，
  `UnchangedObservationRun.intervened` 才置 true。
- 加了前缀之后，第 5 次的回执不再等于第 3、4 次的回执：
  观察序列从 `O,O,R,R,R` 变成 `O,O,R,R,R'`，`run` 停在第 5 次之前，
  埋点永远不触发。**空转检测直接失效**，而这恰好是本方案想解决的问题本身。

**决定性实验（2026-11-17 实测）**：

```text
# 加前缀
[bun run smoke P1-intervened-true]
[FAIL] P1-intervened-true
    ✗ 事件 UnchangedObservationRun {"intervened":true} 期望 1 条，实际 0 条

# 仅把拦截分支的 output 恢复成恒定 receipt（其它一行不动）
[PASS] P1-intervened-true (8.4s)
```

两害相权：「提示延迟一轮送达」远轻于「空转检测的核心埋点失效」。

也评估过另外两条路，一并否决：

- **改 `P1-intervened-true` 的期望来容纳前缀**：它是既有用例、守护另一个已上线能力。
  为新加的提示改旧契约的语义，等于让旧功能给新功能让路；而且 `expect-reviewed`
  只能由人加，agent 不得给自己加。**改测试前提不属于 RL-006 允许的「契约被有意变更」**
  ——这里变的是**测试所依赖的行为契约**（回执恒定），而那个契约没有理由跟着变。
- **把前缀放在 `tool_result` 之外（hook 附言等）**：P1 的拦截回执走的就是
  `tool_result` 的 `output`，没有第二个通道能让模型看到「第几次」而不改变该值。

**实际采用的替代**：`hinted` 与 `level:1` 事件都延后到 `pass()` 真正送达时再落。
第 5 次若被拦，就当这次「没送出去」，下一次放行窗口再送，文案里的计数是送达时的
真实次数（第 6 次 / 第 7 次…），比「第 5 次」更准。代价是提示最多晚一个探测窗口
（120s）——可接受，因为拦截回执本身每轮都在说「结果没变，不用再查」。

## 拿什么证明它生效了

- `bun run smoke`：**41 例 41 通过**（含 `P1-intervened-true`；若采用被否决的方案，这一例会红）。
- 新增单测 `T-P5-7`（`packages/core/tests/task/wait-poll-escalation.test.ts`）锁住三件事：
  拦截回执**不含** P5 文案、此时 `escalation.hinted` 仍为 `false`、
  探测窗口到期后提示**照常送达**且计数是第 6 次。
- 变异自证：把 `pass()` 里的 `hinted = true` 挪回达标处（即恢复「提前置位」）
  → `T-P5-7` 红；恢复后 14 pass / 0 fail。
