# 身份段不加多 agent 编排差异化标签

## 决定了什么

身份段（`buildIdentityIntro`，`packages/core/src/config/system-prompt.ts:933-946`）保持
**三档（zh / en / strong-guard）共用的四行极简文案**，不写入任何产品差异化或功能列表标签：

- 不写「支持多 agent 编排」「workflow / team_create / monitor 等能力」；
- 不把工具清单搬进身份段（工具的可发现性由 `<tool-guide>` 与 deferred 名单负责）。

第二轮 review 提出的「身份段单薄、没体现多 agent 编排差异化」**不采纳**。
本 Note 于 2026-11-22 复核时补记，决策出自 2026-11-19 的两轮 review 复核。

## 放弃了什么（以及为什么不选）

**放弃的方案**：在身份段加一行「你可以编排多个子代理 / 使用 workflow 完成大规模任务」，
以「体现能力差异化」。

**不选的理由**：

1. **诱导过度使用**。`workflow` 与 `team_create` 恰好是 `sub_agent` 的「更重版本」，
   两者自己的 guidance 都在劝退：「一次性派几个子代理用 `sub_agent` 就够」
   （`packages/core/src/tool/workflow.ts:166`、`packages/core/src/tool/team-create.ts:71`）。
   把编排能力写进**身份段**（每轮都可见、且带「你是谁」的权威语气），等于把更重的工具
   当功能徽章发出去，模型会在不需要编排的任务上倾向编排——代价是 token、延迟与误用率，
   而且这种倾向**没有任何门禁能测出来**（它只体现为轨迹里多出来的编排调用）。
2. **身份段是最贵的常驻区**。它每轮都在，四行已经覆盖「写代码 / 跑命令 / 解释 / 用工具」
   四条真实能力面；加营销句换不来行为改善，只换来固定的 prompt 体量。
3. **差异化不靠自我描述**。模型不会因为身份段写了「我会编排」就在合适的时机编排；
   它靠的是工具描述里的**操作契约**（何时用、何时不用、和谁互斥）。

**如果将来确实要补身份段**，正确方向是写成操作契约而不是功能列表，例如：

> 你的判断以证据为准：任何「已修复 / 已存在 / 零调用」的结论都要带 `file:line`。

这与既有的 `answer-discipline #6` 同源，属于**加固**而非营销。

## 拿什么证明它生效了

- 身份段仍是三档共用四行、无编排/产品标签：
  `packages/core/src/config/system-prompt.ts:933-946`（zh 与 en 各四行）；
  `grep -rn "workflow\|team_create\|multi-agent\|多 agent" packages/core/src/config/system-prompt.ts`
  在身份段区间（`:933-946`）零命中，唯一命中在 `:1160` 的 tool-guide 注释里（讲 tool 定义体量，
  与身份段无关）。
- 本 Note 本身是防回退锚：下一个 agent 再提「身份段加编排差异化」时，这里已有否决论证，
  不必把上面三条理由重推一遍。
- **没有加机械门禁**，这是有意的：身份段是自然语言表达，唯一能写的判据是
  「断言不含某些词」，那种门禁会在合理的措辞调整时误报，而它要防的「诱导过度使用」
  恰恰是措辞级判据测不出来的。约束落在本 Note + review。
