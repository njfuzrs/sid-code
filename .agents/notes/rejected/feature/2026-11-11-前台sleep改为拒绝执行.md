# 前台 `sleep N` 不改成「拒绝执行」（B 档不做）

## 决定了什么

N6 只做 A 档（引导，见
`implemented/bug-fix/2026-11-11-前台sleep改为引导后台等待.md`），**不**对齐 Claude Code 的
`detectBlockedSleepPattern` + `validateInput` 去**拒绝执行**命中的前台 sleep。

方案 §N6 自己也把这件事定成两档：「先做 A，B 看 A 的数据再决定（这条最容易误伤，宁可慢）」，
B 的前置条件是「A 上线两周后、数据显示模型看到提示仍然 sleep」。

## 放弃了什么（以及为什么不选）

- **拒绝执行的误伤面是真实的**：`sleep 2 && curl localhost:3000/health` 是等本地服务起来的
  标准写法，`sleep 5 && retry.sh` 是限速重试的常用形态。这些调用本身**没有错**，
  只是被同一条形态判据扫到。CC 能拦是因为它的 Monitor 是首轮可用的替代路径；
  sid-code 这边 A 档的引导才刚上线，还没有「模型看到提示后仍坚持 sleep」的数据。
- **sid-code 的闸门链会放大「工具被拒」的后果**：todo 闸门 / 停滞阶梯 / 承诺提醒都可能
  把一次被拒的工具调用当成需要处理的事件。方案 §N6 的 B 档明确要求先跑 G2 冒烟确认
  不会出现「被拒 → 闸门强推 → 再 sleep」的循环——这个验证成本远高于 A 档，而收益未证明。
- **A 档还没有取数**：新事件 `ForegroundSleepGuided` 刚落地，一条真实会话的数据都还没有。
  在没有任何「引导无效」证据的情况下先上拦截，等于把「更省」建立在猜上。
- **不做的替代方案是「等数据」**：A 档的 193 次（N ≥ 30）/ 67 次（2–29s，条件性）
  全量分布已经记在 implemented Note 里，两周后与本仓 `~/.sid-code/trajectories/`
  的新会话对比即可判定。

**重新评估的触发条件**（满足任一条就带数据重新提案）：

1. A 上线两周后，`ForegroundSleepGuided` 后的**同会话后续**仍有 ≥ 3 次前台 `sleep N`
   （即模型收到引导后照旧），且 `unwaited_longest_run` / `probe_spin_requests`
   （N7 的字段）p95 没有下降；
2. 出现「排了唤醒又用前台 sleep 阻塞，导致唤醒 lag > 60s」的真实会话 ≥ 3 次。

重新提案时必须先做方案 §N6 要求的 G2 冒烟：给定一次被拒的 sleep，确认不会出现
「被拒 → 闸门强推 → 再 sleep」的循环。

## 拿什么证明它生效了

否决，没有代码改动。依据可复查：

- 方案 §N6 的原文（「两档，先做 A，B 看 A 的数据再决定」）。
- implemented Note 第三段的全量扫描：975 会话 / 前台 sleep 260 次 / 78 会话，
  其中 N ≥ 30 的 193 次会关闭 A 档引导，2–29s 的 67 次是条件性引导
  —— 这 67 次正是 B 档最容易误伤的那部分（正常节奏 / 限速重试）。
- 本仓 CC 对照证据：`claude-code/src/tools/BashTool/BashTool.tsx` 的
  `detectBlockedSleepPattern`（`:322`）与 `validateInput`（`:525`）—— 它的拒绝文案里
  同时给了后台 Bash 与 Monitor 两条替代路径，且 Monitor 是首轮可用工具。
