# 不照搬 Claude Code「鼓励用 bash 脚本批改文件」的引导

## 决定了什么

system prompt 和工具描述**不加**「多处修改时优先写一段 bash / python 脚本一次改完」之类的引导。编辑仍以 `edit` / `write` 为主路径，`edit` 继续坚持唯一命中，不命中就报错。

来源是 harness 对比 bench（P1 维度 13、P3 否决项一）：同题下 cc 用 bash 批改把写调用数压到 29，sid 是 49。看上去像「更省」，实际只省了调用次数这个代理指标。

## 放弃了什么（以及为什么不选）

- **照搬 cc 的批改引导**：省下的只有调用次数。写操作轮数 27 vs 28、入参总字符 69K vs 76K，两边持平，判分题两边全过。代价是静默失配：cc 15 个 python 批改脚本里只有 6 个校验了 `replace` 是否命中，另外 9 个没命中时静默不改，要靠后面的测试才能发现。`edit` 唯一命中的报错，恰好是 bench 里 sid 做得比 cc 好的一点（P1 组 D 总结「sid 在两处做得更好，应保留」）。
- **批改脚本加命中校验的提示**：等于把 `edit` 的唯一命中检查搬进模型手写的脚本，靠文案保证。P2 维度 14 的数据显示，同一请求里有相反信号时，system 文案的违背率是 0.23–0.72，靠不住。
- **把「调用次数」当作优化目标**：P3 铁律回验第 ④ 条已经点破，这个指标会奖励把同样的浪费换个名字。要优化编辑成本，看轮数和 ΣP，不看调用数。

**重新评估的触发条件**：出现带判分的多文件批改题，且 sid 在**轮数或 ΣP** 上显著落后（不是调用数）；或者 bash 写入路径有了和 `edit` 同等的命中校验机制，而不是靠文案。

## 拿什么证明它生效了

这是否决，没有代码改动。依据是已有的 bench 数据，可以复查：

- 同目录 `P3-汇总-结论与backlog.md` §3 铁律回验第 ④ 条、§2 否决项。
