# 否决给交互模式设默认轮数 / 墙钟 / 成本上限

## 决定了什么

交互模式**不设**默认的轮数、墙钟或成本硬上限。`SID_MAX_TURNS` 保持 opt-in，与 `rejected/feature/2026-07-14-工具循环检测默认开启.md` 记录的用户决定一致。「长且无进展」由停滞升级阶梯（`query/stall-escalation.ts`）按**进展**刹车，而不是按**长度**。来源：评估会话 ce7ea52e，评估报告 §5 决策 4。

## 放弃了什么（以及为什么不选）

- **默认轮数上限**（如 200/500 轮）：任何固定值都会误伤合法长任务（大重构、长评测）。本机最长的会话有 1343 次 API，但其中也有合法的长 CI 等待（`57de4f89`）；数值拍不出依据。
- **默认墙钟上限**：宿主休眠会污染耗时口径（见 headless 挂起那次的结论），而且同样误伤合法长任务。
- **默认成本上限**：成本曲线随模型变化巨大，没有一个对所有模型都合适的默认数。
- 被评会话的真正问题不是「长」，而是「长且无进展」。只有进展判据能把这两类分开。
- 代价：停滞升级 L2 缺省是影子，所以影子期内交互模式仍然只有 L1 + 2e + ESC 兜底。如果影子期结论是 L2 无法做到零误判，这一项要重新讨论。

## 拿什么证明它生效了

（rejected 记录，没有可跑的验证。）依据是本机 370 个会话的离线重放（口径见 `implemented/feature/2026-10-21-停滞升级阶梯L1L2影子与收尾闸门联动.md`）：≥200 次 API 的 5 个会话里，既有真事故（`ce7ea52e`）也有合法长任务（`57de4f89` 轮询 CI），仅凭长度分不开。
