# 重复读硬拦截（D4 第二部分）按预登记门槛不触发，不做

## 决定了什么

PR8 的第二部分——把 `repeat_narrow` 从「非阻塞提示」升级为「硬拦截」（阻断第 N 次重复读）——
**不实施**。只做第一部分：`read_many` 纳入重复读登记（见
`.agents/notes/implemented/bug-fix/2026-11-19-read-many-纳入重复读登记.md`）。

判据来自方案 §6 PR8 的预登记规则（跑之前写死，跑完不许改）：
E1 之后子代理「未改动重读率」仍 > 11-12 前基线 31.1% + 5pp（即 >36.1%），
或 PR6 之后主会话仍 > 30%，才触发硬拦截。

E1（2026-11-18）实测：子代理未改动重读率 **72.6% → 20.0%**，低于 31.1% 基线，远低于 36.1% 门槛。
同一轮验收里轮次 max 313 → 60（≥100 轮的从 12 个降到 0）、`SubagentCost` p50 降到旧臂的 50.4%、
p95 降到 23.7%、报告 `file:line` 总量是旧臂的 1.374 倍；E1-bis 修口径后重判 13/13 通过。
主会话侧：PR6（#941）已合入，但方案自己写明「未改动重读率尚未验收」，没有数据支持
「主会话仍 >30%」，因此同样不触发。

以后若要重启这个议题，必须回到同一份预登记门槛、拿 PR6 之后的新轨迹数据重判，
不能凭「重复读看起来还是很多」的印象直接上拦截。

## 放弃了什么（以及为什么不选）

- **无条件硬拦截**：在数据不支持时增加一个会拒绝合法操作的路径。`read` 是安全只读工具，
  改完代码后重新确认某段、按行号复查同一区域都是正常行为；拦截的误伤成本高于它节省的 token。
- **「先提示 N 次，第 N+M 次阻断」的两段式**：看起来更温和，但阻断阈值同样没有数据可定。
  在重读率已低于基线的分布里，任何阈值都只能靠猜；而猜错的代价是不可逆的（工具调用失败）。
- **按会话累计重复读率动态升级**：需要跨工具、跨轮次的会话级统计与回退机制，
  复杂度远高于收益；当前 `ReadHint` 事件已经能从事后轨迹算出同一口径，
  真有回潮可以先在数据里看到，再按预登记规则重启，不需要提前付这套机制的成本。

## 拿什么证明它生效了

- E1 数据与门槛对照：方案 §8.7（E1）、§8.9（E1-bis）；文档 §6 表格明确记录
  「E1 已判定两项均不触发（重读率 20.0% < 31.1%+5pp）」。
- 本次 PR 让第一部分落地后，`read_many` 的重复读也进入 `ReadHint` 事件流
  （8 个 G1 用例，其中一条直接断言事件字段 `read_count` / `overlap_ratio` / 窗口），
  下一次门槛判定的数据源不再缺一块——这本身就是「现在不做拦截」的前提条件：
  看不见的重复读没法判，先把它看见。
