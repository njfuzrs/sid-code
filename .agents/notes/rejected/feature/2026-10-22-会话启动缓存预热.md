# 下线从未接线的会话启动缓存预热（warmupPromptCache）

## 决定了什么

删除 `packages/core/src/session/warmup.ts`（`warmupPromptCache`），连同只为它存在的配套一起删：
`network-profile.ts` 的 `warmupMs` 与 `SID_CODE_WARMUP_TIMEOUT_MS`、`billing-sink.ts` 白名单里的
`cache_warmup`、`help.ts` 的 `SID_WARMUP_CACHE` / `SID_DISABLE_CACHE_WARMUP` 两行，
并重新生成 `website/ref/env.md`。

删除前在 main（`40009be3`）上 grep 过：全仓只有定义处 `warmup.ts:46`，没有任何调用方，
也没有 index 再导出它。超时、计费归类、日志通道都接好了，唯独入口从未接线，
于是读 `network-profile.ts` 或 billing-sink 的人会以为预热已在生产启用。

## 放弃了什么（以及为什么不选）

放弃「在 resume 分支接线」：

1. **命中没有保证**：预热请求传的是 `model: ""`（走 provider 默认模型），而 prompt cache 按模型隔离，
   而且 system 和 tools 要与主循环首轮逐字节一致。只要有一处不一致，预热就是白付一次
   cache_creation（input × 1.25），换不来首轮的 cache_read。要让它可靠，得把模型解析和
   prompt 组装的时机与主循环对齐，那是一项新功能，不是修缺陷。
2. **本地无法证明收益**：只有在真实 Anthropic 流量上对比首轮 `cache_read_input_tokens` 才能看出效果，
   接线后的 PR 拿不出这份证据。
3. 门控只覆盖 Anthropic + resume，覆盖面本来就窄。

将来要重做时，先在主循环上量出 resume 会话首轮 cache miss 的真实比例（p95 成本差），
再设计「与主循环共用同一份 system/tools/model 解析」的预热，而不是恢复这份实现。
