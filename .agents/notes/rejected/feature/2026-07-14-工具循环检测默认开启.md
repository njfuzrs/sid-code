# 否决工具循环检测默认开启（shape 误判率≈100%，exact 召回≈0）

## 决定了什么

工具循环检测**默认全局关闭**，仅 `SID_ENABLE_LOOP_DETECTION=1` 显式开启。
检测代码全部保留（`_disabled` 路径把 record / recover 变 no-op），env 门控可逆。

同时**改掉了旧的论证措辞**：原先写"对齐 CC"，那站不住 —— 它描述的是别人做了什么，
不是我们的判据。现已改成实证依据（`help.ts` + `loop-detection.ts` 注释）。

## 放弃了什么（以及为什么不选）

放弃两条路径，各有实测依据（探针 `scripts/loop-detection-probe.ts` + `scripts/loop-stats-probe.ts`，
均只读、可复跑）：

**① 放弃"放宽阈值继续默认开启"。** 曾把 `ToolShapeLoopDetector` 阈值从 5/8 放宽到 7/10，
治标不治本。根因是 shape 检测把工具调用降维成 `toolName + key-set + anchor字段` 指纹、
**刻意丢弃参数 value**，天然无法区分"真死循环"与"正当推进"。对 bash 尤其严重：
`command` 值不进 key、又无 `path`/`cwd` anchor，于是 8 条语义完全不同的命令
（`git status` / `rm -rf` / `release.sh` …）shape key **全塌成同一字符串** ——
检测器实际退化成"窗口内 bash 数 ≥ 阈值就报警"。`read` 带 `file_path`（anchor）则能区分，
证明这是 bash 特有的退化。

42 个真实会话回放：模拟开 shape 检测 14/42 命中，抽样 14/14 **全是误判**
（`git status`→`diff`→`log` 巡检 / 发布流程 / 系统性 glob）= **误判率≈100%**；
模拟开 exact 检测仅 1/42 命中且是低危的 commit 后 status 轮询 = **召回≈0**。两个检测器都无净收益。

**② 放弃"只对只读命令开检测"这个分级提案 —— 它会适得其反。** 基础设施是现成的
（`bash/read-only-validation.ts` 的 `isReadOnlyCommand`/`isDestructiveCommand`，探针实测 15/15 准确），
但只读的 `status`→`diff`→`log` 正是最高频的**正当**模式，占误判样本的 46.2%。
正确切法恰好相反：只读命令做**「输入 + 输出双重复」**检测（能精准抓到"10 次 `git status`
输出一字不差"这类真死锁，同时放过输出各异的巡检），有副作用 / 破坏性的交权限层。
当前缺口是检测器只 record 输入（`loop.ts`）、看不到 observation，接入有成本 —— 故未做。

顺带记一条**附带发现，比循环检测本身更该关注**：交互模式 `maxTurns` 默认 = `Infinity`
（`loop.ts` 的 `config.maxTurns || Infinity`）、`costLimit` 默认不设 →
关掉检测后，交互模式唯一的硬兜底只剩用户按 ESC。用户决定暂不改行为，仅记录。

## 拿什么证明它生效了

- 两个只读探针脚本可随时复跑，误判率 / 召回率两个数字都是回放真实会话得出的，不是估计。
- bash shape key 退化有实锤：8 条语义不同命令的 shape key 打印出来是同一字符串。
- 真实事故有会话可查：`20260706-162837-38428f6e` 执行 `/commit` 时连跑
  `git diff`/`add`/`commit`/`log` 被判"bash shape 探测循环"并反复刷屏，
  `warn.log` 明确记录"8 次内出现 7 次"。
- ⚠️ 语义反转的复核点：新语义下 `delete env` = 关闭、`="1"` = 开启，与 2026-07-06 那版**相反**，
  写测试时必须注意。同批全量单测里 `loop-watchdog.test.ts`(2) 与 `output-stall.test.ts`(1)
  是**预先存在**的失败（流看门狗 / 输出停顿，与工具循环检测无关），别误归因到本次改动。
