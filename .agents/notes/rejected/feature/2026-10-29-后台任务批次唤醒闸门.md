# 不做「同批后台任务全部完成前不唤醒主循环」的闸门（B1 选 (c) 不改）

## 决定了什么

同一批后台任务逐个完成时，每条 `<task-notification>` 都会唤醒一轮主循环（「1 个完成，还剩 3 个」）。这是 F3 「更快 ↔ 更省」取舍的已知代价，**维持现状**。

决策阈值按方案文档事先写死：中间轮占主循环计费 < 5% 就不做。实测 **3.33%**。

## 放弃了什么（以及为什么不选）

- (a) 批次闸门：收益只有约 3% 计费。代价是要在 registry 引入「批次」概念，还要把多个唤醒入口（TUI 空闲续跑、Bridge、headless、`background-wake.ts`）收敛到同一个判据函数。延迟唤醒也会重新碰到事故 `20261016-124505-786b1586`（通知躺在队列里无人消费）的风险面。某个子代理挂住时，其余结果会被一起拖住。
- (b) 2–5s 合并窗口：同批相邻完成间隔 p50 是 23.5s，只有 22% 在 5s 以内，能合并掉的很少。
- (d) 提示词让中间轮空回复：省下的只是 output，大头是 input，每轮约 5 万 token 照付。
- 复测会话里中间轮占 44.7%，几乎全来自一次服务端缓存波动（第 3 轮 cache_read 只有 1664）。跨会话看，缓存未命中的中间轮只贡献 0.15%，所以不能拿单个会话定案。

**重新评估的触发条件**：中间轮计费占比 ≥ 5%，或者用户反馈中间轮发言打扰体验。

## 拿什么证明它生效了

一次性统计脚本扫了 `~/.sid-code/trajectories/sessions/` 下全部 573 个会话：

- 合格会话（同一 1s 窗口内启动 ≥2 个后台任务）24 个，主循环 `BilledRequest`（无 agent_id、无 caller）569 次。
- 中间轮判据：上一个主循环请求之后有 `TaskLifecycle delivered via=notification` 到达，output < 200，且同批仍有未终态任务。命中 24 轮。
- 中间轮占主循环上下文 token 2.83%、计费 **3.33%**。单会话计费占比 p50 3.5% / p95 30.4% / max 44.7%。
- 计费按 `~/.sid-code/gateway-pricing.json` 的 input / cacheRead / output 单价计算。⚠ anthropic 口径的 `input_tokens` 不含 cache_read，openai 口径含。第一版脚本没区分这一点，算出了负成本，按 provider 区分后才得到上面的数。
- 局限：样本只有 24 个会话、14 个有中间轮，以 claude-opus-5-5 为主。
