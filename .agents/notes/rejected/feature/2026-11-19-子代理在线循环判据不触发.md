# 子代理在线循环判据（PR9）两条触发条件都不成立，三个离线判据搬到在线也是误杀机器

## 决定了什么

PR9 **不做**。既不把 `trace/digest.ts` 的三个判据搬到子代理循环当在线规则，
也不接 LLM 认知检测。产品代码零改动，本 PR 只落这份否决论证。

否决有两条独立理由，任一条都足够：

1. **触发条件两条都不成立**（§7.1.3 G5 的预登记判据）：批 3 合入后，日常轨迹里
   `task_stop` 打在子代理上 0 次，打满默认上限（100 轮）的子代理 0 个。
2. **第 1 步的离线评估给出了否证**：三个判据在现有 89 个 sidechain 上，
   精确率 0.29%–2.44%、召回 1/5、正常子代理假阳性最高 93.2%。
   就算触发条件成立，这套判据也不能直接搬——它会把绝大多数正常子代理判成空转。

## 放弃了什么（以及为什么不选）

### 触发条件：批 3 之后，两条都不成立

口径与分界点：`~/.sid-code/trajectories/sessions/*/events.jsonl`，1292 个会话、
548 条 `SubagentStop`；「批 3 之后」取 PR5「explore 默认轮次上限 100」的合入时刻
`2026-11-18T11:05:24Z`（PR #930），因为触发条件说的就是「默认上限上线后」。

**条件 A：仍有子代理需要 `task_stop` → 不成立。**
全量 15 次 `task_stop` 调用里，目标是子代理（`TaskLifecycle.task_type = local_agent`）
的只有 **1 次**：`2026-11-16T09:19:32.937Z`（`tid=aufy7ledt`）——**就是本方案的触发
事件本身**，早于批 3。批 3 之后 **0 次**。其余 14 次的目标是 `local_shell`(11) /
`local_monitor`(1) / 无法归因(2)。

**条件 B：打满默认上限且 r > 35% → 不成立。**
批 3 之后共 16 条子代理结束记录，`turns` 分布 `min=15 / p50=32 / max=61`，
`turns >= 100` 的 **0 条**，16 条全部 `completed/finalize`。
（与 E1 的 `turns_max=60` 独立吻合，见 §8.7。）

> 一个必须点破的口径限制：批 3 之后的 16 条全部落在 `11:37–11:42` 这 5 分钟内，
> 样本窗口很窄，不足以单独支撑「问题已消失」的强结论。所以本 Note 的结论不单靠它，
> 而是「E1 的造场景数据（`task_stop_calls=0`、`turns_max=60`）+ 本地日常轨迹
> （`task_stop` 打子代理 0 次、`turns_max=61`）」两条独立数据源互补。

### 第 1 步离线评估：三个判据逐个都不能用

正例全集（按事实定义，不按字段）：`stop_action=max_turns`（3 个，2026-11-05 的
custom 代理）+ `aborted`（1 个，2026-11-13 的 custom 代理）+ 被父代理 `task_stop` 杀
（1 个，aufy7ledt），共 **5 个**。反例 = `completed` 且有 sidechain 的 **88 个**
（其中 11-12 前的 13 个）。

**正例的 sidechain 覆盖率只有 1/5**：4 个 custom 代理发生在 `agent_transcript_path`
落盘之前，没留下 sidechain。所以「在全部 sidechain 上算召回率」这件事，分母本身
只有 1 个可验证样本。

| 判据 | 命中 | 真正例 | 精确率 | 正例召回 | 反例假阳性 |
| --- | --- | --- | --- | --- | --- |
| `zero_yield_subagents`（`status !== "completed"`） | 44 | 1 | 2.27% | 1/5 | 0/88（结构性 0，见下） |
| `subagent_io_imbalance`（`input/output > 50`） | 312 | 1 | 0.32% | 1/5 | **82/88 = 93.2%** |
| `repeated_tool_shape_run`（连续同形状 ≥ 4） | 41 | 1 | 2.44% | 1/5 | **40/88 = 45.5%** |
| 三者并集 | 347 | 1 | **0.29%** | 1/5 | — |

三条各自的结构性问题，都不是「阈值没调好」：

1. **`zero_yield` 对「打满上限」结构性零召回。** 它的口径是 `status !== "completed"`，
   但打满上限的 3 个子代理 `status` 全是 `completed`——它们进了强制总结轮并成功收尾，
   在 `SubagentStop` 里看起来和正常完成一样。这个判据抓的是「没跑完就崩」，
   不是「跑完了但一直在空转」。改阈值改不动，口径本身不对。
   （表里「反例假阳性 0/88」也因此没有信息量：反例的定义就是 `completed`，
   判据天然不可能命中它们，它不是「判得准」，是同义反复。）
2. **`subagent_io_imbalance` 在正常 explore 上 93.2% 命中。** explore 天然 input 重
   output 轻——88 个正常样本的 io 比 `p50 = 133.6`，阈值 50 落在分布左侧。
   它区分不了「空转」和「读了 100 个文件后写一份总结」，而后者正是 explore 的本职。
3. **`repeated_tool_shape_run` 假阳性 45.5%。** 阈值为 4 时，「连续读同一目录下的
   不同文件」就会命中；而唯一可验证的正例 `maxShapeRun` 恰好等于 4，卡在阈值上才命中
   ——召回是「刚好擦边」，不是判别力。

### 其余候选路径，逐条否决

- **不管数据、直接搬到子代理循环当在线规则**（PR9 步骤 2）：精确率 0.29% 意味着
  347 次命中里 346 次是误判。每次误判的代价是一个正常子代理被中断、已读的上下文作废、
  父代理重派。比不做更差。
- **接 LLM 认知检测**（PR9 步骤 3）：前提是触发条件成立。两条都不成立时，为一类
  批 3 后 0 次出现的现象付每轮一次模型调用，与「更省」直接冲突，也没有可验收的对象。
- **按 §6 PR5 定值规则第三档重新定值**：那一档的定义是「打满上限且 r > 35%」，
  现在打满上限的样本是 0 个，无从观测 r，定值只能靠猜。
- **改 `zero_yield_subagents` 口径，把「打满上限」也算零产出**：会让 `/digest` 把
  正常收尾的打满子代理报成病态，污染现有诊断信号；而本 Note 的结论恰恰是
  「不需要在线判据」，改它也没有消费者。

## 拿什么证明它生效了

本次 PR 只加这份 Note，不改产品代码，所以「生效」= 上面每个数字都能被独立复现。
三条复现路径：

1. **触发条件 A/B**：遍历 `~/.sid-code/trajectories/sessions/*/events.jsonl`（1292 个
   有 events 的会话），从 `SubagentStop` 取 `turns / status / stop_action /
   agent_transcript_path`；从 `PreToolUse{tool_name:"task_stop"}` 取 `task_id`，
   再与同会话 `TaskLifecycle.task_id → task_type` 联接，判定目标是子代理还是 shell/monitor。
   实测输出：`local_agent` 类 `task_stop` 全量 1 次（11-16，aufy7ledt）、批 3 后 0 次；
   批 3 后 16 条子代理 `turns min=15/p50=32/max=61`、`>=100` 的 0 条、全部 `completed/finalize`。
2. **离线评估**：对 89 个可用 sidechain 逐个重算三个判据的子代理级等价物——
   `status != "completed"` / `in_tokens / out_tokens > 50` / 连续
   `tool + 首参数首词` 同形状 ≥ 4——与正例标签（`max_turns` / `aborted` /
   被 `task_stop` 杀）求交。输出即上表（精确率 0.29% 的口径是三者并集 347 命中里
   真正例 1 个）。
3. **交叉印证**：方案 §8.7 的 E1 造场景数据给出 `task_stop_calls=0`、`turns_max=60`；
   本地日常轨迹独立给出「打子代理 0 次、`turns_max=61`」。两个数据源互不重叠，
   结论一致。

以后若要重启这个议题，必须重新满足 §7.1.3 G5 的两条触发条件，拿批 3 之后的新轨迹
重判；并且要先解决上面第 1 条的口径问题（`zero_yield` 认不出打满上限），
否则任何在线判据都只是把正常子代理拦下来。
