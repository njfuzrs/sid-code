# 放行类注入不加「但仍优先使用专用工具」之类的对冲文案

## 决定了什么

给模型的放行类文案（bypass / 全放行档位下的提示、工具「可以用」的许可）**不追加**「但仍应优先使用专用工具」「尽量不要……」这类对冲句。要让模型少做某件事，用离行动更近的位置说（tool_result 尾注写「禁止 + 替代做法」），或者用 harness 机制兜底，不在同一段 system 文案里正反各说一句。

来源：P2 维度 14（指令遵循）对比了 cc 的 bypass 注入。cc 在放行注入旁边另有偏好专用工具的说法，模型照样跟着放行那条走。

## 放弃了什么（以及为什么不选）

- **加对冲句**：维度 14 §4 按文案位置拆违背率。「同一请求里另有相反信号」的 system 文案违背率 0.23–0.72，是所有位置里最不被听的一类。冲突时模型跟离行动更近的那条走。加对冲只加 tokens，不改行为；还会让以后读文案的人以为这条约束是有效的。
- **把对冲句挪到 system 更显眼的地方**：维度 14 的结论是同一位置内的方差远大于位置间的方差，真正的预测变量是有没有相反信号，以及文案离行动的距离（尾注 > 题面 > 工具描述 > system > 项目指令中段）。挪位置不解决冲突。
- **可行的替代**：Q1 后台轮询就是例子。回执里写「Do NOT Read」并配 harness 拦截，F3 上 flash 第一次真正触发了拦截，也兜住了。这是本 Note 推荐的路径，不是否决的对象。

**重新评估的触发条件**：有 A/B 显示某条对冲句在双模型上都显著降低了目标违背率（不是只看 opus）。
