# 否决「可观测性接线率」静态门禁，改人工分诊

## 决定了什么

不建「接线率」静态门禁（原方案：扫 `src/` 里导出函数有无被其它文件引用，算出接线率，
低于阈值报红）。改为一次性人工分诊 + 直接修债。原设计文档已标 `status: superseded`。

分诊结果：**42 个「疑似未接线」里只有 4 项是真缺陷**，全部已修：

- `refreshMetadata` 零调用 → 切模型后 `_ctx_model` 恒为旧值，事件全归因到错模型；接到 `applyPrimaryModelSwitch`
- `shutdownFeatureFlags` 零调用 → 关闭期仍远程 fetch；接到 `runShutdownSequence`
- `asVerified` 零调用 + 三份重复 cast → 收口
- `extractSessionId` 真死代码 → 删

顺带删掉 `span-manager.ts` + `als-context.ts`（能力已被 `context.ts` 的 `TraceContext.spanStack` 取代）。

## 放弃了什么（以及为什么不选）

否决理由是复跑方案自己的取数命令得出的，四条：

1. **基线复现不出来**：方案写 134/89/31/9，实测 155/113/33/9。而 `89/134 = 66.4%` 是它「整体验收」的唯一判据。
   模式 `^export function` 还漏掉 `export async function`(3)、`export class`(12)、约 130 个 class 方法。
2. **口径测的不是「接线」**：判据「src 内有非自身文件引用」把 113 个判为活，其中 33 个的引用者
   **全在可观测层内部**。被算成活的恰好包含方案表格自列为债的 `sanitizeToolName` —— 表格与命令自相矛盾。
3. **看不见旗舰缺陷**：`logEvent` 有 7 个 src 引用文件 → 报绿，而生产调用点只有 `app.ts:2752` 一处。
   门禁测「有无 ≥1 引用」，真缺陷恰恰是「只有 1 个生产调用点」。
4. **方案自列的六个先例，0 个抓得到**：四环防线 / 团队记忆 / `evictTerminalTasks` 都不在扫描范围内，
   `recordSubAgent` 是 class 方法，analytics 报绿。

**38/42 的误报率本身就是最强的否决证据** —— 这个比例下的门禁只有两个结局：豁免白名单刷满，或被人摘掉。

最大的假阳性根因：取数命令用 `grep -v "^$f$"` 排除定义文件自身，把「同文件内调用」也算成零引用 ——
9 个「真死代码」里 4 个因此误判。

另有两条曾写进 CLAUDE.md 北极星的说法被此次核验推翻，已更正：
「analytics 1113 行只挂 1 个埋点」（实际 12 个 `log*` 全接线，5 条漏斗共 25 个生产调用点，
`logEvent` 直接调用只一处是**刻意的** —— 业务侧必须走 `analytics/events.ts` 门面强制脱敏）；
「OTLP 出口不通」（三处白名单均已接通）。

## 拿什么证明它生效了

- 复跑方案 §6 的全部取数命令，逐条对照，数字对不上（155/113/33/9 vs 文档的 134/89/31/9）——
  这是否决的第一手依据，不是推理。
- 4 项真缺陷修完后各自带回归测试；`refreshMetadata` 那条的验证判据是切模型后事件里的
  `_ctx_model` 跟着变（改前恒为旧值）。
- 「是否接到生产」的正确口径已固化为：数**跨模块/跨层的生产调用点数**，排除同层自引用与同文件调用。
  对「埋点有没有落过数据」这个问题，运行时口径（`scripts/defense-trigger-rate.ts`）是 ground truth，
  天然免疫上述全部盲区 —— 想立静态门禁前先问它是否比运行时口径更划算。
