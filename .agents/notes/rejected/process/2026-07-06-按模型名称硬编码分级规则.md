# 否决「按模型名称硬编码强/弱模型分级」

## 决定了什么

代码里**不得**出现按模型名称匹配的能力分级规则（`if (model.startsWith("claude")) ...` 这类），
即使短期看起来合理。开关类默认值一律改为：**全局统一默认值 + 一个环境变量/配置项做显式覆盖**。

这条是用户在循环检测 P0-1 修复中的明确否决：我最初提议「循环检测按模型分级默认开关
（Claude / GPT-4o 关，DeepSeek / Ollama / 其他开）」，被直接否决 ——
"不想按照模型来分级，这样会留下隐患，要禁止代码中硬编码这种规则"。

## 放弃了什么（以及为什么不选）

放弃的是「按模型身份缩小生效范围」这条降风险路径。

不选的理由：模型名单与能力会持续漂移。今天判定为"强模型"的名单，明天会因为新模型上线、
老模型行为漂移而过时或覆盖不到。**写死的分级规则本身就是维护隐患，而不是防御** ——
它会在无人察觉时静默失配，且没有任何信号提示"这张名单已经过期了"。

对冲风险的正确位置也不同：如果一个防御机制默认全局开启看起来有风险，
先看能不能**降低触发后果**（只软提示、不硬终止），而不是靠限制生效范围来降低风险敞口。

这条**不等于**"任何按结构/能力的区分都不行"。区分依据如果是稳定的结构性事实
（例如"这个任务是否 fork 继承了完整父上下文"），就不违反本条 ——
同一次任务里子代理 `maxTurns` 按 fork / 非 fork 分档就被明确认可保留了。

## 拿什么证明它生效了

- 循环检测最终形态是「全局统一默认值 + `SID_ENABLE_LOOP_DETECTION` 显式覆盖」，
  代码里零模型名称匹配。同范式后续被复用到 `SID_ENABLE_HYPOTHESIS`、裸符号省略规则。
- 判据是可机械复核的：在开关类默认值的判定处 grep 模型名字面量（`claude` / `gpt` / `deepseek`），
  应为零命中。这是一条随时可复跑的检查，不依赖记住这次讨论。
