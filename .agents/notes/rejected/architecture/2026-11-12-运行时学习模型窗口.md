# 否决「运行时从 400 学习模型上下文窗口」这一类设计

## 决定了什么

**不再接受任何形式的「运行时观测 → 改写模型固定属性 → 跨会话生效」的窗口学习**，
包括「只本会话生效」「不覆盖窗口只用于提前压缩」「给网关墙场景兜底」这些折中变体。

S6（`2026-10-18-压缩重注入角色交替与运行时学习已放行窗口.md` 的后半部分）已于 2026-11-12 整体撤销，
本 Note 保存否决论证，防止下一个 agent 看到「网关 400 后没有学习」时重新提议同一件事。

## 放弃了什么（以及为什么不选）

S6 的推理链在三处断裂：

1. **错误的归因**。它把「请求被拒」等同于「输入超过窗口」，但同一句 `Input tokens exceed the model context limit`
   至少有三个成因：输入本身超窗、**输入 + max_tokens 超窗**、网关额外限制。S6 无法区分，一律当成第一种。
   实测根因是第二种：每次请求都发 `max_tokens=384000`（注册表里的物理上限），而 DeepSeek 按
   「输入 + max_tokens ≤ 1,048,576」校验 → 可用输入只有 664,576。6/6 次溢出的「溢出前最后一次成功输入」
   都落在 654k–664k，最大 664,057 与 664,576 只差 519，没有一次是输入本身逼近 1M。
2. **错误的修正对象**。哪怕网关真在某个值设了墙，正确做法是修正**请求预算**（max_tokens），
   而不是改写**模型属性**（上下文窗口）。窗口是厂商公布的固定属性，不会因为一次请求失败而改变。
3. **自我强化**。学到 664k 之后压缩阈值按 664k 算，会话更早被压缩，再也够不到真实上限，
   永远不会出现「更大的成功请求」来纠正它；`Math.min(旧 ceiling, admitted)` 让下界只降不升，
   7 天 TTL 只是让错误值过期，过期后再撞两次又学回同一个值。

**代价是用户实感的**：分母被改小成 664,057，Footer 百分比放大 1.506 倍（同一批任务 34%–44% 显示值，
真实只有 22%–29%），有效窗口损失约 1/3，压缩/遮罩阈值全部按错的分母计算。

**如果要为真实的网关墙兜底**，正确路径是用户在 `availableModels[].contextWindow` 里显式声明，
或显式配置 `SID_FALLBACK_CONTEXT_WINDOW`；不是让产品偷偷把模型属性改小。

## 拿什么证明它生效了

撤销的依据全部来自本机轨迹与代码，不靠推理：

- `~/.sid-code/learned-input-ceiling.json` 实测内容：键为 `origin-deepseek-v4-1-flash@<网关 base_url>`，
  值为 `ceiling=664057`、`learnedAt=2026-11-09 01:17`。
- `events.jsonl` 中 `"context_window":664057` 出现 6105 次、`1000000` 出现 576 次（11-09 之前）；
  即 S6 生效后分母被系统性改写。
- 700+ 会话轨迹里 `warn.log` 含上下文溢出的共 6 个会话，全部是同一模型、同一报错，
  「溢出前最后一次成功 input + 384,000」距 1,048,576 分别为 2462 / 1563 / 9918 / 5958 / 875 / 519。
- S6 立项 Note 自己写了「0.665 成因未证」——这个数可以由 `(1,048,576 − 384,000) / 1,000,000 = 0.6646` 精确算出。
- 撤销后的回归由 `packages/core/tests/llm/no-learned-window.test.ts` 守：磁盘上有有效旧学习文件时窗口仍取静态值；
  变异自证（恢复读取点）会使其 2 fail。
