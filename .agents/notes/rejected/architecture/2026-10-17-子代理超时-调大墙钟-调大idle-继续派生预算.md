# 子代理超时：否决「调大墙钟 / 调大 idle / 继续派生预算」三条路

## 决定了什么

否决。子代理不再有任何「过了多久」的总时长限制，改为与主循环同构（漏斗内容无进展断流 + 重试，
单轮硬超时只兜 abort 链路失效）。见 `implemented/architecture/2026-10-17-子代理去掉墙钟硬kill默认maxTurns-对齐CC.md`。

## 放弃了什么（以及为什么不选）

1. **调大墙钟（300s → 600s / 900s）**：#284 合入后 9/9 次子代理失败全部死在超时层，0 次是「限制救下失控子代理」。
   事故 20261016-222758 的死法是 900s 硬 kill——任何固定值都会被足够慢的上游击穿，调大只是把浪费翻倍。
2. **调大 idle（60s → 更大）**：idle 层的问题不是阈值，是语义——到点只置标志、不断流，等漏斗重试时把重试流判死
   （事故 20261016-224545）。PR #319 已整层删除；调大阈值等于让同一个缺陷晚点发作。
3. **继续按 p95 派生预算**：冷启动并行时样本不足恒退回 definition 值（两起事故都如此）；
   更根本的是判据仍是「过了多久」而不是「有没有推进」，后者已经由漏斗承担。

下一个想加回子代理墙钟的人，先回答：它要防的失控场景，ESC / task_stop / 单轮硬超时 / 重试上限哪一个防不住？

## 拿什么证明它生效了

否决依据来自轨迹全库扫描（`~/.sid-code/trajectories/sessions/*/events.jsonl`，#284 后 `SubagentStop` completed 25 / error 9，
9 次逐个对应到超时层）与 CC 源码对照（前台子代理默认无墙钟、内置代理无 maxTurns）。
详见方案文档 `bugfixes/todo/20261017-子代理执行失败-超时层叠加掐死重试-对齐CC去限制-修复方案.md` §1、§5、§6.4。
