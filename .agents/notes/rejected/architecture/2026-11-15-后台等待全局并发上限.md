# 不给后台等待设全局并发上限，只按对象去重

## 决定了什么

后台等待（bash 后台 / monitor / schedule_wakeup）**不做全局并发上限**，也不做「同一时刻只允许一个等待」。准入只按**对象签名**判定：同一对象上的第二次等待是 duplicate（不启动），不同对象可以并行（R2 + R6）。

## 放弃了什么（以及为什么不选）

候选一：**全局并发上限 ≤ 4**。否决理由：b0aa0f1e 的真实轨迹里同一脚本连挂 4 份、同一个 PR 被等 4 次，4 份正好卡在上限内 —— 上限 4 对本案**完全失明**。上限值只要 ≥ 实际重复次数就一次都不会触发，它是一个不知道重复次数时拍的常数。

候选二：**全局并发上限 = 1**。否决理由：会误伤合法的并行等待。一个会话同时等「PR 的 CI」和「该 PR 的 mergeable 状态」、或同时等两个无关 PR，是正常用法（`N4-quiescent-declared-wait` 就是单等待场景，真实会话里多对象并行更常见）。上限按数量判，无法回答「是不是同一个东西被重复等」这个真问题。

候选三：**按 (kind, 对象) 组合上限**。否决理由：仍然是数量阈值，只是换了个维度；同一对象被等两次时它照样放行（上限 ≥2）或误伤（上限 =1 时跨 kind 的合法组合，如 monitor 看 CI + 唤醒定时检查）。

选按对象去重的理由：重复等待的伤害来自「同一个对象被多份等待各报一次」，按对象判能精确定位，且不需要任何拍出来的常数。跨对象并行不加限制。

## 拿什么证明它生效了

- `packages/core/tests/task/wait-admission.test.ts` 的真值表：同 subject 同命令 → duplicate；同 subject 不同命令 → replace；不同 subject → start。
- `packages/core/tests/trace/digest-wait-source.test.ts` 的「R9 验收 2」：同一对象 4 次调用 = 1 次 start + 3 次 duplicate → 并存峰值 1。对照同文件验收 1 的真实轨迹（修复前同对象并存 4）。
- G2 `tests/smoke/cases/R2-dup-wait-same-subject`（duplicate 不起进程）与 `replace-wait-same-subject`（replace 淘汰旧的）。
- 反证：若采纳候选二（上限 = 1），上述「不同 subject 的两条等待不算并存」用例与多对象并行的 G2 场景都会变红——它们锁住的正是合法并行。
