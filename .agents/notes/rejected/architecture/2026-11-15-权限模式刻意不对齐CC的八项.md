# 否决：权限模式上刻意不对齐 claude-code 的八项

## 决定了什么

否决。以下八项**保持现状、不改代码**。它们都在「权限模式对比」中看起来像「sid-code 比
claude-code 少做了什么」，逐条核过之后结论是「不该跟」。PR-1 修掉 auto 的两条真实越权
（M1、M1b）后，这些差异全部属于**有意的取舍**，不是缺陷。

| # | claude-code 的做法 | 否决理由 |
| --- | --- | --- |
| M10 | acceptEdits 自动批准 `rm` / `rmdir` / `mv` | `rm -rf .` 的 `.` 经 realpath 后就是 cwd，「在工作区内」这个判据对它失效（`checker.ts` P1-3 注释）。CC 用关键路径检测兜底 `rm -rf /`，兜不住工作区内的递归删除。sid-code 实测 `acceptEdits + mv a b` → 需确认，保持。 |
| M11 | v2.1.283+ 交互终端默认 auto，但**只限 Pro/Max/Ultra/Team 订阅档**；Enterprise、Claude API、Bedrock/Vertex/Foundry 仍 opt-in，`-p` 与 Agent SDK 仍默认手动 | sid-code 的用户形态（企业网关、各家 API）正落在 **CC 自己也没改默认**的那一侧，理由见 J1。 |
| M12 | bypass 跳过受保护路径的安全检查 | `always-allow` 的 Step 8 排在 Step 6 `safetyCheck` 之后，这是「always-allow 不能写 `.git/hooks/`、settings」的实现方式；10-24 Note 修过的 symlink 绕过也依赖这个顺序。要 CC bypass 的效果请用 skip 档。 |
| M13 | plan 在 bypass 可用时命令直接跑、auto 可用时交给分类器 | 出口总闸 `enforceModeHardConstraint` 是 10-24 用七条实测绕过换来的唯一事实源；放开等于把 plan 从「代码约束」退回「流程约束」。`checkPlanMode` 注释已记过一次同类否决（`shouldPlanInheritBypass` 删除且刻意不接活）。 |
| M14 | 没有 `deny-write` | sid-code 独有的代码级只读档，零维护成本（只占出口总闸一个分支），删掉没有收益。 |
| J1 | 默认模式改成 auto（M11 的落地决策） | **裁决：保持 `default`**。① M1、M1b 证明 auto 修好前不可信；② sid-code 的分类器本地注入（`config.classifierModel \|\| config.model`），未配分类器模型时每个 ask 多一次主模型调用，「更省」倒退，且无服务端审查分摊成本；③ 没有数据：本机 622 个会话里 auto 只有 1 个，无法证明误放行率与拦截体验可接受。「配了分类器模型就默认 auto」看起来折中，但条件用户感知不到，会让同一人在两台机器上得到不同默认档，违反可预期性。 |
| J8 | `--restricted` flag；root 下拒绝 skip 档 | `--restricted` 是一组限制的打包，sid-code 每一项都有独立开关（`disableBypassPermissionsMode`、`disallowedTools`、`deny-write`、`strictPluginOnlyCustomization`），企业场景由 managed settings 统一下发更难绕过；打包成本是多一套需与各开关保持同步的组合逻辑。root 拒绝 skip 会直接打断容器内无头运行（Harbor 评测、CI），而容器本身就是隔离边界。 |
| — | 关键路径 `rm` 在 auto 下是「两分钟倒计时提示」 | sid-code 是 `critical` 硬拒。**sid-code 更严**，与 M10、M12 同一取向：把「不可逆的破坏」留在人工确认一侧，不做倒计时自动放行。 |

## 放弃了什么（以及为什么不选）

- **放弃「差异即缺陷」的读法**：这份清单的来源是一次横向对比，报告列的是「CC 有、
  sid-code 没有」。逐条回到代码与实测之后，M10/M12/M13/M14 是安全取向更强的选择，
  M11/J1/J8 是用户形态与成本结构决定的。按「对齐」去改会把「更安全」方向上的存量
  优势改掉（CLAUDE.md：每个改动都要点破牺牲了哪一维）。
- **放弃「默认 auto + 配了分类器模型才生效」的折中（J1 选项 C）**：用户感知不到
  「配没配分类器模型」，违反可预期性。真要改默认，走 J1 的推翻条件（拿到 ≥30 个
  auto 会话的误判数据 + 分类器成本有分摊机制）。
- **放弃把 `--restricted` 做成命令行 flag**：企业下发走 managed settings，打包成 flag
  的收益只是「一个参数」，成本是与 4 个独立开关的同步逻辑，且命令行参数比 managed
  settings 更容易被本地绕过。
- **放弃本轮扩大 auto 分类器的覆盖面（M19 三项）**：进入 auto 时剥离危险 allow 规则、
  审查跨代理消息、子代理三段审查——三项都要先回答「分类器误判率是多少」，而本机
  auto 样本只有 1 个会话。在没有度量的组件上叠加复杂度是本末倒置，另立专题，
  等 PR-1 合入且 auto 轨迹 ≥ 30 会话后再评估。

## 拿什么证明它生效了

这不是代码改动，验证方式是「保持现状的证据仍成立」：

- M10：`acceptEdits + mv a b` 实测仍需确认（`checker.ts` P1-3 注释记录）；
- M12/M13：`always-allow` 写 `.git/hooks/` 仍被 Step 6 `safetyCheck` 拦下，
  PR-1 新增用例 4（`write <ws>/.git/config` → `step=6`）复验了这条顺序没有被动过；
- M14：`deny-write` 仍在模式闭集内；
- J1：`defaultConfig().permissionMode` 未改，PR-1 的端到端用 `--permission-mode auto`
  显式进入；
- 推翻条件（写在方案第七节，这里留指针）：J1 需要 ≥30 个 auto 会话的误判数据 +
  分类器成本分摊机制；J8 需要企业用户明确提出 `--restricted`，或出现本机 sudo 运行
  skip 档的事故。
