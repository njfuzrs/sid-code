# 否决 LSP「编辑前后诊断计数 delta」，改修子代理断层

## 决定了什么

不做「编辑前记 `preErrorCount` → 编辑 → `setTimeout(500)` 等重诊断 → `postErrorCount` →
`delta > 0` 则注入回归提醒」这套机制。同方案 §5 的三项演进（趋势曲线 / 自动回滚 `git checkout` /
codeAction 联动）更该砍。

改为修真正的缺口：**被动 LSP 管线在子代理路径上完全断层** —— `agent/tool-executor.ts` 在
edit/write 后不通知 LSP（连 `didChange` 都不发），`agent/agentic-loop.ts` 从不注入诊断
（`collectDiagnosticText` 全项目仅主循环一处调用）。五处改动已落地，其中一处**超过 CC**：
诊断注入前判 `toolRegistry.get("edit") || get("write")`，纯只读子代理（explore / summarize）不注入。

## 放弃了什么（以及为什么不选）

放弃计数 delta，两条硬伤：

1. **会被 churn 抵消而漏报** —— 修掉 2 个错误、同时引入 2 个新错误 → `delta = 0` → 静默放过。
   这正是它声称要抓的场景。
2. **`setTimeout(500)` 在慢语言服务器上恰好失效** —— 500ms 是个赌博值，赌输时读到的是编辑前的诊断。

CC 源码实证（`claude-code/src`）：**CC 刻意不做计数 delta**。它两条管线都用别的口径 ——
① IDE/MCP tracker（`DiagnosticTrackingService`）用 baseline 的**集合成员差集**
（`getNewDiagnostics` filter 不在 baseline 里的条目），不算 `count_after - count_before`；
② 自 spawn LSP（`LSPDiagnosticRegistry`）用**内容级跨轮去重**，编辑后 fire-and-forget
`didChange`/`didSave`（不 await、不轮询）+ 清缓存，靠下一轮 attachment 自然覆盖。

**将来若接 IDE（VSCode / JetBrains over MCP）**，值得抄的是管线①的 baseline **集合差集**，
**不是**这份方案的计数 delta。别再走计数弯路。

另外，同一方案换宏大包装后又提过一次（codeAction quickfix，2026-07-13），带 3 个未验证的代码假设，
其中 §3.5「编辑后 setTimeout(500) 主动请求」正是 CC 的反面、§3.6「每轮注入 quickfix」的
"零 token"是虚假卖点（每轮常驻）。那次只落地了一个 pull 式只读子集
（`peekDiagnosticsForFile` 只读快照 + 第 10 个 `codeAction` 操作 + 诚实展示"只读、用 edit 工具落地、
不自动改文件"），**关键不变量是 peek 绝不消费 pending** —— 否则每轮诊断注入链会断掉。

## 拿什么证明它生效了

- CC 源码是逐条 grep 核过的，不是印象：`codeAction`/`quickfix` 在 `claude-code/src` 全零命中；
  CC 的 LSPTool 操作枚举与我们 9 个逐字相同、无第 10 个；全库无 `applyWorkspaceEdit`。
  **CC 有完整 LSP 却刻意不接 codeAction**，所以这是标杆划的边界，不是我们的能力差距。
- 子代理断层修复走真实 `typescript-language-server` 做 e2e：缺 import 的文件 → peek 拿到
  `Cannot find name 'resolve'` → `codeAction` 返回带真实 `newText` 的 quickfix →
  `collectDiagnosticText` 在 peek 之后**仍可正常消费**（这条断言就是在守上面那个不变量）。
  方案原设计传空 `context.diagnostics` 时此处会返回空。
- 测试 +15 例，全量 5432 pass，`make rebuild` 通过。
- 一处刻意不往回改的取舍：我们只注入 Error/Warning，CC 注入全严重度 + 排序 ——
  我们这样更省 token，别为了"对齐"改回去。
