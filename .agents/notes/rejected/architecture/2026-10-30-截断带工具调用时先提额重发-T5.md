# 否决「截断 + 工具调用时先提额重发」（T5）

## 决定了什么

T5 设想的改动：停因是 `max_tokens` 且最后一块是 `tool_use` 时，先原样提额重发一次（对齐 CC 和 Anthropic 文档的第一档），失败再走现有的 F1/F2。
**不做，代码不动。** 现有的 `empty_param_retry`（F1）已经接住了观测到的全部样本。缺陷本身仍然成立：`max_tokens_escalate` 在工具执行之后，带工具调用的截断走不到提额那一档。但在数据里，这个缺陷没有造成过损失。

判据（T6 预先写死）：「截断 + 工具调用」占比 < 0.1%，且没有写坏文件的案例，就关掉 T5。两条都满足：

| 数据源 | 调用数 | 截断 | 截断且带 tool_use |
| --- | --- | --- | --- |
| 本地 `~/.sid-code/trajectories`（10-04 至 10-30） | 19,450 | 0 | 0 |
| `evals/external-benchmarks/harbor` | 4,592 | 24 | 2 |
| `agent-traj-bench` | 4,405 | 0 | 0 |
| 评测合计 | 8,997 | 24 | **2（0.022%）** |

这 2 例都在 deepseek 臂 `w3-sid-ds41-54`，output 撞上了 32,768 的上限，都由 `empty_param_retry` 接住，下一轮正常 `tool_use`：

- `password-recovery`（`20260911-190421-17f6bceb`）：之后的两次 write 都成功，没有重写同一文件
- `make-mips-interpreter`（`20260911-180630-8cdd534a`）：之后两次 `todo_write` 参数校验失败，原因是缺 `active_form`。这是 schema 漏字段，不是写坏文件

## 放弃了什么（以及为什么不选）

- **照做 T5**：给一个 0.022% 的场景加一条恢复分支，而现有路径已经兜住了。还会多一个 continue 理由、多一份 cap、多一次往返，换回来的「少写坏一次文件」在样本里一次都没出现
- **等 11-30 本地复查后再一起关**：评测这一半已经满足判据，本地 19,450 次调用 0 截断。拖着不关，T5 会一直挂在待办里被重新评估。11-30 的复查照做，作为翻案条件，不作为关闭前提

## 拿什么证明它生效了

- 取数口径：扫 `AfterModelRaw` 的 `stop_reason ∈ {max_tokens, length}`，按 `content_types` 是否含 `tool_use` 拆开。两个样本回读了截断后续轮的 tool_use / tool_result
- 口径限制：harbor 轨迹的 `model` 统一是 `harbor-gateway`，按模型拆只能靠 run 名推断；数据集中在 2026-09，早于 `tool_use_facts`（10-29），看不到 `tool_use_truncated`；`harness-bench/results` 没有 sid 轨迹
- **重新打开的条件**（任一条）：2026-11-30 跑 `bun scripts/defense-trigger-report.ts`，本地「截断且带 tool_use」占比 ≥ 0.1%；或者出现 `tool_use_truncated` 之后写坏文件、重写同一文件的案例；或者 deepseek 等模型的默认 max output 下调，导致撞上限变多
