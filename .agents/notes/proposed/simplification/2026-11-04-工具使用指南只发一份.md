# 已加载工具的使用指南只发一份（tools[].description），A/B 开关先行

## 决定了什么

新增环境开关 `SID_CODE_TOOL_GUIDE_DEDUP=1`（默认关）。打开时，`buildToolGuideSection`（`config/system-prompt.ts`）不再为**已加载**工具渲染「### X 工具使用指南」段。

根因是同一段文字发了两遍。`toolToDefinition`（`tool/registry.ts:55-58`）已经把 `usageGuide()` 拼进 `tools[].description`，system `<tool-guide>` 又用同一个 `usageGuide()` 渲染一份，两边同源，正文逐字相同。

- 延迟工具的指南不动：它们首轮不在 tools[] 里，system 那份是唯一能看到的地方。
- 「可用工具」的一行摘要和「未加载的工具」名单都保留。
- 开关不在 `SystemPromptContext` 里，所以单独进了 `generateCacheKey`（`__toolGuideDedup`），同一进程里切换开关不会命中另一臂的缓存。

现在是 `proposed`：要过双模型 A/B（bench_fix 06a），通过后改成默认行为、删掉开关，再把本 Note 移到 `implemented/`。不通过就移到 `rejected/`，记下是哪个模型、哪道题退步。

## 放弃了什么（以及为什么不选）

- **删 description 那份、留 system 这份**：子代理的工具定义走 `registry.definitionsForTools()`（`agent/sub-agent.ts:1169`），延迟工具激活后也走 `toolToDefinition`，两条路径都只认 description。删 description 会让子代理和激活后的工具失去指南。cc 也只有 tools[] 一份。
- **直接改默认行为，不加开关**：A/B 要求对照臂和改动臂只差这一处改动。main 距离 F3 的冻结二进制 `3e555757` 已经多了 300 多个提交，现成数据当不了对照臂，只能在同一个二进制上关开各跑一遍。
- **顺手删掉延迟工具的完整指南（Q5-b）、合并 bundled `skill__*`（Q5-d）**：一项一个 A/B，否则退步时没法归因。这两项排在 Q5-a 之后。
- `agent/tool.ts` 的注释原本写「system 里那份信号比 description 强得多」。这是本改动最大的风险（弱模型可能更不愿意派子代理），但它从来没被测过。现在注释改成「未经 A/B 的假设」，验收单独看 L3f 的子代理派发次数。

## 拿什么证明它生效了

- 单测 `packages/core/tests/config/tool-guide-dedup.test.ts`，6 条：默认关时行为不变；打开后 system 里没有已加载工具的指南，但 `registry.definitions()` 的 description 里还有；延迟工具指南保留；英文档同样生效；缓存键能区分两臂。
- 变异自证：
  - 把开关判断改成恒走旧路径，3 条红（开关开、英文档、缓存键）；
  - 去掉缓存键里的 `__toolGuideDedup`，缓存键那条红。
- 回归：`affected-tests:run` 860 pass / 0 fail；`system-prompt.test.ts`、`deferred-tools-in-prompt.test.ts` 不用改。
- 实测（本 worktree 构建的二进制，空 git 仓库，`origin-deepseek-v4-1-flash`，`--strict-mcp-config`，每臂 1 次）：

  | 臂 | 首调 inputTokens（usage） | system 字符 | tools 字符 | system 里的指南段 |
  |---|---|---|---|---|
  | 关 | 25,391 | 25,525 | 30,376 | 17 |
  | 开 | 22,075 | 18,853 | 30,376 | 4（只剩延迟工具） |

  每次调用省 3,316 tokens（13.1%），tools[] 不变。这个探针没有项目 CLAUDE.md，换到真实仓库，绝对值不变、占比会变小。
- 质量是否退步还没测，要等 06a §4 的双模型 A/B。探针里开关打开的那一臂把「只回复 ok」答成了「好的」，样本只有 1 次，不能下结论，A/B 时一并留意指令遵循。
