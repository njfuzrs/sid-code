# `for` 循环体全是只读时是否该放行——本轮不放宽，待核实 CC 行为

## 决定了什么

**本轮不放宽**。`cd <ws> && for p in 1 2; do git log; done` 保持判非只读、落确认。
本 Note 只记录现状与复核方法，不作为实现依据。

现象（方案 §3 B10）：取证会话 14 次「工作区内 `cd` + 非只读主体」里有 **5 次**是这种形态：

```text
for p in 730 731 732 733 734 735 736 737; do printf "#%s -> " "$p"; git log --oneline --all --grep="($p)" ...; done
for s in eced3bfd b736fc6f 582d9622 2861c6db e424f97e 6ecfbad4; do printf "%s -> " "$s"; git log --all ...; done
```

`splitCompoundCommand` 把 `for p in …` / `do printf …` / `done` 拆成独立段，三段都不是只读命令，
所以整条判非只读。PR-2 的 Step 5.6 同样不放行（集成测试里有断言）。

## 放弃了什么（以及为什么不选）

**不放宽的四条理由**：

1. **对齐的前提是知道 CC 怎么做，现在不知道。** CC 的 `permissions.md:226` 只说
   ask/deny 规则对 `for` 循环体生效，没说只读放行认不认循环；源码里新的 AST 路径会展开
   循环体（`ast.ts:693`），但只读判定层用的是旧切分器，两层叠加的结果读不出来。
   在不知道基准的情况下「放宽」等于自创一套口径。
2. **循环变量可能出现在命令位置**：`for c in ls rm; do $c x; done`。要放宽就必须做变量追踪，
   而 CC 新代码里专门为此写了注释（`ast.ts:693-700`）——说明它自己也认为这不是白送的。
3. **收益与风险不对称**：5 次确认的收益，换「循环变量当命令」这一类任意执行的漏放风险。
4. **PR-2 的边界已经足够大**：B3 的 cd 复合判定刚引入候选 cwd 集合、仓库归属、相对路径读
   重定向三组新逻辑，再叠一层循环展开会让同一个 PR 的 review 面失控。

**为什么不做「循环体全部静态可见且都是字面量命令才放行」的窄口径**：`for p in 730 731`
的循环变量必然以 `"$p"` 形式出现在参数里，纯静态判定要么放过 `$p`（那 `$c x` 也一起放过了），
要么要求「变量只出现在参数位置」——这需要真正的数据流分析，不是一次 PR 的增量。

## 拿什么证明它生效了

- 集成测试（`readonly-compound-integration.test.ts`）有一条
  `ASK: cd <ws> && for p in 1 2; do git log; done（B10 不放宽）`，断言真实
  `PermissionChecker` 下 `allowed === false`；
- 方案 §6.1 的 PR-2 用例表把这条列在「必须仍拦」组，修前修后行为一致（不放开；
  修前是 Step 14 普通确认，修后仍落普通确认）。

## 复核方法（结论出来后再决定是否进入下一轮）

在 CC v2.1.28x 的 Manual（默认）模式下跑两组命令，看是否弹确认：

1. **循环体全只读**：`for f in a.txt b.txt; do cat "$f"; done`
2. **循环变量在命令位置**：`for c in ls rm; do $c x; done`

判据：

- 若 ① 零确认、② 有确认 → CC 做了「变量只在参数位置」的追踪，本仓要放宽就得先补这层分析；
- 若 ① 也确认 → CC 也不放宽，本 Note 可以关闭（无需实现）；
- 若两者都零确认 → CC 用的是更宽的展开策略，需要单独评估 `$c x` 这类形态的风险后再提方案。

复核时记录 CC 版本号与 `permissions.md` 的对应行号——这份 Note 的价值在于
「下一个 agent 不会重新论证一遍」，不在于结论本身。
