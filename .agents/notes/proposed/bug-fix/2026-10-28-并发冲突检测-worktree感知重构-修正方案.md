# 并发冲突检测 worktree 感知重构：按风险分析修正后的实施方案（8 PR → 修正顺序 PR-5/8 → PR-1 → PR-2 → PR-4/6/7）

## 决定了什么

外部方案文档（20261016-并发冲突检测-worktree感知重构.md）列出 11 个缺陷（B1–B11）与 8 个 PR。
经对照 HEAD 52133acf（v0.1.612 后）逐一核实，**11 个缺陷全部仍成立**，方案方向可行，但按
风险分析做了以下修正，全部修正项已并入实施顺序：

### 修正后的实施顺序

1. **PR-5**（状态栏 worktree 识别）与 **PR-8**（无头模式冲突摘要进工具输出）先行——
   两者独立、低风险、用户可感知。
2. **PR-1**（存储层双轨重构）**吸收 PR-3、C1、B-a/B-b 边界修正**一起做——它们改的是
   同一个函数簇（`intentKeyForPath` / `declareFileIntent` / `queryFileIntents`），分开做
   会造成两次契约变更。
3. **PR-2**（子代理 agentId 维度）随后，顺带修复 C2（子代理并发写意图文件互相覆盖）。
4. **PR-4 / PR-6 / PR-7** 可并行收尾。

### 关键技术决定

- **A1（契约先定）**：PR-4「知道了，继续」按钮的 `ConflictAction` 语义必须在 PR-1 就定死
  （新增 `"accept-risk"` 或复用 `"continue"` + `ConflictReport.acceptedRisk` 标记），
  否则 PR-7 的误报率代理指标（action 分布）会被未定义的 action 值污染。
- **A2（性能是必需项不是优化项）**：`declareFileIntent` 是全仓最高频路径之一
  （`read.ts` 每次读文件都调），PR-1 引入的 `realpathSync` + `findCanonicalGitRoot`
  必须带**进程内缓存**（按路径前缀记忆化），否则每次 read 多两次同步 IO 遍历。
- **B-a（Write 新建文件）**：`realpathSync` 对不存在的文件抛 ENOENT，归一化必须用
  「最近已存在祖先」策略：对 `dirname` 逐级回退找第一个能 realpath 的祖先，再拼回文件名。
- **B-b（gitRoot 起算点与 null 回退对称）**：`findCanonicalGitRoot` 必须从
  `dirname(filePath)` 起算而不是进程 cwd；返回 null 时（separate-git-dir 等布局）
  写入侧与查询侧必须**对称地**回退到同一套降级 key（物理路径本身），任何一侧单方面
  回退都会造成写进去的 key 和查询算出的 key 对不上 = 静默漏检。
- **C1（原子写）**：意图文件改 temp + rename 原子写，并入 PR-1。现状是并发读侧
  `queryAllFileIntents` 对 parse 失败的文件直接 `unlinkSync`——半写文件会被误删，
  这不是防御是数据丢失路径。
- **PR-4（B-c）非阻塞路线**：`isWorktreeBranchConflict === true` 时不调用
  `conflictHandler`（不弹窗），直接返回 `continue` 并在写工具 output 里附一行说明。
  弹窗分叉只留给同分支真冲突。**block 模式判定在自动放行之前**——用户显式配置
  `conflictSeverity=block` 时哪怕只是分支分叉也照样阻止（显式配置 > 自动决策）。
- **D1（PR-6 追加，冲突闸门单一实现）**：B8 给 notebook_edit 接冲突检测时，不接受
  「第三份 ~90 行拷贝」——edit/write 的两份拷贝靠「两处必须同步改」注释人肉同步，
  已是漂移隐患（PR-4 就同时改了两处）。提取 `tool/conflict-gate.ts` 的
  `runConflictGate`，三个写路径工具共用；语义差异只剩埋点的 tool 名。变异⑤单点
  改坏闸门、三套件齐红，证明「单一实现」不是纸面宣称。
- **D2（PR-7，观察者模式替代文档失实的 `getTraceCollector()`）**：外部文档 §2.10
  让 `recordConflict` 直接调 `getTraceCollector()?.appendEvent(...)`——该单例
  **全仓不存在**（文档第三处失实）。改用 `decision-telemetry.ts` 同款的模块级
  观察者：`conflict-analytics.ts` 持有 `_observer` 并导出
  `setConflictEventObserver`，collector 在 `registerHooks` 时自注册；未注入
  （测试/无轨迹模式）静默 no-op。理由：session 域反向 import trace 域会形成
  循环依赖，而观察者方向是 trace→session 单向接线，与权限埋点（B11 的
  PermissionDecision）同一架构，消费侧口径天然对齐。
- **D3（PR-7，hitlMs 缺失语义 = 没等人，不落 0）**：只有 `conflictHandler`
  弹窗分支的事件带 `hitlMs`；`branch_auto_continue` / `blocked` /
  `headless_fallback` 三个自动决策分支**没有这个键**。落 0 会被读成「秒批」，
  与 `decision-telemetry` 的 `durationMs`（仅 prompted=true 时落）同一条口径。

## 放弃了什么（以及为什么不选）

- **放弃「8 个 PR 严格按文档顺序串行」**：PR-3（key 计算重构）与 PR-1（存储双轨）改同一
  函数簇，分两个 PR 意味着 `intentKeyForPath` 签名变两次、W15 测试改两次，且中间态
  （PR-3 合入而 PR-1 未合）写入侧与查询侧口径不一致。合并为一个 PR 反而满足
  「能独立上线/回滚/一次 review 完」三条测试。
- **放弃「意图文件按 agentId 分文件」（PR-2 原案）单独做**：C2（子代理并发覆盖）的根因
  就是一会话一文件 + 子代理共享父 sessionId，按 agentId 分文件顺带修掉它，不需要
  额外的锁机制。
- **放弃「用锁保护意图文件写入」**：锁引入死锁与残留锁清理问题（worktree GC 已经为
  锁付过学费，见 W13），temp+rename 原子写在单文件粒度上足够。
- **放弃「冲突检测改用 git merge-base 判断分支分叉」**：需要每个写操作 spawn git 子进程，
  在最高频路径上不可接受；`findCanonicalGitRoot`（纯 statSync/readFileSync）+ 分支名
  比对已够判据。
- **放弃「notebook_edit 复制一份冲突块」（PR-6 原案的最小实现）**：外部方案文档
  §2.7 只要求在 notebook-edit.ts 补 declareFileIntent/checkConflict，照抄意味着第三份
  ~90 行拷贝。三份人肉同步的实现必然漂移（PR-4 加一个分支就要同步改两处的教训），
  提取共享闸门的成本（一次提取 + 三处调用点改造）远低于长期漂移成本。
- **放弃「notebook_edit 在子代理路径特例 new（todo_write 模式）」**：todo_write 特例
  是因为它不在工厂里；notebook_edit 现在持 tracker 且需要子代理隔离重建，工厂 +
  STATEFUL_TOOL_NAMES 是既有收敛点，特例化反而制造第二条构造路径。
- **放弃「PR-7 给 collector 加 getConflictStats() 拉取接口」（拉模式）**：拉模式要求
  collector 在会话结束时主动去 conflict-analytics 读累计值，而 analytics 是模块级
  全局态——多会话（子代理并行）时读到的边界不清，且与权限埋点（推模式，事件级）
  形成两套口径。推模式（观察者逐事件转发）让 conflictStats 的生命周期天然跟随
  collector 的 SessionStart 重置，无全局态残留问题。
- **放弃「session-index 里存冲突比率（误报率代理）」**：比率不能跨会话合并
  （0/1 与 100/200 平均不等于 100/201），只存计数与原始等待样本，比率由
  northstar-snapshot 消费侧复算。与 permission 块（存 prompt_durations_ms
  样本不存比率）同一条规则。
