# 并发冲突检测 worktree 感知重构：按风险分析修正后的实施方案（8 PR → 修正顺序 PR-5/8 → PR-1 → PR-2 → PR-4/6/7）

## 决定了什么

外部方案文档（20261016-并发冲突检测-worktree感知重构.md）列出 11 个缺陷（B1–B11）与 8 个 PR。
经对照 HEAD 52133acf（v0.1.612 后）逐一核实，**11 个缺陷全部仍成立**，方案方向可行，但按
风险分析做了以下修正，全部修正项已并入实施顺序：

### 修正后的实施顺序

1. **PR-5**（状态栏 worktree 识别）与 **PR-8**（无头模式冲突摘要进工具输出）先行——
   两者独立、低风险、用户可感知。
2. **PR-1**（存储层双轨重构）**吸收 PR-3、C1、B-a/B-b 边界修正**一起做——它们改的是
   同一个函数簇（`intentKeyForPath` / `declareFileIntent` / `queryFileIntents`），分开做
   会造成两次契约变更。
3. **PR-2**（子代理 agentId 维度）随后，顺带修复 C2（子代理并发写意图文件互相覆盖）。
4. **PR-4 / PR-6 / PR-7** 可并行收尾。

### 关键技术决定

- **A1（契约先定）**：PR-4「知道了，继续」按钮的 `ConflictAction` 语义必须在 PR-1 就定死
  （新增 `"accept-risk"` 或复用 `"continue"` + `ConflictReport.acceptedRisk` 标记），
  否则 PR-7 的误报率代理指标（action 分布）会被未定义的 action 值污染。
- **A2（性能是必需项不是优化项）**：`declareFileIntent` 是全仓最高频路径之一
  （`read.ts` 每次读文件都调），PR-1 引入的 `realpathSync` + `findCanonicalGitRoot`
  必须带**进程内缓存**（按路径前缀记忆化），否则每次 read 多两次同步 IO 遍历。
- **B-a（Write 新建文件）**：`realpathSync` 对不存在的文件抛 ENOENT，归一化必须用
  「最近已存在祖先」策略：对 `dirname` 逐级回退找第一个能 realpath 的祖先，再拼回文件名。
- **B-b（gitRoot 起算点与 null 回退对称）**：`findCanonicalGitRoot` 必须从
  `dirname(filePath)` 起算而不是进程 cwd；返回 null 时（separate-git-dir 等布局）
  写入侧与查询侧必须**对称地**回退到同一套降级 key（物理路径本身），任何一侧单方面
  回退都会造成写进去的 key 和查询算出的 key 对不上 = 静默漏检。
- **C1（原子写）**：意图文件改 temp + rename 原子写，并入 PR-1。现状是并发读侧
  `queryAllFileIntents` 对 parse 失败的文件直接 `unlinkSync`——半写文件会被误删，
  这不是防御是数据丢失路径。
- **PR-4 非阻塞路线（B-c）**：`isWorktreeBranchConflict === true` 时不调用
  `conflictHandler`（不弹窗），直接返回 `continue` 并在写工具 output 里附一行说明。
  弹窗分叉只留给同分支真冲突。

  实际实现（`worktree/canonical.ts`）零处 `realpathSync`，只读 commondir 指针。
  realpath 归一化必须作为 PR-1 的独立工作项实现，不能指望现成函数。

## 放弃了什么（以及为什么不选）

- **放弃「8 个 PR 严格按文档顺序串行」**：PR-3（key 计算重构）与 PR-1（存储双轨）改同一
  函数簇，分两个 PR 意味着 `intentKeyForPath` 签名变两次、W15 测试改两次，且中间态
  （PR-3 合入而 PR-1 未合）写入侧与查询侧口径不一致。合并为一个 PR 反而满足
  「能独立上线/回滚/一次 review 完」三条测试。
- **放弃「意图文件按 agentId 分文件」（PR-2 原案）单独做**：C2（子代理并发覆盖）的根因
  就是一会话一文件 + 子代理共享父 sessionId，按 agentId 分文件顺带修掉它，不需要
  额外的锁机制。
- **放弃「用锁保护意图文件写入」**：锁引入死锁与残留锁清理问题（worktree GC 已经为
  锁付过学费，见 W13），temp+rename 原子写在单文件粒度上足够。
- **放弃「冲突检测改用 git merge-base 判断分支分叉」**：需要每个写操作 spawn git 子进程，
  在最高频路径上不可接受；`findCanonicalGitRoot`（纯 statSync/readFileSync）+ 分支名
  比对已够判据。
