# `/goal` 清除哨兵：删除写侧死代码，读侧降级为旧版文件只读兼容

## 决定了什么

`packages/cli/src/app.ts` 里的 `__CLEARED__` 哨兵：

- 删掉 `persistGoalState(clearMarker)` 参数及写入分支。全仓没有任何调用方传 `true`。
- 常量改名为 `LEGACY_GOAL_STATE_CLEARED_MARKER`，注释改成如实描述来历，替换原来那两处「/clear 会落哨兵」的承诺性注释。
- `restoreSession` 读侧的比较保留。v0.1.609 之前的 `/clear` 往会话文件里写过这个值，不比较的话它会被当成 JSON 解析，解析失败后同样跳过恢复，但会多打一条误导性的「goal state 恢复失败」warn。
- 官网 `website/use/plan-mode.md`「目标跨会话」一节改写：
  - 恢复最近会话的命令是 `-c`，不是 `--resume`；
  - 删掉「clear 后恢复不会带回旧目标」这个不成立的承诺，改为说明「旧目标随旧会话一起恢复」。

来历：`7752ffb6` 引入哨兵，当时 `/clear` 续写同一个 jsonl。`1121f4a6`（v0.1.609）把 `/clear` 改为「结束旧会话 + 开新会话」，同时删掉了 `persistGoalState(true)` 和另外三个归零快照调用，剩下的几块都没清掉。所以这是重构留下的残留，不是「从来没接线」。

## 放弃了什么（以及为什么不选）

- **按原设计重新接线（在 /clear 里写哨兵）**：插入位置不对时会静默失效。`clearConversation()` 第一步 `finalizeSessionStore()` → `endSession()` 会把 `currentFile` 置成 null（`store.ts:766`），之后 `appendMetadata` 开头就 `return`（`store.ts:741`）。要生效只能放在 finalize 之前，那样就是往旧会话里写「目标已清除」。可是被恢复的旧会话里，消息历史是完整的，单独抹掉目标，会形成「历史里有目标、`/goal status` 显示无目标」的分裂状态。这个语义目前没有产品依据。
- **连读侧比较一起删**：功能上看不出区别（解析失败也是跳过），但旧版文件会每次恢复都打一条假的「恢复失败」warn，误导排障。比较的代价只是一行，所以留着。
- **顺手修「clear 后直接退出，`-c` 回到 clear 前会话」**：根因在 `/clear` 加懒创建（`store.ts:422-428/755-758`）和 `loadLatest` 按 mtime 取文件的交互，影响面是整份会话，不只是 goal。不归本 PR 管，需要单独定 `/clear` 的产品语义。官网已如实写出这一行为。

## 拿什么证明它生效了

- 新门禁 `packages/cli/tests/app/goal-clear-sentinel-legacy-wiring.test.ts`（3 条）锁住三件事：写侧不复活、读侧在反序列化之前跳过哨兵、`clearConversation` 不调 `persistGoalState`。
- 变异自证：三种变异逐一施加，每种都让且只让对应用例变红（各 `2 pass 1 fail`），恢复后 `cmp` 与原文件一致。三种变异是：删除读侧 guard、在 `persistGoalState` 里重新写哨兵、在 `/clear` 里调 `persistGoalState`。
- `clear-rotates-session-wiring.test.ts` 5 条照旧通过。affected-tests 与 `make build` 的结果见 PR 正文。
