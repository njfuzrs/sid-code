# MCP 资源工具按「真的有资源」启用，没有资源时不占常驻 schema

## 决定了什么

`ListMcpResources` / `ReadMcpResource` 增加 `isEnabled()` 判据：只有当**某个已连接
MCP server 的 `resourceCount > 0`** 时，它们才进入 `definitions()` /
`activeDefinitions()` 发出的工具 schema。

- 判据落在 `MCPManager.hasResources()`（`packages/core/src/mcp/manager.ts`），
  遍历 `serverStates` 早退判断 `resourceCount > 0`；
- 工具侧 `managerHasResources()`（`packages/core/src/tool/mcp-resources.ts`）每轮
  重新求值，**不是注册时快照**——MCP 是异步连接的，注册时 manager 可能还没连上；
- 两个工具**不声明 `shouldDefer`**，保持「有资源时就是常驻可见」的语义。它们在
  `registry.get()` 里仍然查得到，历史上下文里的调用不会按名字找不到。

顺带把 `MCPManager` 的判据成本压到最低：早退遍历，不构造 `getAllResources()` 数组。

## 放弃了什么（以及为什么不选）

**放弃 A：按「配置里有没有 MCP server」启用。** 绝大多数 MCP server 只暴露 tools
（工具栏几十个），resources 原语很少用。30 天轨迹里 `ListMcpResources` 只被调用 1 次、
`ReadMcpResource` 0 次，但每个配了 MCP 的会话都要为这两个工具付 883 字节常驻 schema
和 2 个 strict 名额。按「有没有 server」启用等于几乎不启用。

**放弃 B：把这两个工具改成 `shouldDefer = true`（延迟加载）。** 延迟名单解决的是
「工具多到首轮放不下」，代价是每次要用都得先 `tool_search` 往返一次。资源工具本身
调用频次极低，但 `ReadMcpResource` 往往紧跟在 `ListMcpResources` 之后，再叠一层
tool_search 往返不值得。更关键的是：延迟名单是静态的，**有资源时它也会被藏起来**，
模型得先知道该搜什么才能搜到。`isEnabled` 表达的是「这个能力此刻存不存在」，
语义比「默认藏起来」准确。

**放弃 C：注册时求值一次快照。** MCP 连接是异步的，快照会让「先注册、后连上有资源的
server」这条路径永远看不到这两个工具。代价是会话中途 `false → true` 时工具数组变长，
插入点之后的工具区缓存失效一次——但**只在 server 确实有资源时发生一次**，且与 MCP
工具晚到属于同一类已知代价。

**放弃 D：顺手把 `resources` 的刷新做成周期性。** `refreshResources()` 只在连接时跑
一次，server 后期新增资源不会反映到 `resourceCount`。这是既有行为，不在 D7 范围内；
如果将来要做，应该单独一个改动，因为它会改变 `getStatus()` 的语义和重连逻辑。

## 拿什么证明它生效了

**G1 单测**（`packages/core/tests/tool/mcp-resources-enabled.test.ts`，5 个用例）：

- manager 未就绪 / 无资源：两个工具不在 `activeDefinitions()`、也不在 `definitions()`；
- 工具仍在注册表里（历史调用不 404）；
- 有资源（fake manager `hasResources() === true`）：两个工具进 `activeDefinitions()`，
  且 `isDeferred()` 为 false（常驻，不是延迟）；
- 每轮求值：真实 `MCPManager` 注入 `resourceCount = 3` 后，同一 registry 下一轮即可见；
- `MCPManager.hasResources()`：无 server false、0 资源 server false、任一 server 有资源 true。

```
bun test ./packages/core/tests/tool/mcp-resources-enabled.test.ts
→ 5 pass / 0 fail
```

**端到端双向验证**（真实 `sid-code` 二进制 + 本地 stdio MCP server）：

| 场景 | 首轮 `request.tools` 数量 | 含资源工具 |
| --- | --- | --- |
| 只暴露 tools（`resources/list` 返回 -32601） | 21 | 否 |
| 暴露 3 个资源 | 23 | 是（两个都在） |

验证方式：`SID_CONFIG_DIR` 指向临时目录，`./sid-code -p "只回复两个字：收到"` 跑一次，
读 `trajectories/sessions/<id>/raw.jsonl` 里 `request.tools`。反向用例同时证明
MCP 确实连上了、`isEnabled` 判据真的在按资源的实际存在与否切换。

**其余门禁**：

```
bun run affected-tests:run        → 1803 pass / 0 fail
bun test ./tests/tool/prefix-collision-gate.test.ts ./tests/tool/builtin-tool-meta.test.ts \
        ./tests/tool/unknown-keys-coverage.test.ts ./packages/core/tests/tool/content-provenance.test.ts
                                  → 70 pass / 0 fail（D2 前缀门禁与 content-provenance 哨兵）
```

**没有跑 `bun run smoke`**：本次改动只影响首轮工具 schema 的成员资格，不改 hook / 预算 /
结构化输出 / 工具执行链；G2 回放用例的断言不涉及这两个工具的 schema 内容。
