# 工具输出清理改为按「过期程度」批量提交，不再只看窗口剩余

## 决定了什么

新增第五条本地清理通道 `context/stale-tool-output.ts`（纯函数 `planStaleToolOutputClear`），由 `ContextManager.getCleanedMessages` 每轮调用一次，决策落进 `staleClearState`，之后每轮逐字节重放。

判据只看结构性事实，不看窗口大小、不看模型名：

- 一条工具结果之后，模型已经又进行了 **K=8** 个工具轮（按「含 tool_use 的 assistant 消息」计，一轮并行多个调用只算一轮）；
- 不是活跃文件（被 edit/write 过）的**最近一次** read。更早的 read 是改动之前的旧版本，照样清理；
- 不在当前 turn 内，单条不少于 500 字符，不是持久化引用；
- 工具分类沿用 microcompact 的白名单：只读工具（read/grep/只读 bash…）替换为带重读指引的占位；有副作用的工具（edit/write/写型 bash）只保留前 200 字符摘要，并提示「不要为找回内容而重跑」；未知工具和 MCP 工具原样保留。

**攒批**：待清理的释放量累计 **≥ N=20k token** 才一次性提交。没到门槛就不动前缀，这一轮缓存照常命中。

接线要点：

- 已有稳定占位的块互相豁免（masking / 冷清理 / 大输出清理 / 本通道），不会被改写两次；`applyColdCacheClear` 的豁免集合也加入了本通道；
- 释放量记入 `tokenFreedTracker`（策略名 `staleToolOutput`），Footer 和压缩档位都会扣除；
- 前缀改写来源新增 `stale_clear`（`SendMutationCause`），落到 `prefix_break.cause`；同时发出 `ToolResultCleared{stage:"stale_clear"}`，aftereffect 报告可据此统计「清理后同签名重跑」；
- 生命周期与 coldClearState 一致：压缩、截断、setMessages、clear 时统一清空。

北极星：朝「更省（上下文）」方向，**牺牲的是缓存命中率**（每次提交让一段前缀失效一次）；如果占位不够用，还可能导致重读（伤「更准」）。下一段给出了这两项代价的量级。

## 放弃了什么（以及为什么不选）

| 方案 | 否决理由 |
|---|---|
| 遮罩阈值从 78% 调到 40% | 仍然是按「窗口剩余」判断：1M 窗口下 40% 是 40 万 token，常见任务到不了；128k 窗口下又会过度清理。阈值本来就不该和窗口挂钩 |
| 大输出门槛从 30,000 字符降到 3,000 | 每轮都会有新输出越过门槛，KEEP_RECENT 窗口每前移一次就改写一次前缀，缓存每轮失效 |
| 每轮清理所有过期结果，不攒批 | 每轮都改写前缀，等于每轮缓存失效 |
| 复用 microcompact（`preserveRecentCount` 按条数算） | 它按「最近 N 条消息」保护，与工具轮无关，也不豁免活跃文件；而且只在 hard 档的管线里运行，状态不粘性 |
| 清理思考链 | 违反 DeepSeek 协议（上一份报告 §6 已否决） |
| 活跃文件的所有 read 都豁免 | 同一文件改前改后读了好几次，旧版本已经被最新的 read 覆盖，留着纯属浪费 |
| K/N 做成环境变量 | 先不开放旋钮。常量写死在模块顶部，校准后改常量走 PR，避免出现「本机调过、CI 没调」的两套行为 |

## 拿什么证明它生效了

**离线回放（上线前校准，2026-11-12）**：数据为本机 `~/.sid-code/trajectories/sessions` 中 11 月的 DeepSeek 主会话，按 `session-summary.json` 的 `model` 筛选，共 323 个，其中 ≥40 轮的 228 个。对每个会话的 `messages.json`，在每条 user 消息处截断，模拟一次 `getCleanedMessages`，并把已提交的决策冻结后带入下一轮。

| K / N | 末态工具结果释放 p50 / p95 | 工具结果占（不含 system/思考）p50 前 → 后 | 每会话提交 p50 / p95 / max | 额外缓存未命中占累计输入 p50 / p95 / max |
|---|---|---|---|---|
| **8 / 20k（采用）** | 59.2% / 78.7% | 71.4% → 50.8% | 2 / 3 / 4 | **0.29% / 0.81% / 2.66%** |
| 8 / 10k | 65.8% / 80.4% | 71.4% → 45.0% | 3 / 6 / 8 | （未跑） |

- 「额外缓存未命中」的算法：每次提交时，从第一个被改写的块到当时末尾的全部消息 token 计为一次重建；累计输入 = Σ每轮（45k 固定开销 + 当时投影的 token）。这是**上界**估算，因为没有扣掉「这些 token 本来就是新增、不会命中」的那部分。按 V4-2 的门槛（命中率下降 ≤ 3pp），**p95 0.81pp、最坏 2.66pp，均在门槛内**。
- N 取 10k 时多释放约 6pp，但提交次数翻倍。20k 与遮罩的 `MIN_PRUNABLE_THRESHOLD` 同一量级，采用 20k。
- 回放脚本在 `/tmp/f4replay/replay.ts`，会话结束后不保证保留。核心逻辑已写在上面，复算时只需按这个逻辑重写。

**单测与变异自证**：新增 `packages/core/tests/context/stale-tool-output.test.ts`，共 11 用例，覆盖判据、攒批、活跃文件、白名单、并行轮计数、粘性重放、记账、生命周期、与冷清理不叠加。三项变异各自先改坏、确认变红，再恢复回绿：

1. 去掉攒批门槛（`entries: candidates`）→ 2 用例红；
2. 去掉重放（删 `applyFrozenClearState(cleaned, this.staleClearState)`）→ 1 用例红；
3. 不豁免活跃文件 → 1 用例红。

**还没证明的（上线后用 V4 验收）**：回放只能看到上下文侧的收益和缓存代价的上界，**看不到模型会不会因为占位而重读**（V4-3 同文件重复 read 占比，基线 9.8%），也看不到会不会多走轮次（V4-4 turns p95）。这两项要用 `sc-dev` 跑同类任务至少 7 个，与基线对比。如果 V4-3 上升，优先调大 K，不要放宽白名单。
