# 新底座提供 TerminalWriteContext，退出时清进度条与 tab 状态（契约 O3，B9 / T7.2b）

## 决定了什么

- 新增 `packages/tui/src/components/TerminalWriteContext.ts`。`ink.tsx` 的 `render` 给子树套这层 Context，值是实例上的 `writeRaw`：经 autoBind 绑定，身份在实例生命周期内不变，直写 stdout，不等帧，非 TTY 也写。`render-port/next/hooks.ts` 原来那个没人提供值的空 Context 改成导出这一个。
  - 之前 next 上 `useContext(TerminalWriteContext)` 恒为 `null`。所以 CLI 的 `useTerminalIntegration` 在「忙 → 闲」时的 BEL + OSC 777 通知在 next 上**整条静默不发**，没有任何报错。
- TTY 卸载时，在恢复光标之后写两条清除序列。规则来自黑盒对拍旧底座（D-5），覆盖 10 种环境，逐字节一致：
  - OSC 9;4 进度清除 `ESC]9;4;0;BEL`：**固定 BEL 终止**（kitty 下也不换 ST），**不包裹**（tmux 下也不包），和之前写没写过进度无关，和终端是否支持进度条（WT_SESSION、VS Code 版本）也无关。
  - tab 状态清除：复用 T7.2a 的 `tabStatusSequence(null)`，随终端选终止符，按 tmux / screen 包裹。`SID_DISABLE_TAB_STATUS` 非空时不写（`0` 也算），和之前写没写过无关。
  - 非 TTY 两条都不写。
- 这两条相对其余模式恢复（鼠标、扩展键、focus、bracketed paste、显示光标）的顺序**不在本任务里对齐**。next 现在还没写那几段，顺序归 X3（T7.1b）。
- S14 从 2 步扩到 6 步：标题 + tab 忙、标题去 ANSI + tab 空闲、经原始写入口发 OSC 9;4 三种状态、`useTerminalIntegration` 的「忙转闲」通知（BEL + OSC 777）、OSC 8 超链接（进程内切到 iTerm2）、tab 状态经 tmux 包裹。基线用 legacy 重新生成，**前两步与旧基线逐字段相同**。
- 新契约测试 `terminal-progress.test.tsx`（11 条），夹具 `fixtures/osc-unmount-app.tsx` 跑在子进程里，因为旧底座卸载时 `writeSync(1)` 直写 fd 1。SPEC 的 O3 测试列从 S14 改指向它。

## 放弃了什么（以及为什么不选）

- **新增一个 `useTerminalNotification` / `progress()` 端口 API**：CLI 至今没有任何地方发 OSC 9;4，只用 `TerminalWriteContext` 写 BEL 和 OSC 777。端口面按 `SURFACE.md` 只有 `TerminalWriteContext` 这一个符号。为一个零调用方的 API 定契约，就是在造「防线全在、调用全 0」。S14 里的进度三态是经原始写入口写的，验的是「写入口能把它原样送到终端」。
- **退出清除做成「写过才清」**：探针证明旧底座是无条件清（从没写过进度也清）。改成有条件，会让 next 的 S1–S6 在「(退出后)」少 1 条 OSC 9，与基线不一致。
- **O3 契约比整段卸载字节**：第一版这么写，10 条全红。红的原因是 next 还缺 X3 那几段模式恢复，等于让 O3 替 X3 红。改成只比 OSC 9 / 21337 片段，并对 legacy 和 next 各自断言实测字节，防止两边一起错。
- **断言原始写入早于首帧**：测试环境 `NODE_ENV=test` 同步出帧（R13），在 bun test 子进程里先后顺序反过来了，单跑脚本时又是另一个顺序。这个先后不属于 O3，改成断言「恰好写一次」（同时证明身份稳定，effect 不重跑）。
