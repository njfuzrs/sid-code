# settings.monitor：企业开关与阈值只收紧（FIX-7）

## 决定了什么

把方案 §5.4.5 / §10.6 承诺但一直没落地的 `settings.monitor.*` 接上（issue #703，方案 §L1）。

- `config/settings/types.ts` 新增 `monitor?: { enabled?: boolean; maxConcurrent?: number; maxTimeoutMs?: number }`；
- 新增 `config/monitor-policy.ts`：**逐来源**读 `settings.monitor`，数值取 `Math.min`、`enabled` 取 `&&`（任一来源 false 即关闭，缺省 true）；
- `task/monitor-task.ts` 新增 `getMaxConcurrentMonitors()` / `getMaxMonitorTimeoutMs()` / `getDefaultMonitorTimeoutMs()`，一律 `min(代码常量, 配置)`——**常量是上限，配置只能收紧**；
- `MonitorTool.isEnabled()` 读 `enabled`；`call()` 头部再拦一次（挡 schema ≠ 执行层不可达，与 bundled skill 同形态）；
- `ToolSearchTool.selectTools` 补一道 `registry.enabled()` 过滤：被 `isEnabled` 挡掉的工具不再回「已激活」，改回「已被策略禁用」；
- 工具描述里写明「企业管控只对本轮之后新启动的监控生效，已在运行的不受影响」（方案 §6.1 要求）。

## 放弃了什么（以及为什么不选）

1. **直接用 `getSettings()` 的合并结果做 min** —— settings 合并链是「后者覆盖前者」，`policySettings` 排最后。企业写 `maxConcurrent: 99`（显式允许）时会盖掉用户写的 `2`，再与常量取 min 得到 4，用户的收紧值被静默放宽。改为逐来源读、分别取 min。
2. **在 `config/monitor-policy.ts` 里同时与代码常量取 min** —— 会让 config 反向依赖 task 才能拿到常量，形成循环依赖；常量是 task 领域知识，收敛逻辑留在 `monitor-task.ts`。
3. **给突发阀 / 总量阀也加配置项** —— 方案只要求并发与期限两个字段。那两个阀是防雪崩常量（10 秒 40 行、累计 60 条），不提供配置出口就是不提供「调没」的可能。
4. **在工具执行器统一检查 `isEnabled`** —— 会让「调用时报错」的语义扩散到所有工具（许多工具没实现 isEnabled）。monitor 在自己的 `call()` 头部拦一次，范围最小、文案可解释。
5. **只改 L1 点名的三个文件、不碰 `tool-search.ts`** —— 测试暴露出精确名快路径（`registry.get()`）不过滤 `isEnabled`：企业关闭后 `tool_search("monitor")` 仍回「已激活 1 个工具」，是假信息。复用 `registry.enabled()` 的既有判据（不另写一份 isEnabled），改动 13 行。
6. **企业配置收紧时杀掉已在运行的 monitor** —— 只对新启动的生效。杀掉在途监控会让模型已经挂上的等待源凭空消失（D4 同类误判）；写进工具描述与本文。
