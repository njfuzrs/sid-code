# 热缓存清理恢复：OSS 归档核对通过才删，promote / rollback 自动回暖

## 决定了什么

对应 B46 P3。P1 之后每个版本发布即归档到 OSS（回读校验），P2 之后 nginx 对热缓存未命中的版本文件回源 OSS。
服务器版本目录从此只是热缓存，清理可以恢复：

- `RELEASE_KEEP_VERSIONS` 默认 0 → 5（0 仍是「不清理」）。
- 窗口外、非指针指向的目录，删除前逐个跑 `scripts/archive-ops.sh verify`：每个平台 tarball 与 `.sha256`
  都在归档里（逐 key 精确比对）、归档 `.sha256` 与服务器逐字相同（下载回来 `cmp`）、对象大小一致。
  判据只认输出里的 `__ARCHIVED__ <ver>` 整行，其余一律保留并打印「未归档，拒绝清理」。
- 回暖与清理同 PR：`release.sh --promote` 与 `rollback.sh` 在原有目录检查前先跑 `archive-ops.sh warm`，
  服务器没有该版本时从 OSS 拉到同盘隐藏暂存目录、`sha256sum -c` 通过后 `mv` 原子落位。
  回暖失败不单独 fail，落到原有的 `__NO_DIR__` 报错。

## 放弃了什么（以及为什么不选）

- **比 ETag 代替下载 `.sha256`**：分片上传的 ETag 不是 MD5，换上传方式就会静默失效。`.sha256` 只有百来字节，下载比对更直接。
- **整包下载 tarball 做 sha256 再删**：每次清理要拉 5 × 40MB × 候选数，只为删一个服务器副本。大小 + `.sha256` 逐字相同已覆盖「对象缺失 / 被换」两类真实风险；字节级完整性由 P1 归档时的回读校验保证。
- **核对失败时跳过核对继续删**：这会把热缓存清理退回到 P0 之前的永久删除。宁可多留一个目录。
- **promote / rollback 指向回源 URL 而不回暖**：指针指向的版本承接全部用户流量，不该靠回源扛；回暖后与旧路径完全同构，后续检查不用改。
- **把 verify / warm 并进 `archive-version.sh`**：那个脚本的唯一职责是「写归档」，成功标记语义单一；读路径另起脚本，两者的成功判据互不混淆。

## 拿什么证明它生效了

- `bun test ./tests/release-archive.test.ts ./tests/release-channel.test.ts ./tests/release-flow-contract.test.ts`：130 pass / 0 fail。
  清理块从 `release.sh` 抠真实 `if…fi` 执行，远端 `archive-ops.sh` 也是真脚本（ossutil 换 fake）：
  全归档 → 删；未归档 / `.sha256` 不同 / 大小不同 / ossutil 整体失败 / 核对脚本上传失败 → 全部保留。
- 变异自证：把清理里的 `grep -qx "__ARCHIVED__ $d"` 换成 `true` → 5 条红。
- ECS 真跑（只读 + 临时目录，2026-10-08）：`verify` 线上 0.1.602 → `__ARCHIVED__`；`warm` 0.1.603 到 `/tmp` 临时根 3.4s，
  与线上目录 `diff -r` 只多一个 `provenance.json`；重跑 → `__WARM_PRESENT__`；`warm 9.9.9` → 失败且不留目录。
- 线上真实清理（服务器 5 个版本、窗口 5 → 下次发版后 6 个才首次触发删除）与 `rollback.sh` 回暖，留到下次发版后验收。
