# 记忆 T1–T3 两周复查：T2 默认值改 3、容量判据脱离文案、扫描边界锁行为

## 决定了什么

对《记忆写入与召回横向剖析》第五部分（PR #518）做两周窗口复查后的收尾改动：

- **T2 节流默认值 1 → 3**：`resolveMemoryExtractInterval` 的缺省从 1 改为 3（`packages/core/src/memory/extract/extractor.ts`），env / settings 仍可覆盖。依据是 2026-11-02 ~ 11-15 的 872 次真实 `ran` 事件：平均每次写入 0.97 条，N=3 把 fork 调用压到约 1/3；抽取 fork 每次看完整对话，晚写不丢上下文，且收尾 `drainPending` 对积压补跑一次。
- **`readIndexCapacity` 的 `truncated` 不再只依赖截断文案**（`packages/core/src/memory/index-capacity.ts`）：改为「文案命中 **或** `entries >= INDEX_MAX_ENTRIES` **或** `bytes > INDEX_MAX_BYTES`」。原因是文案由 `INDEX_TRUNCATION_NOTICE` 动态生成、内嵌上限数字，常量一改旧 MEMORY.md 里的文案就匹配不上，T3 的 `index_full` 拦截会静默失效。
- **扫描上限的边界显式化**（`packages/core/src/memory/scan.ts`）：`scanMemoryFiles` 是「先按 mtime 取最新 `SCAN_MAX_FILES` 条、再交给调用方按类型重排」，与索引的「全量按类型排序后截断」候选集不同。加注释说明这是 I/O 保护上限的固有边界，并新增测试锁住当前行为。
- **补 3 条测试**：常量变更后旧文案失效靠上限兜底、字节超限判截断、目录 201 条时清单只覆盖最新 200 条。

## 放弃了什么（以及为什么不选）

- **只保留文案判据（不加上限兜底）**：否决。2026-11-15 复查发现 `INDEX_TRUNCATION_NOTICE` 内嵌 `200 条 / 25KB` 两个数字，改任一常量都会让旧索引的文案匹配失败，而窗口期（改常量 → 下次 `writeIndex`）内 T3 拦截整体失效。`readIndexCapacity` 已经算出 `entries` / `bytes`，兜底是零额外 I/O 的一行判据。
- **把 `SCAN_MAX_FILES` 调大 / 让抽取清单自己枚举全量**：否决。它是 I/O 保护上限（每次抽取要读 ≤N 个文件头），调大只多一点 I/O 但会把「目录膨胀」的成本转嫁给每轮抽取；且 `STORE_MAX_ENTRIES=200` 的归档会把目录稳态压回 200，错位最多 1 条、每次写入后即收敛。
- **新增 G2 回放用例覆盖 interval / catch_up**：评估后不做。抽取 fork 是后台异步任务，replay 的请求 index 会与主会话交错，用例稳定性差；单测已断言 `skip_reason` / `catch_up` 字段，真实运行样本见下。
- **T2 默认值改 2（折中）**：否决。影子数据是 872 次 `ran` 的完整样本（不是小样本估算），N=3 的收益与写入延迟已有明确口径；N=2 的收益约为一半，没有数据支撑它更优。

牺牲点：T2 改 3 后，记忆写入最多延迟 2 个 end_turn（此前每轮写）。收窄的是「写入及时性」，换「更省」；收尾补跑兜住长会话尾巴，但短会话（<3 个 end_turn）完全依赖 `catch_up` 那一次。

## 拿什么证明它生效了

- `bun test ./packages/core/tests/memory/extract-quantify-t1-t3.test.ts`：**24 pass / 0 fail**（新增 3 条）。
- 变异自证 2 条：① 把 `truncated` 改回只看文案 → 2 条兜底测试红；② 把 `slice(0, SCAN_MAX_FILES)` 改成 `slice(0, 1000)` → 边界测试红。均已还原，恢复后 24 pass。
- `bun run affected-tests:run`（cli / config / memory 三个目标）：**4734 pass / 9 skip / 0 fail**（308.9s）。
- **造数据验证零生产样本路径**：用隔离配置（`SID_CONFIG_DIR=/tmp/sid-interval-sample`）+ `SID_CODE_MEMORY_EXTRACT_INTERVAL=3` 跑一次真实会话，`telemetry/events.jsonl` 产出两条此前从未出现的形态：
  - `skipped{reason:"interval", seq:1, interval:3}`
  - `ran{catch_up:true, seq:1, interval:3, written:0}`
  证明 `loop.ts` → `extractor` → telemetry 的端到端接线在 interval>1 时确实走到节流与收尾补跑（此前生产 901 条事件全是 `interval:1`，这两条路径零样本）。
- 复核数据（2026-11-15 实跑）：`orphan_count` 11-07 的 61 → 11-15 的 50（遥测口径，持续下降）；`index_full` 累计 41 次（11-03 ~ 11-12，全部 `via=save_memory`）；`memory_extract` 901 条中 `ran` 870 / `skipped` 31（`main_wrote` 27、`in_flight` 4，无 `interval`——默认值改后才会出现）。
