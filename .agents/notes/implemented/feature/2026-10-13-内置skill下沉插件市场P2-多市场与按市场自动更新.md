# 内置 skill 下沉插件市场 P2：多市场、按市场隔离缓存、同名拒装、按市场自动更新、plugins-release.sh

## 决定了什么

- **多市场**（方案 §6.2 第 1、4 条）：`market.ts` 新增 `resolveMarkets()`，顺序固定为企业 `company`（由 backend.url 推出）→ 官方 `sid-code` → `extraKnownMarketplaces`（字段名对齐 CC）。官方市场默认注册，`officialMarketplace: false` 可以关掉。官方地址固定为 `https://www.sid-code.cc/plugins/index.json`，可用 `SID_CODE_OFFICIAL_MARKET_URL` 覆盖（镜像或测试用）。
- **市场名由本机配置决定，不再取 index 自报的 `name`**。缓存文件名、`installed.json` 里的 `market.name`、插件标识符后缀，全部用这个名字。P1 之前所有市场都叫 `DEFAULT_MARKET_NAME`，这正是缓存互相作废的根因（§2.4）。改完之后缓存按市场名天然隔离，缓存逻辑本身一行没改。保留名（`sid-code` / `company` / `local` / `builtin` / `inline`）不能被 extra 占用；与已注册市场地址相同、非 url 源、明文 http 的条目会丢弃并告警。
- **官方市场永不携带设备凭据**，即使它和 backend.url 同源。
- 三个新 settings 字段 `extraKnownMarketplaces` / `officialMarketplace` / `pluginMarketplaceAutoUpdate` 已登记到 `SECURITY_SENSITIVE_FIELDS`。项目级 settings 不能加市场，也不能开自动更新：否则 clone 一个仓库就可能装上别人的 hooks。
- **同名插件只能装一份，跨市场同名一律拒绝并提示**（方案 §6.2 第 3 条给了两个选项，这里选了「检测并拒绝」，`installed.json` 的键不改）。理由：插件运行时的命名空间是 `/插件名:skill名`，两个同名插件本来就不可能同时加载，把键改成 `name@market` 只会把冲突从安装期推迟到加载期。拒绝发生在下载之前。`installed.json` 格式没变，旧条目不需要迁移。
- `/plugin update` 回到每个插件**自己安装时的那个市场**比对版本。来源市场已从配置里移除、或地址变了，就跳过，不会去别的市场找同名插件。
- `/plugin market [--market <名>]` 默认列出全部市场，单个市场失败只在自己的段落标 ✗。只有所有市场都失败才返回 ok:false，单市场下保持 P5 的语义（401 → ok:false）。新增 `/plugin marketplaces`。列表按 index 里的 `kind` 标注 skill 包 / 插件（§5 的「顺带小改动」）。
- 指定历史版本时，制品地址优先取 `versions[i].artifact`，没有就把当前地址里的版本段换掉。原来硬编码 `artifacts/<name>/<ver>`，静态市场带 `.tar.gz` 后缀，这个写法会 404。
- **按市场自动更新**（`plugin/auto-update.ts`，在 App.tsx 启动时 fire-and-forget）：
  - 官方市场默认开，企业 / 额外市场默认只提示。`pluginMarketplaceAutoUpdate: {"company": true}` 按市场名覆盖，管理员可以在 managed settings 里下发；
  - 只升级已装插件，从不新装；
  - index 里登记的 hooks + MCP 算一个指纹，安装时记进 `market.execSignature`。新版本指纹不同，或市场没给组件清单、无法判断，就不静默升级，只提示；新版本完全不带 hooks / MCP 时允许升级；
  - 只有缓存、拉不到最新目录时不动。没装任何市场插件时不联网。用目录锁防止多实例同时升级。
- **`scripts/plugins-release.sh`**：
  - 门禁：G1 工作区干净；G2 `HEAD` 是 `origin/main` 的祖先（先 fetch，判据照搬 `release.sh --promote`）；G3 版本不可覆盖（本地 tag、远端 tag、远端 index、服务器上的制品文件四处都查）；G4 新版本必须高于线上最新版本；
  - 发布顺序：制品先传到临时名，在服务器端复核 sha256，再 `mv -n` 落位；
  - index 替换：先比对线上 index 的 sha256 是否仍是读取时那份（防并发发布），然后 `cp` 一份 `.prev-<时间戳>`，再 `mv -f` 原子替换，最后回读校验；
  - 回滚是指针操作：把 `.prev-*` 拷回 `index.json`，模型与 `rollback.sh` 一致。
  - 合并逻辑在 `plugins-pack.ts` 的 `mergeIntoIndex` / `--release-prep` 里，可以单测。
- 服务器目录默认 `/var/www/html/plugins`（`PLUGINS_DEPLOY_PATH`），**刻意不放进 website-deploy.sh 管理的站点目录**：那边每次部署都 rsync `--delete` 到新的 release 目录，插件放进去会在下次官网部署时整体消失。

## 放弃了什么（以及为什么不选）

- **`installed.json` 改成 `name@market` 做键**：见上。运行时命名空间不允许同名插件共存，改键只是把报错推迟，还多一次存量迁移。
- **市场名沿用 index 自报的 `name`**：两个市场能自称同名，缓存与安装标识就会互相冒充。P1 前的 bug 就是这个形态。
- **自动更新复用本体的 `settings.autoUpdate`（off / notify / auto）**：本体与插件的信任模型不同。方案要求按市场区分默认值，一个全局开关表达不了「官方开、企业关」。
- **按 manifest 文件内容判断 hooks 有没有变**：需要先下载新包。index 里的组件清单是上架时服务端算好的，比对它零下载。代价是信任 index，但 index 本来就是 sha256 的信任根。
- **自动更新给出确认弹窗**：启动路径上的后台任务不该打断输入，所以只给一行瞬时提示，用户自己去跑 `/plugin update`（那里会展示组件清单）。
- **plugins-release.sh 用 rsync 整目录同步**：`--delete` 会误删历史制品，而且做不到「先校验再切 index」的顺序。
- 本 PR **没有**真实跑一次 `plugins-release.sh` 上传到生产：那是 P3「生产真实走一遍」的内容。nginx 的 `/plugins/` 是否指向 `PLUGINS_DEPLOY_PATH` 也属于 P3，脚本末尾的冒烟检查会提示这一点。
