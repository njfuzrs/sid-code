# 长会话按键延迟 P1：屏幕行跨帧复用 + 补全菜单溢出时叠画

排查报告 `docs-research/sid-code/bugfixes/todo/20261030-长会话输入框打字粘贴上屏延迟-排查报告.md` 的 PR3 / PR4 / PR5，合成一个 PR。
P0（#499：横向裁剪快路径 + 启动警告不吞首键）已在 main。

## 决定了什么

**PR3：视口之上的历史行复用上一帧屏幕缓冲**（`packages/tui/src/output.ts`、`renderer.ts`）

- `Output.getScreen(reuse)` 先按行登记「写到这一行的写操作序列（对象身份）+ 每次写入时栈顶裁剪框（对象身份）」。
  与上一帧逐项相同的行，直接把上一帧那一行的 `chars/widths/styles/links/wrapEnd` 拷过来，不执行操作；
  一个写操作的落点行全部可复用就整条跳过（省掉 split、裁剪、transformer、tokenize）。
- 复用状态按根节点存在 `renderer.ts` 的 WeakMap 里，只给动态区，上游 Static 不用。
- 判据只认**对象身份**：blit 缓存 `replay(dy=0)` 推的是同一对象；节点重渲、纵向平移都会产生新对象，那些行一律重写。
  所以不变量是「同一个写操作对象 + 同一个裁剪框对象 → 同一行单元」，前提是 transformer 是纯函数。

**PR4：补全菜单在帧溢出时叠画在输入框上方的历史行上**（`packages/tui/src/ink.tsx`、`dom.ts`、`components/Transient.tsx`、`render-node-to-output.ts`、`packages/cli/src/ui/InputArea.tsx`）

- `<Transient float>`：外层零高锚点 + 内层绝对定位 `bottom: 0`。叠画与否由底座在 `calculateLayout` 之后判定
  （`layoutFloatingTransients`），只在形态需要翻转时多算一次布局。三个条件：不算浮层的帧高 ≥ 视口行数；
  叠画区整块在视口内；上方放得下。
- 叠画态先用空白铺满浮层矩形，菜单行比历史行短时不露出底下的字。
- `hasMountedTransient(root, {inFlowOnly: true})`：**叠画态的浮层不算「在流浮层」**。这一条是端到端实测才找到的：
  真实 TUI 里关菜单的同一帧输入区会少一行，帧变矮，如果叠画态还算浮层，diffFrame 照旧判成「关浮层」走整帧重画。
- 只有补全菜单用 `float`；`DialogSwitch` 的对话框保持在流布局（可能比视口还高，叠画放不下）。

**PR5：`getCursorVisualPosition` 接收已算好的视觉行**（`packages/cli/src/ui/text-buffer.ts`、`InputArea.tsx`）
两个调用点都先算过一遍 `getVisualLines`，现在直接传进去。

## 放弃了什么（以及为什么不选）

- **PR3 B 档（只落视口窗口）**：要改 full reset、补空行、选区、帧 diff 四处依赖，并逐项对拍冻结基线，超出一次 review 的体量。
  A 档落地后按键延迟已经降到 10ms 左右，剩下的大头是 yoga 布局和 diff，不在 getScreen。
- **PR3 按行内容 hash 判断可复用**：hash 碰撞会让 scrollback 里某块历史静默不刷新，测试很难撞到。对象身份零误判，代价是
  纵向平移的行（如 History 头部插入）不复用，那是少数帧。
- **PR3 只按「行在视口之上」复用、不比操作序列**：视口之上的行在流式输出、历史追加时也会变（内容平移），这么判会出错。
- **PR4 方案二（只在被顶上去行数 > 0 时 reset，不带 `ESC[3J`）**：每开关一次菜单 scrollback 多一份约 9 行重复内容，越积越多；
  `ESC[2J` 不带 `3J` 在不同终端行为不一（见报告 #4）。
- **PR4 让 CLI 自己算帧高决定要不要 float**：CLI 拿不到帧高，硬算等于复刻一遍布局；判定放底座、在布局之后做，CLI 只声明「可以叠画」。

**牺牲了什么**：PR3 牺牲「更准」的一点余量（不变量依赖 transformer 是纯函数、replay 推同一对象）；PR4 在菜单打开期间
盖住视口最后几行历史，选中复制那几行会复制到菜单文字（都是打开期间的暂时状态，关闭后恢复）。
