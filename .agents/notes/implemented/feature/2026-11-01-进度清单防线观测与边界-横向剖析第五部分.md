# 进度清单防线：观测补字段与边界修正（横向剖析第五部分 T1–T7）

## 决定了什么

- **T1**：`TodoReworkDetected` 补 `hits: [{ item, file }]` 和 `hitCount`。`item` 截断到 200 字，`file` 不截断（它是归因主键）。
- **T6**：逐个核对压缩出口。loop 内 7 处置位齐全，注释写的「8 处」不成立。真正漏掉的是**手动 `/compact`**：它在两条用户消息之间执行，碰不到 `LoopState`，下一条消息重建时三个重注入标志恒为 false。修法是把三连赋值收口成 `markPostCompactReinject`；手动压缩打会话标记，由 `queryLoop` 入口消费。哨兵测试锁住「loop.ts 不许出现裸置位」。
- **T2**：todo_gate 在 `hasRunningBackgroundTasks() || hasPendingNotifications()` 时不续跑，改发一条中性说明，按未完成项签名去重，不消耗续命预算。写法与「只剩 blocked」分支一致。
- **T3**：新增 `SID_DISABLE_TODO_GATE` / `SID_DISABLE_TODO_NAG` / `SID_DISABLE_TODO_REWORK`，默认仍开，只认字面 `1`，与 `SID_DISABLE_PROMISE_NUDGE` 同一约定，注册表 `toggle` 已登记。NAG 开关不管压缩后重注入（那是信息丢失兜底，不是催促）；REWORK 开关只压提醒，事件照发并带 `suppressed: true`，关闭臂里仍能数出分母。
- **T5**：前置核实结论是**不清空**。microcompact / masking 只改 tool_result，不动 `tool_use.input`；snip / 截断 / 摘要是整条删除。所以只要扫描还能找到 `todo_write`、且距离小于 `TURNS_SINCE_WRITE`，压缩后的补贴就是重复注入，跳过。被删掉（`Infinity`）时照常补贴。标志的消费点前移到读取处，保持 pending_consume 只回落一处。
- **T7**：`TodoProgressAdvanced` 补 `completedDelta`（可为负）和 `contentChanged`。事件名不改，注释写明「每次成功写入都发，不代表有推进」。

## 放弃了什么（以及为什么不选）

- **T4 统一计数口径：本 PR 不做**。方案排期本来就把它放在最后，原因是它属于事件 schema 变更，要等 21 字段语义文档和分析脚本对齐。倾向的仍是选项 B（改名 + `-1` 改 `null` 加 `reason`）。
- **T6 没有补「第 8 处」**：loop 内没有缺口，硬补一处等于造一个假置位点。真正的缺口在 loop 外，所以改成会话标记。
- **T2 没有改成「后台任务时延长预算」**：延长预算仍然是在催模型，而这时候下一步的主语是后台任务。漏拦的代价有上界：任务完成后通知会唤醒循环，闸门届时会再判一次。
- **T3 没有用 settings 键**：A/B 臂要按进程切换，env 最直接。settings 要等真有用户想常关时再加。
- **T5 没有否决**：方案预期「大概率否决」，但核实下来前提不成立（参数没被清空），所以照做。

## 拿什么证明它生效了

- 每项都有接线测试驱动真实 `queryLoop`（`packages/core/tests/query/todo-plan-part5-wiring.test.ts`、`post-compact-flags.test.ts`），每项都做过变异自证：
  - T1：删掉 `...reworkEventData(...)` → `Expected 1 / Received undefined`
  - T2：去掉后台任务条件 → `Expected 0 / Received 3`（todo_gate_retry）
  - T3：去掉两处开关判断 → 两条用例都红
  - T5：判定函数恒返回 false → 冗余判定用例变红
  - T6：去掉入口消费 / 一处 `markSessionCompacted` → 哨兵变红
  - T7：去掉 `...todoWriteDelta(...)` → 用例变红
- T3a 门禁（`one-shot-flag-invariant.test.ts`）的扫描下限从 40 调到 20：字面置位从 45 收口到 27，这是本次契约变更带来的。补了一条断言，确认三个标志的置真点落在 helper 里。
- 上线后要看的信号：
  - `todo_gate_retry` 与 `running_background_tasks=true` 同时出现的次数应归零（T2）
  - `TodoReworkDetected.data.hits` 按 file 分桶，看返工是否集中（T1）
  - 压缩后补贴里「`todo_write` 仍在 8 条之内」的那一类应消失，可从 `NoProgressNagInjected.afterCompact=true` 的 `turnsSinceLastTodoWrite` 分布核对（T5）
- trade-off：T2、T5 在「更准」方向可能漏拦或漏注一次，换来「更省」（少一轮续跑 / 少一次重复注入）。两者都有兜底：T2 有通知唤醒后的再判，T5 在清单真被删掉时照常补贴。
