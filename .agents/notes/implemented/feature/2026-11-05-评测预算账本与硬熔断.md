# 评测预算账本与硬熔断：账本按池记账、坏行 fail-closed、null 成本按单题上限算

## 决定了什么

落地《评测接入 CI/CD》§5.4 第 6 条与 §7.1 D2（任务 T19）。新增两个文件：

- `scripts/eval/lib/eval-budget.ts` —— 账本读写 + 熔断判定 + null 成本折算（纯函数层）
- `scripts/eval/eval-budget.ts` —— CLI：`check` / `record` / `summary`
- `tests/eval/eval-budget.test.ts` —— 36 条断言（含 CLI 子进程）

账本落 `~/.sid-code/eval-gate/ledger.jsonl`（经 `sidHomePath("eval-gate", …)`，所以 `SID_CONFIG_DIR` 对它生效）。一次运行一行，append-only。

**四条写死的口径**（每条都在源码注释里写了理由，这里只记结论）：

1. **判据是 `本月已花 + 本次上限 > $150`，严格大于**。所以 `$149 + $1 = $150` 允许，`$149 + $2 = $151` 拒绝。§5.4-6 原文就是 `>`，没有改成 `>=` 的余地。
2. **「本月」按写入端的本地自然月**，`ts` 写成带本地偏移的 ISO 8601，月份取前 7 位。写入那一刻「这次算哪个月」就定死了，读的人换时区也不会漂。
3. **坏行 fail-closed**：账本里有一行解析不了就判 `INVALID` 并点名行号，不放行。读不懂账本 = 不知道本月已花，放行等于熔断失效。
4. **成本为 null 的题按单题上限（默认 $1.8）记，不按 0**。`effectiveRunCost()` 把折算量（`assumedUsd` / `nullCostTasks`）单独报出来，事后不能把它当真实花费引用。

**账本行新增 `pool: "routine" | "oneoff"`**。D2 把预算分成例行 $150/月 和 P2 一次性 $130（原文「单独批，不占例行预算」）。只记一个总数的话，T15 跑完 k=3（≈$78）就吃掉例行额度的一半，后面的 L2 会被一条本该无关的预算拦住。月上限只汇总 `routine`；`oneoff` 照常记账但不参与判定。

**CLI 退出码分三档**：`0` 允许/成功、`2` 拒绝开跑（`INVALID`）、`1` 用法错误。拒绝与用法错误必须分开——前者等人做决定（补预算或修账本），后者是脚本自己写错了。`2` 沿用 `run_fingerprint.py` 的 INVALID 约定。

**「零模型调用」是结构性的，不是靠承诺**：`withBudgetGate(decision, run)` 在拒绝时返回 `{ ran: false }`，`run` 一次都不执行。模型调用只能发生在 `run` 里。

边界：本 PR 只交付账本与熔断能力。接进 `scripts/eval/release-gate.sh` 是 T20 的事（T20 依赖 T12/T17/T19）。

## 放弃了什么（以及为什么不选）

- **放弃给 CLI 加 `--monthly-cap-usd` 开关**。硬熔断的全部意义是「不能被开跑的人随手放宽」；给了开关，$150 就只是一个默认值。lib 的 `checkBudget({ monthlyCapUsd })` 保留参数供单测造边界，CLI 不暴露。
- **放弃「坏行跳过并继续」**。这条最容易被当成「更健壮」：一行坏数据凭什么阻塞全部运行？但账本的唯一职责是回答「本月已经花了多少」，答案不完整时放行 = 熔断失效。本仓在 `evals/CLAUDE.md` §3.6 记过同一个形态（`null` 在下游被当 0 求和，低报 1.1%）。代价是账本坏了要人修——写进 reason 里点名行号与原因。
- **放弃用 UTC 月**。UTC 可复算但不符合「本月」的人类直觉：本机 UTC+8 在 11-01 02:00 跑的一次 L2（$26）会被记进 10 月，人看到的是「11 月已花 $0」。选了本地月，代价（月初 0–8 点归当月）写在源码注释与这里。
- **放弃「超了先跑完再判」**。D2 原文：「不做『超了先跑完再说』，否则上限只是一个数字」。
- **放弃把 `planned_cap_usd` 也计入「本月已花」**。计划上限不是花费；混进去会让一次 $40 的 L2 在跑之前就被记成花了 $40，与「实付」这个字段名矛盾。账本里两个字段并存，`actual_usd` 才参与汇总。
- **放弃复用 `packages/core/src/telemetry/usage-ledger.ts`**。那是产品侧的 token/成本账本（每会话一行、无预算池、无熔断语义、容错跳过坏行）。语义完全不同的两份账本共用一个文件，等于让「评测预算」跟着用户日常会话的花费一起漂。
- **放弃 Python 实现**（harbor 工具链是 Python）。`SID_CONFIG_DIR > SID_CODE_HOME > CLAUDE_CONFIG_DIR > ~/.sid-code` 这套优先级在 `packages/core/src/config/paths.ts` 有唯一权威定义，Python 侧复制一份就是第二个事实源（`paths.ts` 的文件头注释记着这份漂移已经坑过一次）。TS 侧直接 import `sidHomePath`，且 `tests/eval/` 天然被 `bun test` 与 `affected-tests` 覆盖，不用再按 `evals/CLAUDE.md` §4.1 给 `.py` 补一层 TS 门禁。
- **放弃在 `release-gate.sh` 里内联判定逻辑**。那个脚本还没写（T20），现在内联等于把判据埋进一个将来才会出现的 shell 里；先做成可测的库 + CLI，T20 直接调用。

## 拿什么证明它生效了

**单测**：`bun test ./tests/eval/eval-budget.test.ts` → **36 pass / 0 fail / 105 expect**。

**完成判据逐条对上**（T19 原文：「单测用 `SID_CONFIG_DIR` 隔离；账本写到 $149 再开跑必须被拒，且零模型调用」）：

- `SID_CONFIG_DIR` 隔离：`beforeEach` 把 `process.env.SID_CONFIG_DIR` 指到 `mkdtempSync(tmpdir())`，`afterEach` **恢复原值**（不是 delete，避免抹掉 bunfig preload 的兜底）；CLI 子进程通过 `spawnSync` **显式传** env。有一条专门断言 `ledgerPath()` 落在 sandbox 下。
- `$149` 拒绝：账本写 $100 + $49 两行 → `check --layer L2 --planned-cap-usd 2` 退出码 **2**，stdout 含 `$149.00` / `$151.00`。
- 零模型调用：CLI 拒绝路径下**账本逐字节不变**（`readFileSync` 前后比对）；库层 `withBudgetGate` 用计数 spy 断言 runner 调用次数 **0**。

**变异自证**（`evals/CLAUDE.md` §4.3；判据是「红的是哪一条」，不是「有东西红了」）：

| 变异 | 结果 |
| --- | --- |
| ① 熔断比较符 `>` → `>=` | 2 条红：`边界：$149 + $1 = $150 → 允许`、`oneoff 的花费不占例行预算`（都是靠 150 这个边界活着的断言） |
| ② 坏行 `corrupt.push(...)` 删掉（静默跳过） | 3 条红：`坏行进 corrupt 并点名行号`、`坏行 → INVALID(ledger-corrupt)`、`summary 遇到坏行退出 2` |
| ③ `assumedUsd += perTaskCapUsd` → `+= 0` | 4 条红：`null → 单题上限`、`负数/NaN 与 null 同档`、`全部为 null 时不返回 0`、`record 用 --costs-json 时按单题上限折算` |

每次变异后 `cp` 回备份并用 `shasum -a 256` 核对三个文件与变异前逐字节一致（实测 lib 恢复后 sha 与变异前相同：`42d95e5d…`）。

**CLI 冒烟**（真实执行，非单测）：

```
$ eval-budget check --layer L2 --planned-cap-usd 40      # 空账本
ALLOW layer=L2 pool=routine month=2026-11 spent=$0.00 planned=$40.00 remaining=$150.00
exit=0

$ eval-budget summary                                     # 记了 $100 + $49 之后
2026-11  例行 $149.00 / $150.00（2 次，剩 $1.00）

$ eval-budget check --layer L2 --planned-cap-usd 2    # ← 完成判据那条
INVALID(over-monthly-cap) ... spent=$149.00 planned=$2.00 remaining=$1.00
本月已花 $149.00 + 本次上限 $2.00 = $151.00 > $150.00，拒绝开跑
exit=2
```

**已知局限（如实登记）**：

- 并发不设锁。L2 由 launchd 单实例驱动，预期间隔 ≥ 数小时；两个 check 同时通过、两个 run 同时花钱的窗口在现设计下不存在。若将来 L1 与 L2 可能同刻开跑，需要加文件锁或「预留行」，那是新的决策。
- 账本行只在**跑完**写（D2 的「一次运行一行」）。进程在 record 之前崩掉的那次花费不会自动入账，需要 `record` 手工补记。这一点没在代码里做兜底，只在 reason/注释里点破——自动补记需要知道崩在哪一步，猜出来的数字比缺失更糟。
- 「零模型调用」的证明是**结构性**的（拒绝时 runner 不被调用），不是对真实网络的观测。这在单元层面是充分的（模型调用只能经由 runner），但真跑链路的零调用仍要靠 T20 的接线正确。
