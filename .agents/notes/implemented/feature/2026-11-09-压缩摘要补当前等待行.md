# 压缩摘要补「当前等待」行：让模型压缩后仍知道自己还在等什么

## 决定了什么

压缩把对话换成摘要，模型从此看不到「我在等 monitor m7 盯 PR #662」。登记表在进程内、不受压缩影响
（`listWaits()` / `hasPromisedWait()` 照常为真），但**模型的认知**受影响：它可能重复起一个盯同一对象的
monitor，或在 `task_stop` 前不知道自己还在等什么。所以有等待源时，把当前等待写进压缩摘要正文。

四处改动：

- `task/wait-registry.ts` 新增 `describeCurrentWaits(now?)`：取 `listWaits()`，每项用**已有的**
  `describeWaitSource`（面板 / reminder / 回执三处共用的那一份标签）拼上承诺后缀
  （deadline → `，最晚 HH:MM:SS`；terminal → `，结束即通知`；其余 → `，退出或转入静默时通知`），
  多条用 `；` 分隔。没有等待源返回 `null`。
- `query/compact/auto-compact-prompt.ts`：`CompactSummaryMessageOptions` 加可选 `waitLine`，
  `getCompactUserSummaryMessage` 把它拼在摘要正文之后、转录路径/保留消息提示之前。
- `query/auto-compact.ts`（自动压缩主路径）：调用处传 `describeCurrentWaits() ?? undefined`。
- `query/compact/partial-compact.ts`（手动 `/compact` 三条模式共用）：摘要消息正文追加同一行。

两条路径都只**读**登记表，不释放、不重登记——「压缩前后 `listWaits()` 结果相同」是验收项。
无等待源时两条路径都不输出这一行（绝大多数压缩没有等待源，恒加一行只会把「没有等待」也写成显式信号）。

## 放弃了什么（以及为什么不选）

- **不在 `runPostCompact` 里注入一条独立消息**。它是 auto / manual / reactive / collapse 四条压缩路径
  共用的收尾单一事实源，改一处就能全覆盖，看起来更省事。否决理由：方案要求「摘要里补一行」，
  而独立消息会让模型读到「摘要 + 又一条 unexplained 的 user 消息」两段；压缩摘要本身是一次性生成的，
  不像每轮前缀那样有缓存代价，没有理由把它拆出去。代价是手动 `partialCompact` 要单独改一处
  （它不经过 `getCompactUserSummaryMessage`），这两处已在测试里各自钉住。
- **不覆盖 reactive / collapse / snip 三条路径**。它们产出的不是 LLM 摘要正文：reactive 是本地
  snip 的描述、collapse 是分段摘要、snip 是纯裁剪，没有「摘要正文」这个落点；且它们都跑在
  prompt-too-long 紧急恢复里，往里加内容只会让本就紧张的空间更紧张。真要统一，应该另立方案
  把它们收敛到 `runPostCompact`，而不是在这次 L3 改动里顺手做。
- **不新增第四份等待源标签文案**。标签复用 `describeWaitSource`；只有「什么时候回报」的后缀是本函数
  自己拼的，且措辞与 `todo-reminder.ts` 里 `describeWaitLine` 的现有文案同形（那一个是私有函数，
  导出它会把 T2 reminder 的文案变成公共契约，风险大于收益）。
- **不把「当前等待」升级成常驻 system prompt 附件**。方案 §6.1 的风险栏已经点破：多一行会改变缓存前缀。
  放在一次性生成的摘要里没有这个问题；常驻附件则每轮都在前缀上，属于另一个取舍（更准 ↔ 更省），
  不在本次范围。
- **不改 `listWaits()` 的语义**。它内部会 `sweepExpiredWaits()`（本来就有的行为），压缩只消费结果。
  如果为了「摘要更准」在压缩路径上顺手释放过期等待源，就会把「压缩」变成一个有副作用的动作，
  正是验收项「压缩前后 `listWaits()` 相同」要防的。

## 拿什么证明它生效了

新增 `packages/core/tests/query/compact-current-waits-line.test.ts`（5 条，全部从真实入口进：
`autoCompact()` 与 `partialCompact()`，不直调内部拼装函数）：

- 自动压缩：登记 monitor 后压缩 → 摘要含「当前等待：」+ `describeWaitSource` 渲染出的那一项 + 「最晚 」；
  且压缩前后 `listWaits()` 的 `kind:id:description` 三元组完全一致。
- 自动压缩：无等待源 → 摘要不含「当前等待」。
- 自动压缩：monitor + 定时唤醒两个源 → 同一行里都出现，用「；」分隔（2 段）。
- 手动 `/compact`：摘要消息以 `[前段摘要]` 开头、含「当前等待」与监控描述，`listWaits()` 前后一致。
- 手动 `/compact`：无等待源 → 摘要不含「当前等待」。

变异自证三组（改坏 → 看红在哪 → 恢复）：

| 变异 | 改法 | 实测结果 |
| --- | --- | --- |
| A 删自动路径注入 | 注释掉 `auto-compact.ts` 的 `waitLine:` | 2 条 auto 用例红（「含描述」「多源」），3 条绿 |
| B 删手动路径注入 | `partial-compact.ts` 的摘要文本去掉 `waitLine` 拼接 | 1 条 manual 用例红，4 条绿 |
| C 无等待源也输出 | `describeCurrentWaits` 空集时返回 `当前等待：（无）` | 2 条「不含该行」用例红，3 条绿 |
