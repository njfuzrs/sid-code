# 发布归档 B46 P5–P7：versions.json 版本清单、update --list、I1 审计与回源冒烟门禁

## 决定了什么

- **版本清单是归档的派生物**：`scripts/manifest-ops.sh dump`（ECS 上，一次 `ossutil ls` + 全部 `.sha256` / `provenance.json`）→ `scripts/lib/release-manifest.ts` 在开发机生成 `versions.json` → `manifest-ops.sh publish` 原子写到指针层，并在 OSS `manifest/versions-<UTC>.json` 留只追加的审计副本。不读、不合并旧清单。
- 清单**不写通道**（以 `latest.txt` / `beta.txt` 为准，客户端自己标注）；`archive_since=0.1.602`，之前的 20 个 tag 进 `lost`（P4 裁决不重建）；0.1.582–0.1.599 区间自动带 `self-update-broken`。
- 序列化为**一个版本一行**的合法 JSON，install.sh 不依赖 jq/python3，靠 grep 那一行读 `known_issues` / `rebuilt`。
- 客户端 `packages/core/src/update/manifest.ts` + `sid-code update --list`；`--version x` 先查清单：不在 → 报不存在并提示 `--list`；在 `lost` → 报已丢失；**清单拉不到 → 直接交给 install.sh**（不拒绝、不降级）；指针指着但清单未收录的版本判为可装（清单可能比指针旧）。
- install.sh：显式 `SID_CODE_VERSION` 下载失败时提示 `--list`；装的版本低于 latest 时提示 `autoUpdate: off`，并打印 `known_issues` / rebuilt。只提示，不改配置。
- `release.sh --upload` 顺序：归档 → 回读校验 → **清单（失败只 warn）** → **I1 审计 + 最老已归档版本 HEAD 冒烟（失败即 fail，beta.txt 不动）** → beta.txt → 热缓存清理。另有单独入口 `--publish-manifest`、`--audit-archive`。
- P7：`website/start/install.md`、`website/use/auto-update.md` 改成「0.1.602 起全部可装、`--list` 可查、停留需关自动更新、0.1.599 及更早要重跑 install.sh」；`rollback.sh` 列表文案改成热缓存口径；`deployment.md` 补 bucket / RAM / 凭据 / 权限反向测试记录。

## 放弃了什么（以及为什么不选）

- **从服务器热缓存目录生成清单**：热缓存只有最近 5 个版本，`--list` 会只剩 5 行且看起来完全正常。只有归档知道全集。
- **审计读服务器上已有的 versions.json**：那份可能是上一次发布写的，等于拿昨天的照片证明今天没丢东西。审计一律从本次 dump 现生成。
- **清单发布失败即 fail**：清单是加速失败的展示用派生物，客户端在拉不到 / 拉到旧清单时都有正确降级；让它挡住发布链是本末倒置。反过来 I1 审计和回源冒烟守的是「任何打过 tag 的版本都能装上」这条承诺本身，所以它们是门禁。
- **审计放在发布收尾**：那时 beta.txt 已经写了，只能事后告知。放在写指针之前。
- **在 ECS 上用 python3 生成清单**：会出现第二份解析逻辑；服务器只取数，判定只在 TS 里有一份。
- **清单用缩进多行 JSON**：install.sh 就得引入 jq/python3 依赖，或者提示静默失效。
- **让 install.sh / 客户端替用户写 `autoUpdate: off`**：影响以后所有升级，是用户的决定。
