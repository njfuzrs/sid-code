# 记忆漂移与维护 T2/T3/T4 收尾：分位标注、锚点统计、dream 三道闸

Source: 漂移与维护-落地方案（2026-11-02）

## 决定了什么

方案（`20261102-07H2`）在 T1 落地后停了 9 天，T2 第 2/3 条、T3、T4 全部未开工，
`next_action` 要求的三件事（拍板分档、拍板锚点口径、重跑影子统计）一件没做。
本轮把剩余四项一次收完，并顺带补掉 T1 唯一遗留项。

**T1 遗留：`memory_guard.memory_type`（两条归档路径都带）**
`evicted_to_archive` 此前只有 `kind / via / scope`，答不出「被挤走的是不是 user」——
而 T1 整个改造就是为「user 不再被优先淘汰」服务的。本机 267 条历史事件证明这个维度
确实缺失（无法回溯分类）。

**T2-2：`annotateIndexAges` 从「超过 1 天」改成「索引里最旧的一批（30%）」**
影子统计（2026-11-07，11-15 重跑）的结论是任何固定天数档都不可达 ≤30%：
sid-code 库 ≥7 天占 55.1%、≥30 天占 0%，落在「一半都标」和「一条不标」两端。
改为按 `updatedAt` 排序取最旧 `floor(n × 0.3)` 条，用 **key 集合**而不是时间阈值
（同一批导入的同 `updatedAt` 条目会被阈值整批标上，占比一次冲破 30%）。
「1 天内不标」保留，与 `buildFreshnessWarning` 同判据。

**T2-3：`INDEX_FRESHNESS_NOTICE` 措辞同步**
从「标记越旧……越可疑」改成「带 ⏳ 的是最旧的一批（约三成），其余没标记**不代表是新的**」——
补上分位口径下最容易产生的误读：没标 ≠ 新鲜。

**T3：`memory_index_health` 增加 `anchor_referenced_count` / `anchor_dead_count`，
索引行不打 ⚠**
只做统计。理由：影子统计实测「全部失效」误报面 71%–97%（iam-studio-fe 单根判定 97%
是「整条记忆在讲别的仓库」），把 ⚠ 常驻进 system prompt 的代价远大于收益。
提取正则从 `scripts/` 搬进 `packages/core/src/memory/anchor-health.ts`，
脚本改为 import —— 两份正则各改一半是必然结局。

**T4-1：dream prompt 允许「只核对锚点」**
原文「不要为核实去查项目」与现实现冲突：`createExtractPermissions` 本来就放行
只读命令（`app.ts:5464`）。改成「允许只读检查引用的仓内路径是否存在，不要读源码内容、
不要跑 git」——接受现状而不是收紧，因为「路径已不存在」恰恰是判断记忆过时最便宜的信号。

**T4-2：`superseded_by` 边**
prompt 的 consolidate 阶段要求：被合并掉的条目先写 `superseded_by: <保留的 key>`、
只留一行 frontmatter、再写空正文。归档判据是 `parseInfo.emptyBody`（剥 frontmatter 后为空），
所以保留这行边不影响归档，归档区能看出「它被谁取代」。

**T4-3：dream 宿主侧损失闸门**
`runForkedAgent` 前快照顶层 `.md`（文本 + type），`finally` 里判「正文变空或文件被删」，
`user` 类型归档 >1 条 → 按快照写回、整次作废、warn。允许 1 条是因为「用户说过某条已过时」
这类合法删除确实存在，全禁会让 dream 无法收敛。
顺序刻意放在 `reconcileMemoryDir` **之前**：先回滚再重建索引，反了会先归档出一批孤儿。

## 放弃了什么（以及为什么不选）

- **分档标注（`⏳` / `⏳⏳`）**：能给出「多旧」的层次，但**不满足验收口径**。
  分档后「带任何标记的行占比」仍等于「≥7 天占比」（55.1%），p50 压不到 0.3；
  只有让「标记占比」本身成为被控量才行。符号层级留给需要的场景，本轮不做。
- **按库自适应 p70 阈值**：与分位方案等效（都是把占比钉在 30%），但多一个
  「阈值本身要随库重算并缓存」的状态，且解释成本更高（用户问「为什么这条标了」时，
  分位能答「因为它在本库最旧的三成里」，自适应阈值要答「因为本库 p70 是 12 天」）。
- **T3 进索引行打 ⚠**：误报 71%–97%。「零误报干扰」优先于「模型当场看见」，
  这正是方案自己列的第三个选项。
- **T3 多根解析（方案选项二）**：需要在 `MemoryStore` 里维护「仓库根候选集」，
  而记忆目录与仓库根不是一一对应（`--add-dir`、worktree、monorepo）。
  先只统计单根（`projectRoot`），等 `anchor_dead_count` 曲线证明值得再投入。
- **T4-1 收紧为禁 bash**：与现实现冲突（现状放行只读），收紧等于改权限面 +
  prompt 两处，且丢掉最有效的锚点检查能力。
- **T4-3 全禁 user 删除**：合法删除被一起禁掉，dream 会卡在「想删但不能删」，
  下一轮又列出来，反复空转。
- **阈值做成 settings 可配**：`INDEX_AGED_FRACTION` 是**指标口径常量**，不是用户偏好。
  做成配置会让「同一份索引在不同配置下有不同标注」，
  分母口径漂移是北极星明令禁止的（「分母比口径重要」）。

## 拿什么证明它生效了

新增 `packages/core/tests/memory/drift-maintenance-t2t4.test.ts`，**17 pass / 0 fail**。
关键用例是**造数据**的边界（真实库凑不出这些形态，等生产数据等于永远不验）：

- 100 条 → 恰好标 30 条，且是 updatedAt 最小的 30 条
- 4 条 → 标 1 条；3 条 → 0 条（floor 到 0，小库不制造噪声）
- 40 条同 `updatedAt` → 标 12 条（时间阈值实现会标 40 条，这条专门钉住 key 集合实现）
- 锚点：全部不存在算 dead、部分存在不算、多根任一命中算活着、空根返回 0/0
- dream：1 条 user 放行、2 条拒绝、非 user 批量归档不拒绝、文件被删也算归档、
  精炼（正文变短）不算归档

受影响的既有测试同步更新（**契约有意变更**，不是改断言凑绿）：
`read-side-drift-p0.test.ts` 的 4 条年龄断言（口径从「>1 天」变为「最旧 30%」）、
`sc07-memory-p0-p1.test.ts` 的 finally 接线窗口（600 → 2000 字符，因 T4-3 插在前面）。
实跑：`read-side-drift-p0 + sc07` **42 pass / 0 fail**。

门禁：`bun run format` / `format:check` / `lint`（0 warning 0 error）/
`typecheck:gate`（62/62，无新增）/ `make build`（自检全过）。

两个**在 worktree 里失败、在父仓 main 通过**的测试已举证与本次无关：
`tests/build/rules-paths-scope-nonempty.test.ts`（worktree 路径布局导致 `git ls-files`
解析不到归属目录）、`tests/build/no-real-trajectory-writes-runtime.test.ts`
（同一成因，且不 import 本次改动模块）。两者在父仓 main 上单跑 3 pass / 0 fail。

影子统计（2026-11-15 重跑，证明「单档不可达」的结论比 11-07 更强）：
