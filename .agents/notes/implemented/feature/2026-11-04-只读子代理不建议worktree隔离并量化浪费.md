# 只读子代理不建议 worktree 隔离，并把「建了没用」量出来

会话 `20261103-213816-f5beebde` 复盘方案（`docs-research/sid-code/bugfixes/todo/20261104-会话f5beebde复盘-流迭代器泄漏与额度误判等六项-落地方案.md`）的 O1 / PR6。

## 决定了什么

**1. 工具描述把「只读任务不要传 isolation」写在模型看得到的每一处**（`packages/core/src/agent/tool.ts`）

- `description()` 正文末尾加判据，并点名 explore / plan / verify；
- `inputSchema()` 里 `isolation` 参数的 describe 同步加同一句；
- `usageGuide()` 新增一条「什么时候传 isolation=worktree」。

三处都要，因为它们是三条独立通道：模型读工具清单时看 description，读参数定义时看 schema description，
系统提示词里的「### sub_agent 工具使用指南」段单独拼 usageGuide（`system-prompt.ts`）。
缺任一处，就会有模型从那条通道**只看到「可以隔离」、看不到「只读不要传」**。

**2. 加一条 `SubagentIsolationUnused` 事件，先量出浪费有多常见**（新增 `packages/core/src/trace/isolation-telemetry.ts`，
接线点在 `agent/tool.ts` 的 `setupIsolation` cleanup，`packages/cli/src/app.ts` 注入 sink）

- 判定：子代理结束时对该 worktree 调 `WorktreeManager.countChanges`，`changedFiles === 0 && commits === 0`
  即「建了没用」，落一条事件。字段：`agent_type` / `description` / `worktree_name` / `lifetime_ms` /
  `changed_files` / `commits`。
- **判据复用 `countChanges` 而不是另写一套**：它与 `remove()` 的「无改动才删」同源。两套判据必然漂移，
  漂移后事件会和真实删除行为对不上——那种数字比没有数字更糟。
- `countChanges` 返回 `null`（git 出错）时不发：宁缺不错，别把「不知道」记成「零改动」。
- 前台 / 后台共用 `setupIsolation`，所以两条执行路径都被覆盖；`setupIsolation` 多收一个 `agentType` 参数
  （两个调用点都传 `params.type`），否则事件里没有「哪类子代理在浪费」这个最关键维度。
- 走模块级 sink（`setIsolationUnusedTraceSink`，App 在 collector 就绪后注入）而不是给 `SubAgentTool` 穿线：
  与 jit / file-freshness / skill / task-lifecycle / subagent-cost 同一模式——cleanup 闭包拿不到 collector
  （它是 App 私有），而工具先注册、collector 后就绪。测试用 `setIsolationUnusedTraceSink(null)` 复位。

**3. 一周后的判定入口（人工查询，不做成自动指标）**

```bash
grep -h '"event":"SubagentIsolationUnused"' ~/.sid-code/trajectories/*/events.jsonl \
  | jq -r '.data.agent_type' | sort | uniq -c
```

按 `agent_type` 分布决定要不要做更强的约束：`explore` / `plan` / `verify` 占比高 = 工具描述没劝住，
需要机制层拦截；`task` 占比高 = 正常写类子代理「碰巧没改」，不该当浪费处理。

## 放弃了什么（以及为什么不选）

- **懒创建 worktree（首次写操作时才建）**：读操作会在主工作区和 worktree 之间切换视图。主工作区有未提交
  改动时，同一个子代理前后读到的内容不一致——语义变化远大于这点创建开销。
- **按 prompt 关键词（「只读」）自动忽略 isolation**：本仓禁止按措辞硬编码判定的老教训，换个说法就会漏。
- **按 `AgentDefinition.readOnly` 自动清掉模型传的 isolation**：`readOnly` 描述的是工具集边界，不等于
  「这次不会写」——`verify` 是只读类型但能跑 bash，`task` 也可能只是探查。静默改写模型入参还会让
  frontmatter 声明的默认 isolation 语义分叉。方案明确要求「先量再决定」，这一层留到有数据之后。
- **直接把埋点塞进 `WorktreeManager.remove()`（或让它返回改动数）**：remove 是 fail-closed 的数据保护路径，
  改它的契约会波及 exit-worktree、GC、team 等全部调用方。改为在 cleanup 里**先**做一次 `countChanges`、
  再照旧 `remove`——多一次 `git status`（子代理收尾路径，量级毫秒），换零语义漂移，值得。
- **用方案原文说的「残卷的 `changedFiles`」作判据**：`SalvageCollector.changedFiles` 只记工具写文件路径
  （`extractMutatedPath`），漏掉 bash 写文件、`git commit`、「写了又删」。它与「worktree 是否真的白建」
  不是同一个问题，而且子代理成功结束时根本没有残卷。改用与删除判定同源的 `countChanges`——这是与方案
  的一处事实差异，判据方向一致（零改动 = 浪费），实现口径更准。

**牺牲了什么**：子代理收尾路径多一次 `git status`（只为埋点）；`SubagentIsolationUnused` 只覆盖
`sub_agent` 工具的 `isolation`，`workflow` 的 `agent({isolation:'worktree'})` 走 `sub-agent-runner.ts`
自己的 worktree 路径，未接这条埋点——要覆盖它得再穿一条线，等真有数据需求再说。

## 拿什么证明它生效了

新增测试 `packages/core/tests/agent/subagent-isolation-unused.test.ts`（9 条）：

- 命中方向：同步零改动 → 恰好一条事件，断言 `changed_files=0` / `commits=0` / `agent_type` /
  `description` / `worktree_name` 形如 `agent-<8 hex>` / `lifetime_ms >= 0`；后台零改动同样落一条。
- 不命中方向：真有改动 → 0 条；没传 isolation → 0 条。
- 健壮性：sink 未注入时清理照常完成、子代理结果不是 error；三处工具描述都含判据；事件名常量与字符串一致。

**变异自证**（CLAUDE.md 要求，看它报了什么不只看退出码）：把判据从
`changes.changedFiles === 0 && changes.commits === 0` 放宽成 `changes !== null`，重跑：

```
(fail) O1：... > 有改动的隔离子代理 → 不落事件（否则事件变成噪音）
  expect(received).toHaveLength(expected)
  at subagent-isolation-unused.test.ts:151
 8 pass / 1 fail
```

恢复判据后 `9 pass / 0 fail`。说明这条断言不是恒绿。

**门禁结果**：

- `bun run affected-tests:run` → 4455 pass / 9 skip / 1 fail。唯一失败是
  `isolated-subagent-cwd.test.ts > 未绑定 cwd 时不出现隔离提示`，按 CLAUDE.md 三条证据判定与本改动无关：
  ① 该测试不 import 本次任何改动模块（`grep isolation-telemetry|agent/tool.ts` 无命中）；
  ② 在父仓 main 上单跑该文件 12 pass / 0 fail；
  ③ 成因明确——该用例断言「进程 cwd 不在 worktree 内时系统提示不出现【隔离环境提示】」，而本次测试进程
  cwd 就是 `.sid-code/worktrees/subagent-isolation-unused`，失败输出里提示的「根目录」正是本 worktree。
- 相关既有测试：`subagent-background-isolation.test.ts` + `worktree/w19-w27-defects.test.ts` → 29 pass / 0 fail。
- `make build` → exit 0，产物自检五项全绿。
- 另外六道静态门禁全绿：`lint`（0 warning / 0 error）、`format:check`、`lint:boundary`、
  `lint:command-system`（四道）、`lint:legacy-tool`（棘轮 58/58）、`typecheck:gate`（64/64，无新增）。

**没有证明的**：一周后的触发率要等真实会话数据，这条事件只是把分母建起来；
「工具描述能否劝住模型」在单测里无法验证，只能看后续 `SubagentIsolationUnused` 里只读类型占比是否下降。
