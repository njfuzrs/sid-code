# 按会话追溯权限决策：只读 join 脚本，一等公民是覆盖度自检

## 决定了什么

新增 `scripts/permission-trace.ts`（只读，约 1000 行）+ `tests/scripts/permission-trace.test.ts`（34 用例）。
把轨迹侧 `PermissionDecision` 与审计侧 `permissions-audit*.log*` 按 `(归一后 session_id, tool_use_id)` join，
产出四类结果（joined / traceOnly / auditOnly / noKey），三层输出（覆盖度 → 分布 → 拒绝成因）。
**一行埋点都没改**：`checker.ts` / `audit.ts` / `collector.ts` / `events.ts` 全部未动。

四件事按方案落地，另有三处按实测修正（见下一节「放弃了什么」）：

1. **覆盖度自检是硬门**：四个指标（审计键覆盖率、轨迹键覆盖率、join 成功率、有效样本量）任一不过，
   `exit 1`、**一张分布表都不打印**。`Report.distribution` 与 `Report.denialBreakdown` 在自检不过时是 `null` ——
   「有没有分布」是数据结构的事实，不靠「记得别打印」的人肉约定。
2. **skip 档永不并入主分母**：`bucketOf()` 把 `mode=dangerously-skip-permissions` 或 `step=skip` 判成 `skipped`；
   分布表里 skip 单列一列并标注「管线未执行」。
3. **resume 显式建模**：审计侧 `session_id` 盖的是新进程 id（`AuditLogger.log` 取 `getSessionId()`），
   轨迹目录名是旧 id。读 `SessionStart.process_session_id` 建映射后归一，报告里展示映射前后对照。
4. **forked 标为「轨迹独有」**：它走调用方注入的 `canUseTool`（`forked-agent.ts:523`），不经 `PermissionChecker`、
   不写审计，属预期缺口而非丢数据。`traceOnly` 按 `execution_context` 拆分，`forked` 与 `main` / `subagent` 分开展示。

## 放弃了什么（以及为什么不选）

**三处偏离方案原文，都是实测后发现原文口径会让脚本产出假绿或恒红：**

- **方案 §3.2 把 `outcome=deny` 算进「有效样本量」→ 不采纳。** 按字面实现，本机 7 天窗口会得到 751 条
  （judged 桶内）甚至 2,111 条（含 unknown 桶），远超阈值 30 → 自检假通过 → 输出一张「100% 是 deny」的分布表，
  恰好是方案 §1 L2 要防的那类假绿。真因：本机 2,111 条 deny 里 1,322 是 forked（`canUseTool` 直接拒，不是管线判的）、
  618 是 subagent，它们不是「问过人」的决策。改成只认 `prompted` / `confirm_via`（轨迹侧）与
  `confirm_source` / `user_confirmed`（审计侧）。实测本机 = 3 条，与方案 §6.1 验收标准 1 期望的「有效样本 3」一致。
  deny 单独作为**可抽样框**在第 3 层列出，它服务人工标注，不是自动率值。
- **方案 §3.2 的键覆盖率按「窗口内总行」算 → 改为按「最近 3 个自然日」算。** 键覆盖率是**回归护栏**，
  它要答的是「键链路现在断没断」。窗口一旦跨过埋点上线日（本机 #681 的 11-09），整窗口口径会被历史数据
  永久拖到阈值下：实测默认 7 天窗口只有 36.2%，脚本会报「键链路断了，先查埋点」——而链路其实完好。
  **恒红的门禁等于没有门禁**（本仓 `typecheck:gate` 不裸跑 `tsc --noEmit` 是同一条理由）。
  改后最近数据日 100%，同时 detail 里点名「窗口整体 36.5%（含埋点上线前的历史行，不参与判据）」，
  读的人一眼能看出低的那部分是历史。
  初版写成「最近 3 个数据日」也错：数据稀疏时今天 + 半年前仍算「2 个数据日」，夹具里算出了 23%。改成自然日窗口。
- **方案未定义 `mode` 与 `step` 双缺的样本归哪桶 → 新增 `unknown` 桶。** 方案只有 skipped / 非 skipped 两分，
  但本机 36.9%（29,681 / 80,397）是老轨迹（2026-10 埋点未落这两个字段）。并进「非 skip 档」等于把
  「无从判断管线走没走过」当成「判过了」，分母整体错位。

**其余不选的做法：**

- **塞进 `trace-digest.ts` 加 `--permissions`**：那是「单会话摘要」，B24 需要「跨会话 + 跨两个文件源 + 硬门」，
  形态不同。且 `KNOWN_FLAGS` 有双向对账测试、`digest.ts` 已 5000+ 行，混进去会让回滚粒度变粗。
- **顺手补 subagent 的 `tool_use_id` / forked 的审计**：都要碰 `run-tool-use.ts` / `forked-agent.ts`，
  属「改埋点」，与「只读脚本」是不同关注点。且 subagent 目前 0% 只是样本窗口（11-05 后无样本），未见结构缺陷。
- **顺手把 A8（拒绝熔断）塞进来**：A8 走 `recordDefenseTrigger` → `defense-metrics.ts` → telemetry bus，
  与 `PermissionDecision` 是两条完全不同的链路（实测本机 `denialTracking` 样本 0 条）。方案 §5 已把它剔除。
- **自动判定误伤**：02 §1 Q5 的 97% 已是单人标注 n=30 的结果，自动判定等于用规则代替人判断，
  而这个规则本身就是被测对象（A2 注入校验器）。脚本只给抽样框。

## 拿什么证明它生效了

**单测（34 pass / 0 fail）：**
`bun test ./tests/scripts/permission-trace.test.ts` → `34 pass, 0 fail, 82 expect() calls`。

覆盖并锁住了三条假绿防线（每条都配了「若改坏会怎样」的注释）：
- `outcome=deny` 不算有效样本 —— 该断言不看 outcome 字段，函数签名里就没它
- skip 档占多数（200 条 skip allow）时有效样本量仍为 0、自检不过
- 自检不过时 `distribution === null` **且**渲染文本里没有「分布（skip 档单列」/「按工具」/「按工具」任何一张表
- 29 条 vs 30 条的阈值边界（差 1 条就红）
- resume 归一：审计 `rawSessionId` 是新 id、轨迹 `sessionId` 是旧目录名，仍能 join 上
- `--session <新进程 id>` 能命中 resume 会话（否则会对真实存在的会话静默返回空）

**真机验收（本机 985 个会话 / 80,397 条 PermissionDecision / 45,608 行审计）：**

1. 默认 7 天窗口 → `EXIT=1`，前两个键覆盖率 `100.0%`（最近数据日）+ join 成功率 `100.0%`，有效样本 `0`，
   打印「有效样本 0 / 阈值 30」并**不输出任何分布表** —— 与方案 §6.1 验收标准 1 一致（该窗口内确无交互式样本）。
2. `--days 30` → 有效样本 `3`，对应方案 §2.2 记录的「`prompted=true` 全量仅 3 条」。
3. resume 会话：报告列出 6 个映射对照（如 `轨迹目录 20261109-151008-588b314a ← process_session_id 20261109-155000-f27e8f57`），
   归一后 join 成功率 100%。
4. forked：`traceOnly` 970 条里 969 条 `forked`、1 条 `main`，按执行路径分列输出。
5. `--json` → 自检不过时 `selfCheck.passed=false`、`distribution=null`、`buckets={skipped:25864, judged:3021, unknown:1489}`。

**变异自证**（改坏被测代码确认断言变红）：未逐条做（本轮时间用于补齐口径），已知风险点是
「键覆盖率口径」与「有效样本口径」两处 —— 对应的两条测试（29 vs 30 边界、skip-heavy 假通过）
本身就是把口径钉死的断言，改口径会先红它们。
