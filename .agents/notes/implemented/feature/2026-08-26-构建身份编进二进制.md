# 构建身份编进二进制：commit 成为产物的唯一身份（方案 PR-A）

## 决定了什么

**版本号不是身份，commit 才是**，而且身份必须**跟着字节走**。

起因是一次实测事故（2026-08-26）：`package.json` 是 `0.1.601`，tag `v0.1.601` 打在
**8月21**，而 8月26 合入的 429 重试修复与权限修复都不在里面
（`git merge-base --is-ancestor <fix> v0.1.601` 失败）。`make build` 刻意不 bump 版本号，
所以「重新构建」不会改变 `artifact_for()` 挑中的那个路径 —— 于是
「跑评测验证本轮修复」静默跑成了「跑 5 天前的代码」，
**分数正常、日志正常、`run-meta.json` 里的 `sid_code_version` 也正常，没有任何一处报错**。
`git describe` 才能看出那道缝：`v0.1.601-59-g454cf79c` —— 一个版本号后面挂着 59 个提交。

本 PR 只做「把身份编进去 + 能读出来」这一层（方案 §3 + §4），
**三道门禁（G1 评测前置 / G2 发布通道 / G3 分支包）不在本 PR**，是后续 PR-B/PR-C 的事。
这么切是刻意的：门禁的判据全部建立在「产物能自报 commit」之上，
先把这一层做实并验证过，门禁才有东西可读。

落地的东西：

- `packages/shared/src/build-info.ts` —— 格式与解析的**唯一事实源**（8 个字段、
  两条正则常量、三态 `dirty`）。
- `scripts/build-info-line.sh <origin>` —— 构建期取数 + slug 化，
  三个构建入口共用一份。origin 是闭集 `local|ci|release`，越界直接 exit 2。
- `sid-code --build-info [--json]` —— 放在 bootstrap 零导入快速路径里
  （和 `--version` / `--self-check` 同层）。
- `Makefile` / `release.sh` / `exec-swebench.sh` 三处构建入口全部带上 `--define`。
- 两个测试文件、19 条用例，每条都配了变异自证注释。

三条**改回去不会报错、只会静默失去价值**的约束，都写进了代码注释：

**① 默认值前缀必须与真值不同**（`SIDCODE_BUILD_V0_NONE|` vs `SIDCODE_BUILD_V1|`）。
`--define` 是编译期字面量替换，所以 `process.env.X ?? "默认"` 会被 DCE 折叠掉；
但把默认值存进一个独立的 `const` 之后它**会留在二进制里**（实测真产物里 `grep -c` = 1）。
靠「前缀不同」而不是靠「DCE 会帮我们删掉它」—— DCE 是优化行为，随 bun 版本可能变。
破坏后的形态是：**门禁把每个产物都读成 `commit=unknown`，一律退化到 mtime 兜底，
看起来还在跑**。

**② `commit` 必须是第一个字段。** 值域字符类漏一个字符时症状是
「从截断点往后静默丢字段」——实测漏 `@` 时 `builder=a@b.com` 被截成 `builder=a`，
其后的 `origin` 整个丢掉，而 `origin` 恰恰是 G2 的判据。
把最关键的字段放最前面，坏的方式至少可预期。

**③ 不动 `getVersion()` / `getRawVersion()`。** 把 commit 拼进版本号会误触发
`app.ts` 的网关定价全端点强制刷新（它用版本号做刷新水位线），
还会污染 `trace/collector.ts` 的 `app_version`（北极星按 release 归因的键）。
实测 `--version` 输出前后一字不变。

## 放弃了什么（以及为什么不选）

**旁路 `build-info.json` 文件** —— 最省事，但**挡不住本方案要防的场景**：
`docker cp` 只 cp 二进制、`SWE_ARTIFACT` 可以直接指向裸二进制，
旁路文件与产物一分离，身份就没了。身份必须在字节里。

**JSON 格式编进去** —— 实测会被 bun 的字符串处理在字节流里切碎，
`grep -o` 取不出完整结构。单行 `|` 分隔可以一次取全（34MB tar.gz 流式抽取 0.108s）。

**只保留 `--build-info` 这一条通道** —— 通道 B（字节嗅探）**不是备选而是必需**：
最需要门禁的那个场景恰好执行不了产物（arm64 宿主 + `linux-x64-baseline` 产物）。
本次实测在 arm64 上执行 x64 产物 → `exec format error`，通道 A 在那里根本不可用。

**把 `--build-info` 声明进顶层 parseArgs** —— `docs-gen-reference` 的对账门禁要求
help 里的 flag 要么在 parseArgs 里、要么进白名单。选了白名单（附理由）：
进 parseArgs 意味着完整 CLI 会"接受"它，然后**静默忽略**这个请求 ——
而「看起来正常但其实没量到」正是本方案要消灭的形态。

**把 release.sh 的构建挪到 bump 提交之后**（那样 `dirty` 就真是 false、
`commit` 就真是 bump 提交，判据能写得很干净）—— 不做。
当前顺序（洁净门禁 → bump → 构建 → 提交 → tag）是
「构建失败时不留下 bump 提交」这个性质的来源，`track_for_rollback` 建立在它之上。
所以本 PR **顺着事实写**：发布产物的 `dirty` 必然是 true、脏文件恰好只有 `package.json`，
因此额外记一个 `dirty_files` 字段让 G2 能断言"脏的只有它"。
照直觉写成 `dirty == false` 会 100% 误拦每一次真实发版，然后被人加 flag 绕过 ——
**误报会训练人绕过门禁**，这条判断贯穿整个方案。

**用 mtime 判新旧**（上一轮的 `warn_if_stale_artifact`）—— 两个方向都会错：
`cp` 会把 mtime 重置成"现在"（假阴性，正是门禁本该抓的场景），
docs-only 提交会推进 HEAD 时间（假阳性）。commit 编在字节里，两个洞都不存在。

## 拿什么证明它生效了

**实测（本机 arm64 mac，bun 1.3.14）**：

1. **A1 通道 A**：`./sid-code --build-info` 输出 8 字段全齐、`--json` 可解析；
   `--version` 输出 `sid-code v0.1.601 (TypeScript)` 前后一字未变。
2. **A2 通道 B**：`grep -a -m1 -o` 从 93MB 裸二进制取回**完整那一行**（含 `@`、`+`、`/`），
   与通道 A 逐字段相同。tar.gz 流式抽取 0.108s。
3. **A7 跨架构**（这一条是通道 B 存在的全部理由）：编出
   `linux-x64-baseline` 产物 → 在 arm64 宿主上执行 → `exec format error`（通道 A 不可用）
   → 同一份字节嗅探成功取回身份。
4. **T13 不可伪造**：`SID_CODE_BUILD_INFO=<别的 commit> ./sid-code --build-info`
   仍输出编译期值。这是身份能当身份用的前提。
5. **默认值确实留在产物里**：`grep -ac 'SIDCODE_BUILD_V0_NONE|'` = 1，
   偏移 62747664 vs 真值 62744914 —— 它无害**只是因为前缀不同**，
   不是因为 DCE 删掉了它。约束 ① 的直接证据。

**门禁的变异自证**（每一条都真的改坏跑过一遍，不是"机理上讲得通"）：

| 变异 | 结果 |
| --- | --- |
| `BUILD_INFO_NONE_PREFIX` 改成与真值同前缀 | 2 条红 |
| 值域字符类删掉 `@` | 2 条红 |
| Makefile 的 `BUILD_DEFINES` 删掉那个 define | 1 条红 |
| `release.sh` 的 origin 从 `release` 改成 `local` | 1 条红 |
| `exec-swebench.sh` 删掉一处提示语里的 define | 1 条红 |
| 嗅探正则去掉 `commit=` 锚点 | 3 条红 |
| `--build-info` 快速路径改成 `false && ...` | 3 条红（含 T1 那条锚在 `full_cli_entry` 上的） |

**写测试过程中发现两个真 bug，都是"绿着的错"**：

- **嗅探正则只锚前缀会取到空壳。** `BUILD_INFO_PREFIX` 这个常量**本身**也是产物里的
  一个字符串，所以每个产物里至少两处命中前缀，**先后顺序是运气**：真产物里真值在前
  （`-m1` 侥幸对了），但同一份代码编的小 fixture 里裸常量在前，
  `-m1` 取到「只有前缀、后面什么都没有」的空壳 → `commit=unknown` →
  门禁把身份完好的产物判成"没有身份"。修法是把正则锚到 `commit=` 上
  （这也是「commit 必须第一个」那条约束的第二个用途）。
- **T1 的第一版断言没有区分度。** 原本用「配置目录里有没有文件」证明
  `--build-info` 在快速路径里；实测把快速路径关掉后，完整 CLI 在 parseArgs 阶段
  就以「未知选项」退出了，**一个文件都没写**，断言照样绿。
  换成 profiler 的 `full_cli_entry` 打点后才有区分度（绕过前 grep -c = 1，绕过后 = 0）。
  这是「代理指标会奖励把浪费重新贴标签」那条教训的同一形态。
  顺带一条：**断言顺序也要按变异来排** —— 先断 `full_cli_entry` 再断 `exitCode`，
  反过来写变异会先在 exitCode 上炸掉，被测的那条断言根本没被验证到。

**门禁全绿**：`bun test` 11102 pass / 1 fail、`make build` 无
`will always be undefined`、`bun run lint` / `lint:boundary` / `format:check` 全过、
`docs:gen-reference` 已重跑（`website/ref/cli.md` + `env.md` 一并提交）。

那 1 个 fail 是 `plan-mode-write-plan-file`，**与本次改动无关，三条证据齐**
（CLAUDE.md 要求的举证）：① 它只 import permission / plan / config 三个模块，
本次一个都没碰；② 从**不含 `.claude/` 的 cwd** 跑同一文件 6 pass / 0 fail；
③ 成因是 worktree 路径含 `.claude/`，相对路径 `src/test-not-a-plan.ts` 解析后命中
`checker.ts:198` 的敏感路径拦截，在 plan-mode 判定**之前**就返回了
（结论仍是 DENY，只是 reason 不同）—— 正是 CLAUDE.md 已登记的两类 worktree 环境产物之一。

## 朝向哪个北极星

**可观测**，而且是它的前提层：「每一个产物都能说出自己是哪个 commit 编的」。

四大方向的曲线全部按 release 归因，而**一个版本号对应几十个 commit** 时，
归因的键本身就是错的 —— 「跑评测验证本轮修复」跑成「跑 5 天前的代码」
就是这个错键的直接后果。本 PR 不产出任何一条曲线，
它修的是**画曲线所依赖的那个键**。

**牺牲了什么**：每次构建多一次 `git` 取数（实测 `make build` 全程 3.3s，
脚本本身 ~50ms，可忽略）。以及产物里多了 ~200 字节明文。

**它不能防什么**（写在模块头注释里，避免下一个人误以为这是安全机制）：
那一行是明文，可以用十六进制编辑器改掉。**门禁防的是疏漏不是恶意**，
防篡改需要签名，那是另一个量级的工程。
另一处已知盲区：`dirty=true` 时 commit 只描述了基线，改动内容无记录 ——
只能报警不能解决，所以消费方必须点破而不是假装 commit 描述了全部。
