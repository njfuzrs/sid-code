# 「始终允许」按子命令生成前缀规则，而不是记住整条命令

## 决定了什么

`bash` 的会话级「本会话始终允许」与持久化（`Shift+A`）都不再只记整条命令原文，改为
按 `&&` / `;` / `|` 拆成子命令、给**每个需要批准的子命令**生成一条 allow 规则（最多 5 条）：

- 新增 `packages/core/src/permission/bash-allow-rules.ts`（纯函数 `buildBashAllowRules`）：
  - 多子命令 CLI（`git` / `npm` / `bun` / `docker` / `make` …）取「程序名 + 第一个位置参数 + ` *`」，
    如 `bun test a.test.ts 2>&1` → `Bash(bun test *)`；名单外程序取「程序名 + ` *`」。
  - 免确认段不生成规则：只读段、首段 `cd <dir>`、管道下游纯过滤器。
  - 超过 5 条 → 退回整条精确规则（`fallback: "too-many"`）。
  - 危险确认 → 只给整条精确规则（`fallback: "dangerous"`）。
  - 规则语法表达不了的命令（含 `)` / `*`）→ 不生成规则而是退回会话记忆
    （`fallback: "unrepresentable"`）。
- `packages/cli/src/app.ts`：新增 `applyBashAllowRules`（决定写会话还是 local settings），
  `answer === "always"` 与 `persistBashAllowRule` 都改调它；只在生成不出规则时才退回
  `rememberDecision`（旧行为）。
- `packages/cli/src/ui/components/permission-choices.ts` + `DialogManager.tsx`：确认框的
  「本会话始终允许」「持久化」两项把**将要写入的规则**写进 description（`本会话记住 Bash(bun test *)`），
  用户能看到实际放行范围而不是自己敲的那条完整命令。
- `packages/core/src/permission/safety-confirmation.ts`：把 `isSafetyConfirmation` 从
  `checker.ts` 抽出成独立模块；`tool-executor` 在调用确认回调时透传 `safetyConfirmation`，
  使「危险确认只记精确、只在会话内」这条在一处判定。

## 放弃了什么（以及为什么不选）

- **不生成「整条命令 + `*`」的规则**（`Bash(cd /ws && bun test *)`）。它把 cd 前缀和管道都
  框进规则里，换个目录或去掉 `| tail` 就不命中——正是缺陷本身。只读/过滤器段本来就走
  免确认路径（`checker.checkAllowList` 的既有豁免），写进规则只是给会话加噪音。
- **不给解释器 / shell / 包装器生成前缀规则**。`python3 *` 等于放行本机任意脚本，
  语义上不是「这条命令」的前缀。覆盖 `python*`（含版本号）/ `node` / `deno` / `ruby` /
  `perl` / `php` / `bash` / `sh` / `zsh` / `dash` / `ksh` / `fish` / `npx` / `eval` / `exec` /
  `source` / `.` / `xargs` / `env` / `sudo` / `doas` / `time` / `nice` / `nohup` / `timeout`，
  外加 `bun -e` / `bun --eval` / `bun -p` / `bun run <文件>`、`find … -exec`、前导变量赋值。
- **不在表达不了时强行生成**。`rules.ts` 用 `\(([^)]+)\)` 解析规则参数：`Bash(echo $(date))`
  整条匹配失败 → 规则**静默失效**（用户以为已放行）。而精确规则里的 `*` 会被
  `matchShellRulePattern` 当通配 → `Bash(ls *.ts)` 放行 `ls a.ts`，比批准范围宽。
  两种都比「不生成」更糟，所以含这些字符时退回会话记忆。
- **不做「危险确认也放行同类」**。`isSafetyConfirmation` 覆盖 `dangerousCommand` /
  `safetyCheck`（hook 要求确认）/ `destructiveTool`（MCP 自报）。一次人工确认是「这次可以」，
  不是「以后这类都放行」；据此派生前缀规则会让 hook 特意拦下的命令被一次点击永久绕过。
  所以危险确认只记精确规则、只写会话、不落盘。
- **不把 `isSafetyConfirmation` 直接从 `checker.ts` 导出**。`checker.ts` 是权限判定的巨型模块，
  `query/tool-executor` 静态 import 它会把整条判定链拉进执行层的模块依赖图；
  抽成 `safety-confirmation.ts` 让两边共用同一口径且只有一条窄依赖边。
- **不改进会话记忆键（`bash:<整条命令>`）去做前缀匹配**。记忆键是一次性字符串集合，
  表达不了通配/前缀；硬造成前缀匹配等于在记忆层复制一套规则匹配逻辑，还要处理优先级、
  与规则文件的遮蔽关系。规则层本来就有这套能力（`matchShellRulePattern`），复用它是唯一
  不引入第二套语义的选择。

## 拿什么证明它生效了

- **端到端（验收要点 1/5）**：真实 `PermissionChecker` + 会话规则 `Bash(bun test *)`，
  `cd <ws> && bun test b.test.ts | head` → `allowed: true`；同一条规则下
  `cd <ws> && python3 y.py 2>&1 | head` → `needsConfirmation: true`。
- **单测**：`packages/core/tests/permission/bash-allow-rules.test.ts` 29 pass
  （含危险确认只精确、6 条退回整条、`python3 x.py` 精确不放行 `python3 y.py`）；
  `packages/cli/tests/ui/components/permission-choices.test.ts` 39 pass（含规则文案）。
- **变异自证**（两次都把被测代码改坏再恢复）：
  - 关掉解释器判定（`INTERPRETER_LIKE_RE` 短路）→ 9 个断言变红（`python3` / `node` / `bash` /
    `xargs` 等全部退化成前缀规则）；恢复后 29 pass。
  - 上限 `MAX_BASH_ALLOW_RULES` 5 → 10 → 「超过 5 条退回整条精确」变红；恢复后 29 pass。
- **选测**：`bun run affected-tests:run` → 6113 pass / 9 skip / 0 fail（504 文件）。
- **构建**：`make build` exit 0，无 `will always be undefined` 告警。
- **G2 / G4**：`bun run smoke` 28 通过 0 失败；`bun run smoke:tui` 2 通过 0 失败
  （确认框文案改动走的是 G4，`A1-dialog` 未受影响）。
- 其余门禁：`lint` / `format:check` / `lint:boundary` / `lint:command-system` /
  `lint:legacy-tool` / `typecheck:gate`（62/62，无新增）全绿。
