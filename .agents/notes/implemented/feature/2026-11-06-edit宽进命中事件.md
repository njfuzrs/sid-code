# edit 的四种宽进匹配各自可观测：新增 normalized 策略与 EditLenientMatch 事件

## 决定了什么

`packages/core/src/tool/edit.ts`：

1. `MatchStrategy` 新增 `normalized`；引号归一化路径不再伪装成 `exact`，单独返回该策略并带
   `matchStartLine` / `matchEndLine`。`flexible` / `regex` / `fuzzy` 的返回也补上命中行，
   `fuzzy` 另带 `similarity = 1 - score`。
2. 新增模块级 sink `setEditMatchSink` 与事件名 `EditLenientMatch`。非 `exact` 命中**成功写盘后**
   发一条，字段：`strategy` / `file_ext` / `old_len` / `occurrences` / `replace_all` /
   `match_start_line` / `match_end_line` / `similarity`（仅 fuzzy）。不记 old_string / new_string /
   文件路径原文——原文已在 messages 里，重复落盘只放大轨迹体积。
3. `packages/cli/src/app.ts` 在 collector 就绪后把 sink 接到 `recordCustomEvent`（同
   EditFailureReminder / ReadHint 的延迟接线写法）。
4. `deferUnreadCheck` 显式把 `normalized` 与 `exact` 同权放行，保持「未读文件只能精确改」的
   既有边界——否则新增策略名会静默收紧这条行为。

## 放弃了什么（以及为什么不选）

- **不把 `EditLenientMatch` 登记进 `EVENT_ANCHORS`**：方案文档写的是「登记」，但该门禁
  （`defense-registry-complete.test.ts`）只解析 `packages/core/src/query/` 下的发射点，
  `tool/edit.ts` 不在扫描范围；硬登记会因「stale：锚点没有发射点」直接红。`ReadHint` 同样在
  `tool/read.ts` 且未登记。要登记得先把门禁扫描范围扩到 `tool/`，那是另一个改动。
- **不在失败路径发事件**：歧义 / 未命中已被 `EditFailureReminder` 覆盖；`EditLenientMatch` 的
  用途是「宽进成功后抽样核对改对没有」，只记成功。
- **不记文件路径**：只放 `file_ext`。路径原文对聚合没有增量，却会把项目名带进轨迹。
- **不顺手做 T1/T2**：扩字符表会改变匹配行为，先把观测接上（方案排期把 T3 放在 T1 前，正是
  这个理由）。
