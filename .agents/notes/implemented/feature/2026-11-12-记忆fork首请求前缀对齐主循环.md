# 记忆 fork 首请求的 tools / thinking / messages 三处对齐主循环最后一次实际发出的请求

## 决定了什么

deepseek 族记忆 fork 的首请求，缓存命中率 p50 只有 6%（405 个会话）。原因是请求体有三处和主循环不一样：
thinking/effort 写死成关（DeepSeek 把这两个参数算进缓存键，只改其中一个，整条前缀就 0 命中）；
fork 发全量 52 个工具，主循环发 tool search 之后的子集；
fork 发原始消息，主循环发清理后的视图。这次三处一起对齐：

- **快照**（`agent/fork-prefix.ts`）：`query/loop.ts` 在 BeforeModel 之后、建流之前调 `recordMainRequestShape`，
  记下本轮**实际发出**的 `tools` 和思考参数。快照按 ctxMgr 放进 WeakMap。
  fork 调 `resolveForkRequestShape` 取回快照。
  以下三种情况退回全量工具 + 关思考（即改造前的行为），并写 `prefix_source=fallback`：没有快照、模型不同、
  快照里缺 fork 必需的工具（`MEMORY_FORK_REQUIRED_TOOLS`）。
- **思考参数按方言声明照搬**：`WireDialect.cacheKeyIncludesThinking` 是新增的能力位。
  只有 `deepseekOpenAIDialect=true`，依据是实测，记在 `llm/dialect/deepseek.md`。
  其余族一律 false，不改现状：Anthropic 的缓存键不含 thinking，没测过的族不猜。
  照搬思考时，`maxTokens` 取主循环与 fork 两者中较大的值，
  因为 DeepSeek 的 `max_tokens` 包含思维链。
- **messages**：`ContextManager.getForkPrefixMessages()` 只读地复现主循环的发送视图，不推进任何清理状态。
  这份视图和发送路径共用同一个清理函数。
  快照不含 transient reminder。
- **思维链通道**：fork 开思考后，`reasoning_content` 会以 text 块（`_raw_block.type=thinking`）的形式送达。
  `forked-agent.ts` 把它单独收起来，写进 `_meta.reasoning_content` 回传，不当正文处理。
- **观测字段**：`BilledRequest` 新增 `tools_hash` / `tools_count`（主循环和 fork 都写）和 `prefix_source`（只有 fork 写）。
  挂在 OpenAI/Anthropic provider 的全部计费出口上。
- 接线方：session-memory、memory-extract、auto-dream、`/btw`。
- 已有守卫单测「fork 工具 = registry.definitions()」锁的正是旧的错误行为，这次**有意改掉**，
  改成「有快照时 = 主循环工具」。

**牺牲**：照搬思考参数后，deepseek 族 fork 也要思考，输出 token 和耗时都会增加，即**更快**和**更省**里输出那一项。
fork 是后台任务，不阻塞用户；省下的输入费远大于多出的输出费（见下）。
对**更准**的影响方向不确定，看 `save_memory` 和 edit 次数，只观察，不设阈值。

## 放弃了什么（以及为什么不选）

- **fork 自己重算 `activeDefinitions()`**：模型中途通过 tool_search 激活的工具，
  以及 `withholdLateMcpTools` 扣下的晚连 MCP 工具，重算都会对不上。所以只认主循环实际发出的值。
- **按模型名判断 `/deepseek/i`**：本仓禁止按模型名硬编码分级，改成方言声明。
- **所有族都照搬思考**：Anthropic 的 fork 首请求 p50 已经有 72%，照搬只会让它白付思考费。
- **按 canUseTool 白名单裁剪 fork 工具**：老注释的否决理由仍然成立，裁剪会让 tools 段分叉。
- **fork 换便宜模型（D）/ 只发摘要（E）**：换模型，缓存键就整体换掉了；只发摘要，fork 就变成了子代理，记忆质量会下降。
  论证见调研文档 §5.4。
- **快照存在 ContextManager 字段上**：这是与上下文无关的状态。用 WeakMap 放在 agent 层，会话结束会自动回收。

## 拿什么证明它生效了

- G1：`packages/core/tests/agent/fork-prefix-alignment.test.ts`（12 例）覆盖调研 §6.4 的六条，
  外加只读性与思维链通道。`packages/core/tests/llm/request-shape-observation.test.ts`
  走真实 `OpenAIProvider` 流式路径（mock fetch），断言落盘的 `BilledRequest` 上有这三个字段。
- 变异自证（每次都确认变红后再恢复）：工具改回 `registry.definitions()`；思考写死 `SIDE_CALL_NO_THINK`；
  去掉协议族判断；去掉缺工具退回；messages 改回 `getMessages()`；在 reminder 注入之后再存快照；
  思维链当正文收；去掉 provider 出口上的 `shape: observeRequestShape(params)`。最后一条变异让两例变红，
  Expected 2 / Received undefined。
- 端到端：`make build` 后用同一个任务跑两轮（stream-json 无头，每轮之后等 45s，让 fork 跑完），
  模型 `origin-deepseek-v4-1-flash`（企业网关），本地新版跑 3 个会话，线上 v0.1.615 跑 1 个会话做对照：

  | 版本 | fork 首请求 thinking/effort | tools 和主循环 | 输入 | 命中 |
  | --- | --- | --- | --- | --- |
  | 线上 0.1.615（第 1 轮） | disabled / omitted | — | 68,877 | **5,888（8.5%）** |
  | 本地新版 3 会话 × 2 轮 | enabled / max | `tools_hash` 相同（23 个），`prefix_source=snapshot` | 26,830–28,596 | **25,472–27,264（94.9%–95.3%）** |

  另外：对照版本 fork 的输入是 68,877（52 个工具全量），新版是 27K（23 个工具）。
  新版 fork 的输出是 261–377 token，单次耗时 3.4–4.5s。对照版第 2 轮能命中 67,712，是因为它读到了自己第 1 轮写下的缓存，
  这和调研里「第 2 轮以后 84%」的现象一致。
- 还没做、留给发版后：调研 §6.2 的主指标是 deepseek 族会话第 1 轮 fork 首请求命中率 p50 ≥ 0.80，
  需要至少 30 个发版后的真实会话，用 `d16-fork费用占比与可省金额.py` 统计。
  claude 族 `cache_write` 是否下降也留在发版后看。
