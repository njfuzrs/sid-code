# explore 默认轮次上限 100，子代理可见剩余轮次

## 决定了什么

三件事一起做，因为它们必须一起才有意义：只给上限不加可见性 = 模型在不知情的情况下被打断；只加可见性不给上限 = 无限长跑的空转合法化。

1. **`BUILTIN_AGENTS.explore.maxTurns = 100`**（`packages/core/src/agent/agent-definition.ts`）。
   **只给 explore 加**，verify / task / general-purpose 保持无上限。定值来自 E1 的**预登记规则**
   （跑前写死，不是事后挑一个好看的数字）：修复后组 explore 轮次最大值 M=145、长跑
   （>66 轮）子代理的重复读率 r=42.9% > 35% 阈值 → 落到第三档「暂定 100，不调大」。
2. **`sub_agent` 新增 `max_turns` 参数**（`packages/core/src/agent/tool.ts`），透传为
   `SubAgentTask.maxTurns`，在 `resolveSubAgentMaxTurns` 里**优先于** Agent 定义的默认值。
   前台与后台两条执行路径都接了（只改一条是最容易漏的形态）。
3. **剩余轮次可见**（`packages/core/src/agent/agentic-loop.ts`）：新增 `turnBudgetNoticeThreshold`
   纯函数，阈值 = `max(3, ⌈maxTurns × 10%⌉)`；剩余轮次降到阈值时，往**当轮发送副本**注入
   一条 `system-reminder`，写明「最多 N 轮 / 当前第几轮 / 还剩几轮」，整条生命周期**只注入一次**。
4. **子代理收尾约束改指向 harness 的实测提示**（`packages/core/src/agent/sub-agent.ts`）：
   措辞从「如果你**感觉**快要达到轮次限制」改成「当你收到 harness 的『还剩 N 轮工具调用』提示时」。
5. 重新生成 `website/ref/tools.md`（`sub_agent` 参数表新增 `max_turns`）。

## 放弃了什么（以及为什么不选）

- **放弃「所有子代理类型统一加上限」。** 只有 explore 的长跑有数据（42.9% 重复读），
  verify / task 的长尾没有证据表明异常。全加会把「修一个已知异常」变成「改所有子代理的行为」，
  且一旦 verify 因为上限被打断，损失的是**正确性**而不是速度——那是更贵的错。
- **放弃「不加 visible、只强制在打满后总结」。** `MAX_TURNS_FINALIZE_PROMPT` 只在打满之后才出现，
  模型在此之前对预算完全没有判据，只能凭感觉收工。E1 里长跑子代理的重复读率正说明这个「感觉」不准。
  只有把「还剩几轮」变成事实，模型才可能做出「再深挖一层 vs 现在收」的比较。
- **放弃「每轮都报剩余轮次」。** 递减的数字会变成噪音，而噪音的处置是模型学会无视它。
  一次性警告在实践中才会被当真。测试里钉了「第 3/4 轮不再出现」。
- **放弃「固定 N 轮（比如剩 3 轮）才提示」。** 上限 100 时剩 3 轮太晚（模型来不及收），
  上限 10 时第 7 轮提示又太早（等于逼它草率收工）。10% 比例的两种规模都落在「还有余地、
  但该停止开新战线」的窗口里，下限 3 是给极小上限兜底。
- **放弃「把 100 调大以覆盖 M=145 的长尾」。** 长跑仍在空转时调大上限等于把空转合法化。
  长尾的处置是「说明为何打满 + 用更大值重派」，留给 PR9 评估。
- **放弃「在工具 schema 描述里鼓励模型事前预判轮次」。** 模型对「这个任务要几轮」没有判据，
  凭感觉猜只会让正当的深度调研被误截。描述里写的是**事后重派**路径：报告「已达轮次上限」
  且结论不完整时，用更大的值重派并把已有结论写进 prompt。
- **放弃「把提示写回 ctxMgr」。** 与 LSP / todo 注入同一条不变量：瞬态提示只进发送副本，
  否则之后每轮都会重发给模型直到被压缩裁掉。

## 拿什么证明它生效了

**单测**：`bun test ./packages/core/tests/agent/subagent-max-turns-pr5.test.ts` → 15 pass / 0 fail / 31 expect。
三条各自断言到**接线**上，不只是常量：① 定值 + `resolveSubAgentMaxTurns` 真的消费它；
② schema 接受 + 前台/后台两条路径都把值放到 `SubAgentTask.maxTurns` 上；
③ 驱动真实 `runAgentLoop`，逐条检查**实际发出的 messages** 里有没有提示、只出现一次、不写回 ctxMgr。

**选测**：`bun run affected-tests:run`（判定 selective，跑 `packages/core/tests/agent/` 全目录）
→ 770 pass / 0 fail / 86 files。

**静态门禁**：`bun run typecheck:gate` 62/62 存量、**无新增**（过程中它抓到过一次真实接线缺口 ——
`executeInBackground` 的 params 类型漏了 `max_turns` 字段，tssc 报 TS2339 后补上）；
`bun run lint` 0 warning 0 error；`bun run format:check` 通过；
`bun run lint:boundary` / `lint:command-system` / `lint:legacy-tool` 三道棘轮全过；
`bun run docs:gen-reference --check` 通过（`website/ref/tools.md` 已重新生成）。

**G2 冒烟**：`make build` 成功后 `bun run smoke` → 42 例全过；`expect-guard` 报「本次没有改动 G2 用例」。

**变异自证**（每条都是「改坏 → 跑 → 看到红 → 恢复 → 再跑绿」，看的是**报了什么**而不只是退出码）：

| 变异 | 实测 |
| --- | --- |
| `explore.maxTurns` 100 → 50 | 2 fail（定值断言 + `resolveSubAgentMaxTurns` 消费链断言） |
| 删掉两处 `maxTurns: params.max_turns` 透传 | 2 fail（前台「传了 max_turns」+ 后台 `run_in_background` 路径） |
| 删掉 `turnBudgetNoticeSent = true`（= 每轮都注入） | 1 fail（「只注入一次」断言） |
| 删掉 `Number.isFinite(maxTurns)` 守卫 | 1 fail（「无上限 → 永不注入」断言） |

四次恢复后重跑：15 pass / 0 fail。

**没覆盖的**：端到端的「模型实际因此少跑了轮次」属于 G5 评测层面，本地单测与 G2 都测不到；
E1 的预登记规则规定了修复后组要重跑对比，那一步不在本 PR 内。
