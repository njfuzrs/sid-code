# 项目记忆索引截断时自动切到按需召回并停止全量注入，/context 列出固定开销来源

## 决定了什么

1. **注入模式判定收成一处**（新增 `packages/core/src/memory/inject-mode.ts`）。判据只看结构性事实：项目 `MEMORY.md` 带写侧追加的截断警告（`readIndexCapacity().truncated`）就走 `recall`，否则走 `full`。结论**按记忆目录在进程内锁定**，CLAUDE.md 热重载、/language 等重建 system prompt 时都复用它，会话内不会来回翻转。
2. **召回模式下 system 里不再放全量项目索引**。`store.getIndexContent` 把项目段换成一行指针（`buildRecallModePointer`），写明「完整索引在 `<dir>/MEMORY.md`，需要时 Read」。全局索引、团队索引不受影响，因为召回只覆盖项目目录。
3. **召回接线改读同一个判定**。app.ts 的 `drainRecalledMemories` 原来查 `isMemoryRecallEnabled()`（已删除），现在查 `resolveMemoryInjectMode(memoryDir).mode`，这样不会再出现「全量索引 + 召回」双份注入。
4. **召回失败时单向回退**。`findRelevantMemories` 新增 `onSideQueryError` 回调，用来区分「没选中」和「辅助调用坏了」。召回坏了就 `fallbackToFullInjection`，本会话起改回全量，并用新增的触发源 `memory_recall_fallback` 重建**一次** system prompt。回退只在真的发生切换时返回 true，重建最多一次。
5. **`SID_CODE_MEMORY_RECALL` 改为覆盖开关**：`=1` 强制召回，`=0` 强制全量（也是回滚出口），其它值或不设时按截断自动判定。
6. **/context 显示固定开销来源**（新增 `packages/core/src/context/fixed-overhead.ts`）：
   - 列出项目、全局、团队三份记忆索引，以及每个 `@` 导入文件，标出「经 `CLAUDE.md:18` 导入」，单项超过窗口 2% 时给出提示（说明来源和处理方法）。
   - 导入清单的来源：`processImports` 新增 `onImported` 回调，记录导入路径、来源文件、行号和自身字符数，存进 `ProjectRules.importedFiles`，`mergeProjectRules` 时按顺序拼接。
   - 文本从**实际发出的 system prompt** 里切，不读磁盘，所以被截断、在作用域外、召回模式下没注入的内容都不计入。嵌套导入只算外层文件自身的内容，不重复计数。
   - token 数 = 启发式 × `ContextManager.getCalibrationFactor()`，与 /context 其它分类同一口径。这些来源是「记忆/CLAUDE.md」分类的细目，不进 total。

## 放弃了什么（以及为什么不选）

| 候选 | 为什么不选 |
|---|---|
| 把索引预算从 25KB 降到 10KB | 截断更多、漏得更多。省下的 token 是用「模型看不到记忆」换来的 |
| 自动不展开 CLAUDE.md 里的大 `@` 导入 | 用户显式写了 `@`，静默不展开违背用户意图，也与 CC 不一致。sid-code 只负责让开销可见 |
| 默认对所有用户开启召回 | 每条用户消息多一次辅助调用（实测 2.1s、input 20,770 token）。小记忆库全量注入更准、更快 |
| 直接打开 `SID_CODE_MEMORY_RECALL=1` 当作修复 | 修复前 `prompt.ts` 不看这个开关，全量索引照样注入，召回只会让 token 净增 |
| 召回失败时逐条消息切换回全量 | 索引在 system 静态区，每次失败都会击穿 prompt cache。改为会话级单向回退 |
| /context 用官方 tokenizer 计数 | 多 provider 共用，单一厂商的 tokenizer 对其它 provider 会引入新偏差（`token.ts` 头注释的既有裁决）。改用真实 usage 反推的校准系数，未校准时 UI 已如实标注「启发式估算」 |
| 模式判定按「磁盘文件数 > 200」 | 文件数不等于索引是否装得下（有字节上限、类型排序）。以写侧的截断警告为准，与 `writeIndex` 同一判据 |

**牺牲了什么**：方向是「更省」，代价是召回模式下每条用户消息多一次辅助调用，有延迟（实测 2.1s）和失败的可能。失败会回退全量，不会零注入。另一个代价是跨过阈值的那个会话首轮 system 前缀变一次，缓存失效一次。
