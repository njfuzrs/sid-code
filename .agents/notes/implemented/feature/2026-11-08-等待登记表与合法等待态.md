# 等待登记表与合法等待态

- **PR**: PR 1（`feat(task): 等待登记表与等待态判据统一`）
- **方案**: `docs-research/sid-code/bugfixes/todo/20261108-等待外部状态-合法等待态与Monitor工具-设计方案.md` §5.1–§5.3

## 决定了什么

**1. 引入「等待源 + 回报承诺」，把「有东西在等」从隐含约定变成显式登记。**

`hasAwaitedBackgroundTasks()` 的口径（「在跑」≠「值得等」，60s 静默的后台 shell 不算）是对的，
它防的是常驻服务死等（20261103-130950-00ef059c）。缺的是第二类等待：**显式声明了
「最晚什么时候回报」的源**——`schedule_wakeup` 排好的唤醒、带期限的后台命令、monitor。

`wait-registry.ts` 只存 registry 里没有的东西（期限 / subjects / 唤醒）。
agent / workflow / 普通 shell 一律**派生**（现读 `task/registry.ts`，判据逐字复用
`isAwaitedBackgroundTask`）——不双写，因为两个事实源迟早漂移。

**2. `hasPromisedWait` 是 `hasAwaitedBackgroundTasks` 的超集。**

派生分支逐字复用旧逻辑，新判据只多出显式声明的 `deadline` 源。所以没有新等待源的会话里
两个判据结果完全相同（回归主断言 T-W2-1 逐组合验证）。这一条是 PR 1 能安全上线的全部理由：
它不给存量会话引入任何新行为。

**3. 判据统一改问登记表（W2 的 6 个改动点）。**

T2 闸门、停滞阶梯 L2、`waitForBackgroundNotification`、promise-nudge 从
`hasAwaitedBackgroundTasks` / 「有后台任务」改为 `hasPromisedWait`。
`EndTurnShape` 新增 `promised_waits` 字段与旧的 `running_background_tasks` **并列**
（不替换）——旧查询保持可用，新字段才能回答「闸门为什么因为一个唤醒放行了」。

**4. 后台 bash 新增 `wait_until_seconds`（60..3600，钳制）。**

CC 的分流规则是「只要一次通知就用后台 Bash + 会自己退出的循环」，这条路在本仓被 60s 静默
判据堵死。声明期限后 harness 不必靠静默猜：期限内一直算「值得等」，到期由自己的定时器
kill + 通知。不带这个参数的后台 bash 行为与改动前**逐字节相同**。

**5. 唤醒登记进表 + 只用确定信号失效。**

`schedule_wakeup` 成功后登记为 `deadline` 源；替换 / `cron_delete` / 注入三条路径分别释放。
失效只用 harness **确定知道**的事实：S1（模型自己写的清单清零）、S2（被等对象已终态，
subject 从 prompt 里抽取）。**不判「目标达成」**——#642 §6.3 的否决理由仍然成立。
撤销时用户能看到一行系统提示（只给用户看、不进 ctxMgr），这正是 #642 否决自动撤销时
最担心的「轮询静默中断、用户以为还在等」。

**6. `ScheduledInjectOutcome` 新增 `dropped_invalidated`。**

与 `dropped_superseded` 分开：都是「不注入」，但一个是「换成新的了」、一个是「不需要了」。
混在一起之后「僵尸唤醒还剩多少」无法从轨迹上归因。

## 放弃了什么

- **只改提示词让模型自己收尾**（方案 §7.1）：模型看不到 harness 的判据，改了也不知道为什么被放行。
- **只加 monitor 工具、不动判据**（方案 §7.2）：**这条最需要点破**——monitor 是 PR 3，
  但用户在 PR 1 之后就该拿到收益（7dd98bf5 那种强推与两条会话的僵尸唤醒）。
  把价值绑在「模型愿意用新工具」上，等于让判据修复的上线时机由模型行为决定。
  下一个 agent 不要以为「加了 monitor 就够了」。
- **登记表落盘、`/resume` 后恢复**（方案 §7.8）：登记表描述的是「当前进程里有谁会回来叫醒我」，
  进程没了这些承诺本来全部失效（后台 shell 随进程清理、会话级唤醒不持久）。恢复一份
  没有执行者的承诺，只会让闸门为一个不存在的回报放行。
- **用自然语言判断「目标已达成」来撤销唤醒**（方案 §7.9）：判不准，误杀一次就让轮询静默中断。
- **把 T2 那行瞬态状态条同时给用户和模型**：原实现只 `yield {kind:"system"}` 进 TUI，
  模型看不到。改成给模型的 `<system-reminder>` 并按「未完成项签名 ⊕ 等待源 id 集合」去重；
  TUI 那行删掉（等待源在面板里逐行可见，再写一遍就是第二份，PR 2 的 `WK` 行承接）。
