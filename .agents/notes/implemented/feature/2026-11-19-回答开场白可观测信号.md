# 「不要输出接收确认开场白」这条规则第一次有了可观测信号

## 决定了什么

system prompt 的回答规范 #8 自称「每一轮都生效、且这类开场白会自我强化」，
但此前全仓没有任何度量：某个版本把 prompt 改坏、反而更容易写出开场白，
不会有任何东西报错。本次补的是**只度量、不干预**的信号链：

1. `trace/collector.ts` 新增 `detectAckOpener()` 与两个累计字段
   `ack_opener_turns` / `ack_opener_total_turns`。判定刻意保守：只有**本轮 assistant
   的第一条文本块**以「已收到 / 已阅读 / 已载入 / 收到了（可选：注入文档名）」开头才计数；
   正文中间出现不算。零文本块（纯 tool_use）与多段文本的轮次不进分母。
2. 字段随会话索引落盘（`trace/session-index.ts` 定义 + `trace/builder.ts` 透出）。
   分母为 0 时两个键都不写——「缺失」与「0 个开场白」是两件事。
3. `/context` 面板展示该比率；`scripts/northstar-snapshot.ts` 作为**辅助口径**
   （不进四个方向的主口径，它会随 prompt 版本漂移）。

## 放弃了什么（以及为什么不选）

- **运行时拦截/改写开场白**：那是把一条软规则变成硬拦截，模型话说到一半被改写，
  体验比多说一句「收到」更糟；而且这样就没有信号了——拦截后比率恒为 0，
  反而看不见规则退化的趋势。
- **用 `/context` 里已有的 token 占比做代理指标**：开场白是「有没有」的布尔事件，
  用体量代理会被回复长度稀释，看不出比例变化。
- **判定放宽到「回复里出现这些词」**：会把大量正常回复计进来（例如正文写「已收到你的
  反馈」），比例虚高后没人再看这个数——这属于「有指标但不可信」，比没有更危险。

## 拿什么证明它生效了

- `bun test packages/core/tests/trace/` → 240 pass / 0 fail。新增用例覆盖：
  首条文本块命中计数 +1、正文中间命中不计数、纯 tool_use 轮次不进分母、
  索引行在分母为 0 时不写两个键。
- 落盘隔离：测试把 `SID_CODE_SESSION_INDEX` 指向 tmpdir，全程不写真实 `~/.sid-code/`。
- 变异自证：手工构造一条以「收到，已阅读 CLAUDE.md」开头的 assistant 消息喂给 collector，
  `STATS` 输出 `{"turns":1,"totalTurns":1}`，session-index 行含
  `"ack_opener_turns":1,"ack_opener_total_turns":1`；正常回复计数不变。
- `bun scripts/northstar-snapshot.ts --self-test` 通过；合成数据里补了「字段存在但分母为 0」
  的用例，防止 `0/0` 被算成 0%。
- 已知局限（如实记录）：本机历史 session-index 全是 D-07 之前的版本行，
  真实数据侧 `sessions_with_field=0`，开场白率在真实快照上会显示 `null` 并提示
  「旧版本行属预期」。需要真实会话积累才能看到非 null 值——这不是接线缺陷。
