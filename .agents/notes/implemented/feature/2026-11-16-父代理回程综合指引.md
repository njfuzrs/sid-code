# sub_agent 回程侧补「由你自己综合」引导，核验指引不落（抽样否决）

## 决定了什么

在 `packages/core/src/agent/tool.ts` 的 `SubAgentTool.usageGuide()` 末尾（「嵌套限制」之前，
属于「何时不该派」之后的第一条回程指引）新增一条：

> **多个结果由你自己综合，不要把「按发现去修」再派出去**

含义：几个子代理陆续返回后，读结果、判断哪些成立、自己动手改是父代理的活。再派一个
`task` 子代理「按上面的发现去修改」，等于把**理解与判断**也外包——它拿不到父代理手上的
其余结果，父代理也失去判断改得对不对的依据。派出去的是**执行**（跑命令、改文件），
不是**综合与判断**。

**只加这一条**：方案原定的第二条「引用子代理给的 `文件:行号` 做修改前，先自己读那一处」
被前置抽样否掉（见下节），方案原文的判读规则就是「核验占比已经很高，则只加第一条」。

配套：
- 新增 `packages/core/tests/agent/subagent-result-synthesis.test.ts`（4 个用例）——断言这条
  文案存在、区分「派执行」与「派综合」、且不被后续改写挤掉。
- 一条**反向**断言（`not.toContain("动手修改前先自己读")`）：防止有人凭直觉把被抽样否掉的
  第二条重新加回来而不重新取证。要加回来就先改这里与方案文档的判据。

## 放弃了什么（以及为什么不选）

- **方案原定的第二条「先自己读那一处」**：前置抽样否决。本地 95 个会话、332 条子代理结果，
  其中 194 条结果文本里提到了可判定的文件名。按「结果后 3 条 assistant 消息内，对结果提到的
  文件先读还是先改」分类：

  | 行为 | 条数 | 占比 |
  | --- | --- | --- |
  | 纯核验不写（读了原文，没动这些文件） | 160 | 82% |
  | 未涉及结果里提到的文件 | 31 | 16% |
  | 先读再改 | 0 | 0% |
  | 不读就改 | 3（初判）→ **0**（人工核验后） | 0% |

  那 3 条初判「不读就改」全部出自同一会话 `20261104-135746-2d0ec310`，人工读原文确认
  是**文件名子串误判**：父代理先 `edit` 的是它自己的临时汇总文件 `/tmp/ctx-memory-audit.md`
  （内容里出现 `MEMORY.md` 字样），随后才 `read` 子代理提到的源码。核验实际已经在自发发生，
  再加一条只会白增父代理的 `read` 调用（方案 §T6「风险」段列出的正是这个成本）。
- **把这条写进系统提示词（`system-prompt.ts`）**：否决。`usageGuide()` 只拼进
  `tools[].description`（`registry.ts` 的 `toolToDefinition`），系统提示词刻意不重复渲染
  同一段引导（F5-Q5a，2026-11-04）。回程指引与「何时该派」同属 `sub_agent` 工具的使用说明，
  放同一处才不会被读到两遍。
- **同时约束「结果后一律不许再派 task 子代理」**：写宽了会误伤真实场景——抽样里 37 次
  「结果后 3 条内又派子代理」中，多数是继续探查另一个方向或并行修互不相干的缺陷，
  那是正常分治。所以文案限定在「不要把**综合与判断**外包」，并显式写明执行可以派。

## 拿什么证明它生效了

- 新增测试 + 相邻的分治判据测试：`bun test ./packages/core/tests/agent/subagent-result-synthesis.test.ts
  ./packages/core/tests/agent/subagent-divide-criteria.test.ts` → **11 pass / 0 fail**。
- **变异自证**：删掉新条目后重跑，4 个用例中 3 个变红（`由你自己综合`、`按发现去修`、
  `嵌套限制在新条目之后` 三条断言失败），恢复后 4/4 绿。恒绿的门禁比没有门禁更危险，
  这一步是确认断言真的绑在文案上。
- `bun run affected-tests:run` 与 `make build` 结果见 PR 正文。
- 判据数据本身：抽样脚本口径与结论写进私有库剖析附 B（`H1-委派与交接-剖析.md`），
  与方案文档 T6 段的「完成判据」对齐。上线前后的行为对照（方案要求的「各 10 个会话」）
  需要在合入后自然积累，本 PR 记的是**上线前基线**。
