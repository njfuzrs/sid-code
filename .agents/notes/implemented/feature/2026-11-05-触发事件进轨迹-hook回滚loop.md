# hook 执行 / 用户回滚 / 定时到点触发三组事件进轨迹（观测缺口 PR1）

## 决定了什么

`events.jsonl` 新增三组事件，全部走既有的「模块级 sink + collector 延迟接线」模式（与
`skill/telemetry.ts`、`trace/jit-telemetry.ts` 同款），不新造机制：

- **`HookExecuted` / `HookAsyncCompleted`**（`core/src/hook/hook-telemetry.ts`）：埋在
  `HookRunner.executeHook` —— 并行 / 串行 / SessionEnd 预算串行 / streaming 四条路径的唯一咽喉。
  同时把 `runId` 从「有 lifecycle 监听才生成」改为无条件生成，并透传进 `AsyncHookRegistry`，
  异步 hook 的后台完成才能与启动事件配对。`source`（user / project / plugin / skill / policy）
  由 `HookPlanner.createExecutionPlan` 写进一个 `WeakMap<HookConfig, string>`，runner 埋点时查
  —— 不改 `HookConfig` 类型、不污染用户配置对象。runtime hook 一律不记。
- **`Rewind`**（`core/src/session/rewind-telemetry.ts`）：埋在**用户动作的入口层**，一次动作恰好
  一条 —— Esc+Esc 面板在 `RewindManager.rewindTo`，`/rewind <n>`、`/undo [file]`、`/restore`
  在各自的 CLI 命令里。`outcome` 闭集 `ok / nothing / snapshot_miss / error`，其中
  `snapshot_miss` 专门给 D5 那个「有快照 id 但恢复返回 null」的复发计数。
- **`ScheduledFire` / `ScheduledInject`**（`core/src/cron/cron-telemetry.ts`）：一次「到点触发」
  是两个时刻，必须分开记 —— `ScheduledFire` 在 `Scheduler.fireOnce`（含 `lag_ms` = 到期到真正
  触发的延迟，会话忙导致的推迟在这里），`ScheduledInject` 在宿主真正调用注入器之前
  （含 `queue_wait_ms` = 排队等待）。`CronTask` 增加 `origin`（loop / cron_create /
  schedule_wakeup），旧任务记 `unknown` 不回填。
- **消费侧**：`digest` 新增「触发计数」一节（hook_runs / hook_blocks / hook_p95_ms /
  rewinds{via} / scheduled_fires / scheduled_skipped / scheduled_lag_p95_ms），
  事件名与生产侧共用常量；新增 `tests/trace/trigger-events-wiring.test.ts` 反死线门禁。

隐私是硬约束（events.jsonl 会被 `trace/uploader.ts` 上传）：hook 只记 `hook_id`（name 或
`cmd:<sha12>` / `url:<host>`），不记 command 原文、stdout、stderr；定时任务只记
`prompt_len` / `prompt_sha12`；`/undo <file>` 只记 `path_sha12`。

## 放弃了什么（以及为什么不选）

1. **给 collector 订 HookSystem 的新事件（`HookExecuted` 作为 HookEventName）**：hook 事件本身
   会再触发 hook 执行，有递归风险；而且要动对外 hook 契约与参考页，代价远大于收益。
2. **在 `CheckpointManager` 层统一埋回滚**：`rewindTo` 内部也会调 `restoreToSnapshot`，埋在那里
   一次面板回滚会记两条；且 `/rewind <n>` 只动对话、根本不经过 checkpoint，会整条漏掉。
3. **复用 OTel span**：span 走 `traces.jsonl`，除导出器外零读取方；清单与 digest 都读
   `events.jsonl`，为这三组事件引入第二套取数源会让「同一件事两个数」。
4. **把触发信息塞进 `UserPromptSubmit`**：那是对外 hook 输入契约，改了要动参考页和用户脚本；
   新增独立事件不动契约。
5. **为 SessionEnd hook 丢事件调整收尾顺序**：追踪结构方案正在改那一段，叠改会冲突；
   本次只做埋点，已知边界写进测试注释。
6. **给隔离 HookSystem 的 hook 加 `agent_id`**：runner 拿不到该信息，硬穿线代价大且并非
   本 PR 的目标（先有事件，再谈归属）。

## 拿什么证明它生效了

- 单测（新增 4 个文件，全绿）：
  - `core/tests/hook/hook-executed-telemetry.test.ts`（9 条）：四条执行路径各一条、runtime 0 条、
    exit 2 → blocking、超时 → timeout、async 的 `run_id` 配对、命令原文与 stdout 哨兵不在序列化事件里。
  - `core/tests/session/rewind-telemetry.test.ts`（9 条）：三种 mode 各恰好一条、点不存在 →
    nothing、`restoreToSnapshot` 返回 null → snapshot_miss。
  - `core/tests/cron/scheduled-fire-telemetry.test.ts`（6 条）：假时钟下 `lag_ms` 从 0 到 ≥600000、
    未授权 → skipped_ungranted、注入器抛错 → fire_error、缺 origin → unknown。
  - `cli/tests/app/scheduled-inject.test.ts`（3 条）：入队不发事件、flush 时 `queued=true` 且
    `queue_wait_ms` 等于时间差、抛错重入队同轮不重复发。
- **反死线门禁的变异自证**（两次）：把 `app.ts` 的 `setScheduledTraceSink(` 改名 → 门禁 1 fail；
  把 `runner.ts` 的 `emitHookTrace(HOOK_EXECUTED_EVENT_NAME` 改名 → 门禁 1 fail；恢复后 7 pass。
  这是本次唯一能证明「门禁真的会红」的证据。
- 门禁：`bun run affected-tests:run`（6085 pass / 10 skip / 1 fail）。失败项是
  `large-data-startup-gate.test.ts`（性能门禁）：父仓基线单跑 9 pass、worktree 重跑 9 pass，
  失败那次空目录首帧三次测量 3159/863/8598ms（相差 10 倍），是紧跟 6096 个测试之后的负载抖动。
- `bun run lint` / `format:check` / `lint:boundary` / `lint:command-system` /
  `lint:legacy-tool` / `typecheck:gate`（62 错误 / 基线 64，无新增）全部通过。
- `make build` 成功，产物自检通过（关键修复已内联进二进制）。
- `bun run docs:gen-reference` 无变化 —— 预期如此：没有改对外 hook 契约、工具 schema 或命令签名。

## 已知边界（不在本 PR）

- SessionEnd hook 若在 collector 关闭 writer 之后执行，事件会被 `recordCustomEvent` 静默丢弃；
  实测未复现（SessionEnd 在退出路径上先于 writer 关闭），不为此改收尾顺序。
- 隔离 HookSystem（agent 声明的 hooks）的事件会进主会话轨迹，但分不出是哪个子代理。
- bridge（远程接管）那组事件是 PR2，端到端依赖企业后端。
