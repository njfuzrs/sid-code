# 发布产物归档到 OSS：回读校验通过才算已归档，没归档就不算发布

## 决定了什么

对应 B46 P1 第 2–4 步。服务器版本目录降级为热缓存，事实源是私有 bucket `sid-code-releases`。

- 新增 `scripts/archive-version.sh`（scp 到 ECS 执行）。先确认平台齐全、本地 sha256 复核，再从产物二进制取 `SIDCODE_BUILD_V1` 与 `Bun vX.Y.Z` 生成 `provenance.json`。对象已存在就跳过、缺的补传；上传后再列一次确认每个 key 都在；最后整目录回读，跑 `sha256sum -c`，`.sha256` 逐字比对。全部通过才打印 `__ARCHIVE_OK__ <ver>`。
- `release.sh`：
  - `archive_remote` 只认 `__ARCHIVE_OK__` 那一行。
  - `--upload` 在原子切换之后、写 install.sh 和 beta.txt 之前归档，失败就 fail，指针不动。
  - 新增 `--archive-existing`，现存目录一律标 original，可重跑。
  - 新增 bun 版本门禁：当前版本必须等于 `.bun-version`。
- `tests/release-archive.test.ts`（17 条）+ `tests/fixtures/fake-ossutil.sh`。这个桩复刻了真 ossutil 的两处行为：cp 遇到已存在对象时 skip 且返回 0；ls 按前缀匹配。

## 放弃了什么（以及为什么不选）

- **已存在即失败**（原设计「禁止覆盖」的字面实现）：发布凭据没有删除权限，一次中途失败的归档就永远重跑不了。改为跳过不覆盖，内容不对的在回读那一步照样会红。
- **用 `ossutil stat` 判断存在性**：发布凭据没有 GetObjectAcl，会返回 403。也不看 `ls` 的 `Object Number`：它是前缀匹配，只有 `.sha256` 时也会把 tarball 判成「在」。改为逐行 `grep -Fx`。
- **provenance 取目录 mtime / tag / 发布机的 bun**：mtime 是上传时间；tag 指向 bump 提交，而实际构建的是它的父提交；发布机的 bun 可能已经升级（0.1.602 实测是 1.3.14，0.1.606 是 1.4.2）。一律从产物字节取。
- **归档放在写 beta.txt 之后**：那样失败时用户已经能装到这个版本，「没归档就不算发布」就落空了。

## 拿什么证明它生效了

- `./scripts/release.sh --archive-existing`：0.1.602–0.1.606 共 5 个版本，每个 11 个对象，回读校验通过；之后连续重跑 3 次全绿，上传 0 个、跳过 11 个。
- 换一条路径独立核验：在 ECS 上直接 `ossutil ls`，每个版本 11 个对象；0.1.602 的 provenance 是 commit `99e28297…`、bun 1.3.14；用发布凭据 `ossutil rm` 返回 `AccessDenied by bucket policy`（I2）。
- 首次真实归档踩到两个 bug，本机桩测试都没测出来：
  1. 身份行正则吞掉了 JS 字面量收尾的 `";`。已修，测试桩改成与真实产物同形。
  2. `printf | grep -q` 在 pipefail 下因 SIGPIPE 偶发误判「对象不存在」。在 ECS 上实测，旧写法 3000 次失败 69 次，here-string 0 次。已修，并加了静态断言。
  - ⚠️ 已归档的 5 份 provenance.json 里 `build_info` 和 `note` 末尾残留 `";`。对象禁止覆盖、发布凭据又删不掉，只能由主账号在控制台删除后重跑 `--archive-existing` 才能更正。commit、built_at、bun_version 三个字段不受影响。
- 变异自证 8 处，每处都只红目标那条：回读 sha、`.sha256` 逐字比对、`grep -Fx` 改前缀、上传后复查、`--upload` 归档 `fail` 改 `warn`、bun 门禁改 `warn`、正则改回去、改回管道写法。
