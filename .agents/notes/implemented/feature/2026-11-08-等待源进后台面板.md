# 等待源进后台面板：唤醒可见 + 面板与消息流去重

- **PR**: PR 2（`feat(ui): 等待源进后台面板，面板与消息流去重`）
- **方案**: `docs-research/sid-code/bugfixes/todo/20261108-等待外部状态-合法等待态与Monitor工具-设计方案.md` §5.7（PR 2 范围）

## 决定了什么

**1. 等待源进**现有**后台任务面板，不新开区域。**

`schedule_wakeup` 的唤醒在面板里成一行 `○ [WK] <prompt 首行>  HH:MM 触发 · 剩 Xm`，
与 shell / 子代理 / workflow 并列（`TodoPanel.tsx` 的 `WakeupRow`）。
子代理进度当初做成独立于消息流的第三区域，结果同一个子代理渲染两遍、过程黑盒、
面板不消失三个缺陷**同源于这一个选择**——唤醒再开一个区就是同一个错误。

**2. 面板数据源 = registry ∪ 调度器，两条路，一个出口。**

唤醒不是 `TaskState`（没有进程、没有 outputFile），它在调度器的 `sessionTasks` 里。
`state-bridge.ts` 的 `updateTasks()` 合并两路：`getPanelVisibleTasks()` + `scheduler.listSessionWakeups()`。
只取 `origin === "schedule_wakeup"` 的会话级一次性任务——`/loop` 与 `cron_create` 有各自的
出口（`/loop`、`/cron list`），进「等待态」面板会让人以为 agent 在等它们。

**3. 调度器主动播报，不靠轮询。**

`addSessionTask` / `replaceSessionTasksByOrigin` / `removeTask` / `fireOnce` 四处调
`notifyTaskChanged()`（从 `task/registry.ts` 导出）。不播报的话面板上的 `WK` 行
要等下一次无关的 registry 变更才出现或消失——「安排后不出现、注入后不消失」
正是 T-T1-3/T-T1-4 要锁的两个行为。`state-bridge` 早已订阅 `onTaskChanged`，所以
一个通知同时驱动两路数据源重算。

**4. 用 `peekScheduler()` 而不是 `getScheduler()`。**

后者未初始化时会造一个 `onFire` 为空的兜底实例并打一条 warn。面板刷新只是
「读一读有没有挂着的唤醒」，不该有「顺手创建了调度器」这种副作用。

**5. 唤醒行的三个语义都与普通任务行不同，所以单独一个 `WakeupRow`：**

- 字形 `○` 空心且**不旋转**（`○` = 在等、没在干活；`◐` = 在跑，L1.1 同族递进）；
- 统计列是「HH:MM 触发 · 剩 Xm」不是耗时——用户关心「什么时候结束」；
- **没有终态行**：到点注入即从面板消失（那一刻消息流已出「定时唤醒 · …」，
  再留终态就是重复）。`status` 用 `"waiting"` 而非 `"running"`，否则标题的
  「N 运行中」虚高、还会去订阅 250ms 旋转动画。

**6. 面板 = 现在怎样，消息流 = 发生过什么（§5.7.2 去重表的落点）。**

唤醒「挂着、几点触发」只进面板；消息流只在「安排」和「作废」两个时刻各出一行
（作废那行是 PR 1 做的）。所以 `TodoPanel` 的唤醒行**不显示**最新事件、不留终态。
`Ctrl+T` 隐藏面板时由 Footer 兜一句 `N 个唤醒等待中 · Ctrl+T`——否则用户隐藏后
会忘了它还在等，而唤醒到点会**自己**叫醒 agent（§2.4「凭空冒出来」的病灶）。

**7. 窄终端摘要改成按类型计数。**

`后台：1 shell · 1 agent · 1 唤醒`（对齐 CC 的 `getPillLabel`），各类计数为 0 时省略。
此前是逐个列 `agentType`，任务一多就把单行撑爆，而后半截恰好是最该看到的类型。

## 放弃了什么

- **独立的「等待区」/ 第三个区域**：见上面第 1 条。**这条最需要点破**——它是
  本仓真实踩过的坑（子代理进度那次），下一个 agent 不要以为等待态足够特殊、
  特殊到该有自己的区域。
- **状态栏 / 终端标题显示「等待中」**：与面板重复（§5.7.2 去重表第一行）。
  例外只有 `Ctrl+T` 隐藏时的那一句 Footer 兜底，因为它补的是「面板不可见」这个缺口，
  不是同一份信息的第二遍。
- **面板里显示「最新事件」**：正上方就是同一句话（§5.7.2 第三行）。事件只进消息流。
- **逐个选择 / 详情对话框**（§5.7.8）：CC 的 `BackgroundTasksDialog` 是独立 UI 工程，
  与「等待态」无关。第一版靠对话让 agent 调 `task_stop`，`/ps`、`bg_task_list` 已能列。
- **轮询调度器刷新面板**：面板刷新挂在 `notifyTaskChanged` 上（事件驱动），
  加定时器会让「即消失」变成「最多 N 秒后消失」。
- **`listTasks()` 取唤醒**：它每次都 `refreshDurable()` 读磁盘，挂在 UI 刷新路径上
  等于每帧一次磁盘 IO。新开的 `listSessionWakeups()` 只读内存。

**与方案的差异（如实记录）：**

- 方案把「删除 T2 等待瞬态状态条」列进 PR 2 范围，但**PR 1 已经删了**——
  `query/loop.ts:5013` 的注释明确写着「并删掉原来那行只进 TUI 瞬态状态条的
  `yield {kind:"system"}`」。本 PR 没有重复劳动，这一项无需再做。
- 方案写 Footer 提示文案是 `N 个监控 · M 个唤醒等待中 · Ctrl+T`。PR 2 只有唤醒
  （监控是 PR 3），所以当前实现是 `M 个唤醒等待中 · Ctrl+T`；
  `deriveWaitSourcesHint` 已按可扩展形状写好，PR 3 加 `monitors` 计数即可。
- 唤醒行描述取 `prompt.split("\n")[0]`（首行）而不是整段 prompt：
  面板一行放不下，完整内容在安排那一刻的工具卡片里。
