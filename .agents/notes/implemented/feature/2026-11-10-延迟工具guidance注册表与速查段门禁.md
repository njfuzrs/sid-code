# 延迟工具 guidance 注册表 + <deferred-tools-guidance> 速查段（FIX-5：D6）

## 决定了什么

D6 的根因：延迟加载的契约只覆盖「名字可见」（`<available-deferred-tools>` 只列名），不覆盖
「知道何时用」——引导靠逐能力手写段落，补了 cron（`<scheduling-capability>`）、monitor
（`<waiting-capability>`，FIX-3），其余 15 个内置延迟工具零引导。有引导的 `schedule_wakeup`
自然调用 18 次、无引导的 monitor 0 次。修法是**机制化**：引导从「手写段落」变成「工具自报 + 门禁」。

改动：

- `packages/core/src/tool/types.ts`：`ToolCapabilityFields` 新增 `guidance?`（何时该用，一句话），
  `bridge.ts` 的 `FORWARDED_KEYS` 同步透传（键表穷举，漏了 tsc 报错）。
- **18 个内置 `shouldDefer` 工具各写一句 guidance**（改各自的工具文件）：只写「什么时候选它」，
  不写参数细节（那些激活后经 `description` 拿到，写两遍是常驻成本）。
- `registry.ts` 新增公开入口 `getEnabledDeferredTools()`：与 `deferredToolNames()` 同口径
  （`isCurrentlyEnabled` + `isToolDeferred`，均为 private，门禁测试不能复制判定逻辑——必然漂移）。
- `system-prompt.ts` 新增 `buildDeferredToolsGuidanceSection()`：汇总全部延迟工具的 guidance，
  按名称排序（注册顺序变化不改段落内容，保 prompt cache 前缀稳定）注入
  `<deferred-tools-guidance>`。判据用 `partitionByDeferral`（`isStaticallyDeferred`，静态配置），
  与延迟分区同一口径——**不读运行时态**（`activatedTools` 等），本段落在 DYNAMIC_BOUNDARY 之前的
  静态前缀里，读运行时态 = prompt cache 前缀击穿（`deferred-tool-view.ts` 文件头约束）。
  `prompt-sections-en.ts` 加英文框架措辞。
- 门禁测试 `packages/core/tests/tool/deferred-guidance.test.ts`（10 条）：
  - **源码对账**：`scanShouldDeferFiles()` 扫 `tool/` 源码得出实际 `shouldDefer=true` 的文件集 ==
    期望清单（双向对账，新增延迟工具文件时先红，把它加进清单时必须同时构造它并写 guidance）；
  - **覆盖率 100%**：经 `getEnabledDeferredTools()` 遍历，每个内置 shouldDefer 工具 guidance 非空；
  - **MCP 工具不进门禁**（`mcp__` 前缀按前缀规则延迟、由 server 动态注册、无 guidance 落点）；
  - **与 D4 段不重复**：monitor 在速查段只出现一行，且不含 `run_in_background` / 轮询间隔 /
    沉默不等于成功（那些归 `<waiting-capability>`）；
  - 段行为：`toolSearch=false` 不出段、keepLoaded 豁免不进段、en 档框架措辞。
- 验收基建 `scripts/verify-monitor.ts`：新增 `D6-guidance-task-output` / `D6-guidance-workflow`
  两个场景 case（prompt 不出现工具名，测意图映射）；`analyzeDiscovery` 参数化 `target`
  （`monitorCalled` → `called`），判据同 `D4-discovery` 三档命中。

北极星方向：**更准**（延迟工具从「知道名字」到「知道何时用」）。牺牲**更省**：每个有延迟工具的
会话首轮 +683 token（实测，见下），落在静态前缀区，命中 prompt cache 后只付缓存读价。

## 放弃了什么（以及为什么不选）

- **方案 A（每个能力单独一段）**：18 个内置延迟工具 = 18 段，首轮 token 线性爆炸，且仍然没有
  门禁，下一个工具照样漏。
- **方案 C（`searchHint` 进 `<available-deferred-tools>`）**：`searchHint` 是搜索关键词不是
  使用场景，解决不了「何时该用」；且全部延迟工具 × 一行每轮都付。
- **MCP 工具进门禁**：`mcp__` 前缀工具由 server 动态注册，没有可加 guidance 字段的源码位置
  （方案 §D6 修复段 ⚠️ 明确收窄，本 PR 照此）。
- **cron / monitor 不进速查段**：不选。门禁按「全部内置 shouldDefer 工具」收口，它们保留一行——
  专属段（`<scheduling-capability>` / `<waiting-capability>`）哪天删除时该工具自动回落到速查段，
  不会零引导；两段按「专属段讲深度、速查段讲广度」分工，单测机械拦住重复。
- **en 档翻译 guidance 文案**：不翻。本仓语言规则明确工具文案保持原文（中文）；en 档只翻
  段落框架措辞（标题 / 激活说明），与既有段落（L3 的 en 档）同一口径。
- **方案伪代码的 `registry.isCurrentlyEnabled(t)` 直调**：private 方法，测试文件调不到。落地改为
  公开入口 `getEnabledDeferredTools()`（方案 §D6 修复段已预判并给出了这个修法）。

## 拿什么证明它生效了

```text

```

### 2. 段落真的进了请求体 + 首 token 成本（真实入口，不是单测）

`make build` 后 `-p` 起会话（非 git 工作目录，同一 prompt「把 ok 这个词原样输出给我」，
模型 `origin-deepseek-v4-1-flash`），读 `raw.jsonl` 首个 `usage.input_tokens`：

```text

修复后（本 PR 二进制，会话 20261110-170955-488e9544）：20771，guidance 段有
→ 首轮 +683 token（18 条 guidance，方案预期 550~650，实测略超；无延迟工具的会话该段不出现，零成本）
```
