# 新增 /perf：把已采集的性能指标做成用户能看的产品内出口

## 决定了什么

性能指标（TTFT、生成耗时、tok/s、端到端、工具耗时、上下文峰值）早就采集了，但缺出口：
跨会话趋势只能在仓库里跑 `scripts/northstar-snapshot.ts`，只装了二进制的用户看不到。

- 新命令 `/perf`（别名 `/performance`），实现在 `packages/cli/src/command/commands/perf/`：
  - `/perf [id|latest]`：单会话，看慢在哪一段（模型 vs 工具、TTFT 按 model、上下文峰值）
  - `/perf --days N`：近 N 天 vs 前 N 天，带判读（改善 / 变差 / ≈ / 样本不足 / ⚠）
  - `/perf --by-version`：按版本列出，就是 release 曲线的用户版
  - `--json`：机器可读
- 计算与渲染全部是纯函数，放在 `packages/core/src/trace/perf-report.ts`，命令层只做分派。
- 采集侧给 `session-index.jsonl` 补 5 个字段：`tps / gen_p95 / gen_n / tool_duration_ms / context_peak_ratio`。
  此前它们只写进 `session.traj`，而轨迹会被 LRU 清掉、索引不会，所以一清理趋势就断了
  （实测本机：索引 408 行，轨迹只剩 177 个）。两条写入路径（SessionEnd 权威行、增量行）共用
  `collector.perfIndexFields()`；`gen_p95` 需要 digest，只在权威行里给。
- `aggregateSessionMetrics` 新增 `gen_p95/gen_n`，与 `aggregateProviderStats` 的 gens 同源。
- 文档：新增 `website/use/performance.md`；侧栏「成本与用量」改为「成本与性能」组，下挂两页。

## 放弃了什么（以及为什么不选）

- **把 northstar 快照整体搬进 core 给 /perf 复用**：快照的视角是四个方向加一致性断言，
  服务于发版审计；/perf 要的是「慢在哪 + 有没有退步」。整体搬过去，会把发版口径
  （比如成本用均值）原样暴露给用户，还要拆一个 1700 行的脚本。所以只共用同一个数据源
  和同一套分位数规则（每会话一个值，再取分位，不对分位数求平均），算法另写一份更小的。
  代价是两处可能漂移；目前只有 TTFT / e2e 两项重叠，口径一致。
- **cost=0 的会话进成本分布**：实测本机近 7 天 48 个会话大半 cost=0（网关未回价），
  中位数塌成 $0，被判为「成本降 100%」。改成只统计已计价的会话，并在标签上写明。
- **在 `/stats` 或 `/telemetry` 里加延迟**：`/telemetry` 要先开 `telemetry.enabled`；`/stats`
  是当前会话面板，做不了跨会话趋势。都不是合适的出口。
- **TPOT / ITL、自动告警**：前者没有采集，后者需要调度。这次不做，文档里写明「还没有」。

## 拿什么证明它生效了

- `bun test ./packages/core/tests/trace/perf-report.test.ts`：16 pass。变异自证：把趋势判定里的
  `c.n >= MIN_TREND_SAMPLES && p.n >= MIN_TREND_SAMPLES` 改成 `true`，「样本不足不下结论」那条
  用例变红（15 pass / 1 fail），复原后全绿。
- `bun run affected-tests:run`：3451 pass / 0 fail。`make build` 通过。
- 用本机真实数据直接调用命令模块，三个视图都出了数：
  - `--days 7`：本期 48 / 上期 62 会话，TTFT P50 5.7s (n=13) vs 2.2s (n=57)，判「变差 ⚠」；
    按模型拆开看，本期 claude-opus-5-5 占 19 个会话、P50 11s。所以这次变差主要是模型组合变了，
    不是同一个模型变慢。这正是按模型那几行要回答的问题。
  - `--by-version`：0.1.600 到 0.1.609 共 10 个版本，tok/s 全部「无样本」。这是预期结果：
    这个字段从本 PR 起才写进索引，旧行没有。
  - 单会话：生成耗时 P95 1.0s，远小于 TTFT P95 33s。追查后确认是口径而非 bug：
    `stream_completed.elapsedMs` 从 lifecycle 创建（收到响应头之后）开始算，等待都落在 TTFT 里。
    渲染文案和文档已改成「响应头→流结束」，避免被读成「生成很快」。
- **还没验证的**：新字段要等下一次真实会话结束才会写进索引。合并后用 `sc-dev` 跑一次会话，
  `/perf --by-version` 那一行的 tok/s 应该从「无样本」变成有值，这才是端到端验收。
