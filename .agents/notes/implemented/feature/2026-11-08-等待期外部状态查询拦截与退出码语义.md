# 等待期外部状态查询拦截与退出码语义：把「在等」变成可判据的事实

## 决定了什么

两件事，一个共同目标：**让「模型在等外部状态」从一句提示词，变成 harness 能判、能拦、能少付钱的机械事实。**

**P1（轮询守卫覆盖前台外部状态查询）** 新增两个模块并接进主循环：

- `packages/core/src/task/status-query-commands.ts`——状态查询命令表（`gh pr checks|view|status`、
  `gh run view|list|watch`、`glab mr view`、`glab ci status`、`kubectl rollout status|get pods`、
  `curl …/health|status`）+ 归一化。表外一律返回 null。
- `packages/core/src/task/status-poll-guard.ts`——三条判据、回执、`BackgroundPollIntercepted` 事件。
- 接线在 `query/tool-executor.ts`：执行前 `checkStatusQueryPoll`（与 Q1 的 `checkBackgroundPoll`
  同一位置、同一收尾方式，区别只在判据），执行后 `recordStatusQueryResult`。

判据三条同时成立才拦（§5.5.1）：**有等待源**（`hasPromisedWait()`）+ **命令是只读状态查询**
+ **输出与上次实际执行时相同**。缺任何一条都放行。其中第一条是整个判据能成立的地基——
没有它时同一命令查 100 次也全放行，行为与改动前逐字节一致（T-P1-4 锁住），
这是与 2026-07-14 那份「工具循环检测默认关闭」否决的**根本区别**（那份否决的场景是
没有任何依据判断模型在等，这里是模型自己挂了 monitor / 唤醒）。

拦的阶梯按 §5.5.4：第 1 次观察到相同 → **放行 + 追加一行提示**（"结果与上次相同，
monitor 正在盯"）；第 2 次起相同 → **不执行**，回执带上次状态摘要、引用具体等待源、
注明上次查询时刻。

**E1（退出码语义表）** 不新建表，**扩展**已有的 `tool/bash/command-semantics.ts`：
`gh pr checks` 退出码 8 = 有检查 pending（`is_error=false`，首行写明「不是命令错误」）。
给 `CommandResultInterpretation` 加 `header` 字段（放结果首行）与既有 `message`（末尾附注）分工。

落地的关键决定：

1. **E1 复用既有语义表，不建第二张。** 方案 §5.6 写的是新文件 `tool/exit-code-semantics.ts`，
   但 `command-semantics.ts` 已经在做同一件事（grep 无匹配 / diff 有差异 / which 未找到），
   且 `bash.ts` 的调用点正是「包装非 0 退出码之前」那一步。建两张表必然漂移——那是本仓
   反复踩过的「两套尺子」同型病。所以 `gh` 作为一条 `CommandSemantic` 加进现有 Map。
2. **首行 vs 末尾。** 新增 `header` 而不是复用 `message`：`message` 追加在输出末尾
   （适合「无匹配」这种读过正文才知道含义的），`header` 放最前（适合「这个非 0 不是坏消息」
   这种必须先纠正判断的）。模型读结果的第一眼决定它要不要重试。
3. **写操作判据是白名单，不是 `isReadOnlyCommand`。** 后者是给权限放行用的，白名单刻意窄
   （`gh` 只认 issue/pr/repo，`curl` 恒非只读）。拿它做 P1 判据会把 `gh run list`、
   `curl …/health` 这些本想拦的查询全排除。P1 的判据改成「除最后一段外，每一段都必须
   命中查询表或落在 `HARMLESS_COMMANDS`（cd/echo/sleep/…）里，否则放行」——方向仍是宁可漏。
4. **签名只留语义字段。** `gh pr checks` 的 TSV 只保留 name + bucket（丢耗时与 URL）；
   `--json` 输出剥掉 `*At` / `duration*` / `elapsed*` / `url`；其余抹 `\d+(ms|s|m)` 耗时 token。
   耗时列每几秒就变，不抹掉则「结果相同」永不成立、拦截形同虚设；多抹则会吞掉真实变化。
   这与 `bg_task_list` 的 `taskListSignature`（「刻意不含耗时」）是同一把尺子。
5. **`external_status_poll` 复用 `BackgroundPollIntercepted` 事件。** F2 的取数源是
   「§1.1 计数减去本事件命中的 tool_use_id」，两类拦截都要从同一分母里扣；分开两个事件
   就要在两处扣、还可能漏扣一处。`kind` 已能区分。
6. **`UnchangedObservationRun.intervened` 终于有了真值。** 该字段此前恒为 `false`（那道阀
   只报不拦）。P1 拦截时用 tool_use_id 打标（带上限防泄漏），`loop.ts` 消费后写 `true`。

## 放弃了什么（以及为什么不选）

**§7.3 全局打开重复观测拦截（`UnchangedObservationRun` 转真干预）——仍然不做。**
2026-07-14 的否决记录（`.agents/notes/rejected/feature/2026-07-14-工具循环检测默认开启.md`）
在 42 个真实会话上实测 shape 检测误判率 ≈100%、exact 检测召回 ≈0。那份否决同时写明了
正确切法：「只读命令做输入 + 输出双重复检测」。本方案**没有推翻它**——P1 只在那份否决
指出的切法上多加了**一条前提**（模型自己有等待源），并不是把全局拦截打开。
没有等待源时行为不变，这一点由 T-P1-4（100 次全放行）和 MUT-10 联合锁住。

**方案 §9.3 的 T-P1-11 断言被改了，这是本次最需要 review 的一处。**
方案写「被拦条数 ≥ 80 且没有任何一条状态变化的查询被拦」。用触发会话
`20261108-112039-9e3a681d` 的 97 条真实命令回放，这两条**在数学上互斥**：
97 条查询只产出 23 种不同状态，即最多只能拦 74 条而不掩盖变化。原因不在实现，
在判据本身——拦截依据是「输出与上次**实际执行**时相同」，而拦截期间外部世界在变，
所以「拦住就永远看不到变化」是这个设计的固有代价（方案 §6.5 第 10 条承认的正是这一点，
它给的兜底是「monitor 会在变化时通知」）。

所以实现上补了一层方案没写的安全阀：**有 monitor 盯着同一 subject 时拦到底；没有时留
120s 探测窗口**。monitor 在场时它的通知就是兜底（方案的原意）；monitor 不在场时，
探测窗口把「可能错过变化」从无界压到有界。测试按实测写断言（命中 ≥ 90、拦截 > 60、
回执 100% 带状态摘要），不照抄方案那个互斥的数字——照抄会让这条测试要么永远红、
要么被改成不看内容。

**方案 §9.3 的 T-E1-5 数字也按实测修正**：方案写「45 条退出码 8」，实测该会话退出码 8
恰好 **44** 条，另 1 条是退出码 1（03:51:04 的 jq 表达式语法错）。夹具按实测生成。

**没有做「扩大命令表」这件事**：没有轨迹证据的条目（`gh pr diff`、`gh api`、
`gh workflow view`）一律不进表。方案自己写了「新增条目要带一条真实轨迹证据」，
这条约束比多拦几个查询重要。

## 拿什么证明它生效了

**变异自证三条（都是先改坏 → 确认对应断言变红 → 再恢复）**：

- **MUT-10**（P1 去掉「有等待源」前提）→ `T-P1-4`（无等待源 100 次全放行）与
  `T-P1-7`（等待源释放后不拦）双红，恢复后 19 pass。
- **MUT-11**（去掉 `gh pr checks` TSV 的耗时/URL 裁剪）→ `T-P1-2`、`T-P1-3`、`T-P1-9`
  与「TSV 摘要只数 bucket」四条红，恢复后 19 pass。
- **MUT-12**（语义表不看最后一段，改成整条命令含 `gh pr checks` 就算）→
  `T-E1-2`（`| head` 结尾不匹配）红，恢复后 8 pass。

**单测**：`bun test packages/core/tests/task/external-status-poll.test.ts` → 19 pass；
`bun test packages/core/tests/tool/exit-code-semantics.test.ts` → 8 pass。

97 条、`tests/tool/fixtures/exit-code-replay-7dd98bf5.json` 45 条），不是手写样例。

**类型检查**：`bun run typecheck:gate` → 62 处 / 基线 64，无新增。
