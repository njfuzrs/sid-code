# goal 默认轮次 150 → 300，并在 80% 处注入一次性软提醒

## 决定了什么

1. **`DEFAULT_GOAL_CONFIG.defaultMaxTurns` 150 → 300**（`packages/core/src/goal/config.ts`）。
   同时新增 `GOAL_TURNS_NEAR_LIMIT_RATIO = 0.8`，作为「接近上限」的唯一事实源。
2. **两处兜底收口到常量**：`createGoal`（state.ts:89）与 `deserializeGoalState`
   （state.ts:156）原本各写一个 `?? 150`，现在都走
   `?? DEFAULT_GOAL_CONFIG.defaultMaxTurns`。改默认值时不会再出现「改了一处、
   旧会话恢复仍按 150 算」的半修状态。
3. **80% 软提醒**：`GoalState` 新增 `softLimitWarned?: boolean`；`reminder.ts` 新增
   纯判定 `shouldWarnNearTurnLimit` 与文案 `buildNearTurnLimitReminder`；
   `loop.ts` 的 goal 状态回注段（`turnsUsed++` 之后、发请求之前）每轮判定一次，
   首次命中时置位、注入一条 system-reminder、发一条 TUI warning、写一条
   `GoalReminderInjected{reason:"near_turn_limit"}` trace。
4. **两个消费方共用一个阈值**：cli 状态栏 `deriveGoal` 的 `nearLimit` 从字面量
   `0.8` 改为 import `GOAL_TURNS_NEAR_LIMIT_RATIO`；`/goal status` 的提示文案
   与 `website/use/plan-mode.md` 的默认值表格同步。

## 放弃了什么（以及为什么不选）

- **放弃「软提醒挂在 end_turn 的 `handleGoalGate` 里」**。那是最省事的位置（改动只
  一个文件），但它和轮次硬上限目前有完全相同的缺陷：连续 `tool_use` 空转时根本走不到
  end_turn —— 而 G6 放宽默认轮次的动机之一正是这类长任务空转（方案 §3.6：「只调默认值、
  不修 G1/G2，等于把空转上限从『无』换成『无』，再把下次修好之后的失控面放大一倍」）。
  挂回 end_turn 等于把要修的缺陷当成落点。改挂 `loop.ts` 每轮必经的回注段后，
  提醒在空转场景下照样触发，且不依赖尚未合入的 G1 `limits.ts`。
- **放弃「等 G1 合入后再做 G6」**。方案 §4.4 的前置写着「不允许先于 G1 单独合入」，
  但 G1 正在并行会话（`fix-goal-hard-limits`）里在途开发；而 G6 的默认值与软提醒
  可以做成**不依赖 `limits.ts`** 的独立落点（见上一条）。先合的实际风险为零：
  当前 `maxTurns` 硬上限本来就只在 end_turn 生效，放宽默认值不改变任何已被执行的
  上限；软提醒本身是纯增益。已在 PR 描述里显著标注这个合入顺序与理由，供 review 否决。
- **放弃「0.8 在 core 与 cli 各写一遍」**。两处漂移时没有任何东西会变红：状态栏黄了
  但模型没收到提醒（不知道要收尾），或模型收到提醒但状态栏还是灰的（用户以为很宽裕）。
  收敛成常量后，两个消费方在编译期绑定。
- **放弃「把 `agentic-loop-*.test.ts` 里的 `maxTurns: 150` 也改成 300」**。逐条确认过：
  那些是测试**显式指定的上限**（用于构造「轮次耗尽」场景），不是对默认值的断言。
  改成 300 会让测试意图变模糊，且跑得更久。
- **放弃「默认 maxTurns 设为 Infinity / 只靠软提醒」。** 硬上限是失控的唯一兜底；
  去掉就等于「跑满 300 轮之后继续跑」，与方案的双闸设计相悖。
