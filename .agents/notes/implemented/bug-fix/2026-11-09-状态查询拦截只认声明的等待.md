# 状态查询拦截只认声明的等待，回执不再谎报（D12 / D13 / D14）

## 决定了什么

P1（等待期前台状态查询拦截）的三处判据与回执各改一处，均为**收紧**方向：

1. **D12 判据 1 换成 `hasDeclaredExternalWait()`**（`task/wait-registry.ts` 新增）。
   旧判据 `hasPromisedWait()` 含派生出来的子代理 / workflow / 普通后台 shell，它们承诺的是
   「**自己**结束时会回报」，不是「查询的那个**外部对象**变化时会回报」。实测 R10：模型起了一个
   无关的 `bun test` 后连查 `gh pr view` 被拦，回执还说「状态变化会以通知送达」——没有任何东西在盯 PR。
   新判据只认三类**显式登记**：monitor、唤醒、`wait_until` 后台命令（`promise.kind === "deadline"`）。
   `checkStatusQueryPoll` 的 `StatusPollContext` 字段随之改名（`hasPromisedWait` → `hasDeclaredExternalWait`），
   杜绝两个问题再共用一个函数。T2 闸门仍用宽口径，不变量不变。

2. **回执不再 fallback**（`task/status-poll-guard.ts` 新增 `describeWaitRelation`，回执与首次提示共用）。
   旧实现 `waits.find(...) ?? waits[0]` 会拿一个无关等待源说「状态变化会以通知送达」。
   新文案只引用**模型自己声明**的等待，并按种类区分：只有 monitor 覆盖了本对象才说
   「状态变化会以通知送达」；唤醒 / `wait_until` 一律是「它只是一个定时器，到点才会再看，
   期间状态可能变化」；只剩异对象 monitor 时如实说「它不盯这个对象」。普通 shell / 子代理的 id
   永不出现在回执里（E2E-16 的判据）。

3. **D13 覆盖判定从对象粒度收紧到「monitor + subject + 命令族」**。
   `WaitSource` 新增可选 `commandFamilies`；`MonitorTool.call` 登记时用
   `extractStatusQueryFamilies(script)` 扫脚本；`covered` 要求三者同时命中。
   扫不出（自定义脚本）→ 空数组 → 视为不覆盖 → 回到 120s 探测窗口。
   **这是更准 ↔ 更省的取舍点**：monitor 没报告的字段每 120s 放行一次，
   `fg_status_polls` p95 会比「拦到底」略高。方案 §5.3 允许从 ≤5 放宽到 ≤8，本文按该口径落地
   （理由与数字见 PR 正文，不是静默改目标）。

4. **D14 P1 拿加工前输出**。`bash` 在 `interp.header` 非空时填 `meta.rawOutput`（加 header 之前的
   `output`，不进模型上下文），`tool-executor` 优先读它；同时 `normalizeChecksTsv` 容忍
   「首行等于 `GH_CHECKS_PENDING_HEADER`」的形态（该常量从 `command-semantics.ts` 导出，
   两处逐字同源）。两道都留，与 `markNotificationsDelivered` 的做法一致。

**与方案的一处刻意偏离（D13）**：方案写的是 `WaitSource.commandKinds?: StatusQueryKind[]`，
按 `StatusQueryKind`（`gh_pr` / `gh_run`）判覆盖。但方案自己的验收复现是「monitor 只跑
`gh pr checks`，模型查 `gh pr view --json reviewDecision` → 第三次放行」——两者同为 `gh_pr`，
按 kind 实现这条验收永远不可能绿。所以细到**子命令族**：新增 `StatusQueryFamily`
（`gh_pr_checks` / `gh_pr_view` / `gh_run_view` / …），字段名取 `commandFamilies` 而非
`commandKinds`（名字要能读出内容）。`matchStatusQuery` 的返回值增加 `family` 字段。

## 放弃了什么（以及为什么不选）

- **把「存在盯同一 subject 的等待源」当硬前提（没有就不拦）**：9e3a681d 的事故场景是
  唤醒在等、没有 monitor——唤醒不盯对象、只是定时器。这个前提会让 P1 在最需要它的场景失效。
  所以「仅唤醒」格必须是拦截（D12-4 锁住）。
- **按 `StatusQueryKind` 实现 D13**：见上，无法通过方案验收，且真实事故正是同族不同子命令。
  代价是每条命令规则都要多给一个 `family`（新增规则漏给只会退回「不覆盖」，保守方向）。
- **给「monitor 在场」也设一个大的探测间隔（600s）**：最坏情形有界，但不区分查询是否被覆盖，
  对被覆盖的查询白白多放行。字段级判断更准；兜底方案留作后续另议（YAGNI）。
- **把 header 挪到输出末尾**：方案 §5.6 与 `bash.ts` 注释明说首行是有意的（模型读结果的第一眼
  决定重试还是改道），为了 P1 挪位置会回退 E1 要解决的 G8。
- **只靠 `meta.rawOutput`，不做剥首行容忍**：`meta` 属于轨迹侧通道，未来若有工具绕过
  `bash` 直接产 header 就失守；只靠剥首行则绑死在一句文案上。两道互补，且真实入口用 JSON
  形态（带 header 的文本不是合法 JSON）使两道防线各自可被变异单独命中。
