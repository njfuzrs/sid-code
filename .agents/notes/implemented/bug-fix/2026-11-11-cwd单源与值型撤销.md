# CG-1：cwd 分成「当前位置」与「工作区根」两层，并给 bash 的 cd 加带作废声明的持久块

## 决定了什么

**一、`process.cwd()` 不再承担两种语义（R1/R2/R3）。**

回源码核过：`process.cwd()` 的实际语义是「工作区根」——只有 `switchCwd` 会改它，
而 `switchCwd` 只在进出 worktree 时调用；bash 的 `cd` 只写 `state.cwd`。于是同一个
`process.cwd()` 在不同调用点被读成了两种东西，两种都错了一半：

| 语义 | 读哪个 | 本次改到的点 |
| --- | --- | --- |
| **当前位置**（模型此刻在哪执行） | `getCwd()` | 4 处 `workingDir`（`init-helpers.ts`、`app.ts` ×2、`memory.ts`）、JIT 相对路径基准（`app.ts` `discoverJitContext`） |
| **工作区根**（项目身份：规则、记忆、hook projectDir） | `getProjectRoot()`（复用现有函数） | `loadAllCLAUDEmd` ×5、`MemoryStore` ×8、团队索引 ×4、`hookSystem.setProjectDir`、`getSessionMemoryPath` / `initSessionMemory` / `ensureAutoMemPath` / `startTeamMemoryWatcher` |

隔离子代理找 git 根（`agent/tool.ts`）**刻意保留 `process.cwd()`**，理由见下一节第 7 条。

`enter_worktree` 找 git 根原本就读 `getCwd()`，未改。

**二、cwd 变更改成「值型」出口，带作废声明（R4）。**

`bash` 的 `cd` 写回时，如果**跨出或回到工作区根**，就经 `ctxMgr.recordWorkspaceNotice`
排一条持久块；`query/loop.ts` 已有的消费点把它包成
`<working-directory-change>…</working-directory-change>`，标签与消费点都沿用，不新增。

通知正文（中/英双语，按 `resolveEffectiveLanguage` 选）：

> 工作目录现在是 X。此前上下文里关于工作目录的说法（包括系统提示里的 `<working-directory>`）以本条为准。

接线方向是 `App` 在 `ctxMgr` 就绪后向 `BashTool` 注入回调（`setCwdSwitchListener`），
与既有的 `setSandboxManager` / `withFileReadTracker` 同向；bash 工具不反向 import
`ContextManager`，避免 core 工具层 → CLI 的环。

原有的 `cwdChangeNotice`（tool_result 尾注）**保留**：它给的是「这一轮立刻可见」，
持久块给的是「后续每轮都看得见旧说法已作废」，两者不是替代关系。

**三、报错带路径（R5）与测试 0 匹配提示（R6）。**

`enter_worktree`、`/worktree` 的「不在 Git 仓库」报错改成带「检查过的目录 + 三选一的下一步」。
判据取 `getCwd()`，与工具实际执行目录同源。

`bun test` 匹配 0 个文件时在结果末尾追加「没有匹配到测试文件 + 两条核对方向」，
不动 `isError`。

## 放弃了什么（以及为什么不选）

1. **不新增 `getWorkspaceRoot()`**。源码里已有语义一致的 `getProjectRoot()`
   （`bootstrap/state.ts`：启动时设为 `process.cwd()`、注释写死「项目身份（启动时设置，不变）」、
   `switchCwd` 不碰它）。再包装一层会让两个语义相同、名字不同的函数并存，
   CG-5 的 G-b 门禁入口随之分裂。
2. **不做「全部 `process.cwd()` 换成 `getCwd()`」**（02 文档 PR-S1 的原始口径）。
   那样 bash `cd /tmp` 之后的第一次提示词重建会把项目规则整个丢掉，比原来的问题更糟且**静默**。
   分层是后续规划 §2.1 的裁决，本文按它执行。
3. **cwd 通知不做「每次 cd 都发」**（D1 的选项 ①）。选 ②：只在离开或回到工作区根时发。
   依据是全量 3242 次 cd 里有 1738 次落在仓库外，仓库内部的 cd（`cd packages/core`）
   不会让 `enter_worktree` 或 git 失败，每次都发纯属烧 token。D1 在文档里是「待拍板」，
   按推荐项开工，若日后数据表明仓库内 cd 也出过事再放宽。
4. **不新起 `<state-change>` 标签**。沿用 `<working-directory-change>`，
   `loop.ts` 的消费点一行不用改，缓存前缀也不受影响。
5. **`bun test` 的 0 匹配不改成错误**。实测（bun 1.4.2）这条命令的退出码**本来就是 1**
   ——01 文档 C1 写的「退出码 0」不准。所以 `isError` 已经是对的，本改动只补「为什么失败 + 下一步」。
6. **没有把 `MemoryDialog` 的 `cwd` prop 一并改掉**。它来自 UI 组件的显式 prop，
   不属于「裸写 `process.cwd()`」，改它要连带改 `DialogSwitch` → `BottomRegion` 的传参链，
   超出 CG-1「消除裸写」的范围。
7. **隔离子代理找 git 根（`agent/tool.ts`）保持 `process.cwd()` 不变**。文档 §2.1 的表格
   把它列为「工作区根」，但同一份文档的 F1 又明确写「**不改**：用工作区根是对的」——
   现状已经是对的：`process.cwd()` 不跟 bash 的 `cd`（cd 只写 `state.cwd`），
   `findGitRootForAgent` 又会 canonical 化到主仓，真实场景与 `getProjectRoot()` 等价。
   **这是 CI 首轮教我的一次取舍**：我按表格改成了 `getProjectRoot()`，5 条 B14 隔离回归
   测试立刻红（它们用 `setCwd()` 表达「会话工作区」，而 `getProjectRoot()` 不跟 `setCwd`）。
   收益只是语义显式，代价是动 5 条守 worktree 隔离的既有断言 —— 不成比例，已回退。

离线判据之外，还有一个**结构信号**来自实现过程中撞到的真问题：
`isUnderWorkspaceRoot` 最初没做 realpath 归一化，测试立刻红了两条
（`tmpdir()` 是 `/var/folders/...` 而 `pwd -P` 给 `/private/var/folders/...`）。
这不是测试写错，是生产路径上同样的坑：macOS 上「根内部的 cd」会被误判成「跨出根」，
通知一去一回刷两条。已修并在函数注释里写明原因。
