# continue 路径封顶、发送错误单入口、闸门耗尽语义定稿 + continue 收敛度可观测

来源：对照 `docs-research` 的《AgenticLoop 从零到一》§4「continue 的十五种理由」回源码核出三个缺陷，再按本机 401 个会话轨迹核实。

## 决定了什么

1. **`model_context_window_exceeded` 有界**（`query/loop.ts`）。
   - 规则：压不动就立即收尾；压得动也只续写 `MAX_CTX_WINDOW_RECOVERIES = 2` 次，与子代理 `agentic-loop.ts` 的 B5-1 同值、同取向。
   - 收尾时：`done.incompleteReason = "context_window_exhausted"`，SDK 映射为 `error_during_execution`，无头 probe 记 failed；同时补齐孤儿 tool_use 的占位 tool_result。
   - transition 改记专属的 `context_window_recovery`，不再冒用 `max_tokens_continuation`。
   - 删掉这条分支里的 `maxOutputTokensRecoveryCount++`。它会让之后真正撞 max_tokens 时失去 Stage 1 的「先提高上限」：escalate 只在计数为 0 时才会尝试。
   - 压缩失败也走 `settleCompaction`，落一条 `CompactionAttempt`（此前只写 warn.log）。
2. **发送错误只有一个处理入口**。
   - 删掉「连接阶段」try/catch 整段（约 130 行）。它结构上不可达：生产 `sendWithRetry` 是 `async *executeWithFallback`，调用时只返回迭代器，不会同步抛错。本机 39 条 errors.jsonl 里 `phase=connection` 为 0。
   - 非生成器实现（测试替身）的同步抛错：调用时捕获，在流式 try 的第一行原样重抛，与流式错误共用一个 catch。
   - 随之删除 `handleContextOverflow`（deps 字段、engine 透传、app.ts 实现、auto-compact.ts 函数、28 个测试 mock），以及 recordError phase 联合类型里的 `"connection"`。
3. **闸门耗尽语义定稿**（唯一事实源 `query/gate-exhaustion.ts` 的 `GATE_EXHAUSTION_EFFECT`）。
   - **退化类**（unanswered / empty_param / context_window）：耗尽后整条链收尾。这是已有行为，本次只是写成表、加上测试锁住。
   - **质量闸门**（stop_hook / todo / hypothesis / promise_nudge）：耗尽后只是本门不再续命，后续门照常判定。
   - **用户授权续跑**（token_budget / goal）：按各自的判据终止。
   - 耗尽日志改成「本门放行（后续闸门照常判定）」，不再写「放行」，让日志和实际行为一致。
4. **可观测性 / 数据层**。
   - **新事件**：`GateExhausted {gate, effect, retries, cap, promptSeq}`，每条消息每道门最多一次。
   - **`setTransition` 维护的计数**：这是 continue 理由的唯一写入点，在这里维护 `continueCounts`、`maxContinueStreak`。游程不计 `tool_use`，且 `tool_use` 会打断其它理由的游程。
   - **`TurnComplete` 新增字段**：`continue_counts`、`max_continue_streak`、`gates_exhausted`。
   - **digest**：新增 `continuePaths` 节，有两个恒为 0 的北极星项：
     - `overCapPrompts`：游程超过 `CONTINUE_STREAK_CAPS` 的消息数；
     - `continuedAfterChainEnd`：退化门耗尽后，同一条消息里仍出现闸门续命的次数。
   - `northstar/README.md`「更准 ①」补了这一行。

## 放弃了什么（以及为什么不选）

- **「任一闸门耗尽即整条链收尾」**（把 P1-3 推广到所有门）：
  - 质量门耗尽只说明这项检查劝不动了，不说明用户想停。`/goal`、`+500k` 恰恰是用户在授权继续，让 todo 耗尽连带掐掉 goal，等于用一道门的失败否决另一道门的授权。
  - Stop Hook 先于 hypothesis，若 Stop Hook 耗尽（lint 仍红）就收尾，未裁决的假设会被当成结论交付，而这正是 hypothesis 门要拦的。
  - 每道门都独立封顶，续命总次数是各门上限之和，有界。
- **耗尽后只跳过「会 continue 的门」、保留「只提示的门」**：这需要给每道门再标一维属性，而上面的三分法已经能回答所有组合，多一维只会多一个漂移点。
- **把 `handleContextOverflow` 挪进流式 PTL 分支，而不是删掉**：
  - 它的判据是「报错文本含 context 或 token 就算」，然后把 **max_tokens（输出上限）** 调到「窗口 − 输入 − 1000」。
  - 本机 8 次 PTL 全部是「Input tokens exceed the model context limit」，输入已经超窗，调小输出救不回来，只会多发一次注定失败的请求。
  - 真正有效的 PTL 恢复（reactiveCompact + 熔断）在流式阶段一直都有。
- **用 `async function*` 包一层，把同步抛错延迟到首次迭代**：试过了，有 18 个测试红。替身 `processStream` 往往不迭代 stream，错误会凭空消失；而且请求发出的时机也被推迟了一拍。改成「捕获后在流式 try 首行重抛」。
- **在 ctx-window 分支复用 `consecutiveCompactFailures >= 3` 熔断**：那是会话级、跨路径的计数，含义是「连续失败」。本分支压不动时第一次就该停（再试必撞同一上限），等它攒到 3 是白烧两次。保留它的累加（让别的路径的熔断看到这次失败），但不拿它当本分支的判据。
- **`CONTINUE_STREAK_CAPS` 收录所有理由**：
  - `timeout_retry` 的上限可配置；
  - `max_tokens_*` 靠递减收益检测终止；
  - `loop_recovery` 有检测器内部的计数和软重置；
  - goal / token_budget 是用户授权，按预算或评估结论终止。
  - 这些都没有固定上限，硬写一个数只会制造假告警。
- **本 PR 同步改 docs-research 那篇文档**：用户明确说文档漂移暂不处理。

## 拿什么证明它生效了

- **新测试** `packages/core/tests/query/continue-path-caps.test.ts`：13 pass，覆盖三个问题、TurnComplete 字段、反漂移锁、digest 聚合。
- **变异自证**：7 处逐一改坏，每次都只有对应用例变红，恢复后全绿。
  - M1 去掉上限检查 → 2 fail
  - M2 压不动仍续写 → 1 fail
  - M3 恢复 `maxOutputTokensRecoveryCount++` → 1 fail
  - M4 同步抛错不重抛 → 1 fail
  - M5 todo 耗尽不落事件 → 1 fail
  - M6 tool_use 不打断游程 → 1 fail
  - M7 digest 不判收尾后续命 → 1 fail
- **全量门禁**：
  - `bun test` → 17514 pass / 10 skip / 0 fail
  - `make build` → 自检通过，`will always be undefined` 0 条
  - `bun run lint` / `format:check` / `lint:boundary` / `lint:command-system` / `typecheck:gate`（66/66）全绿
- **端到端**：用本 worktree 构建的二进制跑一次 `-p`（read 一个文件再作答），落盘的 `TurnComplete` 带 `"continue_counts":{"tool_use":1}`；`bun scripts/trace-digest.ts <id>` 渲染出「continue 路径: 超封顶 0 收尾后续命 0 / 1 条消息」。
- **数据侧预期**（上线后验证）：
  - `continuePaths.overCapPrompts` 和 `continuedAfterChainEnd` 应恒为 0；
  - `CompactionAttempt{trigger:ctx_window_exceeded}` 第一次出现时，应伴随 ≤2 次 `context_window_recovery`；
  - `errors.jsonl` 不再可能出现 `phase=connection`（类型已收窄）。
- **未覆盖**：本机 14,066 次模型调用里 `model_context_window_exceeded` 为 0 次（OpenAI 映射产不出这个值，只有走 Anthropic 协议的 Claude 4.5+ 会返回），所以问题 1 没有真实轨迹样本，只有用例和变异证明。
