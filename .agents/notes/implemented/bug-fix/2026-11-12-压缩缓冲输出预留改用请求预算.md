# 压缩缓冲的「输出预留」改用请求预算，不再取模型物理上限

## 决定了什么

`ContextManager` 的完成缓冲区（completion buffer）里，输出预留分量从「模型 / 渠道的物理输出上限」
改成「本次请求的输出预算」：

- `ManagerOptions.maxOutputTokens` → `requestOutputBudget`，私有字段与 setter 同步改名
  （`setMaxOutputTokens` → `setRequestOutputBudget`）。语义从「模型最多能输出多少」
  变成「本次请求打算预留多少」。
- 新增 `packages/core/src/llm/output-budget.ts`，先落「预算基准」这一半：
  `DEFAULT_REQUEST_MAX_TOKENS = 32_768` + `resolveRequestBudget(explicitMaxTokens?)`
  （用户显式值 > 默认常量，不含任何钳制；发送侧的物理上限 / 窗口钳制由 F1 在同一文件扩展）。
- `packages/cli/src/app.ts` 四处传参点（构造 + `/model` 切换 + 配置重载 + 恢复路径）
  改为传 `resolveRequestBudget(config._explicitMaxTokens)`；三处切模型路径不再把新模型的
  `getMaxOutputTokens()` 一起塞进 `setMaxTokens`——预算不随模型变，随模型变的是窗口。
- `COMPLETION_BUFFER.DEFAULT_OUTPUT_RESERVE`（16k）保留为「未注入预算」时的兜底。

效果（1M 窗口）：输出预留 120k → 32,768，completionBuffer 140k → 52,768，
emergency 触发用量 860k → 900k；hard 档仍由 18% 相对门槛（180k）主导，不变。
200k 与 80k 窗口下两种取值都落到 12% 比例钳制，行为零回归。

## 放弃了什么（以及为什么不选）

- **继续传物理上限、只靠 12% 比例钳制兜底**：钳制只是让错误值不至于太离谱，
  名字与语义仍然不一致；换一个窗口更小、输出上限更大的模型，缓冲又被抬高一次。
  这正是排查报告 §4 原则 3「一个名字一个语义」要根治的东西。
- **在 `ContextManager` 内部直接读 `config` / env 解析预算**：会让 manager 依赖全局配置，
  破坏「构造参数注入、可多实例、可单测」的现状；预算解析放在 `llm/output-budget.ts` 纯函数里，
  主循环与压缩侧共用同一个来源。
- **把 F8 并入 F1 一起做（方案原计划 PR-1 = F1 + F8）**：F8 是独立的「同名不同义」缺陷，
  能独立上线、独立回滚（回滚 = 恢复传物理上限），且不依赖 F1 的发送侧钳制。
  F1 的在途改动（config.ts / loop.ts / output-budget.ts 完整版）与本改动不冲突：
  本 PR 只占 `output-budget.ts` 的常量与预算基准函数，F1 在其上扩展完整钳制。
- **让 `setMaxTokens` 继续接收第二个参数并在切模型时重设**：切模型时传预算会让
  同一份用户配置在不同模型上得到不同的缓冲量级，属于把「模型属性」重新混进预算。

## 拿什么证明它生效了

- 单测：`bun test ./packages/core/tests/context/manager.test.ts ./packages/core/tests/llm/output-budget.test.ts`
  → 46 pass / 0 fail。新增用例锁住 1M 窗口 `completionBuffer = 52_768`、`emergencyRemaining = 100_000`、
  `compressionRemaining = 180_000`，并用 `requestOutputBudget: 384_000` 作对照组锁住「物理上限不能进预留」。
- 变异自证（两次，均先改坏再恢复）：
  - 把 `outputReserve` 临时固定为 `384_000`（模拟旧行为）→ 2 个 F8 用例变红，恢复后 2 pass；
  - 把 `resolveRequestBudget` 默认值临时改成 `16_384` → output-budget 用例 2 fail，恢复后全绿。
- `bun run affected-tests:run` → 5644 pass / 9 skip / 1 fail。失败项是
  `packages/cli/tests/sdk/wait-criteria-source-guard.test.ts` 在整批 460 文件同进程跑时
  11.1s 超过 bun 默认 5s 超时；单跑该文件 3 pass（65ms），与本改动无关（它只扫描
  `packages/cli/src` / `packages/core/src/sdk` 的旧等待判据字面量）。
- `bun run typecheck:gate` → 无新增类型错误（62 处 / 基线 64 处）。
- `make build` → 产物自检通过；`bun run smoke` → 26 例全过（含 A6-compact、A7-budget-exceeded）。
- `bun run lint` / `format:check` / `lint:boundary` / `lint:command-system` / `lint:legacy-tool` 全绿。
- 旧名字残留扫描：`grep -rn "setMaxOutputTokens\|maxOutputTokens:" packages/*/src packages/*/tests`
  无命中（测试里 `maxOutputTokens: [0-9]` 的命中都是模型能力目录字段，与 manager 选项无关）。
