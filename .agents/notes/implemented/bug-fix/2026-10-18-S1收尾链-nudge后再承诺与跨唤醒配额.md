# S1 收尾链：nudge 后再承诺照出 L1 提示，nudge 配额按用户 prompt 计（复审 B1/M6/D7/T7）

## 决定了什么

- **B1**：`classifyEndTurnShape` 新增输入 `afterPromiseNudge`。loop 在本次响应是在回应刚注入的 L2 nudge 时置 true，此时即使上一次响应（那句承诺）没调工具，也按「工具之后」走形态判定。「工具 → 承诺 → nudge → 再承诺」最后一轮因此仍是 `promise_after_tools`：L1 常驻提示照出，计入 `short_text_end_turns`，第二次 nudge 被 `capped` 挡住。
- **M6**：`promiseNudgeCount` 与 `prevResponseHadToolUse` 每轮写回 `SessionState`（键 `S1_PROMPT_CARRY_KEY`）。`QueryLoopConfig.continuation=true`（只有 `QueryEngine.resumeWithNotifications` 传）时从这里继承，新 prompt 时归零。同一 prompt 下的空闲唤醒不再每次多给一次 nudge 配额；唤醒后首轮的「上次含 tool_use」也接得上。`types.ts` 注释改正为「只在新的用户 prompt 时重置」。
- **D7**：L2 的触发条件看响应 content 里有没有 `tool_use` 块，不看 `stop_reason=tool_use`。这是有意为之，`loop.ts` 加了注释说明理由：fall-through 的「声称 end_turn 却带 tool_use」会照常派发工具，按块判才符合事实。
- **T7**：`plain-text-end-turn-notice.test.tsx` 新增一组驱动真实 `queryLoop` 的用例。按 app.ts 的路由，在 persistent 事件到达时用 `ctxMgr.getMessages().length` 取锚点，`done` 后从同一个 ctxMgr 全量重建，断言提示在 done 之前到达，并紧跟最后那句承诺。

## 放弃了什么（以及为什么不选）

- **在 nudge 之后把 `state.prevResponseHadToolUse` 硬置 true**：会污染 `PromiseNudge.outcome`（它读的就是这个字段，判 nudge 之后有没有真调工具），也会污染 EndTurnShape 的 `prev_turn_had_tool_use` 事实。改成单独传一个输入，事实字段保持原样。
- **计数挂在 engine 层按 promptSeq 保存**：`promptSeq` 每次 queryLoop 都 +1，续跑也算一次（缺口7 的既有口径），它不能代表「用户 prompt」。改它会动到所有埋点的分组口径。由调用方显式声明 `continuation` 更直接。
- **只继承计数、`prevResponseHadToolUse` 照旧归零**：唤醒续跑的首轮一般是读通知后再干活，如果第一句就是承诺，会被判成纯问答而静默。复审要求两者一起评估，这里一起继承。
- **D7 改成按 `stop_reason` 判**：fall-through 的响应会派发工具，按 stop_reason 判反而不符合事实；影响面小，保留现状并写明理由。
- **T7 拉起整个 App 闭包测 `appendPersistentHint`**：App 没有可单测的脚手架。用真实 loop 事件流加 app 的同口径锚点，再配上原有的 app.ts 源码路由断言，覆盖了锚点口径这个未验证点。

已知盲区：`continuation` 只由 `resumeWithNotifications` 传。SDK / Bridge 走的也是这个方法，所以自动覆盖；但如果将来新增续跑入口忘了传，会退回「每次重置」，属于少拦一次，不是误拦。engine 层用源码断言锁住了现有入口。
