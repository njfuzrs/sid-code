# 窄终端摘要按全量统计与 monitor 工具字段补全（D16 / D17）

## 决定了什么

### D16：摘要统计口径改为全量，终态过滤收进 `compactSummaryText`

`packages/cli/src/ui/components/TodoPanel.tsx`：

- `compactMode` 的摘要调用从 `compactSummaryText(visibleTasks)` 改为 `compactSummaryText(tasks)`；
- `compactSummaryText` 内部先过滤终态任务（core 的 `isTerminalStatus`），再按类型计数。

根因：`visibleTasks = windowed.slice(0, 5)` 是「屏幕放得下」的那部分，而摘要的语义是
「屏幕放不下时仍告诉用户一共有什么」。50 列下 3 monitor + 1 唤醒 + 2 shell 时，唤醒是第 6 条
被挤出视口，旧实现摘要只剩 `2 shell · 3 监控`。终态不计入摘要（它说的是「还在后台的」），
过滤放在函数内部而不是调用方——下一个调用点不会再传错集合。

### D17：`bg_task_list` 状态签名补 monitor 事件数；三个工具补 monitor 字段

- `packages/core/src/task/background-poll-guard.ts` 的 `taskListSignature` 对 monitor 追加
  `:ev${eventCount}`，与子代理的 `toolUseCount` 同一位置同一写法；
- `packages/core/src/tool/task-list.ts` / `task-get.ts` / `task-output.ts` 各加一支
  `isMonitorTask`：输出 `<deadline>`（本地时钟）与 `<event-count>`；`task_get` 另输出
  `<command>`（截 500，与 shell 同）；
- `formatClockWithSeconds` 从 `tool/monitor.ts` 的私有函数移到 `task/monitor-text.ts` 导出——
  三处输出必须是同一个本地时钟口径，复制三份会再漂移一次。

根因：签名只拼 `id:status[:toolUseCount]`，monitor 从 0 条收到 2 条新事件后第二次查询
仍被轮询守卫当成「状态相同」拦掉；三个工具只处理 `isAgentTask` / `isShellTask`，
模型想问「最晚几点结束、已经报了几条」得去读 `.output` 文件。

本 PR 的后续 commit 追加了 D19 / D20 与 L4 的四条测试缺口（含 T-T1-8 的等值断言），
见同目录 `2026-11-09-窄终端摘要与monitor事件合并.md`——两份合起来是完整的 FIX-6。

## 放弃了什么（以及为什么不选）

- **D16 把终态过滤放在每个调用方**：调用方目前只有一处，但摘要口径是「全量减去终态」，
  放在调用方等于让每个新调用点重新记住一遍；放函数内部只写一次。
- **D17 让三个工具各自从 `tool/monitor.ts` 导入 `formatClockWithSeconds`**：工具之间互相
  import 会把 `monitor.ts` 的模块副作用（schema、权限逻辑）带进三个查询工具；移到
  `task/monitor-text.ts` 后依赖方向是 tool → task，与既有分层一致，也延续了 D18
  「monitor 展示文案/格式单一来源」的约定。
- **给 `bg_task_list` 的 monitor 加 `<command>`**：文档只要求 `bg_task_get` 加；列表页已有
  `<description>`，再加 command 会让输出膨胀，模型要看命令可以走 `bg_task_get`。
- **把 `eventCount` 也塞进 `bg_task_list` 的「运行中」拦截回执**：回执已带任务 id 与耗时，
  且本次调用会被放行（签名已变），模型马上就能看到新计数，回执里重复一遍没有收益。
