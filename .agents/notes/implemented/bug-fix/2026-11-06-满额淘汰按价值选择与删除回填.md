# 记忆满额淘汰按价值选择，删除时回填被挤走的记忆

## 决定了什么

修 2026-11-06 事故（会话 `20261106-153208-aee98a86`）：满额 200 条时连写 5 条测试暗号，
把 5 条真实记忆（含 1 条 `user`）挤进 `archive/`；删掉暗号后它们没有回来。
对应《20261106-记忆写入-临时内容误存与满额驱逐真实记忆-修复方案》的 PR-A（D2/D3/D4）。

四处行为变更，全部在 `packages/core/src/memory/`：

1. **A1 淘汰排序**（`store.ts` `set()`）：从 `updatedAt` 单键（LWU）改为三级排序——
   索引保留顺序的逆序（`-indexTypeRank`，直接复用 S9 的 `indexTypeRank`）→
   `.read-stats.json` 的 `readCount` 升序 → `updatedAt` 升序。
   于是 `reference`/`project` 先走、从未被 Read 过的先走，`user` 最后才动；
   与 `writeIndex` 的排序口径统一，不再出现「索引说保 user、淘汰先删 user」。
   **刻意不加**「user/feedback 永不淘汰」的硬保护：200 条全是 user 时会让写入失败。
2. **A2 代价可见**（`store.ts` / `tool/memory.ts` / `/memory set`）：`set()` 返回值从
   `void` 改为 `MemorySetResult { evicted, isNewKey }`；`formatEvictionNotice()` 把
   「这次写入把谁移到了 archive/、删掉它就会放回」拼进 `save_memory` 工具结果与
   `/memory set` 输出。模型在同一轮就能看到写入的真实代价。
3. **A3 遥测**（`analytics/events.ts` `logMemoryWrite`）：新增 `is_new_key` 与
   `evicted_count`，字段口径写进 `northstar/README.md`（分母 = `is_new_key === true`
   的 `memory_write` 条数，写死）。team / agent 路径给不出同口径判据，不传该字段，
   不进分母。
4. **A4 删除回填**（新增 `memory/eviction-log.ts` + `store.ts` `delete()`）：
   淘汰成功时向 `archive/../.evictions.jsonl` 追加 `{ evictedKey, archivedAs, evictedBy, at }`
   （append-only，不改历史行）；`delete(key)` 成功后按 `evictedBy === key` 回填：
   归档文件还在、当前条数 < `STORE_MAX_ENTRIES`、目标不重名、解析得出有效条目时
   `rename` 回原文件名并重建索引，同时打 `memory_guard(restored_from_archive)`。
   重名**绝不覆盖**（不在这条「不删数据」的路径上再删一次）。

## 放弃了什么（以及为什么不选）

- **只改提示词**（上一轮的建议）：修不了数据损失——用户真心说 5 句「记住我偏好…」，
  满额时照样挤掉真实记忆。提示词是概率防线，数据安全不能只靠它。已拆成独立 PR-B。
- **调大 `STORE_MAX_ENTRIES`**：只是把问题推后。它必须与 `INDEX_MAX_ENTRIES` 同值
  （`types.ts` 注释），而索引受 25KB 字节预算约束实际只列得下 ~136 条，调大只会造更多孤儿。
- **满额时拒绝主路径新建 key**（照搬 `checkIndexFull`）：用户真心要记的内容会被拒绝，
  比挤掉一条低价值记忆更糟。主路径需要的是「代价可见」，不是「禁止」。
- **硬保护 `user`/`feedback` 永不淘汰**：200 条全是 user 时写入会失败；
  按排序选，最坏情况只退化成现状（仍归档、仍可回填）。
- **「删任意一条就恢复最近被淘汰的一条」**：会恢复与这次删除无关的记忆，用户无法预期；
  账本只撤销「这条记忆当初造成的淘汰」，语义精确。
- **新增 `delete_memory` 模型工具**：超出范围。删除目前走 `/memory` 命令与 write/edit，
  A2 的提示已经告诉模型可以删。
- **把 C3-C（索引截断归档）也纳入回填账本**：C3-C 的触发原因是索引字节预算，不是某一次
  写入造成的因果，`evictedBy` 语义不成立。本次不扩大范围。
- **在 `memory_guard(evicted_to_archive)` 上补 `memory_type`**：方案 §5.5 的后续观测项，
  不属 PR-A；`northstar/README.md` 里已如实标注该拆分「暂未采集」。

## 拿什么证明它生效了

新增 `packages/core/tests/memory/store-eviction-value.test.ts`（11 个用例，隔离到
`SID_CONFIG_DIR` + 显式 `projectMemoryDir`/`globalMemoryDir`）：

- `bun test ./packages/core/tests/memory/store-eviction-value.test.ts` → **11 pass / 0 fail**。
- **变异自证 ①**（把 A1 排序改回 `a.updatedAt - b.updatedAt`）→ **7 fail**，
  其中目标断言原文：
  `expect(result.evicted[0]).toMatchObject({ key: "r000", type: "reference" })` 变红
  （旧口径挤走了 `u000`，user 类被误伤）；
  恢复后 11 pass。
- **变异自证 ②**（注释掉 `await this.restoreEvictedBy(...)`）→ **2 fail**：
  `expect(existsSync(join(projDir, "reference_r000.md"))).toBe(true)` 收到 `false`；
  `expect(guards).toContain("restored_from_archive")` 收到 `["evicted_to_archive"]`；
  恢复后 11 pass。
- `bun run typecheck:gate` → 无新增类型错误（62 处 / 基线 64）。

事故场景复刻（用例 1）：100 条 user（最旧）+ 100 条 reference（较新）+ 新写 1 条 →
被归档的是 `reference_r000`，user 一条不少；`delete(新 key)` 后 `reference_r000`
回到原文件名、`MEMORY.md` 重新出现它、`archive/` 里不再有。
