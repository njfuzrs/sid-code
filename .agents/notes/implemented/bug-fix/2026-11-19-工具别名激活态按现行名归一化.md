# 工具别名激活态按现行名归一化，`tool_search(select:旧名)` 从「已被策略禁用」恢复为可用

## 决定了什么

三处改动，同一个不变量：**`activatedTools` 里存的永远是工具实例的 `name()`**。

1. `Registry.activateTool()` 由 `add(toolName)` 改成 `add(tool.name())`。
   `isToolDeferred()` 一直用 `tool.name()` 查激活态，存传入名会让别名激活永远查不到——
   激活了却仍然被判为「未激活的延迟工具」。
2. `Registry.isActivated()` / `markDeferred()` 同样经 `get()` 归一化后再读写集合，
   保证旧名撤回时不会留下幽灵激活态。
3. `ToolSearchTool.selectTools()` 的 enabled 判据由 `enabledNames.has(name)` 改成
   `enabledNames.has(tool.name())`。`enabledNames` 收的是各工具 `name()`，拿用户原始名
   比对会让 `select:bg_task_get` 一路落进 `disabled` 分支，模型看到
   「以下工具已被策略禁用」，而该工具其实好好活着。

D-03 把 guidance 里的 `bg_task_get` / `teamMessage` 改成现名属于「教模型正确名字」；
本次这条修的是「模型照旧名调用时真的能用」——两者是同一件事的两半，缺任一半，
旧录制轨迹或模型的旧记忆都会撞墙。

## 放弃了什么（以及为什么不选）

- **只在 tool-search.ts 改判据、不动 registry**：能让 select 走通，但 `isActivated()`
  和 `markDeferred()` 仍在用传入名，同一根因会在撤回延迟、状态查询两个入口复现。
  一处归一化比三处各自适配更不容易漏。
- **把别名表从 registry 里删掉、只留现名**：`bg_task_get` 是真实历史名（曾是独立工具，
  后并入 `task_output`）。删表等于让旧会话/旧录制全部失效，代价远大于保留一张表。
- **给 `select:bg_task_get` 单独写一条特殊分支**：那是把「别名回退」退化成白名单，
  下一个重命名还得再改一次。

## 拿什么证明它生效了

- `bun test packages/core/tests/tool/deferred-guidance.test.ts` → 20 pass / 0 fail。
  其中原先 `test.skip` 的端到端用例已转真跑：`select:bg_task_get` 不报「未找到」
  也不报「已被策略禁用」，返回体含 `bg_task_get`，且 `isActivated("task_output")` 为 true。
  同时断言 `monitor` 未被顺带激活（别名回退不能变通配）。
- 新增断言 `isDeferred("task_output")` 在旧名激活后转 false——这一条直接锁住 1 号改动。
- `bun test packages/core/tests/tool/`（整目录）→ 2648 pass / 0 fail。
- `bun run smoke` 43/43、`bun run smoke:tui` 5/5，说明激活态口径变化没有影响任何
  回放链路。
