# 上传重试队列接入 `.upload-attempts` 跨进程退避/终态，并让重复条目收敛

## 决定了什么

`packages/core/src/trace/uploader.ts` 的 `processRetryQueue` 与 `appendToRetryQueue` 改了三处行为，前提是「sid-code 不该有两套互不知道对方的重试机制」：

1. **接入跨进程退避与终态**。`processRetryQueue` 在 `existsSync(filePath)` 之后、真正上传之前读会话目录里的两个记账文件：
   - `.upload-failed` 存在 → 条目标 `failed`，计入新增的 `stats.markedFailed`，不发请求；
   - `.upload-attempts` 仍在退避窗口（`isInBackoff`）→ 条目**原样保留且不递增 `attempts`**，计入新增的 `stats.backoff`。本轮一个字节都没发，不该消耗重试预算。
2. **失败/成功都回写同一份记账**。上传失败调 `recordUploadFailure(sessionDir, reason)`：它是 `backfill.ts` 用的同一个函数，累计到 `MAX_AUTO_ATTEMPTS`（8）会写 `.upload-failed`，此时条目直接进终态（不必等队列自己的 `maxQueueRetries=50`）。成功则**按会话聚合**后清 `.upload-attempts` / `.upload-failed` —— 只有「该会话本轮参与过、且本轮全部条目都成功」才清，否则 traj 成功会把 raw 刚记下的失败次数抹掉，一个持续失败的会话就能无限循环「失败 → 另一个文件成功清账 → 再失败」。
3. **`appendToRetryQueue` 去重不再看 `status`**。旧实现是 `entry.status !== "failed"` 才跳过，等于「判死的那条」不阻止追加：每失败一次就再生一条全新 pending，`maxQueueRetries` 因此没有上限。failed 条目不复活是刻意的，重传只能走 `--upload-traces`。
4. **`processRetryQueue` 读队列后先按 `(session_id, file)` 合并重复条目**，保留 `attempts` 最大的那条（= 最接近终态的记账），并列时保留先出现的。合并数进 `stats.deduped` 并打一行 info。
5. **手动路径与自动路径分开**：`processRetryQueue({ ignoreBackoff: true })` 无视退避、终态，也重试 `status=failed` 的条目；`cli.ts` 的 `--upload-traces` 传 true（与 `backfillPendingSessions` 的同名选项同一口径）。`startQueueScan` 与维护子进程不传，走退避与终态。

`QueueProcessResult` 新增 `backoff` / `deduped` 两格，`formatQueueResult` 在不为零时点出来。理由是同一个教训的第二次应用：`processRetryQueue` 曾返回 `void`，让「传了 1267 个」与「静默丢了 1267 个」在输出上完全一样；这次如果不说，「全在退避」与「什么都没做」同样无法区分。

触发证据（会话 `20261103-114056-3b4f9ca7` 的取证）：`warn.log` 里 35 分钟出现 7 组 `20261022-034121-20f64f92/traj` 上传失败，而该会话的 `.upload-attempts` 记着「第 5 次失败，2026-11-03 09:54」，按 `backoffMs(5)=16h` 本该在 16 小时内不碰。`~/.sid-code/trajectories/.upload_queue.jsonl` 里同一个 `(session_id, session.traj)` 有 9 条：8 条 `attempts:50/status:failed`（10-22 到 11-02 一路 append）+ 1 条 `attempts:23` 的 pending，累计自动尝试 50×8+23 = 423 轮。

方向：服务「更省」（445MB 会话不再每 5 分钟吃一次上行带宽）。牺牲的是「更准」的一个窄角——补传侧 8 次终态的会话，队列侧也不再自动重试；这部分数据仍在本地，`--upload-traces` 可随时重传。

## 放弃了什么（以及为什么不选）

- **删掉重试队列，只留补传扫描**：队列承载「服务端不可达时会话结束时的文件」（`uploadSession` 在 `serverReachable=false` 时直接入队），补传扫描按目录 mtime 与时间闸工作，两者入口不同。合并是更大的重构，不在本次范围。
- **把 `maxQueueRetries` 调小**：B2 不修的话上限照样失效（failed 不阻止追加，每次都是新条目从头计数）；B1 不修的话 5 分钟一轮的频率不变。调小只会让单条更早死，不改总尝试轮数。
- **大文件直接不传**：数据主权与可观测要求轨迹能完整归档。445MB 本身的成因在「启动慢」那份记忆里已修，大小阈值是另一个议题。
- **成功时每个文件立刻 `clearUploadAttempts`**：写测试时才发现的坑（「同会话 traj 成功不会清掉 raw 刚记下的失败」这条用例一开始是红的）。必须按会话聚合到本轮结束，否则交错成功/失败会让退避计数被反复重置。
- **`ignoreBackoff` 只绕过 `.upload-failed`、仍跳过 `status=failed` 条目**：那 `--upload-traces` 就救不回队列里已经判死的条目，与 `upload-attempts.ts` 头注释「手动命令无视退避与终态」直接冲突。手动路径一律重试。
- **只在 `appendToRetryQueue` 加去重、不做存量合并**：本机已有 9 条同 key 记录，只堵新增的话它们会永久占着队列，且其中那条 pending 仍会被反复重试。合并是一次性的收敛动作。
- **给队列条目也做 8 次上限（复用 `MAX_AUTO_ATTEMPTS`）**：两套计数故意并存 —— `.upload-attempts` 是会话级、跨进程、决定「自动补传还给不给机会」；`entry.attempts` 是单条目的队列预算。前者 8 次先到，后者通常到不了 50；把它删掉会让「手动路径不写终态」的语义无处可依。

## 拿什么证明它生效了

- `bun test ./packages/core/tests/trace/uploader-queue-backoff.test.ts`：9 pass（新增），覆盖退避跳过 / 终态跳过 / 失败写记账且目录 mtime 不变 / 累计到 8 次进终态 / 手动路径无视终态并清账 / 会话级清理不被交错成功抹掉 / failed 条目阻止追加 / 9 条收敛成 1 条 / 不同 key 不合并。
- `bun test ./packages/core/tests/trace/uploader-queue.test.ts ./packages/core/tests/trace/uploader.test.ts`：46 pass，既有队列与上传行为未变。
- 变异自证（改坏后重跑，恢复再跑）：
  - `if (isInBackoff(...))` → `if (false && isInBackoff(...))`：「仍在退避窗口内」1 条 fail，恢复后转绿；
  - `appendToRetryQueue` 的去重条件改回 `&& entry.status !== "failed"`：「同 key 已有 failed 条目时不再追加新 pending」1 条 fail，恢复后转绿。
- `bun run typecheck:gate`：64 处 / 基线 64 处，无新增（`QueueProcessResult` 加字段后同步了 `uploader-queue.test.ts` 的 `formatQueueResult` 用例对象）。
- 未做的端到端验证（诚实记录）：文档要求的「本机开 30 分钟以上会话，`warn.log` 不再出现该会话的上传失败行、`.upload_queue.jsonl` 收敛为 1 条」需要真实服务端不可达环境与 30 分钟窗口，本次没有跑。可替代的确定性证据是「9 条收敛成 1 条」的单测，以及 `.upload-attempts` 生效后请求计数为 0 的断言。
