# bash 解析器把引号外换行当 `;`：从源头修 `parseBashCommand`，heredoc 正文先剥离

## 决定了什么

**目标语义写死一句：引号外、heredoc 正文外的换行，等价于 `;`。** 三条实现都服务于它：

1. **`parseBashCommand` 入口归一化**（`packages/core/src/tool/bash/parser.ts`）：
   `normalizeCommandText()` 先 `extractHeredocBlocks().stripped` 剥离正文，再
   `foldLineContinuations()` 折叠 `\<newline>`（bash 语义：两字符都删除，命令继续）。
   顺序不能反——先剥 heredoc，正文里的 `\<newline>` 才不会被当成续行。
   递归改走内部的 `parseNormalized()`，避免每层重复剥离。
2. **两处序列分隔符正则各自加 `\r?\n`**：`parseNormalized`（D1/D2 的出口）与
   `splitShellSubcommands`（D3 的**唯一**出口，`permission/bash-security.ts` 的 flag
   混淆检测走它）。少改一处就修不干净，所以这两处各有独立的变异自证。
3. **`operator` 归一化**：`splitOutsideQuotes` 会把捕获到的分隔符原样塞进 `separators`，
   而 `BashASTNode.operator` 的类型只有 `"&&" | "||" | ";"`。不归一化时运行时是 `"\n"`，
   类型是假的；`toSequenceOperator()` 把它折成 `";"`。

配套三件：

- **heredoc 剥离抽成叶子模块** `packages/core/src/tool/bash/heredoc.ts`。`parser.ts` 要用它，
  而 `permission/bash-security.ts` 已经 import 了 `parser.ts`，从 `tool/bash/` 反向 import
  `permission/` 会形成目录级双向依赖（`lint:boundary` 查不出，它只查包级）。
  `permission/shell-structure.ts` 改为 re-export，3 个既有消费者零改动。
- **`echo` 豁免把换行算作 shell 操作符**（`permission/bash-security.ts`）：不算的话
  `echo hi`⏎`grep "-"exec .` 会因 `baseCommand === "echo"` 被整体豁免，第二条命令的
  混淆 flag 直接漏扫——同一处 D3 缺口在豁免分支上的出口。
- **`getGitCleanTargets` 统一到 `expandShellCommand`**（`checkpoint/bash-affected-files.ts`）：
  它原先是 `parseBashCommand` + `extractSimpleCommands` 的**第二套提取器**，多行命令下
  后一条命令的参数会被并进 `git clean` 的 pathspec。主路径 `:189` 早已是这个口径，
  改成同源即可。

`tokenize` **刻意不动**：它现在就是 `/\s/.test(ch)`（`\s` 含 `\n`），走到它时引号外换行
已被上层拆走；改它反而会把 `splitShellWords`（`cli/src/command/custom.ts`）的切词行为
一起改掉。

## 放弃了什么（以及为什么不选）

- **只改 `isReadOnlyImpl`（方案 B）**：改动面最小，但 D3（flag 混淆漏扫第二段）与
  D4（`git clean` 参数污染）留着不修。同一根因在下游打补丁，下一次换个调用点又会冒出来；
  本仓既有判据是「与 safetyCheck 共用同一份提取」。
  它的「回归风险接近零」也只对 parser 其它消费方成立——`isReadOnlyCommand` 自身输出照样翻，
  9 处调用点的回归面与方案 A 完全相同。
- **只把 `\n` 加进正则、不剥离 heredoc**：实测会把 `cat > notes.md <<'EOF'` 正文里的
  `rm -rf /` 拆成独立命令段，撞上危险命令检测——最普通的写文件白弹/白拦。这是引入回归。
- **改 `validateNewlines` 让它顺带拦掉多行命令的只读判定**：它已经是 `severity: "ask"`
  且覆盖所有 bash 命令，再加强只增加弹窗，且解决不了 `isConcurrencySafe` / `trackCwd` /
  tracker / git 缓存这些非权限出口。
- **在 9 个调用点各加一次「先按换行拆」**：同一根因 9 个补丁点，必然漂移。
- **顺手删 `getCommandPrefix` 死导出（D5）与 `extractPathsFromCommand`**：与本次无关，
  单独开 `chore:` PR，不塞进这个修复里。

## 拿什么证明它生效了

**变异自证（每条都实际改了源码、跑了测试、看了输出，再恢复）**：

| 变异 | 结果 |
| --- | --- |
| `parseNormalized` 的分隔符正则改回 `/\s*(&&\|\|\|;)\s*/` | A 组 4 条、B 组 1 条、C 组 1 条、G 组 1 条变红 |
| `splitShellSubcommands` 的正则改回（去掉 `\r?\n`） | F 组 2 条 + `bash-newline-obfuscated-flags.test.ts` 3 条变红，A–E/G/H 不动——证明 D3 走的是另一条正则 |
| `normalizeCommandText` 去掉 heredoc 剥离 | C 组 2 条 + F 组 heredoc 用例变红（`rm -rf /` 重新出现在命令段里） |
| `\r?\n` 改成 `\n` | **G 组未变红**，见下 |
| `normalizeCommandText` 去掉 `foldLineContinuations`（补做） | D 组唯一一条变红 |

**第 4 条如实记录**：`\r?\n` → `\n` 后 CRLF 用例仍绿。原因不是测试没写好，而是 `\r`
在 JS 正则里属于 `\s`、且 `String.trim()` 也会去掉它——当前实现下两种写法的**行为不可区分**。
保留 `\r?\n` 是意图显式化（意图上不依赖 `\s*` 回溯），但 G 组本质是**行为锁定**，
不是「变异可证伪」。文档原先预设它必须变红，实测不成立，这里以实测为准。
