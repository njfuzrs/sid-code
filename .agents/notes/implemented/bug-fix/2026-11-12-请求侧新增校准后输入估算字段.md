# request_sent 新增校准后估算字段，与未校准字段并存而非改义

## 决定了什么

`raw.jsonl` 的 `request_sent` 预写行新增 `estimated_input_tokens_calibrated`：

- 取数源是 `ContextManager.estimateTokensFor(发送副本, toolCount)`——与 `recordActualTokens`
  校准分母（`rawEstimateTokensFrom(snap.sent)`）同一对象，所以它与 `usage.input_tokens`
  是可直接比值的量。它与 Footer（`getContextUsageForDisplay`）、压缩判断
  （`getCompactionLevel`）共享同一个 `calibrationFactor` 与同一套启发式基线。
- 未校准（本会话还没收到过真实 usage 的首轮）写 `null`，**不回落**成未校准值。
- 原字段 `estimated_input_tokens`（采集器本地 `estimateMessagesTokens`，纯启发式）
  **数值行为一字未改**，只新增字段。`token.ts` 的启发式系数也没动。

链路：`hook/types.ts` 加字段位 → `query/loop.ts` 主循环与收尾总结轮各算一次传下去
（收尾轮传 `toolCount=0`，因为那时确实不下发工具）→ `trace/collector.ts` 落盘，
`?? null` 兜住没有校准的路径。

## 放弃了什么（以及为什么不选）

1. **直接改 `estimated_input_tokens` 的含义（改成校准值）。** 否决理由：同名改义会让
   新旧轨迹的时间序列在改版点整体平移约 25%，所有按该字段画的曲线与算的比值都会静默出错，
   而没有任何东西会红。这正是北极星铁律 3 说的「分母口径一变曲线就整体平移」。
   代价是新旧分析脚本要分字段读——这个成本是显式的，比静默错数好。
2. **在 collector 里直接持有 ContextManager 自己算。** 否决理由：采集器是 hook 订阅者，
   与 context 层没有依赖关系，为了一个字段造一条反向依赖不划算，也让 collector 单测
   需要构造整个 ContextManager。改由 loop 在已有的 `llm_request` 载荷上多带一个值，
   与 `max_tokens`（V1-1）走同一条路。
3. **校准值用 `estimateTokens(toolCount)`（全量历史 + `lastActualInputTokens` 锚点）。**
   否决理由：那是「压缩判断的尺子」，含全量历史与已释放量扣减，和 `usage.input_tokens`
   （发送副本口径）不是同一对象；遮罩场景下两者会分叉。V6-1 要的是 0.95–1.05 的比值，
   必须用发送副本口径。
4. **首轮回落成未校准值。** 否决理由：那会让这一行冒充校准值，分析者无法区分
   「校准过」与「没校准」，正是本次要根治的「字段没标明口径」。

## 拿什么证明它生效了

- `bun test ./packages/core/tests/trace/collector.test.ts`：116 pass / 0 fail。新增两条用例
  分别锁「传入值原样落盘且未校准字段不受影响」与「未传时为 null」。
- `bun test ./packages/core/tests/query/calibrated-estimate-before-model.test.ts`：2 pass。
  走**真实 queryLoop** 断言接线——只测 collector 会漏掉「loop 永远传 null」这种死接线。
  其中一条精确断言 `payload.estimated_input_tokens_calibrated ===
  estimateTokensFor(payload.raw_messages, 0)`（在 hook 回调内同步重算，因为
  `raw_messages` 是会被后续追加的同一数组引用，事后重算会假红：实测 9 vs 7）。
- **变异自证**：把 collector 的 `?? null` 改成 `?? totalTokensEst`（即回落成未校准值），
  `collector.test.ts` 立刻 1 红（115 pass / 1 fail）；恢复后 116 pass。
- `bun run affected-tests:run`（hook / query / trace 三域）：2789 pass / 0 fail / 230 文件。
- `make build` + 产物自检通过；`bun run smoke`：26 例 26 通过 0 失败。
- `bun run typecheck:gate`：62 处 / 基线 62 处，无新增；`lint` / `format:check` 全绿。
- 端到端（V6-1）：用 `./sid-code -p` 跑真实会话，比对同一 index 的
  `estimated_input_tokens_calibrated` 与 `usage.input_tokens`，第 2 轮起落在 0.95–1.05。
