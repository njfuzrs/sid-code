# 账本按逻辑会话 id 落行，resume 后不再拆成两行

## 决定了什么

`UsageLedgerEntry.sessionId`（`usage-ledger.jsonl` 的去重键）改取**逻辑会话 id**
（resume 时 = 被恢复会话 id = `trajectories/sessions/<id>/` 的目录名），不再取
`sessionState.sessionId`（本进程新 id）。

改动两处：

- `packages/core/src/telemetry/usage-ledger-entry.ts`：`buildUsageLedgerEntry` 新增
  `logicalSessionId?: string` 入参，`sessionId: input.logicalSessionId ?? input.sessionState.sessionId`。
  缺省回退只为单测与不区分进程的调用方保留，生产调用方必须传。
- `packages/cli/src/app.ts`：`buildLedgerEntry()` 传 `this.getLogicalSessionId()`，
  且**延迟到调用时取**（不在构造期捕获）—— 构造函数早于 `restoreSession`，捕获局部变量
  会把进程 id 定死，这和 checkpoint / `transcript_path` 的既有教训是同一形态
  （`app.ts` 的 D5 注释）。

第二条改动是端到端验收逼出来的，不是原方案里写好的：

- `packages/cli/src/app.ts`：`runHeadless`（`-p`）与 `runHeadlessSDK`
  （`--output-format stream-json`）的收尾在 `finalizeSessionStore()` **之前**补调
  `persistUsageStats()`。原先它只挂在 TUI 每轮 done 上，两条无头路径从不落
  `usage_stats` / `side_call_stats` / `agent_usage`。

为什么这条必须同 PR：单独看「无头不落统计」不是 bug —— 那时账本按进程 id 拆两行、
每行只含自己那段，按 `sessionId` 求和**恰好对**。但账本改成逻辑 id 单行后，resume
那一行只含第二段，就从不双计变成**少算**，而且只有一行时「按行求和」根本看不出来。
即：单行化的前提是「同一行所有字段同一会话作用域」，缺了落盘，修复本身会把
「双计」换成「丢账」。端到端复现见下方证明段。

### CP-12 取证结论（修复依据）

账本 key 的来源链（修复前，`eb982497`）：

1. `usage-ledger-entry.ts:73` — `sessionId: input.sessionState.sessionId`
2. `app.ts:1168` — `const sessionId = opts.config.sessionId || generateSessionId()`
3. `app.ts:1269` — `new SessionState(sessionId)`（构造期局部变量注入）
4. `config.ts:2027-2029` — `loadConfig` 收尾：配置里没有 sessionId 时生成**新进程 id**
5. `app.ts:6447-6468`（`restoreSession`）— **刻意不改** `sessionState.sessionId`，
   只设 `this.resumedSessionId = sessionData.id`；注释写明进程 id 用于
   crash marker / PID / trajectory，必须跨进程唯一
6. `app.ts:2185-2187` — `getLogicalSessionId() = resumedSessionId ?? sessionState.sessionId`
7. `trace/collector.ts:790-800` — `traceSessionId = isResume ? input.resumed_from! : input.session_id`
8. `usage-ledger.ts:199-206` — `upsertUsageLedger` 按 `entry.sessionId` 去重

即：**轨迹目录名与账本 key 取自两个不同的 id**。resume 后同一逻辑会话在账本里拆两行，
新行 id 在 `trajectories/sessions/` 下没有目录；而行内 `promptTotal` / `costUSD` 因
`usage_stats` 回灌是会话口径、`byAgent` 只含本进程 —— 同一行两种作用域，按行求和把
resume 前的用量算两遍。

辅助统计在 resume 时的回灌路径（三条都已在 `restoreSession` 里，**修复前就是通的**）：

- `usage_stats` → `SessionState.hydrateUsage`（`app.ts:6585-6601`）：
  `totalCostUSD` / `sideCostUSD` / `modelUsage` 全会话连续
- `agent_usage` → `hydrateAgentUsageBaseline`（`app.ts:6613-6617`）：byAgent 会话基线
- `side_call_stats` → `hydrateSideCallBaseline`（`app.ts:6618-6636`）：影子调用次数 / token / byLabel

所以**不需要新增任何回灌**，缺的只是 key。取证时同时纠正方案 §6 CP-12 的一处误判：
「resume 前的两个 fork 没回灌」不是回灌缺失 —— fork 成本走 `totalCostUSD`（发生侧
`updateUsage`），`sideCostUSD` 只装消费侧自报的 title 等；两段相加后与账本行一致
正是现状，照原文去「补 fork 回灌」会把它记两遍。

## 放弃了什么（以及为什么不选）

- **改 `sessionState.sessionId` 本身，让进程 id 与逻辑 id 合一**：否决。进程 id 跨进程
  唯一是 crash marker / PID / trajectory 的硬需求（`restoreSession` 注释已写明二者刻意
  分离），合并会在 resume 时与原进程的资源键冲突。
- **读侧按轨迹目录名回填 / join**：否决。历史账本行没有记录 `resumed_from`，读侧无法
  判断两行属于同一逻辑会话；能判定的只有写入时那个 id。修读侧等于把「不可判定的问题」
  推给消费方。
- **顺带回改历史双行数据**：否决（方案明确不回改）。合并需要靠时间 + 设备 + 模型猜归属，
  猜错会让「按行求和」从双计变成错配。
- **另加四条回灌**：否决，不需要。三条回灌路径本来就存在且正确，问题只在 key；
  重复加会把 `sideCostUSD` 记两遍（`side_call_stats` 那条注释已经写明这个陷阱）。
- **给 `buildUsageLedgerEntry` 加必填参数**：否决。会让 core 的纯函数单测与所有
  `sessionState`-only 调用方被迫编一个 id；可选参数 + 生产调用方显式传，责任落在唯一生产者
  （`App.buildLedgerEntry`）身上，测试也用同一个入口断言。

## 拿什么证明它生效了

- 新测试 `packages/cli/tests/app/ledger-logical-session-id.test.ts`（走真实链路：
  进程 A 计费落盘 → 段边界 reset 本进程记录 → 进程 B `restoreSession(同 id)` → 再计费落盘）：
  `bun test ./packages/cli/tests/app/ledger-logical-session-id.test.ts` → **2 pass / 0 fail**。
  断言：账本只有 1 行、`sessionId === 被恢复 id === getLogicalSessionId()`、
  `promptTotal` = 两段之和（1500）、`costUSD` 连续且大于首段、`sideCostUSD` = 0.75、
  `byAgent.extract.requests` = 2。第二条用例反向自证「非 resume 会话仍用自己的 id」，
  防「永远返回某个全局 id」也能通过。
- **变异自证**：把 `app.ts` 的 `logicalSessionId: this.getLogicalSessionId()` 改回
  `this.sessionState.sessionId`，同一测试立刻变红：
  `expect(rows.length).toBe(1)` → `Expected: 1, Received: 2`；恢复后重新 2 pass。
  说明这条断言真的在守 key，不是恒绿。
- 门禁：`bun run affected-tests:run`、`make build`、`bun run lint`、`bun run format:check`、
  `bun run typecheck:gate` 结果见 PR 正文。

端到端（方案 E4，`sc-dev` 跑一次真实 resume + 按价复算 `BilledRequest`）属于本机验证，
结果记在 PR 正文；历史双行数据不回改，消费侧按 sessionId 去重时新数据自然单行。
