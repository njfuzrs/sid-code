# 网关额度 403 按上游 code 归为额度耗尽，并按账户跨循环共享

## 决定了什么

来源：会话 `20261103-213816-f5beebde` 复盘 F2（方案《20261104-会话 f5beebde 复盘-流迭代器泄漏与额度误判等六项-落地方案》§3）。

**一句话：把「网关用 403 说额度不足」这条真实语义接进唯一分类器，并让「账户余额空了」这个事实只被撞出来一次。**

事故形态：网关回 `403 {"error":{"message":"令牌[...]额度不足","type":"shell_api_error","code":"pre_consume_token_quota_failed"}}`，分类器判成 `auth_suspect`（鉴权可疑），主循环 + 3 个并行子代理各按 `auth_suspect` 的 3 次预算重试，合计 12 发注定被拒的请求；用户看到的文案是「API Key 无效或已过期」，照着换 key 永远修不好。

六处改动，按调用链从底到顶：

1. **新增 `llm/upstream-error-body.ts`**：`parseUpstreamErrorBody()` 解析上游错误体里的 `type` / `code` / `message`，`pickUpstreamTag()` 选判别标签。**`code` 优先于 `type`** —— 网关的 `type` 常是无判别力的外壳（`shell_api_error`），具体原因在 `code`；官方 API 没有 `code` 时回落 `type`，两个方向的真实形态都覆盖。
2. **三条协议路径的 `!response.ok` 全调它**：`openai.ts` 的 Chat 流式 / Responses 流式把 tag 放进 `error` 事件的 `type` 字段；两处**非流式**分支（同样走 `!response.ok`）挂到 `err.error` 上（`normalizeThrown` 的 `extractUpstreamType` 从那里读）。`anthropic.ts` 的 SDK catch 分支改为复用同一个 `pickUpstreamTag`，把优先级从 `type > code` 反转为 `code > type`。
3. **`byUpstreamType` 认额度类 code**（`quota` / `billing` / `balance` / `credit` 子串），**放在 `authentication` / `permission` 之前**：`permission_denied_quota` 这类组合 code 真实存在，额度语义更具体（额度耗尽要充值，鉴权失败要修凭据，下一步动作完全不同）。
4. **401/403 的额度窄口**：`byStatus(401|403)` 之前先查一次**只含额度词条**的词表，命中 `quota_exhausted` / `usage_limit_reached` 才采信，其余一律仍按状态码。这是对「文本里的巧合关键词不该推翻结构化状态码」原则的**有边界例外**，例外清单只有两个额度码。理由：new-api / one-api 这一族网关用 403 表达额度耗尽，有些实现只写 message、不给 code。
5. **词表补「额度不足」「quota_failed」「令牌额度」**；`error-lexicon.ts` 把「短期限流否定语 / 用量到顶 / 欠费」三组短语抽成常量，主词表与窄口共用一份（两份必然漂移）。
6. **`codeFromStructured` 收敛到唯一分类器**：删除它自带的第二套 `type.includes(...)` + `switch(status)`，改调 `classifyFamily`。顺带给 `byUpstreamType` 补齐 `content_policy` / `request_timeout` / `timeout` / `server_error` 四个 type —— 它们原本只在第二套分类里被认，不补齐就等于用「消掉第二套分类」换一次面板文案回退。
7. **账户级额度标记**（`availability.ts` + `quota-scope.ts`）：漏斗判定额度耗尽时按 **(归一化端点, 凭据指纹)** 写一条标记，同账户的后续请求在建流之前直接快速失败。`Provider` 新增可选 `quotaScope?()`，`openai` / `anthropic` 实现；不实现的 provider 一律放行（fail-open）。
8. **额度耗尽不再写模型嫌疑**：它是账户级事实，不是「模型坏了」。误写成 suspect 会让用户去换模型（同账户的下一个模型照样没钱），与本仓 `fallback.ts:358-360` 记过的「把凭据过期误归因到模型」是同一族错误。

### 实施时与方案有出入、需要知道的三件事

**① 窄口不能用 `matchErrorLexicon`，必须用专门的 `matchQuotaLexicon`。**
方案 §3.3 ③ 写的是「先查一次词表」。实测按字面实现会**静默失效**：主词表第 4 条「认证失败」里含 `hasBoundaryDigits(lower, "401"|"403")`，而 provider 拼出来的 message 必然带着 `HTTP 403` 这三个字符 —— 直接查整张表会先返回 `auth_failed`，永远到不了欠费那一条。所以新增 `matchQuotaLexicon`，只跑「短期限流否定语 → 用量到顶 → 欠费」三组。

**② 方案列的三种清除条件会死锁，补了 TTL。**
方案说标记在「retry_same / 换凭据 / 任意一次请求成功」时清除。后两条都要求**有请求真的发出去并成功**，而标记生效期间请求全被拦 —— 第三条结构性走不到。补了 60s TTL 作为唯一不依赖用户的自愈出口；同时**主线程 / headless 豁免**（与 `isAvailable` 的 I4 同口径），这是「用户充值后重发 → 真实请求 → 成功 → 清除」这条路的唯一实现途径。

**③ 拦截点在建流之前，不是循环内。**
`openStream` 在重试循环外调用。虽然生产 provider 的 `sendMessageStream` 是 async generator（调用只构造对象、不执行函数体），但任何在调用期就有副作用的实现（测试 mock、未来可能的 eager 实现）都会被调到，而「这一发不该发出去」的判据必须在**调用之前**成立。所以 `quotaHit` 在建流前算好，命中时用 `EMPTY_STREAM` 占位、循环第一次 attempt 直接 break 到降级/询问出口（finally 的清理照常执行）。

## 放弃了什么（以及为什么不选）

- **只在词表里补「额度不足」**：本会话的路径根本不查词表（状态码先定案），补了也不生效。这正是评估初稿差点开出的错方子。
- **把 403 整体改判为 `request_suspect`**：真鉴权 403（权限不足、组织被禁）会少一次 `auth_refresh`，对 OAuth 场景是回退。所以做成「只对两个额度码开窄口」。
- **额度耗尽直接判死、0 次重试**：违反 `MIN_ATTEMPTS = 2` 的「措辞只能加速、不能判死」原则；网关偶有预扣失败后立即恢复的情况，留一次重试的代价很小。
- **额度标记跨进程持久化**：额度会被外部充值恢复，持久化会让新会话误判。只做进程内 + 60s TTL。
- **复用 `markSuspect` 表达额度耗尽**：语义错误（见上文第 8 条），而且会让「换模型」这个动作被错误归因。
- **`byUpstreamType` 用 `t.includes("api_error")` 认 5xx**：会命中网关的泛化壳 `shell_api_error`，把真鉴权失败判成可重试的 5xx。改成 `t === "api_error" || t.includes("server_error")`，泛化壳不参与判定。
- **`codeFromStructured` 传入 message 让窄口也生效**：本函数的契约是「只看结构化字段」。带 message 进来等于又开一条文本推断的路，而那条路已经有 `inferErrorCode` 兜底；provider 层现在会传 code（F2 ①），结构化判据已经够用。
- **给 `GiveUpEvidence` 加 `familyReason` 字段**：`recordGiveUp` 需要知道「这次放弃是不是额度耗尽」，但 evidence 里只有 `GiveUpReason`（budget / same_fingerprint …）与 `family`。加字段要牵动 `recovery-single-exit` 的静态断言与一批测试；改成把已有的 `action.verdict` 传进 `recordGiveUp`，零契约变更。
- **`quotaScope` 用 provider 名字代替 (端点, 凭据)**：同一 provider 名下可能挂多个网关/多个 key，混成一个会让「另一个账户有钱」被误判成「都没钱」。而明文 apiKey 不能进内存 Map 的 key（dump 即泄漏），所以用 sha256 前 16 位做指纹。

## 拿什么证明它生效了

### 单测（新增 30 条）

```
bun test ./packages/core/tests/llm/quota-403-classification.test.ts
# 30 pass / 0 fail
```

五组用例对应五层根因：

- **第 1 组（解析）**：真实 403 正文解析出 `type`/`code`；`pickUpstreamTag` 选 `code`；官方形态（无 code）回落 `type`；非 JSON / 空 body / 纯字符串 error 返回空对象且不抛；外层哨兵 `type:"error"` 不被当标签。
- **第 2 组（结构化判据）**：真实 403 + 真实 code → `request_suspect / quota_exhausted`；额度 code 不依赖状态码；组合 code `permission_denied_quota` 走额度；反例（真鉴权 403、泛化壳 `shell_api_error`）不被误伤。
- **第 3 组（窄口）**：**不带任何 type** 的 `令牌额度不足` + 403 → `quota_exhausted`（这条是窄口的专属用例，删掉窄口立刻红）；无状态码纯文本；三条新词；老词条不受影响；400 + 额度文案仍按 `invalid_request`（窄口只对 401/403 开）；`not your usage limit` 不被采信。
- **第 4 组（文案同源）**：403 + 额度 code → 面板 `quota_exhausted`；真鉴权仍是 `auth_failed`；状态码族与 type 族的既有映射逐条不回退；认不出的输入返回 `undefined`。
- **第 5 组（跨循环共享）**：第一条循环判定后**同账户第二次调用不发 HTTP**；换凭据 / 换端点不命中；主线程 / headless 豁免；不实现 `quotaScope` 的 provider 放行；成功产出一次即清除标记；额度耗尽不写模型嫌疑。

### 变异自证（三项，都是先改坏再恢复）

| 变异 | 结果 |
| --- | --- |
| 删掉 `classifyFamily` 的 401/403 额度窄口 | 第 3 组「403 不带 type」核心用例**变红**（1 fail） |

每次变异后都恢复并确认回到 30 pass / 0 fail。

### 一处遗留边界（诚实记账）

`byUpstreamType` 的额度判定用子串，`balance` 会命中 `load_balancer_unavailable` 这类
与余额无关的 code。概率极低（LLM 网关的错误 code 里几乎不出现），且最坏后果是
「把一次可重试故障按 request_suspect 的 2 次预算处理」—— 仍会重试，不是判死。
按方案 §3.3 ② 的原文保持子串实现，不为此加一层词边界。
