# monitor 不再享受沙箱自动放行：只给「真的会在沙箱里跑」的 bash 放行

## 决定了什么

`permission/checker.ts` Step 7（沙箱自动放行）的触发条件从 `isCommandSemanticsRequest(req)`
收窄为 `req.toolName === "bash"`。

`isCommandSemanticsRequest` 是 #683 为「monitor 复用 bash 的规则匹配」引入的判定
（`toolName === "monitor"` 且带非空 command 也算）。它被 Step 7 复用后，monitor 连带继承了
「沙箱保护下自动放行」：用户开启沙箱并配置 `autoAllowBashIfSandboxed: true`（opt-in，默认 false）时，
monitor 的任意脚本跳过确认直接执行，而 monitor 的子进程是裸 `spawn`
（`task/monitor-task.ts` 的 `spawn(shell, [...args, opts.command])`），**没有**
`sandboxManager.wrapCommand` 包裹——bash 的两处执行都有（`tool/bash.ts:1048`、`:1580`）。
决策日志因此写下「允许(沙箱保护下自动放行) / 沙箱保护下自动放行」，声称了一个并不存在的保护。

修复后 monitor 回落到后续步骤：规则匹配（`commandRuleRequest` 仍把规则名归一成 bash，
`Bash(gh pr checks:*)` 照样命中）、模式硬约束、弹窗，与「沙箱关闭」时的判定一致。
`isCommandSemanticsRequest` 其余六处用途（危险命令、safetyCheck、deny / allow 规则匹配）**不变**——
它们不依赖「命令在沙箱里跑」这个前提。

## 放弃了什么（以及为什么不选）

**放弃：给 monitor 也套 `sandboxManager.wrapCommand`，让它真的进沙箱。**
三个理由：
1. monitor 的典型命令（`gh pr checks`、`curl`）需要网络与 `~/.config/gh` 凭据，
   Seatbelt profile 对长驻进程的网络 / 读路径策略没有验证过——「进沙箱」可能直接把
   monitor 的主要用例打死，而不是少弹一次窗；
2. Seatbelt 开启路径本身有已知的全挂问题，在它修好之前无法可靠验证；
3. 「monitor 进沙箱」是更安全方向的**新能力**，不是缺陷修复。需要时另立方案，不该搭这趟车。

**放弃：只改日志文案，保持 Step 7 条件不变。** 那仍会跳过用户确认——一个不在沙箱里的
任意 shell 脚本免确认执行，是实际的安全敞口，不是措辞问题。

## 拿什么证明它生效了

1. 新增 `packages/core/tests/permission/monitor-sandbox-autoallow.test.ts`（5 条），
   `bun test ./packages/core/tests/permission/monitor-sandbox-autoallow.test.ts` → **5 pass / 0 fail**：
   - monitor + `shouldAutoAllowBash() === true` + default 模式 + 无规则 → `allowed === false`、
     `needsConfirmation === true`、理由不是「沙箱保护下自动放行」、`step !== "7"`；
   - 同一 checker 下 **bash 同一条命令**仍 `allowed === true` 且理由恰是「沙箱保护下自动放行」；
   - 有 `Bash(gh pr checks:*)` allow 规则时 monitor 仍 `allowed === true`、`decisionReason.type === "rule"`；
   - `shouldAutoAllowBash() === false` 时 monitor 仍是 ask；
   - 反漂移守卫：读 `checker.ts` 源码文本，每个以 `shouldAutoAllowBash()` 为条件的 `if`
     都必须显式含 `toolName === "bash"`（注释行先排除，防止把条件文本复制进注释造成假绿）。
2. **变异自证**（把 Step 7 条件改回 `isCommandSemanticsRequest(req) && …` 后重跑同一文件）
   → **2 pass / 3 fail**，红的是哪几条：monitor ask 用例 `Expected: false, Received: true`；
   规则用例 `Expected: "rule", Received: "other"`（Step 7 抢先放行）；反漂移守卫收到
   `if (isCommandSemanticsRequest(req) && this.sandboxManager?.shouldAutoAllowBash()) {`。
   bash 用例与「沙箱关闭」用例保持绿，说明变异只命中了要抓的地方。恢复后重回 5 pass。
3. 既有沙箱用例未回退：`bun test …/monitor-sandbox-autoallow.test.ts …/p2-wiring-and-sandbox.test.ts`
   → **26 pass / 0 fail**（P2-3 的 plan / deny-write / 危险命令 / 默认值四条防线全绿）。
4. `bun run typecheck:gate` → 62 处错误 / 基线 64 处，**无新增**。
5. **E2E-12 未在本 PR 做**：它要求真开沙箱的端到端环境（`sid-code-dev` 本体而非 `sc-dev`），
   按方案 §7.3 排在 FIX-1…8 全部合入之后。本 PR 证明的是 checker 判定层的条件收窄，
   不是「沙箱本身真的隔离得住」——后者是 Seatbelt 的既有问题，不在 D5 范围内。
