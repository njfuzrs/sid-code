# 会话持久化四项 P1：两条断在中间那一行的接线，两样漏掉对称清理的兄弟存储

来源：`docs-research/sid-code/bugfixes/todo/20260906-会话持久化与检查点-十二项缺陷交叉核查.md`
（十二项缺陷中的 D5–D8，即全部 P1；D1–D4 已在 PR #26 修完，D9–D12 是 P2 不在本次范围）。

## 决定了什么

**四项 P1 合并一个 PR** —— 按 `CONTRIBUTING.md` 的判据（可独立上线 / 可独立回滚 /
一次 review 完），它们三条全过，且关注点是同一件事：**checkpoint 与会话 id 的绑定关系，
以及按会话 id 分文件/分目录的存储的生命周期**。同优先级、同关注点、同一份方案文档，
没有理由分开——拆成四个 PR 只会付四次分支 + CI + review 上下文切换的固定成本。

**D5 / D6 是同一种缺陷形态**：上下游全对，**断在中间那一行接线上**。
grep 两端都能看到看起来完全正常的代码，功能却名存实亡。

- **D5：Rewind 文件回滚改用 `getLogicalSessionId()`，不再用构造期捕获的 `sessionId`。**
  构造函数比 `restoreSession()` 早跑，那时 `resumedSessionId` 还是 null，闭包一旦捕获
  局部变量就把「进程新 id」定死了。而**建**快照走的是逻辑 id，快照实际落在
  `checkpoints/<被恢复会话 id>/`。写对读错的后果不是「都不能用」而更隐蔽：
  resume 后同一批快照 `/undo` 找得到、Esc+Esc 面板找不到。
  改法是**把取 id 延迟到调用时**（闭包不能捕获 id 本身，只能捕获 `this`）——
  这一点决定了不能用「构造时传一个更好的 id 进去」来修。
- **D6：`recordFileChanges` 适配器补上第三个形参 `snapshotId` 并转发。**
  生产端传 3 个、接口声明 3 个、实现方完整处理 3 个、恢复端消费 `snapshotIds` ——
  四处全对，却因适配器箭头函数只写两个形参而集体空转。

**D7 / D8 是同一条被漏掉的原则**：`deleteSessionArtifacts()` 清了 jsonl 本体 /
summaries / sidechain / trajectories 四样，漏了 `checkpoints/<id>/` 与 `progress/<id>.md`。
两样都补上，且**抽成导出的 `deleteSessionSiblingStores()`**——因为删除会话有
**两个入口**：自动清理与 `handleDeleteSession()`（`--delete-session`，此前只 unlink
jsonl 本体）。原先两处各自罗列要删什么，同一条缺陷就存在两份；抄第三遍必然再漏一次。

两处路径口径刻意不自己拼字符串：checkpoints 走 `sidPaths.checkpoints()`
（与 `CheckpointManager.baseDir` 同一事实源），progress 走 work-log 导出的
`progressFilePath()`——写入端会 `sanitizeSessionId()`（非法字符替 `_`、截断 128 字），
自己拼 `${sessionId}.md` 在被清洗过的 id 上**删不中文件，且零报错**。

## 放弃了什么（以及为什么不选）

**没有给 D5 加「构造时传逻辑 id」的方案。** 时序上不可能：构造函数早于
`restoreSession()`，那一刻逻辑 id 还不存在。任何在构造期求值的写法都是同一个 bug
换个位置。判据是**取值时机**，不是取哪个变量。

**没有让 D7/D8 走「扫描孤儿」的清理方式**（遍历 checkpoints/ 找没有对应会话文件的目录）。
它能顺手清掉存量的 27 个孤儿 checkpoint 与 114 个孤儿 progress，但引入一个不可接受的
风险：**判据从「这个会话刚被我删掉」变成「我没找到对应的会话文件」**，而后者在
按项目分目录、`SID_CONFIG_DIR` 被重定向、或扫描面算错时会**误判健康会话为孤儿**——
代价是删掉用户还在用的快照。对称清理只删「本次确实删掉的那个 id」，
是一个**不可能扩大打击面**的写法。存量孤儿留给单独的一次性清理去做，
不与这条常态路径混在一起（§0 铁律：不可逆操作先收窄判据）。

**没有把这四项拆成四个 PR。** 见上文判据。

**没有为 D5/D6 写行为层测试。** 不是偷懒，是没有接缝：`recordFileChanges`
全仓零测试引用，`RewindManager` 的既有测试用**假依赖**注入 `restoreToSnapshot`，
够不到 app.ts 里那一行真实接线——而那一行正是缺陷本体。所以门禁立在源码文本上，
并按仓内先例（`session-start-probe-wiring.test.ts`）用 `readFileSync` 而非 shell grep：
app.ts 曾含 NUL 字节，grep 会判成 binary 并**静默跳过**。

## 拿什么证明它生效了

**两个新门禁都做了变异自证**（本仓要求：没被证明能抓住缺陷的门禁不算门禁）：

- D7/D8 行为门禁（`packages/core/tests/session/cleanup.test.ts` 新增 3 例）：
  注释掉 `await deleteSessionSiblingStores(sessionId)` 这一行接线 →
  `1 fail`，红在 `expect(existsSync(oldCp)).toBe(false)`；恢复后 `10 pass 0 fail`。
- D5/D6 静态门禁（`packages/cli/tests/app/checkpoint-session-id-wiring.test.ts`，8 例）：
  把 D5 改回 `getCheckpointManager(sessionId` → `2 fail`；
  把 D6 适配器改回 `(files, toolName) =>` → `1 fail`；两次恢复后均 `8 pass 0 fail`。

每条断言都配了**反向自证**，防的是「更糟的实现也能变绿」：D7/D8 的用例同时断言
一个受保护会话的 checkpoints/progress **必须还活着**——缺了它，
「helper 把 checkpoints/ 整个根目录 rm 掉」这种实现也会让前三条断言全绿。

**门禁判据刻意不数调用点个数**（`getCheckpointManager` 的调用点数量），
而是断言「不存在 `getCheckpointManager(sessionId` 这种写法」——数个数会在
将来新增一个**正确**调用点时误红，而误红的门禁下一步就是被 `--no-verify` 绕过。

**新门禁自己先被另一道门禁抓了一次，如实记下来。** 全量 `bun test` 报
`no-real-path-writes.test.ts` 违规：`checkpoint-session-id-wiring.test.ts`
「用了 `getCheckpointManager` 却没声明隔离」。这是**假阳性**——该文件是纯静态扫描，
只 `readFileSync` app.ts 的文本，不 import 也不调用任何落盘导出，一个字节都不写；
命中是因为哨兵按 `\bgetCheckpointManager\b` 扫全文，而断言字符串里必须出现这个符号。

处理方式是**满足哨兵**（加 `SID_CONFIG_DIR` → mkdtemp 重定向），
**不去放宽哨兵的判据**：那道门禁的宽口径是它自己注释里写明的刻意取舍
（「宽判据 + preload 兜底」，精确配对会让映射变三态），为一个假阳性收窄它，
换来的是所有真阳性的漏检面变大。代价只是本文件多 12 行样板。

**项目门禁**（在 worktree 内先跑过 `bun install` + `vendor:fetch`，避免
`@sid-code/core` 向上解析到主仓 checkout）：

```
bun run affected-tests        → selective，2 个目标
bun run affected-tests:run    → 1672 pass / 0 fail（154 文件，28.12s）
bun test（全量，提 PR 前要求）  → 11753 pass / 1 fail（797 文件，164s）
make build                    → rc=0，自检 4 项通过
  grep "will always be undefined" → 0 命中（本次新增了导出，这条必须显式查）
bun run lint / format:check / lint:boundary → 全绿（越界依赖 0 处）
bun run docs:gen-reference --check → 参考页与源码一致
```

**那 1 个 fail 与本次改动无关，按仓库要求的三条证据举证**（不叫它「既存失败」——
那个词意味着主干本来就坏，会让人跳过排查；真实成因是 worktree 环境）：

1. **不 import 本次改动的任何模块**：`plan-mode-write-plan-file.test.ts` 只 import
   `permission/checker.ts`、`plan/state.ts`、`config/config.ts`；
   `git diff --name-only origin/main...HEAD` 里没有 `permission/` 或 `plan/` 任何文件。
2. **换到中性 cwd 单跑即通过**：`cd /tmp/... && bun test <该文件绝对路径>` → **6 pass / 0 fail**。
3. **具体环境成因已定位**：worktree 路径含 `.claude/`，命中
   `permission/checker.ts:198` 的敏感路径拦截（`{ pattern: ".claude/", reason: "Claude 配置目录" }`），
   在 plan-mode 判定**之前**就返回。报错原文是
   `非交互模式下自动拒绝: [安全检查] Claude 配置目录`（期望 `计划模式`）——
   结论仍是 DENY，只是 reason 不同。这是记忆里已登记的已知 worktree 产物。

**诚实边界：D6 的修复效果没有端到端复算。** 门禁证明的是「参数被转发了」，
不是「磁盘上的 `file_changes` 真的带上了 `snapshotIds`」——后者要跑一次真实会话
并触发工具改文件才能看到。文档给的复跑命令（附录 A.3）是本机 152 条 / 0 条带锚点；
本次没有重跑它，因为在 worktree 里跑真实会话会写进真实 `~/.sid-code/`。
**这条留给下次真实使用后复算**：`jq` 统计 `lastSnapshotId` 非空条数应从 0 变正。
同理，D5 的「Esc+Esc 面板在 resume 后能回滚文件」是交互路径，本次只做了静态接线保证。
