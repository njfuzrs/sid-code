# 密钥识别规则收成一份带档位的规则表，审计落盘前用它脱敏

## 决定了什么

**B15（规则统一）**：新建 `packages/core/src/permission/secret-rules.ts`，把此前分散在三处的
内容扫描规则收成一张 23 条的表（`SECRET_RULES`），每条声明自己参与的档位：

- `strict`（近零误报，命中即拒）→ R2 记忆闸门（`llm/hooks/secret-redact.ts`）、R3 团队扫描
- `wide`（遮了不伤功能）→ R1 落盘（`permission/sensitive.ts`）、B16 审计

三处消费方改成从规则表取，不再各自维护正则：

- R1：23 条原样迁入规则表，`sensitive.ts` 只剩「wide 档的呈现」（保形遮盖 + JSON 词法扫描）
- R2：从 strict 档取规则，fixture 守护**留在消费侧**（它是「命中之后要不要当真凭证」的上下文判断，
  下沉会让 R1 也开始放过 `AKIA…EXAMPLE`）
- R3：与规则表重复的 6 条改成 `ref` 引用；gitleaks 独有规则、以及需要更精确长度的
  （`github_fine-grained_pat_{82}` / `anthropic_{93}AA`）留作 extension

**补掉的漏点**（B15 的实际工作量，均有探针表断言）：

- `github_pat_` 此前不在 R2 —— 私有记忆可以把 fine-grained PAT 写进去
- `SECRET=…` / `AWS_SECRET_ACCESS_KEY=…` 此前不在 R2 —— R2 的 `GENERIC_API_KEY` 只认
  `api_key` / `access_token` / `secret_key` 三个键名
- R3 收的都是独特前缀，键名赋值类天然缺失 —— 这部分**不补**（见「放弃了什么」）

**B16（审计脱敏）**：`AuditLogger.log()` 在 `JSON.stringify` 之后、`appendFileSync` 之前整行脱敏
（`maskSensitiveJson`），主日志与 `-retained.log` 复用同一个 `line` 变量，一处收口两处生效。
三级降级：字段级占位 → `redactFallback`（自由文本字段全换占位、枚举字段保留）→
`{redaction_failed:true}` 占位行。**不丢行、不落原文**。

`slack-bot-token` / `slack-user-token` 合并为规则表的 `slack-token`：原两条正则都只是
`xox[bpors]-` 的子集，合并后覆盖面只增不减（测试已同步更新契约）。

## 放弃了什么（以及为什么不选）

| 候选 | 否决理由 |
| --- | --- |
| 三套规则合并成一套一模一样的 | 会把「误报代价不同」造成的合理差异一起抹平：团队记忆开始拒正常写入、私有记忆闸门开始误伤。**要消灭的是漏点，不是差异** |
| 以 R2 为唯一真源 | 覆盖面最窄，且带 fixture 守护 —— 审计里 8 处 PEM 全是测试代码字面量，走 R2 会被全部放过。审计需要「宁可多遮」 |
| 把 fixture 守护下沉进规则层 | 会让 R1 放过 `AKIA…EXAMPLE`，与落盘准则相反（R1 现在照遮，是对的） |
| 审计逐字段脱敏（`resource` / `reason` / `decisionReason.reason`） | 字段清单要人工维护，下一个新增自由文本字段一定漏 —— 这正是 `audit.ts` 里 B19 记录的教训（调用点十几个，逐个补必漏）。整行词法扫描自动覆盖所有字符串字面量，且数字不碰 |
| 审计脱敏复用 `trace/writer.ts` 的 `maskJsonSafe` | 循环依赖：`logger.ts` 已 import `sensitive.ts`，而 `maskJsonSafe` 依赖 `getLogger()`。审计侧自带降级（见上） |
| 把 DB URL / Bearer / x-api-key 也补进 R3 | R3 的读者是「同步给协作者的团队记忆」，误报会挡住正常写入且没有逃生舱。这几类形态宽松、在团队文档里高频出现（curl 示例、鉴权头），**只进 R1/R2** |
| 补 `MY_API_KEY=/path/…`（三套全漏） | 值含 `/` 会被判为路径。放宽会让 `KEY=/usr/local/bin/xxx` 这类路径被遮 —— 属于已知不覆盖，写进规则表注释 |

**与方案文档的一处偏差**：方案 §3.3 把 `SECRET=` / `AWS_SECRET_ACCESS_KEY=` 列为「补到 R2」，
§7 又说「`SECRET=` 只进 wide」。按 §6 的验收口径（「矩阵里只剩 (b) 类差异」）实现为
**strict+wide**：赋值写法带 `literalSecretValue` 二次校验（排除表达式、路径、占位、短值），
误报已可控，属 strict 该收的。R2 的覆盖因此只增不减。

## 拿什么证明它生效了

**新增测试**

- `packages/core/tests/permission/secret-rules-consistency.test.ts`（24 例）：
  16 行探针表 × 三档 API，`tiers` 决定 mask/detect 的期望，R3 单独声明；
  「R3 期望与 strict 档不一致必须带 note 且 note 写清误报代价」+ 规则表结构不变量
  （id 唯一 / 每条有 label / 每条至少一档 / 两档非空）。
  **变异自证**：把 `bearer-token` 的 `tiers` 从 `["strict","wide"]` 删掉 wide →
  `bearer` 探针立刻变红（`Received: false`），恢复后 24 pass / 0 fail。
- `packages/core/tests/permission/audit-redaction.test.ts`（12 例）：
  ① `OPENAI_API_KEY=` / `github_pat_` / PEM / `reason` 落盘后被遮，主日志与保留日志都验；
  ② `session_id` / `tool_use_id` / `decision` / `timestamp` / 数字 `0.4428123456780257` 逐字节不变；
  ③ 干净行 `raw === JSON.stringify(entry) + "\n"`；④ 降级路径字段占位、不丢行。
  **变异自证**：审计侧把 `redactLine` 换成恒等函数 → ① 必红（见下方实测记录）。

**那 5 个失败与本次改动无关的三条举证**

1. 失败的是 `isSensitivePath` 路径校验（`checker.test.ts`、`hook-decision-injection.test.ts` 等），
   本次改动没有触碰 `path-validator.ts`；
2. 父仓 `main` 上 `bun test ./packages/core/tests/permission/` → **1174 pass / 0 fail**（同一 HEAD 的代码）；
3. 环境成因已定位到规则：worktree 目录名 `b15-b16-secret-rules-audit-redaction` 含 `secret`，
   命中 `SENSITIVE_NAME_PATTERNS` 的 `/secret/i`；`package.json` 不在 `SOURCE_EXTENSIONS`
   （`.ts`/`.md`…）里，豁免不生效 → 工作区内的 `package.json` 被判「敏感文件（凭证类，默认拒绝）」。
   实测：`PermissionChecker.check({toolName:"read", file_path:"package.json"})` 在 worktree 里
   `reason = 敏感文件（凭证类，默认拒绝）: …/b15-b16-secret-rules-audit-redaction/package.json`。
