# 工作区外读取改为需确认：读边界与写边界同口径

## 决定了什么

`PathValidator.validateAccess` 的第 5 步（工作目录边界）从「仅写」扩展为「读写都查」，
并做两处配套改动，三处缺一不可：

1. **第 5 步读写都查**：路径落在工作目录集合（工作区 ∪ `--add-dir` 追加目录）之外时返回
   `needsConfirmation: true`（不是硬 deny）——交互模式可当轮允许，无头模式按既有规则
   降级为 deny 并把成因写进 `decisionReason.reason`。
2. **敏感文件检查前移**到边界检查之前。否则工作区外的 `.env` / `*.pem` 会先落到边界分支，
   从「硬 deny」退化成「可点确认放行」——那是安全回退。新增 `outsideWorkingDirs` 标记
   与 `sensitiveFile` 区分，避免两件事被混成一件。
3. **checker Step 4 给工作目录边界的拒绝开 allow 规则逃生舱**：此前只有 `sensitiveFile`
   可以经用户显式 allow 规则解除。不开口子的话，用户对「读工作区外文件」没有任何配置
   途径（`Read(/data/**)` 写了也不生效），无头模式下只能失败。

对齐口径：Claude Code 对工作目录之外的 Read 要确认，`--add-dir` 追加的目录则读写都放行。

## 放弃了什么（以及为什么不选）

1. **只改 `PathValidator`、不给 allow 规则口子。** 无头模式（`-p` / `maxTurns > 0`）下
   `needsConfirmation` 直接降级为 deny，用户除了 `--add-dir` 没有任何办法长期放行某类路径；
   `Read(/etc/**)` 这类规则写了也不生效，等于把「可配置」退化成「要么全加目录、要么每次
   点确认」。
2. **只对交互模式收紧、无头模式保持放行。** 同一个安全面在两处口径不同，会出现
   「同一份配置在 CI 上比人宽松」的反直觉结果，而 CI 恰恰是最容易无人值守读走区外文件的场景。
3. **让敏感文件检查留在原位、边界分支先返回。** 那样工作区外的 `.env` 读会变成
   `needsConfirmation`（用户点一次允许就拿到凭证），把 SEC-AUDIT-2026-07-19 P2
   刻意收紧的硬 deny 又放回去了。
4. **顺手把 `grep` / `read_many` 的 `path` 参数也收紧。** 那两个工具本来只对敏感路径走完整
   校验（普通目录作搜索根是有意放宽的），一起动会让这个 PR 同时覆盖两个工具面，
   出问题时无法判断该回滚哪一段。留作单独评估。
5. **加一个默认关闭的配置开关。** 默认不放行就等于没修（CC 的默认行为就是 ask），
   而多一个开关意味着两条路径都要维护与测试。需要长期放行的用户有 allow 规则可用。
6. **对「工作区外写」也一并改成硬 deny。** 写边界一直是 `needsConfirmation`（交互可允许），
   本次只对齐读侧口径，不改写的既有语义——收严写侧是另一个安全面。

## 拿什么证明它生效了

- 新增 `packages/core/tests/permission/read-outside-working-dirs.test.ts`（9 例）全绿：
  工作区内读 allow / 工作区外读 needsConfirmation（断言 `outsideWorkingDirs` 与
  「读取路径在工作区外」）/ 工作区外写口径未变 / `--add-dir` 内读 allow /
  **工作区外 `.env` 仍是硬 deny 且 `needsConfirmation: false`**（前移的核心证据）/
  checker default 模式需确认 / **显式 allow 规则可放行** / 无头模式 deny 且
  `decisionReason.reason` 含真实成因 / allow 规则不放行系统目录保护。
- **变异自证 3/3**（改坏 → 断言变红 → 恢复并逐字节校验）：
  第 5 步改回「仅写」→ 工作区外读 + checker 两条变红；把敏感文件检查移回边界之后 →
  「工作区外 `.env` 仍是硬 deny」变红；去掉 checker 的 `outsideWorkingDirs` 分支 →
  「显式 allow 规则可放行」变红。
- 权限域 **752 例全绿**。5 个既有用例的断言随契约同步（`读操作自动放行`、
  `正常路径不被路径校验拦截`、`工作区外读取允许`、`读取 /etc/ 允许`、
  `hook ask 把本会放行的读操作升级`）——它们的意图保留，fixture 换成工作区内路径，
  否则验的就不是原意而是「区外该不该拦」。
- 门禁：`affected-tests:run` / `make build` / `lint` / `format:check` / `lint:boundary` /
  `lint:command-system` / `typecheck:gate` / `docs:gen-reference --check` 全绿（PR 内贴结果）。
- 已知影响（review 时必须知情）：**这是破坏性变更**。无头模式下读工作区外文件会开始失败，
  用户需要配 allow 规则或 `--add-dir`。建议 release note 点明。
