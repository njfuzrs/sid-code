# 唤醒撤销链路接通：S2 在 monitor 成功终态通知送达时生效，撤销提示改为常驻

## 决定了什么

FIX-4b（缺陷方案 D8 + D9 + L4 的 T-W2-4 + L7 的 wait Note）。
落点：`task/wait-registry.ts`、`query/loop.ts`、`task/index.ts`（re-export），不改 `app.ts`。

- **D8 / S2 接线**。`invalidateWakeups("subject_terminal", …)` 此前在生产代码里零调用方，
  现在由「monitor 成功终态的通知**送达**」驱动：
  1. **快照**：`releaseWait(id, "terminal")` 里，若登记项是 monitor 且带 subjects，把它搬到
     `terminalMonitorSubjects`（键 = 任务 id）。必须在这里搬——D4 之后终态那一刻就释放，
     而 subjects 只存在登记项里，到通知送达时已经读不到；`monitor-task.ts` 的终态写入
     （`updateTask` → `onTaskChanged` → 释放）也早于 `enqueueTaskNotification`。
  2. **消费**：`injectPendingNotifications` 的 `markNotificationsDelivered(...)` 之后
     （通知真正进模型上下文的唯一汇合点）遍历本批通知，调
     `invalidateWakeupsForDeliveredTask(taskId, status)`：只对 `completed` 撤销，
     `failed` / `killed`（到期、`task_stop`）不撤销；**非终态通知不消费快照**——
     monitor 的每条事件都是 `running`，它与终态通知进同一批，先到的事件若吃掉快照，
     紧跟的终态通知就判不出 S2（实测让 R6 一直绿不了，见「拿什么证明」）。
  3. 撤销的 reason 文案为 `监控 <id> 已完成（<subject>）`；快照 5 分钟 TTL 兜底
     （通知可能被 `task_output` 认领而永不送达），会话结束与测试复位时清空。
- **D9 / 撤销提示常驻**。`loop.ts` drain 撤销通知时：
  - `persistent: true`（`app.ts` 的 `event.persistent` 分支已存在，走 `appendPersistentHint`
    写历史区；此前是普通 info → `system:transient`，同一轮 `done` 就被清掉）；
  - `WaitNotice` 新增 `promptPreview`（登记项 `description` 即 prompt 首行，再截 30 字），
    文案 `已取消定时唤醒 <id>（<prompt 预览>）：<原因>`；
  - 同一轮多条撤销合成**一行**（`已取消 N 条定时唤醒：…；…`），不刷历史区。
- **T-W2-4**：等待期 `todo_write` 把项标 `blocked` 后，T2 仍放行。用例走真实
  `TodoWriteTool({ invalidatesWakeups: true })` 写入 + `makeGateHarness` 跑真实 `queryLoop`。
- **L7**：`2026-11-08-等待登记表与合法等待态.md` 的两处不实描述（:44 S2「只用确定信号」、
  :79 T-W3-9「S2 subject 匹配」）按方案要求**不删原文**，各追加一行「更正（2026-11-09）」。

## 放弃了什么（以及为什么不选）

- **不在 `releaseWait(terminal)` 里直接撤销**（方案 D8 修复第 4 条的字面写法）。
  第 1 条要求时机是「通知**送达**之后」，第 4 条要求落在 `releaseWait` 内部——两者在
  实现上不能同时成立：终态释放比送达早一段，且先于 `enqueueTaskNotification`。
  按第 4 条做会把 S2 变成「终态即撤销」，通知投递链路出问题时（D2/D3 的形态）模型
  既不知道结果、也不再被叫醒，正好是 #642 否决自动撤销时最担心的静默中断。
  取第 1 条的语义（S2 判据原文是「已成功终态 + 通知已投递」），用快照桥接两半。
- **不把 subjects 挂到 `TaskState` 上，也不改 `monitor-task.ts`。**
  那两处是 FIX-2 / FIX-7 的共改文件（方案 §4.3），且会让「等待对象的签名」出现第二份
  权威来源。快照只做一次短命中转，来源仍是登记项，送达即删。
- **不加 `WaitEntry.pendingDelivery` 之类的布尔字段。** 快照的方向是「登记项 → 送达点」，
  与 `firedMono` 那种「调度器记事实、等待表查询」不同：这里搬的是即将消失的数据，
  不是可再查的事实。有界性靠 TTL + 送达即删，不靠会话生命周期。
- **不做 app 级 `historyItems` 渲染用例**（方案 D9 验收第 2 条）。`appendPersistentHint`
  与 `bridge` 都是 `runTUI` 内的闭包，现有结构没有「喂一个 system 事件」的入口；
  为一个守卫起真实 `runTUI` + ink 渲染不划算。改为：loop 级真实入口断言
  `persistent === true`（`wait-notice-persistent.test.ts`）+ 源码守卫锁住
  `app.ts` 的 persistent/transient 分流（`wait-notice-persistent-routing.test.ts`）。
  TUI 渲染实证（截图核对历史区那一行）按方案 §L5 归 E2E-7，那里本来就是 D9 的最终判据。
- **不给 `invalidateWakeupsForDeliveredTask` 做「多 subject 去重」。** 同一唤醒被两个
  subject 命中时，第二次 `releaseWait` 已是 no-op（`invalidateWakeups` 只遍历现存登记项），
  不会重复撤销、也不会重复发事件。
