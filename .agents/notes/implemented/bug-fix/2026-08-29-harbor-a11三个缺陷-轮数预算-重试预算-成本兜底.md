# Harbor A11 挖出的三个 harness 缺陷：轮数预算被偷、两层重试预算相乘、超时 trial 成本低报

## 决定了什么

三个缺陷全部取自 A11 真实 benchmark 的第五棒执行记录（`02-Harbor接入方案设计.md`
§15.5 / §15.6 / §15.7），每条都有 file:line 级判据和可复算的样本。**三条共用一个主题**：
harness 在网络故障下**把"故障"记成了"能力不足"或"没花钱"**，而三处都**不报错**。

### 缺陷 1（§15.5）：轮数预算被超时偷走 → 如实记账，但**预算照扣**

`queryLoop` 的 `while (turnCount < maxTurns)` 一进来就 `turnCount++`（在**发请求之前**），
而 SDK 的 `num_turns` 只在 `assistant_message` 上自增。于是一个被 watchdog 杀掉、
零内容产出的轮次：**占掉一格预算，却在 `num_turns` 里完全隐身**。
实测 7 个 `error_max_turns` 样本全部满足 `num_turns + WatchdogKill = 41`（7/7），
其中两题 40 格只换来 **34** 次模型交互。

改动：

| 位置 | 改了什么 |
| --- | --- |
| `query/types.ts` | `LoopState` 新增 `turnsConsumedWithoutAssistant`；`max_turns` 事件带上该字段 |
| `query/loop.ts` | 超时重试分支内递增（**只在"重试真的会发生"那一支**）；收尾日志说出归因 |
| `sdk/schemas.ts` | `SDKResultError` 新增 `num_turns_without_model_interaction`（`.default(0)`） |
| `sdk/message-converter.ts` / `query-engine.ts` | 三个 error result 构造点全部填齐 |
| `cli/src/app.ts` / `sdk/headless-event-format.ts` | TUI 与 headless 文案带上归因 |

**⛔ 刻意不做「被杀的轮次不占预算」**：那样上游持续故障时循环永不收敛
（每次退回同一格），把「预算被偷」换成「无限重试」——后者在无头评测里会一路烧到
1 小时硬顶。所以形态是**保留收敛性 + 把被偷的格数如实透出**。
`turn-budget-stolen-by-timeout.test.ts` 第 2 个 test 专门钉这条设计决策，
防止后人"优化"成不占预算。

### 缺陷 2（§15.6）：两层重试预算相乘 → 把 wall-clock 预算交给内层

内层 `fallback.ts` 有 11 次重试预算；外层 watchdog 在 315s（`headerTimeoutMs 300s`
+ `watchdogHeaderGraceMs 15s`）无首字节时强杀整个调用。实测内层每次只用到
attempt **4–5 / 11** 就被杀，外层 `TimeoutRetry` 又从 attempt 1 重新数 ——
**两层预算不是共享，是相乘**。7 个周期 ≈ 37 分钟、零内容产出（`chunk_count: 0`）。

**这个缺陷的形态值得单独记：修复代码早就在，只是从没被接上。**
`fallback.ts` 的 S3 时间预算钳制（`perCall.deadlineAt`）**早就实现且有测试**
（`tests/llm/resilience-b6-gates.test.ts`），但主循环调的是**不带 `perCallOptions`
的三参版本** —— 于是那套钳制在生产路径上**一次都没跑过**。
本仓「伪配置 / 死功能」的同型：代码在、测试绿、真实路径不经过。

改动：`QueryDeps.sendWithRetry` 增加可选第三参 `{ deadlineAt }`，
`engine.ts` 透传给 `executeWithFallback`，`loop.ts` 在建流前算出
`min(headerTimeoutMs + grace, watchdogNoProgressMs)` 并在**两个**建流点都传。
为此把 `netTimeouts` 的声明从"建流之后"上移到"建流之前"（仍在 `try` 之外）。

**一个阈值都没动。** 记忆里两条相关教训——「多层超时同为 300s → 单点修复只换杀手」
「抬阈值治不了」——说的都是改数字；本次动的是**两层之间要不要交换"还剩多少时间"这个事实**。
`deadlineAt` 取 `min` 而不是 `max`：取大的会让内层以为还有时间、继续睡退避，
然后照样被先到的那层杀掉 = 等于没修。也**刻意不把** `maxTurnDurationMs`（90min 单轮硬顶）
算进来——它是"整轮"预算而 `deadlineAt` 是"这一次调用"的，混进来正是本缺陷的形态。

### 缺陷 3（§15.7）：超时 trial 成本低报 → `session.traj` 兜底

trial 撞 Harbor 的 3600s 硬顶被 SIGKILL 时，`result` 事件从未发出 →
`cost_usd: null` / `sid_cost_source: "missing"`。而 `fix-code-vulnerability` 的轨迹里
有 3 次成功调用、**75,732 prompt tokens、$0.0538** 的真实花费，**没进任何账**。
本次量级小（$7.18 → 真实 ≈ $7.26，低报 1.1%），但**低报幅度与超时 trial 的比例成正比**，
且它**不报错**——`null` 被下游求和当成 0。

改动：`sid_code_agent.py` 新增 `_recover_usage_from_traj()`，在 `result is None` 分支
从 `session.traj` 的 `metadata` 兜底取用量与成本，并落 `sid_cost_source:
"session-traj-fallback"`（**与权威源 `stream-json-result` 区分**，因为兜底值可能偏低——
最后 ≤30s 的调用没来得及落盘）。同时补 `sid_result_event_missing: true` 保住归因。

**口径铁律（本次最容易写错的一处）**：`n_input_tokens` 取
`total_cumulative_prompt_tokens`（flow），**绝不能取 `total_tokens_sent`**（stock，
末次快照含全历史）。stock ÷ flow 会算出一个错的单价，**且它不报错**。
与 §15.1 误用 `cache_write_tokens` 得到"每跑一次变 2.5 倍"是同型。

## 放弃了什么

- **§15.8 说缺陷 1 和 2「不要合成一个 PR」，本次仍合在一个 PR 里** —— 用户明确要求
  三个一起修。折中：**拆成三个独立 commit**，每个可单独 revert，review 时仍是三件事。
  代价是 PR 的 review 面比 `CONTRIBUTING.md` 的单元判据大。
- **不改 `num_turns` 的语义**。让它去数"花掉的格数"会改变一个外部消费者已在依赖的字段，
  且它当前的语义（模型交互次数）是对的。改为**新增**一个字段解释差额。
- **不动任何超时阈值**（见上）。315s 是否合适是另一个问题，本次不碰。
- **不做 `--max-turns` 的自动补偿**（被偷 N 格就多给 N 格）。它会让"上限"这个变量在
  评测里不再固定，跨 agent 对照立刻失去可比性——而可比性是接 Harbor 的唯一理由。
- **兜底成本不写回 `session.traj`**，只在 Harbor 侧回填 `AgentContext`。写回等于造第二个
  事实源；轨迹的权威修复路径是既有的 `backfillTrajCost`（`trace/cost-recompute.ts`）。
- **`_recover_usage_from_traj` 不重算 cost**，直接取 traj 里 collector 已累加的
  `total_cost_usd`。重算需要定价表 + 分时段汇率，在 Harbor 侧重算会与 sid-code 自己的
  账本产生两个不一致的数（§15.7 手算的 $0.0807 与 traj 的 $0.0538 差 50%，
  正说明"手边重算"不可靠——**取源字段，不重算**）。

## 拿什么证明它生效了

**每条修复都做了变异自证**（`CLAUDE.md`：新增门禁必做），因为「测试全绿」在这三处
本来就成立过——缺陷 2 那套钳制就是"有测试且绿"却从不生效。

| 缺陷 | 变异操作 | 变异后结果（= 门禁真的在测它） |
| --- | --- | --- |
| 1 | 删掉 `state.turnsConsumedWithoutAssistant++` | `1 fail`：`Expected 2, Received 0` |
| 2 | 把 `sendWithRetry(…, {deadlineAt})` 改回三参 | **`0 pass / 4 fail`**（整组翻红） |
| 3 | `_num("total_cumulative_prompt_tokens")` → `_num("total_tokens_sent")` | `2 fail`（L1 形态 + L2 行为**双层**都拦住） |

**缺陷 3 还做了真实数据复算**（不是构造 fixture）：直接读第五棒那次被 SIGKILL 的
trial 产物 `runs/a11-sid/fix-code-vulnerability__J7QsoKe/`，跑出

```
session_id  = 20260828-145335-3b0a5194
cost_usd    = 0.053779          # 修复前：None
n_input     = 1146              # flow 口径
prompt total= 75732             # 1146+59195+15391，与 §15.7 记的 75,732 逐字一致
api_calls   = 3                 # 与 §15.7「3 次成功调用」一致
```

L2 那个 test 里的每个数字都取自这次复算，所以它锁的是**真实样本**而非我编的值。

**门禁命令与输出**：

```
bun test packages/core/tests/query/turn-budget-stolen-by-timeout.test.ts   → 4 pass
bun test packages/core/tests/query/retry-budget-shared-with-watchdog.test.ts → 4 pass
SID_HARBOR_PYTHON=… bun test tests/eval/harbor-agent-contract.test.ts      → 23 pass（L1+L2 都真跑）
bun test packages/core/tests/query/ packages/core/tests/sdk/ packages/core/tests/llm/ → 860 pass / 0 fail
bun test（全量）                → 11285 pass / 3 fail
make build / bun run lint / format:check / lint:boundary → 全绿
```

⚠️ **全量那 3 个 fail 的归属必须说清**，否则"3 fail"会被下一棒当成本次引入的：
- 2 个是 `prune-branch-builds`（**修复前就红**，已用 `git stash` 在干净工作区复验：
  同样 `2 fail`），与本次改动无关。
- 1 个是 `SDKResultMessageSchema > error 结果` —— **这个是我引入的，已修**：
  新字段最初写成必填，导致**旧 result 事件全部解析失败**。加 `.default(0)` 后
  `packages/core/tests/sdk/ 129 pass`。这条值得留档：一个"提升可观测性"的改动
  差点变成"旧轨迹读不进来"的 breaking change。

**没有验证的部分（下一棒接手时别当已验）**：三条修复**都没有在真实 Harbor 容器里跑过**
——那需要重开一轮评测（上一轮 4h10m），且 §15.8 明确要求跑前先探上游掉流率
（`curl http://127.0.0.1:4100/__stats` 看 `upstream_error / 200_*`），本次未探。
所以「缺陷 2 是否真的把 37 分钟零产出压下来」目前只有单测层面的证据，
**缺一次真实 run 的前后对照**。缺陷 1 的记账、缺陷 3 的兜底都是纯确定性逻辑，
风险低于缺陷 2（后者改变了重试行为的时序）。
