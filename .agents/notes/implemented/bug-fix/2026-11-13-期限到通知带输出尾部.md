# 期限到的通知带上「期限内最后看到什么」，重挂时把这条事实写回回执

## 决定了什么

R8 的两条修法，落在四个文件与一个新模块：

1. **期限到的 kill 通知带输出尾部**。`registerWaitUntil` 的到期定时器不再直接
   `killShellTask(taskId, { summary })`，改为调用 `expireDeadlineShellTask`：
   先读 `.output` 的末尾 1024 字节（`getTaskOutputTail`），再 kill，把尾部经
   `TaskNotification.outputTail` 传进通知；`formatNotification` 在 `<summary>` 之后
   输出一段 `<output-tail untrusted="true">`，内容是**最后 5 行**（`takeTrailingLines`），
   读不到 / 为空时整段不出现。
2. **同对象重挂时的事实回执**。`expireDeadlineShellTask` 顺带把「这个对象上次是期限到、
   最后一行输出是什么」记进 `wait-registry` 的会话内表（按 subject 索引）；
   `bash.ts` 在 `decideWaitAdmission` 判为 `start`（旧等待已终态）时，把
   `formatPriorDeadlineExpiryNote` 追加到启动回执：
   `上一个盯 gh:pr:779 的等待 <id> 在期限内的最后输出是：<最后一行>。如果状态一直在变，问题在退出条件，不在期限长短。`

两条改动都只**补事实**，不新增任何命令、不拦截任何行为。普通 kill（Ctrl+F /
`task_stop`）不带 `<output-tail>`——那时代码没跑完，尾部输出不构成「等法不对」的证据。

## 放弃了什么（以及为什么不选）

- **限制期限只能缩短不能加长**（方案里明确「不做」）。期限长短本身是合法的用户选择：
  「CI 一般 40 分钟」这种等待就是需要 1800s。harness 看不出「这个等法没有退出条件」，
  它只看得见「模型又把期限加长了」——据此否决只会把合法的长等待一起拦掉，而模型
  照样会在被拒后换个等法重试。真正的修法是让模型看到「期限内一直同一个状态」，
  它会自己得出「加长没用」。这是**信息缺失**问题，不是**权限**问题。
- **把尾部并进 `<summary>`**。summary 是 TUI 单行摘要 + 模型快速判断的字段，多行
  输出混进去会让摘要失去判据（与既有 `<event>` 不并进 summary 的理由同源）。
- **在三个等待入口（bash / monitor / wakeup）都追加 R8-2 的回执**。产生「期限到」
  终态的唯一来源是 shell 的到期定时器，而「同对象重挂 → 判为 start」的路径也只有
  bash 后台等待一条：monitor / wakeup 换等法走的是 `replace`（旧等待还在跑），
  旧的那把没到期，这行事实不成立。三入口一致的是 R2 的**准入判定**，不是这条
  只在「上一次真的到期」时才为真的陈述。等出现「wakeup 也因到期而结束」的形态
  再扩，不提前铺一层没有调用点的导出。
- **给 `deadlineExpiryFacts` 加 TTL**。它要跨整个会话参与「这个对象之前到期过吗」
  的判定，清掉就回到事故前的形态（模型换个命令重挂，又看不到历史）。键是 subject
  字符串，量级由会话内出现过的对象数封顶。
- **让 `expireDeadlineShellTask` 住在 `bash.ts` 里**。那样单测必须等一次真实到期
  （钳制下限 60s），测不动；而且到期收口的三个依赖（读磁盘 / 杀进程 / 记等待事实）
  分属三个下层模块，放在工具实现里会让 `bash.ts` 多背一层协调职责。独立模块让
  `bash.ts` 的定时器与单测调**同一个函数**，测到的就是线上那条路。

## 拿什么证明它生效了

- `bun test ./packages/core/tests/tool/deadline-output-tail.test.ts`：**8 pass / 0 fail**。
  覆盖验收 1（含 `<output-tail>` 且内容等于最后 5 行、空输出不出现该段、
  普通 kill 不出现该段）与验收 2（有历史 → 回执含事实与「问题在退出条件」；
  无历史 → 不含；事实按对象隔离；读不到尾部不记空事实）。
- **变异自证**：把 `deadline-expiry.ts` 的 `const tail = await getTaskOutputTail(...)`
  改成 `const tail = null`，同一文件立刻 **2 fail**（验收 1 的尾部段与验收 2 的回执都红），
  恢复后回绿 8 pass。证明这两条断言不是恒绿。
- `bun run affected-tests:run`：**2016 pass / 0 fail**（137 文件）。
- `make build`：编译 + 产物自检全部通过。
- `bun run smoke`：**28 例全通过**（含 `R2-dup-wait-same-subject`、`N4-quiescent-declared-wait`、
  `replace-wait-same-subject` 三个直接压等待回执的用例）。
- `bun run lint` / `format:check` / `lint:boundary` / `lint:command-system` /
  `lint:legacy-tool` / `typecheck:gate`（62/62 无新增）/ `docs:gen-reference --check`：全绿。

没有做 G3 真模型验证：R8 的判据是「通知里有没有这条事实」，属开关型，由 G1 守；
模型拿到这条事实后会不会改退出条件，是模型行为，不在本次可验证范围。
