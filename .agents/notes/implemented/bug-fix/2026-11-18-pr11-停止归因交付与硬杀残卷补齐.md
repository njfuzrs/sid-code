# PR11 二次修复：把停止归因与硬杀残卷真正接到交付通道上

## 决定了什么

首版 PR11（#927）把「收尾函数 + 优雅停止 + 可见性」的代码写完了，但 2026-11-18 按方案
§6 PR11 / §8.2 的判据二次核验发现三处「写了但没生效」，本 PR 补齐：

1. **停止归因接生产端**。`AgentTaskResult.stopAction` 在 `task/types.ts` 定义、
   `completeAgentTask`（`task/agent-task.ts:185`）也读它拼 `<summary>`，但唯一的后台
   构造点 `agent/sub-agent.ts:1048` 没赋值 —— 后台完成通知永远是「执行完成」，
   打满轮次 / 被父代理停止 / 窗口耗尽三种可信度不同的结论在父代理眼里同形。
   现在补上 `stopAction: result.stopAttribution?.stop_action`，与同步回程共用同一来源。

2. **硬杀残卷允许落盘**。`killAgentTask` 只 `flushTaskOutput` 逐轮文本、从不写残卷；
   而 `failAgentTask` 用 `!isTerminalStatus` 一刀切，把 **killed** 也挡在外面。结果是
   `task_stop force` 与 60 秒超时退化两条硬杀路径上，salvage 的确定性清单（读过的文件 /
   最后 5 次调用）收集了却永远写不进 `.output`。改为只对 completed / failed 停写
   （它们各自写过结果或残卷，再追写会造出两份结尾），killed 与运行中一样追写。

3. **`max_tokens_exhausted` 补专属文案**。它是一条 `success: true` 的出口
   （`agentic-loop` 的 `maxTokensRecovery.decide → "stop"`），没有专属文案时会落到兜底
   分支，父代理读到的是 `非正常结束（max_tokens_exhausted）…` —— 英文枚举名直接进模型
   上下文，不符合「每种非 finalize 出口都有说明」。

配套：`failure-salvage-delivery.test.ts:158` 的旧断言「已被 kill 的任务不追写残卷」是
**本条契约的旧前提**，随本次改动同步改为「killed 仍追写、状态不改、通知不重复」。
这不是为凑绿改预期，而是被方案第 5 步（硬杀出口也要有确定性清单）直接改掉的契约。

## 放弃了什么（以及为什么不选）

**放弃：G2 两条冒烟用例（方案 §6 PR11 的 G2 ①②），本 PR 不做。**

理由分两层，都不是「没时间」：

- `ReplayProvider`（`packages/core/src/llm/mocks/replay-provider.ts:276`）是**纯顺序**
  回放，明确不做「按请求内容匹配」。G2 ① 要求「回放中父代理在子代理第 N 轮时调
  `task_stop`」——后台子代理与主会话**并发**消费同一个游标，谁先发请求取决于微任务
  调度，用例会 flaky。一个 flaky 的 G2 会在阻断合并的门禁上制造随机红，比没有更糟。
- G2 ②（窗口耗尽）顺序虽然确定，但要让子代理的 `emergencyTruncate` 真的腾出空间，
  需要先堆够消息且切点落在 ≥3（实测：切点 1 时 `no_reduction` 失败）。这类夹具的
  `expect` 只能从**人工核过的轨迹**里抄（CLAUDE.md 的 G2 硬约束），本 PR 没有这样的
  轨迹，自造等于从实现反推期望值。

**替代覆盖**：新增的 G1 集成测试用真实 `runAgentLoop` 驱动了窗口耗尽全链路
（provider → classifyStopReason → reactiveCompact → emergencyTruncate → 收尾轮），
用真实 `TaskStopTool.execute` → `requestAgentStop` → 超时 → `killAgentTask` 驱动了硬杀
链路。G2 缺的是「CLI 全链路 + 通知注入父上下文」这一层，需要维护者用真实轨迹补。

**没有选择「改 ReplayProvider 支持按请求匹配」**：它会改变全部 42 个现有用例的调度
语义，属于另一个独立改动，塞进本 PR 会让回滚面从 5 个文件扩到整个 smoke 框架。
