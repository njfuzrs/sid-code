# 预算硬停落成独立的 exit_status，不再记成 user_interrupt

## 决定了什么

M5 验收 F1：远程预算 `block`、本地预算规则 block、本地配额 exceeded 三条硬停
都是 `yield warning` + `yield done` + return。收尾 reason 落 `exit`，末轮
`stop_reason` 不是 `end_turn`，collector 的兜底桶把它记成 `user_interrupt`。
验收会话 `cd672461` 的 `messages.json` 写着
`reason=exit exit=user_interrupt api_calls=1`，没有任何人按 Ctrl-C，
而 `digest.ts` 把 `user_interrupt` 算进 abnormal。

照 `max_turns` 的既有做法补一条真实信号，不另造代理：

- `loop.ts` 的三条硬停在 `done` 上声明 `budgetExceeded: { source }`
  （`budget_rule` / `quota` / `remote`）。
- `engine.ts` 在 `done` 返回之前调 `traceCollector.recordBudgetExceeded`。
  collector 只订 hook，从 hook 里看不出「预算停了」和「用户中断」的区别。
- `collector.ts` 在 `user_interrupt` 兜底之前认这个信号，落
  `exit_status = "budget_exceeded"`，来源写入 `budget_exceeded_source`。
  `abort` / `error` 仍优先；与 `max_turns` 同时成立时 `max_turns` 优先，
  否则一次撞顶会被改写成预期收尾，abnormal 总数静默变少。
- `digest.ts` 单独计一条 `exit_status_budget_exceeded`（severity low），
  **不进** abnormal 名单，列表页也不标红。预算硬停是配置生效的预期行为。

F3 只改展示。`formatBudgetUsd`：不足半分的非零金额用四位小数，其余保持原位数。
远程告警和本地预算规则的文案都走它。验收 B3 的 `$0.001` 限额不再显示成 `$0.00`。

## 放弃了什么（以及为什么不选）

- **从 `stop_reason !== end_turn` 反推预算停**。collector 里 `max_turns` 那段
  注释写明了：换一个同样粗糙的代理只是把错误挪个位置。验收会话的末轮
  `stop_reason` 是 `error`，任何「非 end_turn 即预算」的判据都会把真正的
  请求失败也吞进去。
- **复用 `done.incompleteReason`**。那个闭集的消费方是 SDK，统一映射成
  `error_during_execution`。预算硬停混进去，归因又粘回一条。
- **把 `budget_exceeded` 算进 abnormal**。文档的建议是不算。算进去只是把
  「查中断源」换成「查故障」，处置方向还是错的。
- **F2 按文档修 headless 输出**。文档说告警只进 TUI 状态栏、`-p` 的
  stdout/stderr 都没有。源码不是这样：`formatHeadlessEvent` 从 2026-07-07
  起就把 `system/warning` 写成 stderr，`stream-json` 的 `message-converter`
  也转发 `system` 事件。用验收当时的二进制（`sid-code`，mtime 2026-09-24
  12:36，内联版本 0.1.605）重跑一次 `-p`：模型回复 `pong` 在 **stdout**，
  调试日志也在 stdout，**stderr 只有会话摘要**。文档看到的那句是因为
  `> file 2>&1` 把两个通道合在了一起，再把 stdout 上的调试日志当成了
  「告警只存在于日志流」。按文档改会修一个不存在的断点。
- **F3 改列类型**。文档把 `$0.00` 归因到 Postgres `real`（float4）把 `0.01`
  存成 `0.009999999776482582`。实测 `Number(0.009999999776482582).toFixed(2)`
  是 `"0.01"`，float32 的 `0.01` 同样四舍五入回 `0.01`。验收文案里的限额是
  `$0.001`（B3 用的就是这个值），`toFixed(2)` 对它本来就是 `0.00`，跟 float4
  无关。列类型在 agent-backend，不在本仓；相对误差也不影响比较和对账。
  文档自己的倾向也是先改展示。

## 拿什么证明它生效了

```
bun test ./packages/core/tests/query/ ./packages/core/tests/telemetry/ ./packages/core/tests/trace/ \
  --test-name-pattern '^(?!.*\[slow\])'
# 1858 pass, 0 fail
make build
# 产物自检四项 ✓；rg "will always be undefined" 无命中
```

collector 那组含反向自证：不上报 `recordBudgetExceeded` 时同样的输入仍是
`user_interrupt`；`abort` 优先于预算硬停；与 `max_turns` 同时成立时落
`max_turns`。digest 那组断言 `budget_exceeded` 的 `abnormal === false`，
且不出现任何 `user_interrupt` 异常。展示那组用验收的 `$0.001` 限额断言文案含
`$0.0055 / $0.0010`，并用 `Float32Array([0.01])[0]` 锁住「float32 漂移不是
`$0.00` 的成因」。

没做的：没有再跑一次真实的远程 `block` 会话。那需要把生产 org 的月预算改到
已用量之下，是对外的状态变更，不在这次修复里做。归因链的两端（loop 声明、
collector 落盘）都有测试；中间的 engine 接线有一条读源码的哨兵，断言
`event.budgetExceeded` 和 `recordBudgetExceeded?.(` 都在 `engine.ts` 里。
