# CLAUDE.md 的禁用工具也裁剪工具集，不再只进权限层

## 决定了什么

`app.ts` 的 `applyProjectRules` 合并 CLAUDE.md `## Disallowed Tools` 时，改为调用新抽出的 `applyRuleToolDenylist`（`packages/cli/src/utils/project-rules-tool-denylist.ts`）。它做两件事：

- 对 `this.toolRegistry` 调 `removeByNames`，被禁工具的 schema 不再进上下文，之后注册的同名工具（MCP 回填）也被拒收；
- 把名单按并集去重写回 `config.disallowedTools`，热重载反复合并同一份名单不再无限追加重复项。

修之前，`removeByNames` 只在 `cli.ts` 启动期对命令行 / settings 名单调用。`applyProjectRules` 的三个调用点（doInit、CLAUDE.md watcher、切 worktree）都晚于这次裁剪，所以 CLAUDE.md 里禁掉的工具只有权限层 Step 3 拦。叠加 `--dangerously-skip-permissions` 时 `check()` 在 Step 3 之前早退，这份名单就完全不生效，也不打日志。

热重载的语义定为「会话内只收紧、不放宽」：从 CLAUDE.md 删掉一条禁用，需要重启才会解除。这与 `removeByNames` 拒收名单不可撤销的特性一致，也和远程策略只允许收紧的取向一致。

`registry.ts` 与 `cli.ts` 里「CLAUDE.md 路径只靠权限层兜底」的注释同步改了。权限层判据保留，作为兜底。

方向：更安全（禁用名单在 skip 模式下也能生效）、更省（模型不再反复调用被禁工具、反复换回拒绝）。牺牲的是：会话中途新增禁用会改变工具列表，击穿一次前缀缓存。这条路径本来就低频，可以接受。

## 放弃了什么（以及为什么不选）

- **把权限层 Step 3 挪到 skip 早退之前**：模型仍然看得见工具，仍然会调，每次换回一条拒绝。`cli.ts` 的注释早已否掉这个形态，判据必须是「工具不可用」。
- **热重载以最新 CLAUDE.md 为准（允许放宽）**：`removeByNames` 之后 registry 拒收这个名字，要放宽就得另开重新注册的路径，还要能区分哪些名字来自命令行、哪些来自 CLAUDE.md。为一个低频场景加这套机制不值。
- **只对「新增」的名字调 `removeByNames`**：如果某个名字早已在 config 名单里，但对应工具是后来才注册的，这样做就会漏掉。`removeByNames` 本身是幂等的，对整份规则名单调用更简单，也不会漏。

## 拿什么证明它生效了

- `bun test ./packages/cli/tests/utils/project-rules-tool-denylist.test.ts`：5 pass。断言覆盖四点：裁剪后 `definitions()` 里没有被禁工具；MCP 工具后注册也被拒收；重复合并能去重；`applyProjectRules` 的接线。另有一条测试把前提钉住：`skipPermissions=true` 时权限层对禁用名单直接放行。
- 变异自证 1：把 `applyRuleToolDenylist` 里的 `removeByNames` 调用删掉，前 2 条变红。
- 变异自证 2：把 app.ts 传入的 registry 换成空实现，接线那条变红。两次变异都已恢复。
- `bun run affected-tests:run`：3873 pass / 0 fail。`make build` 自检通过，没有 `will always be undefined` 告警。lint、format:check、lint:boundary、typecheck:gate（66/66）、`docs:gen-reference --check` 全部通过。
