# 子代理停止原因对齐主循环：F1 连坐 + F2 fall-through

## 决定了什么

子代理 `agent/agentic-loop.ts` 的停止原因 / 空参数判断改成与主循环同一顺序、同一组纯函数，**不改执行器**。

1. **F1（D2）**：不论 `stop_reason`，命中空参数即调 `replaceEmptyParamToolUses` 连坐（同一 content 全部 tool_use 降为 text）+ `buildEmptyParamRetryMessage`，上限 `MAX_EMPTY_PARAM_RETRIES`。助手消息以 sanitized 入历史，不再先写入原始 tool_use 再只给退化块补 `tool_result`。
2. **F2（D3）**：`end_turn` / `stop` / `stop_sequence` **且 content 无 tool_use** 才收工；有（非空）tool_use 则 fall-through 执行。DeepSeek「空参数 + end_turn」不再被更早的 `end_turn → success` 吃掉。
3. 低占用下 F1 重试跳过 `reactiveCompact`（与主循环 P0-2 同口径，避免「已精简上下文」假话）。

## 放弃了什么（以及为什么不选）

- **只给退化块补 error tool_result、健康块照跑**：2026-08-04 主循环事故已经否决。F1 随后 `continue`，被保留的健康 tool_use 永不执行 → 必成孤儿 400。「先执行健康工具再重试」会留下半套结果，与「整轮作废重来」自相矛盾。
- **只修 D2、把 D3 留给下一 PR**：只修 D2 会留下更常见的口子——`end_turn` 残留 tool_use 根本走不到 F1。两条都在同一段判断，拆开会让中间态「成功返回但丢工具」继续活着。
- **子代理再发明一张 stop_reason 表 / 再抄一份空参数检测**：主循环漂一次子代理就会再漂（D1–D3 的共同根因）。本 PR 调用 `empty-param.ts` 的纯函数，不新写判据。
- **改 `agent/tool-executor.ts` 分区（D1）**：用户范围明确「不改执行器」。F2 fall-through 之后仍走现有 `executeTools`，顺序问题是下一 PR。
