# 配置文件里的隐私级别在 loadConfig 返回前注入

## 决定了什么

`loadConfig` 在合并完配置后，立即把 `analytics.privacy_level` 注入 `privacy-level.ts`（`setConfiguredPrivacyLevel`）。

起因：数据主权整改验收判据 4 / 6 用 v0.1.609 发布产物做 essential-traffic 真实启动时发现，
`settings.json` 写 `analytics.privacy_level: "essential-traffic"` 时更新检查被拦，**外部模型目录同步照样出网**
（日志 `[MODEL-CAP] 外部目录同步完成：7670 条 / 源 models-dev-opencode+models-dev-stencil+litellm+openrouter`）；
换成 `SID_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1` 则两者都被拦。

根因是时序：目录同步在 `app.ts` 构造期触发（约 843 行），只问 `shouldLoadRemoteConfig()`；而配置值此前只在
`initTraceCollector` / `initTelemetrySystem` / feature flag 初始化里注入，都晚于它。闸本身没问题，是闸读到的值还没写进去。

## 放弃了什么（以及为什么不选）

- **在 app.ts 目录同步调用点前补一次注入**：不选。这是逐个调用点打补丁，下一个更早的出网点会再漏一次；
  放在 `loadConfig` 是唯一能保证「拿到 config 的人一定看到正确隐私级别」的位置。
- **删掉 init 里原有的几处注入**：不删。它们覆盖了不经 `loadConfig` 的调用路径（测试与子命令直接构造 config），同值幂等，删了只增加风险。
- **顺手修插件市场不受 essential-traffic 控制**：不在本 PR。那是缺一道闸，不是注入时序，另开任务，避免一个 PR 混两种改动。

## 拿什么证明它生效了

- 新增 `packages/core/tests/config/privacy-level-early-inject.test.ts`：3 pass；把注入语句替换为空操作后 2 fail（变异自证）。
- `make build` 产物真实启动（隔离 `SID_CONFIG_DIR`，只用 settings 设 essential-traffic）：`debug.log` 里不再出现 `[MODEL-CAP] 外部目录同步完成`，
  `model-capabilities.json` 未生成，出网主机只剩配置的模型端点 `127.0.0.1:9`（网关定价，按设计保留）。修复前同一配置下发布产物 v0.1.609 会拉 4 个外部源。
- `bun test ./packages/core/tests/config/ ./packages/core/tests/analytics/ ./packages/core/tests/telemetry/ ./packages/cli/tests/app/`：1494 pass / 0 fail；oxfmt / oxlint 0 问题。
