# 期限型等待源终态即释放：正常结束的 monitor / wait_until 不再被误判为「承诺违背」

## 决定了什么

`wait-registry.ts` 里显式登记项（monitor / `wait_until` 后台 shell）的释放从「任务被驱逐之后」提前到
「任务进终态那一刻」，并给过期的兜底扫描加一道终态前置判断。四处改动，全部收在这一个文件：

1. **终态即释放（主路径）**：模块内订阅 `registry.onTaskChanged`，遍历显式登记项，`getTask(id)` 已终态就
   `releaseWait(id, "terminal")`。订阅放在模块级（与 TUI 刷新、`background-wake` 同一个事实源），
   不在 registry / shell / monitor 的 9 个任务写点各调一次。
2. **`listWaits` 的补释放条件**：原条件 `!getTask(id)`（任务**被驱逐之后**）改为
   `!task || isTerminalStatus(task.status)`。「终态但还没被驱逐」这一段空窗正是 sweep 误判的地方。
3. **`sweepExpiredWaits` 先判终态**：期限 + 宽限已过时，若任务本身已终态 → 按 `terminal` 释放，
   **不发通知、不记 `late`**；只有任务仍在 `running`（或已消失且无终态记录）才判违约。
4. **释放后补一次 `notifyTaskChanged()`**：`releaseWait` 自身不通知订阅方。第 1 条的回调在 `updateTask`
   的通知链里执行，`background-wake` 的那一次重判看到的登记项还没释放（`hasPromisedWait()` 仍为 true）；
   不补通知，无头等待循环要等下一次任务变更才重判，进程会多挂到那时。

为什么是「三层」而不是一处：主路径（1）挡住正常终态，查询路径（2）挡住「订阅没装上 / 登记发生在终态之后」，
兜底（3）挡住前两层都失效时的假 failed 通知。三层各自都有独立用例与独立变异证明（见第三段）。

## 放弃了什么（以及为什么不选）

- **只改 `listWaits` 的释放条件**（方案文档里最初的最小改法）：能消掉 `late` 事件，但
  `WaitReleased.held_ms` 记的是「下次有人问的时刻」而不是真实持有时长；且在没有查询的会话里
  （无头等待循环已退出）登记项会一直挂着。终态时刻释放才是准确的那一刀。
- **在 `monitor-task.ts` / `bash.ts` 的终态写点各调一次 `releaseWait`**：任务写点分散在 registry /
  shell / monitor 共 9 处，逐个接线必然漏一处（本次 D1/D8 的成因就是「测试直调内部函数、
  生产路径没接上」）。订阅 `onTaskChanged` 只有一个接入点，且与既有订阅方共用同一事实源。
- **把 sweep 整个删掉**：它是「子进程被外部 SIGKILL、调度器挂了」这类真违约的唯一兜底，
  删掉会让真违约静默。保留它，只在前面加终态判断。
- **在 sweep 里对「`getTask` 返回 undefined」也按 terminal 释放**：任务已消失时无法区分
  「正常终态后被驱逐」与「从未注册过的假登记」，放宽会让真违约漏判。正常路径下订阅已在终态时释放，
  走到「已消失」的概率极低；保守保留原判据（方案文档同口径）。
