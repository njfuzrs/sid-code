# 子代理内部字段 `_agentId` 改为「声明式按需注入」，不再无差别塞进每一次工具入参

## 决定了什么

把 `_agentId` / `_parentToolUseId` 的注入从**无条件**改成**声明式按需**：

- `tool/types.ts` 的 `ToolCapabilityFields` 新增 `consumesAgentId?: true`（类型刻意用 `true`
  而非 `boolean`：本字段只有「声明」一种含义，误写 `false` 应当编译报错）。
- 两个注入点改为读声明：`query/run-tool-use.ts`（进程内 + spawn 两条子代理路径共用）
  与 `agent/forked-agent.ts`。
- 三个真实消费者在自身定义处自报：`enter_plan_mode`、`sub_agent`、`save_memory`。
- `tool/bridge.ts` 的 `FORWARDED_KEYS` 同步加一项（编译期穷举，漏了 tsc 报错）。
- 新增 `tests/tool/consumes-agentid-audit.test.ts`：实例对账 + 源码扫描 + 注入点形态三条断言。

契约的完整论证写在 `types.ts` 该字段的注释里；本 Note 只记「为什么是这条路」。

**为什么必须改**：内部字段会从三条出口漏出去，全部实测确认（探针跑在 main `01f04da8`）：

1. `StructuredOutput.execute` 在工具内部拿 workflow 的 JSON Schema **再校验一遍**入参，
   严格 schema（`additionalProperties: false`）必定失败：
   `输出不符合要求的 schema…: /_agentId: 不允许的额外字段 _agentId`。
   子代理自己改不掉这个字段（由执行器注入），只能重试到 `maxRetries`，workflow 拿到 `null`。
2. 宽松 schema 下校验通过，脏字段被当结果捕获：`{"ok":true,"_agentId":"sub-agent"}` 直接进
   workflow 的返回值。轨迹 `20261104-135127-a08c163e` 等 4 个会话的 workflow 结果里都带着它。
3. MCP：`McpToolAdapter.execute` 把入参原样作为 `arguments` 发给 `client.callTool`，
   fake client 实测收到 `{"title":"x","_agentId":"sub-agent"}`。做严格入参校验的 server 会拒绝调用。

## 放弃了什么（以及为什么不选）

**乙（消费端剥离）：在 `StructuredOutput.execute` 与 `McpToolAdapter.execute` 开头调
`stripInternalFields`。** 改动最小，但它是黑名单思路——根因没动。下一个「按原始 input 做事」
的工具（透传给外部服务、写盘、做 schema 校验）照样踩同一个坑，而踩的时候没有任何检查会报。
本轮已经能列出至少两个这样的潜在消费者（未来的结构化工具、未来的 MCP 直通），
黑名单每加一个都要重新发现一次泄漏。否决。

**丙（改走 ALS，彻底从 input 里拿掉）：`enter_plan_mode` / `memory` 改读 AsyncLocalStorage。**
方向正确，但风险与改动面都最大：`memory` 还要区分 forked 与 sub-agent，而 ALS 目前只存了
depth；更要紧的是 **spawn 子进程这条路径的工具在父进程执行**，ALS 由谁设、有没有覆盖到，
需要一次完整的路径核查。`agent/tool.ts` 的注释特意保留 `_agentId` 作兜底，正是怕 ALS
有没覆盖到的路径——在这个前提下用 ALS 替换兜底，等于把「已知的一层防御」换成「未验证的
一层防御」。留作后续独立重构，届时单独评估。否决（本轮）。

**只修 `StructuredOutput`。** 那是乙的变体，见上。否决。

**改 `validateToolInput` 让严格 schema 容忍内部字段。** 这会把「内部字段特殊」写进通用
校验器，让 schema 的 `additionalProperties: false` 对所有调用方都失去一部分效力——
为了一个 harness 自己制造的问题去削弱用户 schema 的语义，代价方向错了。否决。

## 拿什么证明它生效了

**变异自证（两次，都实际跑过并恢复）**：

1. 把 `run-tool-use.ts` 的 `if (tool.consumesAgentId)` 改回 `if (true)`（恢复无差别注入）：
   `bun test packages/core/tests/{query/subagent-internal-fields-not-leaked,query/run-tool-use-contract,tool/consumes-agentid-audit}.test.ts`
   → **5 条断言变红**：严格 schema、宽松 schema、MCP args、未声明工具不注入、注入点形态；
   其余 32 条仍绿（说明变异精准命中，不是整片崩）。
2. 把 `enter_plan_mode` 的 `consumesAgentId = true` 改成 `false`：
   → **3 条断言变红**：执行器路径下「子代理不能进入 plan mode」、实例对账、源码无遗漏。

**测试结果**：

- 新增 `packages/core/tests/query/subagent-internal-fields-not-leaked.test.ts`（7 条）：
  严格/宽松 schema、MCP args、forked 路径（未声明不注入 / 声明者拿到 `forked-agent`）、
  以及三个消费者在执行器路径上仍拿得到字段（`enter_plan_mode` 仍被拒、
  `memory_write` 的 `write_via` 仍是 `subagent`、`sub_agent` 套娃仍被拦）。
- 新增 `packages/core/tests/tool/consumes-agentid-audit.test.ts`（8 条）：双向对账 +
  「注入必须被 `tool.consumesAgentId` 条件包裹」的源码断言（防有人改回无条件注入而工具侧
  声明还在，前两张网看不出来）。
- 既有测试按新契约同步修正 1 条：`run-tool-use-contract.test.ts` 原来断言
  「`echo` 工具收到注入的 `_agentId`」，现拆成「声明者收到受控值」+「未声明者一个都收不到」
  两条。这是**契约有意变更**，不是为凑绿改预期值。
- 相关 5 个文件合计 `69 pass / 0 fail`。

**端到端**：按落地方案 1.5 要求的 P-wf 探针（`agent({schema})` 且 `additionalProperties: false`
跑 3 次、StructuredOutput 错误数应为 0）**本轮未执行**——它要真实模型调用与 bench 探针环境，
属于维护者侧验证；本地已用同一失败形态的最小复现守住（修复前红、修复后绿）。
这条缺口必须写清，不能用「机理上讲得通」替代。
