# fork 前缀漏贴过期清理占位，并把六项「等数据」验收落成一条可复现命令

## 决定了什么

对《20261112-上下文占用虚高与窗口自学习》方案的落地情况做二次核查后，修掉两类遗留：

**1. F4 的 `staleClearState` 没有进 fork 前缀对齐机制（真缺陷）。**

`ContextManager.getForkPrefixMessages()`（D16，fork 共享主循环 prompt cache 的唯一通道）只贴三类粘滞占位：`maskedState` / `coldClearState` / `replacementState`。F4 新增的 `staleClearState` 是**同型粘滞状态**——提交后每轮由 `applyFrozenClearState` 重放，只在 `resetLocalCompactState` 清空——但没被加进去。

后果是确定性的：`commitStaleToolOutputClear` 的 `skipToolUse` 保证 stale 的 `tool_use_id` **必然不落在**其它三类里，所以只要过期清理提交过一次，此后任何 fork（记忆提取 / 会话笔记 / btw）拿到的都是**原文**，而主循环发的是占位，前缀在第一个过期占位处分叉。这不是边缘场景，而是「每个足够长的会话都会中」——正好把 D16 要治的缓存不命中又还了回去（该机制立项时的实测数据：DeepSeek 族 fork 首请求命中率 p50 仅 6%）。

修法两处（`manager.ts`）+ 两处注释（`manager.ts`、`fork-prefix.ts`）+ 一条回归测试。

**2. F7 的四个诊断值改成结构化字段。**

`headless.ts` 窗口不足时原本把「窗口 / 输入估算 / 窗口剩余 / 下限」拼进 `result.output` 文案，父进程要归因只能正则解析人类可读文本。现在 `ChildResultMessage` 增加可选 `diagnostics`（`ChildRequestBudgetDiagnostics`），`emitResult` 加第三参，`SubAgentResult` 以 `budgetDiagnostics` 透传，父进程同时落一条 warn 日志。

**3. 六项「等真实流量」的验收落成一条命令。**

新增 `scripts/verify-context-budget-acceptance.ts`：按**行为**分段（会话内 `max_tokens` 全部 ≤ 32,768 → 修复后；全无该字段 → 修复前，因为这个字段本身是 F1 才写进 `raw.jsonl` 的），从本机真实轨迹算 V1-2 / V2-2 / V2-3 / V4-1 / V4-3 / V4-4。没有真实超阈样本的 V2-3 用合成输入（700k + 1,048,576 窗口）做机制验证，并明确标注「只证明预算层不会拒绝，真实 400 取决于服务端」。

## 放弃了什么（以及为什么不选）

- **不把 `staleClearState` 加进 `hasReplacement` 的那条折叠分支**。`collapseOldPersistedReferences` 的触发条件是「有大输出占位要贴」，而过期占位是短文本、不会与持久化引用折叠产生交互。多一个触发条件只会让 fork 多做一次无意义的折叠。
- **不给 `getForkPrefixMessages` 改成「调 `getCleanedMessages` 再丢弃副作用」**。后者有写入（`sentIntact`、`lastSendSnapshot`、`pendingSendCauses`、清理状态），fork 一调就会改掉主循环下一轮的发送前缀与校准分母——这正是 D16 注释里已经否决过的方案。
- **不在本 PR 里重校准 F4 的 K=8 / N=20k**。验收发现过期清理在本机 95 个修复后会话里只命中 462 / 12,942 条工具结果（3.6%），V4-1 实测 34.69%（目标 ≤25%）未达标。但 K/N 是方案 §5.4 用 323 个会话离线回放校准出来的，改它属于产品调参、需要重跑回放，不能在修 review 遗留的 PR 里顺手改——那会让「这次改动到底修了什么」变得说不清。
- **不改 V4-3 / V4-4 的判据去凑绿**。V4-3 实测 14.49%（基线 9.8%）、V4-4 p95 252 vs 199，两项都没达标。它们分别反映「F4 占位里的『精准重读』指引可能诱导了更多重读」与「turns 受工具集扩张影响、跨版本不可比」，是需要人判断的产品信号；把阈值改成能过的数就是 RL-006 禁止的改断言凑绿。
- **不给验收脚本加 `--synthetic` 全量造数据模式**。只有 V2-3 这一类「机制型」判据适合合成输入；V4-1 / V4-3 / V4-4 是分布型指标，用造的会话算出来的占比没有意义，只会产出一个看起来像数据的数。

## 拿什么证明它生效了

- **变异自证（两处都做）**：把 `staleClearState` 分别从 `hasSticky` 与取值链移除，新用例各变红一次（`12 pass / 1 fail`），恢复后 `13 pass / 0 fail`。两处都被测到，不是只测到其中一处。
- **验收脚本自身的测试**：`bun test ./tests/scripts/verify-context-budget-acceptance.test.ts` → **16 pass / 0 fail**。其中两条钉住了第一版的两个真 bug：① `raw.jsonl` 的 response 行没有 `type` 字段，按 `type === "response"` 判会让 V1-2/V2-2/V2-3 全部「样本不足」；② 空输入时合成场景会给出 `pass: true`，把「没有数据」判成「通过」。
- **真实轨迹实测**（`bun run scripts/verify-context-budget-acceptance.ts --days 30`，1040 个会话 / 110 个修复后）：
  - V1-2 ✅ `stop_reason=length` 0 / 12,198 次请求，output p99 4,098、p99.9 7,642
  - V2-2 ✅ 每会话峰值占比中位数 17.25%、p90 26.42%（代理口径，非「同类任务」）
  - V2-3 ✅ 本机无超阈真实请求，合成 700k 输入下预算判定可发送；修复前报 context-limit 的会话 6 个
  - V4-1 ❌ 34.69%（原文 36.14%），目标 ≤25%
  - V4-3 ❌ 14.49%，基线 9.8%
  - V4-4 ❌ p95 252 vs 199（跨版本可比性最弱，只作参考）
- **门禁**：`bun run lint` 0 error、`bun run format:check` 通过、`bun run typecheck:gate` 无新增（62/62）、`make build` 自检通过、本次改动覆盖的 6 个测试文件 77 pass / 0 fail。
