# 内部工具的「不需要权限」改由工具自己声明，不再靠三张手写名单

## 决定了什么

`ToolCapabilityFields` 新增 `requiresPermission?(input): boolean`；工具在**自己的定义处**
声明「我不需要用户批准」，权限链在阶段一新增 **Step 13.6** 直接放行。首批声明 12 个
工具（`think` / `todo_write` / `task_create` / `task_update` / `task_get` / `task_list` /
`task_output` / `bg_task_get` / `bg_task_list` / `cron_list` / `enter_plan_mode`，
外加 J9 的 `sub_agent`），并从 `checker.ts` 删掉 `HEADLESS_LOCAL_LEDGER_TOOLS` 名单。

四处配套改动，缺一条这个机制就会静默失效：

1. **注册来源打标**（`tool/registry.ts`）：`requiresPermission` **只对内置工具生效**。
   registry 在 `register()` 那一刻给内置工具打一个 Symbol（`TOOL_REGISTRATION_SOURCE`），
   MCP / 插件 / 自定义代理工具的声明一律忽略——那是外部代码，不享受「我写的我担保」。
   判据刻意**不看 `mcp__` 前缀**：名字可以撞，来源只有注册那一刻知道。
2. **bridge 转发**（`tool/bridge.ts`）：`think` 是新接口工具，声明要经
   `FORWARDED_KEYS` 才留得下来。这一行漏了构建不报错、测试也不会红。
3. **deny-write 两处同步**：阶段一 Step 13 与阶段二 `enforceModeHardConstraint` 的
   `mode-gate` 总闸都放行「声明免权限 **且** `readOnly()` 为 true」的工具。
   只改 Step 13 会被阶段二静默改回 DENY（`step: "mode-gate"`）——**实现时实测踩到过**，
   症状是单元测试全绿而线上照旧弹确认。
4. **plan 模式放行位置**：`checkPlanMode` 里的免权限放行放在 `PLAN_MODE_EXTRA_TOOLS`
   **之后**。`sub_agent` 同时在两套判据里，严的那套（plan 下只许 explore）必须先生效。

`sub_agent` 用条件式声明：普通派活免权限，但 `isolation: "worktree"` 仍需确认——
它会真的 `git worktree add` 一个工作树。判据同时看显式参数与 agent 定义的默认值。

`ask_user_question` **本次刻意不声明**：它的语义是「我需要用户输入」，不是「我不需要
权限」。在 `dontAsk` 下放行它等于在「一切需确认的都拒」的模式里弹问卷（claude-code
明确拒绝）。正确的形状是 20261112 方案 M7 的 `requiresUserInteraction?()`，尚未合入，
工具文件里留了 TODO 指向它。

## 放弃了什么（以及为什么不选）

- **再加一张名单（方案 A）**：那正是本缺陷的成因——三张名单、三次事后补名字，
  `task_get` / `task_list` / `think` 从来没被列进去过。名单必然漂移：新增工具的人不会
  知道有这么一张表。选 B（工具自声明）后，声明与实现同处一个文件，review 时一眼可见。
- **用 `mcp__` 前缀判来源**：registry 内部本来就这么分容器，但自定义代理只要把工具
  取名 `mcp__x__y` 就能走进 MCP 分支；反过来一个真 MCP 工具去掉前缀就绕过限制。
  在注册那一刻打标是唯一知道真相的时刻，为此多了一个 `register()` 的 source 参数。
- **把免权限放行提到 Step 5（ask 规则）之前**：会让用户的显式 `ask` 规则失效，
  违背「规则优先」这条已有的契约。变异自证里专门有一条钉住它。
- **让 `ask_user_question` 也声明免权限**：见上，会把 `dontAsk` 的语义打穿。
  这个 PR 只做「不需要的少问」，不做「需要输入的不问」。
- **不传工具实例时按名字兜底放行**：`check()` 的 `tool` 参数是可选的。声明挂在实例上，
  拿不到实例就无法判断来源与声明，一律 **fail-closed**（退回需要权限）。生产链路
  （`query/tool-executor.ts` / `query/run-tool-use.ts` / `swarm/team.ts`）三处都传了
  实例，不受影响；**这个取舍的代价是「只传工具名」的旧测试需要改成传实例**——
  两条旧测试因此更新了前提（有意为之的契约变更，不是为凑绿改断言）。

## 拿什么证明它生效了

**新增测试** `packages/core/tests/permission/internal-tool-permission.test.ts`，32 例全绿：
变放行（交互 default / acceptEdits / 无头 / plan / deny-write）、必须不变
（`exit_plan_mode` / `task_stop` / `cron_create` 仍 ASK、deny-write 下会写账本的三个仍 DENY、
`dontAsk` 下 `ask_user_question` 仍 DENY）、规则优先、桥接来源忽略、`sub_agent` 的
worktree 例外，外加防漂移哨兵（源码声明集合 === 写死清单，双向对账）。

**旧行为探测**：把新测试原样放到修前的 `main`（`342d9dc4`）上跑，**13 pass / 19 fail**——
「变化」那一半全红（default/acceptEdits 首批、无头、plan、deny-write、`dontAsk` 下
`todo_write`、桥接 builtin 对照），「必须不变」那一半全绿。说明测试真的测到了修前行为，
不是恒绿。

**变异自证**（方案 §6.2 四条，每条都先确认变红再恢复）：

1. 去掉 `declaredNoPermission` 里的来源检查 → 「桥接工具声明免权限仍 ASK」变红。
2. 给 `exit_plan_mode` 也加一份 `requiresPermission() { return false }` →
   哨兵与「必须不变：exit_plan_mode 仍 ASK」同时变红。
3. 把 Step 13.6 挪到 Step 1 之前 → 「规则优先」两条 + deny-write 三条一起变红。
4. deny-write 两处都不看 `readOnly()` → `todo_write` / `task_create` / `task_update`
   在 deny-write 下变红（它们会写账本）。

**门禁**（全部在 worktree `feat+internal-tool-permission-declaration` 上跑）：

- `bun run typecheck:gate` → 62/62，✓ 无新增
- `bun run affected-tests:run` → **7138 pass / 1 fail**，唯一失败是
  `isolated-subagent-cwd.test.ts` 的「未绑定 cwd 时不出现隔离提示」：该测试在 **worktree**
  里跑时 `process.cwd()` 就是 worktree、被判为隔离环境，在父仓 `main` 上单跑通过
  （已实测），与本改动无关
- `make build` → 通过，产物自检全绿
- `bun run smoke` → **28/28**
- `bun run lint` / `format:check` / `lint:boundary` / `lint:command-system` /
  `lint:legacy-tool` → 五项全 PASS
- `bun run docs:gen-reference` → 参考页无漂移

**校验强度的边界（别把这当成「证明完毕」）**：`enforceModeHardConstraint` 的 `mode-gate`
那一处是**实现过程中被调试脚本抓出来的**，不是测试先发现的——第一版只改了 Step 13，
单元测试当时全绿，因为测试也没覆盖「阶段二覆盖阶段一」这条路径。补上之后才有现在这条
deny-write 用例。同类风险仍在：任何新增的「阶段二改写阶段一」的放行口，都需要单独核对
它是否也要跟着这条判据走。
