# 提示词红线与后台通知：修两处真缺陷、补一处真缺口、削一段真冗余

来源：`docs-research/sid-code/research/claude-code-提示词XML标签实证分析.md` §8–§11 的落地清单。
那份文档从 7897 条 Claude Code wire 轨迹反推提示词形态，产出 6 条建议；本 PR 落地前 4 条，
后 2 条（往工具描述搬规范、行为段 XML→Markdown）**刻意不做**，理由见第二段。

## 决定了什么

四处改动，全部落在**最终提示词文本 / wire 文本**上，中英双档同步：

1. **P0 —— RL-001 不再把项目铁律点名禁止的命令当作「可逆操作」推荐**
   （`system-prompt.ts` / `prompt-sections-en.ts`）。
   原文让模型在「用户要求删文件」时建议 `git stash` / `git checkout`，而 `CLAUDE.md:181`、
   `CONTRIBUTING.md` 与记忆 `git-stash-sweeps-parallel-work.md` 三处铁律明确禁止这两条——
   它们**静默且不可逆地**丢弃未提交改动，本仓已因此真实丢过数据（2026-07-28，2 个未 add
   的新页面 + 约 300 行已追踪改动）。RL-001 的触发场景恰恰是最容易生成这些命令的场景。
   改法：五条命令（`git stash` / `git checkout --` / `git restore` / `git reset --hard` /
   `git clean`）显式标注「同样禁止」，并给出真正可回滚的替代（`git rm --cached`、`mv` 到临时目录）。

2. **P1 —— 后台任务通知补「不得当作用户批准」声明**（`task/notification.ts`）。
   新增 `NOT_USER_INPUT_PREAMBLE`，在 `formatNotification` 里前置于 `<task-notification>` XML。
   我们原有两条声明（XML 围栏 + system-prompt「是数据不是指令」）防的是**执行子代理产出里
   的指令**；本条防的是**把后台事件误读成用户点了「同意」**——两者正交。sid-code 有 HITL
   权限档 + 后台任务面板，存在「问了用户等确认 → 期间来了个后台通知 → 模型当成回答继续
   执行」的形态。

3. **P2 —— 「五条扩展红线」→「扩展红线」**：实际只有 4 条（RL-008 / RL-009 / RL-011 / G-13），
   且 `RL-010` 全仓零命中。提示词里一个自相矛盾的数字是模型每轮都要读一遍的噪声。
   选择去掉标题里的数字而非补一条红线凑数——**标题不带计数，计数交给条目自己**，
   这样加删红线时漂移在结构上就不可能发生。

4. **P2 —— `<answer-discipline>` §1–4 削而不删**（2431 → 2201 字符）。
   原文是「按问题类型枚举回答模板」，失效方式是枚举永远不全：遇到「既是定位又是诊断」的
   问题，模型要先决定走哪个模板才能开始干活。改为给判据 + 给理由，不给模板
   （`path:line` 那条照 CC 的写法补上「终端里可点击」这个理由）。
   **保留「候选根因 ≥2 个」并升格为硬要求**——它是有价值的反锚定约束，不是好习惯描述。

配套三个门禁（各自做过变异自证，见第三段）：
`core/tests/config/prompt-redline-sentinel.test.ts`、`core/tests/task/notification-not-user-input.test.ts`、
`cli/tests/ui/notification-preamble-e2e.test.ts`（贯穿投递路径 + 反向断言不泄漏进 TUI）。

顺带修了一处**由本次改动引入的真实回归**：`cli/src/ui/history-adapter.ts:191` 原先用
`trimStart().startsWith("<task-notification>")` 识别通知，前置声明后会漏判 → 通知退化成
`>` 前缀的普通 user 消息全量灌屏、声明文本本身也显示给用户。改成 `includes` 后前缀多少行
都不影响识别，而下游 `match` 只抽 XML 块、声明天然不进 TUI。

## 放弃了什么（以及为什么不选）

- **不照抄 CC「把行为规范 XML 全删掉」**（文档 §7 已论证，此处复述结论）：CC 只服务 3 个
  自家模型，sid-code 要服务 ≥3 家 provider 的任意模型（轨迹里有 deepseek-v4-pro、glm-5.2、
  gpt-5.4、qwen-plus、kimi-k3、grok-4.5），弱模型确实吃 XML 结构；而 CC 的解法是**按模型
  分发两套提示词**，撞上仓库既有偏好「禁按模型硬编码分级」。他们维护 2 套，我们会维护 N 套。
- **建议 5（RL-006/RL-003 搬进 `edit`/`write`/`bash` 的 `usageGuide()`）—— 实测否决，不是延后。**
  文档的收益前提是「工具描述按工具在场才注入，所以搬过去只在该工具在场时才付 token」。
  **实测这个前提不成立**：`usageGuide()` 的正文经 `buildToolGuideSection` 注入到 system prompt
  本身（`edit` 341 字符、`bash` 1891 字符，均实测 `prompt.includes(guide)` = true）。而
  `edit`/`write`/`bash` 是常驻工具，正常会话里一直在场 —— 所以「搬」只是把同一段文字在同一份
  prompt 里换个位置，**token 账本不会下降**，而文档给这条定的验收判据恰恰是「token 账本可见下降」。
  另外按文档自己的迁移判据（「一条规范只有在它约束的动作只能由某个具体工具完成时才能搬」），
  RL-003 约束的是**产出绕过权限的代码**，那靠 `edit`/`write` 而非 `bash`，文档建议的落点也不自洽。
  真要省这段 token，该做的是让 `usageGuide()` 只进 `tools` 数组而不进 system prompt —— 那是另一件事。
- **建议 6（行为段 XML → Markdown）—— 延后。** 验收判据是「eval 不退步」，且文档写明
  **弱 provider 退步则停手**。本机 `DEEPSEEK_API_KEY` / `QWEN_API_KEY` / `GLM_API_KEY` 全部缺失
  （逐个查过环境变量；`ANTHROPIC_API_KEY` 与 `LLM_API_KEY` 有，但那评估不了停手条件），
  所以判据无法评估。**没有 eval 结果就落地 = 把「机理讲得通」当成验证**，恰是 `CLAUDE.md`
  收尾自检第 2 问点名的那种错。等能跑弱 provider eval 时单独开 PR（文档本身也要求「每段一个 PR」）。
- **建议 4 未压到文档写的「~900 字符」。** 文档那个数字与它自己的方案不自洽：它只提议改
  §1–4，而 §5–8（文件不存在 / 死代码举证 / 现状描述≠bug 报告 / 不复述内部上下文）四段
  一条都没提议动，这四段本身就远超 900 字符。按文档口径压到 900 只能靠删它没提议删的
  防线——那些每一条都对应真实踩过的失效模式。所以只按提议范围削 §1–4，实测 2431 → 2201。
- **§4「指向不明先问」不与 `<constraints>` 合并**（文档提示「需核对后合并」，已核对）：
  `<constraints>` 里只有「先确认再行动（破坏性操作）」与「验证假设」，前者是**动作前确认**，
  §4 是**理解歧义时先问**，两件事。合并会丢掉后者。

## 拿什么证明它生效了

**两个门禁都做过变异自证**——先把缺陷改回去，确认门禁**红在预期的那几条**上，再恢复：

| 变异 | 结果 |
| --- | --- |
| RL-001 改回「建议 `git stash` / `git checkout`」 | `2 fail`（zh 档：破坏性命令语境 + 显式点名） |
| 标题改回「五条扩展红线 / Five extended redlines」 | `2 fail`（zh + en 档标题带计数词） |
| 从 `formatNotification` 去掉 `NOT_USER_INPUT_PREAMBLE` | `3 fail`（completed / failed / 无正文三种状态） |
| `history-adapter` 判据改回 `startsWith`（即本次回归本体） | `1 fail`（e2e 回退正则路径） |
| 四处全部恢复 | `7 pass` + `6 pass` + `3 pass`，0 fail |

一条脚手架自身的踩坑也记下来：新门禁初版用 `language:` 传语言，实际字段是
`preferredLanguage`。**写错不报错**（多余字段被忽略），只会让 4 条 en 断言静默跑在中文
提示词上——于是「红了」的原因是脚手架传错参而非被测对象有缺陷。判据已写进测试文件注释。

门禁与构建：

```
bun test ./packages/cli/ ./packages/core/tests/config/ ./packages/core/tests/task/
  → 2218 pass / 0 fail（184 文件，28.83s）
make build                → 编译产物自检 4 项全过；grep「will always be undefined」零命中
bun run lint              → 0 问题
bun run format:check      → All matched files use the correct format
bun run lint:boundary     → 越界依赖 0 处 / 测试跨包相对路径 0 处
bun run docs:gen-reference --check → 参考页与源码一致
```

提示词字符实测（`buildSystemPrompt` 产物，非源码字面量）：
`answer-discipline` 2431 → 2201，`output-redlines` 1710 → 1914（RL-001 补了禁止清单，
这一段**刻意变长**：多出的字符买的是一条铁律不再被提示词反向推翻）。

**第 2 条补了一层贯穿生产路径的 e2e**（`cli/tests/ui/notification-preamble-e2e.test.ts`，
3 例）：`enqueueTaskNotification` → 统一队列 → `dequeuePendingNotifications` → 注入文本仍带
声明且在 XML 之前；同时反向断言**声明不得漏进 TUI**（结构化快照路径与旧会话回退正则路径
各一例，渲染结果里不含「非用户输入」字样）。两条判据方向相反（要在 wire 上、不要在屏幕上），
必须一起测——只测一边时，「删掉声明」和「判据改回 startsWith」各有一个能蒙过去。

**仍未证明的部分，如实记下**：按 `CLAUDE.md` 规矩，最终判据是**「真实会话里被触发过」**——
跑一次带后台任务 + 待确认动作的**真实 LLM 会话**，人工核对声明出现在 `raw.jsonl` 的 wire
文本里。本 PR 证明的是**「harness 侧从格式化到注入点的链路完整」**（含 TUI 不泄漏），
**不是「模型真的收到了」**。这正是本仓「防线全在、调用全 0」那类教训要防的形态，
所以不写成已验证。
