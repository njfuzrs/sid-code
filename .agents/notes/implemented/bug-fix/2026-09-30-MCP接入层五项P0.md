# MCP 接入层五项 P0：断线接线、策略闸、SSE 解析、熔断 half-open

## 决定了什么

- **D1** `client.ts`：`transport.onClose` 改为无条件赋值（旧守卫 `if (transport.onClose)` 恒假）。
  同时统一 close 语义：`onClose` 只表示「意外断开」——`MCPClient.close()` 置 `closedByUser`
  后忽略后续关闭事件；`StreamableHTTPTransport.close()` 不再回调 `onClose`（它是五个传输里唯一这么做的，
  接通 D1 后会把主动断开变成自动重连）。`handleDisconnect` 只在 `CONNECTED` 状态下处理断线，
  防止连接中途断开时并发起第二条重连链。
- **D2** `policy.ts`：`isMcpServerAllowed` 内部先按 `createTransport` 的同一规则展开
  command/args/url 的 `${VAR}` 再匹配（副本，不改原配置、不外传展开值）。
- **D5** `transport.ts`：`SSETransport.readSSEStream` 删掉私有解析，改调共用 `parseSSEStream`，
  保留 `endpoint` 握手分派。顺带消掉 D6（事件状态在循环内清零）——同一段代码。
- **D13** `manager.ts`：新增 `MCPManager.policy`，闸下移到 `connectAll` / `addServer` / `connect` /
  `authenticate` 四个入口；`cli.ts` 创建 manager 时注入 `config.mcpPolicy`。
  插件 MCP、`--mcp-config`（含 strict 模式）、IDE 动态注册、运行时重连、插件热重载全部经过它。
- **D23** `manager.ts`：每轮断线重置 `reconnectAttempts`；耗尽后进入 FAILED 同时启动 half-open 探测
  （默认 60s 周期），成功即回 CONNECTED 并清零；`disconnect` / `closeAll` 停止探测，退避等待期间
  被移除或关停则放弃重连。

## 放弃了什么（以及为什么不选）

- **只删 D1 那行守卫**：文档已点明会把「死的重连」换成「乱的重连」（主动断开触发重连），所以同时统一 close 语义。
- **在 `mergeMcpConfigs` 前展开整份配置（D2）**：会把展开后的 url/headers（可能含密钥）写进合并结果与日志，
  并改动签名去重（D3，P1）的行为。放在 policy 内部展开只影响过闸判断，范围最小。
- **保留 config 层过闸、再逐一补 cli/plugin/ide 调用点（D13）**：调用点会继续增加，每加一个就是一个新洞；
  manager 是唯一必经点。config 层原有过滤保留（纵深防御，不改既有行为）。
- **D23 无限次快速重连**：会放大抖动；half-open 用更长周期试探，符合熔断三态模型。
- D3/D6 以外的 P1/P2（D24 重连无超时、D25 断线摘工具等）按要求未动。
