# 增量游标只在 pair 落盘后推进，重试不再丢整轮 tool_result

## 决定了什么

改 `packages/core/src/trace/collector.ts` 的 `computeNewMessages`：**不再在调用时推进
`prevMessageCount`，改为在 `handleAfterModel` 的 `pairs.push(pair)` 之后按落盘 pair 的
`request.raw_messages.length` 推进**。

原来的行为：`computeNewMessages` 在 `handleBeforeModel`（请求**发出前**）被调用，一进来就把
`prevMessageCount` 推到本轮条数。于是失败重试时：

1. 第一次请求：游标推到 81；
2. 请求失败（超时 / 连接断），重试；
3. 第二次请求 messages 仍是 81 条 → `slice(81)` = `[]` → `new_messages` 空；
4. 而落盘的恰恰是第二次的 pair → **整轮 tool_result 不进轨迹**。

后果不是「少一条数据」：`digest` 看到 tool_use 没有对应结果，报出
`tool_use_without_result`（high）+「疑似中途崩溃 / 协议违规」，把排查引向一个不存在的
协议缺陷。这正是检测器精度治理里 T5 要分流的那一类，而这是它的根因。

## 放弃了什么（以及为什么不选）

- **不选「按内容指纹定位增量起点」**（我最初按方案文档的诊断实现的版本）。
  方案文档（`docs-research/.../20261102-X1H3-...md`）说根因是「压缩后条数只少一两条，
  新消息加回来总数又和上一轮相同，`length < prev` 不触发」。回源码核实这个诊断**已经过期**：
  `handlePreCompact` 早就把游标重置为 0，而自动压缩同样触发 PreCompact hook
  （`query/auto-compact.ts` 的 `firePreCompactEvent("auto")`），所以压缩路径本来就是对的。
  按内容找的版本对重试场景**同样切出空**（上一轮最后一条就是当前最后一条），修不到根因。
  已实现并验证过一版，核实后整段回退。
- **不在 `computeNewMessages` 里加「重试检测」**（比如比对 messages 是否与上次相同）。
  那要在热路径上保存上一轮全量 messages 做比对，记忆开销与判定歧义都比「把推进推迟一次」
  大得多；推迟推进天然覆盖重试，且不引入新状态。
- **不按「同 index」判定重试**。index 相同的第二次请求可能是正常重试，也可能是别的调用链
  复用编号；落盘时机的判定不依赖这个语义，更稳。

## 拿什么证明它生效了

- **原始数据核实**（决定了根因判定）：`~/.sid-code/trajectories/sessions/20261019-002707-0d3ddd0e`
  的 `raw.jsonl` 里 index=41 有三条记录 —— 前两条顶层键是
  `timestamp,index,type,model,msg_count,estimated_input_tokens`（请求侧记录），
  第三条才是完整 pair（`timestamp,index,model,request,response,usage,...`）且
  `new_messages: 0`、`_messages_count: 81`。与「第一次推进游标、第二次落盘空增量」一致。
- **新增 3 条单测**（`packages/core/tests/trace/collector-increment-on-commit.test.ts`）：
  重试两次相同 messages 都拿到完整增量；正常一轮落盘后下一轮只取新增；落盘轮增量与
  游标一致。
- **变异自证**：注释掉落盘处的推进 → 「正常一轮落盘后，下一轮只取新增的部分」
  与「落盘的那一轮用完整 messages」两条变红；恢复后全绿。
- `bun test ./packages/core/tests/trace/collector.test.ts`：111 pass（既有增量语义未被破坏）。
- `bun run affected-tests:run`：1107 pass / 0 fail（trace 全域 78 个文件）。
- `make build` 产物自检通过；`lint` / `format:check` / `typecheck:gate`（62 处，基线 64，无新增）通过。

**这条改动只对新会话生效**：历史轨迹里已经落盘成 `new_messages: 0` 的那几轮不会回溯修复，
所以它不能用历史数据验收。要等新会话里出现「同 index 两次请求 + 重试成功」的形态时，
看落盘那一轮的 `new_messages` 是否非空。
