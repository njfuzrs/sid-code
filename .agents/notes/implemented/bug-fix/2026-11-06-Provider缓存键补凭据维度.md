# Provider 缓存键补上凭据维度：同 baseURL 多账户不再串用

## 决定了什么

`ProviderRegistry.getProviderFor` 的缓存键从 `providerName:baseURL` 改为
`providerName:baseURL:credentialFingerprint(apiKey)`（`packages/core/src/llm/registry.ts`）。
指纹直接复用 `quota-scope.ts` 的 `credentialFingerprint`（sha256 前 16 位十六进制，不可逆），
缓存身份与额度账户身份同源。`registry.ts` 里原本写着「key = providerName:baseURL」的
类字段注释同步改成解释「为什么凭据维度不可省」，否则下一个人照旧注释会把这条维度再删一次。

配套测试：

- `packages/core/tests/llm/registry.test.ts` 新增 T1–T4：不同 apiKey 分实例且各自
  `quotaScope().credential` 对得上、同 key 仍复用、空凭据（ollama）行为不变、
  缓存键不得含明文（用探针值 `sk-PROBE-LEAK-CANARY` 扫 `cache.keys()`）。
- 新文件 `packages/core/tests/llm/provider-cache-credential.test.ts`：复刻生产路径
  （主 provider 先建、降级 provider 按 `availableModels` 条目后取，与 `app.ts:1437-1446` 一致），
  用真实 OpenAIProvider 发请求，断言降级请求头里的 `Authorization` 是降级条目自己的 key。

## 放弃了什么（以及为什么不选）

- **不选「干脆不缓存 Provider」**：provider 实例承载 keep-alive 连接复用与
  `quotaScope` 账户级额度状态，每次新建会让同一账户的并行子代理各自重探额度，
  正是 F2 ⑥ 修掉的那个浪费形态。缓存要保留，只补维度。
- **不选「在降级路径上重新取实例 / 依赖 `clearCache()`」**：`clearCache()` 只清 registry
  的 Map，`ModelFallback` 在 App 构造期就已持有 provider 实例引用（`app.ts:1468-1471`），
  清表触达不到它。这是消费端打补丁，治不了「取实例那一刻就已经串了」。
- **不选「把明文 apiKey 拼进缓存键」**：`getProviderFor` 的 `log.debug` 会打印 cacheKey，
  明文键等于把凭据写进日志。T4 就是为此加的防回归。
- **不选「同时把端点也过 `normalizeBaseURL`」**：虽然 `quotaScope` 是这么做的，
  但那会顺带改变「末尾斜杠 / host 大小写」下的实例合并行为，超出本次缺陷范围。
  本次只补缺失的凭据维度，把端点归一留作独立改动，避免一个 PR 混两种行为变化。
- **不选「只改调用方（让每个调用点自己记实例）」**：调用点分散在 `app.ts`、`sub-agent.ts`、
  `cli.ts` 多处，每个都得记「同端点不同 key」这件事；漏一个就复发。缓存键是所有调用点
  唯一的交汇处，改这里才是一次性修根因。

## 拿什么证明它生效了

**修复前（未改源码）**：新增测试 T1 与行为测试都红，且失败形态对得上缺陷 —— T1 报
「期望 not.toBe 但拿到同一实例」，行为测试报「降级请求里 `Bearer sk-account-B` 出现 0 次」。
T2/T3/T4 保持绿，与方案文档预测一致。

**变异自证**（改坏 → 看红 → 恢复）：

| 变异 | 实测结果 |
| --- | --- |
| cacheKey 去掉 `credentialFingerprint(apiKey)` | T1 + 行为测试红，T2/T3/T4 绿（2 fail / 33 pass） |
| 指纹换成明文 `apiKey` | 只有 T4 红（1 fail / 34 pass） |

恢复后两文件 35 pass / 0 fail。

**回归**：

- `bun test ./packages/core/tests/llm/` → 2214 pass / 0 fail（127 个文件）。
  首次跑有 2 条与本改动无关的失败（`capability-wiring-regression` 与
  `model-capabilities-persist-guard`），举证后按仓库约定处置：worktree 的 `node_modules`
  是指向主仓的软链，`realpath node_modules/@sid-code/cli` 指向主仓 checkout，导致测试与
  被测模块跨仓解析；`rm node_modules && bun install` 后 60 pass / 0 fail，全目录复跑全绿。
- `bun run affected-tests:run` → 2210 pass / 0 fail（4 filtered out）。
- `make build` → 编译成功，产物自检 5 项全绿。

**端到端（同 baseURL、双凭据，本地桩网关复刻 A8 现场）**：

隔离配置 `SID_CONFIG_DIR=/tmp/a8-fix-sidhome`：`primary-model` 与 `fallback-model`
同 `provider: openai`、同 `base_url`（本地桩），`api_key` 分别为 A、B；桩对 A 返 401、
对 B 返正常 SSE。

`./sid-code -p "只回复 hello 两个字，不要调用任何工具" --output-format json` 实测：

- 网关请求记录：`Bearer sk-account-A` × 3（主模型 401 重试）→ `Bearer sk-account-B` × 3（降级成功）。
- 输出 JSON 的 `model` 为 `fallback-model`。
- `events.jsonl`：`ModelSwitch.trigger = fallback`，`SessionEnd.exit_status = end_turn`。
- `audit.log`：只有 3 条 `OpenAI HTTP 401 model=primary-model`，降级后无 401。

判定标准「降级请求必须携带降级目标的凭据；缓存键不得出现明文凭据」两条均由上述证据覆盖。
