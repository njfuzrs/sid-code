# goal 闸门认等待态：有显式等待源时放行 end_turn，不再打回模型空转

## 决定了什么

`handleGoalGate` 在「前 N 轮跳过评估」之后、调评估器**之前**新增一道判据：
模型已挂上**显式外部等待**（monitor / `bash --wait_until_seconds` / `schedule_wakeup`）
或**有待投递通知**时，直接放行 end_turn。

- 新增 `packages/core/src/query/goal-waiting.ts`：`collectGoalWaitingFacts` 用窄口径
  `isDeclaredExternalWait` 过滤等待源；`decideWaitSuspend` 做放行判定 + 连续放行记账。
- `GoalGateResult` 增加 `waiting` / `waitIds`。语义是「本轮结束，等事件唤醒下一轮」：
  `shouldContinue=false` 但 **goal 仍是 active**，不写终态。
- `loop.ts` 在 end_turn 处多一个 `result.waiting` 分支：只 `updateGoalState` 落盘计数，
  然后落入正常收尾（不 continue、不另起定时器，唤醒走既有通知续跑通道）。
- `GoalState` 增加 `waitPass: { key, count }`：键是排序后的等待 id 集合（只有待投递通知时
  用 `"notification"` 占位）。同一组等待源连续放行到 3 次后不再放行、回到评估器；
  换组或等待源全部释放则从 0 起算。放 `GoalState` 而不是 `LoopState` 是刻意的——
  后者是消息内口径、每条用户消息重建，放那里等于用户说一句话就把上限清零。
- `GoalGateDecision` 新增 `reason: "waiting"`，附 `wait_ids` / `wait_pass_count`。

## 放弃了什么（以及为什么不选）

- **不用 `hasPromisedWait` 的宽口径**：派生出来的子代理 / workflow / 普通后台 shell
  承诺的是「**自己**结束时会回报」，不是「被查询的外部对象变化时会回报」。用宽口径判，
  一次无关的 `bun test &` 就能让 goal 再也不评估（D12 的同一条教训）。单测直接锁住了这条
  （只挂普通 shell 时 `hasDeclaredExternalWait === false`）。
- **不做成 GoalConfig 开关**（不设 `enableWaitSuspend`）：连续放行上限是防旁路的下限，
  不是业务偏好；加开关只会让「关掉它」成为修另一个问题的默认手段。
- **不在 goal-gate 里直接 import task registry**：`GoalGateContext` 的既有契约是
  「事实由调用方现算、判定保持纯」。注入 `waiting` 让单测能构造三种组合，
  也让极简路径（不注入）行为与改动前逐字节一致。
- **不加 `waiting` 的 TUI 状态栏状态**：goal.status 仍是 active，等待是一轮级的瞬时态，
  加一个持久状态位会让 `/goal status` 与 resume 多出一堆边界（挂起中重启算什么状态？）。
  用户可见性由 system message（`⏸ 目标等待中 (n/3)`）+ trace 事件承担。
- **不在本 PR 做提示词改造（G5）与 P1 轮询守卫（G3/PR-B）**：它们是同一份方案里的独立
  编号项。G2 单独合入后「end_turn 不再被打回」这条机制已经生效；提示词仍写着
  「系统不会让你停止」，会让模型在挂等待前多调几轮工具——那是 G5 的范围，本 PR 不动。
- **不新造 S-goal-wait 回放冒烟用例**：用例的 `expect` 必须从人工核过的真实轨迹抄，
  当前没有这条轨迹。G2 的判据是开关型的（评估器调用次数 0/1、goal 是否 active），
  单测就能判死，按仓库的防线分层它属于 G1。
