# MCP 并发安全改为三个 hint 的 AND，外部来源不享受只读声明固化为契约测试

## 决定了什么

`packages/core/src/mcp/manager.ts` 的 `MCPTool.isConcurrencySafe()` 此前只看一个 hint：

```ts
return this.def.annotations?.readOnlyHint ?? false;
```

并发安全的语义是「可以与其他工具同时执行、不会互相干扰」，只读只是其中一条。协议允许
`readOnlyHint` 与 `destructiveHint` 互相矛盾（甚至同一条 MCP 服务两个都填 true），
也允许不填 `idempotentHint`。改成复用现成方法的三条件 AND：

```ts
return this.readOnly() && !this.isDestructive() && this.isIdempotent();
```

三个 hint 缺失时的取值由 `readOnly()` / `isDestructive()` / `isIdempotent()` 各自决定
（保守方向），本方法不重复读 annotations。这同时保证「并发安全 ⇒ 非破坏性」——
`run-tool-use.ts` 的 fail-closed 分级依赖这条不变式。

第二件事：**外部来源不享受只读声明**。这条此前只活在注释与两个函数的调用关系里——
`checker.ts` 的 `toolReportsReadOnly` 刻意不看来源，来源隔离由 Step 13 的
`declaredNoPermission` 承担（`toolReportsReadOnly && declaredNoPermission`）。
本次把它显式化：

- `toolReportsReadOnly` 的 doc 写明「刻意不看来源，隔离在 `declaredNoPermission`」，
  以及为什么不在这里再叠一道来源检查（会制造两份判据，两份判据必然漂移）。
- Step 13 加注释：删掉 `declaredNoPermission` 或改成 OR 等于放开所有 MCP 工具免确认，
  plan 模式会被打穿。
- 阶段二 deny-write 总闸（`exemptInDenyWrite`）同样承载隔离，加一句同款注释。
- 新增 `packages/core/tests/permission/mcp-readonly-source-contract.test.ts` 把契约
  固化成断言：同一个撒谎的 MCP 工具（`readOnlyHint: true` + 自报
  `requiresPermission() => false`）按 `register(tool, "mcp")` 注册时在 deny-write 下
  DENY（`step: "13"`），按内置工具注册时 ALLOW。

## 放弃了什么（以及为什么不选）

- **在 `toolReportsReadOnly` 里加 `getToolRegistrationSource(tool) !== "builtin"` 检查**：
  这是缺陷文档的首选修法，但 grep 全部调用点（只有 Step 13 与阶段二总闸两处）后发现，
  两处都已用 `declaredNoPermission` 做了来源隔离。再加一道等于同一语义有两处判据，
  一处改动另一处不跟就会「一边拦一边放」——正是本批缺陷反复出现的根因形态。
  改为「注释显式化 + 契约测试锁住」。
- **MCP 工具一律 `isConcurrencySafe() === false`**：能彻底消除采信外部 hint 的风险，
  但会把所有 MCP 只读工具踢出并行批次，串行化的代价落在每一次多工具调用上。
  三条件 AND 已经覆盖真实风险（只读但非幂等 / 只读但声明破坏性），过度收紧不划算。
- **在 `MCPTool` 里缓存三个 hint 的布尔值**：`readOnly()` 等方法已经是一次属性读取，
  缓存只增加「缓存与 def 不同步」的新失败模式，没有收益。
- **只在 `manager.ts` 加注释、不写契约测试**：这个不变式跨两个包的 3 处调用关系，
  只写注释的话，下一个人删掉 `declaredNoPermission` 时没有任何东西会红。

变异自证：

```text
去掉 isIdempotent() 条件（return this.readOnly() && !this.isDestructive()）
  → 2 fail：「只读 + 非破坏 + 明确不幂等」「只读 + 非破坏 + 未声明幂等」
  → 恢复后 11 pass

去掉 Step 13 的 declaredNoPermission 条件
  → 1 fail：Expected "13" / Received "mode-gate"
     （「MCP 来源：readOnlyHint + 自报免权限，deny-write 下仍被拒」变红）
再把阶段二 exemptInDenyWrite 改成只要求 toolReportsReadOnly
  → 2 fail（两条 DENY 断言都变红）
两处恢复后 16 pass / 0 fail
```

`concurrency-safe-hints.test.ts` 覆盖 8 种 hint 组合（含全缺省与空 annotations），
期望值来自人工语义而非实现反推：只有 `readOnly=true && destructive≠true && idempotent=true`
才是 `true`。
