# 安装脚本首装时不再覆盖用户已有的 sc 别名

## 决定了什么

`scripts/install-template.sh` 的两个「写 sc」位置在写入前都先检查目标 rc 文件里是否已有
`alias sc=`：首装（还没有 sid-code 标记块）分支、以及 macOS + bash 的 `.bashrc` 同步分支。
已有时只写 PATH 部分、不写 `alias sc='sid-code --dangerously-skip-permissions'`，
并打印「检测到已有 sc 别名，保留不变」。

背景：块是**追加到文件末尾**的，zsh / bash 对同名 alias 都是后定义生效。修复前只有
「已有 sid-code 块」的重复安装分支做了检查，首装分支不检查 —— 用户在装 sid-code 前
已有的 `sc` 别名（如截图工具）会被块尾定义静默盖掉。官网安装页承诺
「你已经有同名 sc 别名的话它尊重你的，不覆盖」，脚本注释的安全原则 5 也这么声明，
实现只兑现了一半。

同 PR 顺带修正官网安装页两处与事实不符的表述（核验时发现）：

- 「比如 0.1.606 → 0.1.609」跳号例子与发布记录冲突（0.1.607 起的促升记录逐级连续、
  仓库 changelog 数据里没有任何 beta 实例），改写为不含具体号码的机制描述；
- 「在版本目录旁写一个通道标记」改为「在版本目录里」（实际是 `versions/<ver>/.channel`）。

## 放弃了什么（以及为什么不选）

- **改文档、承认覆盖行为**：把安装页的承诺改弱，改动更小。否决 —— 安全原则 5
  本来就是「尊重」，实现向声明对齐才是对的方向；且「装个工具被抢走 sc 别名」对用户是净损失。
- **首装时检测到已有 sc 就完全不写块**：不行。块还承担 PATH 写入，不写会让 `sid-code`
  命令本身都找不到（就是「失败一：command not found」那一类问题）。正确做法是
  「块照写、只省略 sc 行」。
- **把检查范围收窄到「块内有没有 sc」**：那正是原 bug 的形态（用户自己的 sc 不写在块里）。
  判据必须是「目标文件里是否已存在任何 `alias sc=`」。

## 拿什么证明它生效了

1. `bash -n scripts/install-template.sh` → 通过。
2. file:// 假发布目录 + HOME 重定向到 tmpdir 实跑 5 个场景：
   - `.zshrc` 预置 `alias sc='echo mine'` → 安装后用户行原样保留、sid-code 的 sc 0 处，
     `zsh -c 'source .zshrc; alias sc'` 仍输出 `sc='echo mine'`；
   - 无 sc 对照组 → 照常写入 `alias sc='sid-code --dangerously-skip-permissions'`；
   - 重复安装 → 块 1 个、sc 1 行（幂等）；
   - macOS + bash：`.bashrc` 预置用户 sc → `.bashrc` 里 sid-code 的 sc 0 处，仅同步 PATH；
   - 用户（有 sc）二次安装 → 仍不补充 sid-code 的 sc（0 处）。
3. `bun test ./tests/update-auto-e2e.test.ts` → 11 pass / 0 fail（含新增 4 条用例）。
4. 门禁（worktree 内全部跑绿）：
   - `bun run affected-tests:run` → 1595 pass / 1 skip / 0 fail（78 个文件）；
   - 全量 `bun test` → 16518 pass / 10 skip / 0 fail（1135 个文件）；
   - `make build` → 编译 + 产物自检 5 项全过；`lint` / `format:check` /
     `lint:boundary` / `typecheck:gate`（66/66 基线，无新增）全绿。
