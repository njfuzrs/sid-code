# 记忆系统 sc-07 缺陷 6/7/8/11/12/13/14 收口（P2 批）

## 决定了什么

接 PR #206（P0/P1：缺陷 1–5、9、10），把同一份缺陷文档剩余 7 条 P2 一次修完：

- **缺陷 6**：`generateSessionMemoryAttachment` 标 `stable`（走 `stableAttachment`），会话笔记进静态区；
  OpenAI 族下不再每轮被搬成 messages 末尾的 user 消息。
- **缺陷 7**：fork 工具定义**保持全量**，但把理由写死在 `buildToolDefinitions` 注释里（tools 段是
  Anthropic 缓存前缀的第一段，裁剪会让整段历史全价重付），并加守卫测试；提取 / dream 提示词新增
  「不要验证」段（禁 grep 源码、禁 git、禁为核实读代码）。
- **缺陷 8**：裁决规则不变，但冲突副本不再隐身——`rebuildTeamIndex` 追加「⚠️ 未裁决的团队记忆冲突」段
  （不作为记忆条目、封顶 20 行），`TeamMemorySyncResult.conflictFiles` 点名副本，同步收尾汇总告警。
- **缺陷 11**：会话笔记更新提示词加第 9 条反自指约束（指令不是对话的一部分，不得写进笔记）。
- **缺陷 12**：主提示词「不应保存」加「即使用户明确要求」、快照清单、修复配方；新增「写法要求」
  （绝对日期、Why/How to apply）与独立的「依据记忆给建议之前」段；提取提示词同步。
  `save_memory` 增加**软提示**：相对日期、feedback/project 缺 Why 时保存成功但回提示。
- **缺陷 13**：`hasMemoryWritesSince` / `extractWrittenPaths` 改用 `isAutoMemPath`（带分隔符），
  与权限层同一判据。
- **缺陷 14**：`findCompressSplitPoint` 加双下限（保留段 ≥5 条含文本消息且 ≥min(20K 字符, 比例保留量)），
  往前补的**增量**不超过总量 20%；`emergencyTruncate` 传 `minFloors:false` 保持旧行为。

## 放弃了什么（以及为什么不选）

- **缺陷 7 按白名单裁剪 fork 的 tools**：省几 KB schema，换来每次 fork 丢掉主会话 tools→system→messages
  整段缓存前缀（数万 token 全价）。否决。已知未对齐：主循环开 tool search 时发 `activeDefinitions()`，
  fork 仍发全量，此时不共享 tools 段缓存；对齐要透传主循环实际定义，本次未做。
- **缺陷 8 换一种自动裁决（内容长度 / 第二判据）**：没有可靠第二判据，换规则只是换一种静默。
  选择「可见 + 交人处理」。
- **缺陷 12 硬拒绝**：相对日期、缺 Why 靠关键词，误判率不低（引用原话、user/reference 本不需要 Why），
  硬拒绝会让合法保存失败且模型无从绕过。只做软提示，主防线仍是提示词。
- **缺陷 14 上限按保留段总量算**：巨型工具结果本身就可能占保留段 90%，按总量封顶会让补齐一步都走不动，
  恰好在最需要补的场景失效；改按增量封顶。字符下限取 min(20K, 比例保留量)，否则短历史会被一路补到上限、
  改变旧行为（实测两条既有用例因此红过）。
- **emergencyTruncate 也套双下限**：上下文已溢出时多保留可能直接塞不下，保持只按比例。
