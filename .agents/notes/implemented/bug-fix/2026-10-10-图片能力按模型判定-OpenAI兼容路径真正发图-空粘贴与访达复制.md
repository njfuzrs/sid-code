# 图片能力按模型判定：OpenAI 兼容路径真正发图，修复空粘贴丢失与访达复制只剩文件名

## 决定了什么

会话 `20261009-135641-0083c051`（模型 `origin-deepseek-v4-1-flash`）里有两个症状，根因是三处独立缺陷。

**症状 1：模型说「当前 provider 不支持图片回传」。** 根因不在模型，V4.1-Flash 官方支持图片（deepseek-api.md:1831）。
- `OpenAIProvider.capabilities().vision` 写死成 `false`。
- `openai-tool-result-content.ts` 见到 `mediaBlocks` 一律降级成文字说明，完全不看模型能力。
- `warn.log` 里三次读图全部是「已降级为文本说明」。

**症状 2：粘贴图片后输入框只剩一个裸文件名。**
- 缺陷 2：`KeypressContext.bufferPaste` 只在 `buffer.length > 0` 时下发 paste 事件。终端对「剪贴板里只有图片」的信号正是一对空的 bracketed paste，于是 InputArea 的「空 paste → 读剪贴板图片」分支永远走不到，截图粘贴整条链路是死的。
- 缺陷 3：在访达里 Cmd+C 复制文件，剪贴板里是文件引用（`«class furl»`），不是像素数据。终端只把文件名粘进来：内容非空，不走读图分支；裸文件名又不是存在的路径，拖放判定也不认。最后按普通文本插入。

**修法：**
1. **图片能力按模型三态判定**，判定逻辑统一放在新文件 `llm/vision-capability.ts` 的 `resolveVisionSupport`。
   - 三层优先级：`compat.supportsVision`（用户按渠道别名声明）> 注册表 `supportsVision`（按真名匹配）> `undefined`。
   - 缺省值按协议族不同：OpenAI 兼容路径缺省不发图（发给不认图的模型会 400）；Anthropic 路径缺省发图（Claude 全系支持，这是既有行为），只有显式 `false` 才降级。
2. **OpenAI 兼容路径的发图形态**：图片以 `image_url` data URL 放进一条 **user 消息**，排在本轮全部 `role:"tool"` 之后。
   - 为什么不放进 tool message：OpenAI 规范规定 tool message 只允许 text part。
   - 为什么必须排在后面：插到 tool message 中间会打断 tool_calls 与 tool 的配对，直接 400。
   - Responses API 同形态（`input_image`）。
   - PDF 在这条路径没有各家通用的形态，照旧降级。
   - 无图时消息字节级不变，不影响 prompt cache 前缀。
3. `KeypressContext` 改为空 paste 也下发。超时（不完整序列）且没有内容时仍不下发。
4. `clipboard-image.ts` 新增 `resolveCopiedImageFile`。
   - 粘贴文本是裸图片文件名时，用 JXA 读剪贴板里的文件 URL，按**同名**找回真实路径。
   - 剪贴板里没有同名文件就返回 null，普通文本不会被误判。
5. 注册表新增 `supportsVision` 字段，并按 api-reference 文档更新各家模型数据。新增 `deepseek-v4-1-flash` 键；`ROUTE_PREFIXES` 补上 `origin-` 等前缀，对齐 `model-name-normalize.ts` 的 `ROUTE_PREFIX_RE`。在此之前，`origin-` 前缀的网关模型在注册表侧查不到任何条目。

## 放弃了什么（以及为什么不选）

- **按 DeepSeek 扩展把图片直接塞进 tool message**（deepseek-api.md:1852 允许）：这条线服务所有 OpenAI 兼容端点。user 消息里的 `image_url` 是各家共同支持的形态，tool message 带图只是 DeepSeek 的私有扩展，放在通用路径里换一家就是 400。
- **在 `ContentBlock` 里加 image 变体**，让图片作为独立块贯穿主循环：改动面覆盖压缩、持久化、UI 重放、token 估算，远超本次缺陷。现有 `ToolResultBlock.mediaBlocks` 已经能完整承载 Read 读到的图片，缺的只是序列化这一层。
- **把 provider 级 `vision` 改成 true**：能力本来就是按模型的，改成 true 等于对 `deepseek-v4-pro` 这类纯文本模型虚标能力。这个字段保持 false，注释写明它不参与发图决策。
- **未知模型缺省发图，让 400 自愈兜底**：自愈只覆盖 `reasoning_effort` 这一个字段，图片 400 后没有剥离重试的通道。用户会看到整轮失败，比「看不到图」更糟。
- **AppleScript `the clipboard as «class furl»`**：只能取第一个文件，多选复制时会把粘贴的文件名和第一个文件错配。

## 拿什么证明它生效了

- 单测 `bun test packages/core/tests/llm/vision-capability.test.ts`，锁住以下行为：
  - `origin-deepseek-v4-1-flash` 判定为支持图片，`deepseek-v4-pro` 判定为不支持，未知模型返回 undefined。
  - compat 的 true/false 能双向覆盖注册表，snake_case 写法也生效。
  - OpenAI 路径的消息顺序是 `assistant → tool → user(image_url)`，tool message 的 content 仍是 string。
  - 不支持图片或未知模型时，请求里不出现 `image_url`；PDF 照旧降级。
  - 无图时消息字节级不变。
  - Responses API 会在 function_call_output 后追加 `input_image`。
  - Anthropic 路径：Claude 照旧发 image 块，`deepseek-v4-pro` 降级为文字。
- `bun test packages/cli/tests/ui/keypress-empty-paste.test.tsx`：经真实 `KeypressProvider` 解析链，空的 `\x1b[200~\x1b[201~` 下发了一个 sequence 为空串的 paste 事件。做过变异自证：把条件改回 `buffer.length > 0`，结果 `1 pass 1 fail`；恢复后 `2 pass`。
- `bun test packages/cli/tests/ui/clipboard-image.test.ts`（14 pass）：同名匹配、多文件按名取、无同名返回 null、不读剪贴板的快速拒绝路径。
- 真机验证（macOS，需在沙箱外运行 osascript）：`osascript -e 'set the clipboard to (POSIX file ".../27259502_133938618036_2.jpg")'` 之后：
  - `readClipboardFilePaths()` 返回 `["/Users/.../Desktop/27259502_133938618036_2.jpg"]`
  - `resolveCopiedImageFile("27259502_133938618036_2.jpg")` 返回该路径
  - `resolveCopiedImageFile("other.jpg")` 返回 `null`
- 第一版 JXA 脚本在 TS 模板字符串里写了 `"\n"`，被转成真实换行，导致 JXA 语法错误，整段静默返回空。这个问题是靠上面的真机验证发现的，单测（注入 readPaths）测不到。
- **没有验证**：没有向网关路由 `origin-deepseek-v4-1-flash` 发过带图的真实请求。文档只能证明官方直连支持图片，网关是否透传 `image_url` 需要用户在真实环境里确认。确认不透传时，用 `compat.supportsVision: false` 关掉。
