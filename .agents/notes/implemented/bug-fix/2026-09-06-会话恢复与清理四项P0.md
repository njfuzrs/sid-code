# 会话恢复与清理的四项 P0：恢复丢 78% 历史、摘要断线、清理竞争、损坏文件无保护删除

来源：`docs-research/sid-code/bugfixes/todo/20260906-会话持久化与检查点-十二项缺陷交叉核查.md`
（十二项缺陷中的 D1–D4，即全部 P0；D5–D12 不在本次范围）。
触发用户反馈：「恢复对话后 TUI 界面显示不全，或经常发生其他错误」。

## 决定了什么

**四项 P0 合并一个 PR** —— 它们不是四个独立 bug，是两对互为因果的缺陷：
D1 之所以生效是因为 D2（摘要路径恒不可达，长会话必然掉进最差分支），
D4 的危害之所以被放大是因为 D3（并发读到半行 → 判成损坏 → 无条件删除一个健康会话）。
分开修会让每个 PR 都留着另一半的因，说不清是否真的修好。

**D1 —— 恢复的截断口径从「条数」改成「上下文预算」。**
旧实现三条路按条数分（≤20 全量 / 有摘要留 10 / 无摘要留 15），
其中「无摘要留 15」这一条**截掉的历史没有任何补偿，直接消失**。
现在改为按 token 预算保留尾部（`RESTORE_BUDGET_RATIO = 0.6` × 上下文窗口），
条数完全退出判断 —— 一条 tool_result 可能比 50 条问答还大，条数与「装不装得下」无关。
保底 `RESTORE_MIN_TAIL_MESSAGES = 15`，与旧实现的最差分支对齐，
使这次修复**在任何配置下都不会比修复前保留得更少**。

关键判断：**装得下就必须全带**。上下文压力已经有专门的一层在管（`query/loop.ts`
每轮开始、发送之前的分级压缩），那条路径用**带摘要的压缩**替代历史 —— 信息有损但不缺失，
严格优于在恢复处无补偿地直接丢弃。所以恢复的正确职责是尽可能多带，把退让交给压缩层。

**D2 —— 补上会话摘要的写入端，挂在压缩观察者上。**
`saveSummary()` 此前全仓零生产调用点（唯一调用者是个测试），磁盘 0 个摘要文件。
新增 `App.persistSessionSummary()`，由 `onContextCompacted()`（压缩观察者的实体）调用，
复用 `compactWithSummary` **已经产出**的摘要 —— 0 额外 LLM 调用、0 额外延迟。
落盘用 `getLogicalSessionId()` 而非进程新 id，否则 resume 后摘要挂在新 id 下，
下次恢复旧会话又找不到（换一种方式继续断线）。

**D3 —— 自动清理从「启动即 fire-and-forget」改为「恢复目标已知后再启动」。**
`cleanupExpiredSessions` / `identifySessionsToDelete` 新增 `protectedSessionIds` 参数，
`cli.ts` 把被恢复会话的 id 传进去。
修法不是「多传一个参数就完了」——**传参数的前提是那个 id 已经解析出来了**，
而原实现的清理在恢复流程之前几百行就已经启动。所以真正的修改是**启动时机**。

**D4 —— `sessionInfo: null` 拆出成因，损坏文件不再绕过保护。**
新增 `SessionExcludeReason`（6 种成因）+ `DELETABLE_EXCLUDE_REASONS` 白名单
（只有 `missing-fields` / `parse-error` 可删）。
「空会话」「子代理会话」不再被当成损坏，「读文件抛异常」按可能的瞬时故障处理（不删）。
真损坏的文件也要过 `minRetention` 与受保护名单 —— minRetention 是防误删的最后兜底，
而「刚写到一半的会话」被并发读到半行时恰好呈现为损坏。

## 放弃了什么（以及为什么不选）

**放弃「只把 15 调大成 50/100」。** 最小改动、最容易过 review，但它没有解决问题的形状：
常数再大也是个与上下文窗口无关的魔数，仍然会在某个会话长度上无补偿地丢历史，
而且下一个人还要再猜一次这个数字该多大。缺陷文档 §2.5 已经指出这三个常数
（20/10/15）本身就是分别加的、没人把三条路放在一起比过 —— 再加一个常数是延续同一个错误。

**放弃「恢复时不截断、完全全量」。** 语义最干净，但窗口极小的模型 + 极长会话下
会让恢复本身就撑爆上下文，把一个「丢历史」换成「一启动就报错」。预算制 + 保底是折中。

**放弃「会话结束时另起一次 LLM 调用生成摘要」（D2 的另一种接法）。**
它更"正统"（摘要覆盖整个会话而不只是被压缩的部分），但：退出路径上加 LLM 调用会拖慢退出；
失败无处可报（`finalizeSessionStore` 是同步 best-effort）；
而且**那正是最容易变成下一个死接线的位置** —— 退出时的失败没人看得见。
复用压缩摘要虽然覆盖面窄一点，但触发时机的语义正好对上：
会话被压缩 ⇔ 历史超出窗口 ⇔ 恢复时也装不下 ⇔ 正是需要摘要补偿的那种会话。
没被压缩过的会话在 D1 修完后本就全量恢复，不需要摘要。

**放弃「给清理加锁 / 加文件 lock」（D3 的另一种解法）。**
锁能防住并发，但代价是引入跨进程锁的全套复杂度（死锁、陈旧锁清理、超时），
而这里的真实需求只是「别删我正在恢复的那一个」。用受保护名单 + 调整启动时机
是与问题规模匹配的解法。

**放弃「损坏文件一律不删」（D4 的保守解法）。** 那是把一个缺陷换成另一个 ——
真损坏的垃圾文件永久堆积。所以保留了「过了 minRetention 的真损坏文件仍然清理」，
并为此专门写了一条反向断言的测试（否则上面两条保护断言可以靠"干脆不删"变绿）。

**未纳入本次范围：D5–D12（P1/P2 共八项）。** 用户明确只修 P0。
特别注意 **D12 就在 D4 改动的同一个 for 循环里**（`maxCount` 用遍历下标而非保留计数），
一行就能改 —— 但它是 P2，刻意没动，避免把「修 P0」的 PR 悄悄扩成「顺手重构清理逻辑」。

## 拿什么证明它生效了

**D1：拿本机 51 个真实会话复算，与缺陷文档的实测数字直接对账。**

```
$ bun /tmp/d1-recheck.mjs      # 与 estimateTextTokens 同口径（ASCII 0.3 / 非 ASCII 0.6）
命中(>20条)会话数 = 36
这些会话消息总数 = 2465
修复前保留 = 540  (丢弃 1925 = 78.1%)   ← 与缺陷文档 §2.3 的 78.1% 完全吻合
修复后保留 = 2465 (丢弃 0 = 0.0%)
其中全量恢复的会话数 = 36/36
最差单会话（修复后）: …/20260903-145710-de49ded0.jsonl 38条 → 38条 (100%)
```

分母口径写死：分母是「消息数 > 20 的会话」（36 个），即旧实现下必然命中截断分支的那批。
文档原始最极端案例（406 条 → 15 条，丢 96%）在新口径下全量恢复。

**变异自证：每条新测试都确认能抓住旧语义。** 这一步是刻意做的 ——
新增测试全绿本身不证明任何事，得先证明它们在旧代码下会红。

```
# D1：把 planRestoreBudget 改回「≤20 条」+ kept 固定 15
(fail) D1：装得下的长会话（50 条）必须全量恢复，不按条数截断
(fail) 路径 2（超预算 + 有摘要）：恢复后含恢复提示
 11 pass / 2 fail

# D4：把损坏文件处理改回 filter(sessionInfo===null) 后无条件 push
(fail) D4：空会话（无 user/assistant 消息）不被当成损坏文件删除
(fail) D4：minRetention 内的损坏文件不被删除
 5 pass / 2 fail

# D3：注释掉 protectedSessionIds 判断
(fail) D3：protectedSessionIds 里的会话不被清理（同期其他过期会话照删）
 6 pass / 1 fail
```

**D2：判据是「落盘 + 能被 loadSummary 读回」，不是「函数被调用过」。**
新增 `packages/core/tests/session/summary-writer.test.ts` 4 条，其中一条从
`ctxMgr` 存下的观察者回调那一侧触发（`compactWithSummary` 实际调的就是它），
覆盖**接线本身**而不只是落盘函数 —— D2 的原始形态正是「两头都活着、中间没人接」。
为此把内联箭头函数抽成命名方法 `onContextCompacted()`，让接线可被测试。
另有一条反向断言：resume 后摘要**不该**写到进程新 id 下。

```
$ make build            → 自检通过；无 "will always be undefined" 导出告警
$ bun run affected-tests:run
  1658 pass / 0 fail (152 files)
$ bun run lint          → 干净
$ bun run lint:boundary → 越界依赖 0 处
$ bun run docs:gen-reference --check → 参考页与源码一致
```

**这次修复的 trade-off（自检第 3 问）：**
本次是**「更准」+「更安全」换少量「更省」**。
恢复带回全量历史 ⇒ resume 后首轮的 input token 变高（旧实现只带 15 条当然便宜）。
判断是可接受的：旧的"省"是**靠丢用户数据换来的**，而丢掉的历史会直接导致模型重复提问、
重做已完成的工作 —— 那些返工轮次的成本远高于一次多带历史的成本（会话长度是成本最大杠杆，
2× 轮数 ≈ 3–4× 成本）。而且超预算的部分仍由压缩层用摘要接管，不是无上限地带。

**留下的可观测缺口（诚实边界）：** 恢复路径的关键决策（走了哪条分支、按预算裁掉多少条）
目前仍只写 `log.info` / `log.warn`，默认不落盘、不可事后复算 ——
缺陷文档 §11.2 指出的这个采集缺口本次**没有**修。也就是说
「恢复后到底带回了多少历史」这条曲线现在仍然画不出来，上面那些数字靠的是离线复算脚本，
不是线上轨迹。补埋点是独立的一件事，不塞进本 PR。
