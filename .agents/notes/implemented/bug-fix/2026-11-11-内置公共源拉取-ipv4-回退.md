# 内置公共源拉取统一走「域名首试 + IPv4 兜底」

## 决定了什么

新增 `packages/core/src/net/public-fetch.ts`（导出 `fetchPublicUrl`），统一接管**仓库内置公共数据源**的 HTTP 拉取：

- 先走域名路径（与裸 `fetch` 等价，4s 内拿不到响应头即判定该链路大概率是 IPv6 黑洞）；
- 失败后解析 A 记录、逐个直连 IPv4，TLS 的 SNI 与 Host 头仍写域名（证书校验语义不变，CDN 按 Host 分流才对得上）；
- 直连拿到 3xx 不自己跟随，交回域名路径去跟（Location 很可能指回域名，自己跟会再踩同一条黑洞）；
- body 的 32MiB 流式限额与「连接 + 读 body」的整段超时**下沉到同一层**——原来 `fetch` 返回后调用方自己读 body，那一段不受超时信号约束。

改造 4 个调用点：构建期快照 `scripts/gen-model-catalog-snapshot.ts`、运行时目录同步 `packages/core/src/llm/model-capabilities.ts` 的 `fetchCatalog`、覆盖率复算 `scripts/catalog-coverage.ts`、分发二进制下载 `scripts/fetch-ripgrep.ts`。

## 放弃了什么（以及为什么不选）

1. **只加长超时 / 只改构建脚本。** 根因是 Bun 1.4 的内置 `fetch` 没有 Happy Eyeballs：域名同时有 AAAA/A 记录时去连 IPv6，且失败后不回落。加长超时只是把「15s 失败」变成「60s 失败」（实测 60s 仍 `AbortError`）；只改构建脚本则运行时的目录同步、覆盖率脚本、ripgrep 下载继续踩同一个坑。
2. **`dns.setDefaultResultOrder("ipv4first")` / CLI 的 `--dns-result-order=ipv4first`。** 两者实测对 Bun 内置 `fetch` 都无效（设完仍 60s AbortError），所以只能在调用侧自己解析地址。
3. **直接 IPv4 优先（先不试域名）。** 正常网络每次都要多一次 DNS 解析；更关键的是**单测里 `globalThis.fetch` 被 mock 时也会触发真实 DNS 查询**，`model-capabilities-catalog-strategy.test.ts` 的一批既有用例会被拖慢甚至联网。「先域名、后 IPv4」让正常路径零额外开销，也让 mock 的测试完全不受影响。
4. **把用户配置的端点也换掉（`gateway-pricing.ts` / MCP / webhook / OTLP）。** 企业内网端点可能只有 IPv6 可达，强制 IPv4 会反向破坏；这类端点的可达性是用户的网络责任，不是仓库的。只在 `public-fetch.ts` 文件头写清适用范围，刻意不改它们。
5. **纳入 `scripts/release-manifest.ts`。** 它是维护者发布时手动跑的一次性 HEAD 探测，失败会立即被发现且不影响用户；为一个 HEAD 请求引入新的网络依赖面不划算。若将来发布链路也踩这个坑，再单独改。

## 拿什么证明它生效了

真实网络（本机：有全局 IPv6 地址与默认路由，但上游黑洞；curl 强制 `-6` 超时、`-4` 1.15s 成功）：

- 修复前：`bun run scripts/gen-model-catalog-snapshot.ts` → `⚠ 快照源拉取失败: AbortError: The operation was aborted.`（15s 超时，快照不更新）。
- 修复后：`make build` → `⚠ 域名路径 4000ms 内未拿到响应头，改试 IPv4（2 个地址）` → `✓ 快照已生成：4570 条模型 / 551KB`。
- 端到端冒烟：`fetchPublicUrl("https://models.opencode.ai/api.json")` → `status=200 bytes=6017519 总耗时=5353ms`；同一台机器上裸 `fetch` 60s 仍 abort。

单测：`bun test ./packages/core/tests/net/public-fetch.test.ts ./packages/core/tests/llm/model-capabilities-catalog-strategy.test.ts` → **26 pass / 0 fail**。新用例覆盖：域名成功时不查 DNS、回退时 SNI/Host 仍是域名、多 A 记录逐个尝试、直连 3xx 回交域名、无 A 记录直接失败、外部取消原样抛出、content-length 预筛与流式超限 cancel。

选测：`bun run affected-tests:run` → 4394 pass / 2 fail。2 个失败是 worktree 环境下 `tests/build/rules-paths-scope-nonempty.test.ts` 的已知假失败（父仓 main 单跑 3 pass / 0 fail；成因是 worktree 的 `.git` 是 gitdir 指针文件，`ruleOwnerDir` 解析到主仓根而非 worktree 根），与本次改动无关。

**之前为什么没拦住**：`fetchCatalog` 的既有单测全部 mock 了 `globalThis.fetch`，真实网络里「DNS 选哪个地址族」这一层不在 G1 覆盖范围内；这个缺陷只能在真实网络上复现。本次把「域名失败 → IPv4 回退」的行为钉死在单测层（G1），不需要 G2/G4——没有 hook、预算或工具执行链参与。
