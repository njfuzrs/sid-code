# 持久化 worktree 只在接续拥有者会话时自动进入，不再靠 session_end 判结束

## 决定了什么

启动时是否自动 chdir 进 `.sid-code/session-config.json` 里记的 worktree，判据从
「拥有者会话结束了没有」改成「本次显式接续（--resume / --continue / 选择器）的是不是拥有者」：

- `persistence.ts`：`shouldAutoEnterWorktree` 变成纯函数，只有 `sessionId` 非空且等于本次接续的会话 id 时才返回 true。
  删掉 `isWorktreeOwnerEnded` / `sessionJsonlEndsWith`（读 jsonl 末行、查活跃注册表）。
- `cli.ts`：启动恢复段只登记候选（`pendingWorktreeRestore`），**不再先 chdir 再撤回**；
  在会话 id 解析完之后的归属复核里才决定进不进。不进入时**不清持久化状态**，留给下次 resume 拥有者。
- 新增 `setWorktreeOwnerSessionId`：cli 在恢复目标确定后回填逻辑会话 id（分叉时不回填），
  之后 `enter_worktree` 落盘的是 jsonl 的会话 id 而不是本进程新 id；`--worktree` 启动且接续了旧会话时按逻辑 id 重写一次。

现象：在主仓（main）执行 `sc-dev`，横幅显示 `Branch fix/bash-which-exit-semantics`。
进程 cwd 确实被切进了另一个会话留下的 worktree，此后的编辑也会落在那里。

## 放弃了什么（以及为什么不选）

- **修好 session_end 的写入，保留旧判据**：退出路径（关终端、kill、崩溃）恰恰是最不可靠的地方。
  实测本机这个项目最近 23 个有内容的会话只有 12 个以 `session_end` 结尾。
  旧判据「没查到就当崩溃 → 进入」让近半数会话变成放行，修好一条退出路径还会有下一条。
- **按 pid 是否存活判定**：pid 死了不等于用户想回去。同一主仓开新终端做别的事，
  被拉进别人的 worktree 正是这次的事故形态。
- **不进入时清掉状态**：会让「崩溃后 `--continue` 回现场」这条路径失效。保留状态的代价只是一份小 json。
- **代价（已接受）**：真崩溃后普通启动不再自动回到 worktree，要用 `--continue` / `--resume <id>`。
  这与「新会话不继承别的会话现场」一致。旧格式（无 sessionId）的状态不再自动进入，用户可再 `enter_worktree`。

## 拿什么证明它生效了

- 端到端复现：临时 git 仓库在 main，加一个 worktree `fix/stale`，写入一份拥有者会话没有 session_end 的 `session-config.json`，
  再用 `script` 拉起 TUI。修复前的二进制（主仓 `sid-code`）横幅显示 `Branch fix/stale`，本分支构建的二进制显示 `Branch main`。
  启动后 `session-config.json` 原样保留。
- `bun test ./packages/core/tests/worktree/ ./packages/cli/tests/cli/worktree-startup-order.test.ts`：153 pass / 0 fail。
- 变异自证：把 `shouldAutoEnterWorktree` 改回恒 true（旧行为的效果），`persistence.test.ts` 有 4 个用例变红。
- `make build` exit 0，且没有 `will always be undefined` 警告。
