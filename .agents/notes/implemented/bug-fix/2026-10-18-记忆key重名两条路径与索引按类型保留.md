# 记忆 key 重名的两条产生路径在写入侧堵住，索引按 user/feedback 优先保留

## 决定了什么

S9（20261016 静默停住方案）。本仓真实记忆库 209 个带 name 的 `.md` 里有 9 组重名，`MEMORY.md` 只列 78 条。改动都在 `packages/core/src/memory/`：

- **路径 A（文件名被当成 key）**：新增 `resolveMemoryKey`，`set` / `get` / `delete` / `resolveEntryPath` 都先按原样精确查，没命中才剥 `.md` 和类型前缀再查。`formatMemoryManifest` 每行补 `key: <name>`，提取提示词改成「用清单里的 key 原值」。
- **路径 A 放大器**：`migrateDoublePrefixNames` 改写 `name:` 前，先全量收集目录里已有的 name 集合。剥完前缀的 name 已被别的文件占用时，跳过改写并 warn。
- **路径 B（跨进程快照过期 + 推断的 type 不同）**：`set` 在 `files.get(key)` 为空时，对 4 种类型前缀各探一次盘。命中 `name===key` 就认领那个文件，并保留它的 type。
- **索引**：先按类型优先级排（user → feedback → project → reference），同组内仍按 `updatedAt` 倒序。字节预算不变。
- **存量**：新增只读脚本 `scripts/memory-dup-report.ts`，列出胜者、被遮蔽者和仅被遮蔽者才有的行。重名 warn 按 key 做进程内去重。

## 放弃了什么（以及为什么不选）

- **入口无条件剥前缀**：会把合法 key `user-auth` 剥成 `auth`。存量重名下，`delete("project_x")` 还会删到 `x`。变异自证里这种写法让 2 条用例变红。
- **自动合并或删除存量重名**：哪一半该留是语义判断，而记忆是用户数据，所以只给出对比清单。
- **去掉索引行里的文件名来省字节**：Read 路径需要真实文件名。全去掉只留 key+文件名也要 19KB，这一招解决不了容量问题。
- **加大 `INDEX_MAX_BYTES`**：索引每轮都全量进 system prompt。本次只改排序，不加成本。代价是截断掉的条目从 user/feedback 换成了 project/reference。

## 拿什么证明它生效了

- `bun test ./packages/core/tests/memory/`：330 pass / 0 fail，含新文件 `store-dup-key-s9.test.ts` 的 9 条。新用例判的是「磁盘上重名 name 数 = 0」，读的是磁盘，不读 store API。
- 变异自证（逐个回退后跑新文件）：
  - resolveMemoryKey 恒返回原 key：2 红（`project_x` 与 `.md` 用例）
  - 去掉路径 B 探盘：1 红
  - 改写前不查占用：2 红
  - 索引退回纯 updatedAt 排序：1 红
  - 换成被否决的「无条件剥前缀」：2 红（`user-auth`、`delete('project_x')`）
- `bun run scripts/memory-dup-report.ts ~/.sid-code/projects/Users-zhourusheng-Code-person-sid-code/memory`：输出「扫描 209，唯一 name 200，重名 9 组」，与方案 §2 S9 的 9 对一致。存量要等用户按清单处理后，才能用同一脚本核到 0 组。
