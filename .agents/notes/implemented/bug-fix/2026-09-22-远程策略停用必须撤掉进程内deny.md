# 远程策略停用必须撤掉进程内 deny

## 决定了什么

远程策略加载分成权威 / 非权威两类，不再用「fail-open」一个词覆盖：

- **权威**（200 / 204 / 304）：以本次响应为准。204 写负缓存（`last_status:204`、无 settings），`applyLoadedPolicy(null)` 把 `remote-policy-state.applied` 拨回 false。
- **非权威**（超时 / 5xx / 401 / JSON 坏了）：进程不崩。只有「endpoint 一致 + 上次权威是 200 + `fetched_at` 未过 10 分钟」才能继续施加旧 deny，否则当无远程策略。

配套四件同一 PR：进程内 `loadEnterprisePolicyOnce`（cli / app 只 fetch 一次）；`applyLoadedPolicy` 无论 null 都同步 state；单次超时 15s + 失败再试一次；权威 info / 非权威 warn 都带 `elapsed_ms` 和分支名。另加不经模型的 `policy-probe`（audit `source=policy-probe`），出口「规则进了 checker」不再靠 `--system-prompt` 让模型撞墙。

## 放弃了什么（以及为什么不选）

- **只清 `policy-cache.json` / 把 5s 改成 30s / 文档写「停用后请删缓存」**：验收 16:01 会话结束时文件已经没了，拦 curl 的是进程内已经注入的 deny。清文件只救下一次进程。
- **`app.ts` 不再 load**：hook 门控仍要读同一份结果；正确解是复用 once-load，不是少调一次。
- **客户端写死 IPv4**：别的网 IPv6 是通的；超时预算 + 日志 `elapsed_ms` 够归因。
- **拆掉 `<permission-constraints>` 刷触发率分子**：附件在工作。度量与劝阻解耦走探针。
- **和触发率窗口（P1）合成一个 PR**：关注点不同，回滚 L2 不该带走停用修复。

## 拿什么证明它生效了

```
bun test packages/core/tests/config/remote-policy.test.ts \
         packages/core/tests/permission/policy-probe.test.ts \
         packages/core/tests/permission/p2-wiring-and-sandbox.test.ts
```

38 pass / 0 fail。修前必红、现已绿的用例：

- 204 后再 abort → null，不得复活 200 deny
- stale 窗口到点：abort 不得用旧 deny
- `applyLoadedPolicy(null)` 拨回 `applied=false`
- 双 load 竞态：abort 注入 deny 后 204，checker 不再 rule deny `Bash(curl *)`
- 第二次 `PolicyManager.load()` fetch 次数 = 1
- 探针：未 applied 不写 audit；applied deny 时 audit `source=policy-probe`
