# auto 快速路径的路径判定交还 PathValidator，用户 ask 规则不再被分类器放行

## 决定了什么

修 M1、M1b 两条 auto 模式的越权放行。修前两条都能用一条 `write` 语句打到工作区外：

- **M1**：`ToolClassifier.fastPath` 自己写了一套路径判断。Level 1 只看工具名
  （`read /etc/hosts` 直接 `safe: true`，不看路径）；Level 2 用
  `filePath.startsWith(req.cwd)`——`/ws-evil/x`（同前缀兄弟目录）、`/ws/../etc/x`
  （`..` 穿越）都判成「工作区内」。
- **M1b**：用户显式写的 `ask` 规则命中后，auto 仍把请求交给分类器（含零成本 fastPath），
  分类器同意即 `allow`。写了 ask 等于没写。

改动分三处：

1. `packages/core/src/permission/tool-classifier.ts`
   - `ToolClassifyRequest` 增加 `pathVerdict?: "inside" | "outside" | "unknown"` 与
     `skipFastPath?: boolean`；
   - `fastPath` 不再持有任何路径知识：Level 1 的带路径工具（read / read_many / glob /
     grep / ls / ripgrep）必须 `pathVerdict === "inside"` 才放行，Level 2 的 write/edit 同理；
     缺省值按 `"unknown"` 处理（**不放行**）——调用方漏传时必须退化成「多花一次分类器」，
     不能静默恢复成不判路径的旧行为；
   - `skipFastPath` 放在 Level 0 之前：工具自报「与安全无关」（`classifierInput === ""`）
     也不能越过阶段一的确认。
2. `packages/core/src/permission/checker.ts`
   - 新增 `extractAutoClassifyPath`（file_path / notebook_path / path / dir_path）与
     `classifyPathVerdict`，用 `PathValidator.resolveRealPath` +
     `isWithinWorkingDirectories` 算判定。用 `isWithinWorkingDirectories` 而不是
     `isWithinWorkspace`：`--add-dir` / `/add-dir` 授权的目录在 default 档读写都不问，
     auto 不该比 default 更严；
   - 新增 `shouldSkipFastPath`：`pathValidation`，或 `classifierApprovable: true` 的
     `safetyCheck`（`.git/`、`.vscode/`、shell rc）出现时，fastPath 整段退场；
   - `classifierMayApprove` 增加 `rule + behavior === "ask" → false`。这是分类器
     「能不能发言」的唯一判定点，auto 分支不另加 if；
   - `autoFallback` 枚举增加 `"ask-rule"`，把「用户规则命中、分类器根本没说话」与
     「分类器判不安全（unsafe）」分开——混成一个数会把用户规则的效果算成模型误判。
3. `packages/core/src/permission/decision-telemetry.ts`：`autoClassifier` 注释补 `ask-rule`。

## 放弃了什么（以及为什么不选）

- **不新写一个 `isWithinWorkspace` 包装**：直接用 `PathValidator.isWithinWorkingDirectories`。
  再包一层等于又造一个「并行的第二套判定」——M1 的根源就是这个。
- **不给 `pathVerdict` 缺省 `"inside"`**：那样任何漏传的新调用点都会静默退回旧行为，
  而这正是本次要修的东西。缺省 `unknown` 的代价是「漏传 → 多一次分类器」，方向正确。
- **不在 `fastPath` 里读取 `cwd` 自己 resolve**：`cwd` 只是提示串，真实边界包含
  `--add-dir` 白名单与 symlink 解析，只有 `PathValidator` 知道。
- **不把 ask 规则的判断写进 auto 分支**：会形成「auto 分支判断一次 + yesMode 判断一次」
  两处口径。收进 `classifierMayApprove` 后，yesMode 的同类问题在 PR-4 可以直接复用。
- **不做「只读工具一律走分类器」的一刀切**：`READ_ONLY_TOOLS` 在 Step 10 已经放行
  read/grep/glob/ls/read_many，fastPath 的 Level 1 只是第二道；把 Level 1 整体关掉
  只会增加 LLM 调用，不改变任何真实决策。
- **不扩大范围到 Step 10 的只读放行**：`grep /etc/passwd` 这类「只读工具 + 工作区外路径」
  在任何模式下都被 Step 10 放行，属于 default 模式的路径口径（见方案 M4），不在 PR-1。

## 拿什么证明它生效了

**G1（`packages/core/tests/permission/auto-fastpath-boundary.test.ts`，15 例）+ 单测**：

```
bun test ./packages/core/tests/permission/auto-fastpath-boundary.test.ts \
         ./packages/core/tests/permission/tool-classifier.test.ts
27 pass / 0 fail
```

用例编号与方案 §6.1 的 12 条验收表一一对应（另加 8b、两条 ripgrep）。夹具是**真实
`ToolClassifier`**，只把 provider 换成假桩（`throw` / `safe` / `unsafe` 三态），
`fastPathCalls` spy 真实 `fastPath` 锁住 checker 传参，`llmCalls` 计数区分
「快速路径放行（0 次）」与「LLM 放行（1 次）」。没有用 `alwaysSafeClassifier()` mock。

**变异自证**（改坏 → 确认变红 → 恢复，恢复后 `shasum` 与备份一致）：

| 变异 | 变红的用例 |
| --- | --- |
| Level 2 改回 `filePath.startsWith(cwd)` | 单测「同前缀兄弟目录」1 条（集成层被 `skipFastPath` 抢先，见下） |
| Level 1 去掉 `pathVerdict` 检查 | 集成「ripgrep 工作区外」+ 单测「只读工具越界 / 未判定」共 2 条 |
| checker 不传 `skipFastPath` | 集成「read /etc/hosts」「.git/config」共 2 条 |
| `classifierMayApprove` 去掉 ask 规则分支 | 集成「ask 规则命中 read / write」共 2 条 |

⚠️ 如实记录一个覆盖边界：`write` 越界在 checker 里**必然**先命中 Step 4 的
`pathValidation` → `skipFastPath = true`，所以集成层的 Level 2 用例无法观察
`startsWith` 回归，只能由 `tool-classifier.test.ts` 的单测守住。Level 1 用 `ripgrep`
补了真实集成覆盖——它不在 `READ_ONLY_TOOLS` 里，是唯一能不经 `skipFastPath` 走到
Level 1 的只读工具。
