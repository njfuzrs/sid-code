# 没有声明等待源的前台轮询：不改拦截判据，只把「还能怎么等」说给模型

## 决定了什么

N8 的两处改动**都不新增任何拦截**，只改模型看到的话：

1. **P1 的「结果与上次相同」提示按有无等待源分流**（`packages/core/src/task/status-poll-guard.ts`）：
   `recordStatusQueryResult` 在同一签名连续第 2 次观察到相同输出时（`sameRun === 2`，机制原本就有），
   若 `hasDeclaredExternalWait()` 为假，返回 `UNWAITED_POLL_HINT`——
   「用后台 bash + `wait_until_seconds`（条件满足就退出的循环）或 monitor 挂上等待，然后结束本轮」；
   有等待源时保持原文案（`[等待中] … describeWaitRelation`）。同一签名只追加一次，状态变化后重新计数。
   `checkStatusQueryPoll` 一行未改：没有声明的等待仍然一次都不拦（T-P1-4）。
2. **Stall L1 文案在纯轮询场景点名出路**（`packages/core/src/query/stall-escalation.ts`）：
   新增两个累计量 `bashCommands` / `statusQueryCommands`（在 `loop.ts` 的 `collectStallObservation` 里
   用生产函数 `matchStatusQuery` 逐条统计，**只算前台**），`isPollDominatedStatusQuery` 判
   「命中 ≥ `STALL_L1_POLL_MIN`(3) 次且严格过半」时，L1 在原收敛提示后追加一句
   「这类等待改用后台 bash + wait_until_seconds 或 monitor，然后结束本轮」。
   两个新字段同时落 `StallEscalation` 事件，影子数据能复算。

为什么：事故会话 962011a6 在 `gh run rerun` 之后 **68 次前台查询、0 个等待原语、20.8M 输入 token**。
现有防线对这条路径要么只报不拦（`UnchangedObservationRun`、Stall L2 影子），
要么像 P1 一样因为「没有声明等待」直接放行；L1 那句「如果绿点已经满足用户要求，请停止改动，提交收尾」
对一个正在等 CI 的模型没有可执行的下一步。

## 放弃了什么（以及为什么不选）

- **不「没有等待源也拦」**。方案 §N8 明确不推翻
  `.agents/notes/rejected/feature/2026-07-14-工具循环检测默认开启.md`：全局按形态拦截的误判率 ≈100%。
  P1 能开的唯一理由是「模型自己声明了在等」，没有声明就拦等于回到那条被否决的路。
  **代价点破**：这只是一句引导，模型可以无视（962011a6 里 L1 就被无视过一次）。
  如果上线两周后 `unwaited_longest_run` p95 没下降，本 Note 的结论就是
  「没有声明的轮询只能靠拦截解决」，届时拿 N7 的数据复评 §7.3 的否决，而不是在这里偷偷加阈值。
- **不改 `checkStatusQueryPoll` 的任何判据**（探测间隔、`sameRun` 门槛、含写操作放行）：
  这次改的是「说什么」，不是「拦不拦」。混在一起会让回滚粒度变粗。
- **不新造计数器**：复用现有 `sameRun === 2` 的「第一次相同」时机。再往后模型已经在被提示过的
  稳定状态里，继续念一遍只是噪声；状态变化后重新计数则保证它看到过新信息之后再提醒。
- **L1 判据的分母用 bash 调用数，不用工具轮数**：`read` / `grep` 不会「查外部状态」，放进去只会稀释；
  一轮里并行发多条 bash 时逐条计数才反映真实构成。**不算后台 bash**：那是合法的等待手段。
- **本 PR 不做 N6（前台 `sleep`）**。方案把 N6 与 N8 合进 PR-D，但 N6 的两档（引导 / 拦截）
  有各自的误伤评估，混进来会让 review 同时想两件事；本次只交付 N8。
