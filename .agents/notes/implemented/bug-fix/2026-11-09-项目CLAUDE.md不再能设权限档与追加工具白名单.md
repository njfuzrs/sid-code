# 项目 CLAUDE.md 的权限模式与工具白名单段不再生效，只认用户级与企业级来源

## 决定了什么

Harness 厚薄归位专项 B6 / B9 / B23（#672）。

- **项目侧来源剔除**：`loadAllCLAUDEmd` 合并之前，把 `project` / `subdir` / `rulesDir` / `local`
  （以及缺失 `layer`）各层的 `## Permission Mode` 与 `## Allowed Tools` 剔除，记进结果的
  `ignoredSecurityFields`。可信层是白名单 `managed` / `user` / `userRulesDir`
  （`config/rules-security.ts` 的 `TRUSTED_RULE_LAYERS`），新增的规则层默认不可信。
  `## Disallowed Tools` 这类收紧项不受影响。
- **取值校验 + 企业策略**：可信层的取值必须在 `PERMISSION_MODE_VALUES` 里，否则忽略；
  企业 `disabledModes` 或 bypass 禁用命中的也忽略（`resolveRulesPermissionMode`）。
  「只在 default 档才采纳」的原语义不变。
- **留痕（B23）**：采纳与剔除都打 `ProjectRulesPermission` 轨迹事件
  （`field` / `action: applied|ignored` / `reason` / `layer` / `value` 截断 64 字 / `from` / `to` / `trigger`），
  同时 `log.warn`。启动时 `applyProjectRules` 早于 `initTraceCollector`，事件先缓存到 App 上，collector 建好后补发。
- 新增 G2 用例 X6：仓库 CLAUDE.md 同时写两段，default 档无头下 `git remote add` 必须判拒。

为什么剔除点放在 `loadAllCLAUDEmd` 而不是 `app.ts`：合并后 `permissionMode` 只剩最后写它的那一层的值，
层级信息已经丢了；而且所有调用方（启动、热重载、worktree 切换、外部导入审批）都经过这一个函数。

## 放弃了什么（以及为什么不选）

- **项目侧只许收紧、不许放宽**（允许 `plan` / `deny-write`，拒绝 `always-allow`）：需要给 8 个模式排一个严格程度，
  `auto` 和 `dontAsk` 排在哪里没有共识。项目级 settings.json 对 `permissionMode` 是整个剔除，
  两条路径口径不一致会让「这个字段在项目里能不能写」变成要查两份文档。也没有证据说有人在用项目 CLAUDE.md 收紧。
  将来真有需求，在 `stripUntrustedSecurityFields` 里给收紧模式开口子即可，不影响本次结构。
- **只修热重载、保留启动时生效**：启动路径才是更大的口子。clone 一个仓库打开 sid-code，模型还什么都没做，
  权限档已经被仓库内容改掉了，而工作区信任（`permission/trust.ts`）不扫 CLAUDE.md。
- **把 CLAUDE.md 加进 safetyCheck 保护路径（B10）**：防的是「模型写 CLAUDE.md」，防不了「仓库自带 CLAUDE.md」；
  而且 CLAUDE.md 是用户和模型都会频繁正常编辑的文件，每次都确认是很大的误伤面。剔除后写它不再能提权，B10 降为低优先级。
- **`dangerously-skip-permissions` 取值在用户级 CLAUDE.md 也拒绝**：实测它只改模式标签，不打开 `skipPermissions`，
  落到 Step 14 默认确认，不构成放宽。属于另一个「标签与行为不符」的问题，不在本次范围。
- **把 B7（agent frontmatter `permissionMode`）并进同一个 PR**：研究文档原计划 B6 + B7 + B23 一个方案，
  回放实测后拆开。项目级 agent 无头下过不了内容哈希信任（`sub_agent` 报「无效的子代理类型」），
  模型写一个新 agent 文件也要先过写入确认和信任确认，**不构成「模型自己提权」**；
  用户级 agent 声明 `always-allow` 时子代理确实比 default 父会话放得更宽（`step=8-mode` 放行 `git remote add`），
  但那是用户自己配的、官网 subagents 页写明的字段，是否夹到父会话档位是产品取舍，单独评估。

代价（更安全 ↔ 更快）：依赖项目 CLAUDE.md 设 `always-allow` / `acceptEdits` 的用户会开始看到确认框，
无头模式下这些操作会被判拒。迁移办法：写进 `~/.sid-code/CLAUDE.md`、用户级 settings.json 的权限规则，
或命令行 `--permission-mode`。官网没有任何一页承诺过项目 CLAUDE.md 能设权限模式（`grep` website 命中 0）。

## 拿什么证明它生效了

**修复前，构建产物回放复现**（临时探针用例，`realPermissions: true`，2026-11-08）：

| 路径 | 修复前 | 修复后 |
| --- | --- | --- |
| 启动：仓库 CLAUDE.md `always-allow`，`git remote add` | `allow step=8-mode mode=always-allow`，`.git/config` 写入 remote | `deny step=headless:14 mode=default`，未写入；`ProjectRulesPermission{ignored, untrusted_layer, project, trigger:startup}` |
| 热重载：会话中途 `cp` 出带 `always-allow` 的 CLAUDE.md，等 2s 再 `git remote add` | `allow step=8-mode mode=always-allow` | `deny`；事件 `trigger:reload` |
| acceptEdits 档 + 同一 CLAUDE.md | `deny`（`=== "default"` 守卫本来就挡住） | `deny`，多一条 ignored 事件 |
| `## Permission\n见团队 wiki` | `deny`，但 trace `mode: "见团队 wiki"` | `deny`，`mode: default` |
| 取值 `dangerously-skip-permissions` | `deny`（skipPermissions 不跟着变） | `deny` |
| `## Allowed Tools\n- Bash(git remote add *)` | `deny`（本来就不生效，见下） | `deny`，ignored 事件 |

最后一行说明：项目侧的 `## Allowed Tools` 修复前实测就**不生效**——它被追加进 `config.allowedTools`，
而 checker 的 `preApproved` 在构造时就已读完（`checker.ts:650`）。用户级走的是同一条追加路径，推断同样不生效（未单独实测）。
项目侧剔除让它从「哪天接线修好就成了口子」变成「确定不会生效」；用户级不生效是功能缺陷，另记台账。

**单测**（`packages/core/tests/config/rules-security.test.ts`，16 例，含两例走真 `loadAllCLAUDEmd` + 临时 git 仓）
变异自证 4/4：

- `stripUntrustedSecurityFields` 恒返回原对象 → 7 fail
- `rules.ts` 合并前不剔除 → 2 fail（两条真实加载链用例）
- 不校验取值 → 1 fail
- 不查企业策略 → 1 fail

**G2**：`bun run smoke X6-claudemd-permission-mode` PASS；`bun run smoke:mutate X6-claudemd-permission-mode`
1/1 KILLED（合并前不剔除 → `PermissionDecision deny` 期望 1 实际 0）。
