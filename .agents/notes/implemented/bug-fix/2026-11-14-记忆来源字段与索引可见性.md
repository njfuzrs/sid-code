# 记忆带上 `source` 三档来源，`agent_action` 不进索引也不优先召回

（对应缺陷方案里的 PR-2 / P0-3 / MD6。）

## 决定了什么

修的是这条链路：后台记忆提取代理把「agent 自己这一轮做了什么」写成记忆落盘，
它与「用户明确说的偏好」在 `MEMORY.md` 索引里并列；索引全量注入 system prompt，
下一个会话的模型把它当既有事实读回来，按它行动、再把行动结果写回记忆 —— 自我强化。

三条代码判据（不是提示词劝告）：

1. **落盘带来源**：`MemoryFrontmatter` / `MemoryEntry` / `MemoryHeader` 增加
   `source: "user_explicit" | "agent_action" | "inferred"`。缺省 `inferred`——
   老文件（本次之前写的）没有这一行，一律按 `inferred` 解析，**不猜成 `user_explicit`**。
2. **后台路径强制覆写**：`tool/memory.ts` 的 `MemoryTool.execute` 里按
   `querySource === "memory-extract"` 无条件把来源改写成 `agent_action`，**不看模型传了什么**。
   `save_memory` 因此新增 `consumesQuerySource: true` 声明，执行器（`agent/forked-agent.ts`）
   按需注入 `_querySource`；`_querySource` 同时进 `INTERNAL_FIELDS`，模型伪造会被剥离。
3. **不可见 + 不优先**：`agent_action` 不进 `MEMORY.md` 索引（`writeIndex` 渲染前过滤，
   所以 `load()` 重建也走同一条判据 —— 入口不止 `set()`，提取代理是直接改盘的）；
   召回候选按 `memorySourceRank` 重排（`user_explicit` → `inferred` → `agent_action`）；
   满额淘汰时 `agent_action` **最先**被归档（它本来就看不见，不该挤掉模型正在依赖的记忆）。

配套：`docs:gen-reference` 已重新生成（`save_memory` 的 schema 多了一个 `source` 参数）。

## 放弃了什么（以及为什么不选）

- **没在权限层做覆写**。看着更「集中」，但 forked 路径上 `updatedInput` 会被丢弃 ——
  权限层改完测得绿，落盘的仍是原值。这类「测得绿但写不进盘」的修法比不修更危险。
  所以判据放在 `execute` 内部，断言也必须落在磁盘 frontmatter 上。
- **没让模型自报来源**（不加 `source` 参数、全靠提示词）。让最没有判据的角色
  （提取代理没有用户输入可依据）给证据定级，就是本缺陷的成因。schema 里仍保留
  `source` 参数，但只对**非提取路径**生效：`user_explicit` 的判据只有「用户刚说过这句话」
  这个会话事实，工具侧看不到，只能由模型提供。
- **没有把 `agent_action` 删掉或拒绝写入**。只做「移出视野」这一档：
  不进索引、召回排最后、淘汰优先。理由是「这条记录有没有价值」无法用字符串判据判定，
  而删除是不可逆的。它仍可被显式 Read 捞回来。
- **没扩到 `team` / `agent` 两个 scope**。它们的落盘格式是各自独立实现的
  （`memory/team/store.ts`、`memory/agent-store.ts`），不在 P0-3 的验收范围（`MEMORY.md` 索引）
  内。代价点破：这两个 scope 下 `source` 参数会被忽略，来源按各自缺省处理。
  下一轮如果要把来源判据铺开，这里是唯一还没覆盖的地方。
- **没改 `STORE_MAX_ENTRIES` 容量口径**。`agent_action` 仍占条目数配额，
  只是淘汰时排在最前。真要让它们不占容量需要另一套计数口径，那属于容量治理（P1 系列），
  和「来源可见性」是两个关注点。

```
  → 13 pass / 0 fail

  → 430 pass / 0 fail（含改前就有的索引、淘汰、写闸、召回用例，无回归）

bun run typecheck:gate   → 当前 62 处 / 基线 62 处，无新增
bun run lint             → 0 warnings 0 errors
bun run format:check     → All matched files use the correct format
bun run lint:boundary / lint:command-system / lint:legacy-tool → 三道均通过
make build               → 编译 + 产物自检通过
bun run smoke            → 28 例 28 通过 0 失败
```

**变异自证（T-M9，方案要求的唯一证据点）**：把 `resolveWriteSource` 里的
`if (querySource === MEMORY_EXTRACT_QUERY_SOURCE) return "agent_action"` 去掉，
重跑 `source-provenance-p0-3.test.ts` → **11 pass / 2 fail**，
红的正是「模型自称 user_explicit → 落盘必须是 agent_action」与「提取路径不传 source
也落 agent_action」两条；恢复后 13 条全绿。它报的是 `expect(file).toContain("source: agent_action")`
失败，不是退出码。

**选测里的一个失败已举证与本改动无关**：`packages/core/tests/agent/isolated-subagent-cwd.test.ts`
的「未绑定 cwd 时不出现隔离提示（主仓子代理行为不变）」。三条证据：
① 该测试不 import 本次改动的任何模块（它导入 `SubAgent` / `cwd-context` / `BashTool` /
`trace/*`，我改的是 `memory/*`、`tool/memory.ts`、`tool/internal-fields.ts`、`tool/bridge.ts`、
`tool/types.ts` 与 `agent/forked-agent.ts`；唯一交集 `tool/types.ts` 只增类型字段，运行期零影响）；
② 在父仓 `main` 上单跑该文件 11 条全绿；
③ 环境成因：在 worktree 里跑时进程 cwd 就在 `.sid-code/worktrees/memory-source-provenance`，
失败输出里子代理系统提示词的「当前工作目录」正是 worktree 根，并附带了
「【隔离环境提示】…你当前运行在一个隔离的 Git Worktree 中」——而该用例断言的前提是
「主仓子代理不出现隔离提示」。CI 的检出路径不含 `.sid-code/worktrees/`，不会触发。
