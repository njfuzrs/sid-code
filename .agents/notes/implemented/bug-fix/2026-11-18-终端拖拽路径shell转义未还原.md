# 拖拽路径的 shell 转义在 paste 分支还原，判据用 existsSync 兜住误伤

## 决定了什么

**在 paste 分支还原，不做提交边界还原。**

- 新增 `packages/cli/src/ui/utils/dropped-path.ts` 的 `unescapeDroppedPath(text, exists = existsSync)`，
  四条判据全过才替换，否则原样返回：
  1. 单行（多行是代码块/正文）；
  2. 「去成对引号」或「反转义」至少一项真的生效，**比较对象是原文 trim 后的串**；
  3. 还原结果以 `/`、`./`、`../` 开头（`echo a \& b` 这类 shell 片段在 stat 之前短路）；
  4. 还原结果 `existsSync` 为真。
- 接线点在 `packages/cli/src/ui/InputArea.tsx` 的 `key.name === "paste"` 分支、`cleanPasteText` 之后，
  且**放在 `detectDroppedImagePath` 之前**——图片路径同样可能含 `&`，先还原才能命中。
  下游 `shouldPlaceholder` / `registerPaste` / `tb.insert` 全部改用还原后的 `pathText`。
- 首次命中时给一次 transient hint（`droppedPathUnescape`，`shouldShowHint` 3 次衰减 +
  `markHintShown`），按 L4-C 的接线约定。
- 测试设施两处配套：`TuiStep` 增加 `raw` 型（原样注入字节、不 `waitFor`，用于 bracketed paste），
  tui 剧本支持 `${CASE_ROOT}` 替换（拖拽路径必须指向用例仓里的真实文件，否则 `existsSync` 判据永远不成立）。

## 放弃了什么（以及为什么不选）

- **无条件全局反转义**（不判存在性）：会改坏用户粘贴的 shell 片段（`echo a \& b`）与
  Windows 路径（`C:\new`）。`existsSync` 是让「猜」变成「求证」的那一步——代价是不存在的路径
  （用户手敲的错路径）不还原，但它本来也不是拖拽来的。
- **只在提交边界（§5.5 候选 A）按 token 还原**：拖拽在终端里走 bracketed paste，
  `KeypressContext.bufferPaste` 会把它合成 `key.name === "paste"`，paste 分支是更精确的接线点；
  提交边界要处理多行正文、占位展开、`@` 引用等更多形态，误伤面更大。
  §5.0 的接线点确认依据：sid-code 主动启用 bracketed paste mode
  （`packages/tui/src/components/App.tsx:581` 的 `?2004h`、`packages/cli/src/ui/utils/terminalCapabilityManager.ts:29`），
  且 `detectDroppedImagePath` / `resolveCopiedImageFile` 的存在本身证明拖拽历史上就走这条分支。
- **只修图片路径**（沿用 P2-7 的收窄范围）：普通文件（`.md`、目录）同样带转义，用户报的就是 `.md`。
- **改终端配置或让用户关掉 bracketed paste**：用户侧配置不可控，且 bracketed paste 是
  多行粘贴/图片识别的既有依赖。
- **把全文都交给 `existsSync`**：判据 3（路径前缀）在 stat 之前再挡一层，
  避免对正文里恰好含路径形态的文本做无谓的文件系统探测。

## 拿什么证明它生效了

在本 worktree（`worktree-fix-dropped-path-unescape`，基线 `aae2cfc8`）里实测：

- **G1**：`bun test ./packages/cli/tests/ui/dropped-path-unescape.test.ts` → **12 pass / 0 fail**。
  含两条专用回归（「只有引号、内部无转义」的中文/空格目录）与 Windows 路径负向对照。
- **G1 变异自证**（三次，均先变红再恢复）：
  ① 函数体直接 `return text` → 7 条红；
  ② 判据 2 的比较对象改回 `unescaped === s` → 只有两条「只有引号」红；
  ③ 去掉 `exists` 闸门 → 只有「还原后不存在」红。
  （③ 与方案 §7.1 的预期相比少红了「shell 片段」一条：因为实现里加了判据 3 的路径前缀预筛，
  该用例在前缀处就早退，轮不到 exists。行为正确，是方案的预期表没算上预筛。）
- **G4**：`bun run smoke:tui A17-dropped-path` → **PASS（1.0s）**。
  用 `raw` 注入两种 bracketed paste 形态（`\&` 无引号 / 整条单引号），
  断言屏幕出现还原后的路径，且 `UserPromptSubmit.data.prompt` 恰好以干净路径结尾、不含 `\` 与引号。
- **G4 变异自证**：`bun run smoke:mutate A17-dropped-path` → **1 killed**
  （变异的正是接线行 `unescapeDroppedPath(cleaned)` → `cleaned`，屏幕 20s 内没有还原后的路径）。
  这是方案 §7.2 要求的「修复前先红一次」对照。
- **回归门禁**（全绿）：
  - `bun run affected-tests:run` → 5743 pass / 0 fail / 10 skip；
  - `bun run smoke`（G2 全量）→ 43/43；
  - `bun run smoke:tui`（G4 全量）→ 5/5（含新增 A17）；
  - `make build` 产物自检通过；`bun run lint`、`bun run format:check` 通过；
  - `bun run typecheck:gate` → 62/62，无新增。
- **诚实边界**：PTY 注入的是 bracketed paste 形态，等价于「终端以 bracketed paste 发送拖拽」。
  真实 Finder 拖拽（iTerm2 / Terminal.app / VSCode）由用户在真机上再确认一次；
  若某终端发送裸字节（不进 paste 分支），该终端下本修复不生效——此时才需要 §5.5 的提交边界方案。
