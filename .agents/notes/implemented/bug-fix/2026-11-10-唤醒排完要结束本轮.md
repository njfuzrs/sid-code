# 唤醒排下去之后，模型必须知道「本轮该收尾了」

## 决定了什么

`schedule_wakeup` 的三处**模型可见文案**补上同一件事：「唤醒只在本轮结束、会话空闲后触发；
排完不要留在本轮继续查询，没有别的事就结束本轮」。

1. **工具返回文案**（`packages/core/src/tool/schedule-wakeup.ts`）追加一行。原文案只有
   「已安排 N 秒后」+「目标达成后用 cron_delete 取消」，没有一句说唤醒要等本轮结束。
2. **工具描述**（同文件）要点列表加一条 —— 模型在首次选工具时就能看到，而不是排完才知道。
3. **唤醒注入文本**（`packages/core/src/query/scheduled-prompt.ts`）：`origin=schedule_wakeup`
   的注入消息在来源头与 prompt 之间加一行收尾指引（`formatWakeupTurnGuidance`，中英各一）；
   `stripScheduledPromptHeader` 同步剥掉它，并**兼容旧格式**（历史消息里没有这一行）。

只有 `schedule_wakeup` 加这条指引：`/loop` 与 `cron_create` 是固定节奏的周期任务，
注入后本来就该继续做那一轮的工作，加这句会诱导模型提前结束。

## 放弃了什么（以及为什么不选）

- **不在本轮内拦截状态查询**。方案原文也把这条划归 P1（N3）的职责。拦截判据其实已经有
  （`hasDeclaredExternalWait()` 把唤醒算作声明的等待源），缺的是命令匹配面；在这里再造
  一套阈值等于两套判据并存，修 N3 时还得同步改两处。
- **不把收尾指引塞进来源头那一行**。来源头是**身份标记**：`stripScheduledPromptHeader`
  靠它的精确形态做剥离，TUI 靠 `_meta.origin` 判断「这条不是用户敲的」。把行为指令混进
  同一行，会让一行同时承担两种职责，长度也翻倍（模型扫读时更容易漏掉后半句）。
- **不给 `/loop` / `cron_create` 也加**：见上，会诱导周期任务提前收尾。
- **没有重跑 G3 真模型对照**（case 已加，见第三段）。方案把 G3 定为「维护者本机」，
  本机 `~/.sid-code/settings.json` 的 `providers` 为空，没有可用的自有 provider 配置。
