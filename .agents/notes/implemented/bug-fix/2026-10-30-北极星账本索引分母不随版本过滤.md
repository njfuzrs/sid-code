# 北极星快照的账本 / 索引分母改取全部本地行，与轨迹目录数同一总体

## 决定了什么

`scripts/northstar-snapshot.ts` 的 `buildSnapshot` 里，`ledgerSessions` / `indexSessions` 改为从**过滤前**的 `rawLedger` / `rawIndex` 去重计数，不再用按 `--days` 窗口和 `--version` 过滤后的 `ledger` / `index`。指标本身（e2e、TTFT、成本等）仍按版本过滤，只有四个分母统一成「整个本地存储」。人类可读输出在三个口径下方加一行「分母统计整个本地存储，不随 --version / --days 过滤」。

根因：`buildAssertions` 拿账本 / 索引会话数去比 `trajValidSessions`（数 `trajectories/sessions/` 目录，天然不分版本），两边总体不同。`release.sh` 生成快照时带 `--version <新版本>`，新版本刚发出只有 0–1 个会话：

- v0.1.610–v0.1.612：账本 / 索引都是 0，两条断言因 `> 0` 守卫被**静默跳过**；
- v0.1.613：账本 1、索引 1 vs 轨迹有效 577，两条断言**恒红**。

两种都不是漏采，是比较本身无意义。

## 放弃了什么（以及为什么不选）

- **把 `trajValidSessions` 也按版本过滤**：否决。轨迹目录名不带版本号，要按版本过滤就得逐个读 `events.jsonl` 去找 app_version，代价大，而且轨迹受 LRU=100 管辖，按版本切出来的数本身也不稳定。断言要表达的是「索引 / 账本不该比盘上剩下的轨迹少」，这是全局关系，用全局总体判才对。
- **`scope=version` 时直接不产出这两条断言**：否决。这两条断言是发版时唯一会看到的「漏采」信号，而发版快照恰好都是 `scope=version`。跳过就等于这道防线在它唯一被运行的场景里永远不触发（v0.1.610–612 已经是这个形态）。
- **重新生成已入库的 `northstar/v0.1.613.json`**：不做。快照是发版时刻的记录，现在重跑会混进发版之后新增的会话，`generatedAt` 也会变。错的只有两个分母，指标本身是按版本过滤的、没受影响。

## 拿什么证明它生效了

修复前，v0.1.613 发版日志：

```
- ❌ 账本会话数 >= 轨迹有效会话数 —— 账本 1 vs 轨迹有效 577
- ❌ 索引会话数 >= 轨迹有效会话数（索引不受 LRU 影响） —— 索引 1 vs 轨迹有效 577
```

修复后，本机真实数据 `bun run scripts/northstar-snapshot.ts --version 0.1.613`：

```
数据范围: 仅 v0.1.613 产生的行（可用于版本对比）
  （分母统计整个本地存储，不随 --version / --days 过滤）
  ✅ 账本会话数 >= 轨迹有效会话数  —— 账本 883 vs 轨迹有效 577
  ✅ 索引会话数 >= 轨迹有效会话数（索引不受 LRU 影响）  —— 索引 853 vs 轨迹有效 577
```

新增回归用例「按版本过滤时，账本/索引分母仍取全部本地行」：只注入 active / trajValid，账本 / 索引分母由 40 行数据（1 行 v0.1.613）推出，断言分母 = 40、两条断言为绿、`e2e_p50.n = 1`（指标仍按版本过滤）。
