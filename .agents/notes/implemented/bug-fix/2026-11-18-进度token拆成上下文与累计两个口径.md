# 进度里的 token 拆成「当前上下文」与「累计消耗」两个具名口径

## 决定了什么

子代理进度此前只有一个 `tokens` 属性，取的是 `totalUsage.inputTokens + outputTokens` 的
**累计值**。它随轮次单调增长（242 轮的会话能到 1300 万），而同一时刻真实上下文峰值只有 94k。
父代理读这个数判断「它上下文快满了，该动手了」，于是提前几十倍收掉子代理（M1）。

改动分四层，同一个口径：

1. **生产者**（`agent/agentic-loop.ts`）：`onTurnEnd` 的回传类型从内联字面量抽成具名
   `TurnEndInfo`，新增 `contextTokens`——取**最后一次请求**的 `promptTotal`
   （与上下文估算器校准同源：同一个 `normalizeCacheUsage(...)` 结果，同一个 try 块里赋值）。
   **6 处 `onTurnEnd` 调用点收成一个 `buildTurnEndInfo()`**：加字段只需改这一处，
   不再有「改了 5 个出口、漏了第 6 个」而全绿也发现不了的缺陷。
2. **任务进度契约**（`task/types.ts`）：`AgentProgress` 加 `contextTokens`，必填。
   漏传变成编译错误，而不是静默降级成 0。
3. **渲染**（`task/registry.ts`、`tool/task-output.ts`、`tool/task-list.ts` 三处）：
   `<progress tools="…" context_tokens="…" cumulative_io_tokens="…">`。
   原来含义模糊的裸 `tokens="…"` 全部消失。
4. **两条子代理路径都接上**：进程内（`sub-agent.ts` 的 `onTurnEnd` 回调）与 spawn
   （`sub-agent-protocol.ts` 的 `ChildProgressMessage` 加可选字段 + `headless.ts` 上报）。
   spawn 侧字段设**可选**：旧子进程不带它时父进程按 0 处理，不会把"未知"误判成"满了"。

## 放弃了什么（以及为什么不选）

1. **只把 `tokens` 的取数改成 promptTotal、属性名不动**：属性名不改就仍然是一个
   含义随实现漂移的字段，下一个读它的人还是分不清「一共烧了多少」和「现在占多大」。
   两个问题必须两个名字。
2. **保留 `tokens` 作为 `cumulative_io_tokens` 的别名一起输出**：双写会让"到底该读哪个"
   永远没有答案，而代价是每轮多一个属性。旧名直接删——本仓尚无外部消费者依赖它
   （`grep -rnF 'tokens="' packages tests` 只命中 salvage 自己的另一套 `<progress>` 口径，
   与任务进度无关）。
3. **`AgentProgress.contextTokens` 设为可选、渲染时缺省**：那样所有构造点（含测试）
   会静默漏传，渲染出 `context_tokens="undefined"` 或直接少一个属性——正是这次要修的
   "字段在、口径不明"那类缺陷。必填迫使每个构造点显式表态。
4. **在 `sub-agent.ts` 里自己再算一遍 promptTotal**：会和 `agentic-loop.ts` 的估算器校准
   漂成两个数（"进度说 9%，估算器说该压缩"）。取数点只有一个。
5. **给 UI 的 `AgentProgressSnapshot.tokenCount` 也改名**：那一份是**给人看的**累计消耗
   （`/tasks` 卡片上的 "12.3k token"），语义本来就对，且不参与父代理决策。
   改它属于顺手扩大范围。

## 拿什么证明它生效了

1. **变异自证**：把 `buildTurnEndInfo()` 里的 `contextTokens: lastContextTokens` 改回
   `totalUsage.inputTokens + totalUsage.outputTokens`，跑
   `bun test ./packages/core/tests/agent/turn-end-context-tokens.test.ts` →
   `Expected: 100 / Received: 105` 变红；恢复后 4 例全绿。说明这条断言真的在锁口径，
   不是恒绿。
2. **G1 用例**（`packages/core/tests/agent/turn-end-context-tokens.test.ts`）：
   - 驱动真实 `runAgentLoop`，两轮 input 分别 100 / 500：第一轮 `contextTokens=100`、
     `tokenCount=105`；最后一轮 `contextTokens=500`（不是 600）、`tokenCount=610`；
     并断言两者**不相等**。
   - 渲染：`<task-statuses>` 输出 `context_tokens="94000"` 与
     `cumulative_io_tokens="13009075"`，且不含裸 `tokens="`。
   - 源码哨兵：三处渲染文件都同时含两个新属性名（行为断言只覆盖 registry 一处出口，
     而 `bg_task_output` / `bg_task_list` 是另外两条独立渲染路径，漏改不会红）。
   - 新建任务初始进度两个字段都是 0。
3. **类型门禁**：`bun run typecheck:gate` → 62/62 与基线持平，无新增。
   `AgentProgress.contextTokens` 设必填后，全局只剩两个测试构造点需要补，已补齐
   （`cli/tests/command/workflows.test.ts`、`core/tests/session/teammate-registration.test.ts`）。
4. **参考页无漂移**：`bun run docs:gen-reference` 跑后 `git status` 无 `website/ref/` 改动——
   本次改的是渲染逻辑，不动工具参数文档。
