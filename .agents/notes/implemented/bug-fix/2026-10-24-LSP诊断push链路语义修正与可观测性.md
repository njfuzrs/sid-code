# LSP 诊断 push 链路：pending 按 uri 覆盖、归属隔离、过时推送闸门、严重度先于限流，并补 LspDiagnostics 埋点

## 决定了什么

`lsp/diagnostic-registry.ts` 的 pending 语义整体重写，逐条对应审计出的缺陷：

1. **严重度过滤先于限流**（原：先按 10/30 限流、再在 `collectDiagnosticText` 过滤）。Hint 不再占名额，限流改为跨文件按严重度排序（Error 先于所有 Warning）。
2. **超限部分留在 pending 补发**，并在注入文本里写「另有 N 条 Error/Warning 超出单次上限，将在后续轮次补发」（原：整批清空，模型不知道还有）。
3. **pending 按 uri 存最新全量快照**（原：按 `server-seq` 追加，同轮多次推送取并集，会注入已修好的错误）。与 `latest` 同语义。
4. **归属隔离**：每个文件归属最近编辑它的消费者（主循环 `main` / 子代理 agentId），`collectDiagnostics(owner)` 只取自己名下（原：主循环无作用域 collect 清空全部 pending，子代理诊断被偷）。子代理结束 `releaseOwner` 转回主循环。spawn 路径子代理此前编辑后不通知 LSP，一并补上。
5. **pending 有界**：按 uri 覆盖后上限 = 文件数。
6. **过时推送闸门**：`syncFileToLSP` 在第一个 await 之前同步 `beginEdit`（原：await readFile 之后才清，fire-and-forget 调用下一轮 collect 可抢跑）；beginEdit→endEdit 窗口内到达的推送丢弃；声明 `publishDiagnostics.versionSupport`，推送带 version 且落后于已发出版本时丢弃。
7. **只被 lsp 工具打开的文件**：首次推送只记基线（标为已投递）不注入，之后新出现的诊断给主循环（原：以「你刚编辑文件」名义注入既有问题）。
8. **codeAction 整文件范围**用真实文档末尾（`documentEnd`，UTF-16 码元口径），不再写死 999999 行。

可观测性：新增 `LspDiagnostics` 事件（每次 collect 一条，两次 collect 之间无事发生则不写），字段 outcome（injected / clean / info_only / all_delivered / empty）、injected、carried、omitted_info、already_delivered、publishes、publishes_with_version、stale_syncing、stale_version、agent_id；`app.ts` 接线；`trace/digest.ts` 聚合为「LSP 诊断」一节。

## 放弃了什么（以及为什么不选）

- **保留 `scopeUris` 作用域参数、只给主循环也传作用域**：主循环需要的作用域（自己编辑过的文件）本质上就是归属，另维护一份集合会和子代理那份互相不一致；且无法表达「子代理结束后转回主循环」。
- **未编辑文件的诊断一律不注入**：会丢掉「改 a.ts 弄坏了已打开的 b.ts」这类跨文件信号。基线方案的代价是 b.ts 若在 a.ts 编辑之后才首次推送，那次破坏会被当成基线吞掉——接受，因为一律注入的反面已有实测误报（会话 20261022-003851-9f9e6c25）。
- **pull 诊断（`textDocument/diagnostic`）替代 push**：typescript-language-server 5.1.3 不提供 diagnosticProvider，换协议等于对主力服务器失效。
- **只靠 version 判过时**：tsls 5.1.3 的推送不带 version（源码 `publishDiagnostics()` 只发 uri+diagnostics，本次 e2e `publishes_with_version` 恒 0），所以同步窗口闸门是主防线，version 闸门是对支持它的服务器的补强。
- **把超限部分直接丢弃但加提示**：模型拿不到具体条目，只能自己去调 lsp 工具，回到 pull 链路「依赖模型主动性」的弱点。

## 拿什么证明它生效了

- 单测：`bun test ./packages/core/tests/lsp/ ./packages/core/tests/trace/lsp-diagnostics-digest.test.ts` → 165 pass / 0 fail；executeTools 相关的 agent/query/hook 测试 928 pass。
- 变异自证：11 处修复逐一改回旧行为（先限流后过滤 / 截断即丢 / pending 并集 / 无归属过滤 / 同步窗口 / 版本闸门 / 清理晚于 await / 基线 / 截断提示 / 埋点接线 / 999999 末尾），每处对应断言均变红（1–7 条 fail），恢复后全绿。
- 真实 typescript-language-server e2e（临时目录，15 个类型错误 + 1 个只读打开的有错文件）：只读文件 → 注入 null、peek 2 条；编辑后第 1 轮注入 10 行 + 「另有 20 条…补发」，第 2 轮补发 10 行；fire-and-forget 同步后立即 collect → null；子代理名下修复 → 主循环 null、子代理 outcome=clean；事件流 5 条、字段与上述一致。
- 修复前基线（本机轨迹，raw.jsonl 解析）：60 个会话 352 次注入，单文件单次恰好 10 条占约 33%（17 个会话）；1 个人工核实的过时注入（会话 20261012-134748-9496c880 第 52 次请求）。修复后验收看 digest「LSP 诊断」一节：补发数 > 0 说明截断仍在发生但不再丢；stale_syncing / stale_version 是闸门拦下的过时推送数；`clean` 计数是「错误已修复」的直接信号。这些曲线要上线后的真实会话才有样本，本 PR 内无法给出。
