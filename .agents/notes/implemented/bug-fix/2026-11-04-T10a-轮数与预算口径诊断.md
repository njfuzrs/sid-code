# T10a：把「轮数」与「轨迹条目数」拆开，并证明预算熔断器从未被触及

## 决定了什么

**1. 三条离群题的 `num_turns` 不是主循环轮次，是 `session.traj` 的 `total_steps`。**

T0010 / T0051 / T0059 的 `num_turns` 是 370 / 342 / 436，跑批时 `--max-turns=120`。
缺陷文档（traj #4 / B2）据此写成「`max_turns` 这个旋钮实际没生效」。本次诊断推翻那个读法：

- 适配器 `populate_context_post_run`（`evals/external-benchmarks/harbor/sid_code_agent.py`）
  在两个分支上给 `sid_num_turns` 赋**不同口径**的值：
  - 有 stream-json `result` 事件：`result["num_turns"]`（SDK `turnCount`，主循环 assistant 消息数）；
  - `result` 事件缺失（撞墙钟被 SIGKILL）：`traj["total_steps"]`（`trajectory.length`，轨迹条目数）。
- 而 `total_steps` 的构成是「每条 API pair 产生 1 条 assistant action step + 每条 tool_use
  一条 observation step」（`packages/core/src/trace/builder.ts`），**天然约等于 2 × API 调用次数**。
  实测比例：这三条 `num_turns / 工具调用数` = 1.99 / 2.04 / 2.00，其余 36 条 0.45–0.75。
- 可机械判定的判据是注解字段的存在性：兜底分支**不写**
  `sid_num_turns_without_model_interaction`。全批 39 条里只有 4 条为 `None` ——
  正是这 3 条 + T0009（agent 根本未启动），其余 34 条为 0/1。

**落地**：新增 `evals/external-benchmarks/harbor/diag-turn-accounting.py`（三档口径判定 +
成本闸门 + 无轨迹时的反推区间）与 `tests/eval/diag-turn-accounting-contract.test.ts`（L1 门禁）。

**2. `--max-budget-usd 1.8` 没触发，是因为全批最高成本只有 $1.1737。**

熔断器代码路径是通的（`queryLoop` 里 `quotaManager.check(...)` → `level === "exceeded"` →
`terminal: true`），但阈值高于整批分布的上界 35%，**结构上不可能触发**。
`n_budget_capped = 0` 是预期行为，不是「开关没接上」。这条把缺陷 4 里那句
「未被验证生效过」从一句观察变成了可复算的判定。

**3. 主循环轮次在入库产物里不可得 —— 不猜。**

要定论「`max_turns` 到底有没有在 120 轮停住」，必须读原始 trial 的
`sid-home/trajectories/sessions/*/session.traj` 的 `metadata.total_api_calls`。
`total_steps` 反推只能给区间（每轮工具数未知），区间不足以支撑结论。脚本有原始 run 目录时
才填那两列，没有时输出 `n/a` 并打印区间估计。

## 放弃了什么（以及为什么不选）

- **不直接改缺陷 4 的结论文字**：本次能证明的是「370/342/436 不是轮次」，
  不能证明「主循环没超 120 轮」。后者需要原始轨迹，而 1.9G 的 run 目录不在库里。
  把「口径串台」和「上限是否失效」写成两件事，交给 T10b 用原始轨迹收口。
- **不用 `total_steps / 2` 当主循环轮次**：它等于「每轮恰好 1 个工具调用」这个假设下的推算；
  三条的 `tool_calls` 只统计主日志（`agent/sid-code.jsonl`），子代理的工具调用不在里面，
  所以这个推算会系统性偏低。能用它做的只有「量级校验」，不能当结论。
- **不把脚本做成 `bun test` 的必经门禁之外的第二套判定**：脚本是被调用的工具，
  判据留在 TS 侧（`evals/CLAUDE.md` §4.1）。Python 侧的 `--self-test` 只是让门禁能验证
  「判据真的在守」，不替代 TS 断言。
- **不修改 `sid_code_agent.py`**：这次只诊断，不改适配器行为。T10b 才动。
  （改适配器会动到所有 Harbor 实验的产物口径，不该和诊断混在一个 PR。）

## 拿什么证明它生效了

```bash
# 1. 内置自检：15 条断言全绿，其中 2 条是变异自证
python3 evals/external-benchmarks/harbor/diag-turn-accounting.py --self-test
# → 15 个 ✅，0 个 ❌

# 2. TS 门禁 5/5 通过（含两条变异：改坏兜底分支必须红、合并三档常量必须红）
bun test ./tests/eval/diag-turn-accounting-contract.test.ts
# → 5 pass, 0 fail

# 3. 用真实入库产物跑出诊断表（本 PR 的结论来源）
python3 evals/external-benchmarks/harbor/diag-turn-accounting.py \
  --reports-dir ~/Code/person/agent-traj-bench/reports/t8-rerun --max-budget-usd 1.8
# → 三条被标为 session-traj-fallback；其余 36 条 stream-json-result
# → 全批最大 $1.1737 vs 阈值 $1.8，余量 34.8% ⇒ 结构上不可能触发
```
