# 检查点不再收非普通文件，且 `/undo` 不再被「没有可回滚目标」的快照永久卡死

## 决定了什么

改 `packages/core/src/checkpoint/manager.ts` 一个文件，两个方向：

**止新**：`createSnapshot` 的存在性判据从 `Bun.file(p).exists()` 换成
`lstatSync(p, { throwIfNoEntry: false })` 的三态判定（新增 `classifyPathForSnapshot`）：

| 判定 | 含义 | 处理 |
| --- | --- | --- |
| `absent` | 路径不存在 | 原语义：记 `existedBefore: false`（新建文件） |
| `regular` | 普通文件 | 原语义：读内容 → full / diff |
| `non-regular` | 目录 / 字符设备 / 块设备 / FIFO / socket / 软链 | **不进快照**，登记 `skippedFiles`（`reason: "non-regular"`） |

**兼容**：四个回滚入口（`undo` / `undoFile` / `restoreToSnapshot` /
`restoreBeforeSnapshot`）的「删除新建文件」分支一律先判类型，`non-regular` 跳过，
既不计成功也不计失败。`undo` 的判定从「`results` 为空 ⇒ 失败」收紧为
「`results` 为空 **且** `failedFiles` 非空 ⇒ 失败」；两者都空（纯噪音快照）时
**消耗掉并继续撤上一个**。`rebuildContentBeforeSnapshot` 返回 null 从静默跳过改为计入
`failedFiles`——否则「diff 链断了」会被新判据误当成「没有可回滚目标」而消耗掉快照。

`Snapshot.skippedFiles` 新增可选 `reason` 字段，**缺省即 `too-large`**：已落盘的老分片
不需要迁移就仍然语义正确，老断言（`toEqual([{ filePath, bytes }])`）也不用改。

## 放弃了什么（以及为什么不选）

- **放弃「只修 `undo`、不动 `createSnapshot`」**。看起来更小，但历史数据是持续产生的：
  光修消费侧，每个 `2>/dev/null` 的新命令还在源源不断造纯噪音快照。
  不过这也确实意味着**盘上的 18 个会话 / 2,009 条历史条目不会消失**——
  所以消费侧的跳过逻辑不是可选项，是配套必需品。两半缺一都不成立。

- **放弃「靠 errno 分支跳过」（catch EPERM/EISDIR/ENOTEMPTY 再判）**。
  三个平台的错误码不一致：目录在 macOS 是 `EPERM`、在 Linux 是 `EISDIR`/`ENOTEMPTY`，
  `NUL` 在 Windows 上另有形态。靠 catch 一定会漏，且漏掉的形态是静默的。
  **必须在动手删除之前用类型判断**，不能靠失败反推。

- **放弃「纯噪音快照消耗一个就返回 null」**（方案文档 §6.3 留的二选一）。
  盘上实测同一会话尾部连续不可回退快照**最深 10 个**，一次只消耗一个 =
  用户要连敲 10 次 `/undo` 才能退出陷阱。选了「循环跳过」：
  每次迭代要么 return、要么 `removeLastSnapshot`（快照数严格递减），
  最多迭代「快照总数」次，终止性不依赖任何计数上限。

- **放弃「软链按普通文件处理」**（即修复前的事实行为）。`Bun.file(link).exists()` 返回
  `true`（跟随 target），于是软链被当成普通文件收进快照；回退时 `Bun.write(linkPath)`
  会**写穿链接改坏 target**。lstat 让软链落进 `non-regular`，顺带把这个坑一起填了。
  代价是**行为变更**：软链不再被快照保护——已在测试里单列并写明理由。

- **放弃「逐文件 try 包住 stat/读」（方案文档 §7.2 的独立决策）**。
  外层 catch 导致整批丢失是另一个缺陷，但它与本缺陷的判据不同（一个是「不知道类型」，
  一个是「读失败怎么记账」），塞进同一个 PR 会让 review 分不清哪条改动在修什么。
  本次只在 `classifyPathForSnapshot` 处保证「类型未知」不会抛。

## 拿什么证明它生效了

新增 `packages/core/tests/checkpoint/p4-non-regular-file.test.ts`（11 个用例）：

```
$ bun test ./packages/core/tests/checkpoint/p4-non-regular-file.test.ts
 11 pass  0 fail  36 expect() calls
$ bun test ./packages/core/tests/checkpoint/
 122 pass  0 fail  316 expect() calls   ← 111 既有 + 11 新增，零回归
```

**变异自证 5/5 全部被抓住**（脚本逐条改坏 → 跑测试 → 恢复）：

| 变异 | 结果 |
| --- | --- |
| M1 类型判据退回 `existsSync(p)` 二态 | 6 条红 |
| M2 N5 判据退回「results 为空即失败」 | 2 条红 |
| M3 去掉「纯噪音快照继续上一个」的循环 | 1 条红 |
| M4 `restoreToSnapshot` 退回修复前的 `existsSync` + unlink | 1 条红（`failedFiles` 非空） |
| M5 「重建不出内容」退回静默跳过 | 1 条红（N5 回归） |

**变异过程中抓到两条自己写错的测试，说明了这一步为什么不能省**：

1. `restoreToSnapshot` 那条用例最初把坏条目放在**目标快照自己**身上 ——
   回滚区间为空、循环根本不进，**恒绿**。改成「目标 s1 + 区间里 s2 含 `/dev/null`」后才真红。
2. N5 回归用例最初用 `existedBefore: true` + `full` + 空内容构造「重建失败」，
   实际会重建出空字符串、走 `restored` 分支而不是 `null`。改成 `type: "diff"`
   且无 full 基点（`baseSnapshotIndex === -1`）才是真失败。

**另外锁了一条"前提"断言**：`Bun.file().exists()` 对目录 / `/dev/null` 返回 `false`、
对软链返回 `true`（本机 bun 1.4.2 实测）。这条断言值在于——哪天 Bun 改了语义，
它先红，而不是让人从「快照又不收目录了」这种远端现象往回猜。
