# PR11 的停止归因补齐到失败出口，并把「空参数耗尽」纳入统一收尾

## 决定了什么

两处行为改动 + 两处测试补强，都围绕同一件事：**非正常出口的结论与原因，必须无差别地到达父代理**。

1. **失败出口也带停止原因**（`task/agent-task.ts`、`agent/sub-agent.ts`）
   - `failAgentTask` 新增第 4 个可选参数 `stopAction?: string`，在通知 summary 上拼
     `describeStopNotice()`，与 `completeAgentTask` 共用同一个来源。
   - `sub-agent.ts` 的失败分支把 `result.stopAttribution?.stop_action` 传下去。
   - 此前只有成功通道拼了停止原因。于是「循环恢复耗尽」「窗口耗尽后总结也失败」
     这类 `success: false` 的出口，父代理只能读到「执行失败: 工具循环恢复次数耗尽」，
     **分不清「子代理做不出来」与「被上限/窗口截断」**——后者接手接着做还有价值，
     前者重派也是白花。这个区分正是 PR11 的初衷，只是在失败出口断了。
   - `stopAction` 缺省（旧调用方、顶层异常兜底）时 summary 完全不变，不产生额外附注。

2. **`empty_param_exhausted` 出口纳入统一收尾**（`agent/agentic-loop.ts`）
   - 新增 `EMPTY_PARAM_FINALIZE_PROMPT`，该出口在 `onTurnEnd` 之后、`return` 之前
     调用 `runFinalizeTurn`（`signal.aborted` 时跳过，与预算出口同口径）。
   - 这是此前**唯一一条 `success: true` 却不跑收尾轮**的非正常出口。走到它的前提是
     模型连续 `MAX_EMPTY_PARAM_RETRIES` 次发空参数 `tool_use`，最后一条 assistant 文本
     往往正是那句没说清参数的话；父代理却因为 `success: true` 把它当完整结论用。
   - 归因不变（仍是 `empty_param_exhausted`），`success` 语义不变（收尾轮失败不误报失败）。

3. **测试补强**（`tests/agent/pr11-stop-delivery-and-window-exit.test.ts`）
   - 残卷夹具从手搓 `SalvageSnapshot` 字面量改成**真实采集链路**
     （`SalvageCollector.recordTurn` → `snapshot()` → `buildSalvageOutput`）。
     上一版绕过采集器，等于把「采集器到底填不填 read-files / recent-calls」换成常量，
     而这一项的报障形态恰恰是「收集了却落不了盘」。
   - 新增失败出口归因 3 例（含对照组）+ `empty_param_exhausted` 收尾 2 例（含「收尾轮
     没产出文本时不误报失败」的对照组）。

## 放弃了什么（以及为什么不选）

- **不补 4 条 G2 冒烟用例**（PR2 一条、PR5 一条、PR11 两条）。`tests/smoke/cases/` 的
  `expect` 只能从**人工核过的真实轨迹**里抄，不许从实现或自己跑出的结果反推；
  自己造用例等于把「期望」写成「实现现在长什么样」，那样的门禁只会保护 bug。
  这四条留给维护者用真实轨迹补（方案文档 §8.3 的要求）。
- **不把停止原因塞进 `<error>` 通道**。`error` 是残卷正文（4000 字上限 + 超长截断指针），
  往里拼一行元信息会污染「正文 = 可用成果」这个契约；summary 是它唯一该待的地方。
- **不改 `empty_param_exhausted` 的 `success` 语义**。收尾轮拿不到文本时仍返回
  `success: true` —— 这条出口的定位是「如实呈现退化」，把它改成失败会让原本能用的
  半份结论在父代理侧被当异常处理。多花的一轮只为提高产出质量，不为改变判定。
- **不动 PR2（max_tokens 恢复）的测试缺口**。它是另一个模块、另一个关注点，
  按「一个 PR = 一次 review 完」应该单开。
- **不动 `stop-notice.ts` 的兜底分支**（仍会露出英文枚举名）。补文案要逐个确认
  该 `stop_action` 的语义，属于独立的小 PR，不和本改动混在一起。

## 拿什么证明它生效了

- `bun test ./packages/core/tests/agent/pr11-stop-delivery-and-window-exit.test.ts`
  → **16 pass / 0 fail / 47 expect()**。
- **三次变异自证**（逐个改坏 → 跑 → 恢复）：
  1. 删掉 `failAgentTask` 的 `stopNotice` 拼装 → 1 fail（失败出口归因用例红）。
  2. 把失败分支改回 3 参数调用 → **第一次跑出 16 pass / 0 fail**。
     原因是哨兵写成 `toContain("result.stopAttribution?.stop_action,")`，
     而同一文件的成功分支有同一段字面量，纯子串断言被它满足了 —— 一个**恒绿的哨兵**。
     改成锚定调用序列的正则（`failAgentTask(\s*taskId,\s*result.output,\s*notify,\s*result.stopAttribution?.stop_action,`）
     后重跑变异 → 1 fail，恢复 → 绿。
  3. 把 `empty_param` 出口的 `runFinalizeTurn` 短路（`false && !signal.aborted`）
     → 2 fail（两条 empty_param 用例都红，其中一条断言 `calls.length === 5`）。
- 变异落点每次都用 `grep -n MUTATION` 确认并恢复；恢复后重跑全绿。
- `bun run format:check` / `bun run lint` / `bun run typecheck:gate` / `make build`
  与 `bun run affected-tests:run` 的结果记录在 PR 正文。
