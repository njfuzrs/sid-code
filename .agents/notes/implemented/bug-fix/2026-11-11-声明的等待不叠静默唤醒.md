# 声明了等待的后台 shell 不再收到「已静默、不会再自动回报」

## 决定了什么

静默唤醒器与「值得等」闸门用同一个判据对齐：**自己会回报**的后台 shell 不叠静默唤醒。

事故 20261109-191904-962011a6 的形状是两套口径打架，不是哪一句话写错了：

- `isAwaitedBackgroundTask`（闸门）把两类 shell 判成「值得等」——它们退出 / 到期时必有通知，
  不看静默时长：① 输出按结构憋到退出（`outputBufferedUntilExit`，如 `gh pr checks … | tail -30`）；
  ② 显式声明了期限（`wait_until_seconds` → 等待登记表里的 `deadline`）。
- `endMainLoopTurn` 于是把它们登记进 `pendingWakeIds`；
- 60s 后 `takeQuiescentWake`（唤醒器）只看静默时长，放一条「已静默、不会再自动回报」。

模型 1 分钟前刚被告知「期间不按静默判定」，随后又被告知「不会再自动回报」，只能自己前台去查：
11:49:32–11:53:33 连查 32 次、8.45M 输入 token。

改动（`packages/core/src/task/background-await.ts`）：

1. 新增 `reportsOnItsOwn(task)`：憋输出 / 有 `deadline` 登记 → 自己会回报；
2. `endMainLoopTurn` 登记时跳过这类任务（对应原方案 §5.2「`wait_until` 不进 `pendingWakeIds`」）；
3. `takeQuiescentWake` **再判一次**并短路（硬判据）。`wait_until` 的登记发生在 `bash` 工具执行链里，
   主循环收尾在 `queryLoop` 的 finally，「先起命令后收尾」通常成立但没有机制保证，
   只靠登记时排除会在顺序变化后静默失效。

`deadline` 的判定由 `wait-registry.ts` 注入（`setDeadlineWaitPredicate`），
不让 `background-await` 直接 import 它：后者已经反向依赖 `isAwaitedBackgroundTask`
（登记表的派生分支要逐字复用那个口径），直接 import 会成环。

`describeQuiescentWake` 的文案**没改**：对真正的常驻服务（静默且永不退出）它是对的。
改文案去兼容声明等待的场景，会把「常驻服务仍需要这条唤醒」这个事实藏起来。

顺带修了 smoke 运行器的一处实现缺口：非 TUI 分支此前只认运行器缺省的 60s 超时，
忽略了 `SmokeCase.timeoutMs`（类型定义里它是通用字段）。N4 的判据以 60s 静默阈值为被测对象，
用例必须跑 70s，否则会被缺省超时先杀掉。

## 放弃了什么（以及为什么不选）

1. **改静默通知文案**（如「若你声明了等待请忽略本条」）——不选。模型看到的仍是自相矛盾的两句，
   而且把「我有没有声明过」交给模型判断，比在 harness 侧判更不确定。判据应该在产生通知的地方。
2. **只改 `endMainLoopTurn`（照原方案 §5.2 的字面）**——不选，理由见上一节的第 3 点。
   实测代价要如实记：删掉 `endMainLoopTurn` 那行排除，13 条单测**全绿**（被 `takeQuiescentWake` 兜住），
   即它没有独立的回归守卫。这是有意接受的结构：行为判据只有一处（唤醒器），
   另一处只是省掉一次无谓登记，两处共用同一个 `reportsOnItsOwn`，不会漂移。
3. **把静默阈值调大，或给 `wait_until` shell 单独挂一个「静默定时器」**——不选。
   前者只是把矛盾推迟 60s；后者是在已有的 `wait_until` 到期定时器之外再造一个时钟。
4. **改 `isAwaitedBackgroundTask`（闸门侧）返回 false**——不选。它对这两类返回 true 是**对的**：
   它们确实值得等（退出 / 到期必有通知）。问题在唤醒器没跟上这个口径，不是闸门判错。

## 拿什么证明它生效了

**G1 单测**（`packages/core/tests/task/background-await.test.ts`，13 pass / 0 fail，37 个 expect）：

- 输出憋到退出（`gh pr checks 701 --watch 2>&1 | tail -30`）静默 65s → `takeQuiescentWake === false`，
  同时 `isAwaitedBackgroundTask === true`（闸门口径不变）；
- `wait_until` 登记 + `until …; do sleep 30; done` 静默 65s → `false`；
- **顺序守卫**：收尾之后才登记 `deadline` → 仍为 `false`（这条专门守 `takeQuiescentWake` 的短路）；
- **反例**：`bun run server.ts`（无期限、无憋输出）静默 65s → `true`，20261103 事故的修复不回退；
- **真实入口**：`spawnShellTask("sleep 70 | tail -1")` + 真实看门狗 tick + 真实消息队列，
  把「最后有输出」拨回阈值之前，等 7s 后 `drainByKind("task-notification")` 里 0 条含
  「不会再自动回报」，且任务仍 `running`（不是提前退出造成的假绿）。
