# 请求的 max_tokens 改为「按需预留」：物理输出上限不再当每次请求的预算

## 决定了什么

**把 `maxOutputTokens`（物理上限，属性）与请求的 `max_tokens`（预算，决策）拆成两个概念。**
旧实现把注册表里的物理上限（DeepSeek 384k）原样当每次请求的 `max_tokens` 发出；而 DeepSeek / GLM
等 OpenAI 兼容协议族按「输入 + max_tokens ≤ 窗口」校验，输入超过约 664k（= 1,048,576 − 384,000）
就被 400 拒绝 —— 为一次也没用到的 384k 输出让出了 37% 的输入空间（方案文档 F1，§7.1 已用直连请求
把边界验到 ±50 token）。

新增 `packages/core/src/llm/output-budget.ts`：纯函数 `resolveRequestOutputBudget()`，主循环发送前、
收尾总结轮、fallback 的 max_tokens 溢出恢复共用同一实现。

```text
desired = max(请求预算, thinkingBudget + 8K 正文余量)   // 思考预算是下限
desired = min(desired, 物理上限)                        // availableModels > 能力目录 > 注册表
desired = min(desired, 窗口 − 输入估算 − 1K 安全余量)    // 保证「输入 + max_tokens ≤ 窗口」
窗口剩余 < floor → 不发请求（结构化返回，交给压缩 / 报错）
窗口钳制生效时同步下调 thinkingBudget（保证 budget_tokens < max_tokens）
```

关键取舍与配套改动：

- **默认请求预算取 32,768**：与 `defaultConfig()` 原有兜底值收敛成同一个数，不引入新魔法数。
  依据是全族实测 p99.9 均低于它（DeepSeek 10,995 / Claude 5,129 / GLM 19,616 / GPT 14,737 /
  Kimi 2,100），超过 32k 的请求只占 0.005%（2/41,961），`stop_reason=length` 全族 0 次（V1-3 已通过）。
- **`config.maxTokens` 语义改为「请求预算」**：用户未显式配置时用默认 32,768，不再按模型注册表推导；
  物理上限只用来钳制。`availableModels[].maxOutputTokens` 属于物理上限，**不进预算**——否则
  「用户配了渠道上限 384k」会重新变成「每次请求发 384k」，F1 原样复发。
- **Stage 1 截断升档**（复用已有机制）：`stop_reason=max_tokens/length` 时把上限抬到
  `min(物理上限, 窗口 − 输入 − 余量)` 重试一次。旧实现因为默认值就是物理上限，`currentCeiling < modelMax`
  永不成立，这段代码从未在生产触发过。
- **修 Stage 1 升档不复位的缺陷**：`LoopState` 每条用户消息重建但不初始化 override，原来升档后会跨
  整条消息存活。默认预算降到 32k 之后这个缺陷会显形（一次截断后所有轮次都以物理上限发出）。
  复位放在 `stopAction` 分类之后、**所有 continue 分支之前**——工具轮在 6500 行就 continue 了，
  放在后面永远轮不到（这个位置是被回归测试逼出来的，见下）。
- **计数器拆分**：`maxTokensEscalateCount`（Stage 1 门禁，升档成功后归零）与
  `maxTokensContinuationCount`（Stage 2 续写次数，只增不减，续写提示里展示给模型）。
  旧的单一计数同时承担两件事，归零会把展示值一起重置。
- **floor 与安全余量从 `fallback.ts` 抽到 `output-budget.ts` 共用**：发送前的窗口下界检查与
  溢出后的恢复问的是同一个问题（「窗口里还剩不剩得下这么多输出」），各写一份必然漂移。
  `SID_RECOVERY_FLOOR_TOKENS` 因此同时影响两条路径，刻意如此。
- **注册表 6 条在役 DeepSeek 条目改官方精确值** 1,048,576 / 393,216（原 1,000,000 / 384,000 是取整口径）。
  `deepseek-chat` / `deepseek-reasoner` 两条**停用**条目刻意不改：停用后不再发请求，窗口值不参与成本
  （只有 pricing 参与），在没有数据支撑前不臆测改动。
- **`raw.jsonl` 补 `max_tokens`**（`request_sent` 预写行 + 完整 request 记录）：V1-1 的取数源。
  修复前只能从 `debug.log` 抽查，6 条样本不够做验收。
- **不再扩充 `parseMaxTokensOverflowError` 的文案匹配**：新预算逻辑下「输入 + max_tokens 超窗」
  不该再出现；如果出现，说明输入本身逼近窗口，按 `prompt_too_long` 处理是对的。在下游补文案是打补丁。

F8（`ContextManager` 的输出预留改传请求预算）**不在本 PR**：它改的是压缩缓冲，与「请求发多少」
不是同一个关注点，且只影响主会话的 emergency 档触发点。方案文档把它与 F1 同列 PR-1，本次按用户
指定的范围只做 §5.1（F1）。

## 放弃了什么（以及为什么不选）

| 被放弃的方案 | 为什么不选 |
|---|---|
| 只把 DeepSeek 注册表的 `maxOutputTokens` 改小（如 64k） | 注册表要描述事实，384k 是官方公布的上限。改小等于让注册表说谎，换模型照样复发。属于折中 |
| 保持发物理上限，给 DeepSeek 单独加「输入 + max_tokens」钳制 | 按模型名分支，违反方案 §4 原则 5；而且 GLM / Qwen 文档写明同样的约束，Anthropic 旧模型同样有，问题是协议族通用的 |
| 扩充 `parseMaxTokensOverflowError`，让无数字报错也走 max_tokens 溢出恢复 | 每次撞墙都先浪费一次请求再恢复，并依赖网关文案。只能缓解，不能消除 |
| 默认预算按窗口比例（窗口 × 5%） | 1M 窗口得 50k、128k 窗口得 6.4k，后者会让小窗口模型频繁截断。输出需求与窗口大小无关，与任务形态有关 |
| 默认不发 `max_tokens`，交给服务端默认值 | Anthropic Messages API 该字段必填；各家默认值不一致且会变；依赖服务端默认值等于把预算决策交给网关，窗口钳制失去依据 |
| 升档后不回落（保持物理上限） | 一次截断就把整条用户消息的预算永久抬高，F1 原样复发。回落是刻意的，代价是「升档 → 成功 → 回落 → 再截断」可能多一轮，实测超过 32k 的请求只有 2 次 |
| 升档目标直接取 `modelMax` | 物理上限在窗口只剩 200k 时不能直接发，否则把「一次截断」换成「一次必然 400」。必须再过一次窗口钳制 |
| 窗口钳制只钳 `max_tokens`、不动 `thinkingBudget` | `budget_tokens < max_tokens` 是 Anthropic 硬约束，只钳一边会让「旧 Claude + max 档」必然 400 |
| 未知模型（三层上限全 miss）时升档到窗口剩余 | 抬到一个未知上限只会制造 400，交给 Stage 2 续写更安全 |
| 停用的 `deepseek-chat` / `deepseek-reasoner` 一并改精确值 | 停用后不再发请求，窗口值不参与成本；它们属于 V3 族，官方窗口未必是 1M，顺手改等于在没有数据支撑时臆测 |

## 拿什么证明它生效了

- 新增 `packages/core/tests/llm/output-budget.test.ts`：11 个用例覆盖方案 §6.1 的 7 条
  （默认 32,768 / 物理上限钳制 / 窗口钳制 / 用户显式值受窗口约束 / 思考预算下限 / 窗口不足时同步下调
  `thinkingBudget` / 窗口剩余低于 floor 时拒绝发请求），另加「非法预算回落」「env 覆盖 floor」。
- 新增 Stage 1 复位回归（`tests/query/loop-transitions.test.ts` 两个用例）：
  截断 → 升档到 128,000 → 工具轮成功复位 → 再次截断仍先升档，四次请求的 `max_tokens`
  实测为 `[8000, 128000, 8000, 128000]`；第二个用例断言升档后仍截断时直接进 Stage 2，
  续写提示显示「自动续写 1 次」（未被 Stage 1 门禁计数污染）。
- **变异自证 1**：把 `output-budget.ts` 的 `if (windowLimitTokens < floorTokens)` 改成 `if (false && ...)`，
  3 个用例立刻变红：
  ```
  (fail) ⑦ 窗口剩余低于 floor → 返回拒绝发请求（不是 0 / 负数）
  (fail) ⑦b 输入估算本身超过窗口 → 同样拒绝，不产生负数 max_tokens
  (fail) floor 可经 SID_RECOVERY_FLOOR_TOKENS 覆盖（与溢出恢复共用同一常量）
  ```
  还原后 11 pass。
- **变异自证 2**：把 `loop.ts` 的升档复位条件改成 `if (false)`，复位回归立刻变红：
  ```
  (fail) Stage 1 升档成功后复位：下一次截断仍先走 Stage 1，默认预算不被永久抬高
  ```
  还原后 6 pass / 0 fail。
- `bun run affected-tests:run`：**5897 pass / 4 filtered / 0 fail**（420 文件）。
  其中 9 处失败是注册表精确值变更后的过期期望（`1_000_000` → `1_048_576`、`384_000` → `393_216`、
  `900_000` → `943_718`）与出口哨兵计数（7 → 8，新增「预算不足先压缩」出口，按门禁约定补清单）。
  全部在测试侧修正，没有为了凑绿改被测实现。
- `bun run typecheck:gate`：62 处 / 基线 64 处，**无新增**。
- `make build` 成功（产物自检通过）；`bun run smoke` **26/26 通过**（含 A6-compact、A7-budget-exceeded）。
- `bun run lint` / `format:check` / `lint:boundary` / `lint:command-system` / `lint:legacy-tool` 全绿。
- `bun run docs:gen-reference` 已重新生成（`website/ref/settings.md` 随本次提交）。
- 端到端验收（V1-1：真实会话的 `raw.jsonl` 里 `max_tokens` 为默认预算且满足「输入 + max_tokens ≤ 窗口」）
  见 PR 描述。
