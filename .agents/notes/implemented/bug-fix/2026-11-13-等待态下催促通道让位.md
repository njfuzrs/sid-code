# 已声明显式等待且无新进展时，催促通道让位（R5）

## 决定了什么

todo 通道与 work-log 通道的注入判据各加一条让路条件：**纯等待态**下不注入催促。

判据落在新文件 `packages/core/src/query/wait-only-state.ts` 的 `isWaitingOnlyState()`，
三条同时成立才算等待态：

1. 有未完成项（`countUnfinished`，不含 blocked）；
2. 有**显式声明的外部等待**（`isDeclaredExternalWait`：monitor / 唤醒 / 带
   `wait_until_seconds` 的 shell deadline），派生任务不算；
3. 未完成项数 **≤** 有效显式等待数（用 ≤ 而非 ==：一次 CI 等待可以同时兑现
   「等 CI 过」与「等 PR 合并」）。

外加一条让路条件：**上一次 `todo_write` 之后有新的副作用进展**时不算等待态
（「一边等 CI 一边改别的文件」的场景，催它记账是对的）。

为此 `measured-progress.ts` 新增 `revision` 单调计数（落盘副作用 +1、观测值变化 +1）
与 `PROGRESS_REVISION_AT_TODO_WRITE_KEY` 基线；用增量而不是 `hasRealProgress` 的
会话级累积 —— 最常见形态是「改完代码（文件早已落盘）→ 起等待」，拿累积量判会让这个
场景永远命中不了，整条修法失效。

让位的形态不是静音：

- todo 通道改注入一次**现有的**等待态说明（`buildTodoWaitSourcesMessage`，含等待源与
  最晚回报时刻），仍受原有 `throttleSaysYes` 节流管辖；
- `afterCompact` 旁路**保留**（压缩把清单从上下文里抹掉了，不重注模型就永久看不到），
  但 `buildTodoReminder` 新增 `waitingSources` 选项，把「请继续推进」那句换成
  「当前都在等外部状态：…」；
- 两条通道共用 `waitNoticeInjected` 标志，保证同一轮只注入一次；
- 被压掉时落 `NoProgressNagInjected` 且 `suppressed_by_wait: true`，不注入也可数。

`trace/digest.ts` 的 `aggregateTodoStats` 同步把这些事件从 `reminders` 里排除，
另计 `suppressedByWait` —— 否则「回注次数」曲线会被自己抬高，而它正是本改动最需要
可观测的那个数。

## 放弃了什么（以及为什么不选）

- **只在 todo 通道让位、work-log 照常发**：两条通道文案高度重叠（同一份清单派生），
  等待期间一起催就是同一件事复述两遍；只压一条的话告警仍然打断等待。
- **用 `hasRealProgress` 的会话级累积当「有没有新进展」**：会让最常见形态永不让位，
  等于整条修法失效（见上文）。必须相对 `todo_write` 取增量。
- **用 `hasPromisedWait`（宽判据）而不是 `isDeclaredExternalWait`**：派生出来的子代理 /
  普通后台 shell 承诺的是「自己结束时回报」，不构成「清单在等外部状态」的证据；
  宽判据会把「跑着一个后台命令、清单还有 3 项没做」也判成等待态，整体压掉催促。
- **未完成项数必须 == 等待数**：一个等待兑现多项是常见形态，要求严格相等会漏掉它。
- **等待态下完全静音（两通道都不注入、也不注入等待说明）**：模型不知道 harness
  已经知道它在等，仍会原地查询状态（P1 守卫要拦的同一件事）。所以要让位而不是静音。
- **等待态说明每轮注入**：文案逐字节不变、每轮注入 = `reminder-throttle.ts` 顶部记录的
  「弱模型误判成幻影用户消息」形态，沿用原有节流。
- **改 `afterCompact` 的中止条件**：那是「压缩把清单抹掉了」的信息丢失兜底，不重注模型
  永久看不到清单；只让文案让位。
- **新增 G2 冒烟用例 / 改已有用例的期望**：现有 R2/N4 用例的 `mutations` 指向
  `wait-admission.ts` / `background-await.ts`，本次未动这两处；而改已有用例的 `expect`
  需要人工加 `expect-reviewed` 标签（agent 不得自加）。故本改动的回归由 G1 守
  （判定边界 5 条 + queryLoop 接线 4 条）。

## 拿什么证明它生效了

- `bun test ./packages/core/tests/query/wait-only-state.test.ts` → **9 pass / 0 fail**
  （判定边界 5 条 + 接线 4 条：等待态不催且注入等待说明、等待释放后恢复催、
  2 项未完成+1 等待仍催、等待期间改文件仍催）。
- **变异自证**：把 `isWaitingOnlyState` 尾部改成 `return false`，同一文件跑出
  **3 fail**（两条判定边界 + 一条 queryLoop 接线，红在「等待态下不该出现请继续推进」）；
  恢复后重跑 **9 pass**。证明接线测试不是靠纯函数恒真。
- `bun run affected-tests:run` → **2906 pass / 0 fail**（239 files，含
  `packages/core/tests/query|task|trace/`；其中 trace 侧覆盖 `aggregateTodoStats` 的改动）。
- `make build` → 编译 + 产物自检通过（`sc-dev` 未报 `will always be undefined`）。
- `bun run smoke` → **28 例全通过**（含 R2 `dup-wait-same-subject`、N4
  `quiescent-declared-wait` 两个等待相关回归用例，证明等待既有行为未被破坏）。
- `bun run typecheck:gate` → 62/62，无新增；`bun run lint` / `format:check` /
  `lint:boundary` / `lint:command-system` / `lint:legacy-tool` 全绿。
