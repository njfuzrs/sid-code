## 决定了什么

**D19 无头形态的等待语义复用「有没有注入通道」这一个事实。**
`wait-registry` 新增只读 getter `isWakeupRegistrationEnabled()`（不新增全局状态，
写入仍只有 `setWakeupRegistrationEnabled` 一处）；`MonitorTool.call` 在没有通道时
追加「当前宿主在监控结束前不会退出，请等到监控结束后再收尾」。文案不绑定
「无头」字样：stream-json 有注入通道、也会等到结束，用「当前宿主」覆盖两种形态。
`schedule_wakeup` 的描述删掉「典型用法：跑到 CI 过为止」，改为「等外部状态优先用
monitor；本工具用于到点做一件事或没有可流式观测的对象」，保留延迟钳制 / 单链替换 /
缓存 TTL 三段取舍。

**D20 事件聚合只改渲染，不动模型可见的结构化数据。**
`history-adapter` 对同一消息内、`taskId` 相同且都带 `event` 的**相邻**通知合成一项
（`event` 换行拼接 + `eventCount: N`）；`TaskNotificationMessage` 在 `eventCount > 1`
时把摘要行渲染成 `<description> · N 条事件`、事件正文**全部**逐行进 `⎿`。
终态通知（无 `event`）不参与聚合，必须独立成项——「事件 → 终态 → 事件」的先后
顺序不能被重排吞掉终态；不同 `taskId` 不聚合。`_meta.notif` 一条不动。

**L4 的四条缺口各自补在真实入口上。**
T-T1-8 用「3 monitor + 1 唤醒 + 2 shell + 3 终态」构造视口截断，断言整行摘要
**等值**于 `⎿ 后台：2 shell · 3 监控 · 1 唤醒`（只断言「含」会漏掉少一个计数）；
T-M1-24 从 `messagesToHistoryItems` 产出真实 `HistoryItem` 再渲染，覆盖聚合、
不同 monitor、事件+终态混合、旧会话单对象、重建一致五条；
T-M1-17 从 `parseSessionJsonl` 解析落盘会话（`--resume` 同一条路径）再渲染，
并断言 `listWaits()` 为空、`hasPromisedWait()` 为 false——恢复历史不会凭旧通知
重建等待源；MUT-9 补一条从 `enqueueTaskNotification` → `injectPendingNotifications`
→ adapter → 渲染的真实链路用例（见「拿什么证明」）。

## 放弃了什么（以及为什么不选）

- **不在 `history-adapter` 里跨消息聚合。** 只聚合同一条消息内相邻的事件：
  跨消息会把不同回合的事件并成一项，历史区里的时间顺序（以及夹在中间的用户消息）
  就没了。D20 的症状是「一次注入刷 3 行」，同消息聚合已经消掉。
- **不按 `event` 内容去重，也不只保留计数。** 方案要求「三行事件都在」——
  事件正文是模型/用户判断过滤条件是否写对的依据，去重或只留计数等于把它藏起来。
- **不改 `_meta.notif` / XML 结构。** 聚合是纯展示口径：模型看到的通知条数、
  正文与改动前完全一致，回滚只需回滚渲染层。
- **不给 `MonitorTool` 加 headless 字段 / 全局标志。** `ToolUseContext` 没有
  headless 字段，加一个要动工具签名；「有没有 prompt 注入通道」已经是现成的、
  语义更准确的事实（`-p` 单轮无通道，交互式 / stream-json 有通道）。
- **不改 `config/system-prompt.ts` 里的「跑到 CI 过为止」。** D19 的修复面明确
  只点名 `tool/schedule-wakeup.ts` 的描述；系统提示里那段是调度能力的总述，
  同一批里还有 `/loop` 的历史文案，一起改会把「工具描述」这层改动放大成
  跨模块文案重写，留给单独一次。
- **不给 T-T1-8 新造渲染路径。** 直接复用 `TodoPanel` 的窄终端折叠测试文件，
  只把断言从「含」收紧为「等值」——缺陷本身就出在这条既有路径上。
