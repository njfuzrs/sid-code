# Skill 动态发现补上项目扩展信任 / 企业策略门；禁用名单由 SkillManager 持有并覆盖晚到 skill 与 bundled 模型工具

## 决定了什么

三个缺陷一起修，都在「Skill 能不能被模型拿到」这一个关注点上：

- **B1 动态发现绕过信任门**：`SkillActivationCoordinator` 的动态发现原先直接调
  `ExtensionLoader.scanSingleDir`，不走信任过滤和企业面锁定。实测启动时被信任门拒掉的
  **cwd 根目录**项目 skill，模型读一下仓库里任意文件就会被重新加载进 listing（不只是嵌套目录：
  `discoverSkillDirsForPaths` 向上找到 cwd 为止，而协调器的已发现集合不含启动扫描过的目录）。
  修法：`loader.ts` 把 `isSurfaceLocked` 和 `filterTrustedProjectFiles` 提成模块级函数，
  启动项目层与新增的 `scanDynamicProjectDir` 共用；协调器新增 `scanOptions` 入参，
  `cli.ts` 传入与启动扫描同一份 `scanOptions`。有文件被扣下的目录不登记为已发现，
  用户在 TUI 批准后再碰一次即可本会话加载。
- **B2 禁用名单不传播**：`SkillManager` 新增 `disabledNames` 持有当前名单，在
  `addSkillsWithPrecedence`（discover / 插件 / MCP / 动态 / reload 重放的唯一汇聚点）施加。
  `reload()` 不再需要快照对象的 disabled 位。
- **B3 bundled 模型工具不读禁用态**：`BundledSkillTool` 新增 `setDisabledQuery`、
  `isEnabled()` 和执行期 guard；`cli.ts` 注入 `skillManager.isNameDisabled`。
  bundled skill 不进 manager，所以查询按名字查名单，不依赖已加载对象。

## 放弃了什么（以及为什么不选）

- **动态发现直接禁掉 / 只扫非 cwd 目录**：会丢掉嵌套 skill 的合法用法（monorepo 子包自带 skill），
  而真问题是缺门不是多扫。
- **在协调器里预先把启动扫描过的目录塞进 `discoveredDirs`**：只能堵住 cwd 根目录这一种形态，
  嵌套目录照样绕过；门必须装在扫描入口上。
- **B3 在注册时过滤 `disabledSkills`**：只覆盖启动配置，运行时 `/skills disable` 后工具仍在，
  启用后也回不来。改为惰性查询 + isEnabled，registry 的 schema 过滤每轮生效。
- **被扣下的目录也登记为已发现（每目录只扫一次）**：省掉重复 readdir，但用户批准后本会话再也
  加载不到，只能重启。选择每次碰到都重扫一遍被拒目录（readdir + hash），换「批准即可用」。
  这是本次唯一的「更省」让步：成本只落在存在未信任 skill 的目录上。
