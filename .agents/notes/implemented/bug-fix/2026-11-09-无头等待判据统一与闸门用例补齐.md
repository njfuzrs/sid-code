# 无头等待判据统一到 hasPromisedWait，并补齐 T2 闸门的分支级用例（D11 + L4 的 T-W2-3/5/8）

## 决定了什么

**D11：stream-json 无头路径的「值得等」判据从 `hasAwaitedBackgroundTasks` 换成 `hasPromisedWait`。**

只改一处调用点（`packages/cli/src/app.ts` 的 `buildSDKDriver`）：

```ts
hasRunningBackgroundTasks: () => hasPromisedWait(),   // 原：hasAwaitedBackgroundTasks()
```

它决定 `runHeadlessStreaming` 在 stdin 关闭后是否为后台任务继续挂着。旧判据对 shell 要求
`shellSilentForMs < SHELL_QUIESCENT_MS`，而 `wait_until` 等 CI 时静默 60s 是常态 → 被判成
「没有值得等的任务」→ 进程收尾退出、后台 shell 随进程被带走（#674）。新判据是旧判据的**超集**：
派生分支逐字复用 `isAwaitedBackgroundTask`（静默常驻 shell 仍不算，20261103 事故的修复不回退），
额外认出显式声明了 deadline 承诺的等待源（`wait_until` / `monitor` / 已排的 `schedule_wakeup`）。
唤醒同样受益——它不在 task registry 里，旧判据完全看不见它。

同一件事的另外两条落地：

1. **源码级守卫**（`packages/cli/tests/sdk/wait-criteria-source-guard.test.ts`）：
   `packages/cli/src` 与 `packages/core/src/sdk` 下不得出现旧判据的调用；同时正向断言
   `app.ts` 注入的是 `hasPromisedWait()`，并断言白名单条目（`loop.ts` 的 `runningBg =
   hasAwaitedBackgroundTasks()`）仍然存在——它是 `EndTurnShape` 的事实字段，不是等待判据，
   删了就没法复算「当时为什么没拦」。
2. **真实入口用例**（`packages/core/tests/sdk/stream-json-wait-promise.test.ts`）：
   `runHeadlessStreaming` + 鸭子类型假 engine，`hasRunningBackgroundTasks` 接真实
   `hasPromisedWait`。两条：`wait_until` shell 静默 61s+ → stdin 关闭后循环**不退出**，
   shell 终态才退；已排唤醒同样不退出，到点注入后才退。两条都先断言「旧判据 false /
   新判据 true」，把 D11 的差异本身也锁进断言。

**L4 的 T-W2-3/5/8：提取 `makeGateHarness` 并补齐 T2 闸门的分支级用例。**

`packages/core/tests/query/gate-harness.ts` 从真实入口驱动 `queryLoop`（只 mock 模型层），
等待源用真实的 `registerTask` + `registerWait` 构造——`listWaits()` 是模块级单例，mock 掉它
等于把被测判据一起换掉。三条用例：

- **T-W2-3**：只有 `wait_until` shell（静默 61s+ 但声明了期限）→ 一轮即收尾，
  且 `TODO_GATE_BUDGET_KEY.retries` 保持 0（放行分支不消耗续命预算）；
- **T-W2-5**：有 monitor 但清单剩的是**不依赖它**的项 → 仍放行。这是方案 §10.1 明确接受的代价
  （harness 判不准「清单项与监控对象的相关性」），本条锁住行为，防止后来的人把它当 bug「修」掉；
- **T-W2-8**：放行后下一轮请求上下文含等待源 reminder（`WAIT_SOURCES_REMINDER_KEY` 被消费注入
  `sendParams.messages`）；等待源集合不变时第二次不再写入；`{kind:"system"}` 输出里不再出现
  旧瞬态状态条（那条只进 TUI、模型看不到，等于没写）。

## 放弃了什么（以及为什么不选）

1. **不改 `headless-runner.ts` 的订阅回调条件**（`if (bg.hasPending() || !bg.hasRunning()) notify()`）。
   方案 D11 修复第 2 条要求核对的两个信号源已覆盖：唤醒触发后经 `onInjectorReady` 的 `inject`
   自己 `notify()`；唤醒被撤销走 `Scheduler.removeTask` → `notifyTaskChanged()`。而「`releaseWait`
   本身不通知」这个真缺口已由 D4 在 `releaseTerminalWaits()` 里补上（`wait-registry.ts:272`，
   本次已回源码确认）。再在这里加一层是重复保险，且会改变等待循环的唤醒时序（每次任务变更都
   多一次重判），换不到新信息。

2. **不在 `runHeadlessStreaming` 内部 inline 判据**。判据是宿主 driver 注入的能力，测试必须从
   真实入口验「注入的是哪一条」——在 runner 里写死会让 `app.ts` 的接线重新变成不可测的私有细节
   （这正是 PR 1 漏掉 D11 的形态）。

3. **源码守卫只扫 `packages/cli/src` 与 `packages/core/src/sdk`，不扫全仓**。
   `wait-registry.ts` 自己要 import `isAwaitedBackgroundTask` 做派生分支（它就是旧判据的超集实现），
   全仓扫描会把它误判成调用点。范围按方案 §5.2 第 2 条写死，并留了「白名单条目仍存在」的反向断言。

4. **T-W2-5 不去「判相关性」**。方案 §10.1 已定：harness 判不准「清单剩余项是否依赖这个监控对象」，
   判错的代价是把真在等的工作推回前台空转（正是 7dd98bf5 的形态）。所以这一格是**接受**而非修复，
   测试锁的是「仍然放行」这个既定行为。

5. **不做 E2E-10 的 stream-json 版本**。方案 §七把 E2E 排在 FIX-1…8 全部合入之后，本 PR 交付的是
   单测级真实入口（`runHeadlessStreaming` + 假 engine），E2E 那一层留给 L5 统一做。

6. **取舍点破**：D11 是「更准」（无头等 CI 不再静默失败）换「更省」——一个声明了期限的等待源
   会让进程多挂到它回报为止（最多到 deadline + 30s 宽限）。这个代价是方案明确要的：
   旧行为的「省」是把用户的等待直接丢掉。

## 拿什么证明它生效了

**三组用例（格式化后复跑）：**

```text
bun test ./packages/cli/tests/sdk/wait-criteria-source-guard.test.ts \
         ./packages/core/tests/query/todo-gate-wait-sources.test.ts \
         ./packages/core/tests/sdk/stream-json-wait-promise.test.ts
→ 8 pass / 0 fail / 25 expect() calls
```

**变异自证（四组，逐条改坏 → 确认变红 → 恢复 → 回绿）：**

| 变异 | 改什么 | 结果 |
| --- | --- | --- |
| 1 | `app.ts` 判据回退 `hasAwaitedBackgroundTasks()` | 源码守卫 2 fail（offenders 列表 + 正向断言各 1）；恢复后 3 pass |
| 2 | 真实入口用例里 engine 的判据回退旧口径 | 两条真实入口用例 2 fail（`settledWithin(...)` 期望 false 实得 true——正是「提前退出」）；恢复后 2 pass |
| 3 | `loop.ts` 的 T2 判据 `promisedWaits > 0` 改回 `runningBg` | T-W2-3 fail（`llmCalls` 期望 1 实得 4 = 1 + `MAX_TODO_GATE_RETRIES`）；恢复后 3 pass |
| 4 | 删掉 `sessionState.set(WAIT_SOURCES_REMINDER_KEY, ...)` | T-W2-3 与 T-W2-8 各 fail（reminder 为 undefined）；恢复后 3 pass |

四组都观察到了**具体的失败断言**，不是只看退出码。
