# 唤醒已触发、在宿主队列里等注入时仍算等待源（D10 / #674）

## 决定了什么

给「唤醒（`schedule_wakeup`）」补上缺失的那一段生命周期：**fire 之后、注入之前，它仍是等待源。**

改两个文件、三处：

1. **`cron/scheduler.ts` 记触发时刻**：`fireTask()` 在调 `opts.onFire` **之前**，把
   `schedule_wakeup` 任务的触发时刻写进 `firedWakeupAt`，并开一个只读口 `getWakeupFiredAt(id)`。
   为什么放在调度器而不是等待登记表：`wait-registry.ts` 本来就反向依赖 `getScheduler()`，
   反向再 import 会形成顶层循环依赖。这个形状与既有的 `isSuperseded()` / `supersededIds`
   完全同构——「调度器记事实，等待表查询」，不新增第二种事实源。
   必须在 `onFire` **之前**记：宿主注入成功后立刻 `releaseWait(terminal)`，晚一步这条登记
   已经从表里消失，记了也无处可查。

2. **`task/wait-registry.ts` 的有效性判据**：`isExplicitWaitValid()` 对 `wakeup` 先看
   `wakeupFiredMono(entry)`；已触发就返回 true（只要没被 `invalidated` / `superseded`），
   不再要求 `getSessionTask()` 存在——触发那一下调度器就把任务删了，旧判据在这段窗口里
   必然返回 false，闸门据此判「没人会回来」并强推（9e3a681d 的形态）。
   未触发时仍按调度器的账判，`cron_delete` 删掉的唤醒照样立刻失效（旧行为不回退）。

3. **`sweepExpiredWaits()` 的注入兜底**：原来对 `wakeup` 无条件 `continue`（到期由调度器
   负责 fire，在这里判过期会把正常触发误报成违约）。现在拆成两种：
   - 未触发 → 仍然跳过；
   - 已触发、但 `DEADLINE_GRACE_MS`（30s）内既没被注入也没被丢弃 → 判注入路径失效，
     按 `deadline` 源的违约流程处理（`WaitReleased{expired,late}` + failed 通知叫醒主循环）。
   没有这条兜底，一个丢了的注入会让无头 / stream-json 的等待循环永远等一个不会来的回报
   （它们以 `hasPromisedWait()` 为准），进程不退出。
   同时补了两个前置判断：已 `invalidated` / 已 `superseded` 的 fired 唤醒按对应 reason
   释放，**不判违约**——那不是「注入路径坏了」，是「本来就不该注入」。

`WaitEntry` 新增 `firedMono?: number`，存单调时钟下的触发时刻（不是布尔标记）：兜底窗口要算
「触发后过了多久」，而判据统一用单调时钟是文件头的硬约定。墙钟 `firedAt` 用
`monoFromWallClock()` 换算，回拨时差值钳 0（视作刚刚触发，只会让兜底更晚、不会提前误判）。

## 放弃了什么（以及为什么不选）

- **只在 `WaitEntry` 加 `fired: boolean`，由调度器调 `markWaitFired(id)`**（方案文档的原始写法）：
  需要 `scheduler.ts` 反向 import `wait-registry.ts`，而后者已经 import 前者（`getScheduler`），
  顶层循环依赖在 bun 的模块图里能跑但会让初始化顺序变成隐式契约。改成「调度器记、等待表查」
  后没有新增依赖边，也与 `isSuperseded` 一致。代价是调度器里多一个 `Map`（一次会话几十条，
  可忽略）且**不清理**（同 `supersededIds` 的先例：删了会让注入前的判定落空）。
- **不查调度器、只靠 `invalidatedIds` 判有效**：无法区分「fire 了等注入」与「从未触发且
  被 cron_delete 删了」——后者必须立刻失效，否则用户删掉的唤醒会让闸门一直放行。
- **兜底窗口用 `deadlineMono`（fireAt）而不是 firedMono**：`fireOnce` 只在 `!isLoading()`
  时触发，实际触发可能比 `fireAt` 晚很久（每个 tick 一次检查，且会话忙时整轮跳过）。
  用 fireAt 起算会把「刚触发 1 秒」判成「已经过了 30 秒」，误报违约。
- **把兜底做成定时器**：`listWaits()` 落在收尾闸门、停滞阶梯、空闲等待这些热路径上，
  「只要主循环还在跑就一定会问」，放在查询入口即可，不必为每个源挂定时器（沿用既有设计）。

## 拿什么证明它生效了

**回归用例**（`packages/core/tests/task/wait-registry.test.ts` 新增
`describe("D10 唤醒已触发、待注入")`，5 条）：

```bash
bun test ./packages/core/tests/task/wait-registry.test.ts
# 27 pass / 0 fail / 97 expect() calls
```

- T-D10-1（R9 迁入）：**真实触发路径**——`addSessionTask` 时把 `fireAt` 设为过去，调私有
  `check()` 走 `fireOnce` → `fireTask`，断言触发后 `getSessionTask()` 已为 undefined 且
  `hasPromisedWait()` 仍为 true；注入（`releaseWait(terminal)`，与 `app.ts` 同一条路径）后为 false。
- T-D10-2：触发后不注入，推进单调时钟 `DEADLINE_GRACE_MS + 1` → 判违约、
  `WaitReleased{expired,late}`、`isWaitInvalidated` 为 true、failed 通知含「注入路径失效」。
- T-D10-3（与 D8 交互）：已 fired 的唤醒被 S2（`subject_terminal`）撤销 → 不再算等待源。
- T-D10-4：未触发的唤醒被 `cron_delete`（`removeTask`）删除后**立刻**失效（fired 分支不误放行）。
- T-D10-5：同 id 重新登记后，调度器里留着的**旧**触发记录不会把新唤醒当成「已在等注入」
  （判据按 `registeredAt` 过滤）。
