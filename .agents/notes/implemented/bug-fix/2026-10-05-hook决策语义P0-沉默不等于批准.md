# Hook 决策语义 P0：拒绝一票否决、沉默不等于批准、exit 2 一律阻塞、hook 类型单一事实源

## 决定了什么

修 9-27 Hook 缺陷文档里五条 🔴：H24 / H4 / H1 / H29 / H15。

- **H24**：新增 `hook/handler-types.ts` 作 hook 类型唯一事实源，settings Zod、`config/schema.ts`、
  registry 三处都从它派生。prompt / agent 型 hook 不再判非法。真正非法的类型在 Zod 里用
  `superRefine` 报到**整条 hook**上（path 为空），由 D10 的 `removeInvalidValues` 摘掉整条，
  而不是只摘 `type` 键——后者会让 `{type:"nonsense", command:"x"}` 按缺省 command 继续跑。
- **H1**：OR 合并按事件建子类（`createHookOutput`）判阻塞，`permissionDecision:"deny"` 不再漏判；
  阻塞成立时把浅合并后的 `permissionDecision` 钉回 deny，两条通道结论一致、与顺序无关。
- **H29**：BeforeModel / AfterModel 保留字段替换（llm_request / llm_response），
  但阻塞与 `continue:false` 改为一票否决。PreCompact、TeammateIdle 同样声明「可 block」却落在
  last-wins，一并进 OR。结构性测试遍历 `types.ts` 里注释写「可 block」的全部事件做断言。
- **H15**：`parseCommandOutput` 里 exit 2 一律阻塞，JSON 改不了；理由优先 JSON 的 reason，再 stderr；
  JSON 其余字段保留。
- **H4**：runner 的 exit 0 / exit 1 / prompt·agent 验证通过 / 执行失败**都不再写 `decision:"allow"`**，
  聚合器只有在某个 hook 显式放行时才写 allow；SDK 桥改用 `isApproveDecision()` + `permissionDecision:"allow"`。

## 放弃了什么（以及为什么不选）

- **H4 只改 SDK 桥、不动 runner**：桥里改成 `isApproveDecision()` 不够，因为 runner 本身把「没意见」
  写成了 `"allow"`，聚合器再把「无阻塞」写成 `"allow"`——消费方无法区分。缺陷文档 H4.7 点明
  根因是「缺少显式的沉默表示」，所以在生产方去掉这个值，下一个消费 `decision` 的模块不会踩第三次。
  代价：`finalOutput.decision` 在全员沉默时从 `"allow"` 变成 `undefined`；已 grep 全部消费点，
  只有 SDK 桥读 `decision === "allow"`，其余都只读 `isBlockingDecision()`。
- **H24 继续用 `z.enum`**：enum 的 issue 落在 `type` 字段上，D10 只会摘掉这一个键，留下一个
  当 command 运行的残缺条目——比整文件作废更隐蔽。
- **H29 把 BeforeModel/AfterModel 整个改走 OR**：会破坏「多个 hook 分别改 llm_request 不同字段都生效」，
  文档 H29.6 第 2 条明确要求保留。
- **顺手修 H2 / H3 / H16**：同文件同段代码，但不在本次指定范围。H2 在结构性测试里登记为
  `KNOWN_GAPS`，修它时删那一行即可。
