# spawn 协议字段 max_tokens 改名 context_window，子进程请求预算接入输出预算函数

## 决定了什么

**F7 第 2–4 条的三件事一起做，因为它们动的是同一份父子进程契约。**

1. **协议字段改名**：`ParentInitMessage.max_tokens` → `context_window`（`sub-agent-protocol.ts`）。
   它从引入起就是**上下文窗口**，却与发送侧的 `max_tokens`（本次请求的输出预算）同名，
   读代码的人分不清哪个是窗口、哪个是输出上限。
2. **兜底值统一**：`sub-agent.ts` 的两处 spawn 传参（`executeSpawned` 与自定义 agent 的
   spawn 分支）原本各自写死 `task.maxTokens ?? 50000`，现改为共用
   `this.resolveSubAgentWindow(task)` —— 与进程内路径同源：`task.maxTokens` 显式值 >
   registry 派生的主模型窗口 > 50,000。
3. **接入输出预算**：`headless.ts` 的 `maxTokens: 4096` 写死值改为调用
   `resolveHeadlessSendBudget()`，内部与主循环**同一个** `resolveRequestOutputBudget()`。
   新增协议字段 `max_output_tokens` 承载「模型物理输出上限」，由父进程按**实际生效的模型**
   （`sc?.model ?? task.model ?? this.model`）经新增的 `ProviderRegistry.getMaxOutputTokens(model?)`
   解析后随 init 传入。
4. **协议头部记录契约变更**，不保留旧名兼容：父子两端来自同一二进制，不存在版本错配。

配套的可测性改动：把「init 字段 → 预算」抽成导出的纯函数 `resolveHeadlessSendBudget()`
（`runAgentLoop` 依赖 stdin/stdout 与真实 provider，单测起不了），使这条契约有不依赖进程的断言。

## 放弃了什么（以及为什么不选）

- **不保留 `max_tokens` 旧名兼容**。同一二进制内不存在版本错配，保留双名字等于把
  「窗口 vs 预算」的混淆固化进契约，还多一条「该读哪个」的分支。
- **不在 init 里传用户的显式预算（`--max-tokens`）**。子进程不读配置，本 PR 只按文档要求
  传物理上限，预算基准统一走 `resolveRequestBudget()` 的默认 32,768。理由：预算是
  「用户意图」，跨进程传它要连带处理配置热更新与多 provider 切换后的失效判断，
  超出 F7 第 3 条范围；默认值本身是保守安全值（真正能发多少由窗口剩余决定）。
  **代价说清楚**：用户显式调大 `--max-tokens` 后，spawn 出的子代理仍按 32,768 封顶。
- **不给 `getMaxOutputTokens` 编兜底数字**。未知返回 `undefined`（与
  `TokenEstimator.getMaxOutputTokens` 同口径）：编出来的值会被当成「已知事实」参与 min，
  比明确的未知更危险。
- **不为 headless 增加压缩分支**。窗口剩余连 floor 都放不下时如实发 `result{success:false}`
  并带齐诊断值（窗口 / 输入估算 / 剩余 / 下限），而不是发一个必然 400 的请求换一条
  无从归因的流错误。
- **不按文件数拆成多个 PR**。三处改动共享同一份协议契约：只改名不改预算，子进程仍写死 4096；
  只改预算不改名，读代码的人继续把窗口当输出上限。任何一半单独合入都停在半修复状态。

## 拿什么证明它生效了

- `bun test ./packages/core/tests/agent/sub-agent-spawn.test.ts ./packages/cli/tests/headless-output-budget.test.ts`
  → **25 pass / 0 fail**。含新增断言：8k 输出上限模型 → 8,192（物理上限生效）；
  未知物理上限 → 默认 32,768 且 `> 4096`（回归哨兵）；窗口 10k/输入 6k → 3,000 且
  `clampedBy === "window"`；窗口不足 → `ok: false`；两处 spawn 传参的**源码哨兵**
  （`context_window` 与 `max_output_tokens` 各出现 2 次，防「只改一处」）。
- `bun run affected-tests:run` → **6156 pass / 9 skip / 1 fail**。唯一失败
  `isolated-subagent-cwd.test.ts > 未绑定 cwd 时不出现隔离提示` 与本改动无关，三条举证：
  ① 该用例走进程内路径（无 spawnConfig），本次改的 init 字段不参与系统提示词构造；
  ② 父仓 main 上单跑 12 pass / 0 fail；
  ③ 成因是 worktree cwd 含 `.sid-code/worktrees/`，`getIsolatedWorktree()` 把进程自身判成
  隔离 worktree —— 用非 worktree cwd 跑**本 worktree 同一份代码**，12 pass / 0 fail。
- 门禁全绿：`typecheck:gate`（62/62，无新增）、`lint`（0 warning）、`format:check`、
  `lint:boundary`、`lint:command-system`、`lint:legacy-tool`；`make build` 成功产出 76M 二进制。
- `bun run smoke`：**通过**（改了预算，按 CLAUDE.md 的 G2 要求必跑；走录制回放不调模型）。
