# LSP 诊断新鲜度：PR #602 跟进修复（version 优先、屏障白名单、可观测口径）

## 决定了什么

PR #602（客户端代际屏障 + 有界 flush 窗口 + 内容指纹漂移校验）合入后，review 发现 10 处
问题，本 PR 全部修复。核心是三条正确性缺陷 + 一套可观测口径：

1. **version 判据先于 syncing 闸门**（`diagnostic-registry.ts`）。原实现先判 `doc.syncing`
   再判 version，于是带 version 的服务器（gopls / rust-analyzer / pyright）在 didChange 后
   立刻推出的**新鲜**诊断会被同步窗口整批丢掉；它们通常不重推，结果是该文件直到下次编辑
   都没有诊断。现在「version 不落后」的推送直接放行（version 是精确判据，屏障只是无 version
   服务器的兜底）。
2. **无屏障 ≠ 屏障成功**（`manager.ts` / `server-manager.ts` / `diagnostic-registry.ts`）。
   `syncFileToLSP` 原来对「无 barrier」一律 `passBarrier(true)`，注释声称「syncSeq 不匹配会
   return」——事实是 `endEdit` 不改 syncSeq，于是「本次 didChange 根本没发出去」被伪装成
   屏障成功，服务器按旧内容推来的诊断会被判 fresh，还会加「基于你最近一次编辑后的内容」
   标注。现在 `changeFile` 返回 `firstOpen`，三分支（有屏障 / didOpen / 同步失败）分开判；
   registry 用 `syncFailed` 取代只写不读的 `barrierFailed`——同步失败后连 version 判据也
   不可信（服务器回显的 version 可能停在上一代际）。
3. **屏障白名单**（`barrier.ts` / `server-manager.ts` / `types.ts`）。设计文档 §3.1 承诺
   「没跑过的服务器默认判 unverified」，实现却是无条件启用。现在 `BARRIER_VERIFIED_COMMANDS`
   只含实测过的 `typescript-language-server`；未验证服务器不挂屏障（带 version 的走 version
   判据，无 version 的判 unverified）。lsp.json 新增 `"barrier": true/false` 显式覆盖。
4. **BarrierGate 区分失败类型 + 半开恢复**。MethodNotFound（-32601）一次即永久禁用；
   超时类失败连续 3 次后「暂停」而非永久关闭，每 20 次编辑半开试探一次，成功即恢复。
   原实现关闭后永不重试——大工程冷启动的 3 次超时就能把整个会话打成修复前行为。
5. **可观测口径**。新增 `fresh_after_stale`（被同步窗口丢过之后是否补到新鲜推送，按代际计），
   用来区分「晚一轮」与「直到下次编辑都没诊断」——这是 flush 窗口代价的唯一观测口。
   `injected_first_publish` 消费后置 false，修复 carried 跨轮重复计数（否则指标随补发轮次虚高）。
6. **测试覆盖**。新增 `server-manager-barrier.test.ts`：不依赖真实服务器的屏障接线
   （didOpen 不挂 / didChange 挂 / 白名单 / 显式覆盖 / MethodNotFound）。新增 U12–U16：
   version 优先、syncFailed、first_publish、fresh_after_stale、`syncFileToLSP` 三分支。
   为此给 `syncFileToLSP` 加了可选的 `deps` 注入点（生产调用点不变）。
7. **清理**。删除只写不读的 `barrierFailed`、不可达的 `classify` 分支、零调用的
   `BarrierGate.reset()`；补 `waitForDiagnostics`（编辑窗口内会走超时）与 `barrier.ts`
   （flush 窗口可能误丢首推）的注释口径。

## 放弃了什么（以及为什么不选）

- **不在 CI 里装 typescript-language-server 跑 e2e**：设计文档 §5.2 明确「CI 跳过、
  不静默绿」，且 E1 依赖真实时序（本机并行负载下实测会 flaky，单跑稳定）。改用 fake instance
  的单测覆盖接线，e2e 保持本地手工验证——两者分工：单测锁「有没有接对」，e2e 锁「真实时序
  对不对」。
- **不只靠 `syncFailed` 兜住 manager 的分支误判**：`syncFailed` 只能挡「发送失败」的假新鲜；
  未验证服务器的 didChange 是「发送成功、只是没挂屏障」，`syncFailed=false`，必须由 manager
  分支判 false。两处是防御纵深，各自有测试（变异 M2 / M6 分别变红）。
- **不把白名单做成运行时自动探测**：服务器是否按序处理通知、旧推送何时排空，无法在运行时
  可靠探测，只能按 `packages/core/tests/lsp/e2e/` 的探针实测后登记。
- **不按时间戳/固定阈值判过时、不做 pull 诊断、不解析 bash 命令猜改动、不用 fs.watch**：
  沿用 #602 的 rejected 论证，本次未推翻任何一条。
- **不改设计文档本身**：文档在 `docs-research` 仓，不在本 PR 范围。§7「代价是晚一轮」的
  乐观说法已在 `barrier.ts` 头注释里按事实写清（可能直到下次编辑都没有诊断）。

## 拿什么证明它生效了

```text
bun test ./packages/core/tests/lsp/*.test.ts ./packages/core/tests/trace/lsp-diagnostics-digest.test.ts
  → 210 pass / 0 fail
bun test ./packages/core/tests/lsp/e2e/diagnostic-freshness.e2e.test.ts
  → 4 pass / 0 fail（本机 tsls 5.1.3，与 #602 一致）
bun run affected-tests:run
  → 1284 pass / 0 fail
make build
  → 成功，产物自检 5 项通过
bun run lint / bun run format:check / bun run lint:boundary
  → 全绿
```

| --- | --- | --- |
| 去掉 version 优先放行 | U12 | 2 条失败（含 U12） |
| 去掉 syncFailed 保护 | U13 | 2 条失败（含 U13） |
| 不消费 firstOfEpoch | U14 | 2 条失败（含 U14） |

| MethodNotFound 不区分 | U5 | 2 条失败 |

`typecheck:gate` 在 worktree 报 6 项 `packages/core/tests/skill/*` 的模块身份冲突
（绝对路径 vs `<root>`），父仓 main 同门禁通过（62/64，无新增）→ 是 worktree symlink 的
已知假阳性，与本次改动无关（三条举证齐：不 import lsp / 父仓通过 / symlink 成因）。

E1 在并行跑全量时出现过一次时序失败（单跑 4 pass），成因是 e2e 自身注释记载的窗口漂移
（机器负载高导致采样整体后移），不是本次改动引入。
