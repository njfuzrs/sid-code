# 启动期维护任务迁入 detached 子进程，首帧与事件循环阻塞不再随 ~/.sid-code 数据量增长

## 决定了什么

立住一条不变量：**TUI 进程在首帧前和交互期间，主线程不做任何耗时随 `~/.sid-code/` 数据量增长的工作。**
本 PR 合并了方案文档的 PR-A（观测 + 门禁）与 PR-B（维护子进程 + 轻量扫描器）。

PR-A：观测
- `shared/utils/startup-profiler.ts`：新增 `first_frame` 打点（ink 第一次写 stdout，在 `ui/first-frame.ts` 里挂探针），
  以及事件循环漂移探针 `max_loop_block_before_interactive`（从 bootstrap_entry 一直观测到首帧后 3s）。
  设了 `SID_CODE_PROFILE_STARTUP_DUMP=<path>` 时，窗口结束会把结果写成 JSON，不依赖 TUI 正常退出。
- 门禁 `packages/cli/tests/startup/large-data-startup-gate.test.ts`：在 pty 里分别用空配置目录和大数据配置目录起 TUI，
  各跑 3 次取中位数，按差值断言（首帧差 < 150ms，最大阻塞差 < 100ms），另设首帧绝对值 < 3s 兜底。

PR-B：迁移
- 新增内部子命令 `sid-code __maintenance <payload-json>`，在 `bootstrap.ts` 零导入快速路径里分发。
  执行体是 `core/maintenance/runner.ts`，拉起端是 `launcher.ts`，单实例锁、任务水位线、结果文件都在 `state.ts`。
- TUI 侧（`cli.ts` 的 `startBackgroundMaintenance`）只做 O(1) 的事：读水位线判断到期 → 全都没到期就不 fork →
  否则等首帧后 `detached + stdio:ignore + unref` 拉起。子进程 `setPriority(10)`，可以活过 TUI 退出。
  父进程把已解析好的 retention、轨迹目录、`selfSessionId`、D3 受保护 id 通过 argv 传给子进程，子进程不 loadConfig。
- 承接的任务：
  - C1/C2 会话清理：改用新的 `session/light-scan.ts`；
  - T1/T2 轨迹淘汰与空壳清理：从 `TraceCollector` 构造函数整体移到 `trace/startup-prune.ts`，构造函数里一行都不留；
  - H1：从 `runStartupHousekeeping` 拆出 `runHousekeepingCleanup`，原函数只保留 O(1) 的幂等操作。
- 轻量扫描器：≤1MB 的文件读全文后交给 `buildSessionFileEntry`。这个函数是从 `scanSessionDir` 抽出来的，
  和全量扫描器是**同一个**实现，D4/D9/N1 判据一份也没复刻。更大的文件流式逐行读，每行只留行首（取 type）和行尾
  （取 timestamp），只对 ≤64KB 的行 JSON.parse，再线性回放出 sidechain / chain-broken / empty（含 prompt_retracted 弹栈）/
  subagent / lastUpdated 这几项。
- 删除提示：子进程把「删了 N 个」写进 `state/maintenance-result.json`，由**下一次**启动读出，只提示一次
  （#64999「删用户数据必须让人看见」的要求保留）。
- `-p` 保持原语义：不做会话清理；轨迹和管家清理照常进子进程。

方向：**更快**。牺牲的是**可观测/即时性**：清理晚一点完成，删除提示要等到下一次启动才出现。

## 放弃了什么（以及为什么不选）

- **改成 async / setTimeout / 等首帧后再在本进程跑**：只改了「什么时候跑」，没改「在哪个线程跑」，
  O(数据量) 的同步 CPU 活照样挡住按键。方案文档 1.2 节的根因就是这个，否决。
- **Worker 线程**：内存仍算在 TUI 进程的 RSS 里（实测全量扫描 200MB 单行会话时 RSS 1GB）；Worker 也活不过主进程退出，
  补传（PR-C）需要能跑完而不是「进程一退就中断、下次从头」。
- **子进程里自己 loadConfig**：父子两边的保留期口径必须是同一个值（startup-housekeeping.ts 头注释记过会话 30d / 轨迹 365d 的事故），
  而且 loadConfig 有 MCP/企业配置读取和落盘副作用。改成传值。
- **轻量扫描器读到第一条消息就停**（方案原文的建议）：D4 的空会话判断是回放 prompt_retracted **之后**的结果。
  撤回唯一一条大粘贴的会话，全量扫描器判 empty（不可删）；读到第一条就停会判成有效会话，过期即删。判据不一致就是删错，
  所以大文件扫到底，只是不 parse 大行。实测 200MB 单行会话：轻量 24ms vs 全量 658ms / RSS 1GB。
- **复用 `daemon/lock.ts`**：那把锁的路径写死为 daemon.lock，语义是「本机只有一个守护进程」，两者不同。照搬了同一种模式
  （wx 原子创建 + PID 探活回收）。
- **T3（`ensureUploadWatermarks`）也搬进子进程**：核实过，状态文件存在时它只读一个小 JSON（O(1)）；只有升级后首次启动才全量扫一次，
  而且那次的结果决定迁移语义，必须在本进程同步得出。保持不动。
- **补传 U1–U4 一并迁移**：补传的入口在 collector 的 SessionStart 里，并且依赖 resume 感知的 trace session id；
  再加上流式压缩、退避终态，改动面比本 PR 还大。留给 PR-C，门禁里给它留了一条 `test.skip`。

## 拿什么证明它生效了

- 门禁标定（本机，3 次启动取中位数，fixture：1500 个轨迹目录 × 20 个 tool-outputs、300 个会话、
  一份 200MB 单行且含大量转义的会话，均在保留期内）：
  - 修复后：首帧差 +18 / +34 / +142ms，最大阻塞差 −13 / +2 / +15ms → 绿
  - 变异 C1（全量会话清理放回主线程 fire-and-forget）：首帧 469→1167ms，阻塞 72→642ms → 两条都红
  - 变异 T1/T2（放回 collector 构造函数）：首帧 528→881ms，阻塞 94→394ms → 两条都红
  - 标定过程中门禁两次空转，都靠变异抓出来了：fixture 用了已过期的数据，第一轮启动就把它删光；
    正文用纯 `aaaa`，JSON.parse 太快。两处 fixture 注释里都记了。
- 对照测试 `packages/core/tests/session/light-scan.test.ts`：8 类形态 × 大/小两份，轻量与全量逐条判定一致，
  得到的待删清单也一致。第一版实现被它抓到一个真 bug：一行的第一个 chunk 就超过 64KB 时，行首为空，
  chain-broken 被误判成可删的 parse-error。已修，修法见 light-scan.ts 的注释。
- `packages/core/tests/maintenance/runner.test.ts`：三个任务的接线、D3 保护、水位线（含「全部未到期时 launcher 判出空任务」）、
  单实例锁与 stale 回收、提示只出一次，以及真起 `bootstrap.ts __maintenance` 子进程跑完并落结果文件。
- 搬迁前后判据不变：原有 retention / blank-session-prune / session-index / collector LRU / housekeeping-orphans
  这些用例改成直接调新函数，断言一字未改，全部通过。
