# 流式资源释放链的剩余缺口：compact 取消、中断源释放、真实漏斗集成用例

## 决定了什么

来源：PR [#566](https://github.com/njfuzrs/sid-code/pull/566) 的 review（2026-11-04）。该 PR 修的是
F1 + F5（《20261104-会话 f5beebde 复盘-流迭代器泄漏与额度误判等六项-落地方案》§1、§2）。
本次收尾的是 review 中发现、但**不在 #566 范围**的 8 项同族问题。

1. **P2-1：补真实 `ModelFallback` 集成用例**（`packages/core/tests/llm/fallback-abandon-integration.test.ts`）。
   #566 的形态 B 用例用手写 `raceIterate(provider())` 模拟漏斗，只证明「raceIterate + throw」自洽，
   不证明 `fallback.ts` 自己的接线真的走了这条路。新用例实例化真实漏斗 + 假 provider（内部建真实
   lifecycle），断言 provider/lifecycle 的 finally 执行、`BilledRequest` 写出且 usage 等于流内
   `message_delta` 带的值、活跃 lifecycle 计数回基线 —— 这正是方案 §1.6 第 3 条要求的那条。
2. **P2-2：compact 三条路径接 `cancelSource`**（`context-collapse` / `partial-compact` / `auto-compact`）。
   此前 lifecycle 的三层超时在它们身上只能「报告」不能「执行」：idle 30s 判定超时后抛错退出，
   但底层 fetch 仍在读，要等 side-call 硬 deadline 的 signal 才被取消（最坏多挂 30s）。
   每条路径建 per-request `AbortController`、与外部 signal 合并后交给漏斗，lifecycle 的
   `cancelSource` 用它取消本次请求；lifecycle 自身的 `signal` 仍传原 signal（外部取消语义），
   避免 cancelSource 自己触发的 abort 让 lifecycle 误以为外部取消而静默退出。
3. **P3-1：`stream_completed` 遥测带 `timedOut` 标记**（`llm/types.ts`、`llm/retry-telemetry.ts`）。
   超时恰好落在「事件已 yield、消费方尚未请求下一个」的窗口内且消费方随后 break 时，生成器在
   `yield` 处收到 return completion 直接走 finally，超时错误没有机会抛给消费方。此时 `onTimeout`
   已回调、`TimeoutFired` 已发出，但流以「正常结束」呈现。该字段让轨迹能把两者分开，
   不必靠时间窗倒推。未超时时不落该字段（既有事件形状不变）。
4. **P3-2：`activeLifecycleCount` 的 `++`/`--` 严格配对**。`++` 移到 `try` 之前，finally 无条件 `--`；
   去掉 `Math.max(0, n - 1)` 兜底 —— 那是泄漏哨兵，把「多减一次」静默吞掉等于让它失去意义。
5. **P3-3：`cancelSource` 的 abort reason 区分用户取消**。外部 signal 已 abort 时用它的真实 reason
   （仅 `isAbortError` 白名单内才采信，否则回落 `"user-cancel"`），不再一律标
   `"stream-lifecycle-timeout"` —— 后者会让只看 abort reason 的归因把用户 ESC 读成 lifecycle 超时。
6. **L1：四处 `abortPromise` 的 abort listener 正常路径移除**。新增
   `createAbortRaceInterrupt(signal, makeError)`（`llm/race-iterate.ts`）统一 add/remove，
   `raceIterate` 新增 `onExit` 在离开时回调 dispose。`{ once: true }` 只在 abort 时移除，
   正常完成的请求（绝大多数）会永久留下一个 listener —— `AbortSignal` 是 EventTarget 不是
   EventEmitter，**没有 MaxListeners 警告**，长会话线性累积且完全静默。
7. **L2：`raceIterate` 入口合并中断源**。此前每轮 `Promise.race([next, ...interrupts])` 给 M 个
   永不 settle 的中断源各附一个 handler（O(N×M)）；合并成一个后入口只附 M 个、之后每轮附 1 个
   （O(N + M)）。功能不变，去掉「每个事件多分配 M 个对象」的常数开销。
8. **L3：`activeLifecycleCount` 的测试 reset**（`__resetActiveStreamLifecycleCountForTest`）+
   一条「真泄漏」用例：启动生成器后丢弃、不调 `return()`，断言计数保持 +1，再用 reset 清理，
   避免故意泄漏污染同进程后续断言。

## 放弃了什么（以及为什么不选）

- **P3-1 改为「消费方 break 时也抛超时错误」**：消费方 break 的语义就是「不要剩余流了」，
  此时抛一个它不关心的异常会改变 `for await` 的退出契约。只做可观测标记，不动控制流。
- **P3-3 用 `signal.reason` 原文直接作为 abort reason**：外部 reason 不一定在 `ABORT_REASONS`
  白名单内（如调用方自定义字符串），未登记的 reason 会让 `isAbortError` 漏判孤儿 rejection →
  `process.exit(1)`（记忆 `esc-abort-reason-crash-coupling`）。所以只在白名单内采信，否则回落
  `"user-cancel"`。
- **compact 路径把 `reqSignal` 也交给 lifecycle 的 `signal`**：cancelSource 自己触发的 abort
  会让 lifecycle 的 abortPromise reject → catch 里 `signal?.aborted` 成立 → 静默 return，
  把一次真超时伪装成「外部取消」。所以 lifecycle 的 `signal` 必须保持原 signal。
- **让四处在 `for await` 外层各写一份 `try/finally`**：四处循环体动辄上百行，包一层会把整个
  函数重排；漏包一次的后果正是历史缺陷的形态。把「离开时一定执行」交给 `raceIterate` 的
  `onExit`，与「离开时一定 return() 源头」同源。
- **L3 现在就 export reset 到生产 API 面**：`__resetActiveStreamLifecycleCountForTest` 命名已
  明确标注测试专用；不 export 就无法写「真泄漏」用例，而那条用例正是哨兵自身有效性的证明。
- **L2 改用 AbortSignal 而不是合并 promise**：那会同时改动四处调用点的中断源契约，
  收益只是少一层 promise 包装；先做合并（方向 1），把接口变更留给真有需要时。
