# ESC 撤回未送达模型的输入并放回输入框

## 决定了什么

口径：**只有消息还没送达模型（模型零响应）时**，ESC 才撤回这一轮，把原文放回输入框。模型回过任何东西（文本 / 思考 / 工具调用），说明消息已经送达，ESC 只中断、不撤回、不回显。

根因：A4 回填（`4d55c740`）从引入那天起就是死代码。它挂在 `onUserInput` 的外层 catch 上，但 ESC 走不到这个 catch，有两条原因：

- `tuiAgentLoop` 内层 catch（A3，`d9276230`，比 A4 早一小时）吞掉了 abort，不再 rethrow；
- loop 的三条 abort 收尾（退避期、本地限流等待期、流式结束后）都是 `yield done(aborted)` + return，根本不抛异常。

结果是 `await tuiAgentLoop()` 正常返回，紧接着 `clearPendingInput()` 把暂存的原文丢掉。由于没走 `rewindTurns`，乐观追加的 user 气泡和 ctxMgr 里的 user 消息都留了下来，重发时就叠成两条。

改动：

- `app.ts`：每轮建一个 `TurnProbe`，内容包括本轮开始前的消息快照和落盘计数、`modelResponded`（由文本 / 思考回调和 `tool_start` 置位）、`userCanceled`（内层 catch 吞 abort 时，或收到 `done(aborted)` 时，且 reason 为 `user-cancel`）、`failed`（`fatal_error` / system error / 重试耗尽 / 异常穿透）。`onUserInput` 在 `tuiAgentLoop` 返回后和 catch 里都读这个探针。
  - 忙时 ESC 且消息未送达：立即撤回，加上 `markForRestore`。
  - 请求失败且消息未送达：`armRetractable`，保留报错现场。用户在空输入框按 Esc 时再撤回（路径 B）。撤回前会校验消息数组没变过。
- 撤回 = `ctxMgr.restoreToPrefix(快照)` + `sessionStore.appendPromptRetraction` + `rewindManager.dropPoint` + `rebuildDisplay`。
- `pending-input.ts`：判定改为「本轮之后没有任何 assistant」（`isTurnUnanswered` 用快照对比）。新增 `onRestoreArmed` 通知：`isLoading` 的下降沿早于 arm，只靠沿检测会拿到 null。新增路径 B 的可撤回状态。
- `store.ts`：新增 `prompt_retracted` 记录，resume 时弹掉被撤回的消息。
- `InputArea.tsx`：订阅 arm 通知立即回填；空闲时空输入框按 Esc 触发路径 B。

## 放弃了什么（以及为什么不选）

- 沿用 `rewindTurns(1)`：本轮 user 消息可能被 `addMessage` 合并进上一条 tool_result（同为 user 角色），rewindTurns 会连上一轮的 tool_result 一起删掉，造成孤儿 tool_use。按快照恢复没有这个问题。
- 沿用 cc 的 `messagesAfterAreOnlySynthetic` 口径（其后只有 tool_use/tool_result 也回填）：工具已经跑过，说明模型确实收到了消息。用户明确要求「已送达不回显」，所以改用更严的口径。
- 只撤内存、不动 jsonl：`-c` 恢复后，被撤回的消息会重新出现，并和下一条输入合并成同一条 user 发给模型。追加写不能删行，所以用撤回标记。
- 请求失败后立即撤回并回填：这样报错卡片和输入框会同时变化，用户看不到失败原因。改为等用户主动按 Esc。
