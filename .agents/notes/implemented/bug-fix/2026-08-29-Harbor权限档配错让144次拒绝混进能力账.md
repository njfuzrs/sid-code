# Harbor 侧权限档配错，让 144 次权限拒绝混进了「能力账」

## 决定了什么

**一、把 Harbor agent 的权限档换成 `--dangerously-skip-permissions`，与自建 swe-bench 链路对齐。**
`evals/external-benchmarks/harbor/sid_code_agent.py` 的 `CLI_FLAGS` 里，原来的
`permission_mode`（`default=acceptEdits`）换成两条：

- 新增 `skip_permissions`，`cli="--dangerously-skip-permissions"`、**`type="bool"`**、`default=True`；
- `permission_mode` 保留但 `default=None`（不传），choices 里加 `always-allow`。

`type="bool"` 不是随手写的：Harbor 只对 bool 输出**裸 flag**
（`installed/base.py:723-725`），写成 str 会拼出 `--dangerously-skip-permissions True`
—— 而 sid-code 的 checker 判的是 `config.skipPermissions`，只有布尔 flag 会由
`cli.ts:555` 设它。**这条错不报错、也不生效**，形态与原来的 144 次拒绝一模一样。

**二、新增 `_assert_permission_flags_coherent()`，两个档同时给出时拒绝启动。**
sid-code 侧 skip **确实**优先（`config.ts:1557` 覆盖 permissionMode），所以两个都传时
`--ak permission_mode=acceptEdits` 是个**看起来生效、实际被覆盖**的假开关，
而 metadata 会如实记下 `acceptEdits` —— 跑完之后没有任何东西会报错，
只有一份写着 acceptEdits、实际全放开的结果。选择在**起容器之前**失败，而不是读结果时。

**三、新增 `_count_permission_decisions()`，把 deny/allow 的实际条数落进 metadata。**
新增键：`sid_permission_mode_requested`（请求值）与 `sid_permission_denials` /
`_allows` / `_decisions_total` / `_by_decision`（观测值，源
`logs/permissions-audit.log`）。**请求值与观测值刻意分两个键**：前者只证明「我要了什么」，
三个已实测的坑全是「要了但没生效」。日志缺失时落 `sid_permission_audit_missing=True`
而**不填 0** —— 「零拒绝」是换档成功的判据，让一次采集失败伪装成它是最坏的。
这几格写在三条 early-return **之前**，所以被 SIGKILL 的 trial 也带得回来。

**四、改那道门禁的判据（不是拆门）。** `tests/eval/harbor-agent-contract.test.ts:259`
原来断言「源码里不许出现 `dangerously-skip-permissions`」。它**忠实地执行了一个错误的
决定**，且注释理由读起来完全正当 —— 任何人想改回与 swe-bench 一致都会被它拦住。
换成锁四件事：skip 必须是 bool CliFlag / mode 的 choices 不含 skip 名与
`bypassPermissions` / 互斥校验存在 / 观测值落 metadata。

**五、六个脚本落库**（`evals/external-benchmarks/harbor/`），全部用旧 run 双向自证过
—— 不是「文件在」，是**能复现出 144 deny / 0.100 / attempt 最大 7 那组已知数字**：

⚠️ 这里原先写的是 **0.111**，那是我自己的脚本算错的数，见下方「规则 ① 我照字面执行，
把最该扣分的一类失败白送成了一分」。**复现的目标值必须是文档基线 0.100** ——
拿自己算出来的数当靶子，就等于把 bug 写成了验收判据。

| 脚本 | 干什么 |
| --- | --- |
| `verifier_health.py` | **verifier 判据的唯一定义处**（下面两个脚本都从这里取） |
| `analyze-permission-switch.py` | 判据 ①②③：三条分桶规则 + 逐题表 |
| `analyze-retry-cost.py` | 判据 ④：重试墙钟与内层 attempt 上限 |
| `check-comparison-parity.py` | **对照口径核验**（§17.5 第二优先的那条教训） |
| `progress-permission-switch.py` | 跑动时的进度，每题当场报 verifier 健康 |
| `run-permission-switch.sh` | 重跑入口，头注释带两道跑前判据 |

`check-comparison-parity.py` 值得单说：§17.5 指出 A10 那次对照
**不是单变量**（mswea 跑 `mode: yolo` 零确认，我们 `acceptEdits` 144 次拒绝），
而「同题同模型同容器同 verifier 全核过了，唯独没核权限层」——
**清单漏一项，漏的那项就整体记进能力差异**。现在这条清单是可执行的判据：
两侧取数源不同（我们读审计日志的 deny **实际条数**，mswea 读
`info.config.agent.mode`），且两侧都取**观测值不取声明值**。

双向自证：拿 A10 原始数据跑 → **3/3 判「⛔ 不可比」**；拿换档后数据跑 →
**3/3 判「✅ 同档」**。一个恒 ⛔ 的废判据过不了第二关。

**六、闭掉缺口 B**：重编两架构 linux 二进制并另存为
`sid-code-{arm64,x64}-7f437eb84e7a`（前三棒一直欠着）。

## 放弃了什么（以及为什么不选）

- **⛔ 删掉那道门禁。** 它的反向锁价值仍在（防止有人无意识地把权限档改成静默失效的
  形态）。**一道判据错了的门禁，修法是改判据，不是拆门** —— 拆了之后下一次把 skip
  写成 `type="str"` 就没有任何东西会红。
- **⛔ 保留 `acceptEdits` 作默认、只在需要时手工传 skip。** 那等于把「每次跑评测的人
  必须记得传对档」变成永久成本，而忘记的那一次恰好会产出一条**读起来像能力差距**的
  曲线。默认值就是实际会被用的值。
- **⛔ 把「命令行传了 skip」当判据。** 那只证明我请求了全放开。三个坑全是
  「请求了但没生效且不报错」，此时命令行看起来完全正确而容器里照样被拒 144 次。
  所以判据换成审计日志里 deny 的**观测**条数 —— 而**前六棒无人读过那份日志**，
  正是 §17.3 那个错能活这么久的原因。
- **⛔ 顺手放大题量。** 目的是在**同一把尺子**上做前后对照，题量一变就分不清
  「换档生效了」和「换了一批题」。仍是那 10 题、`-n 1`、带 `--registry-path`。
- **⛔ 放宽 injection 启发式**（27/144 = 19% 属此类：19 次 `obfuscated-flags` +
  3 `newlines` + 3 `quoted-newline` + 2 `brace-expansion`）。**实测已确认换档后它们
  一起消失**：那 27 条真实命令回灌进真实 checker，`acceptEdits` 下 27/27 被拦，
  `skipPermissions` 下 0/27 —— **所以它不再是评测阻塞**。
  但它仍是产品缺陷：交互模式下用户写 heredoc（`python3 -c "` 后跟多行、Perl 量词
  `{1,3}`）会无端弹确认。已与评测解耦，独立排期 —— 上一棒那条「照亮墙零风险，
  拆墙要单独论证」仍然成立。
- **⚠️ 上一棒那份 Note 把「改用 skip」列进了「放弃了什么」**，理由是「那是把要测的
  防线关掉，且 L1 门禁明文拦这个字符串」。**本次推翻它**：那道门禁本身就是错的判据，
  而「关掉防线」这个代价在评测语境下是**必须付**的 —— 见下面那条 trade-off。

## 这次牺牲了哪个方向来成全另一个（自检第 3 问）

**拿「更安全」换「更准」，且这个交换必须点破。** skip 同时跳过 safetyCheck 与危险命令
检测，所以**这一轮评测测不到权限层** —— 它只是一个被记进 metadata 的必控变量，
不是一条通过了的验证。可接受的理由与 swe-bench 侧同一句：容器无外网（走网关）、
跑完即销毁、里面只有一个 benchmark 仓库。

**这个代价的具体形状已实测，不是抽象表述**：上一棒留的三条真攻击载荷回归样本
（`git diff {@'{'0},--output=…}` / `find . ''-exec` / `ls $'\x2d\x2drf'`），
在 `acceptEdits` 下 **3/3 拦住**，在 `skipPermissions` 下 **3/3 放行**。
即换档确实把这层拆了 —— 在一次性容器里可接受，**但任何「权限层验证通过」的说法
都不能引用这一轮评测**。

想专门观察防线的路径**仍然保留**：`--ak skip_permissions=false --ak permission_mode=acceptEdits`。
两者不可兼得这件事，现在由互斥校验强制人做一次显式选择，而不是靠读注释。

## 拿什么证明它生效了

**① 基线复算（先证明我要修的东西真实存在）。** 读第五棒那 10 题的
`permissions-audit.log`：**144 deny / 178 allow**，与 §17.2 逐数字吻合。
按成因拆：111 次（77%）是 acceptEdits 不放行普通 bash（`nproc` / `which git` /
`qemu-img info` / `apt-get install`），19 次 injection 误报，3 次写 `/tmp`。

**② $0 预演换档效果：把那 144 次真实被拒调用回灌进真实 `PermissionChecker`**
（生产 checker，不是重实现判据；`cwd=/app`，无确认回调 = headless 同形态）：

```
当前档 acceptEdits        : 放行   0/144   仍被拒 144
换档后 skipPermissions    : 放行 144/144   仍被拒   0
```

这是判据 ① 的离线预测：deny 应趋近 0。**在花 $7 之前就知道方向对不对。**

**③ 真实行为核验（装了 harbor，直接构造 agent 实例）**：

```
默认档            → flags: --max-turns 40 --dangerously-skip-permissions   ← 裸 flag，非 "True"
显式关 skip+观察   → flags: --max-turns 40 --permission-mode acceptEdits
两者同时给         → ValueError（拒绝启动）
env 关档           → flags: --max-turns 40
喂真实 audit log   → {'denials': 22, 'allows': 18, 'total': 40}  ← 与 sqlite-with-gcov 那题逐数字一致
日志缺失           → None（不是 0）
```

**④ 门禁变异自证 5 处，每处确认「红的是哪一条」而非「有东西红了」**
（fixture 用 `cp` 从已知好状态复原，复原后 `shasum` 逐字节一致）：

| 变异 | 结果 |
| --- | --- |
| `type="bool"` → `"str"` | 权限档那条翻红（精确复现坑 3） |
| choices 里加进 skip 模式名 | 同上（把静默失效路径做成官方旋钮） |
| 删互斥校验方法 | 同上 |
| 删观测计数方法 | 同上 |
| `sid_permission_denials` 键改名 | 同上（跨语言边界丢键） |

**⑤ 缺口 B 闭环自证**：两个二进制的 `artifact-identity.ts read` 都返回
`commit=7f437eb84e7a…`（40 位）+ `identity_source=embedded`，而第五棒的基线是
`abb8233e…`。`dirty=True` 的成因核过：只有本次那两个**不参与 `bun build`** 的文件
（`packages/**/*.ts` 中引用 `sid_code_agent` 的处数 = 0，同法查 `permission/checker`
得 19 处，证明该判据有区分力）。

**⑥ 仓库门禁**：`affected-tests:run` 1216 pass / 0 fail；`make build` 通过且
`will always be undefined` 0 处；`lint` / `format:check` / `lint:boundary` 全绿。

## 附带发现：verifier 靠实时下载 uv，这让整轮评测「绿着坏掉」（烧掉 $3.12）

第一次重测跑到第 3 题时发现：**reward 全是 0，而 `sid_subtype` 全是 `success`**。
根因不在 agent 侧 —— 10 题的 `test.sh` **全部实时从 GitHub 下载 17.8MB 的 uv**，
而当天宿主到 GitHub CDN 的链路劣化到 **70KB/s**（基线那次 verifier 全程只要
24–56 秒；这次是 **103 / 243 / 413 秒后放弃**），于是 `uv: command not found`，
pytest 一次都没跑，`reward.txt` 写 0。

**为什么它特别贵**：这种坏法**不报错**。`reward=0` 在下游读起来就是「没解出来」，
与真的没解出来**逐字节一样**；`sid_subtype=success` 还在旁边给它背书。
若不是当场去读 `verifier/test-stdout.txt`，这一轮会产出**一份看起来完整的
「换档没用」的结论** —— 而那正好是本次要推翻的那个错误的镜像。

**判据（跑前必过，已写进 `run-permission-switch.sh` 的头注释）**：

```bash
docker run --rm alpine:3 sh -c 'apk add -q curl; curl -sL -o /dev/null -m 30 \
  -w "%{speed_download}B/s\n" \
  https://github.com/astral-sh/uv/releases/download/0.7.13/uv-x86_64-unknown-linux-gnu.tar.gz'
```

**要 ≥500KB/s**（17.8MB / 35s，留出 pytest 的余量）。坏那次是 70KB/s，
换代理节点后是 **1.02–1.10MB/s**，同一条命令、同一个镜像立刻恢复 ——
**证明不是镜像/`test.sh` 的问题，是宿主链路**。8/28 基线 10/10 题
`installing to /root/.local/bin` 全部成功、pytest 全部有结论行，可以逐题复算。

⚠️ **这条也是一处「分母铁律」的实战**：§14.7 规则 ② 本来就写着
「verifier 坏掉的样本不进分母」，本次它**真的救了场** —— 复算脚本按这条规则把
3 题全部排除，分母落到 0/3，于是「没有结论」而不是「一个假结论」。
规则不是摆设，是这次唯一挡住错误结论的东西。

⚠️ **没有顺手去修这个脆弱性**（预置 uv / 镜像内缓存）：那会改判分环境，
**与基线不再是同一把尺子**，要单独论证并重建基线。这一棒只加了跑前判据。

### 而我自己的规则 ② 一开始也是个「裸子串代理判据」（当天被自己的数据打穿）

初版 `analyze-permission-switch.py` 的规则 ② 写的是「`verifier/*stdout*` 尾部
含 `command not found` → 排除」。三题里它只命中 **2 个**：
`polyglot-c-py` 的 verifier 是在**下载 uv 的中途被超时杀掉**的，日志最后一行停在
`downloading uv 0.7.13`，那句 `uv: command not found` **压根没来得及打印**。
它之所以也被排除，只是**恰好**因为 `reward=None` —— **那是运气，不是判据**。

改成**正向判据**：verifier 跑成了 ⟺ stdout 里有 pytest 的结论行
（`N passed` / `N failed`）。它对「怎么坏的」不做任何假设 ——
下载失败、超时被杀、镜像缺依赖、pytest 自己崩，全都落进「没有结论」。

**形态教训**（与仓库里那条「别用裸子串代理判据」同源）：
`command not found` 是**某一种坏法的症状**，而「没有结论行」才是**「没判分」本身**。
用症状做判据，就会漏掉同一个问题的其它坏法，而且**漏的时候不报错**。

**变异自证（双向，复原后逐字节一致）**：

| 变异 | 期望 | 实测 |
| --- | --- | --- |
| 结论行正则改成永不匹配 | 好 run 分母塌掉 | 纳入 **0/10** ✅ |
| 判据恒真 | 坏 run 被错误纳入 | 纳入 **1/3** ✅ |

### 顺带修掉一处「两处判据不一致」（自己制造的，当天自己发现）

进度脚本与复算脚本一开始**各写了一份** verifier 判据：复算只要 pytest 有结论行，
进度还额外要求 `installing to /root/.local/bin`。两个都"能自证"，
但它们证的不是同一件事 —— **同一题可能一个报 ✅ 一个报 ⛔**，
而分歧会在无人看的时候发生。

判据只能有一个定义处，于是抽出 `verifier_health.py`。顺带把那条多余的
`installing to ...` 要求删掉：它是当前 `test.sh` 的**实现细节**，
上游换个装 uv 的方式（预装、换源、改路径）就会把好数据判成坏数据 ——
**判据要盯结果（判分有没有发生），不盯过程（uv 怎么装上的）**。

**反向自证**：把共享模块里那条正则改成永不匹配，**两个脚本同时翻**
（复算 9/10 → 0/10，进度 ✅判分 → ⛔未判分），复原后逐字节一致。
这才证明是「一处定义」而不是「两份拷贝恰好一致」。

顺带一个收获：新判据能把三种坏法**分开命名** —— `uv没装上` / `下载中被杀` /
`无stdout`，而初版那条 `command not found` 只认得第一种。

⚠️ 第二个变异只让 1/3 漏进来，不是 3/3 —— 另两题被规则 ① 与 `reward=None`
独立拦住了。**这说明三条规则是纵深，不是单点**；但也说明**只靠规则 ② 的
happy path 测不出它坏了**，必须像上面这样把它单独打穿。

### 规则 ① 我照字面执行，把最该扣分的一类失败白送成了一分（前一棒已记过，我重犯）

这是本次最该记下的一条，因为**错的是我的仪器，而错误方向是让分数变好看**。

§13.2 的字面写法是：「`reward=0` 且 `sid_is_error=False` → 判分未发生，不进分母」。
我照字面实现了，于是 `configure-git-webserver` 被排除，复算出 **0.111**，
而文档基线是 **0.100**（分母 10）。我当时把这 0.011 的差当成了「口径小分歧」。

它不是分歧，是 bug。那题的 verifier **跑得好好的**：

```
runs/a11-sid/configure-git-webserver__5LK7HTd/verifier/test-stdout.txt
  1 failed in 22.79s
  FAILED ../tests/test_outputs.py::test_hello_html_exists
  AssertionError: assert 'TEST PASSED' in '... ❌ TEST FAILED: Web server returned HTTP 000 ...'
```

真实情况是 sid-code 写了一篇「怎么配置 git + nginx」的说明脚本、**没真的把服务器配起来**，
然后以 `subtype=success` / `is_error=False` 收工，末尾还在问
「要不要我现在就把访问控制或清理旧文件这两项加进脚本？」。

**那正是最该计分的一类失败**（自检里叫「以为自己做完了」）。把它排除等于给自己白送一分，
而且送的恰好是最该扣分的地方。

**形态**：`reward=0 且 not-error` 这一个条件，同时覆盖了两件**语义相反**的事 ——

| | 语义 | 该怎么处理 |
| --- | --- | --- |
| ① | verifier 没跑成，判分未发生 | 排除（分母不该含它） |
| ② | verifier 跑了、判 0，agent 自我报喜 | **计分**（这就是真实失败） |

只有去看 **verifier 自己的输出**才能把两者分开。`sid_is_error` 是 **agent 的自述**，
**拿它推断 verifier 的状态是跨主语推断** —— 这与记忆里那条
「别用 `sid_is_error` 推断 verifier 状态」是同一条，我却在实现时又犯了一次。

所以 `excluded()` 现在只保留一条**正向**判据：verifier 到底判分了没有。
`sid_is_error` 不再参与分母决策。改完复算 = **0.100，分母 10/10**，与文档基线一致。

**两处代价值得单独记**：

- **前一棒早就把这条写下来了**，就在 `analyze-prefix.py:45-47` 的 `VERIFIER_RAN_PAT`
  注释里（「拿它推断 verifier 的状态是跨主语推断」）。我没读那个文件就自己写了一份判据。
  **同一个仓库里已有的口径，重实现一遍就是重踩一遍** —— 这也是记忆里那条

### 规则 ④：一次 API 调用都没发生的那题，我的仪器把它当成了真实的 0 分

本轮跑动中实测到一个前三条规则**全都放行**的坏样本，形态与本 Note 主体在修的
那件事**是同一类**，只不过混进能力账的是网关而不是权限层。

`polyglot-c-py` 拿到 `reward=0.0`，verifier **判分完全正常**（有 pytest 结论行），
所以规则 ①②③ 一致同意把它计入分母。而它的真实形态是：

```
[AUDIT:API] ✗ Anthropic 请求异常 err=502 Remote end closed connection without response
[FALLBACK] S3：剩余预算 37543ms 不足以「退避 37043ms + 一次请求」，停止重试（已重试 4 次）
{"subtype":"error_during_execution","num_turns":0,"total_cost_usd":0,
 "usage":{"inputTokens":0,"outputTokens":0}}
```

**网关 502 挡了 277 秒，一次 API 调用都没成功，agent 压根没碰过这道题。**
把它当一个真实的 0 分，就是把一次基础设施故障记进能力账。

⚠️ 这个 502 是**瞬时的**，不是网关坏了：事后从宿主与容器各探 3 次全 200
（`chess-best-move` 也有 5 行 502 却照样跑完 41 轮）。所以对策不是修网关，
而是**让仪器认得出这种样本** —— 瞬时故障还会再来，而它每次都长得像一个 0 分。

**判据为什么用 token 而不用 `turns`**：`turns` 来自 agent **自述**的 result 事件，
token 来自 Harbor 侧的 `agent_result` —— **取观测方，不取自述方**（跨主语推断是
本仓反复踩的坑，本 Note 上一节刚踩过一次）。另外 `turns == 0` 理论上还能是
「一轮就答完」，而 in/out token 双 0 只有一种解释。

**`None` 与 `0` 必须分开，这条不是洁癖**：基线 `fix-code-vulnerability` 整份
metadata 缺失（两个 token 键都是 `None`），但它 verifier 判了分、reward 有值，
属于「采集缺失但题跑过了」，**该计分**。写成 `if not tok_in` 会把它一起吞掉。
变异自证实测：改成 falsy 后基线分母 10 → 9、均值 **0.100 → 0.111** ——
和上一节那个 bug **是同一个错数**，两个不同成因撞出同一个错误答案。

判据落在 `verifier_health.agent_ran`（与 `verifier_ran` 同一个定义处），
返回三态 True / False / None。三处自证：

| 变异 | 预期 | 实测 |
| --- | --- | --- |
| 共享模块里 `agent_ran` 恒 True | 复算与进度**同时**翻 | 分母 2/3 → 3/3，进度标记 1 → 0 ✅ |
| 改用 falsy 判断 | 基线被动到 | 10/10 → 9/10，0.100 → 0.111 ✅ |
| 消费者自己数 token 不 import | 门禁翻红 | 31 pass / 1 fail ✅ |

**门禁自己也有一处静默失效，是变异自证抓出来的。** 新加那条断言初版写
`/def agent_ran/`，而它是**子串匹配** —— 把定义改名成 `agent_ran_RENAMED`
（消费者 import 当场 ImportError）**依然匹配得上，那次变异没有翻红**。
补上 `\(` 后才真的会红。一条不会红的断言比没有断言更糟：它占着位置，
让人以为这里有防线。

### 补跑那两题：上游额度耗尽是**第二种**基础设施故障，与 502 不同源

规则 ④ 上线后当天就抓到第二例，而且成因**不一样** —— 这恰好证明判据没有
写死在某一种坏法上（那是本 Note 反复踩的那个坑）：

| 题 | 上游报什么 | 计数 |
| --- | --- | --- |
| `polyglot-c-py` | 502 `Remote end closed connection without response` | 断连 19 次 |
| `regex-log` | **403 `pre_consume_token_quota_failed`（令牌额度不足）** | 30–34 次 |

两者的表征完全一致：`num_turns=0`、in/out token 双 0、`reward=0.0`、
verifier 判分正常。**如果规则 ④ 当初写的是「grep 502」，第二例就漏了** ——
与初版规则 ② 写死 `command not found` 是同一个错误形状。

⚠️ **额度恢复后 `fix-code-vulnerability` 自己跑通了**（29 条消息 / 25 次工具调用 /
14 allow 0 deny），此刻上游只剩瞬时 429（`当前分组上游负载已饱和`）而重试链能吃掉。
所以**不是整轮报废，是那两题报废** —— 这个区分决定了补跑成本是 ~$1 还是 ~$7。

**于是加了按题补跑**（`run-permission-switch.sh` 第二个及之后的位置参数 → harbor 的 `-i`，
支持 glob）。自证两向：不给题名时命令行里**一个 `-i` 都不许出现**（否则跑成空集，
而空集会安静地"全部通过"）；给两个题名时渲染成两个独立 `-i`。用假 `harbor` 拦住
真实调用来验命令行渲染，$0。

**补跑必然产生第二个 job 目录，于是复算脚本要能合并** —— 这里有一条不能省的纪律：
**同题多 job 时靠后的覆盖靠前的，且每题必须标出处**。不标就是把两批不同时间、
不同上游状态的数据无声混进同一个分母，而**混完之后没有任何东西会报错**。
合并自证：拿基线 + 本轮两个真实 job 跑，逐行比对 10 题 —— 被覆盖的行等于新 job 的值、
保留的行等于旧 job 的值，**0 行不一致**，判据 ① 总数仍是 144/178；
变异把覆盖方向改成「先到先得」，`chess-best-move` 的出处当场从 `permswitch-r2`
翻回 `a11-sid`。「出处」列只在合并时出现（单 job 时每行都一样，那列是噪音），
但合并时它不是可选的。

### 换档到底买到了什么：**轮数预算的有效利用率**（这是机理，不是期望）

基线逐题复算「40 轮里有多少调用是废的」——分母是该题的总调用数：

| 题 | 调用 | 被拒 | **有效调用** |
| --- | --- | --- | --- |
| qemu-alpine-ssh | 40 | 27 (68%) | **13** |
| qemu-startup | 41 | 26 (63%) | **15** |
| polyglot-c-py | 33 | 20 (61%) | **13** |
| build-cython-ext | 39 | 22 (56%) | **17** |
| sqlite-with-gcov | 40 | 22 (55%) | **18** |
| regex-log | 33 | 14 (42%) | **19** |
| chess-best-move | 84 | 11 (13%) | 73 |
| log-summary-date-ranges | 8 | 2 (25%) | 6 |

**5 个撞满预算的样本只拿到 13–19 次有效调用**，而对照 mini-swe-agent 是
**8 步解出**。换句话说：基线不是「40 轮不够」，是**40 轮里有一半以上在撞墙**，
而每次撞墙还要烧掉一轮预算。这是「非能力原因混进能力账」的**可量化形状** ——
比「144 次拒绝」这个总数更能说明为什么 0.100 不可信。

⚠️ **但这仍不是「换档必然提分」的证据**：它只证明预算被浪费了，
不证明省下的预算足够做对题。第 1 题就是反例（拿到 95 次有效调用，仍未解出）。
真正的判据在剩下那 5 个高拒绝率样本上。

**真实容器里已核**（不是构造的）：`sid_permission_mode_requested =
dangerously-skip-permissions`、`sid_permission_denials = 0`、
`sid_permission_by_decision = {'allow': 95}`、`sid_commit = 7f437eb8…`
（`artifact-bytes`，缺口 B 闭环）、缺口 A 那个字段读到 `0`。
容器命令行实测长这样，**裸 flag、不带值**（坑 3 在生产路径上被排除）：

```

  --max-turns 40 --dangerously-skip-permissions -- '...'
```
