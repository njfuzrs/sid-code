# 进程内子代理的工具批次在 abort 后停止启动剩余工具

## 决定了什么

`packages/core/src/agent/tool-executor.ts` 的 `executeTools` 在两处「启动工具之前」判断 `signal.aborted`：

- 串行批次：逐个工具执行前检查。
- 并发批次：`runWithConcurrencyLimit` 新增 `shouldStopLaunching` 参数，worker 每次取任务前检查。未启动的槽位返回 `undefined`，调用方补占位。

中断后没执行的工具一律补 `tool_result`（`is_error: true`，文案 `SUBAGENT_ABORTED_TOOL_RESULT` =「工具未执行：子代理已被中断」），保持 N 进 N 出。这些工具没有 fire PreToolUse，所以不补 PostToolUseFailure。

修复前 ESC 之后剩余工具照样走 PreToolUse → 权限 → `execute`。`write.ts` / `edit.ts` 自身不看 signal，会在用户要求停下后真的落盘。主循环（`query/tool-executor.ts`）和 spawn 子代理（每次只回传一个 `tool_use`）没有这个问题。

## 放弃了什么（以及为什么不选）

- **方案原写的「批次开始前」第三处检查**。变异自证里单独删掉它测试不变红：串行前检查和 `shouldStopLaunching` 已经覆盖每一个启动点，批次级检查是冗余的。恒绿的检查留着只会让人误以为它在保护什么，所以去掉。启动点级检查也不依赖 `partitionToolCalls` 的分批形态。
- **像主循环那样中断时向上抛**。调用方 `agentic-loop.ts` 没有接这个异常的收尾逻辑，抛出会改变子代理的结束形态。占位结果写回后，下一轮 LLM 调用会因 signal 已中断自然结束。
- **等「同一能力双执行路径」收口一起修**。write/edit 正在中断后落盘；而且收口后的 `runToolUse` 只管单次执行，「abort 后停止启动」这一层仍留在 `executeTools`，现在修的代码会原样保留。
- **改 spawn 子代理路径**。它没有批次，stdout 读取循环已检查 `signal.aborted`。

## 拿什么证明它生效了

新增 `packages/core/tests/agent/subagent-batch-abort.test.ts`，断言 `execute` 调用次数与 PreToolUse 触发集合，不只看结果文案：

- A 串行 s1/s2/s3，s1 中 abort → 只执行 s1，s2/s3 占位。
- B s1 后接并发 r1/r2，s1 中 abort → r1/r2 不执行。
- C `SID_TOOL_MAX_CONCURRENT=1`，r1 中 abort → r2 不启动。
- D 不 abort → 5 个全部执行，结果按原序。
- 调用前已 abort → 一个都不执行。

修复前跑：A/B/C/预 abort 4 条红（`中断后串行工具仍被 execute` / `中断后下一批次仍被 execute` / `中断后并发批次内排队任务仍被启动`），D 绿。
变异自证：删串行前检查 → A 与预 abort 红；删 `shouldStopLaunching` → B、C 与预 abort 红；恢复后 5 pass。
`subagent-hook-pair-invariant.test.ts` 8 条仍全绿，占位结果不留悬空的 Pre。
