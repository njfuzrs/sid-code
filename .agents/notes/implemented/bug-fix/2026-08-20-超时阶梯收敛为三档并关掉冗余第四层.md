# 超时收敛为三个不同谓词的阶梯，关掉冗余的 fetch 绝对硬顶，并把休眠扣减下沉到流式路径

## 决定了什么

方案 `20260817-GLM-5.3思考阶段卡死-300s硬顶掐断丢弃已累积内容-修复方案.md` 的
**PR7（P0-3）/ PR8（P2-6）/ PR9（P0-6）/ PR10（P0-4）** 四条合成一个单元。

合成的理由：它们回答同一个问题 —— **一条健康的慢流为什么会被杀，以及杀了之后为什么查不出是谁杀的**。
PR10 定义三档谓词，PR7 关掉那个与档③谓词重合、且开枪不留痕的第四层，
PR9 修掉三档共有的"休眠让判据算错"，PR8 补上"怀疑网关时拿什么去对账"。
拆开做的话，PR7 单独上线会退回 0 层（半开连接无人回收），PR10 单独上线会留着一个
默认开启的第四层把新阶梯架空 —— 这四条的验收互相依赖。

### PR10：三档阶梯（`config/network-profile.ts` / `llm/stream-lifecycle.ts` / `config/settings/types.ts`）

改造前六个阈值默认全是 300s，其中三个（fallback 无进展上限 / watchdog / fetchAbsolute）
**谓词完全相同** —— 都是"从某个起点起的绝对计时"。三份同谓词副本的可靠性等于一层，
归因难度是一层的三倍。所以这次改的**首先是谓词，其次才是数值**：

| 档 | 字段 | 谓词（判什么） | 作用域 | 取值 |
| --- | --- | --- | --- | --- |
| ① | `idleTimeoutMs` | reader 连一个字节都收不到 | 单次 `reader.read()` | 240s |
| ② | `contentProgressTimeoutMs` | 有字节但无有效内容（keep-alive 不续命） | 一次 attempt | 480s |
| — | `overallTimeoutMs` | ②的请求级软兜底（不因事件重置） | 一次请求 | 1500s |
| ③ | `maxTurnDurationMs` | 任何未知挂起根因，不感知进展 | 整轮（含重试+退避） | 90min |

连带三项：
- `watchdogNoProgressMs` 300s → 720s。**必须比档② 更宽**：watchdog 是远端观察者，
  读的是 provider 广播的快照、信息严格更少；信息更少的一层更激进，就会抢在 provider
  判定前开枪，而它的记录里没有"哪一档、哪个阈值"。
- `maxTurnDurationMs` 30min → 90min。不抬就会被 `fallback.ts` 的 S3 判据
  （剩余预算 ≤ 退避 + MIN_USEFUL_ATTEMPT → 停止重试）把重试预算判死 ——
  等于放宽了超时却关掉了保成功的另一半。
- `LIFECYCLE_PRESETS` 的 `subAgent` / `sideCall` 两档**从 BASE 解耦**成显式绝对值。
  原来三档全按倍率派生，BASE 一抬会把 `sideCall.overall` 60s → 144s 一起放大，
  **方向与设计意图相反**：side-call 是失败即静默降级的旁路，本该比主链路更早放弃。

另外把 `idle / contentProgress / fetchAbsolute / overall` 四项接进 `settings.json`
（此前只认 env、schema 里没有字段位，用户改 settings.json 完全调不动 —— §4.6 的"伪配置"）。
provider 实例读不到 settings，所以走 `registerNetworkTimeoutSettings()` 由 `app.ts` 注册一次快照。

### PR7：`fetchAbsoluteTimeoutMs` 默认关闭 + `TimeoutError` 纳入可重试

`openai.ts` 两处 `AbortSignal.timeout(...)` 从无条件装上改为**仅在显式配置时装**。
它是第四层，谓词与档③重合，而三条理由让它成为净负值：
职责已被档①（半开=零字节）与档③（未知根因兜底）双重覆盖；
它是唯一把 deadline 委托给 runtime 的一层，runtime 的 abort **不带可归因 reason**；
它**不写任何事件**（不经 `emitTimeoutFired`）—— 这正是上一轮排查被
`Counter({'fallback_stream_timeout': 24})` 带偏的结构性成因。

分类仍要修（用户可以显式开启，那时归因必须对）：新增 `isRuntimeTimeoutError()`，
`classifyError` 把 `TimeoutError` 归成 `RetryableError("timeout")`。
判据是结构性 `err.name`，**不看消息文本**。它与 `isAbortError` 刻意互斥：
认成 abort 会被当"用户取消"静默吞掉，比崩溃更难查。
`cli.ts` 两个全局兜底也补了短路 —— 它的 reason 是 DOMException 对象而非裸字符串，
两个 abort 白名单都管不到它，此前会一路走到 `process.exit(1)`。

### PR9：休眠扣减下沉到流式路径

休眠扣减此前是 `query/loop.ts` 的局部能力（`sleepPause` 在 fallback / lifecycle /
parseSSE 三个文件 grep 命中为 0）。轨迹实证：一次 `sleep_ms ≈ 281s` 的休眠让 fallback
杀掉了一条**真实无进展仅 3.4 秒**的健康流，而同一时刻 loop 的 watchdog（扣了休眠）判定正常。

`shared/utils/sleep-detect.ts` 新增两件东西：`startSleepObserver()`（引用计数的进程级
观测器，5s tick 记账本）与 `createSleepAwareDeadline()`（`remainingMs()` = 阈值 −(挂钟差 − 休眠)）。
三处消费：fallback 流超时 / lifecycle 的 content-progress 与 overall / parseSSE 的
idle timer 与 `contentElapsed`（外加 stallLogger 的口径）。
定时器形态刻意不动（不改成轮询，保留既有精度），改的是**回调里先二次核对**：
`remaining > 0` 说明这一枪是休眠补发的 → 重排而非开枪。

### PR8：`raw.jsonl` 保留网关 request-id

新增 `api/request-id.ts`：三条 provider 路径在拿到响应头时 `recordRequestId()`，
`loop.ts` 组装 AfterModel 时 `takeLastRequestId()` 取走（读一次即清），
落进 `raw.jsonl` 的 `response.gateway_request_id` 与 `events.jsonl` 的 AfterModelRaw。

## 放弃了什么（以及为什么不选）

**① 把 `fetchAbsoluteTimeoutMs` 抬到 1800s（第五轮的原判断）。**
抬档只是把它藏进 30min 硬顶的阴影里，形态不变：仍然是绝对计时、仍然不带 reason、
仍然不写事件。而它掐断健康流的能力不因阈值变大而消失 —— 只是发作频率降低，
下次发作时排查难度一模一样。默认关闭 + 留旋钮才是形态修复。

**② 直接删掉 `fetchAbsoluteTimeoutMs` 的代码。**
与 loop-detection / maxSessionDurationMs 的既有范式不一致（那两个也是翻默认值、留旋钮）。
且删了之后用户遇到我们没预见的 hang 形态时无路可走。

**③ 让 `network-profile.ts` 直接 `getSettings()` 来打通 settings。**
本文件刻意不依赖 Config/settings（文件顶部注释写明：避免与 config.ts 的双向类型依赖），
且会给 provider 热路径引入磁盘读，缓存失效时机不受本文件控制。改为注册快照。

**④ 让各层自己用 `isSleepGap()` 自测休眠。**
一次性定时器的 expected 就是它自己的阈值（如 300s），`isSleepGap(actual, 300_000)`
要求迟到超过 3000s 才命中 —— 对 281s 的休眠**恒为 false**。判据必须来自一个
tick 间隔足够短的独立观测者，这是 `startSleepObserver` 存在的全部理由。

**⑤ 靠"抬高阈值"消化休眠。**
历史记录里单次休眠达 939~946s，任何固定阈值都会被足够长的休眠击穿。

**⑥ 用 `AbortSignal.timeout` 抛出的错误消息文本判超时。**
memory `stream-timeout-misclassified-as-cancel-rootcause` 记的正是这个教训。
runtime 文案随引擎/版本/locale 变，`name` 是规范固定的。

**⑦ 把 request-id 存成裸字符串。**
本仓两族网关头名不同（`x-oneapi-request-id` / `x-shellapi-request-id`），
只留值就分不清该拿它找哪一方对账。存 `{ header, value }`。

**⑧ 对 request-id 做前缀通配（"任何 `*-request-id` 都算"）。**
这个字段是要拿去找网关方对账的，收错比没收更坏 —— 对方按一个不存在的 id 查，
会得出"没有这次请求"的错误结论。用显式闭集清单，加一项的成本是一行。

**⑨ 让新哨兵和 `network-profile.test.ts` 都钉具体数值。**
两处钉同一个字面量，调档时会同时红两处、其中一处的注释还落后于事实。
数值归 `timeout-ladder-sentinel.test.ts` 一处管，旧用例改成钉不变量
（"不分档"、"显式注入原样透传"）。

## 拿什么证明它生效了

**前置门禁（PR8 的"先抓包"要求）** —— 真打了两族网关各一次，只看响应头：

```
$ curl -D - -X POST https://uniapi.ruijie.com.cn/v1/chat/completions ... (stream:true)
x-oneapi-request-id: 202608191725212894588638268d9d6k3FBbQrv
$ curl -D - -X POST https://code.ppchat.vip/v1/messages ... (stream:true)
x-shellapi-request-id: 2026082001254269571978117037044
```

两族都下发、但头名不同 —— 这直接决定了候选清单的形状与"必须留头名"的结论。
探针脚本用后即删（临时文件，不入库）。

**PR7 的关键实证已从文档搬进常驻回归**：
`tests/llm/fetch-absolute-timeout-cuts-progressing-stream.test.ts`
起一个每 20ms 稳定产出 chunk、总时长 2000ms 的本地 SSE 服务，给 300ms 的
`AbortSignal.timeout`。实测：`chunks > 0`（断之前一直在产出）、
`elapsed < 1500ms`（在硬顶量级上断的）、`err.name === "TimeoutError"`。
这条以前只是文档里的一段 `bun -e`，改回默认开启不会红任何测试 —— 现在会。
