# 真实报错到不了 TUI：三处「在抛出点丢弃」+ 两套平行判据

## 决定了什么

让网关 / 大模型的**真实**报错信息一路走到 TUI，而不是一律退化成通用「运行错误 /
请检查错误详情」。修的是**同一条链路上的 7 个缺陷**，共改 6 个源文件：

| # | 文件 | 缺陷 | 修法 |
| --- | --- | --- | --- |
| 1 | `llm/fallback.ts` | 四条「重试耗尽」出口，**只有 ask/abort 那条漏拼 `rootCause`** —— 而它恰是生产默认路径（`fallbackSwitchMode` 默认 `"ask"`，钩子返回 abort） | 补上 `${rootCause}` |
| 2 | `llm/fallback.ts` | ask 弹窗的 `reason` 是常量 `"主模型重试耗尽"`，用户在「等一等 vs 换模型」这个决策点上看不到根因 | 改成透传 `ctx.lastRetryError` |
| 3 | `llm/error-messages.ts` | `inferErrorCode` 认不出网关中文措辞。实测「当前分组上游负载已饱和」→ `undefined` | 补网关措辞 + 402/余额族 |
| 4 | `llm/error-messages.ts` | 状态码用裸 `.includes("429"/"502"/"400")`，被更长数字串误命中 | 复用 `errors.ts` 的 `hasBoundaryDigits`（导出之） |
| 5 | `query/stream-processor.ts`<br>`entrypoints/headless.ts` | 流内 `error` 事件的 `statusCode`/`type`/`streamLevel` **在 `throw` 那一刻全部丢弃**，UI 只能从文本猜 | 新增 `LLMStreamError` 载体，经 `fatal_error.errorCode` 送到 UI，`app.ts` **结构化优先、文本兜底** |
| 6 | `ui/components/RetryStatus.tsx` | `RetryStatusInfo.error` 是**死接线**：app.ts 一直在写，组件从未读过（唯一形似匹配是 `theme.status.error`，一个颜色） | 渲染它（`summarizeRetryError` 单行截断） |
| 7 | `app.ts` `classifyRetryKind` | **第二套平行判据**：自带 `/429|rate.?limit|quota/` 正则，与文案表各自演进 | 收敛为复用 `inferErrorCode` |

顺带按 cc 官方《错误参考》页把覆盖率从 **10/46 拉到 46/46**，新增两个终态码
（`usage_limit_reached` / `context_overflow`）——判据是「用户下一步动作是否不同」，
其余官方措辞一律复用既有码（认证族 13 条全归 `auth_failed`：动作都是「去修凭据」）。

## 放弃了什么（以及为什么不选）

**不为每种官方措辞立一个错误码。** 46 条里只新增 2 个码。`Invalid API key` /
`OAuth token expired` / `AWS authentication failed` 的下一步动作完全相同，各立一码只会
把文案表撑大，而用户看到的建议一模一样。立码的判据是**动作分叉**，不是措辞分叉。

**不在 TUI 侧做"更聪明的文本猜测"。** 一度想给 `inferErrorCode` 加更多正则。否决理由：
猜的两个方向都已实测出错（猜不出 + 猜错），再加正则只是把误判概率挪个位置。正解是让
**上游明确给出的** `statusCode`/`error.type` 别在半路被丢掉 —— 缺陷 5 才是根因，
关键词表只是兜底层。

**不把 `RetryStatus` 的错误文本改成 `wrap="wrap"` 多行。** 提示条在动态区每 500ms 重渲，
网关文案带 request id 实测 80+ 字符，wrap 后占 2-3 行且随倒计时抖动。改单行截断，
完整原文由错误面板承载（那里本来就不截断）。

**`classifyRetryKind` 没有原地扩正则，而是删掉自己那套。** 扩正则能过测，但"两套判据"
这个根因还在 —— 下次往文案表补措辞时，提示条又会落后。

## 拿什么证明它生效了

**变异自证（5 处，把修复改回旧写法必须红）** —— 这是本次唯一硬证据，先于"测试全绿"：

- 删掉缺陷 1 的 `${rootCause}` → 断言收到的字符串**逐字复现用户报的那句**
  `"主模型请求失败，已终止本轮。可重新发送消息重试，或用 /model 切换模型。"`（1 fail）
- 缺陷 2 改回常量 → `reason` 断言红（1 fail）
- 缺陷 3/4 改回裸 `includes` + 删网关措辞 → 3 fail
- 缺陷 5 改回 `throw new Error(...)` → 3 fail
- 缺陷 6 删掉 `{status.error ? …}` → 2 fail

**修复过程中被测试当场抓到的两个自造缺陷**（记下来，因为它们比通过的用例更能说明口径）：

1. 收敛 `classifyRetryKind` 时丢了旧正则里的 `capacity` 与 `quota` 语气 →
   既有单测立刻红，补回。
2. 新加的 `usage_limit_reached` 用子串 `"usage limit"` 匹配，把官方文案
   `Server is temporarily limiting requests (not your usage limit)` 判成**终态** ——
   而该页明确写着它与配额无关、会自动退避重试。判成终态的后果正是本仓库修过一次的
   「限流卡片不消失」：请求早已恢复，红卡永久悬挂。改为先用整句否定语挡掉。
   **这条是子串匹配的典型陷阱，新增关键词时必查反例。**
