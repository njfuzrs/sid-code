# 远程接管轨迹的三处口径修复：confirm_via 消费语义、bridge 标记复位、发送失败分类

## 决定了什么

PR #599（远程接管进轨迹）合入后复核发现三处**会污染证据列的口径缺陷**。本 PR 只修口径，
不扩事件、不改对外契约：

1. **`confirm_via` 从「进程级 sticky 读」改成「source=user 时消费一次」**
   （`permission/decision-telemetry.ts` 的 `consumeConfirmVia`、`analytics/events.ts` 两处门面）。
   原实现 `readConfirmVia()` 纯读不复位，而 `needsPrompt=true` 的决策可能是 classifier / hook
   在弹窗期间抢先赢了（`query/tool-executor.ts` 的记录点注释自己写了这一点）——那次并**没有人
   被问**。于是「一次远程批准」会把通道写进后续所有 `needsPrompt=true` 的决策上，
   A11/A12 的 `confirm_via=="bridge"` 计数与 `BridgePermission allow` 对不上账。
   PR #599 在 `bridge-confirmation.test.ts` 的 `afterEach` 复位 `setConfirmVia(null)`，
   当时被描述成「测试污染」——其实是同一个生产缺陷的外溢。
   **修法两条同时上**：门面只在 `source === "user"` 时读（`normalizePermissionSource` 已经把
   classifier / hook / timeout 分开），且读后清空（一次确认只对应一条决策）。

2. **`setBridgeSessionFlag(true)` 纳入 try**（`cli/src/app.ts` 的 `runBridge`）。
   原实现 `setBridgeSessionFlag(true)` 之后紧跟 `await this.init()`，两者都在 try **之前**，
   复位却在 finally 里：`init()` 或 `new BridgeRunner` 抛错时进程级标记永不复位，
   同进程后续会话的 metadata 会被错标 `bridge: true`。

3. **`BridgePermission` 的发送失败与远程拒绝分开**（`bridge/permission-proxy.ts` + `bridge-telemetry.ts`）。
   原实现把 `transport.write` 失败也记成 `decision: "deny"`，远程拒绝率的分子因此混进
   「请求根本没送到」的链路故障。`decision` 三分集保持不变（结果确实是不允许），
   新增可选 `delivery: "write_failed"` 标出成因；缺省 = 正常送达。

4. **顺手收紧`permissionTimeoutMs` 的两处兜底**：`BridgeRunner` 的事件字段与
   `PermissionProxy` 的实际计时各自写 `60_000`，改一处就会出现「轨迹里记的档位」与
   「真正生效的等待时间」不一致。提到 `bridge/types.ts` 的 `DEFAULT_PERMISSION_TIMEOUT_MS`。

配套补的测试（都是先补断言、再做变异自证）：

- `permanent_failure` 相位**此前零行为测试**（门禁里的 `toContain('"permanent_failure"')`
  被 `consumePermanentFailure` 的**默认参数值**满足，删掉真实调用仍绿）：
  新增「连上后服务端 close(4001) → permanent_failure 1 条 + stopped 1 条」。
  顺带发现 `waitForPermanentFailure()` 的契约是 **resolve(Error)** 而不是 reject
  （`runBridge` 用 `.then(failure => reject(failure))`），首版测试按 reject 写是错的。
- 发送失败 `delivery=write_failed` 用例。
- `confirm_via` 补 `sdk` 通道（四通道里唯一零覆盖的）、classifier 抢赢不带字段、消费一次三条用例。
- digest `triggerCounts` 此前零测试：新增「无 bridge 事件整节不出现」「只数 kind=user_message」
  与 `renderHuman` 输出断言。
- 门禁把 `toContain('"permanent_failure"')` 改成「`waitForPermanentFailure` 函数体内确有
  `consumePermanentFailure()` 调用」，并给「恰好三处 emit」补了棘轮维护说明。

## 放弃了什么（以及为什么不选）

- **放弃把 `confirmVia` 从 `requestUserConfirmation` 返回值带出来**。那要改
  `ToolExecutorDeps.requestUserConfirmation` 的返回类型，30+ 处测试实现与三条鉴权路径都受影响；
  而消费侧加 `source=user` 门槛 + 取走即清已经能消除已观测到的错标。等真正需要「同一次确认
  在多条决策间精确配对」时再动契约。
- **放弃给 `BridgePermission.decision` 加第四个值 `send_failed`**。`decision` 是既成口径
  （allow / deny / timeout），加值会让消费侧的历史聚合整体平移；用可选 `delivery` 字段
  承载成因，老消费方读到的 `decision` 语义不变。
- **放弃给 `BridgeRunner` 加公开的 `sdkCanUseTool` 注入点**。测试用一次
  `as unknown as` 强转即可覆盖 App 的真实分支（与 `requestUserConfirmation` 的既有测法一致），
  不为测试扩大生产 API。
- **放弃把 digest `triggerCounts` 的「无事件即 undefined」改成输出 0**。0 会把「没被遥控过」
  与「这套埋点没接线」混成同一个数，这正是方案 §T5 明确要避免的。
- **放弃在 `trigger-events-wiring.test.ts` 里断言 `sessionEmits >= 1`**。实测过：删掉
  `connected` 的 emit 后旧断言照样绿（PR #599 已记录同一形态）。「恰好三处」是刻意的棘轮，
  新增相位时必须同步改数字。
