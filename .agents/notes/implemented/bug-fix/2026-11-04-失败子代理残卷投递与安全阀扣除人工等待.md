# 失败子代理的残卷必须走到模型手上：通知走 `<error>` 通道、`.output` 收纯工具轮、墓碑指向 sidechain，安全阀扣除人工等待

## 决定了什么

方案《20261104-会话 f5beebde 复盘》PR3（F3 1–6），六处改动，都围绕同一句话：**失败路径上
产出的东西，此前一条都没走到模型手上**。

1. **失败通知带上完整残卷**（`task/agent-task.ts` 的 `failAgentTask`）。此前 `enqueueTaskNotification`
   只传 `summary`（`error.slice(0, 200) + "…[截断]"`），`TaskNotification` 上已有的 `error` 字段
   压根没传——于是 `formatNotification` 里那条 4000 字的 `<error>` 通道一直空着。现在传 `error`，
   `summary` 只留一行原因（从残卷的 `<interrupted-because>` 抽，取不到退回首行）。

2. **残卷写进 `.output`**（同函数）。在 `flushTaskOutput` **之前** `appendTaskOutput(taskId, error)`。
   终态保护前置：已被 kill 的任务不追写，`.output` 归 kill 路径收尾。

3. **纯工具轮也写 `.output`**（`agent/sub-agent.ts` 的 `onTurnEnd`，两条路径都改）。
   此前只在 `info.turnText` 非空时写；本会话三个后台子代理每轮都是纯工具调用
   （sidechain 里 assistant 文本块数为 0），`.output` 从头到尾是 0 字节。现在无文本时写一行
   `[轮次 N] 工具名(首参前 80 字) → N 字节 / 出错 / 结果未知`。

4. **残卷收工具证据**（`agent/salvage.ts`）。`SalvageCollector` 新增 `toolEvidence`：保留最近 6 条
   **成功**工具结果的「调用描述 + 结果前 800 字」，`buildSalvageOutput` 输出 `<tool-evidence>` 段，
   排在 `<findings>` 之后。**这是让只读核查型子代理的成果第一次进残卷的那一半**——它们的
   价值全在工具结果里（git 输出、文件内容）。

   配套把 `agentic-loop.ts` 的 `onTurnEnd` 契约扩了一个**可选**字段
   `tools[].result?: { content, isError }`，在 `execute_tools` 分支按 `tool_use_id` 配对填充。
   并发批次会重排结果顺序，按下标配对会张冠李戴，所以用 id。

5. **墓碑指向 sidechain**（`task/lifecycle.ts` + `task/types.ts` + `sub-agent.ts`）。
   `LocalAgentTaskState` 增 `sidechainFile`，`openSidechain` 之后经一条私有方法写进 registry；
   墓碑记录时 `existsSync` 校验（路径不存在就不给假指针），文案加一行
   `完整轨迹（不会被清理）: <path>`。`.output` 会被驱逐删除，sidechain 不会。

6. **安全阀扣除人工等待**（`task/registry.ts` + `query/human-input-gate.ts`）。
   `TaskStateBase` 增 `hitlWaitAtTerminalMs`，由 `updateTask` 在「非终态 → 终态」的跃迁上写快照；
   未送达分支的截止时刻改成 `end + 10min + (当前等待累计 − 快照)`，且 `isAwaitingHumanInput()`
   为真时直接不驱逐。等待期间 `scheduleSafetyValveWake` 不按 deadline 排（会 0ms 空转），
   改成一分钟轮询；`human-input-gate` 新增 `onHumanInputWaitEnd` 订阅，等待结束这一刻重新排序。

## 放弃了什么（以及为什么不选）

- **只在 `summary` 里放更多字**：summary 是 TUI 的一行标题，塞进几 KB 残卷既渲染不了，
  也进不了模型上下文。已有的 `<error>` 通道 + `truncateForNotification` 的 output-file 指针
  本来就是为这个场景设计的，只是没接上。
- **把工具结果全文写进 `.output`**：`.output` 是给 `task_output` 增量读的，一次只读核查会产出
  几百 KB，同时把 sidechain 的职责重复一份。摘要回答「做了什么、拿到多少」，全文留在 sidechain。
- **删掉安全阀**：`.output` 会无限堆积；方案 §4 已否决过。这里只修计时口径。
- **等待期间停掉安全阀定时器、等待结束再精确恢复剩余时长**：需要在 gate 里维护「剩余时长」状态，
  比扣减多一份状态机。轮询一分钟的代价是一个 unref 定时器，可忽略。
- **给 `evictDecision` 只留算术扣减、不留 `isAwaitingHumanInput()` 短路**：两者在数学上等价
  （等待期间 deadline 与 now 同步后移），但判据本身要能独立说清「等人不是故障」，
  不能只靠一个恒等式 —— 所以两道都留。
- **把失败残卷直接作为 tool_result 塞回主循环**：后台子代理的结果投递所有权在通知
  （`agent-task.ts` 注释里的 F1 约定），另开通道会造成双投递。
- **改 `disk-output.ts` 让 `evictTaskOutput` 取消在途 drain**：写测试时发现驱逐与 drain 有竞态
  （unlink 之后 drain 仍 appendFile → ENOENT）。那是磁盘层既有的并发形态，与 F3 无关，
  本 PR 只在测试里先 flush 规避，不动它 —— 混进来会让 review 分不清哪些改动是必要的。

## 拿什么证明它生效了

**新增单测 31 条，全绿**：

- `packages/core/tests/agent/salvage-tool-evidence.test.ts`（15 条）：纯工具轮也能收到残卷、
  错误结果不进证据、空结果不进证据、只保留最近 6 条、单条 800 字截断、`<tool-evidence>`
  排在 findings 之后、无证据不输出空段、属性引号转义；`formatToolTurnLine` 的字节数 /
  出错 / 结果未知 / 多工具一行 / 80 字截断 / 空工具返回 null。
- `packages/core/tests/task/failure-salvage-delivery.test.ts`（10 条）：残卷写进 `.output`、
  通知 `<error>` 含残卷与 `<tool-evidence>`、summary 只留一行原因、裸错误取首行、
  超长残卷 4000 字截断并附 output-file、killed 不追写、前台 notify=false 仍写 `.output`；
  墓碑三条（有 sidechain 给指针 / 空 `.output` 也给指针 / 路径不存在时不记）。
- `packages/core/tests/task/safety-valve-hitl.test.ts`（6 条）：等待期不驱逐、等待结束后按
  「安全阀 + 等待时长」驱逐、终态之前的等待不扣、无等待时行为不变、已送达任务不受影响、
  终态快照值正确。

**未做的验证（诚实声明）**：方案 §4.5 第一条要求「子代理纯工具轮 + 第 3 轮 LLM 报错」的
