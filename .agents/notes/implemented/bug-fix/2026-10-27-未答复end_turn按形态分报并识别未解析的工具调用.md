# 未答复 end_turn 按形态分报，并识别「工具调用没被解析」

## 决定了什么

`detectUnansweredEndTurn`（`packages/core/src/query/unanswered-end-turn.ts`）命中时同时置 `_unansweredShape`，形态闭集为 `text_drift` / `thinking_only` / `unparsed_tool_call` / `empty`。新增的 `unparsed_tool_call` 优先于 A/B 判定：未答复的内容里带着模型原生工具调用标记（DeepSeek DSML，含写坏的变体）。

loop.ts 按形态做四件事：

- 选警告文案（`describeUnansweredRetry` / `describeUnansweredExhausted`）。
- 选回注提示（`buildUnansweredEndTurnMessage(shape)`）。`unparsed` 那套说明工具没执行，要求先核实、拆小参数后正式重发，不要求 `todo_write`。
- 每次命中落一条 `UnansweredEndTurn` 事件（shape / attempt / exhausted / provider / model）。
- digest 新增「未答复 end_turn」一节，按形态和模型分布展示，`unparsed_tool_call` 非 0 标红。

触发案例：20261026-153949-44168811 #70 与 20261026-155110-ef2ddda8 #44（deepseek-v4-1-flash）。两轮都是 end_turn 加唯一一个约 14k 字符的 thinking，内容是要 edit 追加进文档的正文，末尾残留 `</｜｜DSML｜｜ parameter>`。旧文案「疑似思考泄漏到正文」与事实相反（正文一字未发）。旧提示让模型多花一轮 todo_write（#72 / #46），且没点明写入没发生，模型只能再用 bash 自查一轮。

## 放弃了什么（以及为什么不选）

- **从思考文本里解析 DSML 并直接执行工具**。两例的起始 `invoke name=` 都已不在思考里，工具名和参数边界无法还原。就算标记完整，让一个非提交通道产生副作用也绕过了「模型正式发起调用」这个提交点。思考里的标记也可能只是推演或讲解，执行错了是写文件级别的副作用。因此只识别、不抢救。
- **只改文案、不改回注提示**。文案只影响人怎么排查，模型多烧的那一轮来自提示，只改文案修不到成本。
- **为 `unparsed` 单独设一条 continue 理由或计数**。它和 A/B 是同一道闸门、同一个续命动作，计数分开会让「同一条消息续命总数」超过 `MAX_UNANSWERED_RETRIES`。所以分的是形态，不是闸门。
- **判据用"思考里出现 DSML 一词"**。讲解协议时同样会出现这个词。现在要求竖线、DSML、协议标签名连续出现，先剔除代码块和行内代码，并且在已有实质正文（> SHORT_ANSWER_LEN）时不看思考。
