# monitor 退出时不再丢最后一批事件（含失败分片与 ALL_DONE 汇总）

## 决定了什么

修 review 文档《20261109-等待态四PR合入后review缺陷-修复与验收方案》的 D2（P0，来源 PR #683）。

- `packages/core/src/task/monitor-task.ts` 的 `MonitorRateGate` 新增 `drainAll(lines)`：
  把被持续阀拦下的暂存行与本批行按输出顺序合成**一条**事件，**不计每分钟窗口、不受总量阀**。
  `child.on("close")` 的退出冲刷改用它，不再走 `admit`。
- 修复前：close 回调把残行、200ms 批缓冲与暂存行合并后仍调 `admit`。持续阀已满时返回 `defer`
  （行被塞回 `deferred`，随后随 `ctl` 一起丢弃），总量阀已满时返回 `stop`，两种结果都让这批行静默消失。
  而它们往往正是脚本退出前的失败分片与 `ALL_DONE: fail` 汇总行——模型只看到「监控异常退出（退出码 1）」，
  不知道是哪个检查失败。
- 退出冲刷的行数上界 `MAX_FINAL_FLUSH_LINES = 200`，**保尾不保头**（汇总行在最后），
  超出时事件首行注明「前 N 行已省略，完整输出见 .output」。
- 删除 `takeDeferred()`：它唯一的调用点就是 close 的旧冲刷，语义已被 `drainAll` 吸收。
- 新增测试钩子 `MonitorGateLimits` + `spawnMonitorTask({ __gateLimitsForTest })`：
  总量阀用例要「把上限注入调小」，真跑 60 条通知不现实（持续阀每分钟只放 6 条）。

## 放弃了什么（以及为什么不选）

- **给 `admit` 加一个 `force` 参数**：`admit` 的返回值语义（emit / defer / stop）对退出路径没有意义，
  退出只需要「一条事件正文」。单独一个 `drainAll` 让「终态出口只认这一条冲刷路径」在 review 和后续守卫里
  一眼可辨，也不用在每个调用点判断 `force` 的分支。
- **退出前把限流计数器清零再走 `admit`**：等价于绕过限流，但把「绕过」藏进了状态修改里；
  下一个读者无法从调用点看出退出路径不受限，与 D2 的成因（代码与注释相反）同型。
- **在 `exit` 事件里冲刷（早于 stdio 关闭）**：会丢掉 `printf abc` 这类无换行残行，
  这是 T-M1-9 已经锁住的行为；close 仍是正确的触发点。
- **顺手把 D3（四个出口统一 `finalizeAndDrain`）一起做**：D3 是 `monitor-task.ts` 的更大重构
  （到期 / 限流停止 / `task_stop` 三条路径都要冲刷），验证面与 D2 的「正常退出」不同，
  单独一个 PR 才好回滚。本次只把 drainAll 这一块备好，D3 接入时四个出口直接复用。
- **顺手改 D18 的文案（「…另有 N 条」「共 N 条事件」）**：D18 要改的是限流合并文案与
  终态事件单位，属于独立缺陷；本次不改任何既有文案，避免把「不丢行」与「文案更准」混在一个 diff 里。

## 拿什么证明它生效了

- `bun test ./packages/core/tests/task/monitor-task.test.ts` → **20 pass / 0 fail / 168 expect**。
  新增 5 条：
  1. `drainAll` 合并暂存行与本批行、不受持续阀（纯逻辑）；
  2. `drainAll` 在总量阀已满时仍送出（纯逻辑）；
  3. `drainAll` 超过 200 行时保尾不保头并注明省略行数（纯逻辑）；
  4. **R2 迁入**：脚本 7 行 pass + `check8: fail` + `ALL_DONE: fail`、退出码 1 →
     断言事件串含两行失败信息、事件通知总数 ≤ 7（6 条正常 + 1 条退出冲刷）；
  5. 总量阀用例：注入 `totalNotifyLimit: 1`，脚本输出 `a` 后 1s 输出 `LAST` 并退出 →
     断言 `LAST` 以事件送达（修复前 close 的 `admit` 返回 `stop`，行被丢）。
  两条真实子进程用例都从 `spawnMonitorTask` 真实入口进，不直调 `drainAll`。
- 变异自证：把 close 路径改回「只处理 `emit`」（旧逻辑）→ 上面第 4、5 条**都红**
  （第 4 条失败于事件串不含 `ALL_DONE: fail`；第 5 条失败于事件串不含 `LAST`），
  同时 T-M1-5（退出码 0 无输出）也红——旧写法下空批次会被 `admit` 当成一条事件计入 `eventCount`，
  从侧面说明 `drainAll` 返回 `null` 的必要性。恢复后 20 pass / 0 fail。
- 门禁：`bun run affected-tests:run`（265 pass / 0 fail）、`make build`（产物自检通过）、
  `bun run lint`、`bun run format:check`、`bun run lint:boundary`、`bun run lint:command-system`、
  `bun run lint:legacy-tool`、`bun run typecheck:gate`（62/64，无新增）全部通过。
- 线上观测量（方案 §5.3 D2/D3 行）：抽样轨迹里 monitor 终态通知前是否有事件、
  失败分片是否 100% 以事件送达。本次只交付代码与回归门禁，线上抽样留待 E2E-2（方案 §7.2）。
