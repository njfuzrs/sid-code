# D6 判定唯一入口、D8 子代理延迟加载、D10 权限留漏斗 2

来源：`docs-research/sid-code/bugfixes/todo/20260920-工具调用层-写入门文档时核出的缺陷.md` 的 D6 / D8 / D10。文档写「D6 可并进 D1；D8/D10 先定口径再改」。三项都是「主循环修过、子代理没跟上」或「枚举在、调用无」，同一次审计、同一次交付，合一个 PR。

## 决定了什么

1. **D6** `judgeConcurrencySafe(tool, input?)` 提到 `tool-orchestration.ts` 当唯一入口。分区、流式执行器、`app.ts` 抢跑、子代理 fail-closed 都调它。判定抛错返回 `false`（unsafe），不再把整批分区或 fail-closed 炸穿。
2. **D8** 子代理延迟加载的门闩是「这个隔离 registry 里真有 `tool_search`」——有才 `setToolSearchEnabled(true)` + `activeDefinitions()`，没有就发全量。过滤层放行 `tool_search`（Layer 2/3/4 豁免，仍受 Layer 1 硬禁 + 用户显式 `disallowedTools`）。延迟名单只进发送副本，永不写回 `ctxMgr`；compact 成功后全量重播。`buildIsolatedToolRegistry` 跳过父级 `ToolSearchTool`，挂一份绑本池的新实例——父实例 activate 写的是父会话。
3. **D10** 删掉 `ToolFailureKind` 的 `"permission_denied"`。权限拒绝只走漏斗 2（`logPermissionDeny`），不进 `tool_call` / `tool_failure`。进程内与 spawn 子代理在权限通过之后补漏斗 1（call / success / invalid_input / tool_error / exception / aborted）；hook 阻止是真实调度失败，call + failure 成对。

## 放弃了什么（以及为什么不选）

- **D6 只给 bash 补 try/catch**：bash 的 parser 自己已经 catch，今天抛不出去。缺口在自定义 / 插件工具，以及 fail-closed 那条没包的路径。只补 bash 是治已经不炸的那条。
- **D8 无条件 `activeDefinitions()`**（文档方案 A 的朴素读法）：explore / 用户 `disallowedTools` 裁掉 `tool_search` 之后，模型看到延迟名单却调不出工具，盲调撞「schema 未发送」。门闩比无条件对齐更窄，也更安全。
- **D8 明确发全量并改注释**（文档方案 B）：`general-purpose` / 自定义 `"*"` 会把主循环故意藏起来的 MCP 一次性塞进上下文。子代理是 token 消耗大户，走最贵的定义通道。
- **D8 复用父级 ToolSearchTool 实例**：activate 写父 registry，子代理下一轮 `activeDefinitions` 仍看不到被调出的工具——延迟加载形同虚设，还污染父会话。
- **D10 在拒绝分支补 `logToolFailure({ kind: "permission_denied" })`**（文档方案 B）：漏斗 2 已经按 source / needsPrompt / reasonType 把权限账记清楚。再塞进漏斗 1 是把「拦了多少」和「工具真失败」重新混进同一个成功率分母——正是博客 §14 要禁止的。枚举里留一个没人调的值比没有更糟。
- **forked-agent 漏斗 1 一并补**：那条走调用方注入的 `canUseTool`，漏斗 2 已记 `context:"forked"`。和本次「权限不进失败率」搅在一起会让 PR 无法一次 review 完。
