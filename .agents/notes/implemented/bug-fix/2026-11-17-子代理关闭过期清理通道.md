# 子代理关闭过期清理通道，回到 2026-11-12 之前的已知良好配置

## 决定了什么

给 `ManagerOptions` 加 `staleToolOutputClear?: boolean`（默认 `true`），在
`ContextManager.commitStaleToolOutputClear` 最开头短路；三处**子代理**构造点显式传 `false`：

- `packages/core/src/agent/sub-agent.ts:executeInner`（内置类型路径）
- `packages/core/src/agent/sub-agent.ts:executeCustomInner`（自定义类型路径）
- `packages/cli/src/entrypoints/headless.ts`（spawn 子进程路径）

主循环（`packages/cli/src/app.ts`）**不传**，保持 2026-11-12 的决定。

改动后子代理只剩四条清理通道：遮罩 / 冷清理 / 大输出清理 / 压缩。这就是 11-12 之前的配置。

**为什么只在子代理侧关，而不是回滚整条通道**：K=8 / N=20k 是在**主会话**负载上校准的
（11-12 Note 的离线回放：323 个会话，额外缓存未命中 p95 0.81%），主会话侧收益证据成立；
而子代理侧从来没进过校准集，且它的负载形态与主会话根本不同 —— `collectActiveFiles`
只认 edit/write，子代理是纯只读负载，**一个文件都豁免不了**，于是它读的每一个文件
都会在 8 轮后被清成占位，然后重读。2026-11-16 实测 16 个子代理里 71.8% 的 read 是重复读，
报告里直接写「证据已过期清理」。

**为什么在 `commitStaleToolOutputClear` 开头短路，而不是把 K/N 调到无穷大**：短路连
`planStaleToolOutputClear` 的候选扫描都不做 —— 那是每轮一次的全量遍历（扫全部消息、
建三张表）；调门槛只是让它算完再返回空。

**回退口径**：子代理侧现在完全回到 11-12 之前的上下文策略。同模型 explore 上下文峰值
实测最大 16.1%，离窗口还远，窗口兜底由另外四条通道承担 —— 这条改动把「更准」优先于
「更省」，**主动放弃的是子代理侧那部分 token 节省**，换来去掉重读循环。

## 放弃了什么（以及为什么不选）

| 方案 | 否决理由 |
|---|---|
| 整条回滚（连主会话一起关） | 主会话侧的收益有 11-12 的离线回放证据（p95 缓存代价 0.81%），一起关等于把已校准的收益也丢掉；且主会话有 edit/write 活跃文件豁免，不会形成子代理那种「刚读就被清」的循环 |
| 给子代理单独调 K（如 K=30）或 N（如 N=100k） | 子代理负载上这两个量都没校准过，调大只是把循环推迟，不是消除；而且子代理上下文峰值只有 16.1%，本来就不需要这条通道 |
| 在子代理侧让 `read` 也进活跃文件（「读过就豁免」） | 那等于子代理侧这条通道永不触发（子代理几乎全是 read），效果与关掉相同，却多一套判据和一条要维护的分支 |
| 让子代理继承主会话的 `staleClearState` | 状态按 tool_use_id 索引，跨会话 id 不同构，继承不过来；且语义上子代理该独立决策 |
| 用环境变量/配置暴露给用户 | 这是「子代理这个负载形态不适合」的结构判断，不是用户偏好；开放成旋钮会出现「本机调过、CI 没调」两套行为，与 11-12 Note 拒绝 K/N 做成变量的理由一致 |
| 只改 spawn 路径（报告里观察到重读的那条） | 三处构造点是同一个负载语义。漏一处就是「一半路径还在循环」，而且不会报错 —— 这正是它需要接线测试的原因 |

## 拿什么证明它生效了

**G1 单测**：新增 `packages/core/tests/context/stale-clear-subagent-off.test.ts`，9 用例，分三组：

1. 选项语义（3 条）：`false` 不清理、**默认构造照常清理**（守住主循环不被误伤）、
   显式 `true` 等同默认。
2. 真实子代理执行路径（2 条）：内置类型与自定义类型各跑一次 24 轮 × 8,000 字符的
   read，断言**模型实际收到的 messages** 里没有清理占位。
3. 接线（4 条）：源码扫描三处子代理构造点都含 `staleToolOutputClear: false`、
   `app.ts` 不含、子代理构造点总数 = 3（新增第四处必须被看见）。

**变异自证**（每一项都是先改坏、确认变红、再恢复）：

| 变异 | 预期变红 | 实际 |
|---|---|---|
| 删掉 `commitStaleToolOutputClear` 的开关短路 | 选项语义用例 | ✅ 报出 `[已过期清理: read(...) 原始 8000 字符...]` |
| 删掉 `executeInner` 的传参 | 运行时内置路径 + 静态接线 | ✅ 两处都红 |
| 删掉 `executeCustomInner` 的传参 | 运行时自定义路径 + 静态接线 | ✅ 两处都红 |
| 删掉 `headless.ts` 的传参 | 静态接线 | ✅ 红 |

**变异过程中修掉了一个假绿门禁**（这一条比上面四项都重要）：运行时断言第一版是恒绿的，
两个独立原因叠在一起 ——

1. **工具名不在可丢弃白名单**：`buildReplacement` 只对 `DISCARDABLE_TOOLS`
   （read/grep/glob/ls/…）生成占位，第一版用的 `probe_read` 永远返回 null。
2. **工具被重建、文件也不存在**：`read` 在 `STATEFUL_TOOL_NAMES` 里，子代理会用
   `createStatefulTools` **重建真实 read**，把测试注册的 mock 同名工具替换掉；真实 read 读
   不存在的 `src/f1.ts` 只返回 284 字符错误，远低于 500 字符候选门槛。

两个原因都让「结果够大」这个前提不成立，于是「没清理」永远成立。修法是：在 tmpdir 里
写 24 个真实大文件（100 行 × 80 字符）让真实 read 去读，并加一道**假绿守卫**
`assertRealBigResults`（断言至少一条 tool_result 长度 > 4,000 且不含「文件不存在」），
再断言没有清理占位。修完后重做上面四项变异，运行时断言才真的会红。

判据参数也是实测标定的：10 轮×8k、18 轮×8k 都**不触发**（`roundsAfter >= 8` 只覆盖
前 `轮数-8` 条，累计释放量还要 ≥20k token），20 轮×12k / 24 轮×8k / 16 轮×25k 才触发；
取 24×8k 留余量。

**门禁**（worktree 内，2026-11-17）：

- `bun run affected-tests:run` → 4399 pass / 9 skip / 0 fail（431 文件，342s）
- `make build` → 自检通过（git-status 锚点、内置 skill、ripgrep 平台匹配）
- `bun run smoke` → 42 例全通过
- `bun run lint` / `format:check` / `lint:boundary` / `lint:command-system` /
  `lint:legacy-tool`（57=基线 57）/ `typecheck:gate`（62=基线 62）→ 全绿

**还没证明的**：本次不去证明「子代理侧关掉后 token 用量变化多少」。子代理峰值本来只有
16.1%，收益不在窗口占用而在「少走轮次 / 少重复读」，这两项要看 PR6 的 A/B（同模型
explore 报告对比 read 重复率与 turns）。本 PR 只负责把造成重读的机制拆掉。
