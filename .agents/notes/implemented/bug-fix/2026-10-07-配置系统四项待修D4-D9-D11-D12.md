# 配置系统剩余四项（D4 · D9 · D11 · D12）：权限规则热更新、settings 写入安全、敏感字段过滤锁形状、flagSettings 死缓存

## 决定了什么

- **D4**：`settingsChanged` 现在有权限侧订阅者。`RuleLoader.reloadFileSources()` 只清并重读文件型来源
  （policy / user / project / local），session / command / cliArg / flagSettings 等进程内规则保留；远程策略已注入时
  policySettings 不动。`PermissionChecker.reloadSettingsRules()` 同步 `this.rules`。`app.ts`
  `wireConfigAndElicitationHooks` 订阅 change 事件，重载完成后 `wireToolPermissionChecker()` 重新下发子代理 checker
  （它们是快照，与 W22 同理）。projectSettings 重载时照旧过不可信剥离。
- **D9**：`patchSettingsFile` / `writeSettingsFile` / `mergeMissingTopLevelKeys` 改用 `app-config.ts` 已有的
  `writeAtomic`（tmp + rename），写前调 `backupSettingsFile` 备份到 `<SID_HOME>/backups/`（只备份能解析的内容，
  每文件保留 5 份）。解析失败仍抛错（fail-closed 不变），但会把损坏文件留档，并在报错里给出最近一份可用备份的路径。
  新模块 `config/settings/backup.ts`。
- **D11**：`filterProjectSettings` 改为 `structuredClone` 深拷贝，返回值不再与入参共享嵌套引用。清单条目支持点分路径删除。
  新测试断言清单每一条都能在 `SettingsSchema` 上解析到字段，字段挪位置会让测试变红（`skipPermissions` / `yesMode`
  是 schema 未声明、靠 passthrough 透传的顶层键，测试中显式豁免）。
- **D12**：`setFlagSettings` 不再写那条永远读不到的 L2 条目，注释写明 flagSettings 不参与 L2/L3 缓存。

## 放弃了什么（以及为什么不选）

- **D4 重载全部来源（直接再调 `loadAll`）**：`loadAll` 不清旧值、只做 `set`。文件里删掉的规则会残留，而且会顺手抹掉
  或保留哪些运行期规则也说不清。所以单独写一个先清文件来源、再重读的方法。
- **D4 同时重放 `process.env` / TUI 状态**：Phase 1/2 env 的应用与信任对话框时序绑在一起（D3），在变更事件里重新应用
  B 档变量会重开 D3 的口子。本次只修权限规则这一半，env 不随文件热更新是有意保留的。
- **D9 把备份放在 settings 文件旁边**：project / local 来源在仓库 `.sid-code/` 下，备份落在那里会污染工作树、可能被误提交。
- **D11 把清单改成按 schema 路径声明的结构化列表**：改动面大，所有消费方（rule-loader 告警等）都得改。
  用点分字符串 + 形状测试，已经能拦住「挪字段后静默失效」这一类问题。
