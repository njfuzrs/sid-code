# 单条超大 user 消息：熔断文案补第三态、输入自动退回、收紧三处注入面

## 决定了什么

事故会话 `20261022-034121-20f64f92`：单条 user 消息估算 4500 万 token。所有压缩层都按消息删除或摘要，不会删本轮输入，也不会缩短它，于是连压三轮 `no_reduction` 后熔断。熔断文案却建议执行 `/compact`，照做必然再失败，输入也找不回来。

- **熔断文案第三态**（`query/loop.ts` `buildCompactCircuitBreakerText`）：最新一条真实用户输入占本次请求估算总量 ≥ 0.5，且自身 ≥ 半个窗口时，明说「本轮输入本身约 X tokens，压缩无法缩短本轮输入」，给出缩小引用或拆轮的动作。判定顺序是常驻超窗优先，其次输入超窗，最后才是历史压不动。
- **估算口径**（`context/manager.ts` `estimateLatestUserInputTokens`）：取最后一条含非 tool_result 块的 user 消息，与 `estimateTokensFor` 同源校准，并扣掉常驻开销。tool_result 不计入，因为 toolResultBudget 和 microcompact 压得动它。
- **专用错误码** `context_input_overflow`（`error-lexicon.ts` / `error-messages.ts`）：放在通用「上下文溢出」之前，面板建议里不再出现 `/compact` 引导。
- **输入退回**（`cli/src/app.ts`）：探针遇到该码时记 `inputOverflow`，本轮结束后若未送达模型，直接 `retractUnsentTurn` 并 `markForRestore`。不像普通失败那样等用户在空输入框按 Esc，因为原样重发必然再失败，留在历史里还会让下一轮继续超窗。
- **收紧注入面**：
  - MCP `@server:uri` 接入与 @ 文件同一套单条 100KB / 总量 256KB 预算，超限不注入，进入 `skippedPaths` 告知用户，并引导模型用 ReadMcpResource；
  - 自定义命令 `@{path}` 从 10MB 降到 256KB；
  - hook `additionalContext` 单条上限 100K 字符，超出截断并注明原长度。

## 放弃了什么（以及为什么不选）

- **方案 a：发请求前截断最新 user 消息里的 `<system-reminder>` 注入块。** 要可靠区分注入块和用户原文（用户也可能粘贴含该标签的文本），而且会改写已落盘、参与 cache 前缀的消息。三处注入面已经在源头加了上限，剩下的超大来源只有用户亲手粘贴，那属于用户原文，不该截。这次不做。
- **用「输入占窗口比例」判第三态**：与常驻那条同理。走到熔断时 API 已经实锤超窗，按窗口比例判是在跟启发式估算误差赌阈值，所以改按「占本次请求总量」判。
- **阈值取 0.8（与常驻同值）**：输入之外还有常驻开销和历史。过半就意味着把历史压成零也腾不出空间，0.8 会漏掉「常驻 30% + 输入 60%」这类场景。
- **只看「占总量」一个条件**：短会话里历史只有一两条，最新输入天然占总量大半。选测中 `false-compaction-banner.test.ts` §八 #14 实测把几百 token 的输入报成「本轮输入本身约 0K tokens」，因此补了「自身 ≥ 半个窗口」这个条件。
- **熔断后保留 Esc 撤回（路径 B）而不自动退回**：用户要先知道「按 Esc 能找回」，而这条输入原样重发注定失败，没有留在历史里的价值。自动退回失败（现场被改）时仍回落到路径 B。
- **不改压缩算法本身**：本文档的边界。与 `20261026-AgenticLoop状态机与压缩熔断` 方案（分支 `fix/compaction-outcome-circuit`）都动 `buildCompactCircuitBreakerText`，本 PR 只加参数和一个分支，合并冲突面限于该函数的签名与收尾那段。

## 拿什么证明它生效了

- `bun test ./packages/core/tests/query/compact-circuit-breaker-text.test.ts`：11 pass。新增三态用例：
  - 事故数值 45,425,094 / 45,455,094 判为 `context_input_overflow`；
  - 长历史 + 20 万输入仍判为 `context_overflow`；
  - 常驻与输入都大时判为 `context_fixed_overflow`。
  
  另有一条短会话不误判的用例（总量 600、输入 500、窗口 100 万时判为 `context_overflow`），这条是在选测红过一次后补的。

  另有 `estimateLatestUserInputTokens` 的 3 条用例（扣常驻、跳过 tool_result、无 user 时为 0）。
- `bun test ./packages/cli/tests/app/at-reference-inline-guard.test.ts ./packages/core/tests/hook/additional-context-cap.test.ts ./packages/cli/tests/command/custom-template-pipeline.test.ts`：29 pass。
- 变异自证：逐条把守卫改坏后，测试结果如下。

  | 改坏的守卫 | 结果 |
  | --- | --- |
  | 第三态判定改 `false` | 1 fail |
  | 窗口下限条件改 `true` | 1 fail |
  | MCP 上限改 `if (false)` | 2 fail |
  | hook 上限改 `if (true)` | 2 fail |
  | custom 上限改回 10MB | 1 fail |

  恢复后全绿。
- 未验证：没有在真实 TUI 里端到端复现「熔断 → 输入回到输入框」。app 层回填走的是既有 `retractUnsentTurn` + `markForRestore`，与 ESC 取消路径同一套机制，但新分支没有专门的 UI 测试。
