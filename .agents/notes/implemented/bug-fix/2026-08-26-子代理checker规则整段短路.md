# 子代理 checker 规则整段短路：loader 灌了规则，`this.rules` 还是 null

## 决定了什么

在 `packages/core/src/permission/sub-agent-checker.ts` 的 `createSubAgentChecker()` 里，
`importFromRuleLoader(...)` 之后**补一次 `checker.refreshRulesFromLoader()`**（checker 上已有的现成方法，
`checker.ts:678`），并在调用点写清「为什么必须补」而不是「同步规则」。

根因是**两份状态**：`RuleLoader` 与 checker 实例字段 `this.rules` 各存一份。
子代理 checker 用 `new PermissionChecker(config, undefined, workspacePath)` 构造
（第二参数 `undefined` → `this.rules = null`，见 `checker.ts:451`），随后只把规则灌进 loader。
而阶段一 `hasPermissionsInner` 的**所有**规则分支都以 `if (this.rules)` 为前置门 ——
Step 1 `checkDenyRules`（`checker.ts:742`）、Step 4 敏感文件逃生舱的 `checkAllowRules`（`:809`）、
Step 5 ask 规则（`:844`）、Step 8 `checkAllowRules`（`:938`），以及 `isPathHidden()`
（`:631` 直接读 `this.rules?.deny`）。于是这些分支在子代理上**整段短路**。

实测到的四个后果（修复前后各跑一遍脚本对照）：

1. **allow 规则真失效**。主 checker 配 `allow: ["Bash(npm *)"]` 时 `npm test` 命中规则放行；
   子代理同一请求被 dontAsk 兜底拒掉（`dontAsk 模式下自动拒绝: 工具 "bash" 需要用户确认`）。
2. **deny 的拒绝理由错位**。`deny: ["Bash(curl *)"]` 主 checker 给 `decisionReason.type === "rule"` /
   `behavior: "deny"`；子代理给 `{ type: "mode", mode: "dontAsk" }`。**结论同为拒绝** ——
   这正是 bug 长期潜伏的原因：dontAsk 兜底把它掩盖成了「看起来正确」。
3. **非凭证类 deny 在子代理直接放行**。`deny: ["Read(internal/**)"]` 这种不被
   `path-validator.ts` 的 `SENSITIVE_FILES` 正则碰巧命中的路径，子代理读它 `allowed: true`。
   （`Read(secrets/**)` 之所以看着还"拦住了"，是碰巧命中 `/secret/i` 敏感文件正则，不是规则起作用。）
4. **`isPathHidden()` 恒 false**，glob/ls 列举结果的 deny 过滤在子代理里不生效，被 deny 的文件模型看得到。

**顺带记一条口径不一致（本次刻意不动）**：另一条派生路径
`deriveWithPermissionMode()`（`checker.ts:326`）走的是
`new PermissionChecker(derivedConfig, this.rules ?? undefined, ...)` —— **传了** rules，所以没这个问题。
两条派生路径一条走 loader、一条走构造参数，口径不同。统一它属于重构，不在本次修 bug 的范围内。

**方向自检**：这次主要修「更安全」——子代理不再绕过用户配置的 deny 规则（后果 3 是实打实的越权，
后果 4 让被 deny 的文件对模型可见）。同时也修了「更准」：allow 规则在子代理失效会让子代理
白撞墙、被拒后重试或换路子，多花轮次（而 turns per task 是成本最大杠杆）。没有牺牲哪个方向 ——
这不是 trade-off，是一处纯漏接线。

## 放弃了什么（以及为什么不选）

**(a) 改成 `new PermissionChecker(config, mainChecker.getRules() ?? undefined, ...)` 直接传 rules。**
不选，三条理由：① `getRules()` 可能为 `null` —— 主 checker 在 `initRules()` 之前
（或本身由构造参数 `undefined` 起步）就是 null，此时子代理拿到空规则，故障形态与现在一模一样，
只是从"忘了 refresh"变成"取到了 null"，更难看出来；② 它**绕开 RuleLoader 这个单一事实源** ——
`initRules()` 的注释（`checker.ts:648-655`）明确把 RuleLoader 定为权威（A 加载器），
构造参数的 rules 只是启动占位（B）。走构造参数等于让子代理消费降级后的那一份；
③ 会与 `importFromRuleLoader` 形成**两条并行灌入路径**，且构造器里 `if (rules)` 还会
`importFromPermissionRule(rules, "projectSettings")` 再灌一遍 loader —— 规则重复计数，
来源标签也从原来的真实来源被拍平成 `projectSettings`。

**(b) 让 `importFromRuleLoader` 内部自动 refresh 调用方 checker。**
不选：那是 `RuleLoader` 的方法，让它反向 mutate 持有它的 checker 是**层级倒置**
（loader 是被 checker 组合的下层，不该知道上层有个 `this.rules` 缓存需要维护）；
而且 loader 也拿不到 checker 的引用。真要做只能改成「checker 上包一个
`importRulesFrom(otherChecker)` 门面方法」—— 那是可以的，但主 checker 的 `initRules()`
已有自己的同步时机（`:670` 结尾那句 `this.rules = this.ruleLoader.toPermissionRule()`），
再加一个门面方法会变成第三条灌入路径。本次只补一行调用，保持调用点数量不变。

**(c) 把 `this.rules` 这个缓存字段整个去掉，规则分支直接查 loader。** 这是根治
（两份状态合成一份，同类 bug 再也写不出来），但它要改 `hasPermissionsInner` 的 5 处分支门 +
`isPathHidden` + `describeDenyRules`，属于阶段一逻辑重构。本次范围明确只修 sub-agent-checker，
不动 dontAsk 语义、不动阶段一逻辑。留作后续 simplification 候选。

## 拿什么证明它生效了

**① 修复前先复现**（临时脚本，跑完已删）。同一份规则同时喂主 checker 与子代理 checker，
打印 `check()` 完整返回值。修复前输出：

```
1-sub : {"allowed":false,"reason":"dontAsk 模式下自动拒绝: 工具 \"bash\" 需要用户确认","decisionReason":{"type":"mode","mode":"dontAsk"}}
1-sub.getRules(): null
2-sub : {"allowed":false,...,"decisionReason":{"type":"mode","mode":"dontAsk"}}     ← 主 checker 是 {type:"rule",behavior:"deny"}
3-sub : {"allowed":true}                                                            ← 主 checker 是 deny
4-main: true / 4-sub : false                                                        ← isPathHidden
```

修复后同一脚本：`1-sub` 变 `{"allowed":true,"decisionReason":{"type":"rule","behavior":"allow"}}`、
`getRules()` 返回 `{"allow":["Bash(npm *)"],...}`、`2-sub`/`3-sub` 与主 checker 逐字段一致、`4-sub: true`。

**② 反漂移测试 + 一次删除自证。** 新增
`packages/core/tests/permission/sub-agent-checker.test.ts`（7 test / 24 断言），
把上面 4 个后果写成断言，且**精确到 `decisionReason`**。

自证过程：把 `checker.refreshRulesFromLoader()` 那一行注释掉重跑 → **6 fail / 1 pass**，
具体红的断言是：`getRules()` 非 null（收到 `null`）、allow 规则放行（收到 `allowed:false` + `type:"mode"`）、
deny 的 `decisionReason` 为 `{type:"rule",behavior:"deny"}`（收到 `{type:"mode",mode:"dontAsk"}`）、
非凭证类 deny 拦截（`allowed` 收到 `true`）、`isPathHidden` 为 true（收到 `false`）、
ask 规则进 `getRules().ask`（收到 undefined）。唯一没红的是「子代理 permissionMode 强制为 dontAsk」——
它测的是本次未触碰的原有语义，不该红。恢复那一行后 **7 pass / 0 fail**。

**这一步不是走形式**：只断 `allowed === false` 的写法在删掉修复后**仍会全绿**，
因为 deny 场景被 dontAsk 兜底成同样的 `allowed:false`。测试必须锁 `decisionReason.type === "rule"`
而非 `"mode"`，否则它就是又一个 false gate。

**③ 门禁。** `bun run affected-tests:run`（选测判定为 `./packages/core/tests/permission/`）
与 `make build` 均通过，构建产物无 `will always be undefined` warning。
