# 等待期轮询的五处识别补洞：`gh pr list`、时间戳、脚本正文、无对象去重、计数升级（P1–P5）

## 决定了什么

触发会话（`20261116-162128-586b5e35`）的空转形态是：模型挂上等待后仍在等待期前台反复查询，
140 条 bash 里 **128 条 `matchStatusQuery → null`（全部是 `gh pr list`）**，剩下能识别的那些
又因为首行 `date` 时间戳每轮都不同而「永远算状态变了」——P1 全程只拦下 1 次，模型空转 400+ 轮。
本 PR 按方案 §4.6–§4.10 补五处，全部落在等待子系统，不动 goal 机制：

1. **P1 命令表加 `gh pr list` 族**（`packages/core/src/task/status-query-commands.ts`）
   - `StatusQueryFamily` 加 `gh_pr_list`；`gh pr` 分支接受 `list`；
   - subject 用 **`gh:prs:<repo>:<state>`**（新前缀 `gh:prs:`，与 `gh pr view <n>` 的 `gh:pr:` 分开）；
   - 签名片段按键名**排序**后拼接（`--state` / `--author` / `--json` / `--jq` / `--limit` 都进签名）：
     `gh pr list --json number --state open` 与反序共享 memo（同一条命令的两种写法）；
   - 多段命中时 **subject 取并集**（排序后 `+` 拼接），签名覆盖全部段；
   - **D11 口径统一**：`--limit` 进签名但不进 subject。`gh run list` 的 subject 从
     `gh:run:list:6` 改成 `gh:run:list`（`--branch` 仍进 subject —— 不同分支是两个对象集合）。

2. **P2 归一化抹墙钟时间戳**（同文件 `normalizeText`）：ISO 8601、时分秒无条件抹；
   裸时分**只在行首 / `[` 之后 / 整行仅由它组成**时抹。收窄是刻意的：`846:BEHIND` 这类
   PR 号 + 状态形态、行内 `3:15`（耗时/比值）不能被吞。

3. **P3 脚本正文读取抽到共享模块**（`task/wait-subjects.ts` 的 `readWaitScriptBodies`）
   原先它是 `bash.ts` 的私有方法，monitor 侧拿不到 —— 而 monitor 的 `command` 本身就是脚本正文，
   于是「同一件事」在两个入口抽出两套对象。`bash.ts` 删私有实现、改为 `task.readWaitScriptBodies`；
   `monitor.ts` 读脚本正文后一并传给 `collectWaitSubjects` / `collectWaitCommandFamilies` / `decideWaitAdmission`。

4. **P4 抽不出对象时按「命令 + 脚本 hash」去重**（`task/wait-admission.ts`）
   原实现 `subjects.length === 0 → start`（「抽不出就不参与去重」），后果正是 b0aa0f1e
   四个同脚本进程同时跑。新判据：归一化命令相同 + 双方 hash 相等（含双方都没有脚本）→ `duplicate`；
   hash 不同 → `replace`；命令不同 → `start`。刻意不用「期限更短就算重复」那条判据
   （没有对象时分不开「换个说法」与「确实想再等一件事」）。

5. **P5 等待期前台查询计数与两档升级**（`task/status-poll-guard.ts` + `query/{tool-executor,loop}.ts`）
   - 计数存在 **`SessionState`**（`getWaitPollEscalation`，键 `waitPollEscalation`），
     `tool-executor` 注入 `StatusPollContext.escalation`；
   - 第 5 次：结果末尾追加一句提示（只放行时给；P1 拦截时回执已含「不要反复查询」，不叠两段）；
   - 第 15 次起：**硬拦**，排在 P1 的 120s 探测窗口**之前**（否则「结果一直在变」的查询永远走不到）；
     回执给 `task_stop <id>` / `cron_delete <id>` 出口 + 上次摘要；
   - 清零点两处：用户新消息（`loop.ts` 的 `queryLoopBody` 入口）、等待源全部释放（守卫内判）；
   - 事件 `WaitPollEscalated`（level 1/2 + count/subject/kind），level 2 每段等待只落一次。

## 放弃了什么（以及为什么不选）

- **放弃「多段 subject 保持单值」**：方案 §4.6 第 5 条要求取并集，已按方案实现。
  代价如实记录：`describeWaitRelation` 与 monitor 的覆盖判定用 `subjects.includes()` 精确匹配，
  并集形态匹配不上单对象登记 → 这几条多段命令回到 120s 探测窗口。方向是**多放行**（安全），
  但覆盖优化的收益在这类命令上归零；R4 的 44 条取证命令里 2 条受影响（42/44 不受影响）。
- **放弃「`--limit` 进 subject」**（D11）：limit 只截断行数，不改变「查的是哪一批」。
  代价是 `--limit 5` 与 `--limit 6` 共享 subject，两者的输出差异只能靠签名区分 ——
  这也是签名的职责。
- **否决「去掉 L2 的 `backgroundRunning` 早退」**：单独落 `rejected/bug-fix/2026-11-16-去掉L2等待早退.md`。
- **放弃「P5 计数挂 `status-poll-guard` 的 memo」**：memo 是进程级单例（`defaultMemo`），
  跨会话累积会把「本次等待的第 15 次」算成「整个进程的第 15 次」，「用户消息清零」也无处挂。
  选 `SessionState`（与 `todoGateBudget` 同层）。
- **放弃「只提示不硬拦」**：触发会话里提示之后又查了 100+ 次（模型对提示无反应），
  硬拦是给「绝不结束本轮」的模型兜底；硬拦之后唯一能推进的动作就是结束本轮。
