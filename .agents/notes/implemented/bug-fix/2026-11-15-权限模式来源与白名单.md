# 起始权限模式按「来源可信度」决定能指定哪个档位

## 决定了什么

四个缺陷（M2 / M17 / M3 / M18）与一项策略字段（M15）合成一处改动，因为它们共享同一个判据：
**这份配置文件有没有资格指定这个档位**。

- 新增 `packages/core/src/config/permission-mode-source.ts`：`resolveStartPermissionMode()`
  按 CLI > 企业 managed settings > 未追踪 `settings.local.json` > 项目级 `settings.json` >
  用户级 `settings.json` > 内置默认 的顺序解析起始模式，并为每个来源套一张信任度表
  （`full` / `no-skip` / `restricted`）。
- `loadConfigFile()` 从四个来源读 `permissions.defaultMode`（M2 此前**零读取者**）与顶层
  `permissionMode`（M17：未追踪 local 的顶层字段原本不在 `PROJECT_BEHAVIOR_FIELDS` 白名单里），
  同文件内 `permissions.defaultMode` 优先于顶层 `permissionMode`，两者不一致时打 warning。
- 字面量归一统一到 `normalizePermissionModeLiteral()`：`manual`→`default`（保持既有静默）、
  `bypassPermissions`→`always-allow`（M3，附一条 info 说明跳过了什么）、其余无效值→`default`
  并给 warning（M18）。归一处放在 `loadConfig` 的「无 model 提前 return」**之前**——
  onboarding 首次启动正是照 CC 文档传 `--permission-mode bypassPermissions` 最常发生的场景。
- M15：`permissions.disableBypassPermissionsMode` / `permissions.disableAutoMode` 与顶层
  同名位置等价，两处都写时**取严**（任一处 `disable` 即 disable）；
  `disableAutoMode` 归一进既有 `disabledModes` 通道，不为它新开第二条判定链。
- 顺手把 cli.ts 内联的 bypass 降级逻辑抽成 `downgradeBypassIfDisabledByPolicy()`
  （core `mode-policy.ts`），让「策略最终赢过任何配置来源」这件事可被单测直接覆盖。

## 放弃了什么（以及为什么不选）

1. **不给 `PERMISSION_MODES` 加 `bypassPermissions`。** 它是 CC 的别名而非 sid 的规范名；
   加进合法值集合会让它绕过归一路径、直接流到权限判定（一个不在任何集合里的模式名，
   既不被识别成 skip 也不被识别成 always-allow）。别名在归一表里处理，与 `manual` 同构。
2. **不让项目级 / 被追踪 local 的 `permissions.defaultMode` 一票生效。**
   项目级 `settings.json` 随仓库分发，谁都能提交一份；直接生效等于允许「仓库自带配置把
   clone 者变成无审批执行」。给出的折中是白名单：只允许 `default`/`plan`/`dontAsk`/`deny-write`
   这四个「不会放宽权限」的档位，其余回落并告警。
3. **不把无效值原样保留。** 保留原值会让下游 `isModeDisabledByPolicy()` 之类的判断拿到一个
   谁也不认识、但看起来「没被禁用」的字符串。落到 `default` 是唯一两边都成立的状态。
4. **不给 `manual` 新增启动提示。** 它的归一是 P2-4 的既有静默行为，替它加噪音会淹没
   `bypassPermissions` 那条真正需要用户看见的语义差异说明。
5. **不加顶层 `disableAutoMode` 到远程闭集（`ALLOWED_REMOTE_KEYS`）。** 远程键是与服务端
   `extra=forbid` 对齐的闭集，客户端单方面放行没有意义；顶层这个位置只对本地
   `managed-settings.json` 生效，`permissions.` 下那个才走远程。
6. **没有采用「所有归一都塞进一个归一处」的做法。** 来源解析层必须自己归一——白名单判断
   要在归一**之后**的模式名上做（`bypassPermissions` 先变 `always-allow` 才轮到拒绝）。
   两处归一都在 `validateConfig` 之前，行为一致；G1 用例分别守住两条入口。

## 拿什么证明它生效了

**修复前探针**（`/tmp/probe-pr2.ts`，7 项里 1 项绿）：用户级 `permissions.defaultMode: acceptEdits`
→ `default`；未追踪 local `permissionMode: acceptEdits` → `default`；`permissionMode: bypassPermissions`
→ 原样保留；`permissionMode: acceptedits` → 原样保留；`permissions.disableBypassPermissionsMode: disable`
→ bypass 未被禁。

**新增 G1**（`packages/core/tests/config/permission-default-mode.test.ts`，24 例全绿）：
覆盖验收表 1–14 + P1–P6，全部走真实 `loadConfig({})`（不 mock 读取链——这一组缺陷的共同形态
正是「字段读到了但被某层静默丢弃」，mock 掉读取链就把要验的那段换掉了）。

**变异自证 4 项**（逐项改坏 → 跑测试 → 恢复）：

| 变异 | 预期 | 实际 |
| --- | --- | --- |
| 删掉 `permissions.defaultMode` 读取 | 用例 1/3/5/10 红 | 14 例红（所有依赖 defaultMode 的用例连带） |
| 去掉来源白名单（`isAllowed` 恒 true） | 用例 6–9/11/12 红 | 恰好这 6 例红 |
| 归一不生效（模拟挪到 validateConfig 之后） | 用例 3/4 红 | 用例 3/4 + CLI 两例 + manual + P6 红 |
| 不读 `permissions.disableBypassPermissionsMode` | P1/P3 红 | P1/P3/P6 红 |

**G2 冒烟**（`tests/smoke/cases/X8-project-settings-default-mode/`）：
项目级 `settings.json` 写 `permissions.defaultMode: dangerously-skip-permissions`，
带 `--trust-workspace` 跑回放；`git remote add`（default 档要确认、无头下判拒）判拒，
只读子命令放行做对照。`bun run smoke X8-...` → PASS。
口径与方案原文有一处差异：原文要求「写工作区外文件」，但冒烟运行器的夹具禁止仓外路径
（`findOutOfRootPaths`），故改用 X2 已核过的等效判据「default 档下的写形态被判拒」。
mutation 配方去掉白名单 → 该用例变红（`bun run smoke:mutate X8-...` killed）。
