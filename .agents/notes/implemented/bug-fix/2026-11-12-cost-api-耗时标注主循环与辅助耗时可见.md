# `/cost` 的耗时口径写清「主循环」，并让辅助调用耗时真正可见

## 决定了什么

修 D8（P1）：「API 耗时」只累加主循环，标签没写范围；辅助调用的耗时哪里都看不到。

四处改动：

1. **`/cost` 标签与结构**（`packages/cli/src/command/commands/cost/cost.ts`）
   - `API 耗时:` → `API 耗时（主循环）:`。
   - 新增 `辅助调用耗时:` 行：显示「总耗时 + 本次启动后 N 次调用」；只采集到一部分时写
     「M/N 次采集到耗时」；一次都没采集到写 `—`，**不写 0**。
   - 耗时块后加一行口径说明：会话时长是墙钟（含思考与空闲），API 耗时只算主循环请求，
     子代理与辅助调用不含在内。
2. **计费事件带耗时**（`packages/core/src/llm/billing-sink.ts`）
   - `BilledRequest` 新增 `elapsedMs?: number`（本次 fetch 墙钟耗时，`undefined` = 未采集），
     并落盘到 `events.jsonl` 的 `elapsed_ms`，让 `/cost` 上的数字能在轨迹里复算。
   - `recordNonStreamingBilledRequest` 同步接受并透传。
3. **五个 provider 计费收口点补耗时**（`llm/openai.ts`、`llm/anthropic.ts`）
   - 流式：anthropic 的 `sendMessageStream`、openai 的 `sendViaResponsesAPI` 直接用
     函数内的 `requestStartTime`；openai Chat Completions 路径的计费收口在 `parseSSE` 里，
     给它加了 `requestStartedAt` 参数（**不能用它自己的 `requestStartAt`** —— 那是开始解析
     SSE 的时刻，已吃掉建连与 TTFB，对 10 万 token 的 fork 会系统性低估）。
   - 非流式：三条路径（anthropic、openai Chat、openai Responses）各自在函数开头记
     `requestStartTime`。
4. **数据链**（`packages/cli/src/app.ts`、`core/src/trace/side-call-sink.ts`）
   - billing 观察者把 `req.elapsedMs` 传给 `recordSideCall`，替换原来的写死 `durationMs: 0`。
   - `SideCallRecord.durationMs` 改为**可选**（`undefined` = 未采集），`getSideStats()`
     新增 `durationMs`（已采集之和）与 `durationCalls`（采集条数），`details[]` 带出逐条耗时。
   - 13 个辅助调用点原来写死 `durationMs: 0` 的，改成不传（语义：未采集）。

## 放弃了什么（以及为什么不选）

- **不给 13 个手写 `recordSideCall` 调用点补真实计时**（记忆召回、压缩、分类器、hook、目标评估）。
  它们不是辅助花费的主体（本会话 5 次 fork 与标题生成都走计费通道，43% 的费用在那里），
  逐点补计时需要每个调用链自己找起点，diff 面扩大而收益有限。留成「未采集」并由显示层
  明确标注覆盖度（M/N），比塞一个假 0 诚实。要做属于 D14「按用途拆分含耗时」的范围。
- **不做实时刷新面板**（D2 已定：面板是静态文本，给一行「重开 /cost」提示即可）。
- **不把辅助调用并进 `SessionState.modelUsage`**：那会污染 stock 口径（`↑` 是当前上下文大小），
  见 `state.ts` 里 `addSideCost` 的注释。耗时走独立的 `getSideStats()` 通道。
- **不用 `parseSSE` 自己的 `requestStartAt`**：它比真实请求起点晚一个 TTFB，
  而辅助调用（尤其 10 万 token 的 fork）大头常在 TTFB 上。为此给 `parseSSE` 加了参数，
  而不是图省事用现成变量。
- **未采集显示「—」而不是 0**：`0ms` 与「不知道」在数据上是两回事。这次修 D8 之前
  14 个调用点里 13 个写死 0，正是把两者塌缩成同一个值，汇总只能低估。

## 拿什么证明它生效了

- **新增测试 15 条**：
  - `packages/core/tests/trace/side-call-duration.test.ts`（5 条）：只累加采集到的耗时、
    `durationMs: 0` 与未采集可区分、全部未采集时 `durationCalls === 0`、`details` 带逐条耗时、reset 清零。
  - `packages/core/tests/llm/billing-elapsed.test.ts`（3 条）：流式/非流式 `elapsedMs`
    原样到观察者；未采集时字段缺席而不是 0。
  - `packages/cli/tests/command/cost-api-duration.test.ts`（7 条）：标签「API 耗时（主循环）」；
    `辅助调用耗时` 的全量/部分/全未采集/无调用四种形态；行序（API → 辅助 → 工具）；口径说明行。
  - `packages/cli/tests/command/cost-pending-tasks.test.ts` 同步改了标签断言（有意改动）。
  - 合跑：`bun test` 上述文件 **24 pass / 0 fail**。
- **变异自证 3 轮**（都先变红、再恢复回绿）：
  1. 把 `getSideStats()` 的「未采集不计入」改成 `c.durationMs ?? 0` 累加 → 4 条红
     （core 2 条 + cli 2 条，正是「把未知折成 0」这个缺陷形态）。
  2. 删掉 `/cost` 里 `sideDurationLine` 的注入 → 4 条 cli 测试红。
  3. 删掉 `recordNonStreamingBilledRequest` 的 `elapsedMs` 透传 → 对应 1 条红
     （`Expected 5678, Received undefined`）。
- **门禁**：`bun run typecheck:gate` 62 处错误 / 基线 64（无新增）；`bun run lint`、
  `bun run format:check`、`bun run lint:boundary`、`bun run affected-tests:run`、
  `make build`、`bun run docs:gen-reference` 全绿（结果见 PR 正文）。
- **未做端到端真实会话验证**：本机无可用模型凭据，`/cost` 的辅助耗时在真实会话里的
  绝对值落在 G1 整帧断言 + 计费事件字段上，与 D9 那轮的处理一致。
