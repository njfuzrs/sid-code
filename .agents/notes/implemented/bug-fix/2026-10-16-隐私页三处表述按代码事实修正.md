# 隐私页三处表述按代码事实修正（含一处承诺降级）

## 决定了什么

对照代码核查 `website/use/privacy.md`（隐私问题唯一事实源）后修正三处：

1. **L106 承诺降级为现状描述（本 Note 的核心）**：原文「切到 `essential-traffic` 期间产生的会话不会登记到上传目标，切回 `default` 后也不会被补传」与代码不符。实际链路：essential-traffic 期间 uploader 为 null、会话无 `.uploaded` 标记（`query/init-helpers.ts:67`），但补传扫描器 `trace/backfill.ts` 的 `scanPendingUploads` **全文无隐私级别判断**，判据只有「`.uploaded` 标记缺失」+ 补传水位（会话创建时间 vs 上传目标首次配置时刻，`upload-watermark.ts:15-17`）；切回 default 后 `collector.ts:1164` 自动恢复补传，期间会话必然晚于水位、整批上传。文档改为如实描述此行为，并给出删除目录的彻底规避法。
2. **L84 隐私级别取值规则纠正**：原文「多个信号时取最严的」不准确。`analytics/privacy-level.ts:26-40` 是顺序短路（NONESSENTIAL env → TELEMETRY env → 配置）：两个环境变量之间取严成立；环境变量与配置文件冲突时 env 优先**哪怕更宽松**。改为精确表述。
3. **L27 `state/` 清单补全**：原文只列三项，实际还有凭据同步节流、MCP 审批、守护进程状态等约 10 项（`config/paths.ts:229-236`）。补「等」式列举。

## 放弃了什么（以及为什么不选）

- **不在本 PR 改代码让 L106 的原承诺成立**：这是行为改动（backfill 链上加隐私过滤），混进文档 PR 会让 review 分不清「文档跟代码」还是「代码跟文档」。缺陷与修复方案已单独落盘到维护者文档库 `docs-research/sid-code/bugfixes/todo/20261016-隐私级别期间轨迹补传泄漏-排查结论与修复方案.md`（含证据链、三个候选方案与验证方案），等修复落地后把本页改回原承诺。
- **不采用「文档保持原承诺、等代码修」**：隐私页是唯一事实源，用户此刻正依据它做隐私决策——承诺一个不存在的保护比如实写现状危害更大。原承诺语义合理（修复方向），但在修复落地前它不是事实。
- **不动 L73（IDE 只连回环）与 L124（表达式赋值不改写）**：核查中未能找到确凿反证（L124 已在 `permission/sensitive.ts:61` 找到正面证据；IDE 连接目标由 IDE 侧插件决定），维持原文。
