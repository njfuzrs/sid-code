# 主屏溢出后收缩一律整帧重画，取代补空行

## 决定了什么

现象（用户报告）：任务做完、模型回复最后一条消息时，消息区先出现一大块空白，随后消息从输入框上方「从下往上」长出来，
直到整条消息并入历史才跳到正确位置。

根因是 #390 / #402 / #408 的「溢出后收缩补空行」本身，不是流式渲染或 Markdown：

1. 主屏模式下历史区（History）和动态区同帧，帧高几乎恒超视口，滚进 scrollback 的行拉不回来；
2. 动态区收缩（最后一轮前 TodoPanel 全部完成后收起、spinner / 工具状态消失）时，`diffMainScreen` 在历史区下沿补 p − n 行空行撑住高度；
3. 补过的帧作为下一帧 previous，流式正文出现在动态区（紧贴输入框上方），只要帧还没长回原高，每帧都算收缩，空行继续留在历史区下沿；
4. 于是画面 = 历史尾 + 空白 + 正文 + 输入框，正文增长一行就吃掉一行空白，看上去从下往上长。

xterm 复现（W=30、H=12、历史 20 行，「todo 收起 → 流式 1/3/5 行 → 并入历史」）与用户描述同形：todo 收起后 6 行空白，`⏺ msg0` 先出现在输入框正上方。

修法（用户在两种方案中选定「收缩即整帧重画」）：

- `packages/tui/src/frame/main-screen.ts`：③ 的条件改为 `n < p && (p − n > H − 1 || p ≥ H)` —— 前一帧已溢出视口时任何收缩都 full reset（`2J 3J H` + 整帧，ink.tsx 包在 DEC 2026 同步输出里）。
  删除 `padInsertRow` / `guessInsertRow` / `padShrunkFrame` / `rowsEqual` 与 `FrameDiff.screen`、`historyEnd` 参数。没溢出视口的收缩照旧擦底部（冻结基线行为）。
- `packages/tui/src/ink.tsx`：删除 `historyEnd()`、`previousFrameHadTransient` 与「关浮层 → 重画」的单独判定（已被上一条覆盖），`previousScreen` 恒为本帧。
- `History` 不再打 `internal_history`；`hasMountedTransient` 去掉 `inFlowOnly`。`Transient` 组件保留，标记现在只服务 `float` 叠画（PR4）。
- 与 cc 同口径（cc 的 log-update 在动态区从 scrollback 收缩时同样整屏重画）。

牺牲的方向：**更快 / 更省**。长会话每次溢出后收缩重写整段历史：实测 120 列下 1,000 行 86KB / 9ms，7,000 行 610KB / 34ms，20,000 行 1.7MB / 49ms（`resetMainScreen` 序列化耗时，不含终端解析）。
另外三个用户可感知代价：`3J` 清掉 sid-code 启动前的 shell 输出；用户上翻 scrollback 阅读时会被拉回底部；不支持同步输出的终端（Terminal.app）会闪一下。
收缩的触发频率：spinner / TodoPanel / 工具状态消失、关闭对话框或补全菜单（非叠画态）、输入框变矮。流式正文自身极少收缩：
用 `StreamingMessage` 逐 8 字符回放两篇真实 markdown（CONTRIBUTING.md 前 6000 字、PR4 的 Agent Note），1,267 步里高度回落 1 次、1 行。

## 放弃了什么（以及为什么不选）

- **继续补空行，只把插入点挪到输入框上沿**（本次排查时先提的方案）：正文能从上往下长，但空白仍在，只是换到正文与输入框之间，直到内容填满。
  #390 → #402 → #408 → 本次四次都在换插入点，空白行数恒等于收缩行数，换位置解决不了「出现空白」本身。用户明确要求不出现空白。
- **补空行 + 回合结束静止后补一次重画**：回合中途（等首 token、工具执行间隙）仍会看到空白，是折中而非修复，用户否决。
- **擦底部（冻结基线原行为）**：整帧上移，footer 下面留空白、输入框被顶到屏幕中间，即 #390 修的那个 bug。
- **只重画视口、不带 `3J` 清 scrollback**：被顶进 scrollback 的历史会与重画内容重复出现，越积越多（#408 已论证）；`2J` 不带 `3J` 各终端行为不一。
- **布局层给动态区保留最大高度 / 按视口裁剪动态区**：要猜各块高度，历史上三次复发；tail 截断还会让流式只见尾部（见 2026-06 的流式闪烁根因记录）。

## 拿什么证明它生效了

- `packages/tui/tests/frame.test.ts` 重写「溢出后收缩」两组共 8 例，走真实 `render` + `History` + xterm 重放，断言**每一帧**的视口 == 目标帧尾部 H 行、scrollback == 其余行（无重复、无缺行、无空白）。
  其中「最后一条消息：todo 收起 → 流式逐行增长 → 并入历史」逐帧复现用户现象，并断言流式首帧 `⏺ msg0` 紧跟 `hist19`。
- 变异自证：把条件改回 `(p − n > H − 1 || (p ≥ H && n ≤ H))`（基线口径、不补空行）→ `frame.test.ts` + `transient-float.test.ts` 20 例变红（12 条向量 + 8 例画面断言）；恢复后 118 pass / 0 fail。
- 冻结基线按新行为手改，只动收缩相关：`frame-vectors.json` 97 条中恰好 12 条变化（与 #390 手改的是同一批收缩向量），其余 85 条逐字节不变；
  term-bench `E4` 6 步中只有「溢出态内收缩」一步的 metrics / screen / scrollback 变化（字节 57 → 314，eraseScreen 0 → 1；画面从带 3 行空白变为 `行 4 … 行 26` 连续、scrollback `行 0 … 行 3`），其余 5 步逐项不变。
- `transient-float.test.ts`「关菜单同一帧输入区变矮」从「不重画」改为「重画一次且画面 / scrollback 逐行正确」：输入区少一行也是收缩，不重画就只能留空白。
- 门禁结果（affected-tests、make build、lint / format:check / lint:boundary / typecheck:gate）见 PR 正文。
- **未验证**：没有在真实终端里手动驱动 `sc-dev` 跑一轮带 todo 的长任务观察；上面的画面断言用的是 xterm headless + 真实底座 `render`，不是完整 App。
