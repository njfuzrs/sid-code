# 删掉自己站着的目录：成功的命令被 cwd 追踪的收尾 `pwd` 报成失败

## 决定了什么

`packages/core/src/tool/bash.ts` 两处，加一组测试。

**① 退出码不再被 cwd 追踪污染。** `buildCommand` 从

```sh
<用户命令> && pwd -P >| <file>
```

改成

```sh
<用户命令>; __sc_rc=$?; { pwd -P >| <file>; } 2>/dev/null; exit $__sc_rc
```

原始形态（smoke-10 `pytest-7982` 的真实 agent.log）：

```
[TOOL] ▶ bash {"description":"清理临时测试目录","command":"rm -rf /tmp/symlink_test"}
[TOOL] ✗ bash (54ms)
命令执行失败（退出码 1）:
pwd: error retrieving current directory: getcwd: cannot access parent directories
```

`rm -rf` 本身成功，失败的是收尾那个 `pwd -P`（cwd 已不存在）。`&&` 拼接时
整条退出码取最后一段 → **成功的操作被报成失败**，模型可能重试或改道。
比反过来更难查：日志里那句 `pwd: ...` 看起来像无关噪声。

既有防线覆盖不到：`formatSpawnError` 只处理 **spawn 前** cwd 不存在，
这条是 **spawn 后、用户命令成功、收尾 pwd 失败**。

**② 新增 `cwdStaleNotice`。** 修对退出码之后模型仍不知道自己站的目录没了。
`applyCwdTracking` 返回值从 `string | undefined` 改成
`{ switched?, staleCwd? }`，cwd 失效时在 tool_result 末尾追加一行告知
（与既有 `cwdChangeNotice` 同款位置与理由：零 cache 影响、天然只出现一次）。

判据取 `existsSync(getCwd())` 为假这个**直接事实**，不取"`pwd` 没写文件"——
后者还可能是磁盘满、临时目录被清，拿它当证据会造假信号。

## 放弃了什么（以及为什么不选）

**给收尾的 `pwd` 接 `|| true`** —— 否决，这是最诱人也最危险的修法。
实测 `false && { pwd; } || true` → **exit 0**：它把**用户命令的真失败也吞成成功**，
比原 bug 更坏（失败报成成功比成功报成失败危害大）。已用单测锁住。

**文案写「后续任何命令都会失败」** —— 否决，**实测这是错的**（我第一版就这么写）。
真实后果是**两套 cwd 状态静默发散**：

```
getCwd()                   → /tmp/sidW/x            ← 仍停在已删除的路径
bash 里 pwd                 → /Users/.../sid-code    ← resolveCwd 局部回退到启动目录
normalizeToolPath("f.txt") → /tmp/sidW/x/f.txt      ← 指向不存在的地方
```

成因是 `resolveCwd` 在 cwd 不存在时回退到 `getOriginalCwd()`，但**只在那一次
调用里局部回退、不写回全局**。所以 bash 命令照样跑通，只是跑在了另一个目录，
而 read/edit/grep 仍解析到已删除的路径。**静默跑在错误目录比直接报错更难发现**，
而错文案会让模型以为"不跑命令就没事"。

**让 `resolveCwd` 把回退结果写回全局 `setCwd`** —— 否决（本轮不做）。
它能消掉发散，但会**静默改变模型的工作目录**而模型没有要求过 ——
那是另一类惊喜。当前做法（告知 + 让模型自己显式 cd）把决定权留给模型。
若将来要做，得连带考虑 `getOriginalCwd` 是否总是个合理落点。

## 拿什么证明它生效了

**端到端实测**（真 BashTool，非模拟）：

```
① cd /tmp/sidcwd/inner          → isError=false, getCwd=/private/tmp/sidcwd/inner
② rm -rf /tmp/sidcwd            → isError=false  ← 修复前是 true
   目录真删掉了                  → ✅
   output 含 [工作目录已失效] + 发散说明 + "请显式 cd"
```

**六条回归**（真 BashTool）：

```
✅ exit 3 真失败仍失败           isError=true
✅ 正常 cd 写回 + 切换告知        cwd 跟随，+切换告知
✅ 连续 cd 到另一目录             cwd 跟随
✅ 普通成功命令无任何告知
✅ 失败命令 + cwd 健在 → 无失效告知
✅ grep 无匹配 → isError=false（既有正确行为，我最初期望写错了）
```

**4 条变异自证**（还原后 9 pass / 0 fail）：

| 变异 | 结果 |
| --- | --- |
| 退回旧实现（`&&` 拼 pwd） | 7 pass / **2 fail** ✅ 被拦 |
| 用 `\|\| true` 兜 pwd（吞真失败） | 8 pass / **1 fail** ✅ 被拦 |
| 去掉失效告知 | 7 pass / **2 fail** ✅ 被拦 |
| 文案改回「后续任何命令都会失败」 | 8 pass / **1 fail** ✅ 被拦 |

⚠️ **变异自证救了这次测试 —— 第一版测试是死断言。**
第一次跑变异①（退回旧实现）时**测试仍然全绿**。查出根因：

```
zsh  的 pwd -P → 用缓存的 $PWD，cwd 被删也 exit 0   ← macOS 开发机默认 shell
bash 的 pwd -P → 真去 getcwd()，cwd 被删则 exit 1   ← 容器/CI 里的 shell
```

且必须有 `eval` 包裹（有 shell 快照时才有）才触发 —— `eval` 的二次解析
让 bash 真去 `getcwd()` 而不吃 `$PWD` 缓存。

而 `getPlatformShell` 取 `process.env.SHELL || "/bin/bash"`，所以这组测试
**必须自己把 `SHELL` 钉成 `/bin/bash`**（已用 beforeEach/afterEach 钉住并恢复）。
不钉的话它在 macOS 上永远绿。
**教训：一条只在特定 shell/平台下才有意义的断言，必须自己把那个环境钉住 ——
否则它在开发机上恒绿，而恒绿的断言与没有断言等价。**
