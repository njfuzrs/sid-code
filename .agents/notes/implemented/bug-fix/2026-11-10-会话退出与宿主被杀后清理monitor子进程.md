# 会话退出与宿主被杀后清理 monitor 子进程（FIX-1：D1 + D1-b）

## 决定了什么

monitor 子进程是 `detached` 的进程组组长（为了 `kill(-pid)` 能清孙进程），宿主退出不会连带杀死它。
修复前五条退出路径没有一条碰任务系统：子进程被 launchd 收养（PPID=1）永久泄漏，
`TaskLifecycle` 永远停在 `started`，`wait-audit` 对这种泄漏完全不可见。分两层修：

**第 1 层：宿主侧，宿主还活着的退出路径**（`packages/cli/src/app.ts`）

| 路径 | 调用 | 位置约束 |
| --- | --- | --- |
| `/quit`（`handleCommandExecutionResult` 的 `case "quit"`） | `killAllRunningTasks` | 同步，排在异步收尾（SessionEnd）之前 |
| TUI 正常退出（Ctrl+D / 两次 Ctrl+C，走 `runTUI` 尾部） | `killAllRunningTasks` | `fireSessionEndEvent("exit")` 之前。**方案文档漏了这条**：它既不经过 `case "quit"`，也不是信号（TUI 是 `exitOnCtrlC:false`） |
| 信号 `onSignal`（SIGTERM / SIGINT / SIGHUP） | `killAllRunningTasks` | `armForceExit` 之后、`abort()` 之前（abort 会唤醒无头主路径，它随时可能先 exit） |
| 崩溃兜底 `emergencySessionEnd` | `killAllRunningTasks` | `CrashMarker.write` 之后、`finalizeSessionStore` 之前 |
| `process.on("exit")`（最后一道） | `killAllRunningMonitors`（新增） | 单独包 try/catch，后面才是 `PidManager.removeByPid` |

四条主路径共用一个 App 私有方法 `terminateBackgroundTasksOnExit(path)`（try/catch + 有任务时打一行 WARN）。
`killMonitorTask` → `finalizeAndDrain` 是同步的，所以 `TaskLifecycle{completed,killed}` 与 `WaitReleased{terminal}`
会在 SessionEnd 之前落盘。不会落 `delivered`：终态通知只是入队，进程马上就 exit 了。

**第 2 层：SIGKILL / OOM 兜底**（新文件 `packages/core/src/task/monitor-orphans.ts`）

- `spawnMonitorTask` 拿到 pid 后写 `sidPaths.tasks()/<task_id>.monitor.json`（pgid、spawn 时刻、宿主 pid、宿主记录时刻、会话 id、命令前 200 字符）。
  `finalizeAndDrain` 末尾删除，四个终态出口都会经过它。
- 启动诊断里 `findOrphanPids` 之后调 `reapOrphanMonitors()`。三条判据都在纯函数 `classifyMonitorMeta` 里：
  1. **宿主活着就不动**（`kill(pid,0)`，EPERM 算活；宿主 pid 上的进程启动晚于记录时刻，就判为复用，原宿主算已死）；
  2. **进程组身份核对通过才 SIGKILL**：组内至少一个成员启动不晚于 spawn 时刻 + 2s 容差（与 `PidManager.isPidReused` 同一容差）；
     核对不上就不 kill、只删元数据、写 WARN；
  3. **ps 查不到就不杀**，保留元数据等下次启动。
- 没有元数据文件时只做一次 readdir，不起 ps，不给每次启动加开销。

## 放弃了什么（以及为什么不选）

- **`process.on("exit")` 里也调 `killAllRunningTasks`（方案文档原文）**：没有照做，改成只杀 monitor。
  这道兜底还覆盖无头 `-p` 的**正常结束**：`waitForBackgroundNotification` 在没有带承诺的等待时放行退出，
  这时还在跑的后台 shell 正是 `background-await.ts` 判为「静默」的常驻服务（dev server / watch）。
  它多半是模型有意留下的，下游用户或验证脚本还要用；一并杀掉会改变 `-p` 的既有语义，方案文档也没分析过这个场景。
  monitor 不一样：它的唯一用途是给宿主投递事件，宿主一走它就只是泄漏。
  交互退出、信号、崩溃仍然按方案杀全部后台任务，与 Ctrl+F 同口径。
  **代价**：无头在预算硬停或运行时异常时退出，残留的后台 shell 仍会泄漏，与修复前一样。
- **方案 B：在 `clearAllTasks()` 里加 kill 再接线**：不选，理由同方案文档。那样会把「清理记录」和「终止进程」混进一个函数，
  `killAllRunningTasks` 已经是现成的「终止全部」入口。
- **身份核对用环境变量注入的 task_id（方案文档建议的精确匹配）**：实测不可行。macOS 的 `ps -E` 读不到 SIP 保护的
  系统二进制的环境变量，`zsh -c 'tail -n 0 -F x'` exec 成 `/usr/bin/tail` 后 0/1 读到标记。
  monitor 最典型的命令恰恰是 `tail -F | grep`。命令行核对同样不行：`trace/digest.ts` 的 `findSessionProcess` 注释已经记录过，
  `process_title` 不能可靠排除 PID 复用。改用启动时刻排序的理由：spawn 那一刻 pid P 被我们的 monitor 占着，
  任何复用了 P 的进程都只能在整组消失之后出现，启动时刻必然晚于 spawn。误判需要 pid 在约 3s 内绕回一圈。
- **用父 session_id 做身份核对（方案文档建议）**：元数据里存了 `session_id`（cli.ts 启动时注入的
  `getCurrentSessionId`），但只写进清理日志，用来定位是哪个会话漏的，**不参与判据**。
  会话 id 回答不了「这个 pid 现在还是不是它」，pid 复用只能靠启动时刻排除。
- **方案 2B（shell 外包 watchdog）/ 2C（`detached:false`）**：不选，理由同方案文档（改写用户脚本；孙进程泄漏更多）。
- **已知限制**：启动扫描只在「下次启动」发生，用户永不重启时孤儿会一直留到重启。真正的兜底要 OS 级机制（PDEATHSIG），POSIX 没有。
  另外退出会连带杀掉 `run_in_background` 的 shell（交互退出 / 信号 / 崩溃时）。将来要做 durable 后台任务，需要连同第 2 层的元数据一起设计。
  Windows 未验证（`detached` 在 win32 为 false，扫描直接跳过）。

## 拿什么证明它生效了

**单测（从真实入口进，真实子进程，不 mock spawn / kill）**：

- `packages/cli/tests/app/quit-cleans-tasks.test.ts`：构造真实 App，用真实 `MonitorTool` 挂 monitor，
  驱动 `handleCommandExecutionResult({type:"quit"})`。断言 `process.kill(pid,0)` 抛 ESRCH，
  `TaskLifecycle{completed,killed}` 和 `WaitReleased{terminal}` 在事件流里的下标都小于 SessionEnd 标记；
  另覆盖前台子代理不被杀、无任务 no-op、`emergencySessionEnd`，以及 TUI 尾部和启动扫描两处的静态接线。
- `packages/cli/tests/app/exit-signal-kills-monitor.test.ts`：子进程里构造真实 App 并注册真实信号处理器，
  父进程发**真实** SIGTERM / SIGHUP（期望退出码 143 / 129）；`exit` 模式直接 `process.exit(0)`，验证最后一道兜底。
- `packages/core/tests/task/monitor-orphans.test.ts`：判据纯函数 9 条，加真实进程上的扫描：该杀的组收到 exit 事件；
  宿主活着、pgid 被复用这两种情况下组仍存活；损坏元数据只删不杀；`.output` 不碰；无元数据时不起 ps；
  元数据随真实 `spawnMonitorTask` 的 spawn / 终态出现和消失；`killAllRunningMonitors` 不碰后台 shell。

**顺手修的验收脚本漏洞**：第一次跑 mutC 时，「A 的子进程仍存活」那条断言**假通过**，只靠 events 断言才判出 FAIL。
原因是 `filterMonitorPids` 靠二进制名正则 `sid-code(-dev)?\s+-p` 排除宿主，而 `--binary /tmp/…/sid-code-mutC`
不匹配，A 的宿主（argv 带 token）被当成了 monitor 子进程。已在 `scripts/verify-monitor.ts` 加按 argv 形态
（`-p --dangerously-skip-permissions`）的排除规则，并在 `tests/scripts/verify-monitor.test.ts` 加一条用例
（去掉新规则 → 该用例变红；恢复 → 40 pass）。修复后复跑 mutC，两条断言都 ✗；用最终二进制复跑仍 PASS。

**覆盖不到的部分**：`/quit` 分支的真实 E2E（`-p` 拒绝交互命令，只能靠单测 + 信号路径间接覆盖）；
TUI 尾部只有静态接线检查（依赖整个 Ink 渲染栈，没有行为层接缝）；Windows 未验证。
