# dd 判据从「只看 if=」改成「of= 去向 + count= 上限」，块设备判定从前缀黑名单改反向白名单

## 决定了什么

修 2026-10-26 review 父缺陷文档（`20261024-危险命令正则按原文匹配`）时发现、PR #443
未闭环的一类缺陷：`磁盘擦除` 迁到结构化判定后，判据是「`program === "dd"` 且任一参数是
`if=/dev/(zero|random|urandom)`」——与前缀同一批修的其它 critical 不同，它**完全没用
`of=` 与 `count=`**，而 dd 的危险性恰恰由这两者决定。

改动三处：

1. **新增 `judgeDdCommand(args)`（`packages/core/src/permission/dangerous-command.ts`）**：
   dd 一支的判定树，有序：

   ```text
   of= 目标 t：
   ├─ t 是危险设备节点（isDangerousDeviceTarget）  → 拦（磁盘擦除 / 写入块设备）
   ├─ t 是无损去向（/dev/null、/dev/stdout、of=-…）→ 放行（不论有没有 count）
   ├─ 没有 of=（写 stdout）                       → 放行
   └─ 其余（普通文件 / 相对路径 / tmpfs 文件）
        ├─ 来源是 zero/random/urandom 且无 count=  → 拦 · 磁盘擦除
        └─ 有 count=                               → 放行
   ```

   「无损去向」必须排在「无 count 就拦」之前，否则 `dd if=/dev/zero of=/dev/null`
   （不带 count 的基准测试写法）修完仍然硬拒。`of=-` 是 dd 约定的 stdout，朴素规则
   一条都不覆盖它。模式名区分：来源是零数据报「磁盘擦除」，否则报「写入块设备」
   （`dd if=/dev/sdb of=/dev/sda` 一直是后者，实测如此）。

2. **`isBlockDevicePath` → `isDangerousDeviceTarget`，前缀黑名单改反向白名单**：
   `/dev/` 下除 `null|zero|random|urandom|stdout|stderr|fd/*|pts/*|tty` 之外一律当危险
   设备节点；另外把 `/dev/shm/*`、`/dev/mqueue/*`（tmpfs 挂载点里的普通文件）显式排除。
   这条同时影响「写入块设备」分支（重定向目标、`tee`/`cp`/`mv`/`install` 的参数）。

3. **`isDestructiveCommand`（`packages/core/src/tool/bash/read-only-validation.ts`）的 dd
   一支改为复用 `judgeDdCommand`**：那里原本是独立的一份旧正则
   `/dd\s+if=\/dev\/(zero|random|urandom)/i`，不收窄就会留下「权限层放行、TUI 标红成
   高危」的漂移（调用链 `cli/src/ui/utils/danger-detect.ts:41` →
   `DialogManager.tsx:74,166`，红框 + Enter 默认拒绝）。

**已知残留（有意接受，不是「有 count 就安全」）**：`dd if=/dev/zero of=<普通文件>
count=999999999` 会放行，按默认 `bs=512` 实写约 512 GB，足以填满磁盘。矩阵测试里
这条用例名标注了「已知残留」，避免下一个人按「有 count 就安全」把它当成正确预期。

**行为收紧（有意，写在这里防回退）**：

- `dd if=/dev/sdb of=/dev/mapper/vg-lv`、`of=/dev/rdisk2`、`of=/dev/dm-0`、
  `dd if=/tmp/img of=/dev/mapper/vg-lv` 四条**修前放行**（现存漏报：`if=` 不是零数据时
  完全没人看 `of=`），修后硬拒「写入块设备」。
- 重定向 / `tee` / `cp` 这一支同样认得出 `rdisk` / `mapper` / `dm-*` 等设备名
  （`cat x > /dev/rdisk2` 修前放行，修后硬拒）。
- 反向白名单会多拦一些没见过的设备节点（如 `/dev/ttyUSB0`、`/dev/console`）。这是取舍：
  误拦一个设备节点的代价是「一条命令跑不了、可用 `--dangerously-skip-permissions`
  全局关检测绕过」，漏一次真擦盘的代价是不可逆的数据丢失。

**牺牲的方向**：更安全 ↔ 更少返工。这次两边各让一步——误报收窄（更少返工）与漏报补齐
（更安全）同时做；代价在「反向白名单多拦没见过的设备节点」这一侧，选了更安全。

## 放弃了什么（以及为什么不选）

- **直接删掉 `磁盘擦除`，全交给 `写入块设备`**：会丢掉 `dd if=/dev/urandom of=x`
  （无 count，会一直写到磁盘满）这条保护——`写入块设备` 只认设备节点，认不出
  「往普通文件无限写」。除非把「无 count」也塞进去，那样模式名更不准。
- **只把 `磁盘擦除` 降级成 high（可确认）**：误报从「不能批准」变成「每次都要点」，
  噪音照旧、漏报也照旧。真正需要出口的是 `of=/dev/rdisk2`、`of=/dev/mapper/*` 这类
  **只靠 `磁盘擦除` 兜底的块设备盲区**，而降级对它们只是「点一下就过」——反而更危险。
- **按 `bs × count` 估实际写入量，超阈值才拦**：`bs` 有缺省 512、`count=1M` 这类后缀
  合法、`oflag=append` / `seek` 还会再改落盘量，静态估算的误差面比它挡住的风险大；
  阈值定多少都是拍脑袋。代价就是上面那条已知残留，写进这里而不是默认读者知道。
- **补块设备前缀（而不是反向白名单）**：等于「等下一个设备名出现再漏一次」。黑名单已经
  漏过一次（`rdisk` / `mapper` / `dm-*` 四条现状就在漏），补前缀是把同一个错误推迟。
- **「不是块设备就放行」当默认分支**：`of=/tmp/x` 也不是块设备，无 count 时必须拦。
  反向白名单只判「是不是设备节点」，普通文件那一支仍走 count= 判断。
- **连带把 rm / mkfs 的 UI 标红也换成结构化判定**：`isDestructiveCommand` 的 rm 正则
  同样对 `git commit -m "rm -rf /"` 误标红，但那是显示层、不在本次缺陷范围内；一次性
  连带改会让 review 分不清哪些行为变化是必要的。本次只换 dd 一支，其余保持原样。
- **把 `磁盘擦除` 拆成 `磁盘擦除` / `无限写入` 两个模式名**：可观测性更准，但会动
  `decisionReason.pattern` 的取值集合（审计日志口径、矩阵测试的模式名断言都要改），
  且历史可比性会断——日志里已有的「磁盘擦除」条目混着两种语义，拆名之后按模式做趋势
  对比必须按时间点切分。本次保持模式名不变。

## 拿什么证明它生效了

**探针实测**（真实 `PermissionChecker.check`，`permissionMode=always-allow`，
`SID_CONFIG_DIR` 重定向到 tmpdir）：

- 修前 25 条与缺陷文档 §2 的实测表逐条一致：§2-A 6 条无害 dd 全部「硬拒 · 磁盘擦除」；
  §2-C2 4 条真擦盘（`of=/dev/mapper/*`、`of=/dev/rdisk2`、`of=/dev/dm-0`）全部**放行**；
  §2-C3 的 `of=/dev/null`（无 count）与 `of=-` 硬拒。
- 修后：§2-A 6 条 + §2-C3 3 条全部放行；§2-B 前 5 条、§2-C1 6 条、§2-C2 4 条全部
  `硬拒(critical)`；`dd if=/dev/sda of=/tmp/backup.img`（整盘读到普通文件）仍放行。
  另补测 `/dev/shm`（tmpfs 普通文件）不被反向白名单误伤。

**回归矩阵**（`packages/core/tests/permission/dangerous-command-matrix.test.ts` 新增
E1/E2/E3 三组；`packages/core/tests/tool/bash/is-destructive-command.test.ts` 新增一条）：

- E1 放行组 11 条（含 `of=/dev/null` 无 count、`of=-`、`/dev/shm`、整盘读文件）；
- E2 硬拒组 7 条（`of=/dev/sda`、`of=/dev/nvme0n1`、参数换顺序、`if=/dev/sdb of=/dev/sda`、
  `if=/dev/urandom of=x`、`if=/dev/zero of=x`、`of=x if=/dev/zero`）；
- E3 块设备防线 12 条（§2-C1 6 条 + §2-C2 4 条 + `cat > /dev/rdisk2` + `/dev/shm` 放行对照）。

**变异自证（两个方向都跑，看它报了什么而不只看退出码）**：

1. `judgeDdCommand` 开头临时 `return { 磁盘擦除 }`（等价于只判 `if=`）→
   **E1 放行组 11 条全红** + `is-destructive-command` 的 dd 用例红；E3 保持绿。
   这一方向证明「误报组真的被新判据护住」。
2. `isDangerousDeviceTarget` 临时改回 `/^\/dev\/(sd|hd|nvme|disk|mmcblk|xvd|vd|loop|md)/`
   → **E3 块设备防线 11 条全红**（`rdisk`/`mapper`/`dm-0`/`ram0`/`zram0`/`sr0` +
   `cat > /dev/rdisk2`）+ dd 标红用例红；E1 保持绿。这一方向证明「真擦盘防线真的存在」。
   恢复后 142 pass / 0 fail。

**日志取证（真实误伤，按结构化字段筛，不文本 grep）**：

- 先备份 `~/.sid-code/logs/permissions-audit.log`（10MB 轮转、只保留 1 代，实测
  10,093,250 字节已撞上限），再解析备份文件。
- 结果：33,925 条记录（2026-08-23 → 2026-10-26）里 `decisionReason.type ===
  "dangerousCommand"` 共 33 条，其中 `pattern === "磁盘擦除"` **仅 1 条**，且那一条的
  program 是 `cat`/`wc`（heredoc 正文里含 `dd if=/dev/zero` 字面量，属父缺陷文档 §2.3
  已确认的假命中）。**program 确实是 dd 的命中 0 条。**
- 结论如实记：本机真实使用中没有踩到 dd 误伤，所以「误报存在」的证据来自探针与矩阵测试，
  不来自生产日志。这条取证同时说明「不区分 program 就会把结论读反」不是理论风险——
  唯一的命中就是假命中。
