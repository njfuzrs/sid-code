# 缓存断裂检测：阈值常量同源，/cache --breaks 区分不可信渠道

## 决定了什么

补齐方案 `docs-research/sid-code/bugfixes/todo/20261102-缓存断裂检测-账单侧判据补消息前缀.md`
里 T1/T3 两条**明文要求但此前未落地**的部分（T1/T2 的 #529、T3 的主体 #531 已在 main 上）。

1. **1% 显著性阈值同源**：`CHAR_WASTE_SIGNIFICANT` 移到 `api/message-fingerprint.ts` 导出。
   字节侧（`trace/prefix-break-probe.ts` 的 `judgeDisagreement`）与账单侧
   （`api/cache-detection.ts` 的 `message_history` 判据）都 import 它，各自不再写 `0.01`。
   原状态是两份字面量，注释写着「取同一个值」—— 改了一边另一边不跟着变，就会出现
   同一请求「字节侧说显著、账单侧说不显著」，而这种分歧没有任何报错。

2. **`/cache --breaks` 区分不可信渠道**：
   - 明细逐条标注 `⚠ 渠道 usage 不可信`（不过滤，藏掉记录会被读成「没断过」）；
   - 存在 untrusted 时单独一行说明条数与「未计入健康度建议」；
   - `getCacheHealthAdvice()` 统计时排除 `channelTrust === "untrusted"`，全不可信时不给建议。
   原状态是 `--breaks` 分支完全没读记录里已有的 `channelTrust` 字段（#531 只接了跨会话的
   `--history` 聚合），于是走 ppchat 这类渠道时，会话内明细与健康度建议都会被渠道编造的
   `cache_read` 带偏 —— 建议会让人去改本地 prompt，而问题根本不在本地。

## 放弃了什么（以及为什么不选）

- **只在 `cache-detection.ts` 里保留 `MESSAGE_WASTE_SIGNIFICANT = 0.01`、靠注释约束同步**。
  否决：这正是 `shapeKey` 漂移的同型问题。注释拦不住漂移，也拦不住有人写 `0.02`。
- **把阈值常量放进 `trace/prefix-break-probe.ts` 让 `api/` 反向 import**。
  否决：依赖方向是 trace → api，反过来会让 api 依赖 trace（包内分层规则）。
- **`--breaks` 直接过滤掉 untrusted 记录**。否决：明细是「本会话断过几次」的事实清单，
  过滤后用户会以为没断；正确做法是展示 + 标注 + 在「统计」性质的健康度建议里排除。
- **健康度建议里对 untrusted 占比做加权或阈值放宽**。否决：编造的数字无论怎么加权都不是信号，
  排除比调参诚实。
