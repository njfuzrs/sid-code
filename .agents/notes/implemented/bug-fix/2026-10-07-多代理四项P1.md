# 多代理四项 P1：fork 保留配对工具块、闸门待补一笔、fork 缺省隔离 tracker、自定义 agent 白名单收住 MCP

## 决定了什么

来源：`docs-research/sid-code/bugfixes/todo/20260926-多代理-顺着sc-06核出的缺陷.md` 的 F1 / F3 / F5 / F7。

- **F1** `agent/fork.ts`：`stripDanglingToolBlocks` 原来会无条件丢掉所有 tool 块，现在只删截尾造成的**未配对**块（以「紧随的 user 消息里有同 id 的 tool_result」为判据），已配对的往返原样保留，thinking 一律丢。fork 的契约定为「轻量截尾 + 保留配对工具往返」，`sub-agent.ts` / `tool.ts` 里「继承完整父对话 / prompt cache 友好 / 对标 cc」这几处注释改成按实际行为描述。
- **F3** `agent/background-task-gate.ts`：「不同 label 也丢弃」改成「按 label 待补一笔，前一个结束后串行放行」，同 label 仍然丢弃。首次放行时注册 `pre-flush` 关闭钩子，退出时等在跑的任务（4s 上限），待补的直接丢弃。
- **F5** `agent/forked-agent.ts`：调用方没传 `statefulTools` 时，在内部自建一份独立 tracker 的有状态工具（只替换主注册表里存在的那几个名字），缺省值从「共享」反过来变成「隔离」。
- **F7** `agent/tool-filter.ts`：Layer 3 的 `tools` 白名单对**自定义 agent** 的 MCP 生效，唯一的放行口是在 `tools` 里写出 MCP 全名，`["*"]` 仍然全放。

## 放弃了什么（以及为什么不选）

- F1 不加 `FORK_PLACEHOLDER_RESULT`，也不做字节级继承：我们的 fork 是同步单发，子代理会按类型重建 system prompt 和工具池，缓存对齐本来就做不到。注释里也不再承诺这一点。
- F3 不做 await，也不调换两条语句的顺序：前者会把收尾拖到 44s，后者只是把「永远跑 A」换成「永远跑 B」。退出时**不启动**待补任务，因为刚发出的 fork 几秒内就会被进程退出掐断，只是白烧钱。
- F5 不把 `statefulTools` 改成必填：调用方拿不到工具的构造方式，各写一份就会漂移。生产上三个调用点（app.ts）其实**已经各自注入了**独立 tracker，原文档里「三处都没传」的描述与 app.ts 不符，所以这次修的是缺省值这道纵深防线，不是一个活着的生产路径缺陷。
- F7 不收紧 Layer 4 对 MCP 的豁免，也不对内置类型的 `tools` 收紧 MCP：general-purpose 的后台任务和 `task` 类型会因此整体失去 MCP，那是回退。内置类型的 MCP 去留仍由 Layer 2 的 readOnly 判据决定。

## 拿什么证明它生效了

- `bun test ./packages/core/tests/agent/` 结果 483 pass / 0 fail。
- 变异自证：逐个把四个源文件换回 origin/main 的版本，对应测试都红（fork 1 条、tool-filter 3 条、forked-agent 1 条、gate 5 条），还原后转绿。
- **F3 生效的旁证（CI 实测）**：`packages/cli/tests/sdk/sdk-control-protocol-e2e.test.ts` 的 `can_use_tool` 用例在本分支红、在 main 绿。给 mock 加打印后对比：main 上只有主循环请求（tools=24）；本分支多出 tools=41 的请求，这是 end_turn 之后真正跑起来的记忆提取 fork，它从按顺序 shift 的假服务那里抢走了下一轮的脚本回复。也就是说，修复前这个 fork **一次请求都没发过**。测试已改为显式设 `SID_CODE_AUTO_MEMORY=0`。
- 没有做真实会话验证：F3 的「记忆提取触发率由 0 变成非 0」要等发版后，从 trace 里 `BG_GATE` 的 debug 日志或 MEMORY.md 的写入次数去确认。
