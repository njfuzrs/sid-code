# 敏感文件的名字类规则对源码/文档扩展名豁免，不再把 secret-guard.ts 当凭证硬拒

## 决定了什么

`packages/core/src/permission/path-validator.ts` 把 `SENSITIVE_FILES` 拆成两组：

- 格式 / 固定位置类（`.env`、`.pem`、`.key`、`id_rsa`、`.ssh/`、`.aws/credentials`、`.kube/config`、`.npmrc`、`.git-credentials` 等）：留在 `SENSITIVE_FILES`，行为不变，任何扩展名都拦。
- 名字类（`/credentials/i`、`/password/i`、`/secret/i`、`/token\.json/i`）：挪到新的 `SENSITIVE_NAME_PATTERNS`。只有文件扩展名**不在** `SOURCE_EXTENSIONS` 里时才生效，扩展名比较不区分大小写。豁免的扩展名有 `.ts .tsx .js .jsx .mjs .cjs .py .go .rs .java .kt .rb .php .swift .c .h .cpp .cs .md .mdx`。

判定入口仍然只有 `matchesSensitivePath`，所以 `validateAccess`、`isSensitivePath`（grep / read_many 列举过滤）和 `cli/src/command/custom.ts` 三处用的是同一套规则。

根因：名字类规则是对整条真实路径做子串匹配，不看扩展名，也不区分路径里的哪一段。结果是做凭证防护的源码本身也被硬拒，比如 `memory/team/secret-guard.ts`、`secret-scanner.ts`。本机审计日志里「敏感文件」类的拒绝一共 10 条，其中 9 条是这种误拦；bench 的 L3f（审计 `memory/`）每跑一次撞 3 次。

方向：更准（审计 / review 类任务不再撞墙）。牺牲的是安全，见下面「剩余风险」。

### 剩余风险（点破，不在本 PR 扩范围）

硬编码在源码里的密钥（如 `config/secrets.ts`）现在能读了。这一类本来就不是文件名规则防得住的：同样的密钥写在 `config.ts` 里，改动前也照样能读。

已核实：**工具结果进入上下文之前没有做内容脱敏**。`query/tool-executor.ts` 的 `settle()` 只调 `detectSensitiveData` 打 SECURITY 告警，刻意不改写内容（那里的注释写了理由）；`maskSensitiveData` 只作用于日志、trace 和遥测落盘。所以源码里的硬编码密钥会进模型上下文，能看到的痕迹只有一条告警日志。要补这一层，属于「工具输出脱敏」的独立议题。

## 放弃了什么（以及为什么不选）

- **B：名字类规则只匹配文件名，不匹配目录段**。修不了 `secret-guard.ts`，因为它的文件名本身就含 `secret`。
- **C：维持现状，让用户自己写 `Read(**/secret-guard.ts)` 解除**。每个仓库都得配一遍；无头 bench 和 CI 里没人去配，默认体验就是坏的。
- **D：直接删掉 `/secret/i`**。`secrets.yaml`、`client_secret.json` 这类真凭证文件会漏掉。
- **豁免列表也收 `.json` / `.yaml`**：不收。凭证文件恰恰集中在这些数据格式上。

## 拿什么证明它生效了

- `bun test ./packages/core/tests/permission/path-validator.test.ts`：56 pass / 0 fail。新增的 describe「名字类敏感规则豁免源码扩展名（F1-E1）」覆盖四组用例：
  - 源码 / 文档放行：`secret-guard.ts`、`secret-redact.ts`、`secret-scanner.test.ts`、`password-policy.md`、`credentials-loader.py`、`secrets-docs/README.md`。
  - 凭证文件照旧拒：`credentials.json`、`secrets.yaml`、`client_secret.json`、`password.txt`、无扩展名的 `secret`、`token.json`、`secret.key`。
  - 格式类不受影响：`.env`、`a.pem`、`.ssh/id_rsa`、`.aws/credentials`，以及专门构造的 `.aws/credentials.ts`、`.ssh/config.ts`。
  - 大小写：`Secret-Guard.TS` 放行；另断言 `isSensitivePath` 和 `validateAccess` 口径一致。
- 变异自证（每次只改一处，跑完即恢复）：
  - M1，去掉扩展名豁免（条件写死为 true）：8 fail，「不再误拦」组、大小写组、`isSensitivePath` 组全部变红。
  - M2，把豁免误加到格式类循环上：2 fail，`.aws/credentials.ts` 和 `.ssh/config.ts` 变红。
  - M3，扩展名比较区分大小写：1 fail，`Secret-Guard.TS` 变红。
- `bun run affected-tests:run`：1030 pass / 0 fail。`bun test ./packages/core/tests/permission/ ./packages/cli/tests/command/`（含 `custom.ts` 的使用方）：1653 pass / 0 fail。
- `bun run lint` 0 错，`format:check` 通过，`typecheck:gate` 66 / 基线 66 无新增，`make build` 自检通过，没有出现 `will always be undefined`。
- 合入后的附带观察：F5 的 L3f 样本里「敏感文件拒绝」应降到 0。
