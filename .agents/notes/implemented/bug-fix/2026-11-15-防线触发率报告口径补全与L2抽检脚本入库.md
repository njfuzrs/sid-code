# 防线触发率报告口径补全（覆盖探测 / 截断分项 / 编辑失败提醒）与 L2 抽检脚本入库

## 决定了什么

- `scripts/defense-trigger-report.ts` 三处口径补全：
  - **覆盖探测改探 `AfterModelRaw.tool_use_total`**。`tool_use_facts` 是平铺进 `AfterModelRaw` 的四个整数（`trace/collector.ts`），`AfterModel` 上根本没有这个字段。初版探测写成 `AfterModel.tool_use_facts`，于是恒报「窗口内从未出现」。
  - **新增 `truncated` 三分项**（`text_only` / `with_tool_use` / `params_truncated`），来源 `AfterModelRaw`，判据 `stop_reason ∈ {max_tokens, length}`。对应方案 T6 的「按是否带工具调用拆开」与 T5 要防的「截断 + 工具调用」形态；`params_truncated`（`tool_use_truncated > 0`）是写坏文件的直接证据。
  - **新增 `edit_failure_reminder` 按 `kind` 统计**，并把 `EditFailureReminder` 加进覆盖探测。此前注册表已把该防线的 `metricSource` 从 `none` 改成事件（#489），但没有任何报告侧消费方 —— 口径声明了却没有取数实现。
- `scripts/l2-audit.ts` 新入库：把 T7 那次「18 条 L2 命中点抽检」的口径固化。此前用的是 `/tmp` 临时脚本，`/tmp` 清理后无法复算。脚本对每个 `StallEscalation{level:2}` 导出影子字段、命中前的工具轮、命中后 M 轮内的成功写入，并给两条明确提示（影子字段非零仍触发 / 命中后有成功写入 = 疑似误伤）。
- 这个勘误其实早就写过：`736a0a3d`（2026-10-30 15:29）就在 `origin/feat/defense-trigger-report` 上。但它的**提交时间晚于 PR #480 的合并时间（15:22）7 分 49 秒**，时序上不可能进入 #480，之后也没开新 PR —— 于是方案文档里「已在 PR #480 追加修复」这句话一直是假的。本次连同后两项口径补全一起重新提 PR。

## 放弃了什么（以及为什么不选）

- **没把 `stop_max_tokens` 的来源从 `AfterModel` 改成 `AfterModelRaw`**：现有报告与测试都基于 `AfterModel` 口径，改了会让历史数字不可比。新分项另起字段，两个来源分别计数 —— 同一份报告里能看到「归一化口径」和「原始口径」两个数，反而便于互相校验。
- **没有用 `content_types` 判「带工具调用」**：`tool_use_total` 与 `tool_use_truncated` 同属一份 `ToolUseParamFacts`，同源且是整数，比检查内容块数组更直接，也不必依赖块顺序语义。
- **没把 l2-audit 做成「自动判定该不该触发」**：判读需要人看前后文，脚本只给原始证据。自动判定等于把「什么算停滞」这条口径藏进脚本，下次改判据时更难审 —— 而这个脚本存在的意义恰恰是让判据改动可复算。
- **没动 L2 判据本身**：本次只补可观测性。方案 T7 第二步（统一软着陆出口）的前置条件是「先改 L2 判据」，那属于另一个改动单元。
- **没让 `deliveryTurns` 缺失时回填 0**：旧轨迹（2026-11-06 之前）没有这个字段，按 0 读会把「该版本没有此字段」误判成「命中时确实没有交付轮」，正是这次要修的同类错误。
