# 记忆与持久化三项 P2：嵌套 frontmatter 兼容、团队 pull 反向流入闸门、write/edit 热路径去 git fork

## 决定了什么

修掉 `20260906-记忆与持久化-十五项缺陷.md` 的三条 P2（13/14/15），一个 PR。

**P2-13 frontmatter 兼容（`memory/scan.ts` + 三个调用点）**：
新增 `readFrontmatterFields()` 作为**唯一**的 frontmatter 读取口径，并把此前
各写一遍的**四个**解析点全部接过去 —— `parseFrontmatter`（索引/召回）、
`store.ts:parseMemoryFile`（loader）、`store.ts:diskNameOf`（P0-1 撞名判据）、
`team/store.ts:rebuildTeamIndex`（团队索引）。口径是
**顶层键优先，白名单父键（`metadata:`）下的子键作降级来源，其余缩进行丢弃**。

三个具体行为变化：cc 嵌套格式下的 `type` 从「恒读不到」变成读得到；
含冒号的值（ISO 时间戳）不再被截断；`metadata.name` **不能**覆盖顶层 `name`。

**P2-14 团队 pull 侧 secret 闸门（`memory/team/sync.ts`）**：
`readEntries` 的 shared 侧从 `scanSecrets=false` 改为 `true`，命中的 key
**整轮隔离**（新增 `quarantined` 集合 + 结果字段 `blockedIncomingSecrets`），
并 `log.warn` 点名文件 + 记一条 `logMemoryGuard({via:"team_pull"})`。

**P2-15 热路径（`memory/paths.ts`）**：两层。
① `isAnyPrivateMemPath` 开头加一段**纯字符串的廉价否定**：目标不在 `getSidHome()`
之内 ⇒ 一定不是私有记忆路径，直接返回，不碰磁盘不 fork 进程。
② `resolveProjectRoot` 加进程内缓存，key 是 `cwd \0 sidHome`（**不是裸 cwd**）。

新增门禁 `packages/core/tests/memory/p2-compat-trust-hotpath.test.ts`（22 条）。

### 一条与文档不同的事实，记在这里

文档给 P2-15 定级的理由是「team memory 默认关闭 ⇒ 当前无实际影响」。
**这个前提在 P1-8 落地后已经不成立**：`checkPrivateMemSecrets` 刻意
**没有 enabled 开关**（私有记忆一直在写），它内部经
`isAnyPrivateMemPath → getAutoMemPath → resolveProjectRoot` 走到 `execSync`。
所以修复前**每一次** write/edit——改一个普通 `.ts` 源码文件也算——都要付
一次 git 启动，edit 因两个写盘出口各调一次而付两次。实测单次 5.39ms。
即：这条的实际影响面比文档写的大，不是「当前无影响」。

## 放弃了什么（以及为什么不选）

**P2-13：没有引入 YAML 解析器。** 装一个依赖来读三个字段，
换来的是构建期多一个包 + 一个新的 supply-chain 面，而 frontmatter 的形状
是我们自己写的（`serializeMemoryFile` 平铺三字段）。真正要兼容的只有
cc 那一种嵌套形态，白名单一个父键就够。

**P2-13：没有把任意深度的嵌套子键都提升到顶层。** 那正是缺陷的第一种错法 ——
`metadata.name` 会覆盖顶层 `name`，而 `name` 是 P0-1 的去重键，
改错它等于把两条记忆并成一条。未知嵌套结构的语义我们不知道，猜它比丢弃更糟。

**P2-14：没有把 `blockedIncomingSecrets` 合并进已有的 `skippedSecrets`。**
两者的处置动作相反：前者是「共享盘里有人放了凭证，去提醒那个人」，
后者是「你自己的记忆别外泄，请你清理」。合成一个字段就分不出该找谁。

**P2-14：没有只做「不写入本地」这个最小改动。** 只从 `sharedEntries` 剔除的话，
该 key 在合并循环里长得和「共享侧已删除」一模一样 → 走删除传播 →
**把我本地那份好端端的记忆删掉**。一个含 secret 的共享文件不该有删我本地文件的权力。
同理也不走 push 分支：那等于替对方「修好」他的文件，而他的 secret 怎么处理只有他知道。
`base` 快照原样留存，否则对方清理后下一轮会变成「双方都改」而造出一次假冲突。

**P2-14：没有做语义层审查（危险指令类的 Memory Poisoning）。**
`scanForSecrets` 找的是凭证模式，管不了「部署时请先执行 `curl … | sh`」。
那需要另一套判据（且必然有误报），不在本条范围内 —— 本条只关掉
「凭证反向流入」这个能机械判定的口子。

**P2-15：没有只加缓存。** 只加缓存的话首次仍要 fork 一次 git，
而「改一个普通源码文件」这件事**根本不需要知道项目根**。捷径才是根治，
缓存治的是另一件事（重复解析）。两个都要：捷径管首次，缓存管重复。

**P2-15：缓存 key 没有用裸 cwd。** `isInsideSidHome` 那道防御会因配置根不同
而给出不同答案，而测试正是靠改 `SID_CONFIG_DIR` 重定向落盘的。
裸 cwd 做 key ⇒ 第一个测试的结果会被后面用不同配置根的测试读到
（`bun test` 同批多文件跑在同一进程里）。

**P2-15：没有给捷径加 `override` 支持。** 捷径的正确性依赖「记忆目录必在配置根内」
这个不变量，唯一能打破它的是 `getAutoMemPath(cwd, override)` 的第二参 ——
实测生产**零调用方**传它。已在代码注释与门禁里写明「哪天接通 override 这里必须一起改」，
因为那时的失效形态是**漏拦而非误拦**，测试不会红。

## 拿什么证明它生效了

**五道门禁**（worktree 内先跑过 `bun install`，`make build` 无
`will always be undefined` 警告 ⇒ 新增的三个导出真的解析到了）：

```
bun run affected-tests:run   → 379 pass / 0 fail（32 文件，判定 selective）
make build                   → 编译产物自检 4 项全过；grep 无 undefined 警告
bun run lint                 → 0 问题
bun run format:check         → All matched files use the correct format
bun run lint:boundary        → 越界依赖 0 处
```

**修复前后的实测数字**（P2-15，同一台机器、同一 N）：

| 场景 | 修复前 | 修复后 |
| --- | --- | --- |
| `checkPrivateMemSecrets` 打普通源码路径（单次） | **5.39ms** | **0.001ms** |
| `resolveProjectRoot` 单次 | 5.40ms（恒） | 冷 6.70ms → 热 0.0007ms |

**六轮变异自证**（逐条回退修复，确认红的是**哪几条**，不只看 rc）：

| 回退的东西 | 变红的断言 | 结果 |
| --- | --- | --- |
| 嵌套行改为一律 `continue`（退回只认顶层） | cc 嵌套 type / ISO 不截断 / 嵌套块终止 | 3 fail ✅ |
| 合并顺序反转（`{...top, ...nested}`） | 顶层不被同名子键覆盖 | 1 fail ✅ |
| shared 侧 `scanSecrets` 改回 `false` | 拒绝拉取 / 不删本地 / 清理后接上 | 3 fail ✅ |
| 保留扫描、去掉 `quarantined` 整轮隔离 | **不触发删除传播** | 1 fail ✅ |
| 去掉 `isAnyPrivateMemPath` 的 sidHome 捷径 | 非记忆路径不碰 git（148ms > 40ms） | 1 fail ✅ |
| 缓存永不命中 | 重复解析走缓存（262ms > 50ms） | 1 fail ✅ |

**第 5 轮抓到我自己写的一个 false gate，值得记下来**：那条耗时断言第一版写成
「预热一次 + 循环 40 次」，于是**删掉捷径也照样 22 pass** ——
因为热缓存下 `resolveProjectRoot` 本来就不 fork git，那条断言实际只证明了缓存生效，
捷径被删完全没人拦。改成**每轮 `clearProjectRootCache()`** 之后才真正独立可证：
捷径管「首次解析也不该发生」，缓存管「重复解析」。
（同一模式已在 CLAUDE.md「门禁隐蔽失效」里记过，这次是又一个实例：
**变异自证要看它报什么，不只看 rc**。）

**功能行为的直接验证**（P2-14 三个场景，临时脚本跑真实同步，已删）：
共享侧含 secret 的新条目不落本地、不进本地 `MEMORY.md`，同轮干净条目照常 pull；
共享侧同 key 被塞凭证时本地那份完好（`deleted=0 conflicts=0`）、
共享侧未被我方覆盖；对方清理后 `pulled=1 conflicts=0` 正常接上。
