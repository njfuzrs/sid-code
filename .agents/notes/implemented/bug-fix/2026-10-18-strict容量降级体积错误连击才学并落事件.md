# strict 容量降级：体积错误连击才学且带 TTL，400 前置，降级落事件，两路径共用一个 helper

## 决定了什么

对应遗留清单（20261018 思考开关修复落地复审）的 R3 / R11 / R12 / R13 / T9，改动在
`packages/core/src/llm/strict-tool-budget.ts` 与 `anthropic.ts`。

- **R3 学习策略分两类**：数量错误（稳定 6/6）仍是一次就学、进程内永久有效；语法体积错误（偶发 1/6）
  默认**只降本次请求**，同一端点**连续** `GRAMMAR_LEARN_STREAK = 2` 次才写进端点上限，
  学到的值 `GRAMMAR_LEARN_TTL_MS = 30min` 后过期、回到原上限重新试探。请求成功一次就清零连击。
- **R13**：`parseStrictCapacityError` 先要求 HTTP 状态码为 400（用 `extractHTTPStatus`）。
  SSE 阶段（200 后 `event: error`）的同文案暂不识别，边界写在注释里。
- **R12**：「带降级的创建重试」收成 `createWithStrictBudget({ tools, endpointKey, priorityOf, signal, create, onDegrade })`，
  流式和非流式共用，原先的两份重试循环删掉。
- **R11**：每次降级发一条 `StrictToolDegraded` 事件（`model / endpoint_key / kind / from / to / learned / attempt`），
  digest 新增「strict 降级」一节，汇总次数、按类型拆分，以及本会话学到的端点上限。原来的 `log.warn`
  保留，并补上「已记入端点上限 / 仅本次」。

## 放弃了什么（以及为什么不选）

- **体积错误永不学习，只降本次**：确实稳定超体积的端点会每个请求都先撞一次 400 再降，白烧一次往返。
  连击 2 次后学，是在「一次抖动锁死整个进程」和「每次都先撞墙」之间取的折中。
- **学到的上限落盘**：已在原文件头否决过（上游上限会变）。TTL 是同一理由的延伸。
- **成功 K 次后 +1 试探回升**：要多维护一个计数器，而且 +1 收敛很慢；TTL 到期直接回到默认值，
  逻辑更简单，代价是到期后最多再撞一次 400。
- **SSE `event: error` 阶段也识别**：已经开始流就降级重发，可能重放已 yield 的增量，需要另外设计。
  目前没有观察到这种形态，不预先猜格式。
- **牺牲的方向**：体积错误只降本次时，下一次请求可能又撞 400（更快 ↓ 一点），换来的是 strict 数不被
  偶发抖动长期压低（更准 ↑）。

## 拿什么证明它生效了

- `bun test packages/core/tests/llm/strict-tool-budget.test.ts`：30 pass。
- 变异自证（逐条改坏 → 看到对应断言变红 → 还原，还原后用 `cmp` 核对源码与变异前一致）：
  - 去掉 400 前置 → 「R13：非 400 / 无状态码时同文案不算容量错误」红；
  - 体积错误一次就学 → R3 两条和「T9：非流式语法体积…不写进端点上限」红；
  - TTL 不过期 → 「学到的体积上限按 TTL 过期」红；
  - helper 成功后不清零连击 → 第一轮**没有红**，于是补了 provider 层「中间都成功了不算连击」断言，之后红；
  - 不调用 `onDegrade` → 「R11：降级落 StrictToolDegraded 事件」红；
  - 去掉重试上界 → 「重试次数用完就抛出」红；去掉 abort 判断 → 「已 abort 后不再降级重发」红。
- 现有流式 / 非流式接线用例（发前收口、数量 400 学习、端点隔离、优先级透传）在 helper 重构后原样通过，
  说明 R12 没改行为。
