# 轨迹上传：`auto_upload: false` 与配置级 `privacy_level` 接线，observability 页补全上传配置说明

## 决定了什么

核对「默认不上传、要手动打开」在官网是否写清楚时，回源码发现两处「配了不生效」，一并修掉：

- **`trace.upload.auto_upload` 是死配置**：config 层解析齐全（`config.ts` 的 trace 归一化），
  但 `initTraceCollector` 与 collector 都不读它，配 `false` 照样会话结束自动传、启动补传、起心跳。
  现在 `CollectorOptions.autoUpload` 接线：`false` 时 SessionEnd 不上传、SessionStart 不做启动补传，
  `init-helpers.ts` 也不起心跳 / 队列扫描定时器；uploader 仍创建，给 `/debug` 上传快照这类手动通道用。
  `--upload-traces` 走独立路径，不受影响。
- **settings.json 里 `analytics.privacy_level: "essential-traffic"` 拦不住轨迹上传**：
  配置级隐私等级只在 `initTelemetrySystem` 里注入，而 `app.ts` 先跑 `initTraceCollector`，
  于是 essential-traffic 门控那一刻读到的还是 default，只有环境变量能拦。
  现在 `initTraceCollector` 开头先注入一次（同值幂等）。
- `website/team/observability.md`：「关掉与打开」写明上传必须手动打开、官网模板不含上传、
  老用户自查命令；新增三种打开方式（settings / env / CLI）及其优先级、env 三个变量缺一不可与整块覆盖的坑、
  项目级 settings 不放行 `trace`；字段表补全并写清 `auto_upload` 的真实语义；列出三道强制关闭；
  去掉已漂移的 `src/cli.ts:505-511` 等行号引用。

## 放弃了什么（以及为什么不选）

- **只改文档、把 `auto_upload` 标成「未实现」**：用户恰好需要「配了地址但只手动传」这个档位
  （开发者自己的机器先攒、确认再传），且实现只是两处判断，标未实现是把能修的缺陷写成限制。
- **`auto_upload: false` 时干脆不创建 uploader**：会顺带废掉 `/debug` 上传快照，那是用户显式的手动动作。
- **把 privacy 注入挪到 loadConfig**：影响面大（所有读隐私级别的模块的初始化时序都要重审），
  这里只需要保证轨迹闸门看到正确值，就地注入即可。

## 拿什么证明它生效了

- 单测：`collector.test.ts` 两条（false 时两条自动路径都不触发 / 默认两条都触发）；
  `init-trace-upload-gates.test.ts` 两条（配置级 essential-traffic 时无 uploader / 默认有）。
  变异自证：去掉启动补传的 `autoUpload` 判断 → 1 pass 1 fail；删掉提前注入 → 1 pass 1 fail；复原全绿。
- 端到端（编译产物 + 本地假轨迹服务器记录所有请求，`sid-code -p hi` 跑 25s）：
  `auto_upload: true` 收到 `GET /traj/api/v1/health` 1 条；`auto_upload: false` 收到 **0 条**。
- 文档里新写的优先级说法逐条用 `loadConfig` 实测过：只设 URL/TOKEN 不设 `SID_CODE_TRACE=1` → 仍走 settings；
  设了 `SID_CODE_TRACE=1` 不给 URL/TOKEN → upload 被覆盖为空；CLI 覆盖 env。
- `bun run affected-tests:run` 2351 pass / 0 fail；`make build` 成功。
