# kitty CSI-u 的 `:` 分隔参数改为主码点解析，避免启用 flag 4/16 后丢字符

## 决定了什么

修 `packages/cli/src/ui/contexts/KeypressContext.tsx` 的 CSI-u 解析，两处：

1. **采集循环接受 `:`**：`isCsiParamChar` 把 `:` 与数字一并吃进 `sequence`。此前循环只吃数字和 `;`，`\x1b[38:55;2u` 在 `:` 处截断，`cmd` 只剩 `38:`，`&` 丢失且 `55;2u` 逐字符漏进输入框。
2. **解析前规范化参数**：`normalizeCsiParams` 把每个 `;` 段取 `:` 之前的第一段（主码点 / modifier），其余（候选码点、事件类型、关联文本）丢弃，再交给原 CSI-u 正则。这样 `38:55;2u` → `38;2u`、`38;2;38:55u` → `38;2;38u`，主码点与 modifier（shift）都保住。

只改 CLI 层；新增 `packages/cli/tests/ui/contexts/keypress-csi-u-params.test.ts` 8 条用例。

## 放弃了什么（以及为什么不选）

- **不改 `packages/tui/src/parse-keypress.ts`**：它的 `kittyRe` 对带 `:` 的 CSI-u 走 `make('')`（整段丢弃、不漏乱码），且 `input-vectors.json` 是冻结行为基线（`kitty 97:65;2u` 的期望就是空事件），修改需同步更新基线；CLI 用户输入走 `useKeypress`（KeypressContext），不走它。留作后续单独处理。
- **不接 `detectCapabilities()` / 不改底座 `>1u` 为 `>31u`**：本次只修解析，不改变启用面。实测生产环境 flag 4/16 从未被请求（CLI 的 `>31u` 是死代码，底座只发 `>1u` + `>4;2m`），因此这是防御性修复，不是线上故障修复。
- **不做 §6.2 的 alt/ctrl 宽松处理**：修饰键不产文本是快捷键语义，本身正确；终端误报修饰位是另一类问题，需要真机反馈再定。
- **不处理 event-type（press/repeat/release）**：flag 2 未启用；规范化时 `:3` 被丢弃，release 会被当成按下。启用 flag 2 前需另行处理（届时 release 不应插入字符）。

## 拿什么证明它生效了

- 新增测试：`bun test ./packages/cli/tests/ui/contexts/` → **19 pass / 0 fail**（新增 8 条 + 既有 11 条）。
- 变异自证（两条，看的是**报了什么**）：
  1. `normalizeCsiParams` 恒等返回 → 2 fail，`Expected: true / Received: false`（shift 断言），证明规范化受测试保护；
  2. `isCsiParamChar` 改回只认数字 → 6 fail，`Received: "55;2u"`，精确复现原始缺陷形态。
  两次变异后均已恢复，恢复后全绿。
- 待跑：`bun run affected-tests:run`、`make build`、`bun run lint`、`bun run format:check`、`bun run typecheck:gate`。
