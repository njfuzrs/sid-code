# fallback 流超时从「attempt 绝对计时」改为「距上次内容进展」，且续命时不得换 AbortController

## 决定了什么

`packages/core/src/llm/fallback.ts` 的 `streamTimeoutMs`（默认 300s）这一层，
谓词从**「这次 attempt 跑了多久」**改成**「距上次内容进展多久」**：
流循环里每收到一个内容事件就重排定时器。

把原来 `resetStreamTimeout()` 的两个职责**拆成两个函数**，这是本次改动的要害：

| 函数 | 做什么 | 调用点 |
| --- | --- | --- |
| `renewStreamTimeout()`（新增） | **只重排定时器**，复用同一个 `streamTimeoutCtl` | 流循环内，每个内容进展事件 |
| `resetStreamTimeout()`（保留原语义） | 重排定时器 **+ 换新 `AbortController`** | 只在 attempt 边界（`:1209` 401 重试 / `:1543` 退避后重开） |

判据 `isStreamContentProgress` 取 `content_block_delta` / `content_block_start` /
`message_delta` 三者的**并集**：本层是所有 provider 的公共漏斗，而各 provider 的
`isContentProgress` 口径不同（anthropic 认 delta + message_delta，Responses 只认 delta）。
取窄了会误杀该 provider 的健康流；本层职责是兜底回收僵死连接，
**判宽的代价是「僵死回收慢一档」，判窄的代价是「健康流被杀」，两者不对等。**

**本 PR 不动任何阈值数值**（数值归 PR10/PR14），只改「这一层判什么」。

### 为什么要改

轨迹 `20260817-135824-fcf863e1`（GLM-5.3 经公司网关）：24 次 `TimeoutFired`
100% 是 `fallback_stream_timeout`，`elapsed_ms` 全部精确落在 **300000±300** ——
这是绝对计时器的指纹（真正的"多久没进展就杀"不会这么齐平）。
一条持续吐 `reasoning_content` 的**健康**流被无差别掐断，已累积思考内容全部作废、
被迫从零重来；上下文越大思考越慢 → 越容易触顶 → 恶性循环。
即用户看到的「前期快、后期慢、最终请求失败」。

## 放弃了什么（以及为什么不选）

- **放弃「照 §5 P0-2 字面实现」**（直接在流循环里调原 `resetStreamTimeout()`）。
  这是本 PR 唯一真正危险的选项，也是方案文档专门警告的坑：
  `makeCombinedSignal()` 只在 `openStream` 时**取一次** signal，在飞的 fetch 持有的是
  **旧** controller 的 signal。attempt 中途换 controller → 新 controller 的 `abort()`
  到不了那个 fetch、旧 timer 又已被 clear → **这一层超时被彻底解除**，
  真半开连接再也没人回收。那是退回「0 层」状态，**比现在的 300s 误杀更坏**。
  已用变异实测把这条钉死（见下一节变异 B）。

- **放弃「顺手把阈值放宽到 600s」**。诱惑很大（一起改一次就好），但方案文档 §0.0.1
  约束②写明：放宽必须晚于改谓词，否则就是**用被 300s 删失的分布去论证新阈值** ——
  循环论证。且谓词改对之后值大概率根本不用动（四家竞品都停在 ~300s，
  说明 300s 作为 **idle** 门槛本就够用，我们的问题是把它当成了 **total**）。

- **放弃「只认 `content_block_delta`」**（对齐 Responses 的窄口径）。
  无参数工具调用整条流只有 start + stop、零 delta，窄口径会把它判成"无进展"而误杀。
  这与下方 `hasYieldedContent` 的 B2 判据是同一个坑，那里已经踩过一次。

- **放弃「把续命放在 `yield event` 之后」**。yield 会把控制权交给消费方，
  消费方可能慢（渲染/落盘）；续命不该等它，否则慢消费方会被算成"模型没进展"。

## 拿什么证明它生效了

新增 `packages/core/tests/llm/fallback-content-progress-timeout.test.ts`（5 个用例，
含 3 个行为用例 + 2 个静态哨兵）。**每条都做了变异自证**，不是"跑绿了就算数"：

```
$ bun test ./packages/core/tests/llm/fallback-content-progress-timeout.test.ts
 5 pass  0 fail  16 expect() calls  [1.58s]
```

**变异 A（去掉续命接线，回到旧的绝对计时行为）**：
正向用例如期变红，且红在正确的地方 —— 8 个 delta 只收到 6 个：

```
(fail) 总时长远超阈值、但块间隔小于阈值的健康流 → 不被掐断，完整跑完
error: expect(received).toBe(expected)   Expected: 8   Received: 6
```

**变异 B（续命时 `streamTimeoutCtl = new AbortController()`，即 §5 P0-2 警告的坑）**：
3 条同时变红，其中**行为用例的失败形态正是"超时被彻底解除"**（hang 满 15s 用例超时）：

```
(fail) 先有进展、随后僵死 → 仍被超时回收并转 fallback [15000.01ms] ← hang，超时确实失效了
(fail) renewStreamTimeout 函数体内不得出现 new AbortController
(fail) 换 controller 只发生在 attempt 边界（resetStreamTimeout），且它仍然存在
```

静态哨兵是刻意加的：变异 B 的行为失败形态是**hang 到用例超时**，在 CI 上表现为一条
慢测试，容易被误判成 flake 而加 `--timeout` 绕过。静态哨兵失败时消息明确、零耗时。

**负向对照全部保留**：真僵死流（先有进展后僵死）与零进展流仍被正常回收并转 fallback ——
「防线必须真被触发过」这条铁律没有被本次改动拆掉。

门禁（在 worktree 内，已先跑 `bun install`；rebase 到 `85db0cd0` 后重跑）：

```

bun run lint           ✓ 0 问题
```

### 一条排查留痕：两次超时类失败被证伪为机器竞争，不是本改动

排查期间遇到两条超时类失败，**都没有停在"重跑绿了就是 flake"**，按仓库铁律
「判定与我无关必须举证」逐条核过：

**失败一**：选测里 `resilience-b6-gates.test.ts` 的 S3 用例（`elapsed` 184508ms，
期望 < 5400ms），当次全套 200.85s。

1. **同一命令在干净 `origin/main` worktree 上**：15.12s / 0 fail（我的分支同套 200.85s，
   13× 差距 —— 这个量级本身就说明不是某一条测试的逻辑问题）。
2. **只留源码改动、移走我的新测试文件**：15.17s / 0 fail —— 源码改动单独是干净的。
3. **决定性证据 —— 加探针直接数调用次数**：S3 那条流只 yield `error` 事件，
   实测 `renewStreamTimeout` 调用 **0 次**，即**我的新代码路径在那个测试里根本不执行**。
   （探针测完立即还原，`grep -c` 确认 0 处残留。）
4. 机器侧：`uptime` 负载 35.63（10 核），另有一个 `claude` 进程在跑。
5. 机器安静后连跑 6 次全绿（16.5~16.7s）。

**失败二**：全量里 `loop-watchdog.test.ts` 的 T1（`this test timed out after 15000ms`，
实际耗时 66666ms）。它**确实 import 了 `llm/fallback.ts`**，所以第①条证据不成立，
不能按"零引用"打发。改用另外两条：

- **数字对不对得上**：该用例的 watchdog 阈值被 env 压到 **60ms**，设计上百毫秒内就该
  fire，实际却跑了 66666ms —— **1000× 量级**。这是事件循环被饿死的形态，
  不是判定逻辑错（逻辑错会 fire 得太早或不 fire，不会 fire 得晚 1000 倍）。
  对齐 [[timeout-layers-same-value-swap-killers]] 一类判读：**先看数字对不对得上**。
- **同 base 对照**：rebase 到 `85db0cd0` 后全量 **10175 pass / 0 fail**，
  而同 base 干净 worktree 是 **10170 pass / 0 fail** —— 差值 5 正好是本 PR 新增用例数。

两次都发生在本机同时跑多路任务时（用户已说明另有一个 CC 实例在改代码）。
**成因是环境竞争，不是主干坏了** —— 所以刻意不叫它"既存失败"
（对齐 [[worktree-cwd-breaks-permission-tests]] 的双证据要求：那个词意味着主干本来就坏，
会让人跳过本该排查的东西）。
