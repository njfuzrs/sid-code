# read 体量上限 + glob 路径基准 + 路径纠错验证 + 语言裁决段文案

来源会话 `20261018-224823-dbc19982`（MiniMax-M3，41 轮）的三个现象：read 连续报「文件不存在」、
模型每轮回执「保持中文输出」（TUI 里出现 34 次）、上下文占用 18%。

## 决定了什么

1. **read 输出体量上限**（`tool/read.ts`）
   - 单次输出估算超过 25000 token（`estimateTextTokens`，与上下文估算同口径）→ **报错不截断**，
     报错里按本段平均密度给出建议 `limit`。对标 CC `FileReadTool/limits.ts`：CC 注释记录过截断方案
     实测平均 token 更高（截断塞满 25k，报错只有约 100 字节）。`SID_READ_MAX_OUTPUT_TOKENS` 可覆盖。
   - 单行超过 2000 字符截断显示并标注；有截断时记为部分视图。没有这条，「单行就超限」的文件
     （本次的 `builtin-embedded.generated.ts` 单行 4.2 万字符）在 `limit=1` 时也读不进来，报错成死胡同。
   - 「可不传 limit 一次整读」提示改为同时看行数和体量，不再在 199 行 / 234KB 的文件上鼓励整读。
2. **glob 输出路径相对 cwd**（`tool/glob.ts`）：旧版相对搜索根，`glob(path="packages")` 返回
   `cli/src/ui/X.tsx`，模型拼回时拼错。改为相对 cwd，跳出 cwd 时给绝对路径（对标 CC `toRelativePath`）。
3. **路径纠错建议先验证再给**（`tool/path-utils.ts`）：段级模糊匹配只纠正第一个缺失段，其余段原样拼回，
   拼出的路径未必存在。现在拼出的路径存在才报「可尝试完整路径」，否则只报段级候选并建议 glob。
   本次 `packages/ui/...` 被建议成不存在的 `packages/tui/components/...`。
4. **语言裁决段改为静态配置陈述**（`config/system-prompt.ts`）：注入条件不变；去掉「用户已通过 /language
   **显式**设置」的事件口吻和「一个字都不打折」等重复强调，加「这是会话静态配置，不要确认、复述或回应」；
   en 档整段改英文正文。

## 放弃了什么（以及为什么不选）

见 `rejected/bug-fix/2026-10-19-语言裁决段按冲突条件注入与read截断式上限.md`。要点：
- 语言段按「是否冲突」决定注入：要么正则猜 CLAUDE.md 语言（脆），要么只在 en/auto 注入
  （漏掉「英文 CLAUDE.md + 显式 zh」，把 P0-4 反向重开）。
- read 超限截断而非报错：CC 实测平均 token 更高。
- read 上限按模型窗口缩放：1M 窗口模型正是本次一次吞 4.8 万 token 的那个。
- 文件不存在时全仓按文件名搜索：错误路径起 rg 子进程，大 cwd 下慢，且要再接一遍 deny 规则防泄露；CC 也不做。
- 按模型名对 MiniMax 特殊处理：违反「不按模型硬编码分级」。

## 拿什么证明它生效了

**基线**（本机 189 个会话、2059 次 read，脚本扫 `raw.jsonl`）：read 结果 token p50≈620、p95≈3.5k、
p99≈10.6k、p99.9≈48k；>25k 仅 7 次，其中 3 次就是 `builtin-embedded.generated.ts`。阈值只拦尾部。
复读短语：MiniMax-M3 在注入裁决段的会话里 23/37 段回复命中，其余 9 个模型（含 deepseek 1579 段、
claude 574 段）均为 0。

**read 端到端**（同一文件，改前在 main / 改后在本分支，直接调 ReadTool）：
- 不传参整读：180,589 → 70,013 字符（29 行超长行截断）。
- 本次会话的 `offset=28, limit=240`：179,720 → 69,144 字符。

**变异自证**（逐个改坏 → 对应用例变红 → 恢复）：token 上限置 1e12（2 红）、行上限置 1e9（1 红）、
整读提示去掉体量判断（1 红）、纠错跳过存在性验证（1 红）、glob 回退相对搜索根（2 红）、
语言段恢复事件口吻（1 红）。

**语言段 A/B 重放**（取本会话录制的真实请求，只替换 `<language-precedence>` 段，经公司网关打 MiniMax-M3）：
- 删掉历史里已有回执、看模型是否「自发」复读（5 个轮次 × 6 次）：旧 zh 复读 1/11，新 zh 0/5；
  en 档英文回复 旧 5/9 → 新 6/9，**无退步**（P0-4 的 en 覆盖仍成立）。
- 保留原历史（已有 20+ 段回执在上下文里）：新旧都约 50% 复读（旧 10/19、新 11/18），**无差异**。
- 结论要说清楚：一旦历史里有了回执，模型主要在模仿自己的历史，改文案压不下去；新文案能起作用的只有
  「首次是否触发」这一段，而这一段的样本里复读本就稀少，**当前数据不足以证明新文案降低了复读率**。
  保留这项改动的理由是：它不改注入条件、en 档无退步、事件口吻与复读文本逐字同源，属于去掉诱因。
  有效与否要靠合入后新会话里的复读率（同一脚本的复读短语统计）来判。
