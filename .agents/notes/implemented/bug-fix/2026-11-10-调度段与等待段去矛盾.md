# 「等 CI」只映射到等待原语：scheduling 段收敛为定期复查

## 决定了什么

`<scheduling-capability>` 与 `<waiting-capability>` 原先对**同一意图**给出两套工具：
前者写「自适应轮询（『跑到 CI 过为止』『等部署好了告诉我』）→ `schedule_wakeup` 轮询」，
后者（#722 新增）写「CI 全绿了告诉我 → 后台 bash + `wait_until_seconds` / monitor」。
会话 `20261109-160803-fbb02831` 的 `tool_search` 只激活了 `schedule_wakeup,cron_create`，
monitor 从未进入候选，随后排了唤醒又在前台轮询，第二个唤醒晚 383 秒才注入。

本次把边界划死：

- `buildSchedulingSection`（`packages/core/src/config/system-prompt.ts`）只覆盖**没有可流式
  观测对象**的时间意图：一次性提醒 / 固定间隔 / 定时复查。删掉「跑到 CI 过为止」
  「等部署好了告诉我」两个条件式等待例句；开头总述的「跑到某条件满足为止」同步改成
  「定期复查」，避免总述继续暗示轮询。
- 新增一条「**等外部状态**」让出句，按 monitor 是否注册二选一渲染：
  - monitor 已注册 → 指向 `<waiting-capability>`（后台 bash + `wait_until_seconds`，或 monitor）；
  - monitor 未注册（企业策略关闭 / 精简模式）→ 直接给后台 bash + `run_in_background=true` +
    `wait_until_seconds` 兜底。这条兜底是必需的：waiting 段此时根本不注入，让出句指向它
    等于指向一个不存在的段落。
- 「一次性提醒」的例句从「3 点提醒我看部署」「45 分钟后检查 CI」换成不含外部状态关键词的
  例子（开会 / 复查）。定时映射的可发现性由「3 点」「45 分钟后」这些时间标志承载，
  不依赖 CI 这个词——换掉之后 `<scheduling-capability>` 里出现 CI / 部署 的行只有让出句，
  门禁才能机械判定。
- 英文段（`prompt-sections-en.ts` 的 `buildSchedulingSectionEn`）同步改，两个函数的签名
  都加 `monitorAvailable`；唯一调用点按 `ctx.tools` 里有没有 `monitor` 传入。
- 新增门禁 `packages/core/tests/config/scheduling-waiting-no-contradiction.test.ts`：
  中 / 英 × monitor 注册 / 未注册 = 4 组，每组 3 条（旧例句不许回来、含 CI/部署 的行只能是
  让出句且出口真实存在、含 `schedule_wakeup` 的行不得同时含外部状态关键词）。

## 放弃了什么（以及为什么不选）

- **只改中文、不改英文**：不选。`preferredLanguage=en` 是同一份提示词的另一路，只修中文
  等于一半会话仍拿到互斥指令；门禁也无法覆盖英文。
- **让出句统一写死指向 `<waiting-capability>`，不做注册状态分支**：不选。monitor 未注册时
  该段不注入（`waiting-capability-policy.test.ts` 锁着这个行为），写死会让模型去找一个
  不存在的段落名，比原来的矛盾更难归因。
- **保留「3 点提醒我看部署」「45 分钟后检查 CI」两个例句**：不选。这两条本身是**正确**的
  定时映射（用户给了明确时刻），但留着它们，「CI / 部署」在 scheduling 段就出现在两处，
  门禁只能退化成按行白名单而无法机械断言「只出现在让出句」。权衡后换例句——损失的
  具体性由让出句里的「CI 全绿了告诉我」补回。
- **把 N2（`schedule_wakeup` 返回文案）、N4（静默通知）一起塞进本 PR**：不选。方案 §四 把
  N1/N2/N4 合为 PR-B，但本次只要求 N1；N4 的验收要 65 秒以上的真实入口慢测，捆进 P0 的
  提示词改动会拖慢它合入。三条的验证成本不同，按「上线时机」拆开。
- **对唤醒轮询加运行时拦截**：不选。那是 N3/N8 的职责（命令匹配 + 无声明等待引导），
  本 PR 只改模型可见的措辞，不新增任何拦截路径。

**变异自证**（先改坏、看它报什么、再恢复）：把中英文的「定时复查」改回
「自适应轮询（跑到 CI 过为止 / keep going until CI is green）」后重跑同一命令，

```text

Expected: true  Received: false                  ← 含 CI 的行不以让出句开头
```

恢复后 12/12 绿。**第二轮变异**（验证门禁自身的切片没有恒绿）：把
`if (monitorTool)` 临时改成 `if (monitorTool && false)`（waiting 段不注入）→
zh / en「monitor 已注册」两组各 1 条红，报 `Received: null`（按行首匹配找不到
`^<waiting-capability>$` 段落）；恢复后 12/12 绿。

> 这轮变异是为了补一个**自己写测试时踩到的坑**：monitor 注册时 scheduling 段的让出句里
> 有 `<waiting-capability>` 字面量（行内），第一版 `sectionOf` 用裸 `indexOf` 会把 waiting
> 段的切片起点落到 scheduling 段中间，于是「waiting 段含 `wait_until_seconds`」这条断言
> 被 scheduling 段自己的文本满足掉——一条恒绿的假门禁。改成按行首匹配段落标签，并加
> 「waiting 段导语」锚点断言后才真正生效。
