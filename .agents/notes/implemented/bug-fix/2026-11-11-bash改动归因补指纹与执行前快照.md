# bash 改动归因：补内容指纹 + 执行前快照，把「本命令改的」和「命令前就被外部改的」分开

## 决定了什么

CG-4 修的是 H5 的两半根因，**都保留归因、不取消归因**（§2.3 的裁决）：

1. **部分读取也存内容指纹**（`file-read-tracker.ts`）。
   改造前 `markAsRead` 对部分读取（`offset/limit` 分段、超行数截断）只记 `content = null`，
   `noteBashExecution` 的比对于是只剩 mtime 一条路——`touch`、formatter 重写、云同步、IDE 保存
   都会动 mtime 而不改内容，一律被报成「本命令修改了它」。
   新增 `contentFingerprint()`（sha256 前 16 位）与 `ReadRecord.contentHash`：
   **完整读取与部分读取都存指纹**，`contentDiffers()` 统一先比指纹、`content` 只作老记录兜底。
   指纹**只存哈希不存全文**——部分读取的文件可能是超大文件，常驻全文不划算。
   口径必须基于**磁盘原始内容（含 BOM）**：拿 read 工具剥离 BOM 后的文本算，
   带 BOM 的文件会永远判"变了"。`read.ts` / `read-many.ts` 因此主动传 `contentHash`
   （手里就有原始 `content`），`markAsRead` 只在没传时才自己读一遍磁盘兜底。

2. **执行前快照**（`beginBashExecution` / `noteBashExecution(snapshot)`）。
   改造前归因基准是「读取那一刻」的 mtime，于是**读取之后、命令之前**的外部改动被算到这条
   命令头上——现场形态是模型跑一条 `cat`/`grep` 却被告知「你刚改了这些文件」，
   于是去重新 read、甚至回滚一个不存在的改动。
   现在 `BashTool.execute()` 在调用 `executeCommand` **之前**拍快照（跳过条件与
   `withTrackedFileChanges` 逐条对齐：无 tracker / 后台 / 只读命令都不拍），
   `noteBashExecution` 只把「执行前还是 mtime A、执行后变了」的算本命令改动。

3. **两类文案**（`trackedFilesChangedNotice`）。
   `BashChangedFile` 新增 `attribution: "command" | "external"`，通知分成两段：
   - `[已读文件被本命令修改]` —— 原文案 + 归因说明（命令运行期间其他进程同时改也会列在这里）；
   - `[已读文件在本次命令前已被外部修改]` —— 新增，明确「不是这条命令改的」。
   `beginBashExecution` 拍快照时就已经变了的文件会被**当场吸收**（刷新快照 + `changedByBash`）
   并归 `external`，所以同一处改动不会被重复告知，随后的 edit 也不会被误拦。

4. **埋点**（`file_freshness` 的 `bash_changed_tracked_files`）：
   `files_changed` / `files_deleted` 改为只统计 `command` 归因，新增 `files_external`。
   改造前外部改动混在 `files_changed` 里，看不出「误归因还剩多少」。

## 放弃了什么（以及为什么不选）

- **不改成「只说变了、不说谁改的」**（附件 A §13.4 的上游做法）。否决理由同 02 与附件 B §7.7：
  这个提示来自 2026-10-10 的轨迹证据（agent 自己格式化完文件，下一次 edit 被误判成外部修改），
  上游没有它是没有这层 edit 拦截，不能当反证。去掉归因等于把保护面换成一个更弱的版本。
- **不做 fs.watch / 每写一次文件就记一次**。要把「命令执行期间其他进程也改了」这个窗口也消掉，
  只能在写盘路径上埋监听；成本远超收益，且会让 tracker 从「读时快照」变成「持续监听」，
  内存与可靠性都变差。这个窗口**用文案兜底**（「命令运行期间若有其他进程同时改了同一文件，
  也会列在这里」），验收也不定 0（§2.3：判据是「模型质疑数下降一半以上」）。
- **不把快照拍在 `executeCommand` 内部紧邻 spawn 处**。那里有十几个提前 return
  （缺参数 / cwd 不存在 / 取消 / 转后台…），逐个补快照必然漏。代价是首条命令
  `await snapshotReady` 的等待窗口会被算进「执行前」——但那时模型还没读过文件，
  tracker 是空的，无影响。后续命令该 Promise 已 resolve，窗口是微任务级。
- **不给快照加「只扫最近 N 个文件」的截断**。截断会让「较早读过、这次命令改了它」的文件
  静默不报，比多花几毫秒糟糕得多（见下面的实测：500 个文件也只有 15ms）。

## 拿什么证明它生效了

worktree `fix/cg4-bash-attribution`（基于 `492fcc86`）实测：

- **单测 23 pass / 0 fail**：`packages/core/tests/tool/bash-tracked-file-refresh.test.ts`
  （原有 12 条全绿 + 新增 6 条 CG-4 用例 + 2 条文案分段用例）。
  新增用例覆盖：部分读取后 `touch` 不报变更、部分读取后真改仍要报、读取后外部改动归 `external`、
  两类同时出现时分开列出、外部归因也刷快照（随后 edit 不被误拦）、埋点 `files_external` 计数。
- **变异自证 2 轮**（每轮恢复后复跑 23 pass / 0 fail）：
  - `contentHash` 恒 null → 「部分读取后 touch 不报变更」红（22 pass / 1 fail）；
  - `beginBashTracking` 恒返回 undefined → 3 条外部归因用例红（20 pass / 3 fail）：
    外部归因、两类分开列出、`files_external` 计数。
- **stat 耗时实测**（后续规划 §7 的未核实项，`/tmp/cg4-stat-bench.ts`，rounds=20）：
  | 已读文件数 | p50 | p95 | 单文件 |
  | --- | --- | --- | --- |
  | 10 | 0.34ms | 0.67ms | 34µs |
  | 100 | 4.87ms | 5.65ms | 49µs |
  | 200 | 5.68ms | 8.67ms | 28µs |
  | 500 | 14.90ms | 17.01ms | 30µs |
  空 tracker 1000 次合计 0.07ms（纯调用开销可忽略）。
  结论：**增量 = 一次全量 stat 扫描**（改造前命令后扫一遍，现在前后各一遍），
  100 文件约 5ms、500 文件约 15ms，相对一次 bash spawn + 执行（数十 ms 起）可接受。
- `bun run typecheck:gate` → 无新增类型错误（62 处 / 基线 64）。
  ⚠️ worktree 里改前先看到一批假阳性（`packages/tui` TS2307、`core/tests/skill` 的
  `UnifiedCommand` 名义类型冲突），成因是根 `node_modules` 软链到主仓导致的模块解析分裂；
  按 CLAUDE.md 的处置把软链移开后 `bun install`，复跑即 exit 0。**没有放宽基线**。
