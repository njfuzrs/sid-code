# MCP 项目级审批绑定配置内容指纹

## 决定了什么

`packages/core/src/mcp/approval.ts` 的批准键原来只有 `<项目路径>:<server 名>`。`.mcp.json` 随仓库分发，同名 server 的 `command` / `args` 被人改掉（恶意 PR、被投毒的依赖仓库）后，重启会沿用旧批准、无提示执行新命令。同仓的 `extension/trust.ts` 早就按 SHA-256 内容 hash 记信任，两套机制不一致。

改动：

- 批准键改为 `<项目路径>:<server 名>#sha256:<指纹>`，指纹 = 对配置做键排序稳定序列化后的 SHA-256；
- `getProjectServerApproval` / `approveProjectServer` 新增 `config` 参数，调用方（`config.ts` 加载侧、`mcp-cli.ts` approve、待审批快照批准）都传当前声明的配置；
- 指纹排除 `enabled`（开关不改变会执行什么）；`${VAR}` 按原文算（批准的是仓库里写的文本，换 token 不应重新审批）；
- 重新批准时清掉同名 server 的全部旧指纹记录，防「改回旧内容被静默放行」；
- 拒绝仍按名字记，内容变了也仍是拒绝（fail-closed）；「按项目全部批准」是显式授权，不受指纹约束；
- 升级前的无指纹记录一律不认，回到待审批（用户选择的方案）。

同 PR 修官网两处文档：`extend/workflows.md` 把「缓存命中但结果不一致」改为「fingerprint 变化、永远不命中缓存」，与 `journal.ts` 的 `computeFingerprint` 和 `extend/index.md` 一致；`extend/mcp.md` 模板把 `tavily-mcp@latest` 锁为具体版本，补充 `@latest` 绕过审批指纹的说明，并更新审批记账描述。

## 放弃了什么（以及为什么不选）

- **旧记录首次加载时补指纹（TOFU）**：不打扰用户，但升级前如果内容已被篡改，会把篡改后的版本直接认定为可信。用户选择安全优先，旧记录全部失效。
- **指纹算展开后的配置**：会把用户自己的环境变量值卷进去，换 token 就要重新审批；而且展开值不是仓库作者能控制的东西，绑定它对防篡改没有帮助。
- **拒绝也绑指纹**：内容一变，拒绝就自动解除，等于给攻击者一条「改一个字节就能重新弹框诱导批准」的路。
- **对 `npx pkg@latest` 解析实际版本再算指纹**：要在审批阶段联网解析 registry，违反「未批准不出网」，复杂度也不成比例。改为在文档里明确推荐锁版本。

## 拿什么证明它生效了

- 新增 `packages/core/tests/mcp/approval-fingerprint.test.ts`（10 例）：command / args / url / headers / env 被改都回到 pending；改回旧内容要重新审批；键顺序与 `enabled` 不影响；approveAll 不受约束；无指纹旧记录失效并在重新批准时清除；拒绝不随内容解除；待审批快照批准用快照配置。
- 变异自证 4 组，全部变红后还原（`cmp` 确认文件一致）：只比对名字（6 fail）、不清旧指纹（1 fail）、指纹不排除 enabled（1 fail）、认无指纹旧记录（1 fail）。
- 既有 4 个测试文件（approval-corrupt / mcp-subitems-d12-d17 / oauth-elicitation-b3 / project-files-disable）按新签名与新键格式修正前提，5 个文件 50 pass / 0 fail。
