# 测试与生成器起的 bun 子进程写真实家目录：Bun 不继承运行时 env

## 决定了什么

**现象**：#240 的验证过程中，真实 `~/.sid-code/app.json` 里的 `numStartups` 涨了 2，迁移 v7 也在维护者不知情的情况下对真实配置跑了一遍。

**根因**：`Bun.spawn` / `Bun.spawnSync` 不传 `env` 时，子进程拿到的是**进程启动那一刻**的环境，运行时改过的 `process.env` 不会传下去。
实测 `process.env.X = "v"` 之后，`Bun.spawnSync(["sh","-c","echo $X"])` 输出 unset；node 的 `child_process` 则会继承。
`tests/preload-isolate-sid-home.ts` 是在运行时设置 `SID_CONFIG_DIR` 的，所以不传 env 的 bun 子进程等于没有被隔离。
子进程跑的是一次完整启动（迁移、启动计数、启动管家都会执行），结果直接写进了真实家目录。

**泄漏点**（用伪 HOME 全量跑 `bun test` 定位，结果是伪 `~/.sid-code` 被写入、numStartups=2，另外还写了 VS Code keybindings）：
1. `scripts/docs-gen-reference.ts` 的 `--dump-tools` 子进程。pre-commit 每次提交都会跑它，是触发最频繁的一处。改为给它一个临时 `SID_CONFIG_DIR`，跑完删掉；隔离前后输出都是 44 个工具，没有差异。
2. `tests/website/gen-reference.test.ts` 里 5 处直接起 `--dump-tools` 和生成器的调用，补上 `env: { ...process.env }`。
3. `packages/cli/tests/command/terminal-setup.test.ts`：在 mac 上先调用写入函数、再判断平台，每跑一次就往真实的 `~/Library/Application Support/Code/User/keybindings.json` 写一条 shift+enter。改为在 darwin/win32 上 `skipIf`，完全不进入写入路径。
4. 另外 6 处起 bun 子进程但没传 env 的调用（apply-migration、bridge-ready-url、contracts-runtime、artifact-identity、harbor-agent-contract、compile-smoke、build-info-channels）。这些目前没有观察到写家目录，按同一规则统一补上。

**门禁**：`tests/build/test-isolation-preload-wiring.test.ts` 新增「子进程 env 门禁」。测试源码里，只要调用起的是 bun（参数里有 `"bun"` 或 `process.execPath`），就必须带 `env`。附带变异自证用例。

## 放弃了什么（以及为什么不选）

- **在 preload 里给 `Bun.spawn` 打补丁，自动注入 env**：试过，`Bun.spawn` 是不可配置属性，`defineProperty` 会抛 TypeError，做不到。
- **只修 docs 生成器**：测试里同样的写法还有 10 处，靠人记住要传 env 防不住，所以需要静态门禁。
- **在 mac 上把 terminal-setup 的写入路径改成可重定向（加 env 覆盖）**：那等于为了测试去改产品代码。目前 linux 分支已经覆盖了写入和幂等的断言，mac 上跳过就够了。

## 拿什么证明它生效了

- `HOME=<临时目录> bun test` 全量跑：修复前伪 `~/.sid-code` 里有 app.json（numStartups=2）、迁移水位，还有 VS Code keybindings；修复后的结果见 PR 描述。
- `bun run docs:gen-reference-check` 前后，真实 numStartups 都是 5439，没有变化。
- 门禁变异自证：违规写法会被抓到，`env` 简写和非 bun 子进程不会误报。
