# MCP 状态文件损坏后不再被静默覆盖：告警 + 写前备份原文件

## 决定了什么

`mcp-approvals.json`（项目级 `.mcp.json` 审批记录）与 `mcp-state.json`（按项目的
禁用 / 启用名单）共用同一种缺陷形态：读取时解析失败 → 静默返回空 store / 空对象 →
紧接着的任何一次写入（approve / reject / setApproveAll / setMcpServerDisabled）
都把这份空内容**整体重写回原文件**，用户全部项目的历史审批 / 拒绝 / 禁用记录
被一份几乎为空的文件覆盖，且没有任何日志。

改法是两条，分别落在 `packages/core/src/mcp/approval.ts` 与
`packages/core/src/mcp/project-files.ts`：

1. **读侧**：区分「文件不存在」与「文件损坏」。不存在 = 正常首次使用，静默返回空
   （不告警、不备份）；损坏 = 顶层不是对象或 JSON 解析失败，`getLogger().warn("MCP", …)`
   一条（消息含文件路径与备份去向），**读取结果仍返回空**——空 ⇒ 所有项目级 server 回到
   `pending` ⇒ 重新询问用户，这是 fail-safe 的方向，不是 fail-open。
2. **写侧**：用模块级 `corruptPending` 把「损坏」这一事实从读传到写；写入前若该文件
   正是本次读到的损坏件，先 `renameSync` 成 `<path>.corrupt-<Date.now()>` 再写新文件。
   每个损坏文件只备份一次（写完即清标记）。`project-files.ts` 额外多一道判据：
   只有 `readPath === primary` 才备份——读取路径回退到旧键（worktree 自己那份）而写入
   目标是主仓根那份时，本次写入不会覆盖损坏文件，挪走它反而丢了用户可手动抢救的原件。

行为兼容性：`getProjectServerApproval` 等对外函数签名不变；损坏时的**返回值**不变
（仍是空 / pending），新增的只有日志与备份文件。

## 放弃了什么（以及为什么不选）

- **改成 fail-closed（检测到损坏就拒绝启动 / 拒绝写入）**——过度反应。一个损坏的
  审批文件不该让 CLI 起不来，也不该挡住用户重新审批；这类文件本来就是可重建的缓存物，
  正确姿态是「继续可用 + 留下证据 + 不毁掉原件」，不是拒绝服务。
- **只加日志不备份**——日志会滚动掉。`debug.log` 有 10MB 轮转、审计模式还有独立的
  `audit.log`；一旦轮转，原始字节就再也找不回来了。数据还在磁盘上是「可抢救」与
  「永久丢失」的分界，备份文件是唯一把它留住的载体。
- **写入时把旧内容合并进新内容**——旧内容本来就解析不出来（JSON 无效 / 顶层不是对象），
  没有东西可合并。能做的只有「先留住原始字节，再写新内容」。
- **在读的时候立即备份（而不是写前）**——读发生在每次启动的状态查询路径上
  （`getProjectServerApproval` 被多次调用），读时备份会让「只是看一眼」的调用也产生
  `.corrupt-*` 文件，且每次进程重启都多一份。备份时机放在「即将覆盖」的那一刻，
  副作用最小且语义最准：**备份的唯一目的是防止被覆盖。**

## 拿什么证明它生效了

新增两个测试文件，共 13 个用例，全部通过（`bun test` 输出 `13 pass / 0 fail`）：

- `packages/core/tests/mcp/approval-corrupt.test.ts`（6 例）
- `packages/core/tests/mcp/project-state-corrupt.test.ts`（7 例）

覆盖的关键断言：损坏读出 pending / 空名单；`approve` / `setMcpServerDisabled` 之后
备份文件存在且**与原内容逐字节相同**；新文件是合法 JSON 且含本次记录；同一损坏文件
只备份一次；文件不存在时不产生备份；告警消息含文件路径；linked worktree 下
`readPath !== primary` 时不备份且不覆盖。

**变异自证（真做过，不是"机理上讲得通"）**：临时删掉 `saveApprovals` /
`setMcpServerDisabled` 里的备份逻辑后重跑——

- C1：`4 pass / 2 fail`（红的是「approve 前先备份」与「同一个损坏文件只备份一次」）
- C2：`5 pass / 2 fail`
- 恢复后重跑：`13 pass / 0 fail`

门禁：`bun run affected-tests:run` → 227 pass / 0 fail（含 mcp 目录全部既有测试）；
`make build` → rc=0 且 `grep "will always be undefined"` 计数为 0；
`bun run lint` 0 warning / 0 error；`bun run format:check` 通过；`bun run lint:boundary` 0 越界。
