# 超时埋点字段归一 + 隐身层留痕 + per-model 覆盖替代全局抬阈值，并拆掉最后一对同谓词伪阶梯

## 决定了什么

方案 `20260817-GLM-5.3思考阶段卡死-300s硬顶掐断丢弃已累积内容-修复方案.md` 的
**PR11（P1-5）/ PR12（P1-9）/ PR13（P1-8）/ PR14（§5.A 取值）** 四条合成一个单元。
**PR15 未做，判为不该做**，理由见下面「放弃了什么」。

合成的理由：它们回答同一个问题 —— **上一轮为什么会把方向判错，以及怎么让下一轮判得对**。
PR11 补上"哪一层开的枪"，PR12/PR14 修掉"两层同谓词分不出谁开的枪"，
PR13 钉住"不该开枪时它不开枪"。拆开做的话 PR14 的验收需要 PR11 的层标识才成立，
PR13 的对照用例需要 PR12 的机制才写得出来。

### PR11：埋点（`trace/stream-observer.ts` / `llm/openai.ts` / `trace/collector.ts`）

**① 快照新鲜度（§4.2）。** 新增 `statsUpdatedAt` + `snapshotStaleness()`。
这是上一轮排查绕最大一个圈的成因：`chunksReceived: 0` 看起来是权威实时状态，
实际是一份几分钟没人更新的陈旧快照，而**两种情况的观测结果完全相同**：

| 场景 | lastContentProgressAt | statsUpdatedAt |
| --- | --- | --- |
| 流真卡死（写入方还在 tick） | 停住 | 持续前进 |
| **写入方自己没在写**（真实缺陷） | 停住 | 同样停住 |

要害是**无条件刷新**：即使所有计数字段都因单调取大而没变，也要刷。
只在数字变化时刷新就退回"陈旧与无进展分不开"的老问题。两个写入方
（`updateStreamStats` 字节级 / `recordStreamProgress` 事件级）都刷，
快照年龄才等于"最近一次有人写"。

**② chunk 字段归一（§4.3）。** 同一语义此前四个名字散在四类事件里
（`totalEvents` / `chunks` / `total_chunks` / `chunks_received`），无法跨事件 group by。
做法是**加规范名 `chunk_count` + 老字段原样保留**，而不是重命名四处 ——
重命名会让本机 50 个会话的历史轨迹在新读取方眼里全变 0，而 0 满足一切健康检查
（memory `instrument-only-records-hit-not-write` 记的正是这个失效形态）。
`chunk_count` 必须与 `chunk_count_kind` 成对：三套计数口径**没有**被统一
（事件数 ≤ chunk 数），只带数字不带口径会把两个口径混着平均。

**③ 隐身层留痕（§4.5，本 PR 最要紧的一项）。** 两层防线开枪不留痕，导致
`Counter({'fallback_stream_timeout': 24})` 看似铁证"100% 是这一层触发"，
实则**结构性地只能看到三个闸门中的一个**：
- watchdog 只发 `WatchdogKill`，且往快照里 push `turn_hard_timeout` **冒充档③** →
  新增 `watchdog_kill` 层并补发 `TimeoutFired`。混名的害处是"档③开枪了几次"永远算不对，
  而那正是判断"新阶梯有没有被架空"的关键数；`fallback.ts` 的 `reopenReason` 读的也是
  这个数组的末元素，混名会让重开归因指向一个它没碰过的闸门。
- `fetchAbsoluteTimeoutMs` 把 deadline 委托给 runtime（`AbortSignal.timeout`），
  runtime 的 abort 不带 reason、不经本模块 → 新增 `makeFetchAbsoluteTimeoutSignal()`，
  **只挂监听器、不改计时机制**。刻意不换成 `setTimeout` + 自建 controller：
  那会把它从"runtime 计时"改成"事件循环计时"，而本仓实测过事件循环被半开 TCP 占满时
  `setTimeout` 迟到到 899s —— 这一层的唯一价值恰恰是它不依赖事件循环。

  ⚠️ **它必须返回 disarm 并在流结束时调用**，这一点我第一版漏了、审查时抓到：
  `AbortSignal.timeout(ms)` 到点**一定**会 abort，与 fetch 是否早已成功结束无关
  （signal 不知道自己已经没人用了）。不 disarm 的话，一条 20s 读完的流会在第 1800s
  落一条 `fetch_absolute_timeout` —— **一个从未发生过的超时**。
  这比"没有留痕"更糟：没留痕只是缺数据，假事件让"这一层开了几枪"变成纯噪声，
  且噪声量**正比于成功请求数**（越健康的部署数据越脏）。
  为此把 openai.ts 两条流式路径各加了一个外层 `finally`
  （原来两条路径都没有覆盖整个流生命周期的 finally），并加哨兵断言 disarm 出现 2 次。

**④ stall 分档（§4.7）。** 实测 `StreamStall=1` 而 `WatchdogKill=23`：
23 次长无进展只留 1 条记录（一个 `stallEmitted` 布尔，首次越线后永不再发）。
改为**每流每档位各一次**（30s / 120s / 300s）+ 流结束补一条 `summary` 汇总。
"避免 events.jsonl 膨胀"这个原取向是对的（30s tick 无脑发，卡 10 分钟就是 20 条），
分档后上界固定、且每条对应一个量级不同的事实。汇总条与档位条**互斥**
（`summary` vs `tier_ms`），聚合时必须排除汇总，否则同一次 stall 数两次。

### PR12：per-model 流式超时覆盖（`config/network-profile.ts` / `config/config.ts`）

新增 `ModelConfig.streamTimeouts`（三项：idle / contentProgress / overall）。
**慢是模型的属性，不是全局属性** —— 实测 50 会话 1370 条成功流，最长无进展间隔
只落在两个模型上（glm-5.3 **284.5s**、origin-deepseek-v4-pro **293.1s**），
其余模型 p95 仅 83.7s。全局抬阈值会让**所有**模型的真僵死回收一起变慢。

四条实现决定：
- **不塞进 `ModelCompat`**：那是纯布尔位，`normalizeModelCompat` 明文只接受真布尔
  （字符串一律丢弃）。塞 number 会破掉那条不变量，归一化/校验/别名/跨进程播种四处都要开特例。
- **按渠道别名（name）键**，同 `compat` / `supportsThinking` 的口径：同一真名接官方端点与
  公司网关时，慢的往往是网关那条（排队 + 缓冲），按真名键会把两条渠道一起放宽。
- **只开三项**：`fetchAbsoluteTimeoutMs` 不开（已默认关闭且谓词与档③重合，给应当关掉的层
  加旋钮等于续命）；`maxTurnDurationMs` 不开（整轮硬顶跨模型跨 fallback，
  "这一轮属于哪个模型"没有唯一答案）。
- **注册点选在 `resolveCurrentModelConfig`**，与 `setModelCompat` / `setWireModelAliases`
  逐条同理：它是启动解析与 `/model` 运行时切换的共同咽喉，且两条 early-return 前必须先清空
  （残留会让新配置按旧阈值跑且不报错）。

**优先级链最终定为：调用方 options > env > per-model > settings.network > 默认。**
⚠️ 我第一版把 per-model 排在 `settings.network` **之后**，理由是"用户的全局声明不该被
模型级建议否决"。那是错的：per-model 同样是用户写在同一个 settings.json 里的显式声明，
而且排在全局之后会让它**几乎永不生效**（用户只要碰过一次全局 `idleTimeoutMs`，
模型级覆盖就彻底失效且不报错）——等于把这一层做成死配置。
**这个错误是 PR13 那条对照用例抓出来的，不是想出来的**（见「拿什么证明」）。
env 保留为唯一例外（一次性注入，多个现存测试依赖"临时压到毫秒级"）。

### PR14：拆掉最后一对同谓词伪阶梯（`config/network-profile.ts` / `cli/app.ts` / `llm/fallback.ts`）

**PR10 收敛三档时漏掉了一对**：`app.ts` 把 `watchdogNoProgressMs` 同时注入 fallback 的
`streamTimeoutMs`，`fallback.ts` 的兜底常量也 `= NETWORK_DEFAULTS.watchdogNoProgressMs`。
于是这两层**同值 720s 且同谓词**（PR2 之后 fallback 那层也读内容进展）——
正是 PR10 判定为"病"的形态。代价已实测过一次：两层几乎同时开枪，
先到的背全部锅，而"先到"只是 70ms 的偶然。

新增独立字段 `fallbackStreamTimeoutMs = 600s`，落在档② 480s 与 watchdog 720s 之间。
兜底常量同批改掉（只改注入点会让 `new ModelFallback()` 路径仍是旧形态，
那是回归最容易漏的地方）。

**取值不是拍的，也不是照抄 §5.A 的护栏数字**：PR1/PR2/PR10 合入后重算分布，
`>600s: 0/1370`，而实测 idle gap max 293.1s，600s ≈ 2 倍余量。
§5.A 那组"上限护栏"（600/1500/1800s）**不需要动到** —— 把谓词改对之后值本来就够用，
这与横向对标一致（四家竞品都停在 ~300s 作为 idle 门槛）。

### PR13：常驻回归（`tests/llm/healthy-slow-stream-no-defense.test.ts`）

原用例只断言"没抛错 + 走到 message_stop"。那**拦不住"开了枪却没杀死"** ——
而那恰好是本文档记录的真实形态（`TimeoutFired` 触发、`abort()` 调了，
但 `Promise.race` 没 settle，流继续跑完，这正是 `TimeoutIneffective` 存在的理由）。
那种情况下用例全绿，生产里已经在往轨迹写误杀记录。
判据收紧成**一枪都没开**（`TimeoutFired`/`WatchdogKill`/`StreamStall`/`TimeoutIneffective` 全为 0），
并补一条正向对照（断言 `completed` 事件在，否则"零事件"可能只是 observer 没接上 = 假绿）。

## 放弃了什么（以及为什么不选）

**PR15（`finish_reason=length` 时 prefix 续写）—— 判为不该做，已单独写 rejected note。**
方案里三条前提逐条核验后都不成立，详见
`.agents/notes/rejected/feature/2026-08-20-finish-reason-length-的-prefix-续写.md`。

**没有按 §5.A 把全局阈值抬到 600/1500/1800s。** 新分布显示 `>600s: 0/1370`，
抬全局的收益为零而代价确定（所有模型的真僵死回收一起变慢）。
改用 per-model 把代价限定在真正需要的两个模型上，且**本次一个模型都没填**——
只交付机制与用户入口。填哪个模型应当由真实轨迹驱动，我现在只有两个样本
（各 1 次、n=1），拿 n=1 去写死一个默认值就是拿噪声当分布。

**没有把 `still_progressing` 的判据改成"快照陈旧时不下结论"。** 它现在把陈旧快照
当权威（`lastProgressMs < 30s` 就判"慢但活着"），逻辑上有同型缺陷。但那是
**行为变更**（会改变 digest 把告警降级为 [低] 的判定），不属于"补埋点"的范围。
已把 `snapshot_age_ms` / `snapshot_stale` 落进同一条记录，下一个人有数据可依。

**没有重命名那四个 chunk 字段。** 见 PR11 ② 的理由：会让全部历史轨迹静默变 0。

## 拿什么证明它生效了

**先说两条本次最值得记的 —— 都是"我想对了但做错了"，且都不是自己发现的。**

**① PR12 的优先级链是被用例改掉的。** 第一版写成 `settings.network > per-model`，
机理上讲得通、注释都写好了理由。是 PR13 那条"同一条流只改 per-model 配置，
一次死一次活"的对照用例报红，才发现那个顺序会让 per-model 几乎永不生效。

**② fetch 硬顶的留痕第一版漏了 disarm，会记出假超时。** 审查时抓到：
`AbortSignal.timeout` 到点一定 abort，与 fetch 是否早已成功无关 ——
成功的流会在阈值到点落一条从未发生的超时，噪声量正比于成功请求数。
讽刺的是这个 PR 的主题正是"让埋点说真话"，而我在补留痕时造了个说假话的埋点。

两条合起来的教训：**"机理讲得通 + 测试全绿"里少了对抗性检查时，结论仍可能是错的。**
①是用例拒绝了一个看起来对的设计，②是审查拒绝了一个看起来对的实现 ——
两种都不是靠再想一遍能得到的。

跑过的命令与输出：

- `bun test packages/core/tests/trace/ packages/core/tests/config/` → **1143 pass / 0 fail**
- `bun test packages/core/tests/llm/` → **1470 pass / 0 fail**
- `bunx tsc --noEmit` → 仅 4 条**基线既有**报错（`tests/query/discarded-attempt-usage.test.ts`，
  已用 `git stash` 在 base 上复现同样 4 条确认与本次无关）

新增/加强的哨兵（每条都实际报红过一次，不是写完就绿）：
- `tests/config/timeout-ladder-sentinel.test.ts`：阶梯表补进 fallback / watchdog 两档。
  ⚠️ **它们此前不在表里，而那正是 PR14 那对同值能活下来的原因** ——
  "严格递增 + 间距 ≥120s"这个自检结构性地看不到没被列入的层。
  同时新增"fallback ≠ watchdog"、"只调 watchdog 时 fallback 不跟着变"、
  "兜底常量与 app.ts 注入点都指向新字段"四条。
- `tests/trace/timeout-layer-catalog-sync.test.ts`（新）：`TimeoutLayer` 联集必须与
  `scripts/telemetry-trigger-rate.ts` 的手写副本逐项一致，且每一层都能找到 emit 点。
  手写清单在本仓有多次漂移前科，漏一层的后果是"那一层永久零触发"，
  **而零触发看起来与"它从没出过故障"完全相同**，是最难发现的那类缺陷。
- `tests/trace/snapshot-staleness-and-chunk-field.test.ts`（新）：12 条，含"数字没变但
  新鲜度必须前进"（这条最容易实现错）、"老轨迹回退四个历史名不能静默变 0"，
  以及 4 条钉住 disarm 的（"已 disarm 后到点仍 abort 但不许落事件"就是上面②那个 bug 的回归）。
- `tests/llm/stream-stall-tiers.test.ts`（新）：5 条，钉住游标只前进、首档保持 30s
  （改掉会让新旧轨迹 stall 计数不可比）、汇总条与档位条互斥。

**改哨兵而非删断言的一次实例**：`已默认关闭的第四层不再无条件装 signal` 报红了 ——
因为 PR11 把守卫从 `openai.ts` 下沉进了 `makeFetchAbsoluteTimeoutSignal`。
断言改到新落点（`if (timeoutMs === undefined) return undefined`），
**要守的不变量没变**：不配置就不装。顺带钉住"两条流式路径不许再出现裸
`AbortSignal.timeout(FETCH_ABSOLUTE_TIMEOUT_MS)`"，但**刻意不断言整个文件里没有
`AbortSignal.timeout(`** —— `probeModelCapability` 的 10s 一次性探测也用它，
连坐它只会逼后来人删断言。

数据复算（自建临时探针，跑完即删；口径为 `RetryTelemetry.stream_completed.elapsedMs`
与 `stream_stall.gapMs`，本机 51 个会话目录中 50 个有 events.jsonl）：

```
成功流 n=1370   p50=3.9s  p95=83.7s  p99=294.2s  max=507.8s
  >240s: 29/1370   >300s: 2/1370   >480s: 1/1370   >600s: 0/1370   >1500s: 0/1370
按天：0817 之前 max=296.6s（一堆 296.x 贴 300s 硬顶）
      0817 之后 max=507.8s，296.x 聚集消失
无进展间隔（stream_stall.gapMs）max：origin-deepseek-v4-pro 293.1s / glm-5.3 284.5s
```

**这份分布的关键不是那几个数，是它不再被删失。** 旧分布 max=296.6s 紧贴硬顶且
296.x 挤了一堆（更长的流全被杀掉、没机会以 completed 落盘），是
[[censored-distribution-cannot-justify-its-own-cap]] 的典型形态；
新分布 max 已跑到 507.8s 且那个聚集消失，说明右尾是真的。
§0.0.1 约束 ② 要求"PR14 不得早于 PR1/PR2 且必须用未删失的分布论证"——
这份复算就是那个门禁的凭据。

## 尚未验证的部分（别当成已交付）

- **`watchdog_kill` / `fetch_absolute_timeout` 两层在生产里一次都没触发过**
  （前者需要真强杀、后者默认关闭）。哨兵只证"有发射点"，
  真触发率要跑 `bun scripts/telemetry-trigger-rate.ts` 看真轨迹 ——
  静态测试无论怎么写都替代不了它。这正是本仓"有代码 ≠ 有能力"那条铁律的适用场景。
- **stall 分档的端到端行为没被覆盖**：`STALL_LOG_MS` 是硬编码 30s、env 压不动，
  所以那个文件断言的是源码形态 + 汇总条行为。要真跑需要 30s+ 的用例，
  不值得进常驻回归（会拖慢每次 CI）。已在文件头注明哪部分没覆盖。
- **`fallbackStreamTimeoutMs = 600s` 尚无生产样本落在 480~600s 之间**（`>480s: 1/1370`）。
  它是按 2 倍余量取的，不是被数据逼出来的。下一批轨迹里若出现 500s+ 的健康流，
  应回头核对这一档是否仍够宽。
- **per-model 覆盖在 `query/stream-processor.ts:140` 那一层不生效**（刻意留的缺口，
  已在该行注明）：`processStream` 签名里没有模型身份，硬接要从 loop 一路透传。
  provider 内部四条路径都已生效，那才是真正开枪的地方；本层是外层软兜底、
  默认 1500s 远宽于 per-model 会调的量级。**别为了"看起来接全了"提前加参数。**
