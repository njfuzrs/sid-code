# 重试分类器与面板文案合并为一份共享词表，流内错误不再丢状态码

## 决定了什么

新增 `packages/core/src/llm/error-lexicon.ts`，作为「错误文案 → 错误码」的唯一词表。
`classifyError`（决定重不重试）与 `inferErrorCode`（决定面板文案）此前各写一份关键词，
现在都调它。数字边界判断 `hasBoundaryDigits` 抽到 `status-digits.ts`，
两边共用（词表是 `errors.ts` 的依赖，实现留在 `errors.ts` 里会成环）。

六处行为变化：

1. **`classifyError` 改成「有状态码就只看状态码」**。新增 `classifyByHttpStatus`，
   表与 `error-messages.ts` 的 `codeFromStructured` 对齐，补进此前缺的 402（欠费）
   与 403（无权限）。一条 `503 Service Unavailable`（正文既无数字也无 overloaded）
   此前落到「无法分类」→ 零重试转 fallback，现在判 `overloaded`。
   反向也钉住了：`400 ... overloaded` 不因文案里的关键词被拖进重试。
2. **`classifyStreamError` 回退时把 statusCode 带进 `classifyError`**。此前写
   `classifyError(new Error(message))`，状态码在这一步丢掉，于是 400/404/402 全部
   兜底成 `StreamLevelError("server_error")` 重试 10 次 —— 三者都是确定性失败。
3. **词表补进网关中文文案**：「负载已饱和」「余额不足」「请充值」等。smoke-8 的
   429 此前只靠结构化 code 兜住，纯中文报文在重试侧认不出。
4. **英文短语改词边界匹配**，`capacity` 不再命中 `capacities`。`conflict` 直接从
   词表移除 —— 它本身是完整单词，词边界也挡不住 `git merge conflict`，
   409 只认 `lock timeout` 和带数字边界的状态码。
5. **`openai.ts` 流内 error chunk 不再无条件置 `streamLevel: true`**。改用
   `pickStreamErrorTag`（规则同 `anthropic.ts` 的 `pickUpstreamTag`：空串、纯空白、
   字面量 `"error"` 都不算拿到 type），并新增 `streamErrorStatus` 透传网关塞在
   error 对象上的状态码。
6. **`memory_recall` 纳入 `FOREGROUND_SOURCES`**。`recall.ts` 自己传了
   `maxRetries: 2` 和 15 秒 deadline，而 529 分支在这些预算生效前就 return，
   于是 429 能重试、503/529 一次都不试。

`TerminalReason` 新增 `usage_limit_reached`（用量到顶，等重置或换模型）。
连带把它加进 `cooldown-probe.ts` 的「发还探针配额」一支：它是会话/周窗口用尽，
不是这条冷却记录在问的那个短期限流窗口。

## 放弃了什么（以及为什么不选）

- **再往 `classifyError` 里补一条关键词**。缺陷文档明确要求根治。补关键词治的是
  这一条报文，而两张表还是两张表，下一个网关文案会再分叉一次 —— 这次已经是
  `hasBoundaryDigits` 那轮事故的第二次（那次只修了数字边界这半边）。
- **让 `classifyError` 认不出时兜底成可重试**，对齐 `classifyStreamError` 的行为。
  会把 TypeError 这类确定性故障拖进 10 次退避、每次最长 120s。
  保留 fail-fast，新增 D7 用例把这条边界钉住。
- **把 `summary` / `title` / `classifier` 一起加进前台集合**。全仓没有任何调用方在
  传这三个源，它们的问题是「没人用」，不是「策略错了」。只加真实在用的
  `memory_recall`，并在注释里写明不要顺手加另外三个。
- **把 `conflict` 留在词表里靠词边界兜**。实测词边界对完整单词无效
  （`git merge conflict` 仍然命中），只能移除。
- **词表里留裸 `network`**（2026-09-24 CI 回归后补）。面板侧这个词是安全的，
  它只决定显示哪句文案；但同一份词表现在也驱动 `classifyError`，决定要不要重试。
  裸 `network` 命中 `network down` 这类散文，把一条确定性失败拖进重试。
  收窄成 `network error`：真网络故障不靠这个词，`.code` 走 `getNetworkErrorCode`，
  无结构字段的文案走 `RETRYABLE_CONNECTION_MESSAGES`（里面已有 `network error`）。

全量 `bun test`：**12566 pass / 7 fail**，861 个文件、169s。7 个 fail 全部与本改动无关，
用**同一批 vendor symlink 的干净 baseline worktree**（detached 在本分支的基点
710ef7dd）跑同样 4 个文件复现，失败集合逐条一致：

```

(fail) /model discover 必须消费能力缓存 > 未在速查表、但能力缓存有 → 报 cache 而非 failed   ×2
(fail) 回归面：真实的能力测试文件在假 HOME 下跑完… > 假家目录里不出现 model-capabilities.json
(fail) state-bridge 走 isPanelVisible（面板唯一入口） > 划掉的条目不进 TUI 快照 tasks[]
→ baseline 710ef7dd：同样 281 pass / 1 fail + 98 pass / 4 fail，同名同条
```

⚠️ 在 worktree 里跑测试前必须补两个 symlink，否则会多出 21 个假失败：
`packages/tui-renderer/src` 与 `packages/cli/src/command/commands/claude-api/reference`
都被 `.gitignore` 排除（248 / 258 行）、真实字节在 `.vendor-src/`，
新 worktree 里这两个路径不存在 → `Cannot find module '@sid-code/tui-renderer/*'`。
`lint:boundary` 同理（它 walk `tui-renderer/src`）。

分类相关的 9 个测试文件单独跑：

```

bun run format:check    → All matched files use the correct format
bun run lint:boundary   → 越界依赖 0 处、测试跨包相对路径 0 处
```

**这次差点漏掉的回归（值得单独记）**：第一版把整张状态码表提到了
`x-should-retry: false` 闸门**之前**，于是 429/500/529 配 `x-should-retry: false`
返回 `RetryableError` 而不是 `server_declined_retry` —— 网关说"别打了"仍照打满 10 次
退避，正是 B5-3 当初要修的东西。`resilience-b5-gates.test.ts` 3 条断言抓住了它。
现在的顺序是「终端结论先返回（1a）→ 闸门 → 可重试结论（1b）」，两段都写了注释说明
为什么不能合并成一句 `return structural`。

`status-code-classification.test.ts` 新增四格矩阵（streamLevel × statusCode 的
全部组合）+ 真实报文回放 + 两条分类路径的一致性对账，34/34 通过，2.11s。

三条旧断言由「记录缺陷」改成「钉住修复」，都在原处写明了为什么转向：

- 「同一条 message 不带 statusCode → 认不出来」→ 现在认得（词表补了中文）。
- 「429 不带 statusCode → 只发 1 次」→ 现在发 3 次（文案本身成为判据）。
- 「终端状态码不含 403」→ 403/402 已进分类表。那条注释原文是一道阻止修复的注释。

变异自证（确认新用例真能抓住回归，实跑过）：把 `classifyStreamError` 里传状态码的
那几行改回 `classifyError(new Error(message))`，同一个文件从 34 pass / 0 fail
变成 31 pass / **3 fail**：

```
(fail) 四格 > 带 streamLevel 的 400/404/402 是 Terminal，不是重试（D1）
(fail) 四格 > 带 streamLevel + 带 statusCode：503 无 overloaded 字样 → overloaded（D2）
(fail) 真实网关报文回放 > 400 + 任意 body → 不重试
        期望 {kind:"terminal", reason:"invalid_request"}
        实得 {kind:"retry",    reason:"overloaded"}   ← 400 被文案里的 overloaded 拖进重试
```

最后那条尤其说明问题：丢掉状态码之后，一条 400 会因为正文里恰好有 `overloaded`
被判成可重试 —— 正是缺陷文档说的「判据建在了错误的地方」。

### 补：裸 `network` 拖垮 CI（同日）

PR #95 的 CI 在 ubuntu 与 macos 上同样红两条，都在 `compact-analytics.test.ts`：
`手动路径的每一条 context_compact 都必须是 trigger=manual` 在 **5000.11ms** 超时，
下一条 `数字模式摘要失败` 期望 1 条事件实收 2 条。main 上同一文件的失败路径用例
是 **0.44–0.60ms**（run 35964995201），所以不是既有 flake。

根因是词表把面板侧的裸 `network` 子串搬进了重试分类器：测试 mock 抛的
`new Error("network down")` 在 main 上 `classifyError` 返回裸 Error（无法分类 → 不重试），
在本分支上变成 `RetryableError("network_error")`。compact 路径 `maxRetries: 2`、
退避基数 1s，第 0、1 次各睡约 1s、2s，单条失败路径约 3s；五条路径串在同一用例里的
那条（含两条失败路径）正好越过 bun 默认 5s 超时。超时后未完成的调用把事件写进
下一个用例的 sink，于是「期望 1 收到 2」。

⚠️ 本地复现时第一次跑是**假绿**（57ms）：worktree 的 `node_modules` 是指向主仓的
symlink，`@sid-code/core` 解析到 main 的源码，测的根本不是本分支。删掉 symlink
重跑 `bun install` 后才指向本 worktree。

收窄成 `network error` 之后：

```
bun test ./packages/cli/tests/command/compact-analytics.test.ts   → 8 pass / 0 fail，81ms
bun test ./packages/cli/tests/command/compact-focus.test.ts       → 11 pass / 0 fail，31ms
bun test ./packages/core/tests/llm/ --test-name-pattern '^(?!.*\[slow\])'
                                                                  → 1716 pass / 0 fail，23.64s
make build                                                        → 自检通过，无 undefined 导出告警
```

防回归钉在 `status-code-classification.test.ts`：`network down` 与
`network partition between replicas` 必须「面板认不出 + 重试侧无法分类」，
同时 `Network error: ENOTFOUND …` 与 `network error` 仍判 `network_error`。
