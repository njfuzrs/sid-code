# 撤销 S6「运行时学习已放行输入上限」：窗口只来自静态数据源

## 决定了什么

**整体删除 S6 窗口学习，不保留开关。** 上下文窗口是模型固定属性，不由运行时观测改写。

源码删除清单：

- 模块 `packages/core/src/llm/learned-window.ts`（落盘、TTL、min 收敛、多进程写合并全部一并删除）。
- 写入点：`query/loop.ts` 流式 prompt-too-long 分支的 `learnAdmittedCeilingOnOverflow(ctxMgr, config)` 调用，以及该函数本身（含「学到后当场 `setMaxTokens`」）。
- 读取点：`llm/token-estimator.ts` 的 `lookupAdmittedCeiling` 取 min；`ModelMetaSource` 去掉 `"learned"` 档。
- 展示：`cli/src/ui/components/model-meta-format.ts` 的 `"learned"` 标签。
- 路径常量：`config/paths.ts` 的 `learnedInputCeiling`。
- 注释：`llm/registry.ts` 的 D4 说明、`llm/model-capabilities.ts` 的「这里不学窗口」段落。

**连带删除 S6 引入的 `baseURL` 透传参数**（`cb53c5c3` 为让「学到的上限按 (model, base_url) 查」而加）：
`getContextLimit` / `resolveContextLimit` 第三参、`SystemPromptContext.baseURL`、`AutoThresholdInput.baseURL`、
`collector.computeContextUsage` 的 `baseURL`，以及 12 处调用点的传参。删掉 S6 后它没有任何读取者，
留着就是一个「无法解释为什么存在」的死参数。

**不删用户磁盘上的 `~/.sid-code/learned-input-ceiling.json`**：代码不再读写它，它就是无害孤儿。
自动删除需要一段只跑一次的迁移代码，而产品代码删除用户目录里的文件与仓库铁律同源。

## 放弃了什么（以及为什么不选）

| 被放弃的方案 | 为什么不选 |
|---|---|
| 保留 S6，改成「只在本会话生效、不落盘」 | 学到的值仍然是错的（F1 的表现），只是错的范围变小。属于折中 |
| 保留 S6，学到的值不覆盖窗口、只用来提前压缩 | 仍然是用错误的值驱动决策。压缩时机应由真实窗口和真实用量决定 |
| 保留 S6 给「确实存在网关墙」的场景兜底 | 本机 6/6 次溢出都精确吻合「输入 + 384k 撞 1,048,576」，没有一次证据支持独立网关墙。真要遇到，用户在 `availableModels[].contextWindow` 里显式声明即可（这条路径一直存在且优先级最高） |
| 加一个开关让用户自己选 | 一个明知是错的行为不该作为选项提供 |
| 保留 `baseURL` 形参不删（减少 diff） | 删除 S6 后无任何读取者；留着一个无法解释的参数，下一个改到这里的人（或 agent）还要重新推导一遍它为什么存在 |
| 启动时自动清理旧 JSON | 见上：需要一次性迁移代码，且产品代码不该删用户目录里的文件 |

**已知残留风险（本 PR 未覆盖，必须点破）**：方案文档 §5.2 的副作用表要求 F1（每次请求发 `max_tokens=384000`）
与 F2 同时上线。本 PR 只做 F2。删除 S6 后分母恢复为注册表 1M，用户在 664k 附近仍会撞一次 400，
由既有的 reactive 压缩兜底（功能正确，代价是多一次失败请求）。F1/F8 属于另一个 PR。
