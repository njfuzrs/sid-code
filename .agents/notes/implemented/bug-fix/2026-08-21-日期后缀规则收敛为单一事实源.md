# 日期后缀规则收敛为单一事实源：三处各自演化的正则，其中两处判断实质不同

## 决定了什么

「什么算模型名尾部的日期/批次后缀」这条规则在仓库里有**三份各自演化的实现**，
本 PR 把它们收敛到 `model-name-normalize.ts` 一处：

| 消费者 | 修前的规则 | 后果 |
| --- | --- | --- |
| `model-name-normalize.ts`（采集写键 + 查询候选） | 恰好 6/8 位或 `YYYY-MM-DD`，**锚定结尾** | 基准 |
| `model-registry.ts` 家族匹配 | `/-\d{4,}.*$/`（**4 位起、贪吃到结尾**） | 与基准**实质不同**，见下 |
| `session/utils.ts` 的 `shortenModel` | 只有 8 位与 `YYYY-MM-DD`，**缺 6 位那一支** | 国内厂商命名不缩短 |

前两者的分歧**不是"没复用同一个常量"这种整洁度问题**，是两条链路对同一个模型名给出不同答案：

```
gpt-5.4-turbo-2026     registry 侧剥（4 位）→ 家族基名 gpt-5.4-turbo   采集侧不剥
xxx-250324-preview     registry 侧贪吃剥成 xxx                        采集侧因锚定 $ 完全不剥
```

而分叉**没有任何报错** —— 只会在某一条链路上静默借错一个窗口值。这正是
`20260818-模型元数据体系重构` 方案 §5.2 明确要求过的一条（「**同时 `lookupRegistry` 的匹配也应
享受这条归一化**——否则同一个模型名在两条链路上归一化规则不一致，会产生新的不对称」），
那批 PR 落地时漏掉了。

**刻意保留为两个函数而不是一个。** 两者的**语义**真的不同，合并会打坏家族匹配：

- `stripDateSuffix` **锚定结尾**，服务「剥到基础名做一次精确查」——`deepseek-v3-250324` →
  `deepseek-v3`，查到就是查到，不涉及借用；
- `familyBaseName` 允许日期段**后面还挂变体后缀**，服务「两个名字算不算同一家族」——
  `claude-sonnet-4-20260101` 与表里 `claude-sonnet-4-20250514` 的家族基名都是 `claude-sonnet-4`，
  锚定结尾的规则算不出这种相等。

共享的是**长度判据**（恰好 6 或 8 位纯数字，或 `YYYY-MM-DD`），不是整个正则。
这条同步关系写成了单测不变式（「凡 `stripDateSuffix` 会剥的，`familyBaseName` 必须剥到同一结果」，
1–10 位机械枚举），而不是靠注释提醒下一个人记得。

**唯一的行为变化，是刻意的收紧。** 实测全部 135 个网关模型 + 全部注册表键，
新旧规则只在 2 个注册表键上给出不同的家族基名：`grok-4.20-0309-reasoning` /
`-non-reasoning`（旧规则算成 `grok-4.20`，新规则不剥）。后果是 `grok-4.20-0310`
这类未来批次不再能借到它们的 1M，落 `resolveFallbackWindow` / 400 自愈。这是期望行为：
`0309` 是 4 位批次号不是 6/8 位日期，而 `-reasoning` / `-non-reasoning` 是**能力变体**
（两者行为不同），把它们的值借给一个只知道批次号的名字属于「猜得没有约束」——
与剩下 8 个变体后缀缺口同一处置。

**`model-registry.ts` 的「零 import 纯数据表」性质被有意破了一次。**
`telemetry/cache-bench-core.ts:15` 的「静态引入不成环」判断引用了这个性质。
新增的依赖 `model-name-normalize.ts` **自身零 import**，所以那个结论仍然成立；
并且加了一条门禁断言锁住「该模块必须保持零 import」——有人给它加依赖时在测试里红，
而不是在某条运行时路径上成环。两个文件的头注释都写了这条约束。

## 放弃了什么（以及为什么不选）

**放弃把 `familyBaseName` 与 `stripDateSuffix` 合并成一个函数。** 看起来更干净，
但变异自证里第 2 组就是这个（去掉 `(?:-.*)?`）：家族匹配立刻失效，
`claude-sonnet-4-20260101` 借不到同家族的 200K。两者的语义差异是真实的，不是重复。

**放弃把 `model-registry.ts` 的家族匹配整体挪走**（比如挪进 `model-lookup.ts`）。
那样能保住零 import，但家族匹配是 `lookupRegistryFuzzy` 六级瀑布里的第 5 级，
拆出去要么把整条瀑布搬走，要么在两个模块间来回调用。本 PR 只统一「日期判据」这一个点，
不动匹配链的结构 —— 那批 PR 刚把这条链改完，紧接着再改一次结构没有收益只有风险。

**放弃让 `shortenModel` 复用 `familyBaseName` 而不是 `stripDateSuffix`。**
显示场景要的是「去掉冗余后缀」，不是「找同家族」——用贪吃版会把
`claude-sonnet-4-20250514-preview` 显示成 `claude-sonnet-4`，丢掉用户关心的 `-preview`。

**放弃顺手扩大规则覆盖到变体后缀**（`-maxthink` / `-wot` / `-lite` / `-turbo`）。
那 8 个真实缺口刻意不修，理由在原方案里已经论证过：`-lite` / `-turbo` 的窗口通常真的更小，
剥后借基础名是**高估**。这条边界不因为"顺手"而移动。

## 拿什么证明它生效了

**三条链路现在给出同一个答案**（修前 `gpt-5.4-turbo-2026` 在 registry 侧被剥、采集侧不剥）：

```
                          stripDateSuffix        familyBaseName
gpt-5.4-turbo-2026        gpt-5.4-turbo-2026     gpt-5.4-turbo-2026    ← 修前 registry 侧剥成 gpt-5.4-turbo
deepseek-v3-250324        deepseek-v3            deepseek-v3
qwen3.6-plus-2026-04-02   qwen3.6-plus           qwen3.6-plus
minimax-m2.5              minimax-m2.5           minimax-m2.5          ← 版本号不剥（这条规则唯一的真风险）
```

`shortenModel` 补上 6 位分支（修前 `doubao-seed-1-8-251228` 完全不缩短）：

```
doubao-seed-1-8-251228     → doubao-seed-1-8      ← 修前原样返回
deepseek-v3-250324         → deepseek-v3          ← 修前原样返回
claude-sonnet-4-20250514   → claude-sonnet-4      ← 既有行为不变
minimax-m2.5               → minimax-m2.5         ← 既有行为不变
```

**既有回归全部保持**（`model-registry.test.ts` 的家族匹配四条断言未改一字仍全绿）：
`claude-sonnet-4-20260101` = 200K、`claude-sonnet-4-6` = 1M、`claude-opus-4-8` = 1M、
`CLAUDE-OPUS-4-8` = 1M。

**变异自证 5 组，每组都真被触发**（CLAUDE.md：防线的验收判据是「真被触发过」）：

| 变异 | 结果 |
| --- | --- |
| `FAMILY_BASE_RE` 放宽成 `/-\d{4,}(?:-.*)?$/`（退回旧 registry 的长度判据） | **2 fail** |
| `FAMILY_BASE_RE` 去掉 `(?:-.*)?`（与 `stripDateSuffix` 合并） | 1 fail |
| registry 退回内联 `/-\d{4,}.*$/` | 1 fail |
| `shortenModel` 退回旧的两条正则（缺 6 位） | 1 fail |
| 给 `model-name-normalize.ts` 加一个 `import`（破零 import） | 1 fail |

变异全部还原后 69 pass / 0 fail，`git diff` 确认生产代码只含有意改动。

**主口径未退步**（`bun run catalog:coverage`，本机真实三源数据）：
对话模型覆盖率 105/113 = **92.9%**、窗口投票众数 **92.2%**、真实缺口 **8 个** ——
与本 PR 之前逐字一致。这是本次预期的结果：修的是「两条链路判断不一致」这个结构问题，
而受影响的模型在采集精确层就已命中，所以覆盖率曲线本来就不该动。
**如果它动了，反倒说明改错了。**

**门禁五道全绿**：`bun run affected-tests:run`（1658 pass / 0 fail / 95 文件）、
`make build`（自检通过，显式 grep 无 `will always be undefined`）、`bun run lint`、
`bun run format:check`、`bun run lint:boundary`（越界 0 处）。

**已知未验证**：`grok-4.20-0310` 那类未来批次落兜底之后走 400 自愈这条路径，
本 PR 没有端到端跑过（需要真发一次请求撞 400）。它复用的是既有自愈机制、不是新代码，
但「收紧后确实由自愈接住」这一步目前是推断，不是实测。
