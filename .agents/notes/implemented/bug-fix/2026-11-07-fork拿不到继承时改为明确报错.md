# fork 拿不到继承时改为明确报错，不再静默降级（06H1 T1 / T2）

## 决定了什么

三条静默降级改成确定性行为：

1. **`fork + run_in_background` 直接 `isError`**（`tool.ts` 的 `execute()`，判断放在
   `def.background` 合并之后）。后台路径 `runAsync → executeInBackground → SubAgent.execute`
   从不传 `forkMessages`，此前组合会被静默丢掉 fork、退化成空白上下文起步。
2. **`fork` 但 `mainContextProvider` 未注入直接 `isError`**（`runSync` 开头，放在
   `acquireSlot` 之前——确定性报错不该占用并发 slot，也不建 worktree）。此前静默退化成
   空白上下文，调用方拿到的仍是一次"成功"的 fork。
3. **`forkMessages` 非空时跳过 `shouldUseSpawn()` 强制进程内**（`sub-agent.ts` 的
   `execute()`）。spawn 的 `ParentInitMessage` 只有 `user_prompt`，走 spawn 会把继承的
   父对话整段丢掉。写法与 `task.cwd` 存在时强制进程内一致：都是「这个上下文跨不了进程」。

顺带补上 `execute()` 入参断言里漏掉的 `fork?: boolean`（`runSync` 的参数类型一直有它，
入口断言没有，T1 的判断第一次需要读它才暴露）。

## 放弃了什么（以及为什么不选）

- **不选「后台也支持 fork」**。fork 在本地轨迹里 0 次使用，没有需求证据；支持它要把
  `forkMessages` 穿过 `runAsync` / `executeInBackground` / spawn 协议三层，为一个没人
  用的能力改跨进程协议不划算。改法保留：以后真有使用数据再回来做。
- **不选「把 `forkMessages` 加进 `ParentInitMessage`」**。同上，要改跨进程协议；
  强制进程内是一行条件，代价小得多。
- **spawn 路径选「强制进程内」而不是「报错」**。这条是执行机制细节，不是调用方错误：
  调用方只是要 fork，进程内一样能拿到继承，没有必须失败的理由。报错只留给
  「这个组合根本拿不到继承」的两种情况（后台、无 provider）。
- **不顺手修 spawn 的 `stopAttribution` 缺失**。T3 的排查已确认它是独立缺口
  （`ChildResultMessage` 只带 success/output/usage/turns/toolUseCount/model/provider），
  补它要动同一份跨进程协议，与本次「不让 fork 静默降级」不是一回事。

## 拿什么证明它生效了

新增 `packages/core/tests/agent/subagent-fork-guard.test.ts`，6 个用例：

- `fork + 显式 run_in_background` → isError 且文案含「fork 只支持同步」
- `fork + 定义 background: true`（不显式传参）→ 同样 isError（验证判断在合并之后）
- 未注入 `mainContextProvider` + 同步 fork → isError 且文案点名 `setMainContextProvider`
- 注入 provider 后 fork 照常，`RecordingProvider` 收到的请求里含父对话原文
- `shouldUseSpawn()` 为真 + `forkMessages` 非空 → `executeSpawned` 未被调用，上下文来自 fork
- 对照：没有 `forkMessages` 时 spawn 照常被选中（证明强制进程内只在 fork 时生效）

变异自证三次（改坏 → 断言变红 → 恢复）：

- T1a 判断改成 `false && ...` → 两个后台组合用例变红（4 pass / 2 fail）

- T2 判断改成 `false && ...` → 未注入 provider 用例变红（5 pass / 1 fail）
