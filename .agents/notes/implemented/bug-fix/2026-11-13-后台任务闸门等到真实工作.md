# 后台闸门等到的必须是真实工作：两个 wrapper 交出真 promise

## 决定了什么

`end_turn` 的两个后台任务经 `runBackgroundTask` 闸门提交，但两个 wrapper 原先都是
`async` + 内部 fire-and-forget，返回的 promise 在第一个微任务就 settle。闸门等了个空，
于是三件事全部失效：串行（两个 fork 并发）、退出排空（`drainBackgroundTasks` 立即返回、
进程退出掐断十万 token 级请求）、`/cost` 的「⚠ 后台任务 … 进行中」提示（闸门永远"空闲"）。
而 `admitted` / `deferred` 统计看上去完全正常 —— 这就是它藏了三个月没被发现的原因。

采用方案 ①（最小修法）：

- `packages/core/src/session-memory/session-memory.ts`：`updateSessionMemory` 改为
  `return pending`（真实更新链）；「上一次未完成 → 跳过」分支返回已 resolve 的 promise，
  不复用上一轮那条链。
- `packages/core/src/memory/extract/extractor.ts`：`executeExtract` 由 `void start(...)`
  改为 `return start(...)`。
- `initSessionMemory` 补 `runFork` 测试注入点（与 extractor 既有的 `ExtractContext.runFork`
  同形态），否则无法用「会挂住的假 fork」验证闸门。
- 同步修正 `query/types.ts`、`query/engine.ts`、extractor 头部与接口注释里已失效的
  fire-and-forget 表述（注释与行为不一致本身就是下一个人的陷阱）。
- 新增 `packages/core/tests/agent/background-task-gate-real-work.test.ts`：C1（真实工厂 +
  100ms 假 fork，串行与 busy）、C1 反面（跳过分支立即 resolve）、C3（真实闸门忙时
  `/cost` 输出含进行中提示）、C5（`drainBackgroundTasks` 会等 fork 跑完）。

不 await 这两个 fork：调用方 `query/loop.ts` 保持不 await，主循环收尾延迟不变。

## 放弃了什么（以及为什么不选）

- **方案 ②：删掉闸门、回到各自的 `pending` 锁。** 否决。两把独立的锁在语义上表达不出
  「后台任务全局最多跑一个」，而 2026-08-21 那次多付 32% 账单的事故正是这两把锁同时
  生效时发生的。删闸门等于把已修好的问题还回去，还会丢掉退出排空能力。
- **把两个 fork 改成主循环 `await`（前台化）。** 否决。实测收尾延迟会被拉长到 44s
  （方案 §5.1 B3），用「更快」换「更准的账」是净退步。
- **不改 wrapper，改闸门：把「立即 resolve」也当作 busy 一段时间。** 否决。那是猜一个
  假的忙碌时长，`/cost` 会变成常驻噪音，也无法让 drain 真正等到工作结束。
- **用 `mock.module` 替换 `runForkedAgent`。** 否决。模块级 mock 会跨文件污染同进程跑的
  其他用例；工厂注入点是本仓既有约定（extractor 早就有 `runFork`）。
- **在 `cost-pending-tasks.test.ts` 里接真实闸门。** 否决。那个文件的注释明确说明了不碰
  进程级单例的理由（与 `background-task-gate.test.ts` 互相干扰）。C3 的真实闸门版本放在
  本来就要占用/清理闸门的 C1 测试文件里。

## 拿什么证明它生效了

- `bun test packages/core/tests/agent/background-task-gate-real-work.test.ts` → **4 pass**；
  与既有 `background-task-gate.test.ts` 合跑 → **14 pass**。
- C2 变异自证（改坏 → 变红 → 恢复）：
  - 变异 A：`updateSessionMemory` 的 `return pending` 改回 `void pending` →
    **C1 红**（`events` 收到两个 `fork:start`，两个 fork 并发）、**C5 红**
    （`drainBackgroundTasks` 返回时 `fork:end` 还没发生）。
  - 变异 B：`executeExtract` 的 `return start(seq, false)` 改回 `void start(...)` →
    **C1 红**（`events` 缺第二个 fork 序列，`waitUntil` 在 fork 结束前就满足了空闲条件）。
  - 恢复后重跑 → 4 pass。
- 环境侧的一次真实发现：worktree 沿用主仓 `node_modules` 软链时，测试用相对路径操作的闸门
  与 `@sid-code/core/...` 解析到的是**两个模块实例**，C3 因此读不到忙状态。按 CLAUDE.md
  在 worktree 内 `bun install` 后通过。这条不是被测代码的问题，但会让人误判成"修复无效"。
- 未在本 PR 覆盖（如实标注）：
  - **C4 端到端 `sc-dev` 跑一轮**：需要真实模型与真实会话成本，留给维护者验收。
  - **C6 收益实测**（≥20 个真实会话对比后台时间占比）：需要本机轨迹数据，本 PR 只保证
    闸门语义正确，收益数字应在合并后用真实会话统计，不能从单测推断。
