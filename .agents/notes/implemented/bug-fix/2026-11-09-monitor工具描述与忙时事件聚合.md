# monitor 工具描述补位与忙时事件聚合（D19 / D20）

## 决定了什么

两件事都是「方案写了、代码没做」，各自补实现 + 回归用例：

1. **D19 工具描述缺项**，两处：
   - `tool/schedule-wakeup.ts` 的 `description()` 去掉「跑到 CI 过为止——每次唤醒检查状态」的旧典型用法，
     改为「**等外部状态（CI / PR / 构建 / 部署）请优先用 monitor**；本工具用于『到某个时间点再做一件事』
     或没有可流式观测的对象」。delay 钳制 / 单链替换 / 缓存 TTL 取舍三段保留（它们与 monitor 无关，
     删掉会丢既有约束）。文件头注释同步改写：原注释也用「跑到 CI 过为止」举例，留着就是同一处误导的
     第二份副本。
   - `tool/monitor.ts` 的 `call()` 结果补一句「**当前宿主在监控结束前不会退出**：结束本轮后进程会继续等待，
     监控结束时才输出并退出，期间不需要轮询」。判据复用 `wait-registry.ts` 新增的只读 getter
     `isWakeupRegistrationEnabled()`——同一个「宿主有没有 prompt 注入通道」事实，不新增「无头」标志
     （两个事实源必然漂移）。文案刻意不出现「无头」字样：stream-json 有注入通道、也会等到监控结束再输出，
     那句话对它的语义同样成立。

2. **D20 忙时事件聚合**（`cli/src/ui/history-adapter.ts` + `TaskNotificationMessage.tsx`）：
   `_meta.notif` 结构化路径里，**相邻、同 `taskId`、都带 `event`** 的通知合成一项
   （`event` 换行拼接 + `eventCount: N`）；渲染层 `eventCount > 1` 时摘要行改说
   「`<description> · N 条事件`」，**全部**事件行进 `⎿` 折叠区（首行不再占摘要位，否则与「N 条事件」
   自相矛盾）。单条事件不带 `eventCount`，渲染路径与改动前逐字一致。
   **只改渲染**：`_meta.notif` 里模型可见的结构化数据一条不动（有用例锁住）。

## 放弃了什么（以及为什么不选）

- **在 `ToolUseContext` 上加 `headless` 字段**（方案里的备选）：它要求 cli / SDK / 无头入口各自接线，
  多一个需要三处同步的新标志，而后两个入口本来就要读 `setPromptRegistrationEnabled`。复用既有开关是零新增状态。
- **monitor 自己维护一个「无头」模块级变量**：与 `wait-registry` 的开关重复，两处一旦漂移就会出现
  「wakeup 按有注入通道处理、monitor 按无头处理」这种半分裂状态。
- **把聚合放在 `query/loop.ts` 注入侧**：方案 §5.7.4 的口径是「只改渲染」，注入侧动 `_meta.notif` 会改变
  模型可见的结构化数据（模型可能依赖逐条事件的时间顺序）。放在 adapter 里，`/resume` 重建走同一个函数，
  新旧会话行为天然一致。
- **跨消息聚合**：不做。历史项是一条消息的产物，跨消息合并要维护跨条状态，且用户在两条消息之间看到的是
  不同的回合边界——把「第 1 个回合的 2 条」和「第 3 个回合的 1 条」合成「3 条事件」会抹掉时间维度。
  只聚合相邻项也是同一个理由的局部版。
- **单条事件也带 `eventCount: 1`**：会让「是否存在聚合」与「数量」耦合在一起，渲染层还要多一个判据；
  缺省 undefined 让旧路径完全不变。
- **顺手改 `system-prompt.ts:1257` 的调度映射段**：那里仍以「跑到 CI 过为止」举例并指向
  `schedule_wakeup`。它**不是** D19 点名的「工具描述缺项」，且是 `packages/core/src/config/`
  下的另一个引导源（改动会牵动参考页生成、影响所有会话的系统提示）。按「一个 PR 一个关注点」
  留在本 PR 外，D19 的范围严格停在工具描述与工具结果文案两处。这一点写在这里而不是静默略过，
  是因为它是同一处误导的第二份副本，下一轮收口时应当被看见。
