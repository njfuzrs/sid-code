# glob 撞 20s 超时的根因是 rg 排序，不是上限太短；顺带修掉部分结果死接线与受保护目录整体判失败

## 决定了什么

轨迹 `20261009-135641-0083c051` 里 `glob path=~` 两次报「ripgrep 搜索超时（20秒）」，排查出四个缺陷，一并修复：

1. **`glob.ts` 去掉 `--sortr=modified`，改在 JS 侧按 mtime 排序**（`sortByMtimeDesc` + `finalize`）。
   rg 一排序就退化为单线程，且扫完才吐第一行。同一条命令在 `~` 下实测：带排序 27–32s，不带 5s。
2. **`ripgrep.ts` 超时且有部分结果时改为抛 `RipgrepTimeoutError`（带 `partialResults`），不再直接 return**。
   旧代码先 return，结果有两个：「扫了一半」被伪装成完整结果；glob/grep 里「超时返回部分结果并标注」的分支永远走不到（死接线）。
   现在 glob 的超时路径与正常路径共用 `finalize`（deny 过滤 → 排序 → 截断），grep 的超时路径也补上了 mtime 排序。
3. **rg 以 exit 2 结束、且 stderr 全是逐路径访问错误（`(os error N)`）时，按正常结果返回**（`isOnlyPathAccessErrors`）。
   修完 1 之后端到端实测才暴露出这一条：`path=~` 会碰到 `~/Library` 下几十个 macOS TCC 受保护目录，rg 返回 2，被整体判成「文件匹配失败」，stdout 里已经找到的目标文件跟着丢了。
   判据是白名单：每一行都必须是路径错误才放行，参数错误、正则错误照旧算失败。
4. **超时上限可在 settings.json 用 `searchTimeoutSeconds` 配置**（优先于 `SID_GREP_TIMEOUT_SECONDS`），报错文案同时写清两件事：模型不要搜家目录或根目录，用户可以去哪里调上限。

默认值维持 20s（WSL 60s）。

## 放弃了什么（以及为什么不选）

- **调大默认超时（如 60s/120s）**：会掩盖根因。不排序时扫完整个家目录约 5s，20s 有 4 倍余量。调大之后，模型每次误搜 `~` 都要白等一分钟，部分结果也照样丢（排序时 stdout 为空）。
- **取消超时上限**：headless / 子代理场景没人按 ESC，扫网络盘或 FUSE 挂载会无限挂起。对标看，Codex 的 exec 默认 10s（`codex-rs/core/src/exec.rs` `DEFAULT_EXEC_COMMAND_TIMEOUT_MS`），Claude Code 默认 20s。没有哪家不设上限。
- **让模型在每次调用里传 timeout（Codex 式）**：给 glob/grep 的 schema 加参数会扩大工具面，模型也会倾向于传一个大数绕过收窄提示。暂不做，先看 settings 配置够不够用。
- **改回 rg `--sort`（oldest-first，对齐 CC）**：同样会退化单线程，性能问题不变。

## 拿什么证明它生效了

- 新增 `packages/core/tests/tool/ripgrep-timeout-partial.test.ts`，共 11 条，用假 rg（`SID_RIPGREP_PATH`）稳定复现「先吐几行再挂起」和「exit 2 + 权限错误」，不依赖机器快慢。
- 变异自证，三项都会红：
  - 恢复 `--sortr=modified` → 1 fail；
  - 恢复「有部分结果直接 return」→ 3 fail；
  - 去掉 exit-2 放行 → 1 fail。
- 端到端：真实 rg 在 `~` 下执行 `GlobTool.execute({pattern:"**/*27259502*", path:$HOME})`。
  - 修前：先超时，去掉排序后又报「ripgrep 退出码 2: ... Operation not permitted」；
  - 修后：5.7s 返回 `Desktop/27259502_133938618036_2.jpg`。
