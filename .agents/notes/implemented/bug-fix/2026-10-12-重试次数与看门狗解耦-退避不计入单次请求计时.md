# 重试次数与看门狗解耦：退避不计入单次请求计时，主循环不再给漏斗设 deadline

## 决定了什么

用户症状：上游 429 饱和时报「已尝试 6 次，证据 transient/deadline … 时间预算不足（需退避 142163ms，剩余 140436ms）」，
重试 5 次就终止，而 `maxTimeoutRetries` 是 10。

根因：主循环看门狗判「单次请求卡死」，却把漏斗内的**重试退避**也计入「无进展」。
2026-08-29（见 `2026-08-29-harbor-a11三个缺陷-…`）为止住「两层预算相乘」，把看门狗阈值
`min(header+grace, noProgress)`=315s 当 `deadlineAt` 交给漏斗 —— 次数从此被时间架空：
5s→120s 指数退避在 315s 内最多 5–6 次。那次修的是症状（让内层提前收手），没动根因（外层误把退避当卡死）。

改为三者各管各的：

| 职责 | 谁管 |
| --- | --- |
| 重试几次 | 只由 `maxRetries`（= `maxTimeoutRetries`）决定 |
| 单次请求卡死 | 看门狗 / 心跳 / 整体超时，**退避期不判、退避后从零起算** |
| 用户不想等 | ESC（退避可 abort） |

| 位置 | 改了什么 |
| --- | --- |
| `llm/types.ts` | 新 StreamEvent `retry_backoff`（start/end） |
| `llm/fallback.ts` | 重试退避与 S2 共享冷却等待前后成对发信号；退避前停掉本层流超时（resetStreamTimeout 为新 attempt 重新起表） |
| `query/retry-backoff-window.ts` | 新：包裹流、透传事件、维护退避窗口状态（per-call，不是进程级 —— 进程级会让 A 的退避暂停 B 的看门狗） |
| `query/loop.ts` | 删 `streamDeadlineAt`；看门狗退避中 return，基线取 max(最近内容进展, 最近退避结束) |
| `query/stream-processor.ts` | 退避期不判心跳/首字节，整体超时扣除退避时长 |

子代理 / recall / compact 的 `deadlineAt` **不动**：那些是真实的总时长预算。

## 放弃了什么（以及为什么不选）

- **调大 headerTimeoutMs / 调小 retryBackoffMaxMs**：仍是次数听时间的，只是换个数；首字节卡死要等更久才被杀。
- **deadline 改成 10 次退避之和**：两个上限依旧耦合，且退避含 jitter / Retry-After，算不准。
- **复用 human-input-gate 的进程级计数器**：并行子代理下互相暂停看门狗。

代价：上游持续饱和时最坏约 12 分钟才给出失败结论（原 3 分钟）。这就是 `maxTimeoutRetries=10` 的设计本意（network-profile 注释「名义累计退避约 12+ 分钟」），此前被看门狗悄悄打了折。

## 拿什么证明它生效了

- `bun test packages/core/tests/query/retry-count-decoupled-from-watchdog.test.ts` → 9 pass
  - 正向：400ms 退避 > 60ms 看门狗阈值 → 不被杀；负向对照：同样静默无信号 → 被杀（防空集全绿）
  - 退避结束后真卡死 → 看门狗仍开枪；漏斗 429 持续 → 跑满 1+10 次、10 对信号、0 次 `retry_budget_exhausted`
- 变异自证：删掉 loop.ts 的 `if (retryBackoff.active) return;` → 正向用例翻红（8 pass / 1 fail）
- 门禁文件 `retry-budget-shared-with-watchdog.test.ts` 改名重写为本文件：旧断言「必须带 deadlineAt」正是本次要否决的设计
