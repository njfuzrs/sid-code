# skill 动态发现在路径就是 cwd 时越出 cwd，把用户级 ~/.sid-code/skills 当项目级弹二次信任框

## 决定了什么

`discoverSkillDirsForPaths`（`packages/core/src/skill/dynamic-discovery.ts`）三处改动：

1. 起点：路径本身是已存在目录（`ls` 的 `dir_path`、`glob`/`grep` 的 `path`）时从它自己开始，否则取 `dirname`。
2. 硬边界：每一步都用 `relative(cwd, dir)` 判断，越出 cwd 立即停，不再依赖「恰好走到 cwd」这个相等判断。
3. 用户层排除：家目录本身、以及 `sidPaths.extensionDir("skills")`（含 `SID_CONFIG_DIR` 重定向）不再当作项目层动态发现。cwd=`~` 时它们就在 cwd 链上，前两条拦不住；口径与启动项目层上界 `getExtensionScanDirs`（家目录 = 用户层）一致。

根因：旧代码一律 `dirname(abs)`。会话 `20261020-141455-03a32aa2` 在 cwd=`docs-research/sid-code/summary/01-AgenticLoop` 下第一步就调了 `ls dir_path=<cwd>`，起点变成 cwd 的父目录，循环再也碰不到 `dir === cwd` 这个终止条件，一路走到 `/`，途中命中 `~/.sid-code/skills`。B1（#379）给动态发现补了信任门后，这份用户级 skill 被当成项目级文件送进 `onUntrusted`，于是对话开始后又弹出一次信任框（框里显示 `../../../../../../.sid-code/skills/create-bug-skill/SKILL.md`）。

结论：第二次弹窗不是「审批没在开头集中做」，是一个越界扫描的 bug。用户级 skill 本来就不该进信任门。

## 放弃了什么（以及为什么不选）

- 把动态发现的未信任 skill 也挪到启动时统一审批：动态发现的本意就是不在启动时全量扫子目录，提前审批就得启动时全量扫，正好违背这个设计。而且本例的目录根本不该被扫到，挪审批时机掩盖了越界。
- 在信任门里把 `getSidHome()` 下的路径豁免掉：只能修症状，cwd 外的其他祖先目录（比如 `~/Code/.sid-code/skills`）照样会被越界扫进来。
- 只修起点不加硬边界：起点的修正只覆盖「路径就是目录」这一种情况；有了硬边界，循环的终止不再依赖相等判断（符号链接、尾斜杠）。

## 拿什么证明它生效了

- 同类排查：cwd=`~` 时 `discoverSkillDirsForPaths([~/x.md], ~)` 修复前返回 `[~/.sid-code/skills]`，修复后返回 `[]`；新增用例经变异自证（去掉用户层排除即红 14 pass / 1 fail）。
- 其余向上遍历点（`getExtensionScanDirs`、`TrustManager.findRecord`、`JitContextManager` 的 `isInsideProject`、`findCLAUDEmd`）已逐个核对：前三者有家目录或项目根硬边界；`findCLAUDEmd` 有意走到文件系统根（对齐 CC 读祖先 CLAUDE.md），不进信任门，不属于本缺陷。
- 修复前用真实路径复现：`discoverSkillDirsForPaths([cwd], cwd, new Set())` 返回 `["/Users/zhourusheng/.sid-code/skills"]`。
- `bun test ./packages/core/tests/skill/dynamic-conditional.test.ts`：14 pass / 0 fail，新增两条用例（cwd 本身不越界、目录路径检查自身）。
- 变异自证：把两处改动还原成旧代码，新增两条用例都变红（12 pass / 2 fail），恢复后转绿。
