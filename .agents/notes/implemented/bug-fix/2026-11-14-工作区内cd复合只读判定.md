# 工作区内 `cd` 复合只读判定（B3）+ `git worktree`/`git grep` 只读细分（B8）

## 决定了什么

PR-2 把「`cd <工作区内> && 只读主体` 每次都弹确认」这条浪费补上，同时放开两条纯读 git 子命令。
方案里的 B3 / B8：

**B3：新增 `permission/readonly-compound.ts` 的 `judgeReadOnlyCompoundBash`，接入
`permission/checker.ts` 的新 Step 5.6。** `isReadOnlyCommand` 是**不带上下文的纯函数**，
`cd` 一律判非只读（这是对的，它被 5 个消费者共用），但权限层知道会话 cwd 和工作区边界，
可以补回「除了切目录之外全是只读」的那一半：

- 只接受 `&&` 与 `;`（含换行）连接。`||` 的失败分支、后台 `&` 的并发执行、子 shell / 命令替换
  里的 cd 都让「命令实际在哪个目录跑」不可静态确定，一律不放行；
- cd 目标必须**字面量**（复用 PR-1 的 `NON_LITERAL_PATH`，`~`/变量/通配/转义全拒）、
  **在工作区内**（`PathValidator.isWithinWorkingDirectories`，含 realpath 与 `/add-dir` 白名单）、
  且**不属于别的仓库**（复PR-1 的 `resolveGitRepoTrust`：`foreign` / `bare` 拒，`own` / `none` 放行）；
- 主体单元仍逐段用 `isReadOnlyCommand`；含 git 段时**复用** `judgeReadOnlyGitInOwnRepo`
  （仓库归属 + 剥 `-C` + 前导变量白名单一套口径都不重写）；
- `cd` 之后的**相对路径读重定向**（`cat < in.txt`）不放行：权限层的路径校验按起始 cwd 算，
  与 shell 里 cd 之后的实际含义不一致，静态判不准；
- 放行出口复用 `allowAtToolLevel`，所以 plan / deny-write 的模式硬约束照旧生效
  （工具说「我是只读」只能跳过默认 ask，不能跳过模式约束）。

**`;` 与 `&&` 的差别必须保留**，这是 B3 里唯一容易做错的地方：`cd X && git log` 在 cd 失败时
整条链停下，而 `cd X; git log` 会在**原目录**继续跑。所以用候选 cwd 集合跟踪：
`&&` 用「解析结果」替换集合，`;` 把失败路径的候选并回来；含 git 的单元要对**每个**候选
都判一次仓库归属，集合上限 16（超出判非只读，真实 cd 链不会这么长）。

**`splitCommandStructure` 的 `break` 细分成 `boundary`**（`start` / `&&` / `||` / `;` / `&` / `\n`）。
它原来把四种分隔符压成同一个 `"break"`，`&&` 与 `;` 的 cwd 语义差别在上层根本看不见。
既有消费者只用 `stages`，新增字段向后兼容；`shell-parser.test.ts` 的「两份实现同口径」
一致性断言不受影响。

**B8：`git worktree list` 与 `git grep` 按参数细分，而不是加进只读子命令集合。**
- `git worktree` 只有 `list` 是读（`--porcelain` / `-v` / `--verbose` / `-z`），
  `add` / `remove` / `prune` / `move` / `lock` / `unlock` / `repair` 都改状态；
- `git grep` 有**两个能执行任意程序**的 flag：`-O<orderfile>` 与 `--open-files-in-pager[=<pager>]`。
  直接把它放进 `READ_ONLY_GIT_SUBCOMMANDS` 等于开一个任意代码执行口子。所以用 flag 白名单：
  认识的只读 flag 才放行，`-f` / `--no-index` / `--untracked` / `--pathspec-from-file`
  也**刻意**不放行（见 rejected Note）。

## 放弃了什么（以及为什么不选）

**不在 `isReadOnlyCommand` 里放宽 `cd`。** 它被并发安全判定、失败级联、轨迹回写等 5 个消费者
共用；在那里放宽会连带改变「并发分区」和「cwd 回写」的语义。补回只发生在权限层的 Step 5.6，
纯函数口径一行没动（`isReadOnlyCommand("cd /repo && ls")` 仍是 `false`）。

**不做「单个乐观 cwd」的简化实现（即只跟踪最后一次 cd）。** 方案原文是「`;` 时对 cd 前后两个
cwd 都判一次本仓」，单值实现会漏掉 `cd A; cd B; git log` 里「A 失败、B 相对原目录成功」
这条分支（`start/B` 不在候选里 → 可能放行一个在 `start/B` 的 git 操作）。用集合更保守，
代价是每多一个候选多一次 stat，实测无感。

**不放开 `git ls-remote`**，也不放开 `git grep -f` / `--no-index` / `--untracked` /
`--pathspec-from-file`。前者的理由是网络请求与凭据提示取决于部署环境，后者是绕开权限层路径校验
（等 B5 落地再放开）。四条否决理由都单独记在 `rejected/feature/` 的 Note 里。

**不给「裸 `cd` / `cd -` / `cd ~`」做特殊处理。** 它们都判非只读、落确认。`cd` 无参数回 home、
`cd -` 回上一个目录都可能离开工作区，静态判不准；为它们写特例的收益（一个从未在轨迹里出现的形态）
不值这个复杂度。

**不改 `Step 5.5` 的既有顺序。** 5.6 只在「工具 passthrough 且 PR-1 的 git 边界没有放行」时进入。
工具说 allow 时仍然先走 5.5（含它的 git 边界判定），避免两条路径对同一条命令给出不同结论。

**没有做「cd 之间的 cwd 链去重」优化。** 候选集合理论上随 `;` 连接的 cd 数量指数增长，
用 16 的上限截断（超出判非只读）而不是做符号化推导——真实命令的 cd 链极少超过 3 段。

**与方案文本的三处差异**（都按实测为准）：

1. 方案 §4.3 写的函数名是 `isReadOnlyBashForPermission(command, ctx)`。实现取名
   `judgeReadOnlyCompoundBash`，与 PR-1 的 `judgeReadOnlyGitInOwnRepo` 对齐，
   返回 `{applicable, readOnly, reason}` 而不是纯 boolean——`reason` 要进 PERMISSION 日志，
   否则「为什么没放行」只能靠猜。`applicable: false` 对应方案里「不接管」的那一类。
2. 方案说 `git grep -f <file>` 的路径「交给 B5 校验」。B5 尚未落地，本 PR 保守判非只读，
   等 B5 把路径校验做进 `isReadOnlyCommand` 之后单独放开（否论证已记在 rejected Note）。
3. 方案说「`;` 分隔时对 cd 前后两个 cwd 都判一次本仓」。实现用的是候选 cwd 集合
   （`&&` 替换、`;` 合并失败路径），比「两个值」更保守——多段 `;` cd 时不会漏掉中间分支。

**连带修正一处既有测试的过期前提**（B3 是有意的契约变更，不属于「改断言凑绿」）：
`allow-list-pipeline-filter.test.ts` 里 `cd <工作区内> && tail -5` → `cd /etc && tail -5`。
前者在 B3 之后会**合法地**走只读放行（与 allow 规则无关），用它测「不经 allow 放行」已经不再成立；
换成工作区外的 cd 后，两段仍没有一段命中 allow，且只读路径也不接管，守的还是同一件事。

**一处由既有测试促成的实现补强**：`git-readonly-boundary.test.ts` 的「两步绕过：先 cd 到异仓
（单独一条），再裸 git → ASK」在我第一版实现下变红——`cd <工作区内的嵌套异仓>` 被放行了。
这正是 B4 的两步绕过链的第一环，所以补的是**实现**（cd 目标过 `resolveGitRepoTrust`），
不是改断言。
