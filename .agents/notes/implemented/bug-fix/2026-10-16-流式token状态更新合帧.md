# 流式 token 的 TUI 状态更新合帧到每 32ms 一次，流式阶段 CPU 降到约 40%

## 决定了什么

`StateBridge` 新增 `updateStreaming(patch)`：`current` 同步合并，`emit("change")` 合并到
固定窗口 `STREAM_FLUSH_MS = 32ms` 内最多一次。`app.ts` 里思考 / 正文两条流式回调的
**非首个** token 改走它，首个 token 和其他所有状态切换仍走立即 emit 的 `update()`。

三条约束（单测锁住，见 `packages/cli/tests/ui/state-bridge.test.ts`）：

- `current` 必须同步合并：app.ts 大量代码同步读 `bridge.current`。
- 任何 `update()` 先取消待发定时器，再 emit 含流式字段的 current，保证不乱序，
  状态切换也不被延后。
- 用固定窗口，不用 debounce：持续流式时每个窗口必出一帧。

起因：用户开了 5 个会话时风扇狂转，其中一个跑在 flash 模型上、思考很长的会话
持续占 70–86% CPU。tui 底座的 16ms 节流只节流写屏，每 token 一次的 React reconcile 一次都省不掉。

## 放弃了什么（以及为什么不选）

- **在 React 侧节流（useDeferredValue / 组件内节流）**：bridge 的每次 emit 都会让
  App 根组件 setState，在叶子组件节流时根组件已经 reconcile 过了，省不到大头。
- **debounce**：持续出 token 时会一直不刷屏，用户看到的就是卡住。
- **16ms 窗口**：150 tok/s 下每窗口只能合并约 2 个 token，收益减半。32ms 约 30fps，逐字输出肉眼分不出。
- **把 updateState 整体改成合帧**：会延后工具开始、流式结束这类状态切换，
  也会和同步读 `bridge.current` 的代码交错，出现「先看到工具卡片、后补出最后几个 token」的乱序。

## 拿什么证明它生效了

基准 `scripts/perf-stream-bench.sh`：mock OpenAI 兼容端点 + 真实 TUI 跑在 PTY 下，
3000 思考 + 600 正文 token，150 tok/s，`NODE_ENV=production`，只采流式窗口：

| | emit 次数 | 流式窗口平均 CPU% | 流式期 CPU 秒 |
| --- | --- | --- | --- |
| 合帧前（2 次） | 3615（与 token 1:1） | 29.6 / 24.2 | 7.07 / 5.95 |
| 合帧后（2 次） | 723 | 10.5 / 10.7 | 2.45 / 2.42 |

- 屏幕上最终正文前后逐字节一致（3001 字节，结尾相同）。
- 单测变异自证：把 `updateStreaming` 改回同步 emit 后，4 条新测试红 3 条；恢复后 7/7 绿。
- 基准踩过的两个坑，都会让数字假低：① expect 用 `sleep` 不读 PTY，造成写阻塞背压，
  CPU≈0、profile 72% 停在 native write；② 不设 `NODE_ENV=production` 会加载 React development 构建。

未验证：真实网关 + 真实模型下的端到端数字（mock 的 token 粒度是 1 token/chunk，真实网关
有时会多 token 一个 chunk，那种情况下收益更小）。
