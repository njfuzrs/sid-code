# git stash/branch/tag/remote/reflog 从「按子命令名判只读」改为「按参数白名单判只读」

## 决定了什么

`READ_ONLY_GIT_SUBCOMMANDS` 此前按**子命令名**判只读，把 `stash` / `branch` / `tag` /
`remote` / `reflog` 五个有写形态的子命令整体放了进去。被判只读后
`BashTool.checkPermissions` 直接返回 `allow`（checker Step 5.5），default / acceptEdits
模式下不经确认就执行 —— 而 prompt 红线 RL-001 明写禁止 `git stash`，代码比 prompt 松。

本次：

- 五个子命令移出 `READ_ONLY_GIT_SUBCOMMANDS`，在 `isReadOnlyImpl` 的 git 分支里显式分派；
- 各新增一个**读形态白名单**判定（`read-only-validation.ts` 导出
  `isReadOnlyGitStash` / `isReadOnlyGitBranch` / `isReadOnlyGitTag` / `isReadOnlyGitRemote` /
  `isReadOnlyGitReflog`），未知 flag、未知动词、没有列表开关却带位置参数的一律判写；
- 先滤掉 shell 的 fd 复制记号（`2>&1`），parser 会把它留在 args 里当位置参数，
  不滤会把 `git branch -a 2>&1` 这种纯读命令判成写；
- 把 `--output` 检查提到子命令分派**之前**：五个新分支走 `continue`，写在后面会被跳过。

判据是 `边界-仅prompt` → 下沉为 `边界-强制`：prompt 禁止的写操作，代码层至少要和 prompt
一样严（不再自动放行），是否进一步收到 deny 留给红线对账（方案 §7 的 B2）。

## 放弃了什么（以及为什么不选）

- **把写形态加进 `GIT_DANGER_PATTERNS`（Step 2 危险命令）**：危险层的语义是「高危、标红」，
  `git branch -m` 不属于这一档；而且只修了权限这一个调用点，并发分区、git-status 缓存失效、
  改动已读文件告知等其余 7 个调用点照旧误判。
- **五个子命令整个移出只读集**：311 次纯读调用（`branch --show-current` 一项 183 次 / 85 会话）
  会全部转确认，「更快」的损失远大于收益。
- **只在 `checkPermissions` 里另写一套更严的判定**：两套口径会分叉；`git stash` 后
  git-status 缓存不清、改动告知被跳过这两个顺带 bug 也修不到。#614 已因口径问题专门拆出
  `isReadOnlyIgnoringCd`，不再加第三套。
- **靠 prompt 红线约束**：这正是本条目要消除的形态（`边界-仅prompt`）。

## 拿什么证明它生效了

**单测 + 权限端到端**（`packages/core/tests/tool/git-ref-subcommands-readonly.test.ts`，29 用例）：

- 五个子命令的读/写形态表格、`-C <dir>` / `--no-pager` 前缀、复合命令、fd 复制记号、
  `--contains` 值省略规则、§2.4 轨迹里的真实读/写形态原文；
- 端到端用 `PermissionChecker(defaultConfig())`，工具对象作 `check()` 的**第二个参数**，
  default 与 acceptEdits 两档都断言：写形态 `needsConfirmation === true`，读形态 `allowed === true`。

**变异自证**（改坏 → 看红 → 逐字节恢复）：

- `isReadOnlyGitStash` 恒返回 true → 9 条断言红（含两档端到端），恢复后 29 pass；
- `isReadOnlyGitBranch` 恒返回 true → 8 条断言红，恢复后 29 pass。

**回放验收**（本机轨迹，会话 id ≥ 20261024，`session.traj` 的完整命令，13,107 次 bash 调用）：

- 命中五个子命令 337 次：修复前全判只读；修复后 315 读 / 22 写；
- 22 次转确认里 20 次是真实写形态（`branch -m` ×16、`branch -d` ×2、`branch -f` ×1、
  `stash push` ×1），另 2 次是方案允许的命令替换例外（`git branch --contains $(…)`，
  权限层已由 Step 2「命令替换注入」兜住）；
- **没有一次纯读形态被误判成写**。

（同一批数据用 `events.jsonl` 的 `input_summary.command` 跑时命中 333 次，但其中 158 条
被该字段的 200 字符上限截断 —— 长复合命令被切成 `git branch --show-cur` 这种，
截断样本不能用来下判定结论，故改用 `session.traj`。）

**门禁**：`bun run affected-tests:run`（1291 pass / 0 fail）、全量 `bun test`、
`make build`、`lint`、`format:check`、`lint:boundary`、`lint:command-system`、
`lint:legacy-tool`、`typecheck:gate` 全绿。

**牺牲了什么（已在方案 §5 点破）**：default / acceptEdits 下约 5.5% 的这类 git 调用会多一次
确认，主要是 `git branch -m`；无头（非交互）模式下 ask 会转 deny，用户脚本里依赖
`git stash` / `git branch -m` 的会从「静默执行」变成「被拒」。这是本修复的目的，
release note 需要写明，并给出 `Bash(git branch -m *)` 这类 allow 规则的写法。
外部基准通道全部跑在 `--dangerously-skip-permissions`（或定义里不含这五个子命令），
分数不受影响。
