# 短回执工具新增 `full` 档：折叠判据从「一层」补成「两层」，并修掉换行丢字

## 决定了什么

### 1. `ToolResultDisplayMode` 新增 `"full"` 档（保留正文且不做任何行数截断）

`enter_worktree` / `exit_worktree` 声明 `readonly resultDisplayMode = "full"`。

### 2. 类型定义收归一处

`ToolResultDisplayMode` 的权威定义搬到 `packages/core/src/llm/types.ts`（`ToolResultBlock`
是它的落盘处），`packages/core/src/tool/types.ts` 改为 re-export，既有 import 路径不变。

### 3. 打通四层

- 数据层 `history-adapter.ts`：`full` 原样透传；**错误结果也保留 full**（原先 `isError ? undefined`
  会把 full 一起降级，多行错误又被折回 3 行）。
- 组件层 `ToolResultDisplay.tsx`：新增 `unlimited?: boolean`，为 true 时连
  `useExpandedMaxLines` 算出的基线也覆盖为 `undefined`（hook 仍无条件调用，只是覆盖结果）。
- `ToolMessage.tsx`：`unlimited={displayMode === "full"}`。
- 类型面：`ui/types.ts`、`ToolMessage`、`ToolGroupMessage` 三处的内联联合同步加 `full`。

### 4. 修 `wrapLinesToWidth` 的量纲错配（同一后果的另一条成因）

`SlicingMaxSizedBox.tsx` 的换行函数原先用 `stringWidth(text)`（视觉列）当循环条件、
却把 `maxColumnWidth` 当**码点索引**传给 `slice`。含 CJK 的行视觉宽度约是码点数的 2 倍，
于是「88 列」切出的段实际宽 **126 列**（实测），仍大幅超宽；超宽行再交给渲染器时，
中间那段文本被吃掉——`enter_worktree` 的「此后写文件请用 <worktree 路径>」整句消失。

改为按码点累加 `stringWidth` 切段（`Array.from` 保证 emoji/代理对不被拆开；
单字符宽于上限时也照常输出，避免窄终端死循环）。

## 放弃了什么（以及为什么不选）

- **调大全局 `DEFAULT_MAX_LINES`（3 → 6/8）**：它是所有工具结果共用的兜底，调大等于让
  每张卡片都变长，而 #808/#810 的目标正是别让历史撑爆主屏；且数字是跑步机——总有
  「再多一行又超了」的工具，边界永远要靠猜。`full` 把「必须完整可见」变成可声明的意图，
  而不是全局放宽。
- **把 `enter_worktree` 改成 `compact`**：compact 的默认态是**零行正文**（只在标题行给结果规模），
  路径语义提示会彻底消失，比折 3 行更糟。它的正文只有 6 个视觉行，折它本身没有收益。
- **组件层按行数阈值自动判「短回执不折」**：省掉逐个声明，但把判据留在渲染层，
  与 #813 已确立的「判据在数据层、渲染层只执行」冲突；而且阈值对所有工具生硬生效，
  一个恰好 7 行的长输出会被误放行。
- **让 `"full"` 也进 compact 的「少量行降级」判据**：降级的结果是 `displayMode = undefined`，
  渲染层随即退回 3 行兜底——等于什么都没修。已用测试锁死这条。
- **把类型定义留在 `tool/types.ts` 两处并存**：本次缺陷的成因之一就是 `ToolResultBlock`
  另写了一份内联联合，新增档位时那份不会跟着变（工具声明了 `full`、UI 收到时被类型收窄回
  旧集合）。搬定义 + re-export 一次性消除漂移面。

## 拿什么证明它生效了

```text
bun run typecheck:gate   → 当前 62 处错误 / 基线 62 处，✓ 无新增类型错误
make build               → 编译成功，产物自检全绿（git-status 锚点 / 止损阀 / skill 内嵌 / ripgrep / review）
bun test ./packages/cli/tests/ui/tool-result-display-mode-audit.test.ts   → 42 pass 0 fail
bun test ./packages/cli/tests/ui/components/messages/ToolMessage-full.test.tsx → 4 pass 0 fail
```

`ToolMessage-full.test.tsx` 的三条断言构成本改动的**变异自证**：

1. full 档：归一化空白后整段回执（含「此后写文件请用 … 下的路径。」）全部上屏，整帧不含「已折叠」；
2. 对照组：**同一份正文**只把 `displayMode` 换成 `undefined` → 出现「已折叠」且路径提示不上屏。
   没有这条，第 1 条可能是恒绿（折叠逻辑压根没生效也照样通过）；
3. 错误态同 full 也完整可见（`tool/types.ts` 硬约束 ②）。

修 `wrapLinesToWidth` 的直接证据（隔离渲染 `SlicingMaxSizedBox`，`maxColumnWidth=88`）：

```text
修前：[0] w=126   ← 切出来的段仍超宽 43%，渲染器再处理时丢字
修后：[0] w=63 / [1] w=24 / [2] w=55   ← 每段都 ≤ 88，内容一字不丢
```

选测 `bun run affected-tests:run`（3 个目标、551 个文件、7122 条）：7107 pass / 6 fail。
6 条失败全在 `packages/cli/tests/render-port/terminal-modes.test.tsx`（raw mode 计数开关，
spawn 子进程型），均卡 bun 默认 5s 单测超时；该文件只 import `bun:test` / `node:path` /
跑 fixture 的子进程，与本次改动的模块无依赖，单跑 **16 pass 0 fail** —— 并发负载下的 flake，
非本改动引入。

## 补一句：为什么审计当时没拦住

`EXPECTED_UNDECLARED` 把 `enter_worktree` / `exit_worktree` 判为「短回执，不折」，
但**「不折」只被写进了注释，没有任何机制落地**。审计对账的是数据层的
`resultDisplayMode` 字段，而折行发生在组件层的 `maxLines=3` 兜底 —— 那一层不在任何断言的
观测面内。本次除了加 `full` 档，还把这条认知写进了白名单注释（「进 `EXPECTED_UNDECLARED`
= 接受组件层 3 行兜底截断」），并新增整帧渲染测试把组件层纳入断言。下一个短回执工具
若被塞进未声明清单，会同时踩到注释和一个能红的行为测试。
