# 本轮进行中的输入不再被静默丢弃：提交路由收口到 routeSubmit

## 决定了什么

`App.tsx` 的 `handleSubmit` 首行原为 `if (isSubmittingRef.current) return;`。
`dispatchInput` 会 await 整轮 agent loop（`onUserInput → tuiAgentLoop → for await submitMessage`），
所以第一轮执行期间 `isSubmittingRef` 恒为 true，此间所有提交都在这一行被 return：
输入框已被 `tb.submit()` 清空、没有入队、无「已排队」提示、本轮结束也不发。
官网 `use/interactive.md`「模型正在输出时你还能打字 … 会排队」在用户手动发起的轮次里全部失效
（只有队列 drain 发出的轮次不经 handleSubmit，才碰巧能排队）。

改动：

- `command/streaming-gate.ts` 新增纯函数 `routeSubmit(text, commands, {streaming, submitting})`，
  返回 `enqueue` / `dispatch` / `dispatch-nested`。「本轮进行中」= `streaming || submitting`，
  再交给既有的 `canRunDuringStreaming` 判可否插队。
- `App.tsx` 删除提前 return，按路由分流。`dispatch-nested`（轮内 immediate 命令，如 `/model`）直送但
  **不置位也不清位** `isSubmittingRef`——否则其 finally 会清掉外层那轮的提交位，后续输入绕过入队。
- `src/ui/CLAUDE.md` L4-A 把「流式中多条输入排队」从 ⚠️ 待补改为 ✅，并记下这条禁令。

## 放弃了什么（以及为什么不选）

- **只删掉那行 return、仍只看 streamingState**：派生态在「回车 → isLoading 置位」之前、以及工具批次之间
  可能短暂为 Idle，此时会直送并发起第二轮并发 agent loop，与正在跑的轮次抢写同一份 ctxMgr。
  `submitting` 信号正好覆盖这些空窗，所以两个信号都要看。
- **让 dispatchInput 不 await 整轮（fire-and-forget）**：改动面跨 app.ts 的错误分类、ESC 回填、
  会话硬顶等大量依赖「await 到整轮结束」的逻辑，风险远大于收益。
- **判据留在组件里内联**：不可单测，旧 bug 正是这种「判据散在 useCallback 里没人测」的形态；
  提成纯函数后可用变异用例锁住。

## 拿什么证明它生效了

- `bun test ./packages/cli/tests/command/streaming-gate.test.ts` → 17 pass / 0 fail。新增 `routeSubmit` 4 组，
  其中 `{streaming:false, submitting:true}` 断言为 `enqueue`——只看 streaming 的实现会返回 `dispatch`，
  旧实现会直接丢弃，两种变异都会让它红。
- `bun test ./packages/cli/tests/command/ ./packages/cli/tests/ui/` → 1548 pass / 0 fail。
- `make build` rc=0，`will always be undefined` 告警 0 条。
