# 危险命令从「原文正则」改成「token 结构判定」，heredoc 正文按接收者归属

## 决定了什么

修 2026-10-24 PR #432 收尾时发现、当时未处理的一类缺陷：`hardcodedDangerCheck` 用正则
匹配**命令原文**，分不清「程序在执行什么」与「参数里写了什么字」。

改动四处：

1. **新增 `packages/core/src/permission/dangerous-command.ts`**：把 10 条 critical 从
   `DANGEROUS_PATTERNS` 迁到结构化判定，按 `expandShellCommand()` 已给出的
   `{ program, args }` 判：
   - `rm` / `rmdir`：递归选项（`-r`/`-R`/`-Rf`/`--recursive`）+ 危险路径集；
   - `dd`：`if=/dev/(zero|random|urandom)` 不看参数顺序，`of=/dev/<块设备>`；
   - `mkfs` / `mkfs.*`；
   - 写入块设备：重定向目标与 `tee`/`cp`/`mv`/`install` 的块设备参数；
   - `python* -c` 的那**一个**参数含 `exec(`、`perl -e` 的那个参数含 `system(`；
   - 「下载并执行」「base64 / xxd 解码执行」改成判**同一管道**内的前后段关系。
   危险路径集：`/`、homedir、`*`、前缀为 `/` 或 homedir 的 `/*`、根的直接子目录；
   **刻意不收** CC 的「任意深度 `/*`」（否则 `rm -rf build/*` 会变硬拒）。
2. **新增 `packages/core/src/permission/shell-structure.ts`**：`extractHeredocBlocks`
   （heredoc 正文剥离）+ `splitCommandStructure`（按管道分组）。heredoc 正文的归属由
   **接收者**决定——`bash <<EOF` / `cat <<EOF | bash` 是脚本（递归展开判危险），
   `cat > f <<EOF` 是数据（不参与匹配）。
3. **`shell-parser.ts` / `shell-command-variants.ts`**：`splitCompoundCommand` 先剥离
   heredoc 正文；`expandShellCommand` 改用 `splitCommandStructure`，并新增 `pipelines`
   与 `commands[].text` 两个输出（结构化判定的输入契约）。
4. **`bash-security.ts` 的 `validateNewlines`**：先剥离 heredoc 正文再判。
   heredoc 写文件是最高频的写文件形态，正文里的换行不是「分隔出的第二条命令」。

`high` / `medium` 模式（`sudo`、`chmod -R`、`git reset --hard` 等）**保持原正则不变**：
它们误报的后果只是「多一次确认」，有出口；全文改判据的回归面远大于收益。
`Fork 炸弹` 也保留正则（实测 `echo ':(){ :|:& };:'` 不误报，token 化无收益）。

## 放弃了什么（以及为什么不选）

- **给 `git commit -m` / `gh pr create` 加白名单**：只堵已知形态，`git tag -m`、heredoc、
  `printf > file` 会再冒出来，而且完全解决不了漏报。
- **匹配前把所有引号内容剥掉**：`rm -rf '/'` 会变成 `rm -rf `，漏报更严重。
- **把 critical 降级为 high（可确认）**：误报从「不能批准」变成「每次都要点」，噪音照旧，
  漏报也照旧。降级还等于给真正的危险命令开了一个「点一下就过」的出口。
- **只修正则（加 `-R`、引号、长选项）**：正则表达不了「这是程序名还是参数值」，误报根因还在，
  每补一种形态正则更难读。这一条是 §4.2 里最容易被重新提议的，所以单列。
- **照搬 CC 的「任意深度 `/*`」危险路径集**：会把 `rm -rf build/*` 变成硬拒（当前放行），
  而那是项目里最常见的清理写法。只取 `/`、homedir、`*`、前缀为 `/` 或 homedir 的 `/*`、
  根的直接子目录。
- **把 critical 改成 ask**：CC 判危险返回 ask，我们是硬拒。保留硬拒更安全——但代价是
  误判时用户完全没有出口，所以本次把误报面一起修掉，而不是靠降级换出口。
- **顺带 token 化 high/medium**：见「决定了什么」最后一段。
- **管道级数据流追踪 / 同命令 cd 追踪 / `find -exec` 递归解析**：成本高，本次不做，
  三条残留列在下面。

**已知残留（要修需额外机制，本次不做）**：

| 形态 | 为什么覆盖不到 |
| --- | --- |
| `echo / \| xargs rm -rf` | rm 的 args 里没有路径（路径在上一段），要管道级数据流追踪 |
| `find . -exec rm -rf {} +` | program 是 find，rm 只是它的参数，要递归解析 `-exec` |
| `rm -rf "$DIR"` | 变量静态不可知。只有「以 `*` 结尾」才按危险处理（fail-closed），
  否则项目里常见的 `rm -rf "$BUILD_DIR"` 会变成无出口的硬拒 |

**行为收紧（有意，写在这里防回退）**：

- `curl x | sudo bash`：修前是 high（需确认），现在命中「下载并执行」→ critical 硬拒
  （sudo 已被 wrapper 剥掉，后段就是 bash）。
- `rm -rf /tmp`、`rm -rf /usr/*` 之外，`rm -rf /tmp` 因「根的直接子目录」变硬拒
  （修前放行）；`rm -rf /tmp/x` 仍放行。
- `rm -rf "$DIR"/*`（含未展开变量且以 `*` 结尾）按危险处理。

**牺牲的方向**：更安全 ↔ 更少返工。口径放宽能减少误报（更少返工），但漏报是灾难；
口径收紧能减少漏报（更安全），代价是 `rm -rf /tmp` 这类合法清理被拒。本次选「更安全」，
把「不收任意深度 `/*`」当作对误报的补偿，并用矩阵测试把两半都钉住。

**一处契约变更（需要 review 知道）**：`packages/core/tests/permission/non-interactive-denial-reason-visibility.test.ts`
里 A11 那条 heredoc 用例的期望成因从 `injection` 改成 `需要用户确认`。
原因：那个 injection 命中本身就是误报（换行在 heredoc 正文里），剥离后不再命中；
用例守的「拒绝必须带可行动成因」不变，只是不再把假成因当期望值。

## 拿什么证明它生效了

**探针实测**（`PermissionChecker.check`，`permissionMode=always-allow`，macOS 本机）：

- 修前：19 条误报全部 `硬拒(critical)`；21 条漏报里 18 条 `放行`。
- 修后：19 条误报全部 `放行`；漏报里 `rm -rf '/'` / `"/"` / `/*` / `//` / `-Rf` /
  `--recursive --force` / `$HOME` / `${HOME}` / `/usr` / `/etc`、`dd of=… if=…`、
  `mkfs -t ext4`、`curl x | sudo bash`、`base64 -d | sh`、`xxd -r | bash` 全部
  `硬拒(critical)`。
- 唯一没修的是文档 §4.1 明确列出的两条残留（`xargs`、`find -exec`），矩阵里断言
  「当前放行」并在用例名标注「已知残留」。

**回归矩阵** `packages/core/tests/permission/dangerous-command-matrix.test.ts`：106 条，
覆盖 §2.1 A/B/C/D 组（放行）、§2.2 A 组（硬拒）、§2.2 C 组（继续放行）、
必须保持硬拒的六条对照、heredoc 数据/脚本两种归属、high 仍可确认、
以及「`splitCompoundCommand` 与 `splitCommandStructure` 扁平结果一致」的防漂移断言。

**变异自证**（两次，都看它报了什么而不是只看退出码）：

1. `detectStructuredCriticalDanger` 临时 `return null` → 矩阵 C/D/E/F/G 组大面积变红
   （`rm -rf '/'`、`dd of=…`、`mkfs`、`curl|sh`、`python -c exec` 等），恢复后 106 pass。
2. `extractHeredocBlocks` 临时不剥离 → H/L/O 三组 8 条变红
   （heredoc 正文当数据的放行、正文当脚本的硬拒、`extractHeredocBlocks` 单测），
   恢复后 106 pass。

**门禁**：

- `bun test ./packages/core/tests/permission/ ./packages/core/tests/tool/bash-write-targets.test.ts ./packages/core/tests/tool/bash-redirect-extraction.test.ts`
  → 992 pass / 0 fail。
- `bun run lint` / `format:check` / `lint:boundary` / `lint:command-system` 全绿。

  （worktree 里先踩了一次假阳性：`node_modules` 软链到主仓导致同一模块两种解析路径，
  报 6 项与本次改动无关的 `tests/skill/*` 错误；删软链重装后归零。）
