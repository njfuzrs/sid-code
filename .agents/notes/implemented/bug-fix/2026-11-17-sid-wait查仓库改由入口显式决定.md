# sid-wait 查哪个仓库由入口显式决定，不再让 gh 按 cwd 解析占位符

## 决定了什么

`sid-wait gh-pr <n>` 原先用 `gh api repos/{owner}/{repo}/pulls/<n>`，`{owner}/{repo}` 由 gh
**按 cwd 的 git 仓库**填充。cwd 是会话 cwd（`getCwd()`），会随会话里任何一次 `cd` 漂移 ——
于是在 `docs-research` 目录下等 sid-code 的 PR，gh 拿 sid-code 的 PR 号去查 `docs-research`，
换回一个**真 404**，而 PR 号与 token 都正常。错误文案又把方向指向「PR 号不存在 / 无权限」，
排查代价极高；更危险的形态是 cwd 所在仓库恰好有同号 PR，于是**静默等错对象**。

四处改动（一条链）：

1. **`--repo <owner>/<repo>` 进原语参数**（`sid-wait.ts`）：`parseSidWaitCommand` 从一条正则
   改成按 token 解析，`--repo` 与 `--interval` 顺序任意、各最多一次；`SidWaitGhPrSpec.repo`
   透传到两个入口。非法值（`sid-code`、`a/b/c`）不算原语，照旧走「误用回执」。
2. **仓库在 spawn 之前定死**（`bash.ts` / `monitor.ts`）：入口先调 `resolveSidWaitRepo()`
   ——`--repo` 优先，其次 `git -C <getProjectRoot()> remote -v` 里**按 host 筛 github.com**
   的第一条 remote；解析不出就直接回执可行动错误（含 `--repo <owner>/<repo>`），
   不启动注定失败的任务。基线用 `getProjectRoot()`（会话启动目录）而不是 `getCwd()`。
3. **endpoint 改完整路径**（`createGhCliRestClient`）：`repos/<owner>/<repo>/pulls/<n>`，
   占位符彻底退场。解析失败时抛 `SidWaitFatalError`，`runSidWaitGhPr` 立刻终态，
   **不走 2^n 退避**（否则用户要等三分钟才看到「请用 --repo」）。
4. **失败结论点名仓库**：`rest-fatal` 的 summary 现在写「查询仓库 `o/r` 的 PR #N 被拒绝」
   并给出 `--repo` 出口；前置失败直接原文透出可行动文案。中英提示词也把原先教错的
   `cd <dir> &&` 前缀改成「等别的仓库必须带 `--repo`，`cd` 前缀不会被执行」。

## 放弃了什么（以及为什么不选）

- **只把 `getCwd()` 换成 `getProjectRoot()`**：最省事，但会话本身可能在 `docs-research`
  启动（本仓的真实工作流就是这样），此时项目根也是 `docs-research`，缺陷原样保留。
  它只能算半个修复。
- **保留 gh 的占位符、只改 cwd**：gh 的仓库挑选规则（多 remote / fork / worktree）对用户
  是黑盒，无法断言它一定挑对。缺陷之所以难归因，正是因为「查了哪个仓库」不可见。
  显式路径 + 显式文案把这件事变成可读事实。
- **解析不出时回退到会话 cwd**：这正是缺陷本身。宁可给一条「请用 `--repo`」的确定性失败，
  也不要猜一个仓库然后静默等错对象 —— 假 404 至少会报错，静默等错会报出与本仓无关的
  merged / check-failed。
- **让客户端自己发现「解析结果可能是错的」并二次校验**：客户端没有「目标仓库应该是什么」
  这个信息；`--repo` 是唯一可信来源，其余只能靠会话启动目录的 remote 兜底。
- **把仓库签进等待对象签名（`gh:pr:<n>` → `gh:pr:<owner>/<repo>#<n>`）**：会牵动准入判定、
  `wait-subjects`、通知与 todo 闸门一整串，收益只是「同号不同仓库不再判重复」。
  当前修复已经消灭了「入口静默选错仓库」，签名不变是可接受的取舍。

## 拿什么证明它生效了

- **新增 `packages/core/tests/task/sid-wait-gh-cli.test.ts`（22 例）**：用假 `gh` 脚本
  断言 endpoint 原文，补上「`createGhCliRestClient` 此前零测试」的缺口。覆盖
  `--repo` 解析、三种 remote URL 形态、多 remote 按 host 筛、目录不存在 / 非 git /
  只有 gitee 三种失败、以及「解析失败时一次都不 spawn」（`ghCalls === []`）。
- **`sid-wait-entrypoints.test.ts` 新增 2 例**：断言 bash / monitor 两个入口传给 client 的
  `repo` 与 `cwd`——`cwd` 必须是 `getProjectRoot()`。这是缺陷的入口侧回归，
  解析函数的单测覆盖不到「入口到底传了什么」。
- **变异自证（两处，看到它真的红）**：
  ① 删掉 bash 入口的 `repo` 透传 → `Expected "njfuzrs/sid-code" / Received undefined`；
  ② 让 `requireRepo()` 退回 `"{owner}/{repo}"` → 4 例变红，其中「一次都不 spawn」
  直接暴露出 `ENOENT ... posix_spawn`。恢复后 38 例全绿。
- **门禁全绿**：`bun run affected-tests:run`（3155 pass / 0 fail，216 files）、
  `make build`（exit 0，`grep -c "will always be undefined"` = 0）、
  `bun run lint` / `format:check` / `lint:boundary` / `lint:command-system` /
  `lint:legacy-tool` / `typecheck:gate`（62/62，无新增）/
  `docs:gen-reference --check`、`bun run smoke`（42 例 42 通过）。
- **一处必要的契约同步**：`SidWaitMisuse` 新增必填 `suggestedRepo`，旧测试里那条
  `toEqual({ body, suggestedPr })` 的完整对象断言补上该字段——契约变更的必然后果，
  不是为凑绿改预期（typecheck 从 63 处回到基线 62 处）。
