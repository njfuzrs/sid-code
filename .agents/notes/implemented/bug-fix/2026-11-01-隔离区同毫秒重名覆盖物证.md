# sessions 根目录裸文件隔离：同毫秒重名时追加序号，不再静默覆盖前一份

## 决定了什么

`packages/core/src/config/startup-housekeeping.ts` 的 `quarantineStraySessionFiles()` 给隔离区文件名加的时间戳只到毫秒。两轮清理落在同一毫秒内时目标名完全相同，`renameSync` 会静默覆盖前一份物证，这正是该前缀本来要防的事。现在改成：目标已存在就追加 `-<序号>`，直到找到空位。

测试 `startup-housekeeping-orphans.test.ts` 里「同名裸文件二次出现时不互相覆盖」这条用例用 `setSystemTime` 冻结时钟，让两轮必然同毫秒。原来它撞不撞取决于机器快慢：macOS CI 机器快，会撞上，所以稳定红（main @ 66de22b6、PR #509 都红在这条）；本机慢，撞不上，所以恒绿。也就是说，它对这个缺陷原本是盲的。

## 放弃了什么（以及为什么不选）

- 时间戳精度提到亚毫秒（`performance.now()` / `process.hrtime`）：只是把撞车概率压低，不消除，而且同一轮里多个同名条目本来就拿不到不同的时间戳。
- 只改测试（两轮之间 sleep 1ms，或者给第二轮传不同的时间）：测试会变绿，但生产里的覆盖缺陷还在。属于为凑绿改测试前提。
- 随机后缀（uuid）：同样不会冲突，但文件名失去顺序信息，排查时不好看出先后。序号能保留先后。

## 拿什么证明它生效了

- 变异自证：把 `existsSync(dest)` 改成 `false && existsSync(dest)`（等于撤掉修复），冻结时钟版用例报 `Expected: 2 / Received: 1`，和 CI 失败完全一致。恢复后转绿。
- 冻结时钟之前，本机用变异版跑 30 次全绿：确认旧用例在慢机器上测不到这个缺陷。
- 修复版 `bun test ./packages/core/tests/config/startup-housekeeping-orphans.test.ts` 连跑 30 次，0 失败（26 pass）。
- `bun run affected-tests:run`：844 pass / 0 fail；`make build` 通过并自检通过；`bun run lint` 0 错误。
