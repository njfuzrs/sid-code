# side-call 不对恒思考模型下发 `thinking:{type:"disabled"}`，并给「丢弃了多少已产出内容」建两个互补口径

对应方案文档 `20260817-GLM-5.3思考阶段卡死…修复方案.md` 的 PR3（P0-5）/ PR4（P1-7）/
PR5（P1-6）/ PR6（P0-7）。四条合成一个 PR，因为它们共同回答同一个问题：
**「一次超时切断到底扔掉了什么」** —— PR3 是扔掉整条调用链的那个 bug，
PR4/PR6 是量它，PR5 是让下次排查不必再靠 `bun -e` 重放生产函数。

## 决定了什么

### PR3：恒思考模型收到「关思考」时，降级为**不下发** `thinking` 字段

`openai.ts applyDeepSeekThinking` 里，`params.thinking.enabled === false` 且模型恒思考时
不装配 `thinking` 字段（等价服务端默认=思考开启），而不是发一个必定被 400 拒绝的
`{type:"disabled"}`。降级语义照搬同文件 `applyToolChoice` 对 GLM `auto-only` 的处置。

「哪些模型恒思考」收进新模块 `llm/dialect/always-thinking.ts`，判据是**实测过的服务端拒绝**
（当前只有 `/^glm-5\.3\b/i` 一条），不做版本外推。用户侧出口是新增的 compat 位
`thinkingAlwaysOn` / `thinking_always_on`，用于网关改名（`origin-glm-5.3` 之类）匹配不到内置名单的情形。

**为什么不是「让 side-call 别关思考」**：`side-call-timeout.ts` 的注释写明关思考是为了
省 token + 不撞 side-call 硬超时，那个意图仍然有效。恒思考模型上"关思考"物理上做不到，
正确处置是**接受它会思考**，而不是让整条调用链失败。

**为什么不是「往 model-registry 加 glm-5.3」**：协议能力判定链根本不查注册表
（`classify.ts` 用 `/^glm/i` 正则兜底），加注册表条目治不了这个 bug。

### PR4 + PR6：丢弃量改成**两个视角互为对照**，而不是一个数字

| 视角 | 落点 | 覆盖率（实测） | 为什么需要它 |
| --- | --- | --- | --- |
| 消费方 | 新 `StreamRestart` 事件（`emitStreamRestart`） | 8%（24 次重开只到 2 次） | 它知道**内容块的结构**，能分清思考/文本/工具入参 |
| 传输层 | `retry` 遥测新增 `discardedChars` / `discardedThinkingChars` | 100%（24/24） | 它在**退避之前**发，不会被 watchdog 抢先杀掉 |

新增字段：`StreamRestartOutcome.discardedThinkingLength`（思考字符，是
`discardedTextLength` 的子集）与 `discardedToolJsonLength`（被截断的工具入参 JSON，
**改造前完全不可观测**）。四个消费者里的四份手写 `if (丢了才记) log.warn(...)`
收敛成一个 `recordStreamRestart()`：日志仍有条件（零丢弃不是警告），
**事件无条件发**（否则没有分母）。

PR6 侧在 `fallback.ts` 把 `hasYieldedContent` 这个 bool 扩成 `produced{chars, thinkingChars}`，
并让重试决策**读到**这个事实（当前仍照旧重试 + 打一条明确的代价日志，不改重试策略）。

### PR5：`BeforeModel` 采 `thinking` / `reasoning_effort`

`hook/types.ts` 与 `trace/builder.ts` 补字段位，`loop.ts` 传值，`collector.ts` 回填。
**每轮都记**（不像 system/tools 只记首次）：旋钮是逐轮可变的，只记首次等于记了一个会漂移的快照。

## 放弃了什么（以及为什么不选）

- **放弃照 PR4 原文实现（把 `accumulatedReasoning.length` 加进 outcome）。**
  方案文档 §2.7 的机制描述**经实测是错的**：它说思考被杀时 `discardedBlocks === 0`
  所以「一行不记」。实际跑生产 `processStream` 的结果是 `discardedBlocks=1 /
  discardedTextLength=1000`，**记了**。因为 provider 层把 `reasoning_content` 转成了
  `content_block_start{type:"text"} + text_delta`，内容块**已经存在**，只是 `type` 还没被
  `content_block_stop` 转成 `"thinking"`。照原文加 `accumulatedReasoning.length`
  会**双算**已成形的思考块。改成"按 `thinkingIndexes` 给已计入的字符分类"。

- **放弃「把 `stream_restart` 广播挪到退避之前」**（那样消费方也能 100% 收到）。
  行为变更：退避期间被用户 ESC 时，现状是已产出内容**保留并交付**，挪到前面会变成
  作废。这是用户可见的取舍，不该夹在一个观测类 PR 里做。改为在传输层另开一个 100% 覆盖的
  口径，两个数字的**差额本身**就是"被 watchdog 抢掉的那些"这个诊断信号。

- **放弃「已产出内容就不重试」**（Reasonix `retry.go:277` 那套裁决）。
  它需要 prefix continuation 兜底才不会变成净退步（否则用户拿到的是一段被截断的思考 +
  一个失败），而 prefix 续写是独立工作量。本 PR 只做**前置条件**：先让那一层看得见，
  才谈得上让它做选择。零产出的 attempt 照常重试 —— 有负向对照用例钉住，别把重试关死。

- **放弃用 `supportsThinkingToggle: false` 表达「恒思考」**（不新增 compat 位）。
  方向相反且不可互替：`supportsThinkingToggle:false` 是"这家没有思考开关这个概念"
  （Grok / o-series，两个方向都不发），会连主循环的 `enabled` 一起吞掉，
  等于把 GLM-5.3 的思考能力关死。

- **放弃在 PR5 里顺手给 side-call 补请求参数采集。**
  诚实记一笔：那 11 次 400 **全部来自 side-call**，而 side-call 不经过 BeforeModel，
  所以 PR5 能防的是"下次别再把仪器空洞当事实"，**不是**"下次能直接看到那 11 次请求"。
  side-call 请求参数采集是另一个缺口，已写进 `hook/types.ts` 的注释。

## 拿什么证明它生效了

### 一、PR3 复算了 §2.5.1 的原始证据（直接跑生产序列化函数）

```
$ bun probe-thinking.ts     # 直接调 applyDeepSeekThinking
glm-5.3        side-call → {}                                          ← 改造前是 {"thinking":{"type":"disabled"}}
glm-5.3        主循环    → {"thinking":{"type":"enabled"},"reasoning_effort":"max"}
glm-5.3-flash  side-call → {}
glm-5.2        side-call → {"thinking":{"type":"disabled"}}            ← 负向对照：不受影响
deepseek-v4    side-call → {"thinking":{"type":"disabled"}}            ← 负向对照：不受影响
```

### 二、PR4 的实测把方案文档的机制描述证伪了（见「放弃了什么」第一条）

```
$ bun probe-discard.ts   # 驱动生产 processStream
[A 中途被杀(无 block_stop)] discardedBlocks=1 discardedTextLength=1000 discardedThinkingLength=1000
[C 已成形思考 + 正文]      discardedBlocks=2 discardedTextLength=1005 discardedThinkingLength=1000
```
A 证明"思考被杀时不留痕"不成立（留了）；C 证明思考量是总量的**子集**（1000 ⊂ 1005），
所以原文的「加上 accumulatedReasoning.length」会双算。

### 三、24 次 vs 2 次的差额被定位成**竞态**，不是漏记

轨迹 `20260817-135824-fcf863e1`：24 次 `TimeoutFired(fallback_stream_timeout)`，
`warn.log` 里 `流重开` 只有 2 条。差额的机制是 `WatchdogKill` 在超时后 **56~163ms**
就杀掉生成器，而 `fallback.ts` 要先睡 **4.3~5.7s** 退避才 `yield stream_restart` ——
那句广播根本执行不到。这正是 PR6 把计数点放在退避**之前**的直接依据
（同位置的 `retry` 遥测实测 24/24 全部落盘）。

### 六、还没被证明的部分（诚实边界）

- **PR3 的线上验收未做**：§P0-5 要求"用 glm-5.3 跑一次带压缩/目标评估/工具分类的会话，
  断言 `warn.log` 里 `该模型始终思考` 出现 0 次"。本地只验到了**序列化层**
  （请求体里确实不再有 `disabled`）。要跑真实会话才能闭环，需要可用的 glm-5.3 渠道。
- **side-call 的超时档位是否容得下"它会思考"未实测**。§P0-5 也提到了这点：
  恒思考模型上 side-call 必然思考，`SIDE_CALL_DEFAULTS` 的超时可能偏紧。
  本 PR 不动那组值（改了就是另一个未经论证的阈值变更），但它是一个**已知的下游风险**。
- **`trace-digest` 还没消费 `StreamRestart` 事件**。事件已经落盘、可被 `jq` 复算，
  但没有进 digest 的自动归因视图（那属于 P1-5 的一键时间线，另一条）。
