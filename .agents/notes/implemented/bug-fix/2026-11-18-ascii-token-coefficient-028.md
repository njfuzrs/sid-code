# ASCII 字符 token 系数 0.20 → 0.28：修掉代码/JSON 增量的系统性低估

## 决定了什么

`packages/core/src/context/token.ts` 的 `ASCII_TOKENS_PER_CHAR` 从 `0.20` 改为 `0.28`，
并把这处「代码/JSON 偏高，取 0.20 折中」的旧注释换成实测依据。

**为什么是 0.28，不是拍脑袋**：E1 端到端验收（方案 §8.3）实测 M1 5.4–6.6%、M2 −5.4–−6.6%，
都差一点点不达标。顺着差异做离线测量发现：S1/S2 场景**每轮新增内容**的 ASCII 占比是
86% / 76%（主要是工具结果里的源码与 JSON），按 0.20 估算时增量估算比例 α 只有
0.717 / 0.673——即新增内容被低估 28–33%。系数提到 0.28 后 α 升到 0.906 / 0.817。
0.20 与真实密度（代码/JSON 约 0.25–0.30 tok/char）正好差这一截。

配套：4 个测试文件里 27 处写死 0.20 的前提按新系数重算（其中压缩档位测试改成
`Math.ceil(目标 token / 0.28)` 反推字符数，让它们测档位逻辑而不是跟着系数漂）。

## 放弃了什么（以及为什么不选）

**放弃「不动系数，把 M1 阈值放宽到 7%」**：那等于把验收标准改成迁就现状。而且 5% 这个数
原本是 `token.ts` 头注释对校准回路精度的承诺，不是随便定的。

**放弃「按内容类型分段校准」**：文档 §9 的 R6 已论证过——会话里只有一个总量观测
（真实 input），多个系数不可辨识，会退化成拟合噪声。

**放弃「只按 M1 调系数、不管压缩行为」**：这是这次改动最需要点破的 trade-off。
系数变大 → 同一份真实内容被估得更大 → 压缩触发点前移（更安全但可能更费）。
实测 S3（128K 窗口、唯一会压缩的场景）的 M4 从 3/3/2 **降到 2/2/2**，没有变频繁；
但这是 3 次样本，不能说成「压缩一定不会增加」。真正兜底的是 M3 仍为 0/0（无越界、
无 blocking 强制截断）。

## 拿什么证明它生效了

1. **真实会话对照**（同一套 E0 配置副本、同 prompt、同模型、同 effort、同 max-turns，
   三个场景各 3 次，全部 `success`）：

   | 场景 | M1 改前 → 改后 | M2 改前 → 改后 | M3 | M4 |
   | --- | --- | --- | --- | --- |
   | S1 | 5.4% → **2.7%**（2.5/2.7/3.1） | −5.4% → **−2.6%** | 0/0 | 0 |
   | S2 | 6.1% → **1.5%**（2.1/1.4/1.5） | −6.1% → **−1.4%** | 0/0 | 0 |
   | S3 | 6.6% → **2.5%**（2.4/2.5/2.9） | −6.6% → **−1.4%** | 0/0 | 3/3/2 → 2/2/2 |

   三场景 M1 全部 ≤5%、M2 全部 ≥−5%，M3 保持 0/0，`implausibleEstimates` 全 0。
   成本约 $1.2。

2. **先小成本验证再全量**：只改系数跑 S1 三次（$0.19）确认 M1 从 5.4% 掉到 2.7%、
   M2 不恶化，才继续跑 S2/S3。避免先花 $1.2 验证一个没算过的假设。

3. **代理指标与真实指标分开报**：离线 α 只能说明「增量估算变准了」，不能替代 M1；
   上面的结论全部来自真实会话的 M1/M2，不是 α 推出来的。

4. 门禁：`bun test ./packages/core/tests/context/ ./packages/core/tests/llm/token-estimator.test.ts`
   → 355 pass / 0 fail；`bun run affected-tests:run` → 2614 pass / 0 fail；
   `make build` → 产物自检通过。

5. **改测试不是为了让 CI 变绿**：27 处全是「0.20 下的具体数值」这一前提失效
   （`token.test.ts` 的期望值、压缩档位测试的字符数构造），断言的是同一套逻辑，
   换的是输入换算。压缩档位测试改成反推字符数后，以后再调系数不必再改它们。
