# LSP 七项缺陷修复：帧协议全字节化 + 三处可观测/门控缺口

来源：`docs-research/sid-code/bugfixes/todo/20260903-LSP代码智能-写入门文档时核出的七项缺陷.md`
（D1–D7 一次性修完，不留残项）。

## 决定了什么

**一、D1/D2/D3 —— `lsp/client.ts` 帧解析器改为全程按字节走**

三条缺陷同在 `handleData` 这一个函数里，所以一次改完而不是分三次。
选了缺陷文档列为"改动面更大但收口更彻底"的那个方案：**`buffer` 从 `string` 改成 `Buffer`**，
入口 `handleData(chunk: Buffer)` 不再 `chunk.toString()`。

- **D1**（多字节字符跨 chunk 被切成 `U+FFFD`）：解码只发生在按 `Content-Length`
  精确切出完整消息体之后，跨 chunk 的字节序列天然无损。
- **D2**（畸形 `Content-Length` 永久卡死）：加 `MAX_MESSAGE_BYTES = 32MB` 上界 +
  `Number.isSafeInteger` 合理性校验，超限走 `resetParser()`。
  **`contentLength` 的重置是关键** —— 只加校验不重置，解析器一样卡在等待态。
- **D3**（`buffer` 无上限）：加 `MAX_BUFFER_BYTES = 64MB`，挡"始终凑不出帧头"这类只增不减。
- **额外加了半截帧看门狗**（`STALE_FRAME_TIMEOUT_MS = 60s`，数据驱动、不起定时器）。
  上界校验只挡"声明值过大"，挡不住"声明 1000 字节却只发了 900 就再也不发"，
  后者同样永久停在等待态。这一条是缺陷文档 §D2.5 的"配套建议"，一起做了。
- 顺带：`stderr` 侧改用 `StringDecoder`（中文日志不再被切成 `?`）；
  头部按 `latin1` 逐字节映射解析，前置垃圾里的多字节序列不影响 `Content-Length` 匹配。

**二、D4 —— 子代理诊断注入对齐主循环围栏**（`agent/agentic-loop.ts`）

裸 `# LSP 诊断…` → `<system-reminder>` 包裹 + 「非用户输入」声明。
这是 2026-07-29「模型分不清谁在说话」三处裸注入的**最后一处**，此后该类债清零。

**三、D5 —— `lsp` 工具的启用判据附加「有服务器」**

`success` 需附加 `getLSPServerCount() > 0`（`manager.ts` 新增该同步读接口）。
`pending` 继续放行（"早可见"语义，刻意保留）。
判据提成纯函数 `lspToolEnabledFor(initState, serverCount)`，
门控输入的读取收在可覆写的 `readGateInputs()` —— 理由见第三段。

**四、D6 —— `lsp.json` 配置错误接进已有的健康告警通道**

`loadLSPConfigs` 返回 `{configs, errors}`（新增 `LSPConfigLoadResult`），
manager 存下 `configErrors` 并并入 `getLSPHealthWarning()`，
从而走 `query/loop.ts` 已有的一次性 system 警告 —— 首轮可见且不刷屏。
JSON 解析失败的文案明说「该文件的全部 LSP 配置已忽略」（用户容易以为只错了一条）。
三处状态重置（`resetLSPForTest` / `shutdownLSP` / `reinitializeLSP` / failed 重试分支）都清空它。

**五、D7 —— 补 `tests/lsp/client.test.ts`**

19 个用例。不是"补测"，是 D1–D3 的验证手段（缺陷文档 §D7.2 的判断）。
含 4 条标「防回归」的用例：它们是核查时**原以为有问题、跑完发现没问题**的路径
（头部损坏后恢复、body 内含 `\r\n\r\n` 字面量、多字段头部、前缀垃圾），写下来锁定正确行为。

## 放弃了什么（以及为什么不选）

- **放弃 `StringDecoder` 方案修 D1**。它是 Node 的标准解法、改动最小，
  但只修 D1：`buffer` 仍是 string，D3 的 O(n²)（每个 chunk 把整个 buffer 转一次 Buffer）还在。
  既然本来就要在同一个函数里改三条、且已经在写测试，全字节化更划算。
- **放弃给半截帧看门狗起定时器**。定时器要跟进程生命周期一起摘（`stop()` 里已有一处
  `removeAllListeners` 的 LEAK-6 教训），是新的泄漏来源。数据驱动的检查已经拿到关键性质：
  从"永久报废"变成"下一批数据到达即重新同步"。
- **放弃让工具列表在 LSP 就绪后重新组装一次**（D5 的彻底版）。
  代价是没装 server 的机器在初始化完成前头几轮仍会短暂看到 `lsp` 工具；
  初始化是几百毫秒级，成本高于收益 —— 与缺陷文档 §D5.4 的判断一致。
- **放弃让配置错误阻断启动**。`config.ts` 的 best-effort 降级方向是对的，
  问题只在"降级之后用户看不见"，所以补的是可见性，不是把 warn 升成 fatal。
- **放弃直接测 `isEnabled()` 的零服务器分支** —— 见下一段，这是被实测推翻的第一版写法。

## 拿什么证明它生效了

**核心证据是 10 次变异自证，不是"测试全绿"。** 判据是「红的是哪一条」：

| 变异 | 改了什么 | 结果 |
| --- | --- | --- |
| M1 | 入口恢复逐 chunk `toString()` | **恰好 3 条 D1 用例红**（汉字/级联/emoji） |
| M2 | 取消 `Content-Length` 上界校验 | **恰好 3 条 D2 用例红** |
| M3 | 取消 `buffer` 上限 | D3 上限用例红 |
| M4 | `resetParser` 里不重置 `contentLength` | 看门狗用例红 |
| M5 | 取消半截帧看门狗 | 看门狗用例红 |
| M6 | D4 文案退回裸 `#` 标题 | **3 条 D4 门禁全红** |
| M7 | 判据退回只看 `initState` | 「success + 零服务器」用例红 |
| M8 | 判据函数留着但不接进 `isEnabled` | **首版全绿 → 发现假门禁，见下** |
| M9 | `config.ts` 只打日志不收集 errors | 4 条 D6 用例红 |
| M10 | manager 存下 errors 但不接进告警 | `getLSPHealthWarning` 用例红 |

**两个假门禁是在这一轮里被抓出来的，比修复本身更值得记：**

1. **D5 首版用例写成 `if (state === "success") { expect(...) }`，在本机从不进入那个分支。**
   探针实测：`initializeLSP` 落地后 `count=5`（PATH 里有 5 个 language server），
   `success + 零服务器`这个状态**根本构造不出来** —— 用例绿着，一条断言都没跑。
   把 `PATH=""` 也不管用：`which` 会回落到系统默认路径，实测仍是 5 个。
   **修法**：判据提成纯函数由用例穷举（确定），机器环境无关。
2. **M8 暴露第二层**：即便有了纯函数，"isEnabled 与判据同结论"这种一致性断言
   在有 server 的机器上是 `success && 5>0` ≡ `success`，**把判据整个摘掉照样全绿**。
   **修法**：加可覆写的 `readGateInputs()`，让测试确定地构造 `success + 零服务器`。
   重跑 M8 → 该用例正确变红。

**M9 自身也踩了一次**：第一版变异脚本的两处 `replace` 只命中一处（没写 assert），
于是只有 1 条用例红，看起来像"门禁覆盖不足"。补 assert 重做后 4 条全红。
教训与仓库里那条「交接命令须按最终文本复跑」同源：**静默不匹配 + 退出 0 = 假结论**。

**门禁执行记录（全部在 worktree 内实跑）：**

```text
bun run affected-tests:run   → 1523 pass / 0 fail（106 文件，18.23s）
                               ⚠️ 首跑 3 fail 是 vendor 缺失，跑 bun run vendor:fetch 后归零
make build                   → 自检 4 项通过；grep "will always be undefined" 无命中
bun run lint                 → 无输出（干净）
bun run format:check         → All matched files use the correct format（1879 文件）
bun run lint:boundary        → 越界依赖 0 处 / 测试跨包相对路径 0 处
bun test ./packages/core/tests/lsp/  → 132 pass / 0 fail（8 文件）
```

**新增导出确实进了二进制**（worktree 的 `node_modules` 会向上解析到主仓，
新增导出可能编译成 `undefined` 而构建仍 exit 0 —— 所以这一步必须显式验）：

```text
getLSPServerCount 4 处 / lspToolEnabledFor 3 处 / readGateInputs 2 处
MAX_MESSAGE_BYTES 4 处 / frameStartedAt 5 处      （grep -a，Mach-O 需 -a）
```

**一处诚实标注的度量边界**：想再验"中文文案是否内联"时，字节级扫描 `非用户输入`
等串全为 0。**对照组推翻了"没内联"这个结论** —— 改动前就存在、本次完全没碰的
`LSP 系统初始化失败` / `LSP 服务器异常` 同样是 0（utf8 与 utf16-le 都试过）。
说明 bun `--compile` 存字符串字面量的形式让平文本字节扫描看不见，
**这是测量手段失效，不是代码缺失**。ASCII 符号那一组才是本次有效证据。

**未验证的部分（不写成结论）**：D1/D2 在**真实 language server** 上的触发频率没测
（只证明了机制成立与修复有效）；`lsp` 工具定义的实际 token 数仍是估算，没过 tokenizer。
这两项与缺陷文档附录 B 的边界一致，本次没有缩小。
