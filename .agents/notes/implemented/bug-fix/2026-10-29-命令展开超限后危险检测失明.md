# 命令展开超限后危险检测失明：fail-closed 到危险类确认

## 决定了什么

`permission/shell-command-variants.ts` 的 `expandShellCommand` 有两道上限：`MAX_VARIANTS=128`、`MAX_DEPTH=4`。修前超出的部分会被静默丢弃，返回值里也没有任何信号。deny / ask 规则、危险检测、写目标提取都只看已经展开的部分，于是下面这些命令在 always-allow 或 yesMode 下直接放行（`587eac5c` 实测）：

- `echo 0 && … && echo 199 && rm -rf /`（127 段还能拦，130 段就放行了）
- 同样的长链后面接 `rm -rf ~`、`curl x | sh`、`cp x .git/hooks/pre-commit`
- `sh -c` 嵌套 5 层以上的 `rm -rf /`
- 长链后面接 `curl x`，配了 deny `Bash(curl *)` 也照样放行

修法：

1. `ShellCommandExpansion` 新增 `truncated: boolean`。两种情况置 true：形态数打满后还有没处理的段或内层脚本；嵌套深度用完时还有内层脚本。
2. `checker.ts` 的 `checkDangerousCommand`：结构化和正则的 critical 判定之后，如果 `truncated` 为真，返回需确认，类型为 `dangerousCommand`，pattern 是「展开超限」，severity 为 high。`dangerousCommand` 属于 `isSafetyConfirmation`，yesMode、hook allow、auto 分类器都越不过去。Step 2 排在 Step 5 / 6 / 8 之前，Step 1 deny 漏掉的命令也会在这里落到确认。
3. `hardcodedDangerCheck` 改为接收调用方传入的 expansion，同一条命令不再展开两次。

## 放弃了什么

| 方案 | 不选的理由 |
|---|---|
| 截断即 critical 硬拒 | critical 没有出口。上限一旦误伤合法长命令，用户就被卡死，#443 刚消灭的就是这类无出口误拦 |
| 提高上限（如 1024） | 只是把阈值往后推，构造 600 段照样绕过。上限本身就是防病态输入撑爆展开用的 |
| 截断后对剩余原文跑旧正则兜底 | 旧正则就是 #443 替换掉的东西，引号、`-Rf` 等写法都会漏。兜底等于留一条已知会漏的路 |
| 截断分支放在 critical 判定之前 | 已展开部分里真命中的 `rm -rf /` 会从硬拒降级成确认。前 127 段里的危险命令不能因为后面还有内容就变得能批准 |
| deny 规则侧另外处理截断 | 多余：Step 2 已经兜住，deny 漏掉的命令都会落到确认 |

## 拿什么证明它生效了

- `packages/core/tests/permission/dangerous-command-matrix.test.ts` 新增「P. 展开超限」一组，共 16 个用例，覆盖截断兜底、yesMode、deny 规则、critical 不降级、上限内不误伤、展开层契约。
- 变异自证：M1 删掉截断分支，8 个用例变红；M2 深度超限时不置位，嵌套和契约 3 个变红；M3 截断分支挪到 critical 之前，「critical 不降级」1 个变红。三组都只红了对应的断言，恢复后 150 条全过。
- 牺牲的是「快」，截断的命令要多一次确认，无头模式下会被拒。代价估算：本机 334 个会话、5626 条真实 bash 调用离线展开，形态数最大 46，≥ 64 的 0 条，嵌套 ≥ 4 层的 0 条。
- 来源：bench_fix F3 的 D-01。deepseek-flash 的 P3v、S1v review 回答提出，opus 两批都没有发现。
