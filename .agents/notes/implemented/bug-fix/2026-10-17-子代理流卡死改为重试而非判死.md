# 子代理流卡死改为重试而非判死：删掉 processStream 自带的 idle / overall 超时层

## 决定了什么

`agent/stream-processor.ts` 的 `processStream` 不再挂 `createStreamLifecycle`（idle 60s / overall 180s / 首字节），
只消费事件；子代理身上的流超时**只剩漏斗一层**（`streamWithResilience` → `fallback.ts` startStreamTimeout），
触发即 abort + 重试，与主循环同构。`agentic-loop.ts` 两处调用只传 `{ signal }`，
`AgentLoopConfig.streamIdleTimeoutMs/streamOverallTimeoutMs` 删除；
`ABORT_REASONS` 移除已无调用点的 `agent-stream-overall-timeout` / `agent-stream-heartbeat-timeout`；
`TimeoutLayer` 的 `agent_heartbeat_timeout` / `agent_overall_timeout` 标为历史值保留（统计脚本要读 #284 前后的基线）。

顺带 S6 文案：`classifySubAgentFailure` 在硬 kill 时带出 `hardKilled`，残卷写
「跑满硬 kill 期限 (900秒) 仍未结束，已被终止」，不再写成「达到墙钟预算 (300秒) 并已停止」。

死因（事故 20261016-224545）：idle 层到点只置 `snapshot.timedOut`，连接没断（`getAbortController` 生产零调用方）；
漏斗 180s 真正断流并重试后，重试流首个事件被 `stream-lifecycle` 的 `if (snapshot.timedOut) break` 截断 →
`if (timeoutError)` 返回 error → 子代理 4–8ms 后判失败。

## 放弃了什么（以及为什么不选）

- **只在 `stream_restart` 时清掉旧标志**：能修本例，但留着一个「只判死不断流」的计时器，下一次换个时序照样会杀；两层同谓词互不知情是本仓反复出现的病（见 `oss-stream-timeout-single-layer-beats-three`）。
- **补上 `getAbortController` 让这层也能断流**：等于多造一层与漏斗同谓词的超时，且断流后谁重试？漏斗已经做这件事。
- **本 PR 一并把漏斗档位改成主循环的 600s（方案 S2）**：被否。墙钟 300s detach + 900s 硬 kill 仍在时，600s 阈值让硬 kill 前最多只剩一次重试，失败只是从 L6 挪到硬 kill，验收数据也无法归因。S2 必须和删墙钟（PR-B）同上。
- 墙钟 / 硬 kill / maxTurns / skill fork 限制 / spawn 路径：属于 PR-B（`refactor(subagent): 对齐 CC 去掉墙钟 / 硬 kill / 默认 maxTurns`），本 PR 不动。

## 拿什么证明它生效了

- 新增 `packages/core/tests/agent/subagent-stream-stall-retry-not-fail.test.ts` T1：第 1 次尝试吐半截后静默 300ms 再断流（旧阈值按比例压到 idle 50ms / overall 100ms），漏斗重试，第 2 次交付 → `success: true`、`calls=2`、半截内容被作废。
- **变异自证**：把 `stream-processor.ts` 与 `agentic-loop.ts` 还原成 `main@11cbeea8` 版本（恢复 lifecycle 包装 + `onTimeout` 置 `timeoutError` + 阈值透传），T1 及 5 条反向断言共 6 条红（T1 `calls` 为 1，即重试被判死后不再发起）；恢复修复后全绿。这也证实了方案 §8 第 1 条「重试流首个事件撞旧标志」的推断。
- 锁旧行为的测试改为锁相反事实（补清单不删断言）：`stream-processor-timeout.test.ts`、`agentic-loop-p3-subagent-summary.test.ts` P3-6 段、`subagent-overall-timeout-excludes-backoff.test.ts` 负向对照、`errors.test.ts` ABORT_REASONS 哨兵。
- 端到端：待发 beta 后用 `sc-dev` 并行派 3–5 个 explore（`glm-5.3-uniapi`），判据为超时层导致的 `SubagentStop error = 0`、上游卡顿时可见 `fallback_stream_timeout → attempt=N → completed`。**本 Note 写成时尚未验证**，基线是 #284 后 25 completed / 9 error。
