# 团队默认补全拆出独立水位只补模板新增键；迁移失败不越过失败版本且启动可见（B35）

## 决定了什么

- `migrations/backfill-team-defaults.ts`：v1 补全后在 `migrations.json` 记 `teamDefaults = { hash, keys }`（模板内容 sha256 + 顶层键集合）。新增 `backfillNewTemplateKeys()`，**每次启动都跑、不挂全局水位线**：哈希相同直接返回；不同则只补「本次模板键 − 记录键」里用户缺失的，再更新记录。语义与 v1 相同（只补缺失顶层键、`{}`/`[]` 算表态、不展开 env）。
- 无记录的老用户（B35 前已跑过 v1）：首次只记基线、不补。
- `migrations/runner.ts`：水位线推进到「第一个失败版本之前」（旧实现推到最后成功的版本，v1 失败 + v2–v5 成功 ⇒ 写 5，v1 永不重跑）。失败除 debug 外记一条启动告警；增量补全只在 v1 已完成后跑。
- 新增 `migrations/warnings.ts` 暂存告警，`loadConfig` 并进 `_validationDiagnostics.warnings`（含 onboarding 提前返回那条分支——settings.json 损坏时恰好走那里），TUI 横幅与 `-p` stderr 共用。
- `website/team/defaults.md`：D127 warning 框补上「新加的顶层键会补进去」，「只补一次」一节改写，D128 改成「启动时提示一次，修好后自动重试」。

## 放弃了什么（以及为什么不选）

- **哈希一变就重跑 v1 全量补**（清单第 1 步字面写法）：用户补全后删掉的键会被加回来，违反「删除 = 表态」。哈希只留作快路径，补什么由键集合差决定（清单第 2 步）。
- **无记录老用户按当前模板全量补一次**：分不清「模板后来加的」与「用户自己删的」，会复活删掉的配置（例如 B37 正要收回的 `trace`）。宁可少补。代价：B35 之前已加进模板的键对这批用户仍缺，但这批键在 v1 首跑时已补过，缺的只可能是用户删的或 v1 之后加的。
- **新加一个迁移版本 v7 做这件事**：仍挂在全局水位线上，下次改模板又断，与问题同形。
- **迁移失败直写 stderr**：TUI 接管终端后裸输出会留游离行（runner 原注释的理由仍成立），所以走启动诊断出口。
- **已有键的取值变化也同步**：会覆盖用户值，那是 policy 的职责，不是默认值的。

## 拿什么证明它生效了

- `packages/core/tests/migrations/team-defaults-rerun.test.ts` 8 条；变异自证 5 条全部转红：哈希变就全量补（3 红）、水位越过失败版本（1 红）、不跑增量（1 红）、失败不记告警（2 红）、无记录也全量补（1 红）。
- `bun run affected-tests:run`：901 pass / 0 fail；`make build` 自检通过、无 `will always be undefined`。
- 编译产物在隔离 `SID_CONFIG_DIR` 实测：
  1. 水位线=5、记录键缺 `search`、用户删过 `trace` ⇒ 打印「已补全团队默认配置字段…: search」，`trace` 未补回，水位仍 5。
  2. settings.json 损坏、水位=0 ⇒ `-p` stderr 出现「配置检查发现 5 项提示」含「迁移 backfill-team-defaults (v1) 失败…修好后下次启动会自动重试」，水位停在 0。
  3. 修好文件再启动 ⇒ v1 全量补全，水位推到 5。
