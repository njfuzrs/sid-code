# 子代理隔离埋点补强：判据维度、开关开销与样本来源

## 决定了什么

PR [#568](https://github.com/njfuzrs/sid-code/pull/568)（O1）合入后的 review 发现两处真实缺口与三处验证/口径弱点，本 PR 全部补上：

**1. 补 `commits` 维度的用例 —— 判据的另一半此前没有被任何断言覆盖**

判据是 `changedFiles === 0 && commits === 0`（`packages/core/src/agent/tool.ts`），但唯一的
「不命中」用例只写文件，桩从不 commit。把判据里 `changes.commits === 0` 去掉，原来的
9 条测试仍然全绿 —— 而「写类子代理 commit 后工作区干净」正是最常见的收尾形态，
漏掉这一半会把真实成果误报成「白建」。

新增用例：桩在 worktree 里 `writeFile + git add + git commit`，断言不落事件。

**2. 埋点关闭时不再多跑一次 `countChanges`（新增 `hasIsolationUnusedTraceSink()`）**

原实现把 `countChanges`（同步 `git status`）放在 `emitSubagentIsolationUnused` 之前，
而「sink 不存在就 return」在 emit 内部 —— 不启用遥测的用户、headless / CI 环境，
每个 `isolation=worktree` 子代理收尾都会白付一次同步 git status。本机实测本仓 45ms，
大仓更久，且发生在主线程。

改为调用方先问 `hasIsolationUnusedTraceSink()`，测量前短路。telemetry 模块新增这个
导出而不是让调用方猜，理由写在模块头注释里。

**3. 事件新增 `success` 字段**

原事件的 6 个字段里没有执行结果，一周后按 `agent_type` 统计「只读类型占比」时，
「任务本来就失败、worktree 只是陪着白建」的样本会和「只读任务误用」混在一个分母里。
`setupIsolation` 的 cleanup 改为接受 `success: boolean`，两条执行路径（`runSync` /
`executeInBackground`）各自在 finally 传 `execSuccess`（异常出口保持 `false`）。

**4. `lifetime_ms` 用 `Math.max(0, …)`，测试断言从 `>= 0` 改为 `> 0`**

`Date.now()` 非单调，系统时间回拨会让存活时长为负，均值/分位统计凭空变小；
而 `>= 0` 的断言在值退化成常量 `0` 时仍然全绿，等于没验。

**5. 补 `countChanges === null`（git 出错）用例**

Agent Note 把「返回 null 时不发、宁缺不错」当关键判据，但没有用例覆盖。桩把 worktree 的
`.git` 文件指针改写到不存在的目录，验证不落事件、清理失败不影响子代理结果。

> 实测踩到一个环境陷阱：**不能删 worktree 的 `.git` 文件**。worktree 建在主仓的
> `.sid-code/worktrees/` 下，删掉 `.git` 后 git 会向上找到主仓的 `.git`，`status` 反而
> 成功 —— 第一次跑这条用例时反而落出了一条事件。改为写入损坏的 `gitdir:` 指针才真正
> 让 git 失败。这条已写进测试的注释。

## 放弃了什么（以及为什么不选）

- **把 workflow 的 `agent({isolation:'worktree'})` 也接入这条埋点**：它走
  `workflow/sub-agent-runner.ts` 自己的 worktree 路径（slug `wf_<runId>-...`，description
  用 `ctx.label`，语义与 `sub_agent` 不同）。原 PR 已把「未覆盖 workflow」记为取舍，本 PR
  是 review follow-up，不把它扩成功能扩展；要覆盖得单独论证字段口径，另开 PR。
- **事件再加 `turns` 字段**：cleanup 拿 `result.success` 只需一个布尔穿线，turns 要连带
  结果对象一起传，收益（区分「跑了几轮」）低于成本。一周后的判据只要求分出成功/失败。
- **让 `WorktreeManager.remove()` 返回判定结果、省掉重复的那次 `git status`**：remove 是
  fail-closed 的数据保护路径，改契约会波及 exit-worktree / GC / team 全部调用方。原 PR
  的否决论证仍成立；本 PR 只保证**埋点关闭时不额外测量**，启用时多一次（本机 45ms）是
  已经讲过的取舍。
- **收紧 `typecheck:gate` 基线**：本次改动没有修类型错误，`62 处 / 基线 64 处` 的差值是
  既有状态，收紧属于无关改动，留给专门清理类型存量的 PR。

## 拿什么证明它生效了

新增/加强用例（`packages/core/tests/agent/subagent-isolation-unused.test.ts`，14 条全绿）：

- `commit` 维度：commit 后工作区干净 → 0 条事件
- 失败样本：`success=false` 的事件恰好 1 条，`isError` 为 true
- git 出错：`countChanges` 返回 null → 0 条事件，子代理结果不受影响
- 开关开销：`sink` 在时 `countChanges` 调 2 次（埋点 + remove 内部），关闭时 1 次
  （只剩 remove）—— 用 prototype 计数，不依赖耗时（慢机器上耗时会飘）
- `lifetime_ms > 0`、`success === true`（成功样本）、sink 查询 true/false

**变异自证**（每项都先改坏、确认报的正是对应用例、再恢复）：

```text

                                      → 开关开销用例红：Expected 1 / Received 2
lifetimeMs 固定 0 + success 固定 true  → lifetime 用例红（Expected > 0 / Received 0）
                                      + 失败样本用例红（Expected false / Received true）
恢复后 14 pass / 0 fail
```
