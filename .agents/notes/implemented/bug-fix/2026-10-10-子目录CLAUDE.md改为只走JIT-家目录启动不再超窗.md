# 子目录 CLAUDE.md 只走 JIT：家目录启动不再超窗

## 决定了什么

- **删掉启动期子目录扫描**（`rules.ts` 的 `findProjectCLAUDEmdFiles`）。启动时只加载 cwd → 文件系统根的父链；cwd 之下的 `CLAUDE.md` 全部交给 `JitContextManager`，在工具触达该目录时加载，与 CC 一致（`getMemoryFiles` 只走父链，嵌套目录靠 `getMemoryFilesForNestedDirectory` 按需加载）。
- **熔断文案区分成因**：`buildCompactCircuitBreakerText` 判断常驻开销（系统提示词 + 工具定义）是否占本次估算总量 ≥ 80%。是的话直说「压缩无法解决」，并指向 CLAUDE.md 或 `/context`；错误面板使用新码 `context_fixed_overflow`，不再引导用户执行 `/compact`。
- **CLAUDE.md 附件如实标注**：多文件合并时列出全部来源，不再冒用最后一个文件名。
- **`.mcp.json` 兼容 CC 写法**：`type` 映射为 `transport`，`streamable-http` 归为 http；只有 `command` 时推断为 stdio，只有 `url` 时推断为 http。`mcp.local.json` 同样处理。

## 放弃了什么（以及为什么不选）

- **只给家目录开特例（projectRoot === homedir 时跳过扫描）**：家目录只是最坏的一种形态。`~/Code`、monorepo 根、worktree 父目录都会复发，这只是在形态上打补丁。
- **给扫描加深度 / 文件数 / 字符预算**：这只是把阈值从 89 万挪到某个数，任何阈值都回答不了「这个子目录的规则和当前任务有关吗」，JIT 的触发条件能回答。截断还会让规则随机丢一半，比不加载更难排查。
- **熔断判据用「常驻占窗口 ≥ 90%」**：事故现场正好 91%，判据贴着阈值，换一个窗口或估算偏低就会判错。走到熔断时 API 已经实锤超窗，真正要问的是「超出的那部分是不是历史」，所以按占总量算。
- **代价**：启动时不再预载仓库内子目录的无条件规则，首次触达那个目录之前，模型看不到它们。这和 CC 的行为一致。JIT 每轮工具调用后都会触发，实际延迟只是一个工具回合。

## 拿什么证明它生效了

- 修复前：在 `~` 下执行 `sid-code -p "你好" --debug` 可复现，日志为 `系统提示词构建完成: 2365512字符, ~894748 tokens`、`规则合并完成，实际生效 65 个文件`，返回 400003，连续 3 次后熔断。
- 修复后（同命令、同目录、本分支构建）：`系统提示词构建完成: 24384字符, ~10640 tokens`、`实际生效 1 个文件`，模型正常回复「好」，启动时不再出现 `mcpServers.mastergo-magic-mcp.transport: 无效值 "undefined"`。
- 回归测试：`tests/config/rules-no-startup-subdir-scan.test.ts`（家目录形态 20 个兄弟项目一份不进；仓库内子目录启动期不进、JIT 触达时进且不重复注入根规则）、`tests/query/compact-circuit-breaker-text.test.ts`（事故数值判为救不了、正常情形保留原文案）、`tests/mcp/mcp-json-cc-format.test.ts`、`tests/config/attachments.test.ts` 多文件标注；`rules-layered.test.ts` 中 3 条旧契约用例改写为新契约。
