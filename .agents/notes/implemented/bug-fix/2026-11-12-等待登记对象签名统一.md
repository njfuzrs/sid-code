# 等待登记必须带对象签名：三个入口统一到「命令表 + 自然语言 + 脚本展开」

## 决定了什么

**新建 `packages/core/src/task/wait-subjects.ts`，作为 bash / monitor / schedule_wakeup 三个入口唯一的对象签名抽取处。**

改造前三个入口各管一半，这是「等待表登记了却不知道在等什么」的直接原因：

- `wait-registry.extractWaitSubjects`：只认 `PR #N` / `pull/N` / `run N` 三种**自然语言**，只被唤醒用。
- `tool/monitor.ts` 的私有 `extractMonitorSubjects`：在它基础上加
  `gh pr (checks|view|status) N` / `gh run (view|watch) N` 两条**私有正则**。
- `tool/bash.ts` 的 `registerWaitUntil`：只传 `id/kind/promise/description`，**一个 subject 都不传**。

取证会话的实际写法正是这三处都覆盖不到的形态（全部实测 `matchStatusQuery` 返回 null）：

| 会话 | 命令 | 改造前 |
| --- | --- | --- |
| b0aa0f1e | `bash /tmp/wait-pr-779.sh` | 命令行没有对象，对象在文件里 |
| 8b8d721f | `chmod +x /tmp/wait-pr757.sh && bash …` | 同上 |
| ca8d7e5c | 单行 `for … do s=$(gh pr view 780 …); case … esac; done` | `case`/`esac`/`exit` 让整条命令不是「查询」 |

具体改了四处：

1. **`wait-subjects.ts`（新）** 导出 `collectWaitSubjects` / `collectWaitCommandFamilies` / `extractScriptPaths` / `extractNaturalLanguageSubjects` / `MAX_SCRIPT_BODY_BYTES`。命令类规则**直接复用 `status-query-commands` 的命令表**（候选片段切分也用它的 `statusQueryCandidates`，为此把它从私有改为导出），于是「P1 认得的查询」与「等待表认得的对象」是同一把尺子。
2. **`bash.ts` 的 `registerWaitUntil`** 现在多收一个 `cwd`，登记时传 `subjects` 与 `commandFamilies`；新增私有 `readWaitScriptBodies`，把命令里字面出现的脚本文件正文读出来（≤64KB、只读普通文件、读不到就跳过）交给抽取函数。
3. **`monitor.ts`** 删掉私有 `extractMonitorSubjects`，改调新函数。
4. **`wait-registry.extractWaitSubjects`** 保留同名导出，但规则本体搬走、改为委托窄口径的 `extractNaturalLanguageSubjects`（唤醒只有自然语言，跑命令表会把 prompt 里举例的命令当成真在查询）。

签名格式（`gh:pr:<n>` / `gh:run:<id>` / …）与 `findWaitBySubject` 的匹配逻辑**一个字节都没动**，所以 R2/R6/P1 的消费方不用跟着改。

## 放弃了什么（以及为什么不选）

**1. 脚本变量展开（`PR=779` + `gh api "repos/$REPO/pulls/$PR"`）—— 留给 R4。**

四个取证脚本全是这个形态，看起来「展开变量就能抽出来」。但 R1 阶段命令表**不认** `gh api …/pulls/<n>`（那是 R4 要补的规则），所以展开之后仍然抽不出 `gh:pr:779`，只是多一层解析。b0aa0f1e / 8b8d721f 靠脚本注释里的 `# 等待 PR #779` 命中自然语言规则就够了。**R4 补上 pulls 路径之后，变量展开才第一次有收益，那时再做。**

**2. 严格「新函数是旧 monitor 函数的超集」—— 放弃了，因为它要求保留假阳性。**

17 条输入逐条比对，16 条一致或新增（`gh pr status` 多抽了 `gh:pr:current`），只有 1 条旧有新无：
`echo "gh pr view 780"` 旧函数抽 `gh:pr:780`、新函数 `[]`。命令表判 `echo` 不是查询是对的——它不产生任何状态变化。要「超集」就得把旧的两条正则当兜底留在 `collectWaitSubjects` 里，那等于把 R1 要消灭的「两把尺子」重新装回去。

代价是真实的：`packages/core/tests/task/wakeup-invalidation-chain.test.ts` 的 R6 真实入口用例，替身脚本原来写 `echo "gh pr checks 662: pass"; exit 0`，靠旧正则抽 subject。已改成 `echo "PR #662: pass"; exit 0`（自然语言形态，指向同一对象），**断言未改**。这条断言本来就是绿的、不是我改红的——父仓 main 单跑 6 pass 复现过，worktree 里改红是因为契约变了，属于「契约被有意改了 → 修测试前提」。

**3. 递归展开（脚本 A 里再调 `bash B` 也读 B）—— 不做。**

真实等待脚本都是一层，递归要处理自引用与深度上限，收益在三个取证会话里一次都没出现。`source` / `.` 也明确不跟随：它们常被用来加载环境或 wrapper，跟进去抽到的是别人的对象。

**4. 在等待表里读文件 —— 不做。**

等待表是纯数据层（进程内会话级），加 I/O 会让它难测，且它拿不到解析后的 cwd。读文件放在 bash 工具那一侧，`wait-subjects.ts` 保持纯函数。
