# 常驻工具的 strict 降级改为显式优先级 + 落 StrictToolsCapped 事件

## 决定了什么

`applyStrictToolBudget()` 在发请求前按端点上限裁剪 strict 工具，这条路径**修前完全不留痕**：
常驻（`deferred=false`）的 strict 工具 24 个 > 上限 20，每轮固定有 4 个被降成非 strict
——没有日志、没有事件、没有告警。轨迹里 `StrictToolDegraded` 是 0 条，于是「上游零 400」
与「一上来就在降级」在数据上无法区分。

三处改动：

1. **可见**：`emitStrictToolsCapped({ endpoint, limit, demoted })`（`trace/stream-observer.ts`），
   在 `anthropic.ts` 的流式与非流式两个调用点各接一次。按「端点 + 上限 + 降级名单」去重，
   每个会话每种组合只写一条 —— 发前收口是每轮都发生的，不去重会把 `events.jsonl` 灌满。
   名单变化（激活延迟工具、上限被 `learnStrictToolLimit` 学小）会重新发，那才是新信息。
2. **可控**：`tool_search` 声明 `strictPriority = 60`、`todo_write` 声明 `40`。
   这两个的值落在 `ask_user_question`(100) / `edit`·`write`(50) 之间与之后，
   因为它们的结果**驱动 harness 状态机**（激活延迟工具、推进 `todo_gate`），
   失败形态是「模型以为生效了、实际没有」——比参数被拒更难发现。降级名单因此从
   「码点序最靠后的 4 个」变成「码点序最靠后、且没声明优先级的那 4 个」。
3. **契约**：`ToolCapabilityFields.strictPriority` 的注释补全为三档声明标准，
   并写明这是一份**优先级而不是豁免名单** —— 想知道实际名单看事件，不要手推。

## 放弃了什么（以及为什么不选）

- **不把 `StrictToolsCapped` 合并进 `StrictToolDegraded`**。两者是不同路径：前者是每轮
  请求前的例行截断（没出事也发生），后者是上游已回 400 之后的事后补救（一次事故一条）。
  合并会让「偶发语法体积错误」与「常驻超限的固定降级」在 digest 里混成同一个计数，
  恰好抹掉本次要修的那个信号。
- **不按「每次降级都记一条」**。20 轮会话会写 20 条同内容事件，digest 的计数立刻失去意义
  （会被读成「发生了 20 次不同的降级」）。所以 key 含端点/上限/名单三要素。
- **不在 `anthropic.ts` 里写关键工具白名单**，而是让工具自报 `strictPriority`。理由与
  `exemptFromLoopDetection` 同范式：新增工具时在定义处就能看到这一项，不会漏。
- **不给所有常驻工具都补一个优先级**（比如按码点序手动排 24 个）。那等于把「谁被降级」
  从一种涌现行为换成一份需要人肉维护的清单，而真正需要保证的只有那 5 个；
  其余 19 个降谁都可以，让它们继续按码点序走。
- **本轮不做 T6（前缀碰撞门禁改用真实注册表）**。用户明确只要 T5，T6 另开 PR。

## 拿什么证明它生效了

**降级名单从真实注册表算出来**（`--dump-tool-meta` → `applyStrictToolBudget`，不是手推）：

```
常驻数: 24  上限: 20  降级数: 4
降级名单: ["sub_agent","think","web_fetch","web_search"]
已声明优先级: ask_user_question=100, tool_search=60, edit=50, write=50, todo_write=40
```

与方案文档的推算一致（配了 MCP 时降 `sub_agent` / `think` / `web_fetch` / `web_search`）。

**新增门禁** `tests/tool/strict-budget-priority.test.ts`（4 条，数据源是 T0 的
`--dump-tool-meta`，不是手写清单）：关键工具不在降级名单；降级数 = 常驻数 − 上限；
名单与 2026-11-12 基线一致；**上限压到 5 时关键工具仍保住**（这一条断的是排序方向
真的在起作用，避免「数量刚好没超」的假绿）。

**变异自证**（两条都确认先红后绿）：

- 删掉 `tool_search` 的 `strictPriority = 60` → 门禁红：
  `tool_search 被挤出了 strict —— 请检查它的 strictPriority / 常驻分层`（3 条失败）。
- 去掉 `emitStrictToolsCapped` 里的去重判断 → `strict-tool-budget.test.ts` 的去重用例红：
  `Expected length: 1 / Received length: 3`、`Received length: 2`。

**事件去重用例**（`packages/core/tests/llm/strict-tool-budget.test.ts` 新增 4 条）：
流式三轮只发 1 条；非流式路径同样接上且共用去重表；上限学小（20 → 12）追加第二条；
不超限时零事件。

**端到端（本机 `./sid-code`，deepseek）：0 条**。非 Claude 模型走不到 strict 收口，
`events.jsonl` 里 `StrictToolsCapped` 恰好 0 条（会话 `20261112-223713-2d482f8c`），
反向证明这条事件不是无条件乱发的。
