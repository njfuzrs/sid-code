# 等待源审计口径：把「重复等待」从不可观测变成可度量

## 决定了什么

补上 R9：**审计口径看不到「重复等待」**。此前只有 `WaitRegistered` 事实事件，
而 R2 上线后同对象的重复等待在入口被判成 `duplicate` **不启动**，于是等待表里什么都
不发生，轨迹里也什么都不剩 —— 修得越有效，这个数越小，最后看起来像「问题从未存在」。
三条改动：

1. **新增 `WaitAdmission` 判定事件**（`packages/core/src/task/wait-admission.ts`），
   `decideWaitAdmission` 的唯一出口统一埋点，字段 `action` / `kind` / `subjects` /
   `existing_ids` / `tool_use_id`。埋点放在判定函数里而不是三个入口各埋一次：
   三入口共用同一个判定点是 R2 的核心设计，埋点跟着复用走，新增入口不可能漏埋；
   各入口各埋一次则漏一个入口不会有任何测试变红。`WaitAdmissionInput.kind` 同时改成
   **必填**，靠类型强制来源标注（漏传会静默落一个 `unknown` 来源，对审计没价值）。
   `wait-registry.ts` 补导出 `WAIT_ADMISSION_EVENT_NAME` / `WAIT_RELEASED_EVENT_NAME` /
   `recordWaitTraceEvent`，sink 仍然只有一份（App 注入）。

2. **digest 新增「等待源」节**（`packages/core/src/trace/digest.ts`）：
   `max_concurrent_waits_per_subject`（同一对象同时并存的最大等待数）、
   `wait_duplicates_blocked` / `wait_replacements`（`WaitAdmission` 判定计数）、
   `stale_notification_claims`（R3 误读）。并存数按 `WaitRegistered.subjects` 聚合；
   **R1 之前的轨迹 shell 类没有 subjects，回退按 `description` 归并** ——
   不回退的话，取证会话 b0aa0f1e 的 4 条重挂一条都数不出来（它正好是 R1 之前的轨迹）。

3. **误读口径进 digest，不再依赖一次性 python 脚本**：`staleNotificationClaims` 用
   `session.traj` 的 `history`（完整消息序列，与 raw.jsonl 的 `new_messages` 增量逐条等价）
   复现方案 §7.3 的判据，**不为了一个指标再读 2–3MB 的 raw.jsonl**。
   三态处理：没有 `history` 时是 `undefined`，不是 0（「算不出来」与「一次都没误读」必须可分）。

4. 口径进长期数据：`SessionLevelMetrics.waitSource` → `session-index.wait`
   （`max_concurrent` / `registered` / `duplicates_blocked` / `replacements` / `stale_claims`），
   键不存在 = 本会话没有等待事件（不是 0）。北极星 `northstar/README.md`「更省」节
   登记 p95 与分母口径（分母 = 有 `wait` 键的会话数）。

## 放弃了什么（以及为什么不选）

- **放弃「只在三入口各埋一次 `WaitAdmission`」**：判定点只有一份，埋点跟着复用走才能
  保证「新增入口不会漏埋」。代价是 `action: "start"` 只代表准入放行、不代表 spawn 成功，
  所以 `duplicates_blocked` / `replacements` 数的是判定，而「实际并存」只看
  `WaitRegistered` / `WaitReleased` 这对事实事件 —— 两组口径刻意分开，不合并成一个数。
- **放弃「把 stale 口径读 raw.jsonl」**：raw 的 `new_messages` 更权威，但为一个指标把
  2–3MB 文件再读一遍不划算，且 digest 的既有原则是不读 raw。改用 `traj.history`
  后与 §7.3 的 raw 参考实现在三个真实会话（b0aa0f1e / ca8d7e5c / 543e0e73）上
  算出 **4 / 2 / 1**，逐一相同 —— 等价性有实测、不是推断。
- **放弃「没 subjects 时按 `id` 或 `command` 归并」**：`id` 每次都是新的（b0aa0f1e 的
  4 条就是四个不同 id），按 id 归并等于没归并；`command` 是归一化后的整条命令，
  R1 已把它交给 `subjects` 的抽取器，回退再用一次等于把 `subjects` 的口径重写一遍、
  且两处必然分叉。`description` 是唯一还留着「同一个脚本」这个事实的字段。
- **放弃「让 `stale_notification_claims` 在无 history 时记 0」**：0 会被读成
  「一次都没误读」，比不出现更危险（北极星铁律：说不出取数源的数字就是自我感觉）。

## 拿什么证明它生效了

1. **验收 1（真实轨迹）**：夹具 `packages/core/tests/fixtures/wait-source/b0aa0f1e/`
   取自 2026-11-12 18:01:57 那次真实会话（`events.jsonl` 的 Wait\* 事件全量 +
   `session.traj` 的 `history[265..335]` 按 block 精简、路径脱敏，裁剪规则写在夹具 README）。
   期望值 **4 / 4**（并存 / 误读）来自方案 §7.3 的独立参考实现与人工逐条核对，
   不是从本实现反推：
   ```
   bun test ./packages/core/tests/trace/digest-wait-source.test.ts
   → 12 pass / 0 fail
   （registered 6、maxConcurrentWaitsPerSubject 4、staleNotificationClaims 4）
   ```
2. **四个反例**（同文件）：起了等待但 thinking 没声称被杀 → 不计；起了等待后真实通知
   送达再说「又超时」→ 不计；没起等待的 thinking 提「又超时」→ 不计；命中措辞但不在
   thinking 前 300 字 → 不计。少一个反例，口径就可能靠「宁可多算」通过验收。
3. **变异自证**：把并存峰值累加与误读累加各删掉一行 → 同文件 **5 fail**；恢复后
   **12 pass**。命令与输出见上；不做这一步，恒绿的测试只证明「实现自洽」。
4. **准入埋点单测**：`wait-admission.test.ts` 两条新用例断言 duplicate 也落
   `WaitAdmission`（含 `existing_ids` / `tool_use_id`）、subjects 抽不出的 start 也落一条
   → 17 pass / 0 fail。
5. **门禁**：`bun run typecheck:gate` → 62 处 / 基线 62 处，无新增；`bun run lint` /
   `bun run format:check` / `bun run lint:boundary` 全绿；`make build` 成功；
   `bun run smoke` 回放用例全绿（详见 PR 正文贴的输出）。
