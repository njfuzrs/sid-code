# Harbor 汇总的三处口径缺陷：同一个根因 —— 「一个数字有两个来源，而判据只看数值」

## 决定了什么

跑 A1（换模型臂）时，在**同一个根因**下抓到三处会污染已发表结论的缺陷，全部按
**fail-closed** 修掉。根因一句话：**同一个字段在不同路径下语义不同，而消费侧只比数值、不问来源。**

| # | 缺陷 | 后果 | 修法 |
| --- | --- | --- | --- |
| ① | `sid_num_turns` 兜底源是 `total_steps`（步骤数），却与 `MAX_TURNS=40` 比 | A2 **已发表的「撞满 40 轮 13/54」实为 12/54** | 源不是权威 result 事件时**一律不判撞满** |
| ② | `cost_usd` 混合口径，汇总只报合计不报混合比 | 兜底占比不同的两臂并排比成本时，**兜底多的那侧看起来更省** | 落 `n_traj_fallback` / `traj_fallback_tasks` + caveat |
| ③ | `w3-summary.py` 在跑动中途照样打印完整形态的 pass@1 | **中途快照可被直接复制进对照表**，而中途子集偏易 | 按 harbor 的 `finished_at` 判未跑完，加 🔴 caveat |

**① 的证据链**：上游本就是两个不同字段（`trace/collector.ts:2406-2407` 的
`turns: apiCalls` 与 `total_steps: pairs.length`），经 `sid_code_agent.py` 的两条路径
（`:857` result 事件 / `:821` traj 兜底）落到同一个 metadata 键。
实测比值：**A2 三个兜底样本恒为 2.0×，A1 达 2.3–5.3×**。
假阳性实例：`install-windows-3.11` —— `total_steps=42`、`api_calls=21`、
`subtype` 连 `error_max_turns` 都没有，却被计进「撞满 40 轮」。

**③ 的量级**：A1 跑到 16/54 时，把 A2 限制在**同一批 16 题**上，A2 通过率 **62.5%**，
而 A2 全集只有 **46.3%** ⇒ 当前子集**偏易 +16.2pp**。因为先跑完的是快的题，不是随机子集。

## 放弃了什么（以及为什么不选）

- **⛔ ① 不改成「兜底时按 api_calls 判撞满」**。`api_calls` 与 `num_turns` 也不是同一个量
  （一轮可含多次 API 调用，重试也计），换一个近似只是把错换个形状。
  fail-closed 漏报的代价是「少一条 caveat」，虚报的代价是「把正常结束的样本说成用完预算」——
  而那恰是这条 caveat 本身要人别误读的东西。**两个方向的代价不对称，所以选漏报。**
- **⛔ ③ 第一版判据「dataset 应有题数 − 已落盘 > 0」被我推翻了**，它在 A2 上**假红**：
  A2 的 job 声明 `terminal-bench-local@2.0`(66 题)，实际只跑并计分 54（§4.8 的历史）。
  于是一个**已跑完并已发表**的 run 被判成「还差 12 题」。
  **那比不判更坏 —— 它会让人怀疑一份正确的结论。**
  ⇒ 改取 job 级 `result.json` 的 `finished_at`（harbor 落的**观测值**），
  而不是我自己推断的题数差。与本仓 model/arm 都取观测值是同一条纪律。
- **⛔ ② 不去「修准」兜底成本**。兜底偏低是结构性的（`sid_code_agent.py:810`：
  最后 ≤30s 的调用没落盘），补不成准值。**能做的是把它标出来**，
  让下游知道这是下界 —— 冒充准值才是真错。
- **⛔ 不顺手修 `claude-sonnet-5` 缺 registry 条目**（见「证明」第 ⑤ 条）：
  当前数值正确，改动会动到 A2/A3 的必控变量，不该在 T4 中途做。

## 拿什么证明它生效了

**① 撞满轮数 13 → 12**：`w3-summary.py runs/w3-sid-sonnet-66` 与
`analyze-model-switch.py` 两处**独立**得到 12，`install-windows-3.11` 不再带标记。
归档 JSON 用 flatten diff 逐字段核过：差异**只有** `maxed_turns` 13→12、
该题 `maxed` True→False、caveat 文案 —— **pass@1 46.3% / scored=54 / $36.907914 逐字未变**
（因为 `maxed` 只驱动判读提醒，不参与计分）。

⚠️ **交叉验证时出现第三个数，我没当成新错误**：按 `subtype=error_max_turns` 计得 **14**。
差集是 `adaptive-rejection-sampler`(37 轮)、`mailman`(39)、`make-mips-interpreter`(38)，
它们满足 **`num_turns + 空转轮数 = maxTurns+1 = 41`**（实测 **14/14 全部满足**）
⇒ 属于「轮数被空转偷走」(#138)，判据没错。两个口径各自成立：
「真撞上限」12、「因轮数预算终止」14。**但都不该把 `total_steps` 混进来。**

**② 混合比**：A2 报 `3/54`、A1 报 `4/14`（跑动中），两侧都正确落盘。
量级也量化了：按「漏掉的调用与已记录调用单次均价相同」外推上界，
A1 14 题 **$1.0053 → $1.1212（+11.5%）**，单题最大 +40%。
⇒ 即使取上界，A1 均价仍远低于 A2 的 $0.683 ⇒ **「更省」的方向结论不依赖这个不确定性**。

**③ 未跑完闸**：A1（`finished_at=None`）报 🔴 caveat；A2（有时间戳）**不报**。
这是关键的一半 —— 只验「该报的报了」会放过假红（我第一版正是那样过的）。

**④ 门禁与回归**：`test-w3-classify.py` **24/0**；`make build` 自检全绿；
`bun run lint` / `lint:boundary` 干净；`affected-tests` 738 项、citations 23/0。

**⑤ 一次被推翻的结论（记下来防止下一棒重踩）**：我曾据「A2 的 `pricing_ratio`
中位恰好 0.6667」断言「记账用了兜底价 $2/$10，按官方价应为 $55.36」。**错的。**
查证后：`claude-sonnet-5` 确实不在 registry（pin 的 `30586ff0` 与 HEAD 双 MISS；
二进制里 `strings` 搜到的那个键来自 **catalog 能力快照**，不是价表），确实落
`FALLBACK_PRICING`；**但 ppchat 渠道自报的 sonnet-5 价与兜底价逐字段相同**
⇒ **$36.9079 数值是对的**。

> **「比值恰好等于某个常数」有两种解释**：① 记账用错了价；② **渠道真按那个价收钱**。
> 我第一反应只想到 ①。分辨方法是**回去查渠道自报价**，⛔ 不是从比值反推。

⚠️ 留下一个**当前无害但会咬人**的风险：那个相等是巧合。ppchat 调价或 A3 换上游
就会静默错账，而 `pricing_ratio` 判据**不会报**——它比的正是 `2/3`，
而 `2/10 ÷ 3/15` 恰好就是 `2/3`。**两层巧合叠起来，让缺失的价表条目看起来像配好了。**
已记入方案文档 §00.6，修法（给它补 registry 条目或在宿主 settings 配 `pricing`）留给下一棒。
