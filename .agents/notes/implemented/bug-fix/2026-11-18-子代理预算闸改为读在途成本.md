# 子代理预算闸改读「已入账 + 在途」成本，而不是只读已入账

## 决定了什么

PR #935（方案 PR7）给子代理接了请求前预算硬停，但**判据读错了数**：probe 读
`SessionState.getEffectiveTotalCostUSD()`，而子代理的花费只在它**结束之后**由
`agent/usage-sink.ts` 入账一次。于是子代理运行期间这个数一直是「它开始前」的值，
判据永远不触发。

G3 的 C4 实测（方案 §8.11）：`costLimit=$0.015` 下子代理跑了 **33 轮、花掉 $0.0441**
——预算的 **3.0 倍**——才自然完成，撞闸的反而是父会话的下一轮。

本次改动把「已花多少」的口径补齐，分四处落地：

1. `SessionState` 新增**在途用量台账**（`inFlightUsage: Map<agentId, {model, provider, usage}>`）
   与四个方法：`setInFlightUsage` / `clearInFlightUsage` / `getInFlightCostUSD` /
   `getBudgetEffectiveCostUSD`。`usage` 存的是**累计值**（覆盖写，不是增量累加），
   与循环自己维护的 `totalUsage` 同源。
2. `agentic-loop.ts` 新增 `onInFlightUsage` 回调，在主轮与总结轮的 `accumulateUsage()`
   之后各调一次 —— 上报时点是「这一轮已经真实计费」的瞬间，不是循环末尾
   （工具执行可能跑很久，那段时间判据就该知道这轮花了多少）。
3. `SubAgent` / `SubAgentTool` 成对注入上报器，`execute` / `executeCustom` 两个 finally
   的最前面清台账（不依赖后续可能抛错的 hook / 状态写盘分支）。
4. `app.ts` 的 probe 与 `query/loop.ts` 主循环那道闸都改读
   `getBudgetEffectiveCostUSD()` —— 两处判据读同一个数。

**刻意没有改 `getEffectiveTotalCostUSD()`**：它是展示与对账口径（footer、`/cost`、
轨迹 `total_cost_usd`），语义是「一笔已结算的钱」。改成含在途会让展示层在子代理运行
期间跳动，且轨迹出现「总额已含子代理、但 `SubagentCost` 事件还没发」的对账窗口。
新增的读口只给预算判据用，两个口径各自单一。

## 放弃了什么（以及为什么不选）

**方案 A：让子代理每轮直接 `updateUsage` 入账（改成权责发生制）。**
否决理由：这是**会计口径变更**，不是修 D3。每轮入账会改变 `SubagentCost` 事件与
`total_cost_usd` 的对账关系，还要处理「结束时补差额」与 `requests` 计数重复，
影响所有子代理（不只是配了预算的用户）。收益是主循环那道闸自动正确 ——
但用新读口同样能达到，不需要动既有口径。

**方案 B：只把「本子代理自己的在途用量」传进回调（probe 侧相加）。**
否决理由：并发子代理各算各的，n 个并发子代理会各花到预算上限（n 倍超支）；
且主循环那道闸仍然看不到后台子代理在烧钱。台账放在 `SessionState` 上，
判据读全体之和，这两个洞一起补掉。

**方案 C：不清台账，靠「子代理结束后 usage-sink 入账时覆盖」。**
否决理由：入账是**累加**，不会覆盖在途那一条；漏清会让判据把「已结束、且已入账」
的钱再算一遍，用户会在根本没花那么多时被拦停。清理必须显式挂在 finally 上。

**方案 D：把 in-flight 并进 `getEffectiveTotalCostUSD()`。**
否决理由同「决定了什么」末段：展示/对账口径与判据口径刻意分开。

## 拿什么证明它生效了

**① 单测（G1，17 个用例全绿）**

```bash
bun test ./packages/core/tests/agent/pr7-subagent-budget-stop.test.ts
# 17 pass / 0 fail / 68 expect() calls
```

新增 8 个用例，其中两条是核心判据：

- `e2e：第 1 轮花掉的钱立刻进判据，第 2 轮请求前就停` —— 一轮恰好 $0.0002，
  阈值 $0.00015：第 1 轮前在途 0（放行）→ 第 1 轮后 $0.0002 → 第 2 轮前命中，
  `stop_action=budget_exceeded`、`turns=1`、工具只执行一次。
- `对照：不上报在途用量时，同样的阈值不会触发` —— 同一个 probe、同样的阈值，
  只去掉上报器就不停（等价于修复前形态）。这条是「差异确实来自本次上报」的证伪对照。

**② 变异自证（先改坏，确认变红，再恢复）**

- 变异 A：注释掉主轮的 `reportInFlightUsage()` → e2e 用例变红（16 pass / 1 fail）。
- 变异 B：`getBudgetEffectiveCostUSD()` 退回 `getEffectiveTotalCostUSD()`（即 C4 失败形态）
  → 台账用例 + e2e 用例双双变红（15 pass / 2 fail）。
- 恢复后 17 pass / 0 fail，`grep -c MUTATION` 两文件均为 0。

本次改动的最终判据不是单测，而是**重跑 C4 的 S-F**：`costLimit=$0.015` 的 cap 组
必须出现 `stop_action=budget_exceeded`，且总额不再冲到预算的 3 倍。
