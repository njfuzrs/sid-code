# Hook 的 systemMessage 接上用户可见出口，事件名与 worktree 通道诊断统一

## 决定了什么

修 2026-10-19 Hook 指南页核查发现的 B1–B5（问题清单在维护者私有文档库）：

- **B1** `HookOutput.systemMessage` 此前没有任何消费点。现在 `event-handler.ts` 在聚合之后调用
  `reportHookSystemMessage`（`diagnostic-sink.ts` 里的模块级 sink）。cli 层的接法：TUI 进状态行
  （transient 8s，只显示首行），`-p` 写 stderr。sink 注册前产生的消息先暂存，最多 20 条，注册时补发
  （SessionStart 跑在 TUI 注册之前）。对齐 CC，`Setup` / `InstructionsLoaded` / `Notification` /
  `ConfigChange` / `PreCompact` / `PostCompact` 的 systemMessage 直接丢弃。
  配套改动：exit 0 的纯文本 stdout **不再**写进 systemMessage（`runner.ts` parseCommandOutput），
  否则每个 `echo ok` 的审计 hook 都会刷状态行。原始文本仍保留在 `HookExecutionResult.stdout`。
- **B2** `LEGACY_EVENT_MAP` 补上 `after_agent` / `before_model` / `after_model`。新增一条表驱动测试，
  遍历枚举，每个可配事件都必须有 snake_case 映射。
- **B3** `UserPromptExpansion` 加入 `CONTEXT_STDOUT_EVENTS`，与 CC 文档的名单一致。它也是可 block
  事件（executor 按 isBlockingDecision 拦截），所以同步改走 `mergeWithOrDecision`（被
  aggregator-veto 哨兵抓到）。
- **B4** 归一化层遇到 `WorktreeCreate` / `WorktreeRemove`（只认 PascalCase）时静默跳过，不再告警
  「未知事件」。`hooks list` 把它们单列出来，并标明「由 worktree 子系统执行」。
- **B5** 新增 `parseWorktreeCreateOutput`：先认 JSON 的 `hookSpecificOutput.worktreePath`，否则取最后一个
  非空行，并去掉 ANSI 转义。

## 放弃了什么（以及为什么不选）

- **B1 选 B 方案（不展示，只删文档承诺）**：会让「exit 1 的 lint 审计 hook」这类最常见的用法永远静默，
  而 CC 是展示的。迁移过来的用户照 CC 文档写，结果什么都看不到，这是行为偏差，不只是文档问题。
- **B1 在各 fire 调用点各自读 systemMessage**：调用点有 30 多个，漏一个就退化，下一次新增事件还要再记得接。
  放在 executeHooks 这一个汇聚点，覆盖全部事件，agent 的隔离 HookSystem 也走同一个模块级 sink。
- **B1 保留 exit 0 stdout → systemMessage**：一旦展示，会把「纯审计 hook」变成噪音源。CC 对大多数事件
  的 stdout 也只写 debug 日志。
- **B3 把 PostModelSwitch 一起加入名单**（CC 有）：sid 的两处调用点（app.ts）不读结果，加了也没人消费，
  等于把一句假承诺写进代码。等接上消费方时再加。
- **B4 方案 A（把两个事件加进 HookEventName）**：枚举成员会进参考页、进 aggregator-veto 遍历、进 B2
  映射断言，还会被读成「HookSystem 会分发它」。它们本来就不走 HookSystem，用独立白名单更准确。
  snake_case 写法刻意不静默，因为 worktree/hooks.ts 按字面量 PascalCase 取值，静默掉会把「写错了」
  藏起来。
