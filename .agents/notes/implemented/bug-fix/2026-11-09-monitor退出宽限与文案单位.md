# monitor 父进程退出即终态（exit 排空宽限）与通知文案单位（D15 / D18）

## 决定了什么

### D15：`exit` 事件 + 400ms 有界排空宽限，宽限到就清进程组

`packages/core/src/task/monitor-task.ts` 在 `child.on("close")` 之外新增 `child.on("exit")`：

- `exit` 到达后挂 `EXIT_DRAIN_GRACE_MS = 400`（与 `tool/bash.ts` 的
  `PIPE_DRAIN_GRACE_MS` 同值同义）的定时器；
- 宽限内 `close` 到了 → 走原路径（`stdout` 的 `data`/`end` 已处理完，残行仍能带上）；
- 宽限到了 `close` 还没到 → 先 `killMonitorProcessGroup(ctl)` 清孙进程，
  再 `child.stdout?.destroy()` / `child.stderr?.destroy()`，然后走**同一个**
  `finalizeAndDrain`（D3 引入的唯一终态出口），退出码取 `exit` 事件给的值；
- 两条路径靠 `ctl.finalized` 互斥，终态只发一条；新增的 `exitDrainTimer`
  纳入 `clearMonitorTimers`，不留悬挂定时器。

根因是 `close` 要等**所有** stdio 流关闭，而孙进程继承了 stdout 管道的写端：
`sleep 60 & exit 0` 时父 shell 毫秒级就退出了，`close` 却要等孙进程结束（`tail -f`
时就是等到期限）。D15 的契约是「脚本结束 = 监控结束」，`tool/monitor.ts` 的
描述里同步加了一段，明确告诉模型不要靠 `&` 留后台监听。

### D18：文案集中到 `task/monitor-text.ts`，两个单位写死

- 新建 `packages/core/src/task/monitor-text.ts`，三个 formatter 是全仓唯一来源：
  `formatDeferredMergeNotice`（限流延迟提示）、`formatOmittedLinesNotice`
  （冲刷截断提示）、`formatDeliverySummary`（终态投递摘要）；
- `admit()` 的「…另有 N 条」改为**末尾**的「（以上含 N 行因限流延迟，非实时）」。
  放末尾是因为 `TaskNotificationMessage` 只取事件首行作摘要，放首行会污染摘要行；
  措辞说的是「以上含」，本来也得在行后；
- `LocalMonitorTaskState` 新增 `outputLines`，在 `pushLines` 与
  `finalizeAndDrain` 的残行处累加；
- 三个终态（exit / timeout / `task_stop`）统一成
  「共投递 N 条通知，输出共 M 行」；到期 0 条时提示「未投递任何通知，请检查过滤条件
  是否覆盖了失败状态」。

## 放弃了什么（以及为什么不选）

- **把 `toolUseId` 补进 `spawnMonitorTask`**：通知 XML 里没有 `<tool-use-id>`，
  模型无法把事件与具体调用对上号。但 `Tool.call(input, context)` 的 `ToolUseContext`
  没有 `toolUseId`（`tool/types.ts`），bash 的后台通知同样没有（`bash.ts` 注释明说），
  两者一致。改它要动工具调用签名，代价远大于收益（方案也判定「不修」）。
- **`exit` 到达即收尾（不等 stdio）**：会让 `printf abc` 这类无换行残行在 `close`
  才读到时丢失。保留 `close` 优先、`exit` 只做有界兜底。
- **宽限内只 `destroy` 流、不 kill 进程组**：孙进程会继续活着占进程组，`ps` 里残留，
  与「脚本结束 = 监控结束」的契约不符。代价是 `nohup tail -f &` 这类**故意**脱离的
  后台进程也会被清掉——这正是契约要的行为，已写进工具描述。
- **文档设想的变异「宽限设 0 并去掉 close 等待 → T-M1-9 红」实测不成立**：
  把 `exit` 改成同步 `finalizeAndDrain` 时 T-M1-9 仍绿——残行由 `stdout.end` 与
  `finalizeAndDrain` 两处 `splitter.flush()` 兜住。改用等价变异
  「`LineSplitter.flush()` 永远返回 null」才稳定命中。这说明 T-M1-9 锁住的是
  「残行被冲刷」，不是「必须等 close」；后者由 D15 的 R8 用例锁住。
- **给条目数字各写一个独立函数**：`formatDeliverySummary` 用一个函数收口两个单位，
  不像三处文案那样各写各的——分散正是这次漂移的根因。

## 拿什么证明它生效了

```text
bun test ./packages/core/tests/task/monitor-task.test.ts ./packages/core/tests/tool/monitor.test.ts
42 pass / 0 fail / 260 expect() calls
```

- R8 迁入：`sleep 4 & echo started; exit 0` → 400ms 内 `completed`、事件含 `started`、
  终态通知恰一条（D15）；
- 孙进程清理：`sleep 60 & echo child=$!; exit 0` → 终态后 `process.kill(pid, 0)` 抛 `ESRCH`；
- T-M1-7 方案原文场景（`sleep 60 & exit 0`）已恢复，与原有「kill 清理孙进程」用例并列；
- T-M1-9 回归：`printf abc; exit 0` 的残行仍作为事件送达；
- D18：限流合并提示不含「另有」、含「2 行因限流延迟」；终态摘要
  「共投递 1 条通知，输出共 3 行」且 M 等于脚本真实行数；`task_stop` 终态同样两单位。
