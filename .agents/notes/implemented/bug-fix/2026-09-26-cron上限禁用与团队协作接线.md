# cron 上限/禁用开关补齐，团队协作层四项半成品接线完成

## 决定了什么

对照 2026-08-15 的对齐方案（20 号文档）核过当前源码后，把仍未修或只修一半的项补完，
全部落在调度器与团队协作这两层：

- **P0-1 cron 任务上限**：守卫下沉到 `Scheduler.addSessionTask` / `addDurableTask`，
  会话级 50、daemon 聚合级 500 两档。`cron_create`、`schedule_wakeup`、`/loop` 三个入口
  都走这两个方法，工具层无法绕过；达上限返回结构化错误且不入队。
- **P0-2 cron 整体禁用**：新增 `SID_CODE_DISABLE_CRON`（`=1` / `=true`）。三层都拦——
  工具注册层不注册四个 cron 工具、调度器 `start()` 不启动轮询（已持久化任务也不会触发）、
  `/loop` 三种用法全部拒绝且动态轮询不退化成 `submit_prompt`。
- **P1-2 teammate 会话注册**：团队成员执行时以 `kind: "teammate"` 注册进活跃会话表
  （身份取自 ALS，普通子代理不注册），结束即注销。teammate 与宿主同进程，
  探活不看 PID 而看其后台任务是否仍在注册表且未终态，否则 `/ps` 会留下永不消失的条目。
- **P1-3 单会话任务清单落盘**：团队清单此前已落盘，主会话 TODO 仍是纯内存。
  新增 `session-task-store`，按 sessionId 落 `~/.sid-code/tasks/sessions/<id>.json`，
  启动时恢复。恢复只替换无团队标记的任务，与团队落盘互不覆盖；
  ID 撞车时重映射，计数器抬到「已占用 ID 与快照自身 ID」的最大值之上
  （只抬已占用的话，重映射会重新发出快照里未撞车的 ID，后写覆盖先写）。
- **P1-4 `/workflows` 进度树**：journal 记录新增 `phase` 字段（不参与指纹，
  改 phase 名不破坏 resume 缓存），`/workflows <runId>` 按 phase 分组渲染，
  phase 为父节点、agent 为 ⎿ 子节点，分组顺序按首次出现的 callIndex。
- **P1-5 按名寻址与广播**：`team_message` 的 `to: "*"` 广播给除自己外的全部成员；
  `send_message` 在团队上下文里 `to` 支持成员名与 `"*"`，成员侧走 ALS，
  leader 侧走 `withActiveTeam` 登记的活跃团队。该登记返回 Promise 而非同步值——
  同步返回会让 finally 在成员跑完前就清除登记，leader 的投递窗口为空。

## 放弃了什么（以及为什么不选）

- **上限守卫放在工具层**：三个创建入口各自检查必然有漏，`/loop` 直建任务不经
  `cron_create`，放工具层会被它绕过。下沉到 scheduler 的两个 add 方法后入口再增加也不用改。
- **daemon 与会话共用 50 上限**：daemon 跨项目聚合全机 durable 任务，套会话级 50
  会把多项目场景卡死。对齐方案原建议的 500 档保留。
- **单会话清单用 JSONL 事件溯源**：团队清单已经是全量 JSON 原子写（temp + rename），
  会话级照同一套做，两套落盘机制并存的维护成本大于并发追加带来的收益
  （主会话清单只有一个写入者）。
- **把成员名寻址塞进 `send_message` 的 task_id 解析**：曾考虑只扩展 `send_message`，
  但成员侧已有 `team_message` 按名投递。最终两者都保留——`team_message` 是成员主动发消息的
  语义入口，`send_message` 补的是 leader（主代理）没有 ALS 上下文时的按名能力。
  名字只在团队上下文里有意义，解析不到就退回 task_id，两类寻址互不干扰。
- **shutdown_request 一类结构化控制消息**：方案自己标注它随常驻协作会话（P2-5）一起做，
  一次性批里没有消费这种消息的循环，现在加只有写入端没有读取端。
- **teammate 按 PID 探活**：teammate 是同进程子代理，PID 恒为宿主进程，
  按 PID 判活会让已结束的成员永远留在 `/ps` 里。改看任务终态。

## 拿什么证明它生效了

新增与修改的测试共 59 个用例，一次跑通（0 fail）：

```bash
bun test ./packages/core/tests/cron/cron-limits.test.ts \
  ./packages/core/tests/task/session-task-store.test.ts \
  ./packages/core/tests/session/teammate-registration.test.ts \
  ./packages/core/tests/swarm/send-message-team.test.ts \
  ./packages/core/tests/swarm/team-message.test.ts \
  ./packages/core/tests/workflow/journal.test.ts \
  ./packages/cli/tests/command/workflows.test.ts \
  ./packages/cli/tests/command/loop-limits.test.ts
# 59 pass, 0 fail
```

覆盖的关键断言：第 51 个会话级任务被拒且不入队、删除后可再建、daemon 模式第 51 个仍可加；
`SID_CODE_DISABLE_CRON=1` 时工具拒绝创建、`start()` 后已到期任务不被触发、
`/loop` 三种用法全拒且动态轮询不退化成 `submit_prompt`；teammate 任务终态后会话算 stale；
会话清单恢复不动团队分区、ID 撞车重映射后依赖边仍指向正确任务；
journal 改 phase 名后 resume 全部命中缓存；`/workflows` 详情里同 phase 的 agent 归组在一起；
`withActiveTeam` 期间 leader 按名与广播投递成功、抛错后登记被清除。

既有回归：`packages/core/tests/cron/`、`packages/core/tests/workflow/runtime.test.ts`、
`packages/core/tests/task/team-task-store.test.ts` 共 96 pass / 0 fail。
