# Worktree 创建/清理不再改主仓状态，同名分支与 hook 各加一道闸（W6–W10）

## 决定了什么

来源：`docs-research/sid-code/bugfixes/todo/20260926-Worktree隔离-顺着sc-19核出的缺陷.md`，本轮只做 W6–W10。

- **W6** `manager.ts` postCreationSetup：删掉 `git config core.hooksPath <主仓>/.git/hooks`。
  worktree 没有自己的仓库级 config，这条命令写进的是主仓 `.git/config`，会覆盖 husky 的 `.husky`，删 worktree 也不还原。
  而它想要的效果本来就是 git 的默认行为：没设 hooksPath 时 worktree 直接用主仓 hooks（实测）。
- **W7** `installCommitAttributionHook`：hooks 目录用 `--path-format=absolute --git-path hooks` 解析。
  它落在本 worktree 的 `--absolute-git-dir` 之外（也就是主仓共享目录）时，不安装，改成返回一条 setupWarning。
- **W8** `cleanup.ts`：GC 删分支之前先读 worktree 实际检出的分支。
  只有它等于 `worktree-<dir>` 时才删，否则传空串，`remove()` 见到空串就一条分支都不删。
- **W9** `create()`：`worktree add -B` 之前，先数目标分支上有几个「别的 ref 都够不到」的 commit。
  有就拒绝，分支指针保持不动。空的残留分支照常重建，保住 D4 的幂等性。
  这个检查放在 `resolveBaseTreeish` 之前，因为 PR 模式的 fetch 会改写这条分支。
- **W10** `hooks.ts`：worktree hook 改为逐来源读取，同样受 `--setting-sources` 过滤。
  项目级 `.sid-code/settings.json` 里的 hook，只在 `TrustManager.isTrustedSync()` 为真时才认。
  hook 打印的路径要过 `validateHookWorktreePath`：必须是绝对路径、真实存在的目录，且不是 `/`，也不是主仓根。
  `trust.ts` 新增 `isTrustedSync`，判据和 `isTrusted` 一样（路径 hash + 配置 hash）。

## 放弃了什么（以及为什么不选）

- **W6 改成 `git config --worktree`**：前提是先在主仓打开 `extensions.worktreeConfig`，一样是在改主仓配置。实测不带这个扩展会直接报错。
- **W7 把 hook 写进 `.git/worktrees/<name>/hooks`**：git 不会执行那个目录里的脚本（实测 0 次触发）。装进去只是换了个地方的死文件。
- **W9 分支已存在就自动换个名字**：同名 `enter_worktree` 每次会落到不同的分支上。用户以为回到了自己的工作，其实进的是一条新分支。报错虽然打断流程，但可以恢复。
- **W10 把 `hooks` 加进 `filterProjectSettings`**：那会连带让仓库里所有项目级 hook（PreToolUse 之类）永久失效，范围比 W10 大得多。现有信任机制已经有「信任后生效、配置变更后失效」的语义，直接复用它。
- **W10 把 `hasWorktreeCreateHook` 改成 async**：cli.ts 的工具注册条件是同步调用它的，整条链都得跟着改。所以改为新增一个同步的信任判断。
