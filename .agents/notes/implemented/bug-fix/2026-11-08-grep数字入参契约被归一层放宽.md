# grep 数字入参的契约被归一层放宽：区间切分吞负号、coerce 把空串变「不限条数」

## 决定了什么

台账 B25（Harness 厚薄归位专项，#672）。两处改动，原则都是「判不准就让 zod 报错，不替模型编一个更宽的值」：

1. `tool/numeric-coerce.ts` 的 `parseIntendedNumber`：区间形态先把**前导符号**剥下来，切完取首数再贴回去；除前导符号外**不许有空段**。修复前的写法是切完 `filter` 掉空段，于是 `"-5-3"` → 5（负号被当分隔符切掉），`"1,,2"` → 1、`"3--5"` → 3（中间空段被吞）。模块头注释写着「拒绝 `"1,,2"`」，代码其实接受它。
2. `tool/grep.ts` 的 7 个数字字段从 `z.coerce.number()` 改成 `z.number()`。数字归一层按设计把 `""` / `true` / `[]` 原样放回让 zod 报错（`input-validator.ts:91-93` 的注释就是这么写的），但到了 coerce 字段，zod 会把它们静默转成 0 / 1 / 0。`head_limit:""` 就这样变成 0，也就是「不限条数」。

改完以后 `"5"` → 5、`"117, 130"` → 117 照常生效（由归一层处理），`null` 仍然由 nullish-normalize 摘掉。新增 `packages/core/tests/tool/grep-numeric-contract.test.ts`，走真实的 `GrepTool` + `validateToolInput`；`numeric-coerce.test.ts` 加了 2 条接受、4 条拒绝。

## 放弃了什么（以及为什么不选）

- **只修归一层、保留 grep 的 coerce，让归一层把放回的 `""` 改成 NaN 来逼 zod 报错**：不选。这是拿一个哨兵值去对冲另一个隐式转换，报错文案会变成「实际收到 NaN」，模型看不懂；而且以后任何新的 coerce 字段都会再次绕开。coerce 在这里已经没有正面作用了（`"5"` 已经由归一层处理），删掉它才是根治。
- **`"-5-3"` 整串拒绝，不保留首数**：不选。模块的既定规则是「区间取首个数」，修复前的注释也写明本意是「避免 `-3-5` 被切出空段」，也就是要支持负数起点。保留符号以后，grep 的 `offset` 由 `min(0)` 拒绝，报错指向的正是模型的真实问题（传了负数）。对没有 `min(0)` 的字段，结果与「取首数」规则一致。
- **顺手给 `mcp serve` 的 `tools/call` 补 zod 校验**：不在本 PR。它直接调 `tool.execute`，不经过 `validateToolInput`（`entrypoints/mcp-serve.ts:220`），有没有 coerce 对它都一样。这是另一个关注点。

## 拿什么证明它生效了

- 修复前探针（`validateToolInput(new GrepTool(), …)`）：`offset:"-5-3"` → OK 5；`head_limit:""` → OK 0；`head_limit:"  "` → OK 0；`context:""` → OK 0；`offset:""` → OK 0。修复后这 5 条全部 FAIL；`head_limit:"5"` → 5、`offset:"117, 130"` → 117、`offset:"3-5"` → 3 不变。
- 变异自证：
  - 把 `parseIntendedNumber` 改回「切完 filter 空段、不贴符号」→ 6 fail（负数区间 2 条、中间空段 2 条，grep 契约 2 条）；
  - 把 grep 的 `head_limit` / `context` 改回 `z.coerce` → 4 fail（空串、纯空白、空数组、`context` 空串）。
  - 两次都已恢复，恢复后 61 pass。
- `bun run affected-tests:run`：1338 pass / 0 fail。跨域引用 grep 的 3 个测试文件：175 pass。`docs:gen-reference` 无产物差异（`z.number()` 与 `z.coerce.number()` 生成的 JSON Schema 相同）。`make build` 自检通过。
