# MCP 零调用的真因是权限层拦死 tool_search；顺带修两处 OAuth / 遥测缺陷（B21 / B22）

## 决定了什么

来源：整改清单 B21（MCP OAuth 端到端实测）与 B22（配了 6 个 MCP、70+ 会话 `mcp__` 调用 0 次）。

B22 原先列了三种可能成因：① 没连上，② 连上了但模型不去搜，③ 任务用不到。实测下来**三种都不是**，
是第四种：**模型去搜了，但在权限层被拒**。

- **`tool_search`、`ListMcpResources` 进 `READ_ONLY_TOOLS`**（`permission/checker.ts`）。
  MCP 工具默认延迟加载，`tool_search` 是把它们调进上下文的唯一入口；它只改 registry 的激活集，
  `readOnly()` 本来就是 true，但不在白名单里 → 落到 Step 14 默认 ask → 无头模式与子代理一律 deny。
  这和 2026-08-01 `hypothesis_*` 被拦是同一形态，也是同一个 Set。
  `ReadMcpResource` 刻意不放（会落盘、返回外部不可信内容）；被调出来的 `mcp__*` 工具每次调用仍然各自走权限判定。
- **`_ctx_mcp_server_count` 接线**（`analytics/metadata.ts` 新增 `setMcpServerCount`，`cli.ts` 在 connectAll 完成后回填已连接数）。
  修前全仓没有任何调用方传这个值，1,616 个会话里全部是 0。因为 MCP 连接是异步的，
  先于 analytics 初始化完成的那次回填会先暂存，等元数据初始化时再补上。
- **OAuth 授权 URL 直出 stderr**（`cli.ts` 设置 `mcpManager.onOAuthAuthorizationUrl`）。
  修前这个回调零接线，URL 只走 `log.info`；不开 `-d` 时 logger 停在 WARN 级，URL 被静默丢掉，
  回调服务器干等 5 分钟，用户看到的就是「连不上、没提示」。
- **官网 `extend/mcp.md`**：新增「需要登录的远程 server（OAuth）」一节，并补了无头模式下要用 `--allowed-tools` 放行 MCP 工具的提示。
  OAuth 一节如实写明只在本地 mock 上验证过。

## 放弃了什么（以及为什么不选）

- **把 `mcp__*` 在无头模式下整体放行**：否决。MCP 工具的 `readOnlyHint` 来自 server 自报，等于把权限决策交给外部进程。
  只放行「发现」入口、不放行「执行」，是这次修复的边界。
- **在 `ToolSearchTool` 上加 `alwaysAllow` 之类的属性绕过 checker**：否决。白名单只能有一个事实源；
  `hypothesis_*` 那次已经确立了「只读工具进 `READ_ONLY_TOOLS`」的做法，再开第二条路径就是两套名单漂移的起点。
- **`mcp_server_count` 记配置数**：否决。配置数从配置文件就能看到，分析时缺的是「这个会话实际可用几个」。
  本机就有 1 个配置了但永远连不上的 server（vibe-coding 内网地址），两者确实会不一样。
- **用公开的第三方 OAuth server 做 B21 实测**：本轮没做。过期刷新需要能控制 token 有效期，只有本地 mock 能做到；
  公开 server 还需要人工在浏览器里授权。所以文档里写的是「只在 mock 上跑通过」。
- **自动打开浏览器**：本轮不做。仓库里没有现成的跨平台打开浏览器的工具函数，而且 SSH / 容器场景下打开本机浏览器反而是错的；
  先保证 URL 一定能被看到。

## 拿什么证明它生效了

- **B22 对照实验**：用隔离的 `SID_CONFIG_DIR` 复制用户的 settings（6 个 MCP），同一条 prompt「用 context7 查 Bun.serve 的 idleTimeout」：
  - 修前二进制：5 个 server 连上（88 个工具），模型调 `tool_search("context7")` 和 `select:mcp__context7__*` 都被拒，
    日志写着「非交互模式自动拒绝」，最后退回 `web_fetch` 作答。
  - 修后二进制：`tool_search` 9 次全部放行，模型激活并调用了 `mcp__context7__resolve-library-id` 6 次（被权限拒，符合设计）。
  - 修后 + `--allowed-tools mcp__context7__*`：`resolve-library-id` 3 次、`query-docs` 3 次，答复引用的是 context7 返回的 `serve.d.ts @default 10`。
  - 遥测：修后同一会话的 `_ctx_mcp_server_count` 从 0 变成 5（MCP 连上之前发出的事件仍是 0，符合预期）。
- **B21 OAuth 全链路**：本地 mock（RFC 9728 + 8414 + 动态注册 + PKCE S256 + refresh 轮换，token 有效期设为 8s），
  用仓库里的 `MCPManager` 驱动：首次连接依次走了发现 → 注册 → 授权 → 回调 → PKCE 换 token → 连接 → `tools/call`；
  等 token 过期后重连，没有再触发交互授权，access token 和 refresh token 都换了新的；`mcp-oauth.json` 权限是 `-rw-------`。
  再用真实二进制无头跑一次：修前 stderr 里 `authorize?` 出现 0 次，修后 1 次。
- **测试**：`checker.test.ts` 新增 6 条，`metadata-mcp-count.test.ts` 新增 4 条（两种时序都覆盖）。
  变异自证：从白名单里删掉 `tool_search`，对应断言变红；把暂存值改回 `0`，2 条断言变红。
- **未验证**：没有对接真实的第三方 OAuth 授权服务器；交互 TUI 里 stderr 的 URL 会不会被 Ink 重绘盖住，也没实测
  （connectAll 发生在 App 渲染之前，大概率能看到，但没截图）。
