# OpenAI 兼容路径的四个发送入口补上 x-client-request-id

## 决定了什么

`packages/core/src/llm/openai.ts` 的四个发送入口（Chat 流式、Responses 流式、Chat 非流式、Responses 非流式）在发请求前各生成一个 `generateClientRequestId()`，做三件事：

- 放进请求头 `x-client-request-id`，和 `anthropic.ts` 保持一致。
- 写进发送前的 debug 日志。
- 在所有失败日志里带上，包括 HTTP 非 2xx、流式 catch 和非流式 catch 的 `AUDIT:API` 行。

Responses 流式的 fetch 在主 try 之外，拿到响应头之前的失败（响应头超时、连接失败）不会进主 catch，所以单独补了一条 `AUDIT:API` 留痕。

动机是：超时、断流、用户中断这几类失败都拿不到响应头，也就没有网关的 `x-oneapi-request-id` 这类标识，之前去找网关方对账时手里什么都没有。这类失败恰恰最需要排障，而 DeepSeek、Kimi、Qwen 和各家网关走的都是 OpenAI 兼容这条路径。服务的方向是可观测性。

## 放弃了什么（以及为什么不选）

- **在 provider 外层（fallback 或 query loop）统一生成一个 ID**：外层的一次逻辑调用会重试多次，共用一个 ID 就分不清是哪一次 HTTP 尝试。现在每次 fetch 生成一个，口径和 anthropic.ts 一致。如果以后需要把多次重试归成一组，应该另加一个逻辑调用 ID，而不是复用这个字段。
- **复用 `logAPIError`**：全仓目前没有调用方（grep 只命中定义本身）。为这次改动把它接进来，会改变两条路径现有的日志口径，超出了本次范围。这里沿用 openai.ts 已有的 `AUDIT:API` 行，只追加 `clientReqId=` 字段。
- **当作幂等键用**：LLM 接口一般不会按这个头去重，它只用来关联日志，防不了重复计费，所以注释里没有这样承诺。

## 拿什么证明它生效了

- 新增测试 `packages/core/tests/llm/openai-client-request-id.test.ts`，5 个用例覆盖四个入口，外加 HTTP 错误路径和每次请求 ID 不同两项检查，结果 5 pass。
- 做了变异自证：把 Responses 非流式的头名改成 `x-client-request-id-MUTATED` 后，只有对应用例变红（4 pass / 1 fail）。恢复后 grep 确认 `"x-client-request-id": clientRequestId` 有 4 处。
- `bun run affected-tests:run`：119 个文件，2107 pass / 0 fail。在 worktree 内单独 `bun install` 之后才跑出这个结果；软链到主仓 `node_modules` 时，`@sid-code/core` 会被解析到主仓源码，出现 2 条和本次改动无关的失败。
- `bun run typecheck:gate` 66/66，没有新增。`lint`、`format:check`、`lint:boundary` 全绿。`make build` 自检通过，没有 `will always be undefined` 告警。
