# 补传迁入维护子进程（流式压缩 + 持久化退避），清理首帧前的同步子进程

承接 #501 的不变量：**TUI 进程在首帧前和交互期间，主线程不做任何耗时随 `~/.sid-code/` 数据量增长的工作。**
本 PR 合并了方案文档的 PR-C（U1–U4）与 PR-D（X1 + M1）。北极星方向是**更快**；牺牲的是**可观测**的及时性：
补传最晚在首帧后、按 1h 维护水位线触发，退避中的会话要等退避结束才再传。

## 决定了什么

PR-C：补传
- **U4 搬家**：启动补传 + 重试队列从 collector 的 SessionStart 挪进维护子进程的 `trace-upload` 任务（`maintenance/runner.ts`）。
  cli 按原判定条件排任务（采集开、url+token、`auto_upload` 没关、非 essential-traffic），把本进程会话 id 和被恢复的会话 id 作为受保护名单传进去。
  `availableModels` 只传定价字段，不带 `api_key`。collector 里不再触发补传，`TraceUploaderInterface.backfillPendingSessions` 也一并删掉。
- **U4 退避与终态**（`trace/upload-attempts.ts`）：失败记到会话目录的 `.upload-attempts`，按 1h·2^(n-1) 退避，48h 封顶。
  第 8 次失败写 `.upload-failed` 终态，之后不再自动重试，在 `/debug` 和 `--upload-traces` 里点名。
  手动命令无视退避，成功后清掉退避记录。被中止（退出）的那一次不算失败。
  这些记账文件写入时**保持会话目录 mtime 不变**，因为 mtime 是补传时间闸、LRU 淘汰、空壳静置判据的输入。
- **U1 流式压缩**（`trace/upload-compress.ts`）：`stream → 逐行变换（只留本地字段 / 家目录脱敏）→ CompressionStream → 落盘 .upload-cache/`，边写边算 SHA256。
  缓存按源文件 size+mtime 加变换选项失效，重试和下次启动直接复用，不再每次重压。
- **U2 成本重算**：去重判据从 traj 本体（不 parse 全文就读不到）移到 `.cost-recomputed` sidecar，一次 stat 就能判断。
  events.jsonl 改成按 1MB 块读，超过 1MB 且行首 4KB 不含 `"AfterModelRaw"` 的行在字节层丢掉，不解码也不 parse。
- **U3 上传体**：手拼流式 multipart（async generator 作 body + 显式 Content-Length），不再用 FormData。

PR-D：首帧前同步子进程
- `isCommandAvailable` 改成 `Bun.which()`（原来 10 次 `execSync which`，约 60ms）。
- gitignore 注册改成异步 `Bun.spawn`，「是否在仓库内」按 cwd 缓存，6 个文件共用一个答案（原来 12 次同步 fork，约 50ms）。
- `loadAllCLAUDEmd` 的 `activeFiles` 改成惰性：只有遇到带非空 `paths:` 的规则才跑 `git status -uall`（原来每次都跑，启动两遍约 88ms）。
- git 状态附件不再跑 `git status --short`：它的结果自 P0-1 起就 `void status` 不进快照，却是这里最贵的一条（约 47ms）。
- git 快照（`head/dirty`）和埋点 `vcs_type/repo_hash` 在 loadConfig 前异步并发预取，同步读取命中缓存；没跑完时仍同步现算，结果一致。
- 状态栏分支名首帧先给空串，异步取到后再 `updateState`。
- worktree GC 并入维护子进程（`worktree-gc` 任务，24h 水位线）。W2 约束不变：payload 在 `startBackgroundMaintenance` 里构造，这个函数在归属复核之后才调用，所以 skipPath 是复核后的事实。
- M1：`MemoryStore.load` 期间迁移那一步已经读过的文本按 mtime 缓存，`loadDir` 直接复用，记忆文件不再读两遍。

## 放弃了什么（以及为什么不选）

- **FormData + `Bun.file` 懒引用**：Bun 会把 FormData 整份物化。300MB 文件实测客户端 RSS 峰值 FormData +631MB，generator +41MB。
  直接 append BunFile 时，文件名还会变成缓存文件的绝对路径（含本机用户名，单测抓到的）。
  另外试过两条都不行：`new Blob([head, Bun.file(), tail])` 作 body 只发出 148 字节；ReadableStream 作 body 时本地 server 收到 0 字节。
- **补传留在 TUI 进程、改成 setTimeout / 首帧后再跑**：只改了什么时候跑，没改在哪个线程跑，同步压缩仍然卡交互（方案文档 1.2）。
- **按大小在本地判终态（超限不传）**：没做。服务端没有大小上限的契约，本地硬判会让「本来传得上」的会话永远不传。改由失败次数判终态，判据只看实际结果。
- **服务端分片上传（PR-C2）**：需要服务端配合，不在本 PR。
- **worktree GC 留在 TUI 里改成异步 git**：`cleanupStaleWorktrees` 内部有十几处同步 git，逐一改异步改动面大；并入已有的维护子进程是现成的隔离边界。
- **首帧前剩下的 memory/paths（2 次）、worktree/manager（1 次）和 attachments（5 次）同步 git**：没改，合计约 50ms，不随数据量增长。
  前者决定记忆 key，首帧前必须有；后者是系统提示词的组成部分，改异步要动 `buildSystemPrompt` 的同步契约。留给后续。

## 拿什么证明它生效了

- 大数据启动门禁 `packages/cli/tests/startup/large-data-startup-gate.test.ts`：去掉补传用例的 skip，新增「配了上传 + 200MB traj」目录。
  修复后 Δ首帧 −21~+17ms、Δ最大阻塞 −19~0ms（3 次中位数），7 条全过。
  **变异自证**：把补传放回 collector 的 SessionStart，Δ首帧 +297ms、Δ阻塞 +140ms，门禁变红；恢复后变绿。
  变异过程中暴露并修掉了三处门禁空转：
  1. fixture 没写 `trace.enabled`，补传根本没排；
  2. fixture 的 events 里没有 AfterModelRaw，U2 没被覆盖；
  3. 挂起不响应的 server 让子进程一直持锁，后几轮整轮跳过（改成立刻回 502，每轮之间清记账并等锁释放）。
  另加了一条防空转断言：压缩缓存落盘、请求到达 server、`.upload-attempts` 写入，三者都要看到。
- `packages/core/tests/trace/upload-pipeline-pr-c.test.ts`（11 条）：逐行变换与整份变换逐字节相同、跨 chunk 边界、无尾换行；
  缓存命中与失效；multipart 能被标准解析器还原且 Content-Length 精确；巨型行被字节层丢弃；sidecar 让第二次不读 traj、events 变了重判；
  退避 → 跳过 → 终态 → 手动无视 → 成功清理；中止不记失败。
- 首帧前同步 spawn 探针（preload 打桩 `Bun.spawnSync`，本仓、真实 `~/.sid-code`，各 3 次）：
  首帧前从 39 次 / 约 405ms 降到 8 次 / 48–51ms，剩下的是 memory/paths、worktree/manager、attachments（不随数据量增长，见上一段）。
  同机 `first_frame` 从 PR-D 前的 880–1160ms 降到 549–690ms。
- 相关目录测试：trace/maintenance/config/memory/identity/analytics/worktree/context/cli 全绿。
  `startup-housekeeping-orphans` 在大批量并行跑时出现过一次超时（951s 墙钟），单独跑 26/26 通过，main 上同样通过，判为负载抖动。
