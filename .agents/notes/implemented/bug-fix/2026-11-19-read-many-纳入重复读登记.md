# read_many 按展开文件登记读窗口，与 read 共享重复读历史

## 决定了什么

`read_many` 现在和 `read` 用同一份重复读口径：每读一个文件就登记一次行窗口
（窗口 `1..min(400, 总行数)`，token 估算用 BOM 剥离后的全文），第 3 次读到高度重叠的窗口时
逐文件追加 `[读取效率提示: ...]` 并发出 `ReadHint(kind=repeat_narrow)` 事件。

实现上把原来 `ReadTool` 的私有读历史抽成 `ReadHistory` 类（`packages/core/src/tool/read.ts`），
由 `createStatefulTools` 创建一个实例注入 `ReadTool` 与 `ReadManyTool`（`stateful-tools.ts`）。
主代理与子代理仍然各有一份——子代理会用独立 tracker 重新调用工厂，隔离口径不变；
直接 `new ReadTool()` / `new ReadManyTool()` 的调用方也各自自建，不跨作用域污染。

改动的行为边界：只补**可观测性**，不加任何限制。提示仍然是非阻塞的，读结果不变；
空文件不登记（与 `read` 的空文件提前返回对齐）。

## 放弃了什么（以及为什么不选）

- **让 read_many 自持一份独立历史**：实现最省，但漏掉的正是 R1 的一半——
  「先 read_many 再 read 同一文件」的重复读在 `read` 侧仍然从 1 开始计数，
  ReadHint 事件也仍然看不到批量读。共享实例是这条修复的目的本身。
- **把提示升级为硬拦截（D4 第二部分）**：E1 数据判定不触发，单独写在
  `.agents/notes/rejected/feature/2026-11-19-重复读硬拦截不触发.md`。此外 `read` 是安全只读操作，
  合法的定向复查（比如改了代码后重新确认某段）会被误伤。
- **把 `ReadHistory` 与 `READ_EFFICIENCY_HINT_MARK`、`setReadHintTraceSink` 整体搬到新模块**：
  这些符号被 `cli/src/app.ts` 按 `@sid-code/core/tool/read.ts` 导入，搬文件要同步改导入路径
  并处理 re-export，收益只是目录职责更漂亮，风险与 diff 都不值。
- **按「本次 read_many 命中 N 个重复文件」汇总成一条提示**：输出更短，但模型无法把提示
  对应到具体文件；逐文件提示与 `read` 的「提示紧跟在内容后」语义一致，也更容易验证。

## 拿什么证明它生效了

新增 `packages/core/tests/tool/read-many-repeat-history.test.ts`（8 例，全绿）：

- 同一批两个文件读 3 次 → 第 3 次两个文件段落各一条提示（`split("读取效率提示")` 计数为 2）；
- `ReadHint` 事件字段与 `read` 同口径：`read_count=3`、`start_line=1`、`end_line=4`、
  `total_lines=4`、`overlap_ratio=1`、`suggest_full_read=true`；
- `ReadHistory` 共享的双向验证：read_many×2 + read×1 → read 第 1 次就提示；反过来 read×2 +
  read_many×1 → 批量读第 1 次就提示；
- `createStatefulTools`（生产路径）注入共享历史的集成用例；
- 未注入共享实例时两套工具互不影响（防跨作用域污染）；
- 不同文件不触发、空文件不登记。

变异自证：把 `read-many.ts` 登记分支的条件改成 `text.length < 0`（永不登记）后重跑，
**5 个用例变红**（第 3 次提示、事件、双向共享、工厂路径）；恢复后 8 pass / 0 fail。
门禁结果见 PR 正文（`affected-tests:run`、`make build`、lint 全绿）。
