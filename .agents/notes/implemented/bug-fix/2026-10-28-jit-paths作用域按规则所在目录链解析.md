# frontmatter `paths:` 改为沿「规则所在目录 → 项目根」逐级判定，JIT 与主加载路径同改

## 决定了什么

- `rules.ts` 新增 `rulesPathsMatchFromOwner(paths, activeFiles, ownerDir, root)` 和 `ruleOwnerDir(sourcePath)`。glob 基准从规则归属目录开始逐级往上到项目根，每一级取落在该级之下的活动文件、去掉前缀后跑原来的 `rulesPathsMatch`，任一级命中即命中。`ownerDir` 不在根内时只判根一级，等价原行为。
- JIT（`jit-context.ts` `loadOne`）改用它，`ownerDir` 是现成的遍历目录。
- 主加载路径（`loadAllCLAUDEmd` 的 `keepInScope`）的 Project 侧也改用它。managed / user / userRulesDir 三层不属于任何项目，仍只按 originalCwd 一级判定。主加载路径**复现了同款缺陷**：探针里 cwd = `packages/cli`、activeFiles = `packages/cli/src/ui/x.ts` 时，`packages/cli/.claude/rules/ui.md`（`paths: ["src/ui/**"]`）修前不进 `loadedPaths`。判据是「同一份规则在两条路径上的命中判定一致」，同一关注点，放在同一个 PR。
- 新增仓库级防漂移哨兵 `tests/build/rules-paths-scope-nonempty.test.ts`：git 跟踪的每份带 `paths:` 的规则文件，都必须命中归属目录下至少一个跟踪文件。当前 2/2（`packages/cli/src/ui/CLAUDE.md`、`evals/CLAUDE.md`）通过。
- **不改** `packages/cli/src/ui/CLAUDE.md` 的 frontmatter。保留真实形态，回归测试才有意义。

根因：被访问文件只换算成相对项目根的路径，再做锚定 glob 匹配，规则所在目录完全不参与。`src/ui/**` 写于文件还在仓库根 `src/ui/` 时（`b9280434`），`afab5725` 分包 `git mv` 之后，本地 668 次 ui 访问 0 次注入。

## 放弃了什么（以及为什么不选）

- **只把这份 CLAUDE.md 改成 `packages/cli/src/ui/**`**：一行就能修，但语义陷阱还在，下次 `git mv` 又会静默失效，而且没有门禁拦。
- **只按规则所在目录解析（纯 CC rules 口径）**：这份文件仍然不命中（`src/ui/**` 相对 `packages/cli/src/ui` 不成立），`evals/CLAUDE.md` 的 `evals/**` 也会坏掉，属于破坏性变更。
- **只按最近的 `package.json` 目录解析**：要额外读文件系统；`evals/` 没有 package.json 时只能回退到根，等于链式方案的一个特例。
- **子目录 CLAUDE.md 不看 `paths`（完全照 CC）**：会让官网已写明的 `paths` 能力在子目录规则上失效，用户写的窄作用域会被放宽。另外要记清楚：**CC 的子目录 CLAUDE.md 根本不看 `paths`**（`getMemoryFilesForNestedDirectory` → `processMemoryFile` 不按 globs 过滤）。P2v 里 CC 能注入靠的是这一条，不是 CC 把 `src/ui/**` 解析对了。「CC 能命中」不能当成「CC 的 glob 语义是对的」的证据。
