# 429 被判「无法分类」致零重试终止整轮；顺带修掉注入防护把 grep BRE 当注入

## 决定了什么

修两个**产品侧**的 bug（不在评测脚手架里，在主循环与权限层上），
以及三个让评测数据失真的评测侧配置问题。都由 smoke-8 轨迹逼出来，全部有实测复现。

### bug ①（P0）：429 根本没被识别成可重试错误 —— 真根因比交接文档定位的深一层

交接文档（ZZZZ.10）把根因定在 `app.ts:1960` 的 `autoFallback()` 返回 `abort`。
**那是终点不是起点**，按它改是修不好的：`abort` 之所以被执行，是因为在那之前
429 已经被判成「无法分类」、**跳过了全部 11 次重试预算**。

三层根因，缺一层都修不好：

1. `anthropic.ts` 置 `streamLevel` 的条件是 `upstreamType &&`，而公司网关的 429 body
   里 `"type": ""` 是**空字符串**（falsy）→ `type` 与 `streamLevel` 都不带上。
   可用信息其实在 `code:"rate_limited"` 里，被丢了。
2. `fallback.ts:1058` 于是走 else 分支 `classifyError(new Error(event.error.message))`
   —— **只传 message，把事件里明明有的 `statusCode` 丢了**。
3. 429 的识别因此退化成对 message 做文本匹配，而 `anthropic.ts` 优先用上游的
   人类可读文案（中文「当前分组上游负载已饱和」，**无 "429" 无 "rate_limit"**）
   → 返回**裸 Error** → `instanceof RetryableError` 为 false → 跳过重试
   → 落到"重试耗尽"出口 → `tryFallback` → 无备用模型 → `abort` → 整轮 fatal。

这也解释了交接文档没解释的一件事：**日志里为什么没有任何解释性 warn**。
流内 error 的"重试耗尽"分支是**静默**的，不像 throw 路径会打「错误无法分类」。

**最有说服力的证据来自同一轮 smoke-8 自己的数据**：pytest-7982 撞的是 nginx
`502 Bad Gateway`，**重试成功了**、跑完了；xarray-6461 / pytest-10081 撞 429，
零重试直接挂。差别只有一个 —— 502 的正文字面含 `502` 三个字符，被文本匹配兜住。
**即：限流能不能重试，取决于网关文案里恰好有没有那三位数字。**
这不是漏了一个场景，是判据建在了错误的地方。

补充一个全局事实：smoke-8 全 10 条实例里**只有 1 条真正发生过重试**，
其余 9 条的 `流式阶段尝试` 全程是 `1/11`。

修法：把判据从「文案」改成「结构化状态码」。
`fallback.ts` 在事件带 `statusCode` 时挂到 Error 上（`getHTTPStatus` 读 `.status`）；
`anthropic.ts` 空串 type 归一 + `code` 收作次选；
`openai.ts` 两条协议路径（Chat Completions / Responses）的 catch 都补 statusCode 透传。

### bug ②：注入防护把 `grep -n "a\|b"` 当成注入

`validateBackslashEscapedOperators` 里两个判据**作用在不同字符串上**：
`hasRealOperator` 扫剥引号后的 `fullyUnquoted`，而转义操作符检测扫**原始命令**。
于是引号内的字符被当成引号外的解析歧义 —— 打到的是最日常的命令：
`grep -n "empty_values\|class ForeignKey" x.py`（`\|` 是 grep BRE 的"或"，
在双引号里对 shell 毫无语法意义）。

修法：检测面统一到 `fullyUnquoted`。**这是根治而非放宽** ——
`extractQuotedContent` 在引号外遇到 `\` 时会把反斜杠和被转义字符**都写进**
`fullyUnquoted`，所以 `ls | cat \| sh` 这类真实威胁一个都不漏。

### 评测侧三件（让数据不再失真）

- **权限模式 `acceptEdits` → `bypassPermissions`**：实测 113 次权限拒绝，
  django/matplotlib 三条实例**过半轮次**（58%/58%/55%）是被拒绝烧掉的。
  被拒的都是做题必需的动作（`pytest`、`write /tmp/repro.py`、`python -c`）。
  于是 matplotlib-20488 被记成「40 轮预算用尽」，读起来像能力不够，
  **真相是它一直在试着跑测试验证修复、被拦了 23 次**。
- **轨迹取回**：轨迹一直在生成（日志有 `轨迹采集已启用`，digest 还报过
  `检出 5 条[高]级异常`），但写在容器内、`docker rm -f` 直接删掉，**零 `docker cp`**。
  这就是归因只能靠 grep agent.log 的原因。现在落到 `/tmp/sid-traj` 并在 rm 前拷出。
- **堵住团队默认配置泄漏**：`backfill-team-defaults` 迁移把**编译进二进制**的
  `team-defaults.template.json` merge 进了容器 settings.json，带进
  `fallbackModel: ali-deepseek-v4-flash`（**评测里出现第二个模型**，D17 不允许）
  与指向线上平台的 `trace.upload`（容器无外网 → 10/10 白跑上传重试）。
  修法：settings.json 显式写全这些顶层键占住位置。
- **P2 观测字段**：`hit_max_turns` / `llm_fatal` / `permission_denials`
  进 `RunRecord`，**只标注不参与判定**（`deriveOutcome` 一行没改），
  让「零 patch 里没有基础设施原因」这条收口判据变成可机械验证的。
- **删掉 `runner.ts` 的 `containerScript()`**：零引用零测试，是 shell 那份的
  平行实现且已漂移（硬编码 `acceptEdits`、写着 `"name":"m"` 那版无效模型名）。
  它 docblock 里四条实测约束已逐条搬进 shell 文件头（搬前 grep 验证过 shell 确实缺 2 条）。

## 放弃了什么（以及为什么不选）

- **❌ 把 `streamLevel` 无脑置位**（最省事的一行改法）。那会让纯网络异常
  （ECONNRESET 等）也走流内错误分类器，而它的兜底是"无法归类即按 server_error 重试"
  —— 等于把**确定性故障**也拖进 11 次退避。statusCode 才是权威且无歧义的判据
  （`matchesHttpStatus` 拿到结构化状态码就不再回退文本匹配）。
- **❌ 按交接文档去改 `autoFallback` 的 abort 语义**。429 修好后根本走不到那里；
  真去改它会把「模型确实不可用」也变成无限重试 —— 把一个正确行为改坏。
- **❌ 整体关掉注入防护那层**。它拦的 parser-differential 攻击是真的。
  但**检查器误判必须当 bug 修**：headless 下误判不是"多问一句"，
  而是工具调用直接被拒、轮次白烧。
- **❌ 评测里逐条加 allow 规则代替 bypassPermissions**。allow 白名单会变成
  **新的必控变量** —— 写多一条少一条都改变 agent 能做什么，而"这一轮放行了哪些命令"
  极难在报告里说清。`bypassPermissions` 是**一个**可记录可复现的取值，
  且容器本身就是沙箱（无外网、跑完即删、只有一个 testbed 仓库）。
- **❌ 让 `deriveOutcome` 读新增的日志信号**。一旦让它读，`outcome` 就从
  「机械可复算的四态」变成「依赖日志文案的启发式」，而日志文案会变。
- **❌ 本轮不跑新评测**。ZZZZ.9 的教训是"起跑前先把仪器 bug 修掉，否则又是一份脏报告"。
  这轮改了权限模式（必控变量）+ 主循环重试语义，跑一轮才有意义。
- **❌ 只跑没通过的题**（用户问过，答案是不行）。`solved` 不是稳定标签 ——
  smoke-2 与 smoke-8 之间 10 条里有 5 条结论变了。已过的 5 条正是"链路正常时的对照组"；
  另外 `cmd_run` 开头会清空 `records.jsonl`，续跑会丢已完成记录。

## 拿什么证明它生效了

- **端到端复现**（照抄 xarray-6461 真实 429 body，headless + 无备用模型）：
  修复前请求 1 次即 fatal；修复后 `准备重试` ×3 → 第 4 次成功拿到内容、
  `yield error: false`。那行 `准备重试` 正是 smoke-8 里 19 次请求一次都没出现过的。
- **注入防护 10 条对照**：误判 3→0，6 个真实威胁（`ls | cat \| sh` 等）全部仍被拦。
- **新增测试**：`packages/core/tests/llm/status-code-classification.test.ts`（10 条，
  核心用例刻意**不带 streamLevel** —— 既有 fallback 系测试的 mock 全部显式写
  `streamLevel: true`，恰好绕过了生产上出问题的那条 else 分支，
  是「绿了但没测到」的又一例）；`bash-security.test.ts` +11；`swe-bench-runner.test.ts` +12。
- **变异自证 5 个方向**，每个都确认断言转红：① 回退 fallback statusCode 透传
  ② 回退 openai Responses catch ③ 回退 anthropic 空串归一
  ④ 回退注入防护检测面 ⑤ 权限模式回退 / 去掉 fallbackModel 占位。
- **全量 11033 pass / 0 fail**（750 文件）；`lint` / `format:check` 干净；`make build` 通过。
- ⚠️ **过程中抓到自己写的一条假绿断言并修掉**：「轨迹必须在 docker rm 之前取回」
  第一版用 `lastIndexOf("docker rm -f")` 扫全文，命中的是**注释**，
  把 cp 挪到真正的 rm 之后测试照样全绿。改成只扫可执行行后变异才转红。
  **本仓那条纪律要防的形态，差点出现在防它的测试里。**
- ⚠️ **顺带纠正交接文档两处证据数字**：ZZZZ.10 记的「429 次数 3」实测是 **1**
  （另 2 处是 `cacheCreationInputTokens: 12429` 之类巧合数字），
  「终止本轮 1 次」实测 grep 到 6（该文案在注释与多分支都出现）。
  这改变结论：**一次 429 就终止整轮**，比原描述更严重。
  教训已写进 `extractAgentLogSignals` 的实现与测试（按错误行形态锚定，
  不用裸 `/429|502/` 扫全文），并配了一条专门的负向断言。
