# 残卷证据段让位「下一步」、`<error>` 补不可信标记、锁住 `onTurnEnd` 接线

PR #574（F3 1–6）合入后 review 出的四项缺陷 + 三个 nit 的跟进修复。六个改动都服务同一句话：
**残卷投递链路的每一环都要有断言，且关键段不能被通道预算挤掉。**

## 决定了什么

1. **`<tool-evidence>` 从「findings 之后」移到「`<next-step>` 之后」**（`agent/salvage.ts`）。
   方案 §4.3 第 4 条原本写的是排在 findings 之后。实测（真实 `buildSalvageOutput` +
   `truncateForNotification`，6 条满 800 字的证据）完整残卷 5133 码点、`<error>` 通道上限 4000，
   截断后 `<incomplete>` / `<next-step>` / `<output-file>` **全部不可见**，证据只剩 5/6 条。
   被挤掉的 `<next-step>` 恰含「认证失败，检查凭证后重试」这类可执行指令，而「让模型知道
   下一步、别自己重做」正是 F3 要修的东西。后置之后截断先丢证据尾部，关键段必在前几百字内；
   完整证据仍在 `.output`（同一份残卷由 `failAgentTask` 写入，截断提示也指向它）。

2. **`<error>` 通道加 `untrusted="true"`**（`task/notification.ts`）。`<result>` 早就有这个标记
   （缺口 2 阶段 1），而 F3 之后 `<error>` 首次承载失败子代理的**完整残卷**，其中
   `<tool-evidence>` 是任意工具结果（web_fetch 的外部网页、仓库文件、MCP 返回）。通知前缀
   `NOT_USER_INPUT_PREAMBLE` 防的是「把事件误读成用户授权」，与「执行产出里的指令」正交
   （该常量注释自己写了这层区分），不能互相替代。

3. **`<tool-evidence>` 正文只转义会破坏段边界的闭合序列**（`agent/salvage.ts` 新增
   `escapeXmlContent`）。属性值走既有的 `escapeXmlAttr`；正文此前完全不转义。实测读一个
   含 `</evidence>` 的文件（例如本仓源码）会让 `<evidence>` 提前闭合、后续内容甩到段外。
   只替换 `</evidence` / `</tool-evidence`，不做全量转义——正文是给模型读的代码/diff，
   全转义会让它几乎不可读，而模型真正需要的是能看清段边界。

4. **补 `onTurnEnd` 的 `tools[].result` 接线测试**（`tests/agent/agentic-loop-stop-policy.test.ts`）。
   PR #574 的 Agent Note 写「接线正确性由 `formatToolTurnLine` 的『结果未知 vs N 字节』
   差别间接保证」——这条论证不成立：那些断言是纯函数级，`result` 由测试自己构造，绕过了
   `agentic-loop`。接线一旦失效，下游只会静默退化成「结果未知」，所有测试仍然全绿。
   复用该文件已有的 `run(scripted, overrides)` 基建（真实 `runAgentLoop` + mock provider），
   断言 `tools[0].result` 与真实执行一致、文本轮不凭空造 `result`。

5. **spawn 路径的 `.output` 粒度注释改成如实描述**（`agent/sub-agent.ts`）。原注释写「与进程内
   路径同一格式……一致性是刻意的」，实际进程内是每轮一行、多工具 `; ` 连接，spawn 是每工具
   一行（协议逐条 `tool_use` 往返，父进程收不到「轮末」信号，同轮多行共享轮次号）。

6. **summary 文案去重 + 单次取值**（`task/agent-task.ts`）。残卷的 `<interrupted-because>` 以
   「执行出错：」开头，summary 模板已经写了「执行失败」，原样拼出来是
   「执行失败: 执行出错：LLM 错误…」。剥掉前缀；顺手把模板里调了两次的
   `summarizeFailure` 提取为变量。

## 放弃了什么（以及为什么不选）

- **按通道预算动态裁剪每条证据长度**（例如 `min(800, (4000 − 其它段) / 6)`）：
  `buildSalvageOutput` 的产物同时流向三个通道——通知 `<error>`（4000）、`.output`（无上限）、
  前台 `<subagent-result>`（16000）。要按预算裁剪就得让格式化函数知道「这次是给哪条通道的」，
  把通道语义漏进纯格式化层。位置调整用一行代码解决了同一个问题。
- **保留「紧跟 findings」的位置，改小 `TOOL_EVIDENCE_MAX_CHARS`**：证据的价值就是「够长才看得出
  结论」（一段 git log / 一个函数定义），压到 200 字等于没有；而且它解决不了「6 条加起来仍超窗口」
  的结构问题。
- **spawn 侧聚合同轮多工具为一行**：要等 `progress` 边界才能判定轮末，多一层缓冲状态与冲刷时机，
  换来的只是少几行、轮次号不重复。改注释说明真实行为更划算。
- **给 `<error>` 内部再加一层 `<partial-result untrusted>`**：多一层嵌套，收益与只加属性相同；
  模型读的是属性这个信号。
- **正文全量 XML 转义**：见上，可读性是这段内容的主要价值。

## 拿什么证明它生效了

**修复前实测（同一脚本，6 条满 800 字证据）**：

```text
完整残卷 5133 码点 → 发送 4044（4000 + 截断提示）
<incomplete>:    被截掉
<next-step>:     被截掉
<output-file>:   被截掉
<tool-evidence:  可见（5/6 条）
```

**修复后**：同形态下 `<incomplete>` / `<next-step>` / `<output-file>` 全部可见
（新用例 `salvage-tool-evidence.test.ts` 的「6 条满额证据使残卷超长时……」断言这一点，
并先断言残卷确实超过 `NOTIFICATION_ERROR_MAX_CHARS`，避免用例在未触发截断时假绿）。

**新增/改写单测**（4 个文件，37 pass / 0 fail）：

- `salvage-tool-evidence.test.ts`：位置断言改为「在 findings 之后、`<next-step>` 之后」；
  新增超长截断下关键段可见、正文闭合标签转义两条。
- `agentic-loop-stop-policy.test.ts`：新增 `onTurnEnd` 带出 `tools[].result`（含 `is_error`）
