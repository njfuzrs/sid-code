# `/context` 的「记忆」分类按实际留在提示词里的前缀计数

## 决定了什么

`packages/core/src/config/system-prompt.ts` 的 `reportSectionTokens` 不再对「判定在场」的段
加**全文**估算，而是逐段在最终 `content` 里定位起点，求原文与该位置起的最长公共前缀长度
`presentLength`，只累加 `estimateTokens(text.slice(0, presentLength))`。

- 公共前缀求法（新增 `commonPrefixLength`）按下标逐 code unit 比较，不复制
  `content.slice(start)` —— content 常有几万字符，而它只被 4 个以内的记忆段各调一次。
- 「在场判定」仍是每段前 200 字符（`indexOf`），与改动前同口径：不足 200 字符的段
  （截断点落进 probe 内）依旧判为不在场、计 0。

修复的是 A5：`truncateToLimit` 截断附件时留下的是 `前缀 + "\n\n[内容已截断]"`，旧实现
`content.includes(probe)` 命中的是那个前缀，加的却是全文估算。于是记忆分类在截断后
与截断前一样大；它被 `min(memoryTokens, rawSystemPrompt)` 钳住后，虚报的量从
「系统提示词」分类里扣走（该分类偏小），面板两个分类同时失准。

## 放弃了什么（以及为什么不选）

1. **放弃按 `truncatedChars` 反推在场长度。** 截断时 `truncateToLimit` 确实知道每个附件保留
   多少字符，但那是 attachments 层的局部变量，要把它回传到 `reportSectionTokens` 就得改
   `truncateToLimit` 的返回形态与 `buildSystemPrompt` 的调用链。而缓存命中路径（`promptCache`
   直接返回 `content`）没有那次截断计算，只有最终的 `content` —— 用一个只在一半路径存在的
   信号，会让「冷启动」和「缓存命中」报出不同的数。从 `content` 反推是两条路径唯一共有的
   事实来源，也是改前「在场判定」已经在用的口径。
2. **放弃把 200 字符 probe 缩短成「只要有一段前缀命中就算」。** 探针越短越容易在别处误命中
   （记忆索引的条目在 `recalledMemories` 里可能重复出现），把「被丢弃的段」误判成在场。
   方案里明确接受「截断后不足 200 字符的段计 0」：那部分最多 200 字符（≈130 token），
   且方向是少算而非虚报，风险远小于误命中。
3. **放弃为 `commonPrefixLength` 单独导出单测。** 它的正确性完全由「上报值 == content 里
   实际在场前缀的估算」这一条端到端断言覆盖；导出它只会让测试复刻实现算法，反而测不出
   「定位错了起点」这类错误。

## 拿什么证明它生效了

**一、G1 三条断言 + 变异自证**（`packages/core/tests/config/system-prompt-section-tokens.test.ts`）：

- `bun test ./packages/core/tests/config/system-prompt-section-tokens.test.ts` → **3 pass / 0 fail**
  - 不截断：上报值 == `estimateTokens(记忆指令) + estimateTokens(完整 CLAUDE.md 附件)`（防回归）
  - 部分截断（`maxTokens` 取完整提示词的 60%，截断点落在 CLAUDE.md 中间）：
    上报值 == `estimateTokens(记忆指令) + estimateTokens(content 里从段起点到 [内容已截断] 的实际前缀)`，
    且严格小于全文估算
  - 整段丢弃（`maxTokens=100`）：上报值 == `estimateTokens(记忆指令)`，既有行为不变
- 变异：把 `const presentLength = commonPrefixLength(text, content, start);` 换成
  `const presentLength = text.length;` → **1 fail / 2 pass**，红的正是部分截断那条：
  `Expected: 3454 / Received: 7726`（7726 = 全文口径），恢复后回到 3 pass / 0 fail。

**二、门禁**（worktree `pr4-memory-truncated-count`）：

- `bun run affected-tests:run`：**939 pass / 0 fail**（选中 `packages/core/tests/config/`）
- `make build`：通过，5 项产物自检全绿
- `bun run lint`：0 warnings / 0 errors；`bun run format:check` 通过
- `bun run lint:boundary`：越界依赖 0 处
- `bun run typecheck:gate`：62 处 / 基线 62 处，无新增
  （worktree 的 `node_modules` 软链会先造出 6 项「同一模块两条路径」的假新增，
  删软链 `bun install` 后归零——不是本次改动引入的）
- `bun run docs:gen-reference --check`：参考页与源码一致
- 全量 `bun test` 未在本地跑：按 CLAUDE.md「选测与 PR 化必须成对」，本地覆盖用
  `affected-tests:run`，全量由 CI 在合并前跑。

**三、一条诚实的边界**：G1 钉住的是「上报值等于实际在场前缀的估算」。它**不**证明真实会话
里 `/context` 面板的「记忆 / 系统提示词」两行在截断场景下与肉眼所见一致——那要跑方案
§8 的 E1（真实会话里触发记忆截断，对照面板与 `content`），本 PR 没做、也没写成已做。
