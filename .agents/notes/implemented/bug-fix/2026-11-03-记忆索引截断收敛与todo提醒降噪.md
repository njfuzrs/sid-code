# 记忆索引用「描述截短 + 低频归档」收敛，todo 提醒在模型推进时放宽到 2 倍

## 决定了什么

落地《20261103-会话 3b4f9ca7 复盘》的 PR-4（C3 + C4，上下文注入方向）。四件事：

1. **C3-A 索引行描述截到 40 字符**（`memory/index-budget.ts` 新增 `INDEX_DESC_MAX_LEN` 与
   `truncateIndexDesc`，store / agent-store / team store 三条记忆线共用）。
   刻意**不**复用 `store.ts` 的 `MEMORY_DESC_MAX_LEN`(150)：那个值写进 frontmatter，
   是磁盘数据，截短即永久丢信息；这里只影响每轮常驻 system prompt 的索引行。
   本机实测（201 个文件、索引行平均 389 字节、描述占 277）⇒ 25KB 只列 63 条；
   截到 40 字符后同一批数据可列 132 条。
2. **C3-C 索引截断时自动归档低频记忆**（新模块 `memory/index-archive.ts` + `store.set()` 接线）。
   三个条件同时满足才进候选：类型 ∈ {project, reference}、`updatedAt` 超过 30 天、
   `.read-stats.json` 里该条 `readCount` 为 0 或缺失。读统计文件本身缺失时年龄门槛
   抬到 90 天。单次最多 20 条，只从**写路径**触发（`load` 不动用户文件）。
   归档去 `archive/`（`scan.ts` 的 `SKIP_DIRS` 成员），字节保留、可人工恢复。
3. **截断告警按签名去重**（`store.ts` 的 `indexTruncationWarnSignature`，dir → `entries/entryCount`）。
4. **C4 todo 提醒降噪**：`getTodoReminderTurnCounts` 新增 `recentToolUseTurns`
   （`recentWindow` 省略时恒 0）；`shouldInjectTodoReminder` 在 `relaxWhenAdvancing`
   （调用方判据 = 清单恰好一个 `in_progress`）且最近窗口内有工具调用时，
   把提醒间隔放宽到 2 倍；`buildTodoReminder` 文案加「距上次更新清单已 N 轮」与当前
   `in_progress` 项名。

## 放弃了什么（以及为什么不选）

- **C3 选项 B（把 `INDEX_MAX_BYTES` 提到 60KB）**：能让 201 条全部可见，但索引每轮全量
  常驻 system prompt，多占约 9K token。选 A 是因为它零结构变更就把可见条数翻倍；
  C 负责降分母。B 的代价是每轮都付，与「更省」直接冲突。
- **只做 C 不做 A**：归档要让索引放得下就得搬走更多文件（分母降得不够快），
  而 A 是纯写侧的一行截断，成本近乎零。两者互补，不是二选一。
- **归档 `user` / `feedback`**：`INDEX_TYPE_RANK` 刻意把它们排最前（S9），
  归档它们等于把索引的优先级设计反过来。
- **读统计缺失时按「从未读过」处理（30 天门槛）**：读统计是 T1.1 才上线的旁路文件，
  老目录里所有条目都缺失，那等于「30 天没写就整批搬走」。改为缺统计时 90 天兜底。
- **在 `writeIndex` 内部直接归档**：它是「渲染索引」的纯写函数，归档要动用户的记忆文件，
  决策属于写路径；藏在渲染函数里会让 `load` 时的索引重建也突然搬文件。
- **C4 只改文案 / 只放宽阈值**：文案让模型不误判，但不减少注入次数（本会话 4 次全进上下文）；
  只放宽则注入的仍是无信息量的重复文本。两者都做。
- **C4 无条件放宽或加大倍数**：与回归哨兵「60 轮停滞至少注入 6 次」的语义直接冲突
  —— 真停滞时反而少催。所以放宽默认关闭（`relaxWhenAdvancing` 不传 = 旧行为），
  且要求「清单恰好一个 `in_progress`」+「最近窗口内真有工具调用」。
- **恢复去重 / 封顶来降噪**：`todo-reminder-scan.ts` 文件头有实测背书（封顶曾导致
  60 轮只响 1 次），否决理由不变。
