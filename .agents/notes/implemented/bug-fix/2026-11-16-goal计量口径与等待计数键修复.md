# goal 计量口径收口：plan mode 暂停、等待计数按类型、三处漏账补齐

## 决定了什么

复核 G1–G6 落地时发现四条残留，全部用自造数据（夹具式集成用例）验证后修掉：

1. **plan mode 期间 goal 暂停计量**（`packages/core/src/query/loop.ts` 轮首）。
   此前只豁免「判上限」而没豁免「累加轮次」与「记账」，三者不一致：plan mode 里调研 N 轮，
   `turnsUsed` 涨 N 而 `tokensUsed` 恒为 0，退出 plan mode 后立刻 `turns_limited`，
   且这些轮的 token 对 `tokenBudget` 完全隐形。
   实测（goal.maxTurns=3、10 轮 tool_use）：plan → `turnsUsed=50 / tokensUsed=0 / status=active`；
   default → `3 / 450 / turns_limited`。现在 plan mode 下三项全部暂停（轮次不增、不记账、不判上限）。

2. **首轮回注判据改 `state.lastGoalReminderTurn === undefined`**。
   原判据 `goal.turnsUsed === 1` 在「暂停计量」后会永远成立（turnsUsed 停在 1），
   导致 plan mode 每一轮都重复注入同一段 goal reminder。副作用是每条用户消息的首轮都会注入一次
   （原实现只有 goal 的第 1 轮会）——与「首轮必注入」的原意一致，代价是每条消息多约 1KB 附件。

3. **G2 等待放行的计数键从「等待 id 集合」改成「等待类型集合」**（`packages/core/src/query/goal-waiting.ts`）。
   等待 id 由工具生成、天然唯一，模型每轮重挂一个新 monitor 就换一组 id：实测连续换 10 个 id →
   10 次全部放行，`MAX_CONSECUTIVE_WAIT_PASSES` 形同不存在，正好是「防旁路」注释要防的那件事。
   现在换实例不重置，换类型（monitor → wakeup）才算新的一组。

4. **补三处 `goal.tokensUsed` 漏账**：强制总结轮（`while` 之外，不经过每轮检查）、
   F1 空参数退化重试轮（在每轮检查之前就 `continue`）、以及 plan mode（见第 1 条）。
   强制总结轮的记账条件包含 `state.goalLimitExit`——命中上限时 `goal.status` 已被改成
   `turns_limited`/`budget_limited`，只判 `active` 会正好漏掉最该记的这一次。

## 放弃了什么

- **否决「plan mode 也计量也判上限」**：plan mode 下的调研会把 goal 预算吃光，
  与 `loop.ts` 既有注释「计划模式不执行操作，不该因 goal 预算而终止」直接冲突。
- **否决「计量但不终止（退出 plan mode 后算账）」**：退出那一刻立刻 `turns_limited`，
  用户看到的是「刚进计划模式什么都没干就被判超限」，归因困难且突兀。
- **否决「不分组、全生命周期累计」**：换一种等待方式（monitor → wakeup）本是合法的新机会，
  一律不再给次数属于误伤。
- **否决「保留换组重置 + 加总闸（最多 N 次）」**：引入第二个计数维度，两个上限的关系要额外解释，
  收益不抵复杂度。
- **本轮不新增 G2 回放用例**（方案 §7.3 的 S-goal-turn-limit / S-goal-wait）。
  回放用例需要先解决「goal 状态如何预置进 `SID_CONFIG_DIR`」这个前置问题，属独立探索；
  本次用 G1 集成夹具造数据覆盖四条修复，G2 层留作后续。
- **不动 `AC` 层文档与方案原文**：方案 §4.1/§4.2 的自述保持不变，本文只记录复核后的增量修复。
