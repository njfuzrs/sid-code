# 只读探查止损阀识别 `git rev-parse`，并把「同一组探查换写法」归一到同一签名

## 决定了什么

`packages/core/src/query/repeated-readonly-guard.ts` 两处放宽，`query/loop.ts` 一处传参：

1. **白名单加 `git rev-parse`**。它是纯只读（AST 关卡 `isReadOnlyCommand` 早已判 true），
   却是模型确认「当前在哪个分支 / HEAD 是谁」最高频的写法——复现会话 `20261109-160803-fbb02831`
   的 88 次分支确认里 69 次以它开头，旧白名单让这些命令整条进不了阀，全会话 0 次触发。
2. **签名归一化**（`makeSignature` 新增 `kind` 参数，bash 探查默认走归一化）：
   - 命令侧 `normalizeProbeCommand`：按 `&&` / `;` 拆段 → 去掉纯标记 `echo` 段 → 排序拼接。
     `echo "$(cmd)"` 这种带命令替换的不剥（输出是真信息）；整条都是 echo 时退回原段，避免空签名。
   - 输出侧 `normalizeProbeOutput`：删掉只由 `=` / `-` / `END` 组成的标记行。
   - `read` 家族（`kind="tool"`）**跳过**这两层：它的输出是文件内容，内容里的 `---` 是 markdown
     分隔线而非视觉标记，删掉会让不同文件内容撞签名。`loop.ts` 收集 read 家族 probe 时显式传
     `kind: "tool"`。
3. 阈值、提醒封顶、终止判据（只对含 `git status` 的批次强制收尾）**一律不动**。

## 放弃了什么（以及为什么不选）

- **只加白名单、不做签名归一化**：复现会话里模型用了 28 种写法换着跑（加/不加 `echo "===END==="`、
  `&&` 换 `;`、调换段序），签名每轮都不同，计数被反复清零。实测只加白名单能在 08:39:39 触发
  （19 次），加归一化后提前到 08:39:25（30 次）。代价是归一化让「换写法的重复」也被判成同一签名——
  但这正是要抓的形态：只读探查的顺序与视觉分隔符不携带信息。
- **用 AST 做命令段拆分**（而不是按 `&&`/`;` 裸切）：裸切对引号内的分隔符会切错，但同一条命令每次
  切法一致，签名仍稳定；跨命令撞签名需要切出的段集合完全相同，概率极低。引入 AST 会显著增加这段
  纯函数的复杂度，收益不足以支撑。
- **对 `echo "$(git status)"` 也剥离**：它携带真命令输出，剥掉会让签名丢掉内容差异、把「输出变了」
  误判成「没变」。保留这一段的保守代价是这类写法仍逃逸归一化——它本身就很罕见。
- **把 `git rev-parse` 家族纳入强制收尾**：终止判据仍是「批次里含 `git status`」。纯 `git rev-parse`
  探查只提醒不终止，避免把合法的分支确认掐断（沿用原设计「强制收尾只给唯一被实证证明会死锁的命令族」）。
