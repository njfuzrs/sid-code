# 压缩管线目标线的 0.3 下限不得高过触发点

## 决定了什么

`pipelineTargetRatioFrom`（`packages/core/src/query/compact/index.ts`）最后一行的下限从固定 `0.3` 改成 `min(0.3, 触发点)`。

旧写法的问题：`SID_CODE_AUTOCOMPACT_PCT` 设到 30 以下（如 8）时，hard 档在 8% 触发，管线目标却被下限抬到 30%。`runCompactPipeline` 一进场判「当前 8% ≤ 目标 30%」，直接返回 `steps=[]` / `needsAutoCompact=false`。消息数不变，`CompactionAttempt.success=false`，下一轮仍超阈值，再触发、再空跑，压缩永不生效。

同一函数的注释早就写明「目标不会反而高过触发点（那会让管线一进场就判已达标而空跑）」，只防住了 masking 线那一侧，0.3 下限从另一侧把同一个问题放了回来。

## 放弃了什么（以及为什么不选）

- **去掉 0.3 下限**：不选。下限的本意是防目标线低到离谱（小窗口、异常阈值），把管线压得过狠。只要它不高过触发点，就和本缺陷无关，保留。
- **在 `SID_CODE_AUTOCOMPACT_PCT` 解析处拒绝 <30 的值**：不选。低阈值是合法用法（评测里为了在 1M 窗口上可靠触发压缩，就设了 8%），缺陷在目标派生，不在输入。

## 拿什么证明它生效了

- 新增用例「override 低于 30%（如 8%）时，目标仍不高于触发点」（`masking-calibration-same-source.test.ts`）：分别取 8% 和 25%，断言目标 ≤ 触发点，且刚过触发线时管线返回 `needsAutoCompact=true`。
- 变异自证：把下限改回固定 `0.3`，新用例变红（1 fail）；恢复后 29 pass。
- 触发轨迹：harness-bench L1，sid-code 会话 `20261025-153208-f745739b`，`CompactionAttempt` 连续 6 次 `success=false`、消息数 11→11 … 17→17；同题 Claude Code 会话成功压缩。修复后用 `sc-dev` 重跑 L1–L3，应看到 `success=true`。
