# 权限规则的工具名支持连字符（插件 MCP 工具能按名字放行 / 拦截）

## 决定了什么

`packages/core/src/permission/rules.ts` 的 `matchRule` 与 `shadowed-rules.ts` 的 `extractToolName`
把规则工具名的字符集从 `[*\w]+` 放宽到 `[*\w-]+`。

插件 MCP 的工具名是 `mcp__plugin_<插件名>_<server>__<tool>`（`addPluginScopeToServers` 加 `plugin:` 前缀，
`normalizeMcpName` 把 `:` 换成 `_`、保留 `-`）。插件名常带连字符（企业市场的 `feishu-docs`），
旧正则对这类规则整条解析失败、`matchRule` 直接返回 false，而且不报错：

- `--allowed-tools` / `permissions.allow` 写精确名或 `mcp__plugin_feishu-docs_feishu__*` 都放不行，
  headless 会话照样「需要用户确认」被拒；
- `permissions.deny` 写同样的规则**也拦不住**——这一半是安全问题：管理员以为禁掉了某个插件的工具，实际没生效；
- 阴影规则检测同样看不到这些规则。

现场：2026-10-15 企业市场 `feishu-docs@1.0.1` 真实会话重测，按插件名精确放行两次都被拒，
只有 `--allowed-tools "mcp__*"` 能读出文档。

## 放弃了什么（以及为什么不选）

- **把插件 MCP 工具名里的 `-` 也规范化成 `_`**：能绕开正则，但会改变已对外的工具名
  （模型侧工具名、`tool_invoked` 归因、用户已写的规则全部漂移），代价远大于放宽一个字符类。
- **字符集直接对齐成「除括号外任意字符」**：过宽。规则串里还有 `Bash(git *)` 这类参数段，
  工具名段放进空格、冒号之类会让 `Bash git` 这种笔误被当成合法工具名静默不匹配，反而更难查。
  只补 `-`，与 `normalizeMcpName` 产出的字符集 `[a-zA-Z0-9_-]`（外加通配 `*`）一致即可。
