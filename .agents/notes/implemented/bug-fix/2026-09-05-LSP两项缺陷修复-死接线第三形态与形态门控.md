# LSP 两项缺陷：死接线的第三形态（实现正确+注释声明+零调用方），与「能力启用看形态不只看配置」

## 决定了什么

修掉缺陷清单的 **D15 / D16（LSP 层全部两条）**。这一层是三层里实现最完整的
（1943 行、接线齐全、还有 CC 没有的主动查询工具），所以只有两条小缺口。

| # | 改动 | 文件 |
| --- | --- | --- |
| D15 | 新建 `/lsp` 命令（`status` / `reload`），并把 `reinitializeLSP()` 一并接进 `/reload-plugins` | 新增 `cli/command/lsp.ts`、`command/builtins.ts`、`command/plugin.ts` |
| D16 | `initializeLSP` 按运行形态门控：`--print` / `--bridge` 下跳过 | `cli/src/cli.ts` |

**D15 的性质**：`reinitializeLSP()` **实现完全正确**（关旧实例 → 清 registry →
`initGeneration++` → 重新初始化），注释还写着「插件刷新时调用」——
但生产调用点是 **0**，而本该触发它的 `/reload-plugins` 完全不碰 LSP。
后果是改了 `.sid-code/lsp.json` 后**无法在会话内生效，只能重启进程**。

这是「死接线」的第三种形态：**实现正确 + 注释声明了调用场景 + 零调用方**。
和 Bridge 那条 `isEligibleForBridge`（D13）形态完全一致 —— 读代码的人不会从注释里
发现问题，因为注释描述的是一个**未完成的计划**，它读起来完全正常。

## 放弃了什么（以及为什么不选）

**① 没有只把 `reinitializeLSP` 挂到 `/reload-plugins` 上**（那是清单给的第一个选项）。
触发重载的真实场景是"我刚改了 lsp.json"，那和"我刚装了插件"是**两件不同的事**。
只藏在插件命令里等于让用户猜。所以做了专门的 `/lsp reload` 作为主入口，
`/reload-plugins` 那条线也接上（插件确实可能带来新语言/文件），但它不是唯一入口。

**② `/reload-plugins` 里先判 `getLSPInitState()` 再报「已重载」。**
`reinitializeLSP` 在 `not-started` 时是**空操作**（刻意如此），
不判就无条件打印"LSP 配置已重载"会是**假消息** —— 而假的成功提示比没有提示更坏。

**③ D16 门控的是初始化，不是能力本身。** LSP 工具仍留在 registry 里：真被调用时
manager 会按 `not-started` 走降级路径，而不是"工具不存在"这种更难解释的失败。

**④ `/lsp status` 把 `not-started` 当正常态解释，而不是当错误报。**
`--print` / `--bridge` 下 LSP 被刻意跳过，不说清楚会让用户以为 LSP 坏了。
`reload` 在未启动时也明确说"无需重载"并给出原因，而不是静默什么都不做 ——
用户敲了命令却什么都没发生会很困惑。

**⑤ D16 的门禁判据没有去匹配某个具体的 `if` 写法**，而是断言"门控变量存在 +
两种形态都被枚举 + `initializeLSP` 调用排在门控之后"。匹配具体写法会在无害重构时误红。

**⑥ 没有碰 `packages/core/src/lsp/*`。** 另一个终端的会话正在改
`lsp/{client,config,manager}.ts` 与 `tool/lsp.ts`；本 PR 的改动全部落在
`packages/cli/`（它们不碰的地方），且只依赖 `reinitializeLSP(workspaceFolder: string): void`
这个已确认稳定的签名。**这是刻意的边界选择，不是巧合。**

## 拿什么证明它生效了

**① 门禁做了三次变异自证**（本仓铁律：每条规则须变异自证，否则可能是 false gate）：

```
变异1：去掉 /lsp reload 里的 reinitializeLSP 调用（回到 D15 零调用）
  → (fail) 门禁：src 里存在 reinitializeLSP 的生产调用点   9 pass / 1 fail  ✅ 红
变异2：把 cli.ts 的 lspSkipReason 改名（回到 D16 无门控）
  → (fail) cli.ts 里 initializeLSP 被 print / bridgeUrl 门控  9 pass / 1 fail  ✅ 红
变异3：/reload-plugins 里不判 initState 就报「已重载」（假消息）
  → (fail) /reload-plugins 也会重载 LSP                      ✅ 红
复原 → 10 pass / 0 fail  ✅
```

D15 的门禁判据刻意是**"有没有真实调用方"**，而不是"函数行为对不对" ——
后者本来就一直是对的，正是它让这条缺陷躲过了所有常规排查。

**② D16 在真实二进制上验证了效果**（不是"机理上讲得通"）：

```
SID_CODE_DEBUG=1 ./sid-code --print --debug "说'ok'两个字"
  → [LSP] 跳过 LSP 初始化：无头模式（--print）下无交互式编辑，索引开销无收益  ✅
```

**③ 命令与输出**：

```
bun test ./packages/cli/tests/command/lsp-reload-and-gating.test.ts → 10 pass / 0 fail
bun test ./packages/cli/tests/command/                              → 332 pass / 0 fail
bun test ./packages/core/tests/lsp/                                 → 96 pass / 0 fail（无回归）
make build                → 自检通过；grep "will always be undefined" 无命中
lint / format / lint:boundary → 全绿（越界依赖 0 处）
```

**④ 尚未验证的部分**：
- **`/lsp reload` 让改动后的 lsp.json 真的生效，没有在装了真实 language server 的
  项目上端到端验过**。单测用的是无配置目录（`initializeLSP` 会立即落 success，
  即"无配置也算成功"那条路径），断言的是"走到了真实重载分支而非早退分支"。
  诚实说法是「死接线已接上、重载分支可达」，不是「改配置即时生效已验证」。
- **D16 的 `--bridge` 分支未端到端跑**（跑它需要过 D14 的准入确认，属另一 PR 的范围）；
  该分支与已验证的 `--print` 分支共用同一个门控表达式。
