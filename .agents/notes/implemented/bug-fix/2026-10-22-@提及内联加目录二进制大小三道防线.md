# @ 提及内联加三道防线：末尾 / 不当文件、二进制不内联、超 100KB 不内联

## 决定了什么

`packages/cli/src/app.ts` 的 `expandAtReferences` 原来是 `resolve + readFile(utf-8)` 整文件内联，没有任何大小或类型检查。
事故会话 `20261022-034121-20f64f92`：用户输入里的 `@sid-code/`（本意是包名）被正则匹配为路径，`resolve()` 吞掉末尾 `/`，
命中仓库根 78MB 的编译产物 `sid-code`（Mach-O），整个内联进 user 消息，`raw_preview.jsonl` 第 68 轮估算 45,425,094 token。
单条 user 消息压缩层无法缩小：snip / emergencyTruncate / reactive 三轮全部 `no_reduction` → 熔断 → 网关 nginx 413，会话报废。

本次加了三道防线，被拦下的提及记入新字段 `skippedPaths`，并同时告知模型（「未注入」+ 引导用 Read 分段读）和用户（transient 状态消息）：

1. 提及以 `/` 结尾时直接跳过，必须在 `resolve` 之前判断；`stat` 不是普通文件（目录、设备）的也跳过。
2. 文件大于 `AT_INLINE_MAX_BYTES = 100KB` 时不内联。先 `stat` 再读取，最多只读 stat 出的字节数，不会把整个文件拉进内存。
3. 前 8KB 经 `isBinaryContent`（与 read 工具同一个检测器）判为二进制的不内联。

## 放弃了什么（以及为什么不选）

- **照搬 CC 的「超限截断到前 N 行再内联」**：CC 的 `generateFileAttachment` 走 `FileReadTool.call`，带完整的 token 预算与二进制扩展名拦截。
  我们这里没有接 read 工具，截断后的内容和完整内容在模型眼里难以区分。改成告知模型并引导 Read，让分段与 token 预算只在一处实现。
- **目录提及像 CC 一样内联 readdir 列表（≤1000 条）**：属于功能新增，不在本次止血范围内。这里只做到不读、不报错。
- **在压缩层加「单条消息超大时截断 user 内容」**：那是兜底，不是根因。被截断的二进制本来就不该进上下文。另开议题。
- **上限沿用 custom.ts 文件注入的 10MB**：10MB 文本约合百万 token，同样会撑爆窗口，不能当防线用。
