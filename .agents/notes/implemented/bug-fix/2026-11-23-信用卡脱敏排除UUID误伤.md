# 信用卡脱敏规则排除 UUID 内部命中，device_id 不再被遮成半截

## 决定了什么

`packages/core/src/permission/secret-rules.ts` 的 `credit-card` 规则加第三道校验
`insideUuid()`：命中区间向两侧扩到「非 `[0-9a-fA-F-]`」边界后，若整段恰好是规范
UUID（8-4-4-4-12），判定为误报、不遮。

根因是信用卡正则允许 `[- ]?` 作千位分隔符，而 UUID 的段分隔符同样是 `-`。于是
「段 1 全数字 + 段 2 全数字 + 段 3 全数字」的 UUID 会凑出 16 位数字，再（约 1/10
概率）通过 Luhn，被遮成 `6507********4909-…`。轨迹落盘的 `device_id` 正是 UUID，
用户排查轨迹时看到半截 ID；`collector.test.ts` 里「device_id 完整落盘」的断言
（`session.traj` / `events.jsonl`）也随之偶发变红。

只影响 R1（`sensitive.ts` 的保形遮盖，即轨迹/日志落盘路径）：R2 的 `secret-redact`
只取 `strict` 档规则，`credit-card` 是 `wide` 档；R3 的 `secret-scanner` 没有卡号规则。

## 放弃了什么（以及为什么不选）

- **收紧正则、禁止 `-` 作分隔符**：真卡号常写成 `4111-1111-1111-1111`（现有一条
  回归测试就锁着这个），一律禁止会把真实卡号漏遮。而 UUID 与卡号的连字符位置无法
  在正则层区分——`8-4-4` 的段边界恰好能落进任意两组四位之间。
- **要求分隔符位置严格 4-4-4-4（要么全无分隔、要么每个 4 位后都有）**：能排除 UUID
  （它只有 2 个连字符，且落在第 2、3 组后），但这是一条隐式的「卡号书写格式」新约定，
  未来遇到 `41111111-11111111` 这类写法会静默漏遮；而「UUID 不是卡号」是更本质、
  更窄的判断，误伤面可控。
- **只在 mask 侧特判 `device_id` 字段**：`maskSensitiveData` 是纯文本函数，拿不到字段名；
  而且误伤不限于 `device_id`——任何 UUID（session_id、trace_id）落盘都会中招，
  按字段特判只覆盖已知的那一个。
- **把 Luhn 换成更强的卡号校验（BIN 前缀表 / 长度表）**：能顺带减少随机数字误报，但
  改动面大、需要维护 BIN 数据，且解决不了「UUID 段边界被当成千位分隔符」这个根因。
- **放宽为「只要出现 `-` 就不当卡号」**：会把 `4111-1111-1111-1111` 一起漏掉，等于
  为了修误报把功能改没。

## 拿什么证明它生效了

```text
bun test ./packages/core/tests/permission/sensitive.test.ts
  → 37 pass / 0 fail / 983 expect（新增 2 条用例）
变异自证：删掉 `!insideUuid(index, value.length, text) &&`
  → 36 pass / 1 fail（「UUID 不被误当成卡号」变红），恢复后 37 pass
bun run affected-tests:run  → 1753 pass / 0 fail（70 files）
bun run lint                → 0 warnings / 0 errors
bun run format:check        → 通过（先跑 bun run format）
bun run typecheck:gate      → 62 处 / 基线 62 处，零新增
make build                  → 通过（编译产物自检全绿）
```

真机探针（`bun` 直接调 `detectSensitiveData` / `maskSensitiveData`）：

```text
修复前：65070000-0009-4909-8def-0123456789ab → 6507********4909-8def-0123456789ab
修复后：原样保留
百万随机 UUIDv4（crypto.randomUUID）：误遮 11 → 0 次
真实卡号仍被遮：4111111111111111 / 5500005555555559 / 4111-1111-1111-1111 / 4111 1111 1111 1111
```

关于「约 1/10」的口径：那是**形态已满足之后** Luhn 对随机 16 位数字的通过率。
端到端看，随机 UUIDv4 还要同时满足「段 1/2/3 全数字 + 段 1 前缀落在卡号 BIN 集合」，
实测百万样本命中 11 次（约 1/9 万），且全部从段 1 起始。修复后该路径为 0。
