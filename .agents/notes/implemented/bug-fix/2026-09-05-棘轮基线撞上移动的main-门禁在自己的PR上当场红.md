# 棘轮基线撞上移动的 main：新接入的门禁在自己的 PR 上当场红

## 决定了什么

把 `scripts/command-system-gate.baseline.json` 的 `legacyBuiltins` 从 **35 改成 36**，
并在 `note` 里写清这个数字为什么被调高过一次（含举证口径）。**只改这一个 JSON 数据文件**，
门禁脚本、测试、`ci.yml` 一行未动。

PR #18 的三个红检查（`lint`、`test (ubuntu-latest)`、`test (macos-latest)`，
外加汇聚门 `all-checks-passed`）是**同一个根因**：G2 棘轮实测 36 > 基线 35。

- `lint` job：`bun run lint:command-system` 打出「✗ G2：旧体系命令从 35 增至 36」后 exit 1
- 两个 `test` job：同一条断言 `expect(countLegacyBuiltins()).toBeLessThanOrEqual(baseline.legacyBuiltins)`
  失败（`Expected: <= 35 / Received: 36`），11615 个用例里只有它一条红
- `all-checks-passed`：汇聚门，上游红它必红

**根因是竞态，不是本 PR 引入了旧体系命令**：门禁脚本与基线文件**都是 PR #18 自己新建的**，
基线 35 是切分支时按当时 main 写下的快照。之后 PR #20（`/lsp` 命令，`a07c34e9`）合入 main，
往 `builtins.ts` 加了 `registry.register(new LSPCommand())`，实测变 36。
本 PR 两次 merge main 把它带了进来，于是**新门禁在自己的 PR 上当场红**。

举证（三条，缺一不可）：

- 本 PR 首个提交全程没碰过那个文件：`git show --stat 906c40ce -- packages/cli/src/command/builtins.ts` 输出为空
- 本 PR 起点的计数就是基线值：`git show 906c40ce~1:…/builtins.ts | grep -c registry\.register` → **35**
- 多出来的那一条只在 main 侧出现：`git show 906c40ce~1:…/builtins.ts | grep -c LSPCommand` → **0**

## 放弃了什么（以及为什么不选）

**① 把 `LSPCommand` 迁到新体系，让实测回落到 35。** 否决：那是改别人刚合入的 PR #20 的成果，
超出本 PR（命令系统七处缺陷修复）的关注点，会让 review 混入无关改动，
也撞上 §0「不动与本次任务无关的代码」。而且 PR #20 的 Agent Note 里
`LSPCommand` 进旧体系是**刻意选择**（它复用 `builtins.ts` 的动态 import 装载），
不是随手写错的东西，推翻它需要单独的论证和单独的 PR。

**② 改门禁机制：让 G2 去和 `origin/main` 的实测值比，而不是比一个入库的常数。**
否决：把 git 查询搬进门禁会引入 CI shallow clone（`fetch-depth`）与离线可跑的问题，
复杂度换不到收益。更重要的是——**下次真有人往 `builtins.ts` 加命令时，棘轮红是正确行为**，
不该被一个"自动追平 main"的机制抹平。那样改等于把棘轮降级成永远追得上的影子。

**③ 放宽成 `>=` 或给 G2 加豁免名单。** 否决：那是直接取消门禁，且全程绿、没有任何东西会报警——
正是这道门禁本身要消灭的形态。

**为什么改成 36 不算脚本第 206 行禁止的「放宽基线」。** 这条必须说清，否则下一个人会照抄这个动作。
脚本禁的是「加一条死代码顺手调高数字，全程绿」——**同一个改动里既引入劣化、又放宽阈值**。
当前情形不同：`LSPCommand` 合入时**这道门禁还不存在**。棘轮只能从接入那一刻起约束"新增"，
接入时刻的实测值就是它的存量起点。推论是机制性的：**门禁接入的基线必须等于接入时刻的实测值**，
否则它第一天就是红的，而这正是现在的形态。

判据留在 `note` 里，供下一次想调高这个数字的人对照：能用同样的口径举证
「劣化不是本次引入」才可以改；举不出来就该去接线或删代码。

## 拿什么证明它生效了

**① 修正前后的对照（同一条命令，只改了那个 JSON）：**

```
改之前：G2 旧体系 registry.register: 36  基线 35  → ✗ exit 1
改之后：G1 死导出: 37 基线 37 / G2: 36 基线 36  → ✓ 两道门禁通过，exit 0
```

**② 变异自证 —— 证明它不是「把数字调到不会红为止」，仍能抓真新增：**

```
往 builtins.ts 临时插一条 registry.register(new __MutantProbeCommand());
  → G2 实测 37 基线 36 → ✗ G2：旧体系命令从 36 增至 37，EXIT=1   ✅ 红
复原（cp 备份回写 + git diff --stat 为空确认）
  → 实测 36，✓ 两道门禁通过，EXIT=0                              ✅ 绿
```

脚本注释里写的「加一条就该红」这件事，现在是实测过的，不是推理出来的。

**③ 五道 CI 门禁在本地全绿：**

```

```
