# wait-audit 补宽口径与「未等待期」统计，让空转在审计里可见

## 决定了什么

`scripts/wait-audit.ts` 新增 4 组字段（口径表已同步进文件头）：

1. **`fg_status_polls_any`** —— 窗口内**宽口径**前台状态查询次数：命令含
   `gh (pr|run|api)` / `glab` / `kubectl` / `curl` 的 bash 调用。**不调 `matchStatusQuery`**，
   只认命令族，所以不随匹配面的修复而平移。
2. **`unwaited_status_polls` / `unwaited_longest_run`（+ `_start` / `_end` / `_requests`）** ——
   会话内**不在任何等待窗口里**的宽口径前台查询次数，以及这些调用里最长的连续段
   （相邻间隔 < 60s 视为同段）的调用次数、起止、段内 `BilledRequest` 条数。
3. **`probe_spin_requests`** —— 会话内「工具调用**全是**只读探查」的请求数。只读探查口径
   复用生产函数 `isReadonlyProbeCommand` + `isReadFamilyTool`（不复制白名单，N5 合入后自动覆盖
   `git rev-parse`）。需 `--with-raw`，未读 raw 时为 `null`。
4. **`--all` 收录判据**从 `wait_windows > 0` 改成 `wait_windows > 0 || unwaited_status_polls > 0`
   （抽成导出的 `includedInAll`，由单测钉住）。

「前台」用 traj 的 `tool_input.run_in_background` 判定 —— 真实轨迹里这个字段存在
（962011a6 实测有 1 次后台调用，`wait_until_seconds` 也在），不需要跨数据源关联。

旧字段 `fg_status_polls` / `gh_queries` / `polls_per_min` 的取数与语义**一字未动**。

## 放弃了什么（以及为什么不选）

- **拿 `matchStatusQuery` 当宽口径分母**。它的匹配面会随 N3 变大（fbb02831 的窄口径从 0
  变成 13+），拿它比修复前后必然得出「修完轮询变多了」。这正是北极星铁律 3 说的
  「分母口径一变曲线就整体平移」，宽口径必须不含匹配逻辑。
- **把「排除后台」也应用到旧字段 `fg_status_polls` / `gh_queries`**。它们是两条基线会话的
  历史对账数字（96 / 106），口径一动夹具回归就整体平移，对账链断掉。要「前台」语义就在
  新字段上做，旧字段保持原样。
- **在 `wait-audit` 里复制一份只读探查白名单**。复制一份就必然与 N5 的判定漂移；复用生产
  函数的代价是这个指标跨 N5 前后不可比 —— 所以它只做观察口径，稳定分母仍是
  `unwaited_status_polls`，这一条写进了字段注释。
- **把 `think` 也算作只读探查**。这是「工具调用全是只读探查」的字面口径；`think` 不探查任何
  外部状态，算进去会让指标虚高。代价是它比方案 §7.6 的「git 分支/状态确认」口径小
  （fbb02831 实测 21 vs 87），差异归因见下。
- **新增一个独立脚本**。指标与 wait-audit 同源（同一份 traj/events），放两处维护必然漂移；
  按方案 N7 修法第 2 条，它也**不接北极星主口径**，先观察。
- **改 `UnchangedObservationRun`**。方案明确不改：它的 `intervened` 恒 false 是 N3 没拦到
  的结果（不是埋点错），N3 合入后会自然出现 true。

## 拿什么证明它生效了

**单测** `tests/scripts/wait-audit.test.ts`：23 → **33 pass / 0 fail**（新增 10 条）。
关键几条刻意写成「按当时实现」的形式（`matchStatusQuery(cmd) ? 1 : 0`、
`isReadonlyProbeCommand(REV) ? 1 : 0`），N3/N5 合入后自动跟随，不会在那天变成假红。

**变异自证**（改坏 → 看红的是哪条 → 恢复 → 回绿），5 组全部按预期报红：

| 变异 | 报了什么 |
| --- | --- |
| 宽口径正则改窄成 `\bgh\s+pr\b` | 1 红：`宽口径覆盖 glab / kubectl / curl …` |
| 删掉绕开 `active` 的 else 分支 | 5 红：无等待源、连续段、有窗口窗口外、宽口径覆盖、`--all` 收录判据 |
| `background` 恒为 false | 1 红：`后台 bash 不计入新字段` |
| `includedInAll` 退回只看 `wait_windows` | 1 红：`--all 收录判据` |
| 段内请求数恒 0 | 1 红：`无等待源的连续查询` |

**真实会话**（`bun scripts/wait-audit.ts <id> --with-raw`，2026-11-10）：

```text
fbb02831: fg_polls=0 fg_any=22 unwaited=27 longest_run=7(req=6) probe_spin=21
962011a6: fg_polls=0 fg_any=33 unwaited=74 longest_run=69(req=68) probe_spin=33
```

962011a6 的连续段起止 `11:55:48.988Z → 12:09:15.270Z`，**段内 68 条请求与方案里
「68 次请求、20,820,174 输入 token」完全对上**。调用数比方案记的 68 多 1（69）：
段起点比方案标注的 11:56:16 早一条，间隔 < 60s 所以并入同一段 —— 这是「< 60s 同段」
这条规则的可解释结果，不是口径错。

`probe_spin=21` 比方案 §7.6 的 87 小，两个原因都可核对：① `git rev-parse` 不在当前白名单
（N5/PR-C 合入后自动覆盖）；② 请求里只要夹一条 `think` 就不计入（保守口径）。这两个数字
不混着用。

**全量 `--all`**（不读 raw，6.9s）：`336 个会话（有等待窗口 20）… unwaited=3118
longest_run=1807`。修前这条命令只列得出那 20 个有窗口的会话 —— 另外 316 个
「什么都没挂就前台查状态」的会话在审计里完全不存在，这就是 N7 说的盲区规模。

**门禁**：`bun run affected-tests:run`（选测自动判定为全量，见 PR 描述）、`make build`、
`bun run lint`、`bun run format:check`、`bun run lint:boundary`、`bun run typecheck:gate` 全部通过。
