# HITL 等待按 loop 作用域归属，并补齐 AskUserQuestion / plan 审批的闸门

## 决定了什么

来源：PR #571（F4）的 review 结论。那份 PR 把 HITL 的计数与耗时统一从 `human-input-gate` 派生，
方向正确，但留下三类问题：进程级计数器被当作「本轮」口径、两个真实阻塞等人点没接闸门、
`during_hitl` 的采样时点与区间语义错配。本 PR 逐条修掉。

1. **闸门加「作用域（scope）」维度**（`query/human-input-gate.ts`）：每个 loop 用
   `openHitlScope()` / `closeHitlScope()` 登记一个 scope，`humanInputWaitElapsedMs(scopeId)` /
   `readHitlSegmentCount(scopeId)` 只算归属该 loop 的等待。归属规则写明「宁可漏计，不可多计」：
   未传 scope 时只在「进程内恰好一个活跃 scope」时推断；一段等待中途混入不同 scope / 无法归属的
   等待时，把已过去的部分结算给原归属，之后的部分不再归属任何 scope。
2. **消费侧改为按 scope 读**：`loop.ts` 的 `apiDuration` 扣减、`TurnComplete.hitl_wait_ms`、
   `beginTurn` 的两个轮首快照全部带 `state.hitlScopeId`。`queryLoop` 在 generator 的
   `try/finally` 里 open/close，并把 scope 写进 `SessionState`（`HITL_SCOPE_SESSION_KEY`），
   让 `tool-executor` / `app.ts` 这些拿不到 `LoopState` 的调用点能显式传入。
3. **最高频的两条路径显式传 scope**：`tool-executor` 的权限三路竞争、`app.ts` 的抢跑路径与
   fallback 询问。子代理 loop（`runAgentLoop`）也登记 scope —— 它不消费，作用是让多 agent
   并发时推断**失败**，从而「后台子代理等人的时间不会被扣进主循环的模型耗时」。
4. **补齐两个未接闸门的阻塞等人点**：`AskUserQuestion` 工具本体（`tool/ask-user-question.ts`）
   与 plan 审批（`app.ts` 的 `setPlanApprovalCallback`）。此前它们既不计 HITL，也不让看门狗
   剔除等待 —— 用户读问题 / 读长计划时会被 turn_hard / watchdog 当成无进展。
5. **`during_hitl` 改成区间语义**：迟到报的是「上一个 tick 区间」的实际间隔，原来只在检测时刻
   采样当前状态，等待刚开始/刚结束的那两个 tick 会误标/漏标。改为区间两端取或。
6. **修掉 review 指出的文档漂移**：`digest.ts` 的 `avgLatencyMs` 注释（已扣人工等待）、
   `debug/session-metrics.ts` 的口径说明、`latency-histograms.ts` 里对已删除
   `recordHitlPrompt` 的引用，以及「metric 与 `had_hitl` 同分母」这条已不成立的断言。

## 放弃了什么（以及为什么不选）

- **用 `AsyncLocalStorage` 自动归属（零签名改动）**。实测在 bun 里，async generator 内
  `enterWith` 的 store **会泄漏给消费方与主流程**（`for await` 循环体与调用者都能读到），
  而 `run()` 无法跨 `yield` 生效。实测脚本：两个并发 generator 各自的 body 内传播正确，
  但 `consumer` 与 `main` 读到了 `{"id":"y"}`。所以放弃，改用显式 scope + 唯一性推断。
- **只在 `app.ts` / `tool-executor` 各写一份「本轮等待累计」**。否决理由：那又是第二份口径，
  且都拿不到 loop 内部创建的 `LoopState`；会话状态是两层都能访问的同一份对象，比再造一份计数安全。
- **多 agent 并发时按「栈顶」猜归属**。并发时 begin/end 交错，栈顶与真实发起者不一致，
  猜错的方向是「多计」（伪造更快的样本）。现在多 scope 时一律不猜，只进进程级累计。
- **完全去掉进程级累计**（强制所有消费者都传 scope）。否决理由：`task/registry.ts` 的安全阀与
  `pairing-deadline.ts` 的配对看门狗依赖「进程等了多久」的语义，它们的窗口不是某一轮；
  改它们属于另一件事，会扩大本 PR 的回滚面。
- **让 `AskUserQuestion` / plan 审批也显式传 scope**。工具 `execute(input, signal)` 拿不到 deps，
  plan 审批回调同样拿不到 loop scope；它们走唯一性推断，单 agent 时正确，多 agent 并发时漏计（安全方向）。
