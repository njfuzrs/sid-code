# 无头运行（-p）的退出码与 JSON 结果按实际结局如实报告

## 决定了什么

来源是 bug2mr P2 无头运行的排查结论（docs-research `20261020-bug2mr-P2无头运行-sid-code缺陷排查.md`）。动手前回源码逐条核过，P1 #2（无头 plan 自动批准）已经由 #446 修复，本次不碰。其余四条一起修：

- **P0 #3 退出码**：新增 `packages/cli/src/headless-exit.ts`，`runHeadless` / `runHeadlessSDK` 收尾统一调用 `resolveHeadlessExitCode`。优先级为：信号退出码 > 1（运行时异常 / 预算硬停 / `done.incompleteReason` 非空）> 0。信号处理器在第一个 await 之前同步写入 `receivedSignalExitCode`，主路径 exit 前优先用它，结论不再取决于两条收尾路径谁先跑完。JSON 在未完成时写 `is_error: true` 和 `error.reason`，被信号终止时写 `error.reason: "signal"`。stream-json 路径通过 `HeadlessRunOutcome.incomplete` 取最后一条 result 的 subtype。会话硬顶引发的 `aborted` 沿用既有约定，仍退 0。
- **P2 #8/#9 JSON 字段**：新增 `packages/cli/src/headless-usage.ts`。`-p --output-format json` 增加 `usage_normalized`（逐模型 `normalizeCacheUsage` 后再累加）、`model`、`provider`（fallback 换过 provider 时逗号拼接）、`total_cost_usd`（与 stream-json 同源）、`num_turns`、`duration_ms`。原 `usage` 保持不变。
- **P3 #6 休眠归因**：`stream-processor.ts` 的检查 tick 用 `sleepGapMs` 识别休眠，把休眠时长从静默判据和整体超时判据里剔除。醒来后不再同时打出「首字节超时: 300s」和「重试 1/10」，重连交给 fallback 层的 C1。
- **P3 #7 stdout 污染**：4 个迁移的用户提示从 `console.log` 改为写 stderr，并加静态门禁 `packages/core/tests/migrations/no-stdout-writes.test.ts`。
- 官网 `website/extend/headless.md` 同步更新：json 格式有成本字段、退出码约定表、停滞叫停退 1。

## 放弃了什么（以及为什么不选）

- **把 incompleteReason 改成在 loop 里抛异常，让它走 runError**：会改到 TUI 和 SDK 共用的 `yield done; return` 契约。TUI 依赖 done 回到等待输入状态（loop.ts P0-b 注释），改动面远大于收尾这一处的判定。
- **改原 `usage.inputTokens` 的口径**：bug2mr 等已有调用方在读这个字段，直接改等于静默破坏。所以只新增字段。
- **先 `getTotalUsage()` 再归一化**：fallback 换过 provider 后，两种口径的 inputTokens 已经加在一起，事后拆不开。必须逐模型归一化。
- **休眠时在 stream-processor 里调 `getSleepLedger().record()`**：观测器已经在记账，这里再记一次会把同一段休眠重复计入全局累计，并多触发一次 onWake 回调。
- **#10 GLM `</arg_value>` 残留**：原文档定为「需拍板，先观察频率」（1/2 会话、全量 1/128 请求），本次不做。

trade-off：方向是「更准」。原来靠「退 0 + 空 content」判成功的调用方，在超时耗尽和被中断时会变红，这是有意为之。

## 拿什么证明它生效了

- `packages/cli/tests/cli/print-incomplete-exit-code.test.ts`（子进程 + 黑洞端点）：
  - 重试耗尽用例退 1，JSON 带 `error.reason=timeout_retry_exhausted` 和 model / 成本字段。变异自证：把判定改回 `runError || budgetExceeded ? 1 : 0` 后，该用例报 `Expected: 1 Received: 0`，变红。
  - SIGTERM 落在退避期用例退 143。⚠️ 用主仓 main 的未修代码跑 3 次，退出码都已经是 143（信号路径赢了竞速），失败只出在 stdout 被迁移提示污染导致 JSON 解析报错。也就是说，原文档「退避期 kill 退 0（4/4）」在当前基线上没能复现，`receivedSignalExitCode` 属于去掉竞速的加固，这条用例证明不了它修前会红。
- `stream-processor-sleep-not-silence.test.ts`：挂钟前跳 1000s 时不触发首字节超时。变异自证：删掉 `lastActivityTime += slept` 后该用例变红。另有一条真实静默仍会中断的用例保持绿。
- `headless-usage.test.ts`：用文档 §7.1 的两组真实数据断言 `prompt_total` 分别等于账本的 690,683 和 3,244,574。
- `bun run affected-tests:run`：3889 pass / 0 fail。跨域补跑（core/llm、core/sdk、cli/cli、tests/eval 等）2580 pass / 0 fail。`make build`、lint、format:check、lint:boundary、lint:command-system、typecheck:gate（66/66）、docs:gen-reference --check 全部通过。
