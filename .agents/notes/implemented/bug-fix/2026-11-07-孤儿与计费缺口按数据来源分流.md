# digest 剩余三条 high 按「谁产生的数据」分流，不再一律报故障

## 决定了什么

排查诊断检测器精度治理的 T5 + T7（方案见 `docs-research/sid-code/bugfixes/todo/20261102-X1H3-排查诊断-检测器精度治理-落地方案.md`）。三处判据改动：

1. **`tool_use_without_result` 按「工具是否真执行过」分流**（`packages/core/src/trace/digest.ts`）。
   判定依据是 `events.jsonl` 里有没有同 `tool_use_id` 的 `PostToolUse` / `PostToolUseFailure`
   （执行侧直接写，与 traj 的增量切片是两条独立落盘路径）。
   - 全部孤儿都有收尾事件 → 新 kind `trajectory_tool_result_lost`，**medium**，
     pointer 指向 `collector.ts` 的 `computeNewMessages`，不发崩溃假设；
   - 尾部孤儿 + 中断类退出（abort / user_interrupt / terminal_closed / unknown）→ **low**；
   - 其余（既无收尾、又不在尾部）→ 保持 **high** + `hypothesis_crash_or_violation`；
   - §20.3 的 maxTurns 降级逻辑优先级最高，未被覆盖。

2. **`errors_jsonl_has_entries` 区分「已恢复」与「最终失败」**。
   `context.willRetry === true` 且**同 index 之后真的出现了 `AfterModelRaw`** 才算恢复：
   未恢复的仍报 high，已恢复的单独报 `errors_jsonl_recovered`（low），让「这轮重试过」仍可见。

3. **`billing_identity_broken` 的「退出截断」判据从一条扩到三条**。
   旧判据只有「SessionEnd 前 10 秒」；新增 `after_session_end`（fork 在 SessionEnd 之后才建连）
   与 `no_session_end`（被强杀 / 终端关闭），窗口从 10 秒放宽到 60 秒
   （实测退出截断样本落在 7–22 秒，真正的中段漏记是 5 分钟起步）。
   缺口 detail 逐个标注归因依据；`billed > conn` 的措辞从「同一 fetch 被重复计费」
   改为「建连事件缺失或重复计费」（两个方向在只有两个计数时不可区分）。

## 放弃了什么（以及为什么不选）

- **不选「建连之后到会话结束再无任何计费事件」作为第四条退出判据。**
  听起来更语义化，实测会把「建连后 5 分钟才结束、期间恰好没有别的模型调用」判成退出截断 ——
  那正是要抓的中段真漏记。既有用例 `digest-harness-actions-not-faults` 的 T3b2（300 秒缺口
  必须是 high）直接因此变红。没有 agent 维度的事件可用于细分（`AfterModelRaw` 全库
  35134 条里 **0 条**带 `agent_id`），更宽的语义判据在这里只会放过真缺陷。
- **不按 `AfterModelRaw.agent_id` 做 per-agent 判定。** 同上：该字段全库为空，
  `?? "main"` 会把 fork 全算成主链，判据恒不成立（静默失效比误报更危险）。
- **T5 不按 observation 文案判「工具是否执行」。** 沿 T2 的结论：文案是给人看的，
  改一次措辞判据就静默归零。用结构化事件 `PostToolUse`。
- **T7 errors 不只看 `willRetry` 就判恢复。** 本地 18 条是「打算重试但最终失败」，
  只看标志位会把它们一起放过；必须要求同 index 之后真的有 `AfterModelRaw`。

  T7 errors 的 `recoveredByRetry` 置 false → 恢复用例红；`classifyBillingGap` 退回只认
  10 秒窗口 → 三个退出形态用例红。

- **真实数据验收**：对本地 877 个会话逐会话跑 digest，与 main 对比（876 个共同会话）：

  | 指标 | main | 本改动 |
  | --- | --- | --- |
