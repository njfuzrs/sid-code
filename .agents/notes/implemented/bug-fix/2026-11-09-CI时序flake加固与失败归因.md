# CI 时序 flake：把「固定等待」换成条件轮询，把「中位数」换成最优轮，把「无归因失败」换成带线索

## 决定了什么

按 `docs-research` 的《20261107-CI时序flake与失败归因-全量排查》（150 次 run 全量排查）落地
第一档与第二档，并把两处生产语义缺陷一并修掉。分四组：

**① 固定等待 → 条件轮询（6 个测试文件）**

| 文件 | 原来 | 现在 |
| --- | --- | --- |
| `packages/cli/tests/ui/components/PluginsDialog.test.tsx` | `press()` 等 100ms 后立即断言（Esc 判窗口吃掉一半） | 断言前 `waitFor(帧含目标文本)` |
| `packages/cli/tests/ui/components/layout-bottom-region-snapshot.test.tsx` | 固定 60ms 等 effect 链 | `renderLayout` 新增 `until` 谓词，轮询到帧满足条件再取帧 |
| `packages/core/tests/memory/extract-quantify-t1-t3.test.ts` | `turns()` 每轮 `setTimeout(5)` 近似等 fork | 轮询到该轮应有的 `calls.n`，再让出一个宏任务排干微任务链 |
| `packages/cli/tests/startup/large-data-startup-gate.test.ts` | 等到 `existsSync(dump)` 就 `JSON.parse` | 等到「能 parse 出完整 JSON」，仍在同一 45s deadline 内 |
| `packages/cli/tests/render-port/main-screen-shrink-e2e.test.ts` | `type()` 完直接 `write("\r")` | `submit()`：轮询「提交的后果」（轮次开始信号），没出现就重发回车 |
| `packages/cli/tests/render-port/selection-runtime.test.tsx` | 吃 bun 默认 5s 超时（实测 5009.75ms） | 显式 `30_000` |

**② 计时判据：中位数 → 最优轮（`large-data-startup-gate.test.ts` 4 处）**

`pairedDelta` 的结果原来取 `median`，改为 `bestRound`（最小值）。3 个样本的中位数对离群值
零鲁棒：实测 `Δframe=[836/226/31]` 的中位数是 226ms，直接越过 150ms 阈值，而 836ms 那一轮
是首次启动冷启动，本来就不是门禁要量的东西。

**③ 失败可诊断性**

- `tests/build/no-real-trajectory-writes-runtime.test.ts`：`Bun.spawn` 的 stdout/stderr 管道
  **读干**，失败时用 `childFailureHints` 抽出 `(fail)` / `error:` 行。原来 `stdout: "pipe"`
  却从不读取，既拿不到归因，也有 pipe 满导致子进程阻塞、`proc.exited` 永不 resolve 的死锁风险。
- `large-data-startup-gate.test.ts` 的 `beforeAll` 加分段 `phase()` 打点。beforeAll 超时时
  bun 只报一条 `(unnamed) [NNNNms]`，2026-11-07 CI 那条 20547ms 的失败完全没有位置信息。

**④ 两处生产代码**

- `packages/core/src/mcp/oauth-callback-server.ts`：`close()` 结算在途的 `pending`（reject with
  「已关闭」），并给 `waitForCode` 返回的 Promise 挂 no-op `catch`。原来 `close()` 只关 http
  server、不清 `waitForCode` 的定时器，5s 后 reject 一个没人接的 Promise，被 bun 归因到
  **另一条测试**上（2026-11-07：纯 sandbox 的 A6d 只跑 3.74ms 就「失败」，失败原因是 OAuth 超时文案）。
- `packages/core/tests/llm/fallback-content-progress-timeout.test.ts`：正向用例从
  `slowButHealthyProvider(8, 40)` 改为 `(32, 10)`。

## 放弃了什么（以及为什么不选）

**① 否决了方案文档给 fallback 的两个改法**（「mock 间隔 40ms→10ms」或「阈值 100ms→500ms」）。

两条都会让**总时长低于阈值**：8×10ms=80ms < 100ms、8×40ms=320ms < 500ms。那样连「不感知内容
进展」的旧实现也不会超时，测试恒绿、验证力归零。慢 runner 上的病因是「40ms 间隔被调度延迟到
>100ms」（余量 2.5x），要放大的是**间隔余量**，同时必须保住「总时长 > 阈值」这个前提。
块数翻倍 + 间隔缩小正好两全：总时长 320ms 不变（3.2x 阈值），间隔余量 2.5x → 10x。

**② 否决了方案文档给 3 轮中位数的首选建议**（轮数提到 5–7）。

`ROUND_ORDER` 是「三轮 × 三种配置各坐一个位置」的对称设计。5 不是 3 的倍数，位置偏差不再
抵消；按 3 的倍数加到 6 轮则墙钟翻倍，而这条测试本来就是 400s 超时的重测试、单分片墙钟
547s 正需要压缩。在「换统计量」和「加样本」之间选了前者。

**③ 否决了「写侧临时文件 + rename」**（方案文档第二档给的两个选项之一）。

`startup-profiler.ts` 的 `writeFileSync` 改成原子写会动生产写盘路径。剖析是诊断手段，
读侧容错（parse 失败继续等到 deadline）已经解决竞态，改生产只为测试让路不划算。

**④ 没动方案文档第三档**（macOS 分片 2→3、把重用例挪独立 job、`--retry`）。

都标着「需算账」：分片 2→3 会撞 Free 档 macOS 并发上限 5（片数 × 在跑 run = 6 > 5，排队
反而更慢）；`--retry` 会掩盖真回归。这些需要维护者按套餐与配额拍板，不适合随本次 PR 顺手改。

**⑤ 没碰 3.9「`0 fail` 但 exit code 1」**。

方案文档自己标了「未定位、无 stack」。没有把它与 3.7 的定时器泄漏混为一谈去猜因果——
那正是「目标指标改善 + 测试全绿 + 机理讲得通」三者同时成立却仍可能错的场景。

**② 全量测试**：`bun run affected-tests` 判定 `full`（改到 `tests/build/` 这个仓库级路径），
按 CLAUDE.md「affected-tests 自己判定为仓库级改动」的口径跑了全量。

**③ 变异自证**：本次没有新增门禁，改动分两类，各自的自证方式不同：

- **测试等待方式**（①②③组）的「变异」就是改回原样 —— 那不是一种可观测的断言变化，
  所以这几条靠**重复运行**证明稳定性，不靠改坏。
- **`close()` 结算 pending**（第④组）有明确的反例形态：把 `close()` 改回「只关 server、
  不清 pending」，则 `waitForCode` 的定时器会在 close 之后 fire，reject 一个没人接的
  Promise。这条的最终判据落在 CI：3.7 那类「失败归因错移到另一条测试」不再出现。
