# 修复 Skill 系统六项 P0：ask 规则、$ 注入、模型路径管道、context 字段、零工具、paths 门绕过

## 决定了什么

来源：`20260927-Skill系统-顺着sc-10-skills核出的缺陷` 的 P0-1…P0-6。P1/P2 本轮不动。

- **P0-1**：`SkillPermissionRules` 加 `ask`，`extractSkillRules` 收集 `rules.ask`，
  `checkSkillPermission` 判定顺序改为 deny → **ask** → allow（ask 早于 allow，
  否则 `allow:["Skill"]` 通配盖掉精确 ask）。ask 的 reason 区分「规则命中」与「敏感属性」。
- **P0-2**：`substituteArguments` 改成**单遍 + 函数形式**替换；`${SKILL_DIR}` /
  `${SESSION_ID}` / 内联 shell stdout 的 replace 也改函数形式。单遍是为了修一个同源问题：
  旧实现分三趟，`$ARGUMENTS` 塞进去的用户输入会被后面的 `$1` / `$name` 再解析一次。
- **P0-3**：`SkillMetaTool` 在分发前跑 `processSkillPrompt`，两分支共用结果；
  新增 `setSessionIdProvider`（app 侧接 `getLogicalSessionId`，函数形态以跟随 resume）。
  **安全裁决**：模型路径下每条 `` !`cmd` `` 按一次 `bash` 工具调用过子代理 checker
  （dontAsk 语义，只有 allow 且不需确认才执行），无 checker 一律不执行（fail-closed）。
  用户斜杠路径保持不设门（显式意图）。正文已消费参数占位符时不再在末尾追加「用户输入」。
- **P0-4 + P2-3**：抽出 `resolveSkillExecutionContext()`（executor.ts），meta-tool 的
  `execute` / `resultDisplayMode`、`SkillCommand`、`skillToCommand` 四处统一调它。
- **P0-5**：抽出 `resolveSkillAllowedTools()` + `DEFAULT_SKILL_ALLOWED_TOOLS`
  （read/grep/glob/ls 只读四件套）：未声明 → 默认集并 warn；显式声明（含空数组）原样尊重。
  接到 meta-tool、SkillCommand、CommandExecutor 的 skill fork、BundledSkillTool 四处。
- **P0-6**：`loadDiscoveredDirs` 对新 skill 走 `conditional.separate`，条件 skill 经新增的
  `SkillManager.gateSkills()`（追加语义）gate 住，只有无条件 skill 进 pendingActivated；
  触发本轮发现的路径若匹配新条件 skill 的 paths，同一轮内激活。

## 放弃了什么（以及为什么不选）

- **P0-5 让 allowed-tools 对 delegate 必填**：最 fail-closed，但会让现存 skill 批量失效，
  且与教学文档 §1.1 的最小示例冲突。
- **P0-5 传 undefined 让下游区分「未声明 / 空」**：`CustomSubAgentTask.allowedTools` 是必填
  `string[]`，改类型面大；而且「未声明 = 全部工具」违背最小权限。
- **P0-5 默认集含 bash**：bash 是写/执行能力，放进默认集等于「不写就给最大权限」。
- **P0-3 模型路径直接执行内联 shell**：会把「没生效的能力」变成「生效了但没门禁的能力」——
  模型能经选一个 skill 间接触发 shell。
- **P0-3 模型路径一律禁用内联 shell**：会让用户 allow 过的只读命令（如 `git status`）也不可用，
  且与用户路径语义永久分裂；按 bash 规则过 checker 能复用用户已有的配置。
- **P0-6 用覆盖式 `setGatedSkills` 重设 gate**：会把 init 时已 gate、尚未触发的条件 skill 放出来。
- **P0-6 新条件 skill 等下一次触碰再激活**：用户要碰两次同一文件才激活，反直觉。
