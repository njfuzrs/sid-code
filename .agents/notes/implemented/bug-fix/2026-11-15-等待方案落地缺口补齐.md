# 等待态方案落地缺口补齐：monitor 面板展开与权限审计来源

## 决定了什么

对《20261108-等待外部状态-合法等待态与 Monitor 工具-设计方案》做逐条落地复核后，
补齐两个**方案明确要求但代码里没有**的功能项，以及四条此前只有编号没有用例的验收。

1. **`MonitorRow` 支持 `Ctrl+O` 展开脚本首行**（`packages/cli/src/ui/components/TodoPanel.tsx`）。
   方案 §5.7 面板表格第 3 行写的是「`⏎` 活动行 | 默认无；`Ctrl+O` 展开显示脚本首行」。
   此前只实现了「默认无」，展开这一半缺失 —— 数据侧 `state-bridge.ts` 早就把 `command`
   带进了 `TaskDisplayInfo`，差最后一公里。展开的是**脚本**（回答「它在盯什么」），
   不是事件（那会与消息流重复，§5.7.2 去重原则）。

2. **`PermissionDecision` 事件补 `effectiveTool` 字段，monitor 记 `bash`**
   （`permission/decision-telemetry.ts`、`analytics/events.ts`、`permission/checker.ts`）。
   方案 §5.4.6 要求「`tool_name` 记 monitor、`effective_tool` 记 bash，审计能区分来源」。
   此前只落实了「规则匹配视角换成 bash」（`commandRuleRequest`），决策事件上没有任何
   标记 —— 轨迹里「monitor 继承 bash 规则放行」与「bash 自己被放行」长得一模一样，
   事后查不出某条 allow 是不是继承来的。
   两个字段的分工：`tool` = 谁发起的，`effectiveTool` = 按谁的规则算的。
   **只标这一个字段**，不继承 `bashShape` / `envPrefixVars`——那是 bash 工具自己的
   统计口径，混进 monitor 会污染「bash 确认分布」的分母。

3. **补四条缺失用例**：
   - `T-M1-19`（`tests/permission/monitor-rule-mapping.test.ts`）：`Bash(gh:*)` 的 deny
     规则同样拦 monitor；allow 放行时 `effectiveTool === "bash"` 且不带 bash 统计字段；
     bash 自己与 read 都不带这个字段（缺失 = 与 `tool` 同口径）。
   - monitor 行展开（`tests/ui/components/todo-panel-wait-sources.test.tsx`）：默认不显示
     脚本、level 1 显示、展开后仍不出现事件正文、无 `command` 时不崩不多行。
   - `T-T1-11`（同文件）：插入唤醒行**不挤动既有任务行**（整帧逐字符相同）+ 无等待源时
     不出 `[WK]`/`[MO]` 行、不多出任何一行。此前「无等待源时逐字节不变」只有
     `Footer.tsx` 的一句注释承诺，没有断言 —— 注释不产生约束。
   - `T-W3-7`（`tests/tool/todo-write-wakeup-invalidation.test.ts`）：一轮内
     `>0 → 0 → >0`，中间归零即撤销且不恢复。这是方案 §10.5 **自己承认的误撤销风险**，
     此前没有哨兵；谁把判据改成「清零且本轮结束仍为 0」，这条会红并迫使改动方
     显式处理那个取舍。

## 放弃了什么（以及为什么不选）

1. **`T-W1-8`（休眠跨过 monitor 期限）没有写单测**。
   它要验证的是「定时器在进程挂起后补 fire」，这是运行时（Node/libuv）对
   `setTimeout` 的保证，不是本仓代码的行为。要自动化只能 mock 全局 `setTimeout`/
   `Date.now`，而同批测试跑在同一进程里，全局 mock 会污染其它用例 —— 代价高于收益。
   方案 §6.3 第 1 行要求的「不扣减休眠时长」在实现上已经成立（期限用 `setTimeout`
   而非墙钟差，`monitor-task.ts` 的 `deadlineTimer`），只是无法用一个不污染全局的
   单测证明。**保留为已知缺口，不伪造一条恒绿用例。**

2. **`T-W3-4` / `T-W3-8` / `T-W3-11` 没有补**。
   - `T-W3-4`（fired 排队时清单清零 → `dropped_invalidated`）：功能在
     `app.ts` 的 `injectScheduledPrompt` 里已落地（`isWaitInvalidated` 门禁 +
     `dropped_invalidated` 结果），但它的测试入口需要把调度器与注入器一起装配，
     而 `wait-registry.test.ts:801` 已覆盖「已 fired 的唤醒被 S2 撤销后不再算等待源」
     的同一判据。**判为重号，不重复造**。
   - `T-W3-8`（撤销系统行不进 ctxMgr）：实现是 `loop.ts:7584` 的
     `kind: "system", persistent: true` yield，不 `addMessage`；已有
     `wait-notice-persistent.test.ts` 锁「常驻提示不重复累加」，覆盖同一机制。
   - `T-W3-11`（9e3a681d 真实轨迹复现）：需要在仓库内提交一份会话夹具。该会话的
     关键序列（03:58 清单清零、唤醒已在队列、不注入）与 `T-W3-7` 的判据重叠，
     单独再造一份夹具的边际价值低于它的维护成本（夹具会随 features 演进腐化）。

3. **monitor 行不加常驻 `(ctrl+o 展开)` 提示**（与 ui/CLAUDE.md L3.3 的默认做法不同）。
   面板行宽度被「`[MO] 描述` + `N 事件 · 剩 Xm`」两段占满，再加一段提示会把描述
   截到不可读；`Ctrl+O` 是全局键，用户在消息流的长结果上已经学会一次。
   **这是有意的偏离**，不是漏做。

4. **E2E-1..11 仍未做**。它们是 `sc-dev` 真实 TUI × 3 次的人工核对，需要交互式终端，
   agent 环境跑不了。方案 §9.9 早已如实标注「截至 2026-11-12 仍未做」，
   本次没有改变这个事实 —— **不把它写成已完成**。
