# 管线达标改同源估算、压缩收尾绑到「压动了」事件上

来源：`docs-research/sid-code/bugfixes/todo/20260920-上下文工程-顺着sc-02-context核出的缺陷.md` 的全部 P1（P1-6 … P1-15）。文档写「P0 之后按放大器 / 尺子 / 收尾 / 切开口」分批；同一次审计、同一次交付，合一个 PR。

## 决定了什么

1. **P1-6** 抽出 `estimateConversationTokens`（CJK 区分、thinking、结构开销、system/tool schema），`Manager.rawEstimateTokens` 改走它；新增 `estimateTokensFor(messages)` 给管线逐步替换消息时用。校准系数吃，压缩前的 `lastActualInputTokens` 下界**不吃**——那是压缩前的锚点，套上会让管线永远认为「还没压够」。`loop.ts` 的 hard 档调用把 `estimateTokens: (m) => ctxMgr.estimateTokensFor(m, toolCount)` 传进去。
2. **P1-7** `pipelineTargetRatioFrom(ctxMgr)` 从 `compactionTriggerUsed / maxTokens` 派生达标比例（钳在 [0.3, 0.95]），hard 档调用时显式传入。1M 窗口 hard 约在 82% 进场，写死 0.7 会多丢一截历史；反过来 completionBuffer 抬高时 0.7 会让管线第一步空跑。
3. **P1-10** `generateCacheKey` 纳入当天日期。日期不是 ctx 字段，缓存命中路径不重算 `generateDateAttachment`；键不含日期时，跨午夜且 TTL 未过期会送出昨天的 `<current-date>`。
4. **P1-11** `cachedMicrocompactState` 接到 `CommandContext` / `AppContext` / `toCommandContext` / `app.ts` 命令上下文 / 手动 `runPostCompact` 调用点。此前类型里根本没有这个字段，第 2 步（重置两个 Map/Set）在手动路径上永远走不到——不是数据错乱，是长会话真实内存泄漏。
5. **P1-12** 手动 `/compact` 质量校验改传 `originalMessages.slice(0, result.splitIndex)`（真正进了摘要的那一段）。auto 路径一直传 `toSummarize`；手动路径把保留段算进分母，覆盖率系统性偏低，本该合格的部分压缩被报成「摘要质量塌陷」。
6. **P1-13/14** 收尾从「绑在 `autoCompact` 函数上」改成「绑在『压缩真的发生了』这个事件上」。`QueryDeps.postCompactTail` 由 App 注入（fileReadTracker / cachedMicrocompactState / sessionDir 只有 App 持有），`queryLoop` 在 `settleCompaction` 返回非 null（实测消息数下降）后调它。reactive 四个调用点 + collapse 成功且消息数真减。`runPostCompact` 允许不传 `originalMessages`/`summary`：这两条路径没有「一段原文 → 一份摘要」的可比对配对，传空串会算出覆盖率 0，把「没有可测的摘要」伪装成「摘要质量塌陷」。
7. **P1-15** `findSplitThinking` 接到 `snipCompact`：thinking 被整条裁掉此前零检测。只报不改——thinking 没法像 tool_result 那样补占位，伪造 thinking 块是在造假思考。

P1-8 / P1-9 **不改代码**：见下一段。

## 放弃了什么（以及为什么不选）

- **P1-8 把 git 快照改回动态区**（上一轮会话的方案，本轮一度落地、被既有测试拦住后撤回）。缺陷文档写明 P1-8「不独立引入新机制」，它是 P0-1 的击穿半径放大器：CLAUDE.md 漏标进动态区后，git 变一个字节就连它一起重算。P0-1 已在 main 落地（`claudeMd` / `denyRules` / `skillListing` 都是 `stableAttachment`），放大器的病根没了。把 git 挪去动态区只是换个方向踩同一个坑（每次新提交都击穿整块动态区），而且会掉进 `attachments.ts` 那段【关键决策】已经处理过的「git 快照冻结死循环」。两条既有测试（`cacheStability === "stable"`、`<git-status>` 在 DYNAMIC_BOUNDARY 之前）是这个方向性结论的守卫，不是要改的断言。
- **P1-9 改 `prependSystemMessage`**：文档自己说「机制对、内容不对」，是 P0-1 的连带效应。CLAUDE.md 已回静态区，搬走的内容不再含它。给 hook / provider 加新切分是对外 schema 变更，不该由这条缺陷修复顺手带出去。
- **给 `firePostCompactEvent` 加 `reactive` / `collapse` 枚举值**：hook 对外 schema 只有 `manual | auto`。reactive / collapse 归到 `auto` 上报（系统自己决定压的），只在内部 trigger 与日志里区分。
- **reactive / collapse 路径伪造一份空摘要去做质量校验**：`checkCompactQuality("")` 覆盖率恒 0，正好污染 `compact-quality.jsonl` 和 `recommendParams` 的均值——这是 P1-12 那类「分母错了，阈值再对也是假数」的翻版。没配对就不测、不入库。
- **在 loop.ts 里直接 import `runPostCompact`**：收尾要的三个会话级实例 QueryDeps 里一个都没有，硬接会把 App 的持有关系拆散。走可选 dep，未注入则退回仅埋点（行为同旧版）。
- **collapse 自报 success=true 就调收尾**：与 `settleCompaction` 同一条铁律——「成功」必须由实测消息数下降定义。假压缩触发重注入会往没腾出空间的上下文里再塞 50K。
- **emergency / blocking 截断也并进本 PR**：文档自己标 P2-22，理由是「那是最后一道强制截断，缺收尾是恢复质量问题，不是声称共享收尾却没共享」。不挤本条。
