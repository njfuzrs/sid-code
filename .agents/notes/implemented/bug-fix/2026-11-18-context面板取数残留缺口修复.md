# 修掉 /context 取数链路上残留的 9 处口径缺口，并给每条补上会变红的门禁

## 决定了什么

2026-11-18 复核 A1–A7 / B1–B9 / C1 / C2 的落地情况时，逐条回源码核验后发现 9 处**代码里实际存在的**口径缺口。本 PR 一次修完：

1. **ASCII 系数两套并存**（`#928` 只改了一半）：`context/token.ts:23` 是 `0.28`，`llm/token-estimator.ts:60` 仍是 `0.2`。后者经 `cli/src/app.ts:2150/2153` 的 `estimator.estimateTools(defs)` → `ContextManager.setToolSchemaTokens` 注入面板，于是同一会话里「消息按 0.28、工具定义按 0.20」，工具 schema 被系统性低估 28.6%。→ 统一为 `0.28`。
   两处常量无法互相 import（`token-estimator.ts` 已依赖 `context/token.ts` 的 `estimateBlockTokens`，反向会成环），改由**行为级**门禁 `token-estimator-coefficient.test.ts` 锁住同值。
2. **`collapsedRefIds` 从不重置**：`manager.ts:621` 声明，唯一读写 `:1772-1773`；`resetLocalCompactState()` 清了 `tokenFreedTracker` 等 8 项却漏它。压缩/`setMessages` 后旧 `tool_use_id` 仍在集合里，再次折叠时 `has()` 命中 → 内容真的又瘦了一次但**不记账** → freed 偏小、`getSendTokens()` 偏大。→ `resetLocalCompactState()` 补 `this.collapsedRefIds.clear()`，与 tracker reset 同处同刻。
3. **E1 分析脚本分母混入重试轮**：`AfterModel.usage` 是跨 attempt 累加的（`accumulateUsage`；`stream_restart` 刻意不回退 usage），`scripts/context-estimate-baseline.ts` 只滤 `calibrated && !aborted`，重试轮的累加 actual 直接进 M1/M2。→ 分母加 `!c.retried`；把原本命名错误的 `excludedRetried`（其实统计 aborted）拆成 `excludedRetried` + `excludedAborted`，并在表格里三项分列。
4. **残差钳 0 会破坏自己承诺的等式**：`fixed-overhead.ts` 在细目之和略超母项时把 `residual` 钳 0，而「细目逐项 round + 母项 ceil/最大余数分配」本就可能差 1~2 token → 面板加总不闭合且残差行（只在 >0 时画）不显示。→ 保留负值使 `Σ sources + residual === 母项` 恒成立；渲染层（`context-render.ts`）用 `max(0, residual)` 且仅在 >0 时画行。
5. **熔断文案两个口径相比**：`buildCompactCircuitBreakerText` 的 `fixedTokens` 走 `estimateFixedOverheadTokens`（不扣 freed），`totalTokens` 却传 `getSendTokens`（扣 freed）→ 释放量大时比值虚高，把「历史里还有可压内容」误报成「压缩无法解决」。→ 三处调用点改 `getHistoryTokens`，并加源码门禁锁住同口径。
6. **B8 对账文案误导**：`used`（发送量，扣 freed）与 `lastActualPromptTokens`（SessionState stock，压缩后仍是压缩前旧值）是两个状态机，差额里混着压缩/清理造成的下降，旧文案却写「本轮新增 − 本地释放」。→ 改文案为「含压缩/清理下降，非单轮增量」，取数源不变（文档设计明确用 stock）。
7. **`tool_use +20` 没有门禁**：`breakdown-same-source.test.ts:181-195` 的 `visited === total` 两边是同一加数，删掉 `TOOL_USE_STRUCTURAL_TOKENS` 会同时变小、断言仍绿。→ 改为捕获 block 分量并断言 `tokens − estimateBlockTokens(block) === 20 / 10`。
8. **中文夹具没测到 `cleanedMessages` 记账点**：原用例先调 `applyColdCacheClear()`，大输出已被换成占位，`getCleanedMessages` 的 cleanMap 为空 → 回退 `chars/4` 后仍全绿。→ 新增不调冷清理的用例，单独断言 `freed.byStrategy.cleanedMessages` 与 `rawFull − rawSent` 严格相等。
9. **归零门禁可绕过**：`context-size-api-gate.test.ts:127` 只匹配 `\.estimateTokens\(`，解构别名 / 方括号访问全绿。→ 扩成「成员访问 + 方括号 + 解构」三条正则（**不拦裸名**：`config/token-utils.ts` 有同名工具函数，拦裸名会误伤 `system-prompt.ts` 的合法调用）。

## 放弃了什么（以及为什么不选）

- **不把两处系数抽成共享常量**：`llm/token-estimator.ts` 已依赖 `context/token.ts`，反向 import 成环；抽到 `shared` 会动包边界与十几个调用方，超出「context 取数口径收尾」这个关注点。改用行为级门禁防漂移，代价是多一个测试文件，收益是不动依赖方向。
- **不修 `accumulateUsage` 导致的 stock 偏大**：`Usage.inputTokens` 跨 attempt 累加是**计费**口径（作废尝试真实计费），而 `mainContextStock` 要的是**上下文**口径（末次 attempt）。修它需要在 `Usage` 上引入 `lastAttemptInputTokens` 并同步 stream-processor / 计费 / 轨迹三处语义，且必须用真实 `stream_restart` 场景验证——与本 PR 的关注点不同，留给单独 issue。
- **不改 B8 的取数源**：文档 §5.3 明确 `lastActualPromptTokens` 取 `getStockPromptTokens()`；换成 Manager 锚点会改「末次请求真实输入」的语义。只修文案，让差额的含义与计算一致。
- **不用 AST 做归零门禁**：三条正则已覆盖当前全部可绕过形态，AST 需要引入 parser 依赖或自写遍历，收益不抵成本。
- **不把 `residual` 的负值显示出来**：负残差对用户没有可行动含义（多为 1~2 token 取整差），只在内部维持等式、debug 日志留信号，渲染层钳 0。
