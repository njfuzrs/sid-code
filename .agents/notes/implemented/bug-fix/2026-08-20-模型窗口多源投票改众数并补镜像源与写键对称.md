# 模型窗口多源投票改众数 + 补 models.dev 镜像源 + 采集写键对称

## 决定了什么

修掉「模型元数据获取」链路上**四个各自独立、且都不报错**的失败点。用户报的症状只是
glm-5.3 窗口被低估 5 倍，但排查发现「数据拉回来了」到「查询时拿到正确值」之间有三个
独立的洞，只修数据源不够。

1. **多源窗口投票从 `min` 改成众数**（→ 平局取大 → 无众数取 max）。
   原设计取 min 的理由是「窗口高估会吃 400，保守更安全」，它隐含一个前提：源之间的分歧是
   测量噪声（1M vs 1.048M 那种）。**这个前提不成立** —— 源数据按 provider 分条，同一模型在
   不同 provider 上是不同部署，第三方托管常阉割上下文，分歧是数量级的（实测 glm-5.2 在
   digitalocean=262144 / scaleway=256000 / routing-run=200000 / 第一方 zai=1000000，差 5.2 倍）。
   min 于是**系统性选中最阉割的那个部署**。
   累加器同时从「一个键一条 entry 两两折叠」改成「一个键一组候选，末尾统一投票」——
   这不是重构，是**众数不可结合**（`mode(mode(a,b),c)` 无意义）逼出来的形态变更。
   `SCHEMA_VERSION` 1→2，让「换了投票规则必须重采」变成机械行为而不是靠人记得删缓存。

   **`maxOutputTokens` 同批也从 max 改成众数**（这条不在原方案里，是复算时发现的）：
   加了第三个源之后，取 max 的正确率从 60.0% 掉到 **31.3%**（53/83 高估，最坏 Infinity 倍）。
   原因是**有些源把 context 值填进了 output 字段**（gpt-4.1 真值 128K，某些源报 1047576；
   gpt-4o 真值 16384，某些源报 128000）。两个源时这种条目是少数，取 max 只偶尔踩到；
   加到 30+ provider 后取 max **几乎必然捞到那条错的**。改众数后回到 74.3%。
   —— 只按方案改窗口投票的话，本 PR 会一边修好窗口一边把输出上限打坏，而症状同样是 400。

2. **采集写键收敛成共享的 `expandKeys`**（新模块 `model-name-normalize.ts`）。
   `parseOpenRouter` 写「全名 + 裸名」两个键，`parseLitellm` 只写全名键 —— 而 litellm 以
   `provider/model` 为主键（实测 3040 键里 2471 个带 `/`，其中 1848 个的裸名根本不存在），
   企业网关暴露的却是裸名。74.8% 的 litellm 数据被存成了**永远查不到的形态**。
   与查询侧 `normalizeCandidates` 互为镜像，对称性写成 property-based 不变式锁住。

3. **新增 models.dev 双镜像源**。models.dev 官方域国内不可达（实测 curl 12s 超时），
   当初选源时因此把整个 models.dev 排除掉了 —— **但它有两个可达的第三方出口**
   （opencode 自建镜像 4.0MB 裸 JSON / stencil 140KB zstd，实测逐对完全相等）。
   litellm+OpenRouter 对国内厂商系统性偏弱，glm-5.3 与整批 doubao 只有 models.dev 有。
   同批必须做的两件（不是搭便车）：响应体 32MiB 字节上限（本 PR 把最大响应从 1.7MB 抬到
   4.0MB，体积敏感度由它引入）、非对话模型按 `modalities.output` 过滤（约 140 条非对话条目
   **确实带 context 值**，混进来会污染上面那个众数投票）。

4. **日期后缀归一化**（`-YYMMDD` / `-YYYYMMDD` / `-YYYY-MM-DD`），放候选链最后一级。
   实测三源全查后剩下的 15 个缺口里，7 个只差这一条规则。

顺带把「覆盖率」从注释里的一句话变成可复算口径：`scripts/catalog-coverage.ts`
（`bun run catalog:coverage`）。原注释写「127 个中 93 个（73%）」，网关新上模型后分母失真，
而**正是那句「73%，还不错」让选源问题一直没被复查**。

## 放弃了什么（以及为什么不选）

- **不改优先级链**（`lookupRegistry` 排在 `lookupCapability` 之前这件事本身是反的：一个 90 条
  带模糊匹配的手写表压着 3000 条精确匹配的采集表）。**刻意留到下一个 PR**，因为有硬顺序：
  实测 `deepseek-chat`（cat=128K/reg=1M）、`gpt-5.2`（cat=272K/reg=1M）、`deepseek-reasoner`
  （cat=131K/reg=1M）三个模型**目前靠 registry 挡住了 catalog 的 min 错值**。先改优先级链
  就是把这些错值放出来 —— 一次线上回归。必须等本 PR 的投票修复 + 重采生效之后。
- **不用推断算法补数据源缺口**。扫了 6 个多 provider 开源项目（opencode / oh-my-pi / pi /
  kimi-code / openclaw），没有一个用「匹配算法」解决元数据缺口；`nearest version` /
  `same major` 之类的模式在这些仓库主源码里**零命中**。它们的做法一致是换数据源 + 未知就是
  null。oh-my-pi 有完整的 semver 解析能力，但**只用于布尔能力门**（这一代之后行为变了吗），
  从不用来外推 contextWindow 这类连续数值。所以本 PR 把力气全花在数据源与投票上。
- **不把 catalog 的 `cost` 字段接进定价链路**。能力是模型固有属性（跨端点复用安全），价格随
  渠道变（同名不同价）。镜像里 glm-5.3 有 4 条不同的价，而网关实采价是 1.0959 —— 网关价才是
  对的，接进来只会引入错算。
- **不剥变体后缀**（`-maxthink` / `-wot` / `-lite` / `-turbo` / `-thinking`）。剩下 8 个缺口全是
  这类，但 `-lite` / `-turbo` 的窗口通常真的更小，剥后借基础名的窗口是**高估**。交给 400 自愈。
- **日期正则不放宽长度**（只认恰好 6 位或 8 位纯数字段）。放宽会把 `minimax-m2.5` 之类的版本号
  当日期剥掉，把不同档位的模型糊成一个 —— 这是这条规则唯一的真风险。
- **不为并发写引入 flock**（opencode 走的是跨进程锁那条路）。能力缓存是纯优化项，为它加一个
  跨进程锁依赖，代价大于现有乐观合并残留的那点风险。
- **接受「宁可高估」这个不对称**（无众数取 max、平局取大）。高估 → 吃一次 400 →
  `learnFromError` 学到真值 → 自愈，**一次性代价且有信号**；低估 → 零报错零信号、过早触发
  auto-compact、每一轮都多烧 token，**永久性代价**。这是用「更安全」换「更省 + 可观测」，
  代价点破在代码注释里，防止下一个人以「保守=安全」的直觉改回 min。

## 拿什么证明它生效了

**主口径（`bun run catalog:coverage`，2026-08-20 实测本机网关缓存）**：

```
分母（gateway-pricing.json 跨桶去重）：全量 135 / 对话模型 113
  旧两源并集   对话  94/113 (83.2%)
  三源并集     对话 105/113 (92.9%)      ← 覆盖率 +9.7pp

投票准确率（真值 = 内置注册表，仅统计有 ≥2 候选值的模型，5% 容差）
  [contextWindow]
    三源  min（旧）   n=77  一致 33 (42.9%)  低估 44  高估 0
    三源  众数（现）  n=77  一致 71 (92.2%)  低估  4  高估 2   ← 42.9% → 92.2%
  [maxOutputTokens]（已含「不超过窗口」钳制）
    三源  max（旧）   n=74  一致 23 (31.1%)  低估  4  高估 47
    三源  众数（现）  n=74  一致 55 (74.3%)  低估 12  高估 7   ← 31.1% → 74.3%

真实缺口（三源 + 归一化后仍查不到的对话模型）：8 个（全是变体后缀，刻意不修）
```

⚠ **两个字段都必须复算，只看窗口会漏掉回归**：上面 output 那组数字里，
「旧两源 max = 64.3% → 三源 max = 31.1%」正是加源引入的净退步。如果只验窗口口径，
本 PR 会带着这个回归合进去，而它的症状（400）与我们修的那个 bug 一模一样。

**关键模型的窗口投票复算**（真实三源数据，非 fixture）：

```
模型                 候选数  min（旧）    众数（现）
glm-5.3              14     1000000     1000000     ← 旧源查不到，现在采到了（用户报的症状）
deepseek-v4-flash    69       32768     1000000     ← 锁住 30.5 倍低估不复现
deepseek-r1          33       32768      128000
kimi-k3              54      262144     1048576
glm-5.2              73      200000     1000000
```

**单测 44 条**（`packages/core/tests/llm/model-capabilities-vote.test.ts`），
并做了 **6 组变异自证** —— 只写测试不做变异自证等于不知道断言拦不拦得住：

| 变异 | 结果 |
| --- | --- |
| 众数 → 无脑取 max | 1 fail ✓ |
| 众数 → min（含平局取小） | 3 fail ✓ |
| 写键改回「只写全名 + 先到先得」 | 8 fail ✓ |
| 日期正则长度放宽 `{2,8}` | 1 fail ✓ |
| 去掉 maxOutput 钳制 + 去掉非对话过滤 | 2 fail ✓ |
| maxOutputTokens 改回 max | 1 fail ✓ |

⚠ 前两组变异**第一次都是全绿的**，暴露了两个断言缺口，因此补了两条用例：
「众数小于 max 时也必须选众数」（此前所有断言里众数恰好都是最大值，无脑取 max 同样能过）、
「纯数字尾段长度窗口只有 6 和 8」（此前的真实反例尾段都只有 1 位数字，放宽到 `{2,8}` 看不见）。
这两条是本次测试里唯一能区分正确规则与错误规则的判据。

**门禁**：`bun test` 全量 0 fail / `make build` 成功且无 undefined 警告 /
`bun run lint` / `bun run format:check` / `bun run lint:boundary` /
`bun run docs:gen-reference-check`（参考页无漂移，本 PR 未新增 `SID_*` 变量）。

**镜像可达性与结构一致性实测**（2026-08-20，国内直连）：

```
https://models.opencode.ai/api.json         http=200 size=4006144 t=0.69s
https://catalog.stencil.so/models.json.zstd http=200 size=143651  t=5.14s
两源逐对相等：192 providers / 6834 models，(provider,model) 对集合完全相同
三源并集缓存键 6212 条（MAX_CACHE_ENTRIES=20000，未触上限）
```

**已知未验证的部分（不夸大）**：镜像的**长期**可用性没有证据，我只验证了「今天从这台机器
可达」—— 所以 litellm/OpenRouter 一个都没删，两个镜像互为备份。32MiB 的体积上限是**按余量
推的，不是压测出来的**（注释里已如实标注）。zstd 解压后的体积没有第二道上限，
`Bun.zstdDecompressSync` 做不到流式限额，该残余风险按可接受处理并写进注释。
