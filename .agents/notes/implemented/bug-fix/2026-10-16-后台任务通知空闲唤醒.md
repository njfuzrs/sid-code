# 主循环空闲后到达的后台任务通知，由空闲唤醒消费而不是无限期躺在队列里

## 决定了什么

事故 `20261016-124505-786b1586`：主代理派出两个 `run_in_background` 子代理后以 `end_turn` 收尾
（"等它们返回后汇总"），30s 后子代理完成、`<task-notification>` 入队，但**没有任何东西消费它**，
会话停在那里，无报错。根因是队列只有两个消费点，主循环结束后两个都不工作：
`queryLoop` 每轮开头的出队（`loop.ts`），和 TUI `useMessageQueue` 的空闲 drain（只认 `user-input`）。
`hasPendingNotifications()` 在全仓零生产调用方——本来就是为这个唤醒判断准备的。

对标 claude-code（已读源码：`hooks/useQueueProcessor.ts` / `utils/queueProcessor.ts` / `cli/print.ts`）：
交互端在「无查询进行中」时消费队列里**所有 mode**；headless 在 drain 完后若仍有运行中的后台任务就继续等。
四种运行形态各接一处，共用同一套原语：

- **core 原语** `task/background-wake.ts`：`subscribeBackgroundActivity`（队列变化 + 任务状态变化，**推迟到微任务**触发）、
  `waitForBackgroundNotification`（返回 `notification | idle | aborted`）。
- **引擎入口** `QueryEngine.resumeWithNotifications()`：注入通知并续跑一轮。**不触发 UserPromptSubmit、不记用户提示、不解析 thinking hint**
  （CC 同样只对 `mode==='prompt'` 做这些；通知正文是子代理产出的不可信数据，`ultrathink` 之类字样不该改变思考档位）。
  `submitMessage` 与它共用抽出的 `runLoop`。
- **注入收口** `injectPendingNotifications`：queryLoop 轮中注入与空闲续跑共用，**补上了落盘**——此前通知只进内存不进
  `sessionStore`，`-c` 恢复后主代理"看过"的子代理结论凭空消失。
- **TUI**：`useMessageQueue` 依赖由 `queueLength` 改为 `snapshot`，队首是通知且空闲时调 `onNotifications`；
  对话框/命令面板打开时不抢占（对标 CC `hasActiveLocalJsxUI`）；续跑占住 `isSubmittingRef`，防用户回车并发开第二轮。
- **`-p` 文本模式**：首轮 `done` 后若仍有后台任务，等通知并续跑（对标 `print.ts` 的 `do…while(hasRunningBg)`）；
  仅在"正常说完"时续等，致命错误 / 预算硬停 / `incompleteReason` 不在故障之上再开新轮。续跑无输出时退回首轮答案。
- **SDK stream-json / Bridge**：stdin 关闭或空闲时同样等待并续跑；Bridge 有 8 轮上限防通知链自我无限续跑。

## 放弃了什么（以及为什么不选）

- **轮询（`sleep(100)` 循环，CC `print.ts` 的做法）**：否决。本仓已有 `subscribeQueue` 与 `onTaskChanged` 两个事件源，
  订阅比轮询省一个定时器、也没有 100ms 的延迟下限。
- **只修 TUI**：否决。同一条断链在 `-p` / stream-json / Bridge 三处原样存在；只修一处会让"后台任务能用"依赖运行形态，
  且 `-p` 那处更糟——进程退出会把还在跑的子代理一起带走。
- **让主模型在 end_turn 前自己等（`task_output` 阻塞）**：否决。这是把 harness 的责任推给模型的措辞，
  模型已经明确说了"等它们返回"，缺的是 harness 兑现这句话。
- **订阅回调同步触发**：否决，且有变异自证。`completeAgentTask` 先 `updateTask`（同步通知监听器）再 `enqueueTaskNotification`，
  同步回调会读到「无运行任务 + 无通知」而误判后台已结束，恰好错过紧随其后入队的那条通知。
- **把通知并入 `user-input` 队列、统一当用户输入处理**：否决。会触发 UserPromptSubmit hook、记成用户提示，
  还会让通知文本里的 `ultrathink` 改变思考档位（见上）。
- **`useMessageQueue` 里"user-input 永远优先于通知"的二次排序**：否决。用户持续输入时通知会饿死；
  取舍交给队列内核的 `(priority, 入队序)`，通知默认 `later`，天然排在 `next` 的用户输入之后。

## 拿什么证明它生效了

四个形态各一组测试，**每组都做了变异自证**（改回旧行为 → 对应用例变红 → 还原 → 变绿）：

| 被测点 | 变异 | 结果 |
| --- | --- | --- |
| `background-wake` 微任务推迟 | 改回同步触发 | 4 个用例变红（含「回调里能看到通知」与「同步栈上不触发」两个方向） |
| TUI hook 空闲消费 | 改回只认 `queueLength`/`user-input` | 核心用例「空闲 + 只有通知 → 调 onNotifications」变红 |
| `injectPendingNotifications` 落盘 | 去掉 `sessionStore.appendMessage` | 「注入的内容落盘」变红 |
| headless-runner 退出判据 | 改回 `inputDone && queue.isEmpty()` 即退出 | 「stdin 已关 + 后台任务在跑 → 续跑」变红 |
| Bridge 续跑 | 去掉 `drainBackgroundNotifications()` 调用 | 3 个用例变红 |
