# Bridge 六项缺陷：关停挂起被强杀兜底掩盖，白名单说着一套不存在的方言

## 决定了什么

修掉缺陷清单的 **D9-D14（Bridge 层全部六条）**。

| # | 改动 | 文件 |
| --- | --- | --- |
| D9 | `flush(timeoutMs)` 带时限并返回 bool；`BridgeCore.stop()` 据此记日志 | `serial-batch-uploader.ts`、`bridge-core.ts`、`types.ts` |
| D10 | 连续失败超限（默认 8 次）丢弃该批 + **丢弃计数** | `serial-batch-uploader.ts` |
| D11 | 永久失败关闭码（1002/1003/1008/4001/4003）不重试，立即回调上报 | `ws-transport.ts` |
| D12 | 心跳加探活：入向静默超 2 个周期判半开，用自定义码 4900 断开重连 | `ws-transport.ts` |
| D13 | 白名单按**真实事件联合体**重写，并成为 `forwardEvent()` 唯一入口过滤 | `bridge-messaging.ts`、`bridge-runner.ts` |
| D14 | 新建 `bridge/admission.ts`：首次确认 + 明文 opt-in + policy 关闭 | `admission.ts`、`cli.ts`、`config.ts`、`paths.ts` |

**最重要的一条发现不在清单里：D13 比清单描述的严重得多。**
原白名单是 `text` / `text_delta` / `tool_use` / `tool_result` / `turn_complete` / `error`
—— **六个里没有一个是真实的 `QueryEngineEvent.kind`**（真实的是 `stream_text` /
`tool_start` / `tool_end` / `done` / `system` / `fatal_error`）。它把三套词汇混成一套：
前四个是 `BridgeOutMessage.type`，后两个是状态字符串。

**所以清单建议的那个"一行修复"（switch 前加 `if (!isEligibleForBridge(kind)) return`）
若照抄，会把 100% 的事件全部过滤掉，Bridge 直接哑掉。** 必须先把词汇重写，
再接线。这是"零生产调用的死代码可以漂到完全脱离现实"的极端案例。

## 放弃了什么（以及为什么不选）

**① D9 没有让 `flush()` 无限等下去"以求可靠"。** 关停时"尽力发完"必须有上限 ——
无限等待不是更可靠，是挂死。默认 2000ms，刻意**小于** `app.ts` 那个 1.5s 强杀兜底
的收尾预算，否则修了这里还是会被截断。

**② D10 的丢弃没有做成静默。** 丢弃必须留计数（本仓判据：降级动作必须留下计数）。
只加上限不加计数，等于把"卡住"换成"静默丢消息"—— 后者更难排查。
计数同时给批次数与条目数：批次数不够用，一批可能 1 条也可能 500 条。

**③ D11 的永久失败集合刻意不含 1006。** 1006（异常关闭、无 close frame）恰恰是
网络抖动、代理超时、进程重启的典型码，是**最该重试**的一类。把它算进永久失败
会把可恢复断线做成永久断线。判据用**状态码**而不是错误消息子串。

**④ D12 的探活判据是"对端还在说话"，不是"我的 ping 收到了配对 pong"。**
后者要求对端实现配对回应，而我们的对端是自托管中继，不能假定它会。
半开时用自定义码 4900 而非 1000 关闭 —— 1000 会被 `onclose` 当成正常关闭从而
**不重连**，那就把一次可恢复的半开变成永久断线。

**⑤ D13 没有删掉白名单函数（清单给的另一个选项）。** 删掉等于把过滤规则永久
固化在一个手写 switch 里，下次要加事件类型还得改两处。保留单一入口更便宜。

**⑥ D14 刻意不照搬 CC 的九道准入检查。** 其中至少五道（服务端灰度、组织策略
下发、强制版本下限、编译期 flag、组织 UUID 归档）是**它的运营需要** ——
sid-code 自托管、URL 由用户自己给，这些门本来就不适用。只做三件事：
首次确认并记住 URL、明文连接要 `--bridge-insecure`、policy 可关。

**⑦ D14 的信任键剥掉了 query。** 认证 token 常挂在 query 上，把它写进磁盘上的
信任文件等于**把凭据落盘**。信任的对象是"这个端点"，不是"这次带的 token"。

**⑧ D14 无 TTY 时 fail-closed 而非默认放行。** 默认放行等于没有这道门。
`config.bridge.enabled` 用 `enabled?: boolean` 而非 `disabled?`：`undefined`
必须表示"未配置 = 不拦"，否则现存用户升级即被拦。

## 拿什么证明它生效了

**① D9 先用清单里那支探针独立复现，再证明修好了**（不是"机理上讲得通"）：

```
修复前：bun test zz-hang-probe.test.ts → "超时：flush 挂住了"，1 pass（断言的是 bug 行为）
修复后：同一支探针            → "flush 返回了"，1 fail  ← 它的失败就是修复的证明
```

**② D13 的门禁做了三次变异自证**（本仓铁律：每条规则须变异自证）：

```
变异1：白名单放回不存在的方言词 text_delta        → 报 bogus: ["text_delta"]  ✅ 红
变异2：删掉 forwardEvent 的入口过滤（回到两套判断）→ 1 fail                   ✅ 红
变异3：给 switch 加一个不在白名单的 case（死代码）  → 报 unreachable: ["compact"] ✅ 红
复原 → 7 pass / 0 fail  ✅
```

门禁的判据刻意选**"词汇是否真实存在"**（从 `query/types.ts` 抽 `kind:` 比对）
而不是**"集合内容等于某清单"**：后者会随产品判断变（哪些事件该给远端看可以讨论），
前者不该变 —— 一个不存在的 kind 永远是 bug，不是选择。门禁还先断言"能抽到 >8 个
真实 kind"，否则正则失效时它会**全绿**，那是最坏的情形。

**③ D11/D12 跑真实本地 WebSocket 服务器，不用 mock。** 要验的恰恰是
"关闭码怎么分流""半开时 isConnected 说不说谎"—— mock 掉就等于把被测对象换成
自己的假设（这正是 D13 的成因）。用 `Bun.serve` 起服务器，连上即用 4001/1008/1011
关闭，断言 `isPermanentlyFailed()` 与 `permanentFailureCount`。

**④ D14 三条拒绝路径端到端跑了真实二进制，看的是真实退出码**（不是 tail 的）：

```
./sid-code --bridge https://evil.example.com  → 「不是合法的 Bridge URL」        exit=1 ✅
./sid-code --bridge ws://127.0.0.1:9/relay    → 「拒绝明文 Bridge 连接」        exit=1 ✅
./sid-code --bridge wss://relay.example.com/ws < /dev/null
                                              → 「无法交互确认」fail-closed      exit=1 ✅
```

⚠️ 这四条端到端验证同时也是**「防线被触发过」这个事实的证据**。安全是"坏事没发生"，
负面事件天然稀疏、分母恒 0、曲线恒平，**分不清"防线起作用"和"运气好"**。
本仓 `scripts/defense-trigger-rate.ts` 实测出过 **0% 触发**（防线全在、调用全 0，
防线自己成了死功能）。所以「加了防线」和「防线被触发过」是两个事实，这里分别验了。
另外 `admission.test.ts` 里每条拒绝分支都被显式触发一次，`policy-disabled` 那条
还断言了**不问人**（顺序判据：policy 拒掉的 URL 不该让用户白确认一次）。

**⑤ 命令与输出**：

```
bun test ./packages/core/tests/bridge/  → 81 pass / 0 fail（修复前 40）
make build                              → 自检通过；grep "will always be undefined" 无命中
bun run lint / format / lint:boundary   → 全绿（越界依赖 0 处）
```

**⑥ 尚未验证的部分**：
- **D12 的 30 秒半开判定没有在真实时间尺度上跑过**：单测断言的是探活基线
  （`lastInboundAt` 在 onopen 被置位）与计数出口，而"静默 60s 后真的断开重连"
  需要等一分钟，未做。这条的诚实说法是「探活机制已接线、基线与计数有断言」，
  不是「半开连接已验证能被检出」。
- **D11 的 10 分钟重连放弃路径未跑满**（同理，不值得等）。
- **真实远端中继的联调未做**：全部用本地 `Bun.serve` 替身。
