# JIT 新鲜度在 mtime/size 变化后再比内容 sha256，只改 mtime 不再重新注入

## 决定了什么

`packages/core/src/config/jit-context.ts`：`LoadedEntry` 增加 `contentHash`（原始内容 sha256），
`markLoaded` 与 `loadOne` 登记时一并记录。新增 `checkFresh()` 作为唯一新鲜度判据，
`loadOne` / `hasStaleOnChain` / `pruneStale` 三处都改为调用它：

1. stamp 取不到 → `missing`（三处沿用原有的各自退化策略）
2. mtime 与 size 都没变 → `fresh`（快速路径，不读盘）
3. 任一变化 → size 也变了直接判 `stale`；size 没变就读盘比 hash，相同则刷新 mtime 并判 `fresh`

触发场景：git checkout/switch/merge/pull/worktree 改写了根 `CLAUDE.md` 的 mtime，内容没变，
JIT 却以 `nested_traversal` 把它再追加到 system 尾部（前缀断一次，同一份规则出现两遍）。
`loadOne` 的 stamp 改为在读盘**之前**取：两步之间若有写入，会记成「旧 stamp + 新 hash」，
下次比对仍能得出正确结论；反过来的顺序会永久漏掉这次写入。

## 放弃了什么（以及为什么不选）

- **方案 4.2「JIT 落点从 system 挪到 user 消息」本 PR 不做**。它改变规则的权威位置，
  修复文档第六节要求先跑一次评测确认遵守率；而且要同时改主循环、子代理、压缩回灌三条路径，
  回滚单元和本修复不同。4.1 单独就能消掉主循环 113 次命中里的「内容未变」那部分
  （其中 57 次已逐字确认），所以先单独上线。
- **方案 4.3「去重键统一为 realpath+hash」本 PR 不做**。它和 4.2 绑定（`prompt.includes` 的去重只在
  system 落点存在），单做没有意义。
- **只比 hash、不保留 stamp 快速路径**：不选。`hasStaleOnChain` 在每次命中目录短路时都会跑，
  每次都读盘算 hash 会把 JIT 的开销放大 N 倍（N=链上规则数），而 stamp 不变的情况才是常态。
- **用 git 的 index/blob oid 当判据**：不选。非 git 项目、未跟踪的 `CLAUDE.local.md` 都覆盖不到。

已知残余：`markLoaded` 记的 hash 是调用那一刻的磁盘内容，和 `loadAllCLAUDEmd` 注入时读到的版本
之间有启动期毫秒级的窗口。

## 拿什么证明它生效了

- 新增 `packages/core/tests/config/jit-content-hash-freshness.test.ts`，5 个用例：预标记后只改 mtime
  不返回块；内容同长度改动仍注入新版；**在真实 git 仓库里 rm + `git checkout --` 后不重新注入**
  （复现文档第三节）；JIT 自加载条目只改 mtime 不注入，之后真改仍注入；`pruneStale` 不剔除只改 mtime 的条目。
- 变异自证：把 `checkFresh` 的 hash 分支改成 `if (false)`，上述 5 个用例里 4 个变红（同长度内容改动那一条
  靠 hash 不同本来就判 stale，预期仍为绿），恢复后全绿。
- 既有 JIT 测试 4 个文件、73 个用例全绿（含 P1-2「内容真改后重新加载」系列）。
- 轨迹侧验收（待数据，至少 50 个会话）：主循环 JIT 加载根 `CLAUDE.md`（`reason=nested_traversal`）的次数接近 0；
  `system_dynamic` 前缀断裂降到原来的一成以下。
