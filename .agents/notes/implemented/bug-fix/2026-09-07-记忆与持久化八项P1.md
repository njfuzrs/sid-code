# 记忆与持久化的八项 P1：三处半接线、两套口径分裂、两个安全缺口、零埋点

来源：`docs-research/sid-code/bugfixes/todo/20260906-记忆与持久化-十五项缺陷.md`
（十五项中的 D5–D12，即全部 P1；四项 P0 已由 #27 修完，三项 P2 不在本次范围）。

## 决定了什么

**八项 P1 合并一个 PR。** 判据是 CONTRIBUTING.md 的三条测试（可独立上线 / 可独立回滚 /
可一次 review 完），三条都过；而它们同属"记忆子系统"这一个关注点、同为 P1（无优先级
错配），所以按「三条全过时按关注点合到最大」合并。更实质的理由是**三对互为因果**：
D7 的孤儿症状与 P0-1 的重名遮蔽**同形不同因**，分开修会让排查时两者继续互相冒充；
D6 换成递归之后 `archive/` skip 名单**从无害变成正确性的一部分**（否则与 P0-2 的归档
淘汰来回震荡）；D12 的埋点是 D5②/D10/D11 的**唯一验收手段**，先修后者再补前者等于
让三条修复在合并时都没有判据。

**D5 —— Session Memory 三处「有消费者、无生产者」补上生产方。**
① `sessionMemoryContent` 全生产零赋值 ⇒ `<session-memory>` 附件从不出现。
新增 `App.pendingSessionMemoryContent` 字段 + `injectSessionMemoryAfterCompact()`，
挂在压缩观察者上。**存成字段而不是临时变量**是关键：`rebuildSystemPrompt` 是覆盖式
重建（`/language`、`/model`、CLAUDE.md 热重载都会触发），漏带一次就把压缩后唯一的
历史补偿静默丢掉。**只在压缩后注入**而不是每轮注入：笔记是被丢弃历史的替代品，
历史还在时注入它是同一份信息付两遍 token。
② `compact_source: "session_memory"` 无写入方 ⇒ 两种压缩产物事后不可区分。
新增 `CompactSource` 联合类型，`addCompactBoundary`/`compactWithSummary` 接受
`source` 参数，`query/auto-compact.ts` 走 Session Memory 那条路时显式传
`"session_memory"`。**收成联合类型而非裸 string**，让写入侧漏传时编译期就红。
③ `SESSION_MEMORY_SECTIONS` 零使用（全仓唯一命中是它自己的定义行）⇒ 模板与常量表
可任意漂移（那句"11 个 section"的错注释就是这么活下来的）。给它两个真消费者：
`isKnownSessionMemorySection()` 让截断**优先牺牲模型自加的 section、保住模板 section**，
`assertTemplateSectionsMatch()` 把模板与表钉在一起（不一致抛错，不 warn）。

**D6 —— `MemoryStore.loadDir` 从平铺 `readdir` 改为走 `scan.ts` 的递归枚举。**
旧实现下子目录记忆「manifest 里有、索引里没有」：提取代理据此判定"已存在，不重复
保存"，而注入侧永远看不见它 —— 那条记忆既不会被重写，也不会被读到。两条线现在共用
同一个枚举实现（同口径），`archive/` skip 名单也随之共用。

**D7 —— 索引截断的三个口径错，收成 `index-budget.ts` 一处实现。**
① 数指针条数而非总行数（表头两行此前挤占配额 ⇒ 200 只放得下 198 条，稳态下**恒有
2 条**在磁盘不在索引）；② 量真 UTF-8 字节而非 `.length`（中文 1 字符 3 字节，实测
190 条中文摘要 `char 25041 / utf8 67725`，**超标 2.7 倍**，而索引每会话全量常驻
system prompt）；③ 只在行边界停、且**预算里先扣掉警告文案的字节**（旧代码先切到上限
再追加警告 ⇒ 最终长度必然超上限，上限自己失守；硬切还会留下 `- [某键](某文件.m`
这种**看起来完整可用**的半行，模型据此 Read 必然失败，比缺一行更糟）。
**为什么必须抽成模块**：同样三个 bug 在 `store.ts:writeIndex` 与
`agent-store.ts:rebuildAgentIndex` 有两份逐字符雷同的实现，只修前者会留一份已知坏的
副本，而它服务子代理跨会话记忆、更少人看、坏得更久。

**D8 —— write/edit 写私有记忆目录与 agent 记忆目录时补 secret 守卫。**
此前只有 team 目录有守卫。新增 `memory/write-guard.ts`，`write.ts`/`edit.ts` 落盘前
调 `checkPrivateMemSecrets()`。

**D9 —— 后台 extract/dream 代理的 `save_memory` 按 scope 收窄。**
旧注释的前提是"落点都在 memoryDir 内、直接放行"，**这个前提不成立**：scope 枚举四个
值里只有 `project` 落在 memoryDir 内，`global` 污染所有项目、`team` 会同步给全体
协作者、`agent` 落在 agents/ 下。更糟的是提取 prompt 里**完全没有 global 的判定标准**
—— 模型对它的使用是无指引的自由裁量。现在只放行 `project`。**write/edit 受路径约束、
save_memory 受 scope 约束**，两个维度各管一半，旧实现只做了前者。

**D10 —— 「写空 = 删除」这个手势收成确定状态。**
dream 的 prune 指令教模型"用 write 写空或 edit 移除对应条目"，但写空在实现里是个
半死状态：不进内存、索引里没有，**但文件还在、`scanMemoryFiles` 仍列出、manifest 仍
列出**。两个真实后果：下一次 dream **反复"删"同一批记忆**（白烧一整轮配额）；提取代理
把它当"已存在"⇒ 一条**已被判定为过时应删**的记忆，反而**阻止了正确内容的重新写入**。
现在写空即归档到 `archive/`（字节保留可人工恢复），prompt 同步收窄为只认写空、
明确禁止用 edit 删部分行来表达"删整条"。

**D11 —— 模块级写入代数 `memoryWriteGeneration` + `invalidateMemoryCaches()`。**
生产有 9 处 `new MemoryStore()`，各持一份内存缓存，而 `loaded` 旧实现**单向锁死**
（唯一写点是 `load()` 末尾的 `= true`，全文件无处置回 false、无 mtime 重读）。
用户可感知的两个后果：长会话中 `save_memory` 之后注入侧索引不更新；后台提取代理写入
的记忆**本会话内注入侧完全不可见**（模型被告知"已保存 3 条"却在索引里找不到）。
设计者其实已意识到跨实例失效 —— `summaryCacheEntry` 就是模块级且写后清的 —— 但它
**只清摘要不清条目缓存**，同一个问题解决了一半，这次把另一半补上。

**D12 —— 记忆子系统三个埋点（此前零埋点）。**
`memory_index_health`（目录 .md 数 vs 索引指针数，差值非 0 即异常 —— 直接对应
记忆库自检的那个口径）、`memory_inject`（注入条目数=分母 / 真被 Read 条数=分子）、
`memory_guard`（各道防线触发次数，**恒 0 的曲线本身就是信号**）。

## 放弃了什么（以及为什么不选）

**拆成 8 个 PR（旧判据）—— 否决。** 2026-08-19 判据已改，且三对互为因果（见上）：
分开修会让每个 PR 都留着另一半的因，说不清是否真的修好。八项同为 P1、同一关注点，
没有「P0 的修复速度被 P2 拖累」那种优先级错配。

**D5① 改成每轮都注入笔记 —— 否决。** 笔记是被丢弃历史的替代品。历史还在的时候注入
它是同一份信息付两遍 token（直接伤"更省"），而收益为零。

**D5③ 只加 `assertTemplateSectionsMatch` 不加 `isKnownSessionMemorySection` —— 否决。**
那样常量表的唯一消费者是一个测试，仍然没有**运行时**消费者 —— 换个形态的挂件而已，
而这条缺陷的实质就是"表可以任意漂移而无人知情"。

**D7 只修 `store.ts` —— 否决。** 见上：会留一份已知坏的副本在更少人看的那条线上。

**D11 改成遍历所有实例清缓存 —— 否决。** 要维护实例注册表（弱引用 / 手动注销），
而语义诉求很简单："加载之后如果有人写过盘就重读一次"。代数比较 O(1)、不持实例引用。
**刻意不覆盖跨进程写入**：那需要 mtime 轮询或文件锁，成本远高于它治的问题
（并发会话各有各的项目目录时根本不冲突）。这条边界写在注释里，不是漏掉的。

**D10 改成直接 `unlink` —— 否决。** 与 P0-2 同一个教训：无备份删除用户记忆不可接受。
归档保留字节、可人工恢复。

## 拿什么证明它生效了

**每个新增测试都做过变异自证**（把修复改回旧行为，确认测试变红），过程中抓到两个
**测不到东西的空门禁**并改掉，这两个是本次最有价值的产出：

1. D5③ 初版断言的是「预算紧张时模板 section 还在不在」。逐 section 截断会把超长
   section 压到 `perSectionTokens` 以内，于是**两种实现下模板 section 往往都还在**
   —— 断言在修复前后同时为真。改成断言**顺序**（`iCurrent < iInvented`）后才
   discriminate：旧实现 `invented@0 / current@2201`。
2. D7 的字节断言必须用**含中文**样本 —— `.length` 与 `utf8Bytes()` 在纯 ASCII 上恰好
   相等，ASCII 样本会让测试在两种实现下同时变绿。这条写进了 `utf8Bytes` 的文档注释。

跑过的门禁与输出：

- `bun run affected-tests:run`（判定 selective / 7 个目标）：**3740 pass, 0 fail**，
  58238 expect() calls，303 文件，45.73s。
- `make build`：编译 + 产物自检 5 项全过。并**显式 grep 了
  `will always be undefined`：0 命中** —— worktree 里 `@sid-code/core` 会向上解析到
  主仓 checkout，新增导出会变 `undefined` 而**构建仍 exit 0**，只看退出码就交付等于
  交一个新函数是 undefined 的版本（进 worktree 后已先跑 `bun install`）。
- `bun run lint` / `format:check`（1916 文件全绿）/ `lint:boundary`（越界 0 处、
  测试跨包相对路径 0 处）。
- `bun run docs:gen-reference --check`：参考页与源码一致（本次动过 `tool/`）。
- 全量 `bun test`：8673 中 1 fail，是 `permission/plan-mode`，**已在干净 origin/main
  的独立 worktree 上复现**（与本次改动无关，符合"宣称无关需三条证据"的要求）。
- typecheck 基线：维持在既存 10 个错误，**无一在本次触碰的文件**里。

**接线不是靠"机理上讲得通"判定的** —— 三个新埋点函数逐个 grep 过生产调用者：
`logMemoryIndexHealth` → `store.ts:1210`；`logMemoryInject` → `store.ts:1139`；
`logMemoryGuard` → 7 处（write-guard / agent-store / store ×3 / extract-permissions /
tool-memory）。这正是本条缺陷（零埋点）与四环防线那次"防线全在、调用全 0"要防的形态。

⚠️ **一个诚实的边界**：D12 的三条曲线目前只证明了"埋点被调用"，尚未有跨版本的真实
趋势数据。「写进去的记忆有没有被召回过」这个问题现在**有了取数源**，但要回答它还需
攒够真实会话 —— 别把"埋点接通"写成"已经在度量"。
