# 上下文占用估算的三处口径错配：常驻 schema 算全量、展示不扣本地释放量、激活后不刷新

## 决定了什么

修掉「状态栏/`/context` 的上下文占用比真实 usage 高 1.4–2 倍」的三条独立成因，全部落在
**口径对齐**上，不动估算算法本身：

1. **常驻工具 schema 只算「实际会发出去的那一份」**（`packages/cli/src/app.ts`）。
   新增 `selectResidentToolDefinitions(registry, toolSearch)`：`toolSearch === false` 时用
   `definitions()`（该档首轮真发全量），其余档一律 `activeDefinitions()`。
   `refreshToolSchemaTokens()` 改调它。此前用 `definitions()`（全量工具池）。

2. **`activateTool()` 补一次变更广播**（`packages/core/src/tool/registry.ts`）。
   `tool_search` 激活延迟工具后，该工具从此刻起进 `activeDefinitions()`、schema 开始真实
   占用上下文；不广播的话订阅方（`refreshToolSchemaTokens`）停在旧快照上，估算反过来偏低。

3. **展示层与压缩决策同源扣掉本地已释放量**（`packages/core/src/context/manager.ts`）。
   `getContextUsageForDisplay()` 与 `getTokenBreakdown()` 都减去
   `tokenFreedTracker.getTotalFreed()`——与 `getCompactionLevel()` 用同一个表达式。
   该 tracker 记的是「发送副本已经瘦掉、全量历史里还在」的三类量：大输出清理
   （`cleanedMessages`）、冷缓存清理（`coldCacheClear`）、遮罩（`masking`）。
   breakdown 的扣减从 `toolResult` 分类里出（三类来源释放的都是 tool_result），
   扣不下就不扣，保证「分类非负」与「total = 各分类之和」两个不变量。

## 放弃了什么（以及为什么不选）

- **不用 `registry.isToolSearchEnabled()`（运行时定档结果）作判据**：它在 `queryLoop` 首轮
  才算出来，而 `refreshToolSchemaTokens` 在 App 初始化 / MCP 连上时就跑。用运行时时序去判
  静态口径必然漂移——这正是 `config/deferred-tool-view.ts` 文件头两条硬约束踩过的坑。
  只认**配置层的 `toolSearch === false`**。
- **不把 `estimateTokens()` 本身改成「发送副本」口径**：全量历史对压缩决策是**有意保守**的
  （遮罩/清理随时可能被回退，且真实 prompt 只会增不会减）。改它会推迟 compact 触发，
  属于用「更准」换「更容易溢出」，方向错。正确做法是展示层单独扣账，决策层保持原样。
- **不在 `getTokenBreakdown` 里做按比例分摊**：三类释放量都源自 tool_result，直接扣该分类
  语义清楚；按比例分摊会造出「每类都少一点」的假精确，且扣减后仍要满足 sum 不变量，
  复杂度换不来正确性。
- **不给 `tokenFreedTracker` 加按 factor 缩放的读取口**：它是未校准口径的粗估
  （字符/4），而 `getCompactionLevel` 已经直接用未缩放的 freed 去减校准后的估算。
  展示层要的是「与决策同源」，不是「比决策更精确」——两边用同一表达式才是这次修复的目标。
- **不在 `refreshToolSchemaTokens` 里保留 `definitions()` 作为 MCP 分类的母项**：
  `/context` 的「MCP 工具」分类应当只反映真实占用的 MCP schema；把它按全量统计会让
  「MCP 是膨胀主因」的展示与压缩决策对不上。

## 拿什么证明它生效了

**1. 先量出问题（本机轨迹 + MCP server 探针，均为同一套 `estimateTokens` 口径）**

- 内置工具全量 41 个 = **14,616 tokens**（`SID_CODE_TOOL_SEARCH=false` 跑一次 headless，
  从 `raw.jsonl` 的 `request.tools` 复算）；实际首轮发送 24 个 = **10,773**。
- 延迟的 MCP 工具（全部 deferred、一个都不发），逐个用最小 MCP stdio 探针拉 `tools/list` 实测：
  context7 2 个/967、playwright 25 个/3,493、chrome-devtools 32 个/5,315、
  lark-mcp 19 个/9,852、master-mcp 12 个/5,314 —— **已测 5 个 repo 合计 24,941 tokens**。
- 于是「刚打开 TUI 的初始占用」= system 23,260 + 全量 schema ≈ 63,000+，
  而首轮真实 usage 45,719 → **约 1.4 倍**；vibe-coding（http transport，探针测不了）再多一点
  就能到用户报的 1.5–2 倍。
- 展示口径的另一半：3 个长会话的全量估算 vs 最后一轮真实 usage =
  **2.66× / 3.2× / 1.93×**（1,162,927→438,012 等）。

**2. 改完之后**

- `bun test ./packages/core/tests/context/display-freed-tokens-same-source.test.ts` → 6 pass
- `bun test ./packages/core/tests/tool/registry.test.ts` → 22 pass（新增 2 例）
- `bun test ./packages/cli/tests/app/tool-schema-scope.test.ts` → 5 pass

**3. 变异自证（每组都先改坏、看到红、再恢复）**

- 去掉 `getContextUsageForDisplay` / `getTokenBreakdown` 的扣减 → **3 条断言红**
  （`清理后展示占用必须下降`、`used 精确等于 max(0, estimateTokens − freed)`、
  `清理后 total 下降且下降量一致`），恢复后全绿。
- 去掉 `activateTool` 的 `scheduleChangeNotify()` → **1 条断言红**
  （`activateTool 激活延迟工具后广播`），恢复后 22 pass。
- `selectResidentToolDefinitions` 换回 `definitions()` → `tool-search 开启时延迟工具不计入`
  一组红（见测试文件 5 个用例）。
