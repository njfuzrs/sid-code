# 会话持久化与检查点：修掉七项 P0（崩溃丢历史 / 会话被误删 / undo 与 rewind 退错格）

## 决定了什么

修掉 `20260927-会话持久化与检查点-顺着sc-08核出的缺陷.md` 里全部 7 条 P0。
它们分属三簇，每簇一个共同根因，所以按簇改而不是按条改。

**A 簇「一个 jsonl = 一条 uuid 链」这个契约在异常路径上被破坏**（N1 / N9 / N15）

- `store.ts` `rebuildRecordOrder`：链回溯没走到链头就扫完全部行 ⇒ 说明中途有坏行吃掉了
  它要找的 uuid，此时**回退线性解析**而不是返回半截链。修前后果不是降级而是全损：
  拿不到 `session_start` ⇒ 整份返回 null ⇒ 判 `parse-error` ⇒ 进自动清理可删白名单 ⇒
  **文件被永久删除**。环检测触发时刻意不走这条回退（uuid 重复会产出重复消息）。
- `utils.ts` 新增 `chain-broken` 排除成因，**不进** `DELETABLE_EXCLUDE_REASONS`。
  判据是新导出的 `hasParsableMessageRecords()`（与解析器同源，不复刻第二套）：
  解析返回 null 但文件里还有可解析的 user/assistant/tool_result ⇒ 内容还在 ⇒ 绝不能删。
- `store.ts` 新增 `ensureTrailingNewline()`，`resumeSession` / `startSession` 转续写前调用。
  治的是 N9 那条**静默丢一轮**的路径：崩溃留下无换行符的半行，`appendFileSync` 裸追加
  把新记录与半行粘成一行 ⇒ 两个 JSON 挤一行双双解析失败 ⇒ 新记录随半行消失，
  而 `appendMessage` 正常返回、界面毫无异常。
- `store.ts` `startSession`：目标 jsonl 已存在且非空 ⇒ **转续写，不写第二条 session_start**。
  N15 是唯一一条「已经在丢数据」的：`--session-id <同一 id>` 多次单跑会把一个文件写成 N 段
  互不相连的链，恢复算法忠实走到第 N 段链头就停 ⇒ 前 N-1 段内容完好却链上不可达
  （文档实测：166 行 / 30 个 session_start / 106 条消息 → 恢复出 4 条）。

**B 簇「快照 sN 代表哪个时刻」没有单一真相源，三个入口各推一遍、两个推反了**（N5 / N6 / N4）

口径收敛到 `manager.ts` 一处：生产时序恒是 `createSnapshot` → 工具改文件，
所以 **sN 存的是「产生 sN 那次调用之前」的内容**。

- `rebuildContentBeforeSnapshot` 不再取 `targetIndex - 1`（sN 本身就是改动前，再退一格就退到
  上一次调用之前）。这一格错位同时产生三种形态：只有一个快照时空转却谎报成功、
  两次以上编辑时一次 `/undo` 退两步、`/undo <路径>` 对只改过一次的文件直接失败。
- `undo()` 在 `results` 为空时**保留快照并返回 null**。修前无条件删快照 + 返回真值，
  一次"空转的成功"永久消耗掉一个快照，连重试机会都没有。
- `rewind-manager.ts` 文件锚点从「登记时取最新快照」改为 `attachSnapshot()` **回填本轮首个快照**
  （`app.ts` 的 `onSnapshotCreated` 驱动，只认第一个、幂等）。`registerPoint` 跑在用户输入提交前、
  本轮快照尚不存在，旧写法拿到的是**上一轮**的快照 ⇒ 回退多撤一整轮；回退到第 1 轮时
  锚点恒为空串 ⇒ 文件层永不回滚，最想撤的那次恰恰撤不掉。
- `restoreToSnapshot` 补 `readFirstFullContentAfter()`：目标快照往前找不到 full 基点时，
  改为取该文件在目标快照**之后**的首个 full。漏的是「目标快照之后才第一次被改」的文件，
  它的 full 落在 targetIndex+k ⇒ 往前找必然 -1 ⇒ 旧代码 `if (content !== null)` 静默跳过。
  信息一直都在（那条 full 记的改前内容就等于目标时刻的内容），是取数方向走错了。
  同时新增 `RestoreResult.failedFiles`，让"回滚失败"不再只体现为一个看着像全成了的
  `snapshotsRolledBack`。

**C 簇 清理的保护只覆盖本进程**（N10）

- `cleanup.ts` 把活跃会话表（`listActiveSessions()`）纳入保护名单，两处判据都走新的
  `isProtectedId()` / `nameGuards`。修前 `currentSessionId` 与 `protectedSessionIds` 都由调用方
  从自己的 config 传入，而清理扫的是**全局** sessions/ 目录 ⇒ 进程 B 删掉进程 A 正在续写的
  会话，**A 侧全程无感**（写缓冲继续 append 到已删除的 inode，用户看不到任何报错）。
- `concurrent.ts` 新增 `SessionEntry.logicalSessionId` + `registerLogicalSessionId()`，
  `cli.ts` 在恢复目标确定后补登记。不加这个字段保护会落空：resume 时活跃表登记的是
  **本进程新 id**，而磁盘上真正在被写的是**旧 id 的 jsonl**，按新 id 永远查不到。

顺带删掉两处因本次改动而变成死代码的东西（否则就是新造文档 N8 批评的同一形态）：
`RewindDeps.getLatestSnapshotId` 与 `App.latestCheckpointSnapshotId` —— 它们唯一的用途
就是喂那个错误的锚点，锚点改走回填后即零调用。

## 放弃了什么（以及为什么不选）

**N15 不选「报错退出」。** `--session-id <已存在 id>` 的用户意图就是"继续这个会话"，
续写正是它的正确语义。报错会把一个可正确处理的场景变成启动失败，
更糟的是让已经变成多段的历史文件**永远打不开**。

**N1 不选「把 `parse-error` 整条从白名单移出」。** 那会让真正的垃圾文件永久堆积，
把 D4 当初"损坏文件该清理"的正确部分一起否掉。改为按「有没有可解析的真实消息」
细分成两档，只保护内容还在的那档。

**N1 不选「链断就抛错让用户手动修」。** 用户拿不到比"线性解析捞回全部消息"更好的结果，
而抛错会让 `--list-sessions` 直接崩在一个损坏文件上。

**N6 不选「保留 `getLatestSnapshotId` 注入项以免动契约」。** 一开始为了少改 app.ts 打算留着，
但它随即变成只写不读——那正是 N8 记录的缺陷形态，等于用新债换旧债。

**N4 不选「把 undo 的职责也塞进 restore」。** `restoreToSnapshot(sN)` 的语义是回滚
sN **之后**的快照，sN 已是最新时无事可做是**合法空操作**；撤销 sN 那次调用本身是 `undo()` 的活。
写测试时我一度把两者混了（断言 restore 到最新快照要改磁盘），是断言错不是实现错。

**N10 不选「新造一套文件锁」。** 活跃会话表本就为"谁还活着"存在，且自带 PID 探活 +
stale 自动清理。保护刻意只覆盖**活着的**进程：否则崩溃残留的注册文件会永久钉住一堆过期会话。

## 拿什么证明它生效了

**新增 22 条专项用例，全部先复现缺陷再验修复**（三个文件）：

```
bun test packages/core/tests/session/p0-crash-resume-integrity.test.ts      # 9 pass（N1/N9/N15）
bun test packages/core/tests/checkpoint/p0-undo-restore-semantics.test.ts   # 9 pass（N5/N4）
bun test packages/core/tests/session/p0-cross-process-cleanup-guard.test.ts # 4 pass（N10）
bun test packages/core/tests/session/rewind-manager.test.ts                 # 20 pass（含 N6 6 条）
```

关键断言都落在"能捞回多少条真实消息 / 磁盘最终是什么内容"，不是"没抛错"：
N1 中间坏一行从 0 条恢复到 9/10 条；N15 三段会话从只剩最后一段到 3 条全在、
且文件里只有 1 条 `session_start`；N9 续写那条消息不再消失（3 条全在）；
N5 形态 B 从"一次退两步回到 v0"变成"只退一步到 v1"；
N4 的 b.txt 从 `B被改坏了` 变回 `B原始` 且进 `files` 列表。

**两处测试前提被本次改动合法改正**（属契约变更，非为凑绿改断言）：

- `checkpoint/manager.test.ts` 的 undo 用例时序原本是**反的**（额外建了个 "initial" 快照，
  构造出"快照数比编辑数多一个"的世界，在那个世界里被修掉的 `targetIndex - 1` 恰好对），
  改为按生产时序「先建快照再改文件」。
- `session/cleanup.test.ts` 的 `writeCorrupt` fixture 原本写一条合法 `user_message`——
  那恰恰是 N1 要保护的形态，改为真正不可解析的内容，并补两条 `chain-broken` 用例
  （都带反向自证：真垃圾照删，防"清理什么都没干"也让保护类断言变绿）。

**五道 CI 门禁**：`bun test` 12785 pass / 4 fail、`make build` 自检通过、
`bun run lint` 0 error、`format:check` 全通过、`lint:boundary` 越界 0 处。
