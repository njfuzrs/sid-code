# 「上下文有多大」拆成 getSendTokens / getHistoryTokens，裸 estimateTokens 归零

## 决定了什么

`ContextManager.estimateTokens()` 这个名字看不出自己问的是哪一种「大小」，于是全仓
**27 处调用方一律直接用**，**全部漏扣本地释放量**（A6）。凡是问「这个会话现在多大」
的地方都有两种正确回答，这次把它们变成两个具名 API，并把裸名字标 `@deprecated`：

- `getSendTokens(toolCount)` —— 发送量（全量历史 − 本地已释放量）。展示、决策、
  预算钳制一律用它。
- `getHistoryTokens(toolCount)` —— 全量历史（含锚点，不扣释放量）。只用于压缩前后
  对比等**度量**（`compact-stats.json` / 防线指标 / adaptive 样本）。数值与改动前
  的 `estimateTokens()` 逐位相同——口径一换，历史曲线就整体平移（北极星第 3 条铁律）。

配套三件事：

1. **唯一扣减口** `localReductionTokens()`。此前 `getContextUsageForDisplay` 与
   `getCompactionLevel` 各自内联 `estimateTokens() - getTotalFreed()`，两处扣减逻辑；
   现在四处（含 `getTokenBreakdown`、`getSendTokens`）都走这一个方法。
2. **扣减乘校准系数**（A3 第二层单位错配）。freed 记账用的是未校准的启发式估算，
   却被从**已校准**的 `estimateTokens` 里减掉；而 `recordActualTokens` 换算锚点时
   是乘了 `factor` 的。同一个 `localReduction` 被按两种单位各算了一遍，中文会话上
   释放量被系统性少记。改成 `calibrated ? round(freedRaw × factor) : freedRaw`。
   `getLocalFreedTokens()` 的字段语义（「决策里实际减掉的那个量」）不变，实现跟着走。
3. **4 个记账点统一到 `estimateTextTokens` 差值**。`coldCacheClear` / `cleanedMessages` /
   `masking` 三处原本用 `Math.ceil(字符数 / 4)`，只有 `staleToolOutput` 用估算差值——
   同一个累加器里混着两种单位，中文原文只记到 38%、ASCII 又记 25%。
   `chars/4` 从这三处全部删除；`MicrocompactPlanEntry` 新增 `savedTokens`
   （在**替换之前**按原文算，与 `StaleClearEntry` 对齐）。

顺带修掉一个**文档没提到的第五个释放源**：`collapseOldPersistedReferences` 会把过量的
「持久化输出引用」折叠成短占位（约 200B → 22B），但**此前完全没有记账**。不补它，
§4.3.3 要求的「`tracker 累计 === raw(全量) − raw(发送副本)` 严格相等」在有旧引用的
长会话里恒不成立。补法是把它从模块级函数收成 private 方法，加 `collapsedRefIds`
粘滞集合按 `tool_use_id` 只在首次折叠时记一次（该函数每轮都从 `this.messages` 原文
重算、结果不写回原文，没有集合就会重复记账把减量算爆），并给 fork 前缀路径
（`getForkPrefixMessages`）传 `recordFreed=false` —— 那条路径的契约是严格只读。

`compact/index.ts` 的回调参数 `estimateTokens` 改名 `estimateMessages`：它的入参是
**任意候选消息列表**（管线每一步的中间结果），调用方传的是 `estimateTokensFor`，
与 `ContextManager.estimateTokens()` 无关。沿用同名会让人以为两者是一回事。

## 放弃了什么（以及为什么不选）

**放弃 A：先合 PR1 再做 PR2（文档 §7.1 的原始串行顺序）。**
PR1 尚未合入，而 PR2 用到的只有它那两个 private helper（`localReductionTokens` /
`sendTokensFrom`）。为此把本轮任务从「PR2」扩成「PR1+PR2」代价翻倍，而这两个 helper
是纯内联抽取、行为不变、由现有 292 个 context 测试保护。所以选择在 PR2 内先做这一步
纯重构再做实质改动——PR2 仍能独立上线 / 回滚，且**只有一处扣减逻辑**（文档明文禁止
出现两处）。代价是 PR1 后做时会在同一块代码上冲突，但那本来就是 PR1 要改的地方。

**放弃 B：只迁移调用点，不动 helper。**
那样 `getContextUsageForDisplay` 与 `getCompactionLevel` 仍各自内联扣减，
「扣减乘校准系数」要改两遍、且下次一定漏一处。文档 §4.3.1 明确要求单一扣减点。

**放弃 C：把 `getTokenBreakdown` 的扣减留在 `scale()` 之前。**
`freed` 是校准后空间的量（`localReductionTokens()` 已乘 factor），在校准前扣等于
把两种单位又混一次。改成先 `scale` 各分类再扣，并保持
`total === Σ categories` 与「分类不得为负」两条不变量。

**放弃 D：给 `collapseOldPersistedReferences` 记账但不加粘滞集合。**
它会每轮重复折叠同一批引用（原文不改），只靠 `recordCompact` 累计会让 freed 单调
膨胀，`getSendTokens()` 最终被扣成 0。粘滞集合是必须的，不是优化。

**放弃 E：把 blocking 用例写成 `getSendTokens() === 具体数字`。**
夹具一旦调整就红，且断言的不是行为。改成三条：档位 ∈ {none, soft}、
`remaining = max − getSendTokens() > blocking 阈值`，外加一条**反向自证**
（按未扣减口径算 `remaining ≤ blocking`）证明这条用例确实测到了那个误判。
