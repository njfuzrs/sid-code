# 前台 `sleep N` 阻塞等待：追加出口引导，但不拦

## 决定了什么

N6 **只做 A 档（引导）**：前台 bash 命令的第一段是 `sleep N`（N 为整数、N ≥ 2）时，
命令**照常执行**，在 tool_result 末尾追加一行出口指引。B 档（对齐 Claude Code 的
拒绝执行）不做，论证与复评条件另存
`.agents/notes/rejected/feature/2026-11-11-前台sleep改为拒绝执行.md`。

具体落地三处：

1. **形态识别**（新文件 `packages/core/src/tool/bash/foreground-sleep.ts`，纯函数）：
   - 只认第一段是 `sleep N`，N 是整数且 ≥ 2；`sleep 30 | cat`（管道流式用法）、
     `sleep 1` / `sleep 0.5`（正常节奏）、`(sleep 30; …)` / `timeout 60 sleep 30`
     （第一段不是 sleep）都不命中；
   - 先剥 `cd … &&` 与环境变量前缀（`stripLeadingCdAndEnv`）——真实会话里
     `cd <worktree> && sleep 150 && gh …` 是主要写法，不剥会漏掉最主要的一类；
   - `\n` 也算命令分隔（多行脚本里单行 `sleep 30` 同样是阻塞等待），`|` 不算。
2. **追加条件**（`bash.ts` 的 `withForegroundSleepNotice`，挂在 `execute()` 的结果链上）：
   - 已有**声明的等待**（`hasDeclaredExternalWait()`：唤醒 / monitor / `wait_until` 后台命令）
     → 任何 ≥2s 的前台 sleep 都引导，文案点破「它在推迟你自己挂的那个等待」；
   - 没有声明的等待 → 只有 N ≥ 30 才引导。30s 的取数依据见下；
   - 后台命令（`run_in_background` / `is_background`）不引导 —— 那正是引导要去的方向。
3. **埋点**（`query/guidance-events.ts` 新增 `ForegroundSleepGuided`，App 已有的
   `setGuidanceEventSink` 自动接线）：字段 `seconds` / `has_declared_wait` / `reason`
   （闭集 `declared_wait` | `long_sleep`），只在**真的追加**时发一条。
   `defense-registry.ts` 的 `EVENT_ANCHORS` 同步登记为 `notDefenseReason`：它只追加提示、
   不拦、不改退出码、不进闸门链。

为什么落在 tool_result 而不是系统提示：这是**某一次调用**的出口指引，模型不 sleep 时
完全用不上，常驻会变成噪音；tool_result 零缓存影响、只在该出现时出现一次。

为什么这个时机：`schedule_wakeup` 与后台通知只在**会话空闲**时送达。fbb02831 排了唤醒之后
又在本轮 `sleep 150/180`，第二个唤醒 lag 383 秒才注入。N2（PR #732）已经把「排完该结束本轮」
写进唤醒文案，但模型仍可能用 sleep 在本轮里「等一会儿」——那是行为面缺口，只能在调用点给出口。

## 放弃了什么（以及为什么不选）

- **B 档（命中即拒绝执行，对齐 CC）不做**：这个形态离合法用法很近，按形态硬拦会误伤
  `sleep 2 && curl localhost` 这类正常节奏；方案也把它定为「A 上线两周后看数据再决定」。
  详见 rejected Note。
- **不做全局阈值之外的「后面是不是状态查询」判断**：全量 251/260 次前台 sleep 里
  196 次后面跟着 `gh` / `curl` / `kubectl`，但 `sleep 30 && bun test` 同样阻塞本轮、
  同样推迟唤醒。按「是否跟查询」筛会漏掉真正的阻塞等待，且要多引一层命令匹配依赖
  （`matchStatusQuery` 在 `task/` 域），收益不抵复杂度。
- **不加开关（env / settings）**：引导只追加一行文本、不改行为，误伤的形态已被
  第一段判据 + 30s 阈值收窄；加开关会让「到底开没开」变成一个新的口径问题。
- **不改 `sleep` 在 `HARMLESS_COMMANDS` 里的地位**（`task/status-query-commands.ts`）：
  那是 P1 命令匹配的无害段判定，与本次引导无关，动了会顺带改 P1 的拦截面。
