# Bash 失败级联：删并行批次那一支，串行批次收窄为「写类失败 → 跳过写类后续」

## 决定了什么

- `query/tool-executor.ts` 并行批次：**删除** Bash `is_error` 联动取消兄弟。并行批次里的 sibling-abort 只剩用户 ESC / 上游中断。
- 同文件串行批次（GAP-02 `bashCascadeTripped`）：触发端与跳过端都加一道判据 `isReadOnlyBashBlock`。只读命令（`cd`/`pushd`/`popd` 不算改动）失败不触发；已触发时，只读后续照常跑，只跳过写类后续。拿不到命令串时按写类处理。跳过文案改成说明「会修改状态、可能落在错误目录」。
- `tool/bash/read-only-validation.ts` 新增 `isReadOnlyIgnoringCd`，**只给级联用**。严格口径 `isReadOnlyCommand` 不变，权限放行、并发分区、cwd 写回仍走它。
- abort reason `sibling-bash-error` 已无调用点，从 `ABORT_REASONS`、`describeAbortReason`、`agent/tool.ts` 的轮级 reason 集合中一并移除。

## 放弃了什么（以及为什么不选）

- **整条级联全删**：不选。`[cd build && make（失败）, rm -rf dist/*]` 这种形态下，后一条写操作会落在错的目录里，而且它自己不报错，bypass 模式下也没人拦。样本里没出现，不能当成「防不住也无所谓」。收窄之后，这条规则剩下的代价只有「写类失败后跳过写类后续」，这种情况下跳过本来就是对的。
- **只剥 `cd` 前缀、保留并行级联**：不选。能进并行批次的 Bash 一定是只读的（`isConcurrencySafe = isReadOnlyCommand`），只读失败不可能让兄弟落错地方，这一支没有任何可防的依赖链。cc 的 StreamingToolExecutor 保留同名机制，是因为它流式执行，只读与写可以同时在飞；本仓的批次划分已经把写类隔离到串行批次。
- **让 `cd X && 只读` 进并行批次（改 `isReadOnlyCommand`）**：不选。它同时决定三件事：权限放行（`cd <恶意目录> && git status` 能借目录里的 git 配置执行代码，cc 也单独拦了 cd+git）、并发分区、cwd 写回（只读跳过 `pwd -P`，cd 就不再持久化）。为了级联去动它，影响面太大。
- **按退出码区分（exit 1 视为「预期失败」）**：不选。grep 无匹配是 1，`make` 失败也常是 1，退出码说明不了这条命令会不会落错地方。

## 拿什么证明它生效了

- 证据（改前）：本机 `~/.sid-code/trajectories/sessions` 全量扫描。串行级联跳过 25 次 / 23 会话，失败方无一是写操作，被跳过的有 17 次以 `cd` 开头，至少 8 次下一轮被原样重跑。并行级联取消 13 次（10 bash + 3 read），失败方全是只读诊断。原形是会话 `20261104-105914-8e89e13c` 的 messages[103]：`ls 旧位置` 按设计 exit 1，与它无关的 grep 被跳过，messages[105] 原样重跑了一次。
- 回归测试：`packages/core/tests/query/tool-pipeline-gaps-20261024.test.ts` §1 改为断言并行兄弟照常执行（含队列中排队的 g10/g11），新增 §2b 五条：轨迹原形不跳、写类失败后只读照跑、写类失败后写类仍跳、只读失败不延迟触发、缺 command 按写类处理。新增 `packages/core/tests/tool/bash/readonly-ignoring-cd.test.ts`，同时锁住严格口径不变。
- 变异自证：`isReadOnlyBashBlock` 恒返回 false，§2b 4 条红；去掉 `ignoreCd` 分支，分类器测试 1 条加 §2b 2 条红。两处都已恢复。
- 端到端未验：需要拿新二进制跑一次带 cd 前缀的「ls 预期不存在路径 + grep」同轮请求，确认第二条不再被跳过。上线后的口径是轨迹里「已取消：同一轮中先行」的出现次数，应只剩写类后续被跳过的情形。
