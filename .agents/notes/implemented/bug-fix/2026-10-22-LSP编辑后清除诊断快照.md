# 文件编辑后 clearForFile 同步清除 latest 诊断快照

## 决定了什么

`packages/core/src/lsp/diagnostic-registry.ts` 的 `clearForFile(uri)` 在清 `delivered` / `pending` 之外，再删除 `latest` 中该 uri 的快照。

修复前，`syncFileToLSP()` 编辑后调用 `clearForFile()`，但旧快照还在。服务器重推之前，`codeAction` 调 `waitForDiagnostics()` 会因 `latest.has(uri)` 立即返回 true，再把编辑前的诊断放进 `context.diagnostics`，拿到的修复建议针对的是旧内容。修复后，`codeAction` 会等新一轮 `publishDiagnostics`，最多等既定的 1500ms，超时后按原设计带空 context 继续。

清除时不唤醒该 uri 的等待者，因为它们等的正是编辑后的新诊断。这一点和 `clear()` 不同：`clear()` 是整体重置，之后不会再有诊断到达，所以要唤醒。

## 放弃了什么（以及为什么不选）

- 给 `latest` 加版本号或代际计数，让 `waitForDiagnostics` 比较「编辑后是否收到过新推送」：能实现同样的效果，但要多维护一份状态。而且注册表注释本来就写明 `latest` 应被 `clearForFile` 清除，直接删除就符合既有语义，不需要新机制。
- 在 `tool/lsp.ts` 的 `codeAction` 调用侧绕过快照：根因在注册表，只修调用侧，将来新增的 pull 式消费者还会踩到同一个坑。

## 拿什么证明它生效了

- `bun test ./packages/core/tests/lsp/diagnostic-registry.test.ts`：37 pass / 0 fail，其中新增 4 条用例，覆盖：清除后 peek 为空、短超时等待返回 false、新诊断到达后能唤醒等待者并 peek 到新值、其它文件的快照不受影响。
- 变异自证：注释掉 `this.latest.delete(uri)` 后，前 3 条新用例变红（34 pass / 3 fail），恢复后转绿。第 4 条锁的是隔离性，在漏清的实现下本来就是绿的，属于预期。
