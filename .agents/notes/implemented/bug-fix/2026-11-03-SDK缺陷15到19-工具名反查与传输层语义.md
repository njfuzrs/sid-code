# SDK 缺陷 15–19：工具名改按 id 反查、第 3 层顺序配对、lazySchema 显式缓存标志、MCP 传输层双向语义与 close 生命周期

## 决定了什么

对应《20260927-SDK与插件-顺着sc-17核出的缺陷》缺陷 15–19，一个 PR 收口。五个缺陷都在 `packages/core/src/sdk/`，彼此独立但同属「恢复管道/公共 API/未接线传输层」的健壮性修复。

**缺陷 15（`session-recovery.ts`）**：`findToolNamesForResults` 不再取 `messages[len - 2]`。改为按 `tool_use_id` 从整段历史反查，从末尾向前扫、同 id 取**最近一次**出现的 `tool_use.name`，返回顺序跟随 `resultMsg.content` 里 `tool_result` 的顺序。位置索引在这个管道里不可靠：第 4/5 层会整条过滤 assistant 消息、第 6 层会剔除坏 block，清洗后「前一条就是发出它的 assistant」不再成立。

**缺陷 16（`session-recovery.ts` 第 3 层）**：`filterUnresolvedToolUses` 从「全历史收集 `tool_result` id 进 Set」改成一次**前向顺序扫描 + FIFO 配对**：`tool_use` 入队，遇到 `tool_result` 消费队中最早的同 id 项；扫描结束仍在队列里的才是未解析。修掉两类被集合判据洗白的历史：`tool_result` 排在 `tool_use` 之前、跨轮同 id 复用（前一轮的 result 把后一轮缺结果的 use 一起洗白）。

**缺陷 17（`lazy-schema.ts`）**：缓存判据从 `cached === undefined` 改成独立的 `hasCached` 布尔。泛型 `T` 不约束非 undefined，工厂返回 undefined 时旧实现每次调用都重新构造且完全静默。`cached` 声明为 `let cached: T`（不再带 `| undefined`）。

**缺陷 18（`mcp-bridge.ts`）**：
- `MCPTransport` 补 `onerror` / `onclose`，对齐 MCP SDK Transport 契约；
- `SdkControlClientTransport.send` 按 JSON-RPC 形状分流：request（有 method 有 id）的响应仍回投 `onmessage`；notification / response 只等控制层 ack、**不把 ack 当 MCP 入站消息**；任何失败走 `onerror`，不从 `send` 抛出；
- 新增 `receiveFromControl(message)`：宿主主动推送（服务端通知 / 对端响应）进入 `onmessage` 的真实通道；
- `SdkControlServerTransport` 同步补 `onerror` / `onclose` / closed 语义。

**缺陷 19（`mcp-bridge.ts`）**：`InProcessTransport` 加 `closed` 标志；`close()` 幂等置位、触发 `onclose`、**双向解引用 peer**（断开 `a.peer ↔ b.peer` 强引用环）；`send` 入口检查 + `queueMicrotask` 回调内**二次检查**——close 可能发生在消息已入队之后。

**缺陷 18c（零接线）本次不修**：`mcp_message` 控制子类型接线属另案（`control-schemas.ts` 已注明），文件头注释如实写明「生产零调用者、不代表功能入口可用」。

## 放弃了什么（以及为什么不选）

- **缺陷 16 没有把第 7 层 `stripDanglingToolResults` 也改成顺序敏感**。第 3 层顺序化后，被剔除 use 对应的 result 会自然变成集合视角的 dangling，由第 7 层切除；而 `checkMessageHistoryIntegrity` 被发送期 `backfillOrphanToolResults` 复用，改语义会动到发送期行为，超出本次 P2 范围。「同 id 多个 result 且其中一条提前」的极端形状仍按集合首次出现语义处理，未单独收紧。
- **缺陷 18 没有把 `send` 改成完全 fire-and-forget**。控制协议要求每个 `control_request` 必须有 `control_response`（否则宿主 `sendRequest` 永久挂起），所以 notification 仍 `await` ack，只是不投给 `onmessage`。真正的双向推送由新增的 `receiveFromControl` 承担。
- **没有顺手改 `config/settings/types.ts` 里的同名 `lazySchema`**（它用 `if (!cached)`）。该函数约束 `T extends z.ZodType`，zod 对象恒 truthy，当前不触发；且不属本文缺陷范围，按「顺手发现的无关问题单独 PR」处理。
- **没有接线 `mcp_message`**。需要控制协议扩展 + CLI MCP 管理器集成，且宿主侧实现不存在；文档已把它定为另案，本次只修传输层自身语义。

过程中发现并修正了一处**测试断言错误**（不是实现错误）：跨轮同 id 用例原期望 `turnInterruptionState.kind === "none"`，实际末尾 assistant 被剔除后历史末尾回到第二轮 user 文本，按三态定义应为 `interrupted_prompt`。这同时验证了缺陷 16 的修复效果——第二个 `tool_use` 确实被剔除，不再误报「在跑 Bash」。

变异自证（缺陷 16）：把第 3 层临时改回全局 Set，用例「tool_result 排在 tool_use 之前」与「跨轮同 id 复用」都会变红；恢复顺序扫描后转绿。
