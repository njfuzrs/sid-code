# G2 用例期望守卫：同 PR 改夹具又改期望即红，改已有期望需 `expect-reviewed`

## 决定了什么

落地总纲 §3.4 的两条检查（M2 遗留，M4 验收前置）：`scripts/smoke/expect-guard.ts`，接在 CI lint job 里，只在 pull_request 上跑。

- **规则 1**：同一个 PR 里，某个**已有**用例既改了夹具（用例目录下除 `case.ts` 以外的文件），又改了期望，直接红，带标签也不放。
- **规则 2**：改了**已有**用例的期望（删除用例也算），红，直到人加上 `expect-reviewed` 标签。
- 新增用例两条都不管。

「期望」的口径是 `case.ts` 的语义指纹：用 TypeScript AST 去掉注释，再删掉用例对象（同时有 `expect` 和 `mutations` 两个属性的对象字面量）上的 `mutations`，然后打印、按 token 重排，去掉尾逗号。所以改注释、排版、变异配方都不算改期望；改 `expect`、改它引用的顶层常量、改 `argv`/`repo`/`settings` 这类输入都算。

CI 接线：

- `pull_request.types` 补 `labeled` / `unlabeled`，否则人加完标签检查不会重跑；
- 比较 PR 合并提交的两个父提交（`HEAD^1..HEAD`，先 `fetch --depth=2`）；
- 标签从 `toJSON(github.event.pull_request.labels.*.name)` 读。

## 放弃了什么（以及为什么不选）

- **只比 `expect` 字段**：会漏。X2 的 `UNTRACKED`、X3 的 `MARKER` 都是顶层常量，`expect` 引用它们，改常量等于改期望。`argv` 换掉也能让断言空转。代价是改 `feature` 文案这种无害改动也要标签，宁可多问一次。
- **把 `mutations` 也算进期望**：不算。源码一漂移配方就 stale，跟着改 `find` 是例行维护，不会放宽任何断言。算进去的话，每次配方维护都要人加标签，标签很快就会变成随手加。
- **另开 workflow 或 job**：不开。这个守卫几百毫秒就跑完，放进 lint job 就自动被 `all-checks-passed` 的 `needs` 覆盖。新开 job 还得同步 `needs`，漏了就是后门。
- **对 push 到 main 也跑**：不跑。PR 已经合了，再拦没有意义。
- **代建 `expect-reviewed` 标签**：不代建。仓库标签属于 GitHub 侧设置，由维护者决定。守卫只看标签名，标签不存在时规则 2 恒红，这正是期望的 fail-closed。

**这条只能做到「可见」，做不到「强制」**（总纲 §3.4 已点破）：agent 和维护者用同一个账号，技术上也能自己加标签。约束靠两处落地：PR timeline 可以追查加标签的人；CLAUDE.md 明文禁止 agent 给自己的 PR 加。

## 拿什么证明它生效了

- `tests/scripts/smoke-expect-guard.test.ts` 13 pass。覆盖指纹口径 5 条、两条规则 6 条，外加真 git 临时仓库按用例归并（夹具、期望、新增、删除、目录外文件）和 base 解析不到时抛错。
- 守卫逻辑变异 4 轮，全部变红：
  - 规则 1 关掉 → 「夹具与期望同改」用例红；
  - 规则 2 恒放行 → 3 条红；
  - 不剔除 `mutations` → 「只改 mutations 不算」红；
  - 夹具改动识别不出 → 真 git 归并用例红。
- CI 接线反漂移（`tests/release-flow-contract.test.ts` 新增 2 条），变异 3 轮，每轮恰好红目标断言：types 去掉 `labeled`、守卫命令换成 echo、`if` 改成 push。
  - 两轮初版变异的替换文本缩进写错，把整份 YAML 弄坏，25 条全红，不能算自证，已按原缩进重做。
- 本地实跑：`bun run scripts/smoke/expect-guard.ts --base HEAD~3 --head HEAD` → A12/A6/X3 三个「新增用例」，exit 0。
