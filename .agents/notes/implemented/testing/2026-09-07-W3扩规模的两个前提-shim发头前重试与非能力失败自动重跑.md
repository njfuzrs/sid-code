# W3 扩规模的两个前提：shim 发头前重试 + 非能力失败自动重跑（84.1% 的失败在结构上可重试）

## 决定了什么

要把 72 题的外部评测跑成闭环（sid vs cc、sonnet vs deepseek），
挡路的不是「上游不稳定」，而是**上游不稳定时失败被记成了 `reward=0`**——
前者只花钱和时间，后者污染要写进结论的那个数字。落地两件事：

**T1 — shim 发头前重试**（`~/.local/share/sid-harbor-gateway/gateway.py`，⛔ 不在版本库）。
8 次 / 240s 窗口 / 2s×1.8 退避封顶 30s / 单向正抖动。
429·500·502·503·504 与 `RemoteDisconnected`·`URLError` 等重试；
**400·401·402·403 直穿**（402 余额耗尽尤其不能重试——`verifier_health.py`
里记着一次它被记进能力账）。⛔ **任何已发头的失败一律不重试**。
两条臂共用同一个 shim ⇒ 对照仍是对称的，不污染 sid vs cc 的比较。

**T2 — 非能力失败自动重跑**（`w3-classify.py` / `w3-run.sh` / `test-w3-classify.py`，入库）。
判据复用 `verifier_health` 的既有五条，不自己重写一份。
`rm -rf` 默认 dry-run，`SID_W3_APPLY=1` 才删；判据抛异常则 `rc=3` 停手
（⛔ 不许「判不出来就删」）。停止条件：坏题集合连续两轮相同就停。

**一处与原设想的实质分歧：分批要按时间，不按题。**
`-i` 会被写进 `config.json` 的 `datasets[].task_names`，而 harbor 有
`existing_config != self.config` → `FileExistsError`（`job.py:254`）⇒
每批一个 `-i` 的 job 永远合不回一个 job，**分母碎成 N 份**——正是 05 号被咬过的
「两侧分母装的不是同一批题」。改成**一条臂一个 job 目录、全程不带 `-i`**，
中断就 `harbor job resume`。

配套把两条文档警告变成闸（`w3-run.sh`）：**臂与 job 名一致性闸**
（名含 `cc` 而 `ARM≠cc` 则 `rc=2`，反向亦拦）、**题集指纹闸 + 磁盘余量闸**。
⇒ 一条警告只在有人读它时有效；一道闸在没人读它时也有效。

CI 侧把 `w3-classify.py` 接进 `tests/eval/harbor-agent-started-criterion.test.ts`
的消费方清单（它是 `agent_started` 的**第三个**消费方，且**会删目录**⇒ 判错代价更高）。

## 放弃了什么（以及为什么不选）

- **换一个稳定端点** —— 根因（为何恰好某些题 80% 失败）仍未定位，05 号如实标着。
  但「让流水线容忍一个 30% 失败率的上游」比「我们有个好端点」更适合作为成果：
  前者可讲机理、有实测数字，后者只是运气。
- **跑前探针判断「现在能不能跑」** —— 闸 2 已被证明会漏（探针 5% vs 真流量 80%）；
  本轮 12 连探针 0% 失败而 `/__stats` 累计 29.9%，两个数都真、口径不同。
  T2 一到位，「上游变差就直接杀掉」的代价归零，因为 resume 从断点继续。
- **靠 harbor 自己重试**（`harbor run -r N` / `resume --filter-error-type`）——
  实测那些 429/502 报废的 trial `exception_info` 是 `None`、`metadata` 整份缺失，
  在 harbor 眼里与「能力不行」完全一样，**两条原生机制都匹配不到**。
- **两臂并行** —— `-n 6` 单臂吃 9.8GB / VM 15.6GB，OOMKill 会伪装成 `reward=0`。
- **默认自动删** —— `runs/` 不在版本库，误删就没了；第一轮人工过目再放开。
- **改一份 07 号** —— 它的判据（89→72、镜像、dataset）仍对，但「下一棒落点」已变
  （从「定预算与臂数」变成「先补重试与续跑」）。改一份指向已变的文档 = 第二个 05 号。
  改为另起 08 号 + 在 07 号 §0 加指路。

## 拿什么证明它生效了

**两套变异门禁**（gateway 26/26 八组、classify 24/24 九组）+ TS 门禁 21 pass / 0 fail
（`bun test ./tests/eval/harbor-agent-started-criterion.test.ts`，28 expect）。

**🔴 实现时抓到一个真 bug，它正是本仓最贵的那类。**
第一版写成 `headers_sent = self._stream_upstream(...)`（**返回值语义**）。
正常路径完全正确，却在**唯一要紧的那条路径上失效**：流传到一半上游断掉
（实测 `CODE_200 -> EXC_RemoteDisconnected` **112 次**）时赋值语句根本没执行，
`headers_sent` 还是 `False` ⇒ 该失败被判可重试 ⇒ **第二个流写进同一个响应体**。
改用可变持有者在**发头前**置位。

同组还抓到一条**假绿断言**：`body.count(b"hello") <= 1` 在 bug 存在时照样绿，
因为 `urlopen` 在第一个响应边界就停。换裸 socket 读原始字节才咬住——
一个连接里两个状态行 `HTTP/1.1 200 OK ... HTTP/1.1 200 OK`。
⇒ **每加一条防线必须配一条能让它红的变异**，否则只是「多了一行看着安心的字」。

同理 `test-w3-classify.py` 一开始漏了 `agent_started` 的 `is False` vs `not`
那条变异——它会把 `runs/ccrun-n6` 判成 **10/10 全坏**（整条 cc 臂的产物被删）。
补了才咬住，并同步接进上面那个 CI 门禁。

**判据对三个既有 run 的结论与 05/07 号记载逐字吻合**（横向交叉验证，不是自证）：
`ccrun-n6` 10/0、`modelswitch-base-rerun` 7/3 且正是记载的那三题、
`modelswitch-base` 5/5（= E1 的「verifier 真判分 5/10」）。

**harbor 增量续跑实测**（不是读代码推断）：resume 3s 返回、已完成 trial 的
checksum 逐字未动；删掉一题后**只有那题**重跑（新 hash `__gih4uTw`），兄弟未被碰。

**两个 flow/stock 与口径纠正：**
- 失败可重试比例 **84.1%（533/634）**，不是先前口算的 75%——第一次把 access-log 的
  403（含 shim 自产的 `/api/pricing`）算进了分母，而那些**没到上游**。
  口径固定为「上游调用的结局」：200=1486、失败=634（29.9%）。
- 文档曾断言「题集一变 resume 当场 `FileExistsError`」。实测**分两种**：
  改 registry **路径** → `FileExistsError`（`job.py:254`）；
  **同路径、内容缩水**（即真实的 prune 场景）→ `ValueError: Existing trial config
  does not match planned job config.`（`job.py:359`）。文档原先只写了前者，已改。

**计数器判据从「惰性建键」改为「预置六个 0」**：原先「读不到 `retry_success`」
有两种完全相反的解释（上游很稳 / 重试根本没装上）而输出逐字相同。
现在「键在」= 结构判据，「值 > 0」= 流量判据，各自单义。
零流量下实测读到 6 个 0（`curl -s http://127.0.0.1:4100/__stats`）。

**§4 每条命令按最终文本复跑过**（本仓铁律：交接命令须按最终文本复跑）：
preflight 六条全绿（docker context = `colima-swebench`、容器内 `avx` = 8、
4100 在跑、两套门禁绿、本地镜像 72 题 / registry `[('terminal-bench-sample',10),
('terminal-bench-local',72)]`、磁盘余 42G）；
一致性闸两个方向 `rc=2`、名实相符 `rc=0` 且 dry-run **零 job 目录、一分钱没花**。

⚠️ **仍未验证的两件事，如实记：**
① 重试**只在假上游上验过**，真流量一次没跑 ⇒ 现在只能说「84.1% 的失败在结构上
可重试且重试路径有 26/26 变异验收」，**不能说「重试在真实评测里生效了」**。
判据是 T3 的 `retry_success` 增量 > 0。
② **cc 的等头容忍度未知**（harbor 的 cc agent 只注入三个 env，没有超时 knob）。
若它 < 240s，cc 臂拿不到 T1 的全部收益。⛔ 若真如此就如实记，**别调 cc 参数**
——那就改了被测对象。
