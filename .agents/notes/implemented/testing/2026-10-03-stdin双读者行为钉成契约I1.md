# stdin 双读者的确切行为钉成契约 I1：两边都收到每块字节，data 先于 readable（B9 / T0.3）

## 决定了什么

设计文档 review 把「底座的 `readable` + `read()` 与 CLI KeypressContext 的 `data` 在 Bun 下共存时到底怎么分字节」列为最大未知项。
实测结论写进 `render-port/SPEC.md` 的 I1，并用 `packages/cli/tests/render-port/stdin-dual-reader.test.tsx`（5 条）只经端口 API 钉住：

1. 真实写入流的每块字节，底座 `useInput` 与裸 `data` 监听**都**收到；
2. 同一块字节 `data` 读者先于 `readable` 读者；
3. 挂着 `readable` 时流是 paused（`readableFlowing=false`）；
4. 直接 `stdin.emit('data')` 只到 `data` 读者，底座 `useInput` 收不到 —— 这正是 `render-port/testing.ts` 的 `render().stdin.write` 的实现方式，所以**用测试 shim 测 `useInput` 组件会什么都不发生**，是测试设施的限制，不是组件 bug；
5. 底座卸载后摘掉 `readable`，剩下的 `data` 读者让流回到 flowing，继续收字节。

新底座若改成「只挂 data」或「先 read() 再自己分发」，第 1、2 条会红。

## 放弃了什么（以及为什么不选）

- **按 Node 文档推断**：文档说同时用 `readable` 和 `data` 时 `readable` 优先、流不 flowing，但没写 `data` 还会不会拿到字节。实测它会（`read()` 时同步 emit `data`）。不实测就会在这里押错。
- **只在 PassThrough 上测**：怀疑 TTY 流在 Bun 下行为不同，所以另用 expect 在真实 PTY 里跑了同一个探针。结果与 PassThrough 一致，测试因此可以只用 PassThrough。
- **把 shim 改成真实 write 以覆盖 useInput**：会改变 19 个现有 UI 测试的输入路径，超出 T0.3（只钉行为、不改行为）。在 I1 里写明限制，留给 T0.5 / T4.x 决定。

## 拿什么证明它生效了

- 探针 `/tmp/i1/probe.ts` + `probe2.ts`（已删）：Bun 1.4.2 与 Node 输出完全一致；PassThrough 顺序 `D:"abc" → R:"abc" → D:"d" → R:"d"`；
  真实 PTY（expect 分三次发送 `a` / `bc` / `d`）顺序 `D:"a" → R:"a" → D:"bc" → R:"bc" → D:"d" → R:"d"`，挂载顺序反过来结果不变。
  另测五种组合：只挂 data（flowing）/ 摘掉 readable 后 data 继续收 / readable 不 read() 时 data 一个字节都收不到 / readable 抛错一次后两边继续收 / data 先流动后加 readable 时转为 paused。
- `bun test ./packages/cli/tests/render-port/`：9 pass（I1 5 条 + R11/R12 4 条）。
- `bun run tui:spec`：I1 的测试列指向这个文件且片段 `I1:` 存在。
