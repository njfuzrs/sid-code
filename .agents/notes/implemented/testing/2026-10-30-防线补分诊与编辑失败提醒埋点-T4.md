# T4 补分诊：4 道 untriaged 防线定类，`edit_failure_reminder` 补 `EditFailureReminder` 事件

## 决定了什么

- `query/defense-registry.ts` 里 T4 初版标 `untriaged` 的 4 道防线定类：
  - `repeated_readonly_guard` → **B**，补 `precondition`（同签名只读探查连续 ≥ `STUCK_REPEAT_THRESHOLD`）
  - `low_yield_spin` → **B**，补 `precondition`（同参同返回值单标量 bash 连续 ≥ `LOW_YIELD_SPIN_THRESHOLD`）
  - `stop_reason_mismatch` → **A**（埋点晚于窗口）
  - `edit_failure_reminder` → **active**：它其实是「触发了没记」，本次补上埋点
- `query/edit-failure-tracker.ts` 新增模块级 sink `setEditFailureReminderSink` 与常量 `EDIT_FAILURE_REMINDER_EVENT_NAME = "EditFailureReminder"`。每追加一次提醒落一条事件，字段是 `tool_name` / `file`（只留文件名）/ `kind` / `count` / `threshold` / `escalated`。`cli/src/app.ts` 在 collector 就绪后用 `recordCustomEvent` 接上，写法照搬 `setBackgroundPollSink`。
- 注册表门禁的事件名解析扩到模块级 sink：除了 `traceAppendEvent({ event: "…" })`，`query/` 下 `export const *_EVENT_NAME = "…"` 也算发射点。不扩的话，这一类事件新增后不登记，门禁照样是绿的。

结论：4 道里没有 D 类，T8 能直接进候选的仍只有 `promise_nudge`。

## 放弃了什么（以及为什么不选）

- **穿 `traceAppendEvent` 进 `ToolExecutorDeps`**：调用方 `tool-executor.ts` 主循环和子代理共用，构造点不只一处，逐个穿线容易漏接，漏接就是又一个「触发了没记」。模块级 sink 是仓里 JIT / 后台轮询 / read 提示已经在用的做法。
- **事件里放完整路径**：归类失败形态只需要文件名，完整路径会把用户目录结构写进轨迹。
- **把 `stop_reason_mismatch` 判成 B**：前置形态真实出现过 2160 次，不能说「没出现」；它们全部早于事件上线，按 T2 的定义是 A。
- **`repeated_readonly_guard` 判 D、进拆除候选**：本地数据以 claude 和 deepseek-flash 为主，这道阀的事故原型是 deepseek-v4-pro。前置形态没出现，只能说明「没遇到」，不能说明「用不上」。
