# P1 idle 无空转定时器：用「静置窗口内回调触发次数」做判据，双底座对拍（B9 / T8.1b）

## 决定了什么

契约 P1（idle 时 0% CPU）原来挂着「⏳ T8.1」。现在落成 `packages/cli/tests/render-port/idle-timers.test.ts`，3 条用例：

- 主屏、alt-screen 各静置 1s，期间 setTimeout / setInterval / setImmediate 的回调**一次都不触发**；
- 已知例外：ResizeObserver 有观察目标时，窗口内唯一的触发源是它的 16ms 轮询（只钉 20–80 次的量级）。

夹具 `fixtures/idle-timers-app.tsx` 在加载端口**之前**包住三个定时器函数，按创建处调用栈的文件名归因。
每条用例一个子进程，子进程没打印结果算失败。

## 放弃了什么（以及为什么不选）

- **用 `process.getActiveResourcesInfo()` 判有没有活跃定时器**：bun 1.4.2 下有活跃 `setInterval` 时它也返回 `[]`（实测）。
  拿它做判据，结论永远是「没有空转定时器」，仪器本身是瞎的。
- **用 CPU 百分比做测试判据**：真实 PTY 下 10s 静置只有 0.01–0.02s CPU，这个量级在 CI runner 上全是噪声；
  空转定时器不论周期多长，在触发计数里都会现形，判据更硬。CPU 只做一次性实测，记在下面。
- **在完整 `sid-code` 上做自动化测试**：完整 CLI 静置 20s 有约 0.13s CPU（两套底座一样），来源混着 CLI 层，
  不是底座契约的口径；放进门禁要起真实会话，太重。

## 拿什么证明它生效了

- 真实 PTY 实测（`expect`，空目录）：完整 `sid-code` 静置 20s，legacy 0.14s / next 0.13s CPU；
  最小夹具静置 10s，两套底座都是 0.01–0.02s，有 ResizeObserver 时都是 0.05s，触发次数 644 vs 652。
- 双底座：legacy 3/3、next 3/3。
- 变异自证：next 的 `ink.tsx` 注入一个 900ms 空转 interval → 3 条全红；ResizeObserver 轮询改成 100ms → 例外那条红。
  另外先验证过仪器能看到东西：注入 500ms interval，10s 内抓到 22 次触发并正确归因到 `ink.tsx`。
- 第一次跑全红是夹具自己的计时 `setTimeout` 被算进去了（在包装之后才取原函数），改成包装前取之后转绿。
- `tui:spec` 64 条里 63 条有测试，只剩 P4（T8.1c）。
