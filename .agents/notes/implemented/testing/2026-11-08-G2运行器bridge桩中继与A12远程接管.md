# G2 运行器支持 bridge 桩中继；用例 A12-bridge 守住「远端批准真的生效并留痕」

## 决定了什么

运行器新增 `SmokeCase.bridge: { messages, permission }`。置上时主运行以 `--bridge ws://127.0.0.1:<port> --bridge-token … --bridge-insecure` 启动，运行器在进程内用 `Bun.serve` 的 `websocket` 起桩中继，按剧本应答：

- CLI 首帧 `auth` → 回 `auth_ok` → 发第 1 条 `user_message`；
- 收到 `permission_request` → 按 `permission` 回 `permission_response{id, allowed}`（`ignore` 则不答）；
- 收到 `status{turn_complete}` → 发下一条；发完最后一条 → SIGTERM 收尾。

首次连接要人工准入，无头下 fail-closed，所以运行器预置 `state/trusted-bridge-urls.json`，键与 `normalizeBridgeUrl` 同口径。会话 id 从隔离配置的轨迹目录取，恰好 1 个。剧本没走完直接判失败。CLI 发出的帧（不含 auth）交给断言，放在 `RunOutput.bridgeFrames`。

用例 `A12-bridge`：真实权限默认档，远端发「删掉 trash.txt」，回放 `rm -f trash.txt`，远端批准。断言：

- `BridgeInbound{user_message}` / `{permission_response}` 各 1 条；
- `BridgePermission{bash, allow}` 1 条；
- `PermissionDecision{bash, allow, source=user, confirm_via=bridge}` 1 条；
- `PostToolUse` 成功，`trash.txt` 已删；
- 桩收到恰 1 帧 `permission_request{toolName=bash}`。

`services:` 不扩 WS handler，改为单独的 `bridge` 字段。原因：bridge 不只是起个服务，还要预置准入记录、换启动参数、按剧本驱动进程退出、从目录取会话 id，这些都属于运行模式。塞进通用 `services` 就得在 handler 里反向控制进程。

## 放弃了什么（以及为什么不选）

- **判据用 deny 方向**：不选。「远端拒绝」和「bridge 代理没接上、无头档位自动拒绝」两种情况下文件都还在，只有远端批准才能让 default 档的 `rm` 真的执行，allow 方向才区分得开。
- **断言退出码**：不断言。进程由运行器 SIGTERM 收尾，退出码恒为 143，`SessionEnd.reason=abort`，都不携带信息。
- **先写一份设计文档**：不写。批 2 的 stream-json 驱动已经验证了「长驻 + 输入通道 + 可靠退出」这套做法，bridge 只是换了传输层。剧本和帧形态写在 `BridgeStub` 注释里，并标注了对应源文件。

**期望来源的缺口（必须点破）**：触发清单 A12 依赖企业后端，还没有人工实测。事件形态取自 2026-11-08 构建产物 + 桩中继探针。那次探针同时发现 `confirm_via` 从未落盘，#668 已修，这里的第三条变异守的就是它。

## 拿什么证明它生效了

- `bun run smoke`：20 例全过；A12 单例 0.6s，连跑 10 次 10 PASS。
- `bun run smoke:mutate -- A12-bridge`：3/3 killed。
  - app.ts 不把 bridge 代理注入 checker → `BridgeInbound{permission_response}` 0 条；
  - permission-proxy 把 `allowed` 恒读成 false → `BridgePermission{allow}` 0 条；
  - collector 删掉 `confirm_via` 映射（#668 修复前的形态）→ 带 `confirm_via=bridge` 的 `PermissionDecision` 0 条。
