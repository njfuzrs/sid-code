# xterm 无头差分测试台 + S1–S14 场景，legacy 基线冻结（B9 / T0.4）

## 决定了什么

- `packages/cli/tests/render-port/term-bench/`：`runner.tsx`（子进程入口）/ `harness.ts`（字节 → xterm → 快照 + 判定）/ `scenarios.tsx`（S1–S14）/ `bench.test.ts`（对 `baseline/*.json` 判定）。
- 新增 devDependency `@xterm/headless@6.0.0`（MIT，零运行时依赖，精确锁版本）。只在测试里用，`make build` 产物里 0 处引用。
- **场景在子进程里跑，fd 1 与 fd 2 指向同一个文件**。旧底座卸载时用 `writeSync(1, …)` 直写 fd 1（契约 X3），进程内 PassThrough 截不到；fd 级重定向才拿得到完整字节。实测 `process.stdout.write` 与 `writeSync(1)` 交替写同一文件时顺序不乱。
- 步骤边界是写进同一字节流的 `OSC 7777` 标记（xterm 忽略未知 OSC）。harness 按标记切段喂 xterm，在标记处拍快照。快照内容：可视区网格（逐格字符 + fg/bg + 粗斜下划反色暗删除线，同样式合并成 run）、scrollback、buffer 类型、光标位置与可见性、四个终端模式，以及本步字节指标（字节数、`2J` / `3J`、同步序列对数、`1049h/l`、按编号计的 OSC）。
- 判定（`compareToBaseline`）：网格 / scrollback / 光标 / 模式 / 步骤序列 / notes 逐项一致；full reset 与字节数不高于基线 1.1 倍；同步序列成对；OSC 计数一致。
- 帧耗时（`onFrame`）不进基线（会抖），由 `bun run tui:bench` 报告分位数。
- `SPEC.md`：32 条「⏳ T0.4」全部替换为指向场景的引用（`scenarios.tsx` `S<n>: {`），`bench.test.ts` 双向校验场景 `covers` 与 SPEC。测不了的 4 条改挂后续任务：P1 / P4 要 CPU / RSS，挂 T8.1 真实 PTY；P3 要 500 项历史，挂 T3.4；M4 超链接命中，挂 T6.2。`verify-tui-spec` 不再接受 `⏳ T0.4`。

## 放弃了什么（以及为什么不选）

- **进程内 PassThrough 当 stdout**：最初的探针就是这么做的，卸载那段 `?1007l … ?25h …` 全部绕过流对象直接上了 fd 1，快照里看不到 X3。
- **把 xterm 的查询回复回灌给子进程**：要改成交互式管道，场景时序变复杂。首批场景不依赖回复；I2 / I3 的分片回复由场景自己往 stdin 注入。
- **场景里不挂 KeypressProvider**：S13 首跑时选区恒为空。原因是底座只在 raw mode 打开时才挂 readable 读者（I1），没有 raw mode 使用者，鼠标字节进不了选区引擎。所有需要输入的场景都挂上了真实的 KeypressProvider。
- **场景里不包 SettingsProvider**：S1 首跑「全绿」，屏幕上其实是底座的错误面板（`useSettings 必须在 SettingsProvider 内使用`）。现在 harness 检测到错误面板就报 error，场景统一包 SettingsProvider。
- **帧耗时进基线做门禁**：同一台机器 3 轮之间 p95 差到 2 倍以上，会频繁误红。

## 拿什么证明它生效了

- 确定性：3 轮 × 14 场景并发跑，`summarize` 结果逐字节相同，14 / 14 identical，总耗时 2.4s。`bun test ./packages/cli/tests/render-port/term-bench/` 16 pass（14 场景 + 清单完整 + covers 双向一致）。
- 变异自证（临时改旧底座，测完逐字节恢复，`cmp` 确认）：
  - 标题只发 OSC 2 不发 OSC 0 → S14 红；
  - `AlternateScreen` 默认不开鼠标 → S7、S13 红；
  - 卸载时去掉 `writeSync(1, DBP)` → **全绿**；去掉 `writeSync(1, SHOW_CURSOR)` → **全绿**。
    原因：正常卸载时，raw mode 释放（`components/App.tsx:325-330`）和 `App.componentWillUnmount`（`:236`）已经各关了一遍。那几条 `writeSync` 是**进程被信号结束、React 卸载来不及跑时的兜底**，正常卸载路径测不到。已写进 SPEC X3。要测兜底得在场景里发 SIGINT，T0.4 没做，留给 T7.1。
- 场景实测确认或推翻的行为（都已写回 SPEC）：
  - R1：主屏每帧都包 `?2026h/l`；
  - R6：S2 动态区收缩恰好 1 次 `2J+3J`；
  - R7：S6 两次 resize 各 1 次 full reset，全程没有 `?1049h`；
  - **X2：经端口 `render` 拿到的 `unmount(error)` 不透传参数，`waitUntilExit` 照样 resolve**（S12 notes），与初稿写的「reject」相反；
  - E1：S10 裸 stderr 写入 0 字节上屏；console.error 要靠 CLI 的 console 护栏才拦得住（与生产 `fullscreen.ts` 同样装上后 0 字节上屏）；
  - M2 / M3：S13 拖选得到「第一行 可以被选中的文本\n第二行 ano」，双击得到「another」，各发 1 次 OSC 52。
- 全量 `bun test`：13401 pass / 0 fail。`make build` rc=0，undefined 警告 0 处，产物里 `xterm-headless` / `term-bench` 0 处。
