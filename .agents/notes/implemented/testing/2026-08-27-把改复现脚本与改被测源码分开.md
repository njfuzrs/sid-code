# 「edit 调用数 > 0」是个不够的判据：把「改复现脚本」与「改被测源码」分开

## 决定了什么

`evals/external-benchmarks/swe-bench/` 三个文件，加一组观测字段：

```
runner.ts   extractAgentLogSignals 增 editsInsideRepo / editsOutsideRepo / editPathsOutsideRepo
            RunRecord 增 edits_inside_repo / edits_outside_repo / edit_paths_outside_repo
record.ts   落这三个字段；新增一条 note（零 patch + 编辑全在仓库外）
grade.ts    buildAcceptance 增 editsOnlyOutsideRepoIds 输入，汇进 unaccounted
```

判据是 **`/testbed` 前缀**（官方镜像的仓库路径），取数源是 agent.log 里
`▶ edit {"file_path":"..."}` 这个**结构化 JSON 入参**，不是 `[PERMISSION] edit(...)` 那行
（后者给人看、会截断，且与前者同时出现会重复计数）。

**A7.11.8 那条 P1 原文是「验收判据从 `edit 调用数 > 0` 换成 `patch_bytes > 0`」。
查过源码后没有照做**，因为 `patch_bytes > 0` 这个判据**已经存在**了
（`grade.ts:415` 的 `link_ok`）。真正缺的不是判据，是**那个形态的可见性**：

smoke-10 的 `django-13964` 编辑了 2 次、`files_edited_count=1`，看起来像"终于开始改代码了"，
实际两次都打在 `/tmp/repro/test_bug.py`，一次没碰 `django/`。这个形态在**所有既有字段上都隐身**：

| 字段 | 值 | 与「完全没动手」的区别 |
| --- | --- | --- |
| `patch_bytes` | 0 | **无** |
| `patch_only_adds_files` | false | **无**（它连新建文件都没进 patch） |
| numstat/diff 不一致那条 note | 不触发 | **无**（`/tmp` 不在 `git add -A` 范围里） |
| `unaccounted` | 「轮次预算用尽」 | **有，但方向错**：引向"抬 max_turns" |

而实测（A7.11.4）此形态下模型**已完整定位到根因、连修法都写出来了**，
只是把预算全花在验证与探索上。这与"不知道从哪下手"的处置完全不同。

顺序也是判据的一部分：新 note **必须排在「轮次预算用尽」之前**，
因为两者会同时成立，而先看到哪条决定了人往哪个方向排查。

## 放弃了什么（以及为什么不选）

**照 A7.11.8 原文把判据"换成" `patch_bytes > 0`** —— 否决，因为**它已经是了**。
`grade.ts:415` 的 `nonEmpty` 就是 `patch_bytes > 0`，`link_ok` 一直用它。
照字面执行等于什么都不做，然后在文档里标一个"已完成"。
A7.11.8 那句话的真实意图是"别再用 edit 调用数判它做没做事"，
而实现这个意图需要的是**新增可见性**，不是替换一个已有判据。

**只看 `editsOutsideRepo > 0`，不加 `editsInsideRepo === 0`** —— 否决。
实测 `django-15128` 是 `in=1 out=2 patch_bytes=3099`（正常修复，边写复现脚本边改源码）。
只看 outside 会把它误标成"只改复现脚本"。**误报比漏报更坏**：
一条假信号会让人去查一个不存在的问题。

**让 `deriveOutcome` 读这个信号** —— 否决，与 `hitMaxTurns` / `patchOnlyAddsFiles`
同款理由：`outcome` 一旦依赖日志文案就从「机械可复算的四态」退化成启发式，而文案会变。
这三个字段一律**只标注、不参与判定**。

**在提取 patch 时把 `/tmp` 下的改动也捞进来** —— 否决。那是替 agent 打扫，
会掩盖行为特征，且官方 harness 只认仓库内的 diff。同 `patchOnlyAddsFiles`
那条「提取时滤掉等于替 agent 打扫」的理由，方向相反但同源。

**用 `files_edited_count`（trace 侧已有）** —— 否决。它在
`packages/core/src/trace/collector.ts:2029`，是 agent 自己的轨迹字段，
**不区分落点**（这正是 A7.11.4 被它骗到的原因），且评测 record 侧读不到它。

## 拿什么证明它生效了

**真实数据 10/10 一致**（在 smoke-10 的 10 份 agent.log 上跑新实现）：

```
astropy-12907     in=1 out=0 pb=504
astropy-8872      in=1 out=0 pb=1093
django-13964      in=0 out=2 pb=0     🔴 命中新判据
                  仓库外路径: ["/tmp/repro/test_bug.py"]
django-15128      in=1 out=2 pb=3099  ← 有 outside 但也有 inside，正确地不误报
matplotlib-20488  in=1 out=0 pb=764
matplotlib-26466  in=2 out=0 pb=1068
xarray-4075       in=2 out=0 pb=993
xarray-6461       in=1 out=0 pb=972
pytest-10081      in=1 out=0 pb=846
pytest-7982       in=2 out=0 pb=748
```

**唯一命中的正是唯一 `patch_bytes=0` 的那条**，路径与 A7.11.4 人工查
`messages.json` 得到的结论**逐字一致** —— 人工结论被机械复现。

**record 端到端**（造含 2 次仓库外编辑 + 撞顶的 agent.log，真跑 `record.ts`）：

```
edits_inside_repo       = 0
edits_outside_repo      = 2
edit_paths_outside_repo = ['/tmp/repro/test_bug.py']   ← 去重后 1 项，不是 2
unaccounted[0] = 零 patch 但**编辑了 2 次、全在仓库外**…      ← 更精确的归因在前
unaccounted[1] = 零 patch 且**轮次预算用尽**…
```

**grade 汇聚三分支**（真调 `buildAcceptance`）：

```
① 有命中     → unaccounted 点破「1 条零 patch 但编辑全在仓库外…」
② 无命中     → ✅ 不误报
③ 旧 run（不传该参数）→ ✅ 不误报（`?? 0` 缺省让 outside>0 恒 false，没量到就不声称）
```

**4 条变异自证**（各让测试失败、还原后全绿）：

| 变异 | 结果 |
| --- | --- |
| 判据去掉 `inside===0`（只看 outside>0） | 142 pass / **1 fail** ✅ 被拦 |
| note 顺序对调（撞顶排前面） | 142 pass / **1 fail** ✅ 被拦 |
| 判据同时匹 `[PERMISSION]` 行（重复计数） | 141 pass / **2 fail** ✅ 被拦 |
| 去掉 `[...new Set()]` 去重 | 142 pass / **1 fail** ✅ 被拦 |
| 还原 | **143 pass / 0 fail** |

测试样本全部是 **smoke-10 真实 agent.log 片段**，不是照实现编的字符串 ——
后者只能证明"函数按我写的方式工作"，证明不了"它认得真实日志"
（沿用本文件既有 `HIT_MAX_TURNS` / `LLM_FATAL_429` 那批样本的规矩）。

**门禁**：`affected-tests:run` **1118 pass / 0 fail**；`lint` 通过；
`format:check` 首次红（1 个文件），跑 `bun run format` 后通过；
`make build` 通过、自检 4 项全过、无 `will always be undefined`。

⚠️ **一条已知的脆弱点，写在代码注释里了**：判据依赖 `/testbed` 硬编码前缀。
换镜像布局（SWE-bench Pro 等）要重新核，否则会**全部落在"仓库外"**，
报告显示每题都在改复现脚本 —— 一个安静的假信号。
