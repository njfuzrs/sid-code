# bash 写目标推断补一条「不误拦」基线，而不是照着缺陷文档去修一个不存在的 bug

## 决定了什么

新增 `packages/core/tests/permission/bash-write-targets-baseline.test.ts`（7 个用例），
把「bash 写目标只来自重定向操作符与写程序参数」这件事钉成回归基线：

- **A 组**（`extractBashWriteTargets` 形态）：缺陷文档点名的两条只读命令，写目标分别是
  `["p7.js"]` 与 `[]`；`cat ~/.sid-code/settings.json`、`ls -la ~/.sid-code` 等一律 `[]`；
  反向断言 `echo x > .git/hooks/pre-commit`、`cp … .git/hooks/pre-commit`、
  `tee .git/hooks/pre-commit` 的目标必须提出来（防护不能跟着一起放宽）。
- **B 组**（端到端）：真实 `PermissionChecker` 在 headless（`--print` + `acceptEdits`）下跑
  这两条只读命令，断言模型看到的文本**不含**「安全检查」；对照组写
  `<ws>/.sid-code/settings.json` 必须**含**「安全检查」。

**没有改任何生产代码。** `extractBashWriteTargets`（`shell-command-variants.ts:529`）自
2026-10-24（`55f20294`）起就已是这个形态，当前 HEAD 也不复现缺陷文档描述的过判。

## 放弃了什么（以及为什么不选）

**放弃 A：按缺陷文档《20261103-04H2-执行边界-两个已核实缺陷》§2 去「修」一遍。**
不选的理由是回审计日志复核后，那批证据不成立：

- 文档说 12 条 `headless:6` 的 deny、理由全是「[安全检查] sid-code 配置目录」。
  本机 `~/.sid-code/logs/permissions-audit.log.1` 里 2026-10-27 有 104 条 deny，
  **没有一条是「安全检查」理由**。真实分布是「破坏性命令需要确认: SID_CONFIG_DIR=…」32 条、
  「破坏性命令需要确认: cd /tmp/…」11 + 9 条，且那些命令是探针会话自己构造的危险字符串
  （`items.push([..., "rm -rf /" ...])`），判「需确认」是**正确行为**。
- 那批探针跑在 `SID_CONFIG_DIR=/tmp/sidprobe-cfg` 下，临时目录已清理，
  轨迹库 `~/.sid-code/trajectories/sessions/` 里也没有 10-27 02:44 的会话 —— 原始记录不可复核。
- 文档列举的两条「只读命令」在 10-27 的审计日志里根本不存在。

按 CLAUDE.md「修缺陷前先回源码核实诊断，照着文档改等于修一个不存在的 bug」，
这里不能写一个「证明 bug 修好了」的测试（那是自欺），只能写「当前正确行为的基线」。

**放弃 B：补审计日志的 `step` 字段。** 复核时确认 10-27 的记录只有
`{timestamp,type,tool,resource,decision,reason,decisionReason}`，`decisionReason` 里没有
`step` —— 这正是「无法从日志判断是哪一步拒的」的成因。但当前代码在
`nonInteractiveDecision` 里已经写了 `step: headless:N`（本次实测只读命令落 `headless:14`、
写配置目录落 `headless:6`），缺口已不存在；再改一笔属于无病行医，不放进这个 PR。

**放弃 C：把 `extractBashWriteTargets` 的「宁多勿少」改成精确数据流分析。**
它现在的取舍是刻意的（函数头注释写了：多提一个候选只会被 safetyCheck 判一次，
漏一个就是一条免确认写 hook 的路径）。没有实测的漏拦案例就不动它。
