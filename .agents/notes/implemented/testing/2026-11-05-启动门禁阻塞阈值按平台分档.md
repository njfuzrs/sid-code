# 启动门禁的事件循环阻塞阈值在 macOS 上放宽到 300ms，ubuntu / 本机保持 100ms

`packages/cli/tests/startup/large-data-startup-gate.test.ts`。这是上一份 note
[《启动门禁首帧阈值按平台分档》](./2026-11-04-启动门禁首帧阈值按平台分档.md)
留下的那一条：当时明确写了「顺手把 Δblock 也分档」被否决，理由是样本不足。
PR #591 又红了一次，样本到了。

## 决定了什么

**1. Δblock 阈值按平台分档：`darwin` → 300ms，其他 → 100ms**

抽出 `blockDeltaLimitMs(platform)` 纯函数 + `BLOCK_DELTA_LIMIT_MS` 常量，两处 Δblock 断言
（「事件循环最大阻塞」与「补传 U1–U4」）都用它。**ubuntu / 本机的 100ms 不动** ——
真实信号在本机是 −13 ~ +15ms，100ms 的灵敏度没必要陪 macOS 一起放弃。

**2. 失败消息与测试名带上实际生效的阈值**

`逐轮 Δblock=[a / b / c]（中位数 Xms，阈值 Yms）`，与首帧那条同款。原先名字里写死
「不超过 100ms」，分档后会在 macOS 上产生「测试名叫 100、实际判定 300」的谎报。

**3. 补一条 Δblock 分档的防漂移断言**

`blockDeltaLimitMs("darwin") === 300`、`"linux"/"win32" === 100`、常量与 `process.platform` 一致。
理由同首帧那条：把两档写成同一个数字（或把 `"darwin"` 拼错）时 macOS 会悄悄退回 100ms，
而噪声没冒头的那几次仍然全绿，退化看不见。

## 放弃了什么（以及为什么不选）

**上一份 note 否决过「顺手把 Δblock 也分档」，这次推翻了它。** 当时的理由是「只有一次失败
（PR #575 的 Δblock 150ms 超 100ms），样本量不足以标定 macOS 上的新阈值」—— 在**当时**成立。
2026-11-05 PR #591 提供了第二个样本，且形态与首帧当年完全同源：

```text
run 41954347885（PR #591，改动只在 TUI 渲染层，不碰启动同步路径）
逐轮 Δblock=[195 / 88 / 210]  中位数 195ms（阈值 100ms）
max_loop_block 空=[125 / 179 / 186]  大=[320 / 267 / 396]
```

两个关键读数：空目录自身的常数阻塞 125~186ms，**比阈值本身还高**（分母比判据还吵）；
三轮里中间那轮 88ms 低于阈值，是噪声形态而非稳定偏移。这与首帧当年「空目录 first_frame
自己波动 148ms、阈值 150ms」是同一个病。

其余否决掉的候选：

- **macOS 上取 250ms（保住 Δblock 对 T1/T2 +300ms 的检出）**：本次实测中位数已经 195ms，
  余量只剩 55ms；首帧当年的教训就是「阈值贴着测量值 = 判定由运气决定」（有一轮只超 0.7ms）。
  取 250ms 等于把同一个 flake 换个数字留着。
- **macOS 上整条跳过 Δblock 断言**：C1（全量会话清理放回主线程）+570ms 是这条门禁抓到的
  最大变异，跳过等于放弃 macOS 上的整类检出，没必要。
- **采样 3 轮 → 6 轮**：上一份 note 已经论证过——只减小方差、不改中心，而这里是中心（噪声水平）
  就高于阈值，加轮次解决不了，测试时长还要翻倍。
- **把两条门禁合并成一条「任一超标即红」**：会让失败消息失去「是首帧还是阻塞」的归因，
  而这两种失败指向的修复方向不同（首帧前多做活 vs 交互窗口内同步阻塞）。

## 拿什么证明它生效了

**分档断言的变异自证**（改坏 → 断言变红 → 恢复）：把 `blockDeltaLimitMs` 的
`platform === "darwin" ? 300 : 100` 改成 `? 100 : 100`：

```text
$ bun test ./packages/cli/tests/startup/large-data-startup-gate.test.ts -t "阻塞阈值确实按平台分档"
error: expect(received).toBe(expected)
Expected: 300
Received: 100
 0 pass / 8 filtered out / 1 fail
```

恢复后通过。

**本机实测（macOS，生效阈值 300ms）**：

```text
[gate] 每轮配对差值（同一轮内 被测−空，frame/block，ms）：
[gate]   轮0 大−空 143/37 传−空 60/-3
[gate]   轮1 大−空 199/49 传−空 84/24
[gate]   轮2 大−空 -166/-48 传−空 -166/-45
```

本机 Δblock 中位数 24~37ms，远低于任何一档阈值——这同时说明 300ms 不是「随便放宽到测得过去」，
而是针对 macOS 共享 runner 噪声的定向修正。

**没有证明的（局限，如实写）**：

- macOS 上 300ms 会不会**仍然**偶尔红，需要靠后续 CI 的真实分布回答。已知最坏的一次中位数是
  195ms，余量 105ms；若分档后 macOS 仍出现红，下一个动作是取更大样本重新标定 macOS 档位，
  而不是继续上调。
- macOS 上 100~300ms 的真实 Δblock 回归会**漏检**。T1/T2（+300ms）在本口径下正好压在边界上，
  靠 Δframe 的 +353ms > 300ms 兜底；这是两条门禁组合覆盖的取舍，写在这里以免后来者误以为
  单条就够。
