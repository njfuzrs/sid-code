# G2 用例 B1-webhook-trigger：本地裸仓 + 签名 webhook 驱动 daemon 跑完一次 PR job

## 决定了什么

- **新用例 `tests/smoke/cases/B1-webhook-trigger/`**（G2）。主运行是一次最小的 `-p`，之后起 `daemon start --webhook`。daemon.log 出现 `webhook 源已启动 :3847` 后，往 `/webhook/github` 投递一条 HMAC 签名正确的 `pull_request opened`，要求返回 202 accepted。
  - 断言 daemon.log 依次出现 `webhook 源已启动` → `headless job 启动 source=webhook` → `headless job 完成`。
  - 断言 `trajectories/daemon-jobs/pr-smoke-owner-smoke-repo-1-*.json` 恰好 1 个，内容为 `source=webhook`、`exitCode=0`、`timedOut=false`。
  - 断言 prompt 里含 PR diff 的 `+新增一行`（证明 clone、fetch base、三点 diff 都跑通了）。
  - 断言 output 来自 `job.jsonl`。
- **期望来源**：核心功能触发清单 B1 的人工实测（2026-11-05，真实 GitHub webhook，`njfuzrs/agent-traj-bench` PR #13）。
- **回贴半边**按裁决 4 本季度不做，不在本例。
- **PR-13 的两个可行性未知数**，答案都是「能，不改产品代码」：
  - **clone 地址**：worker 只把 `owner/repo` 拼成 `https://github.com/<owner>/<repo>.git`，不读载荷里的 `clone_url`。用例在假 HOME 的 `~/.gitconfig` 里写 `url."file://<用例仓>/remotes/".insteadOf = https://github.com/`，重定向到本地裸仓 `smoke-owner/smoke-repo.git`；daemon env 带 `GIT_ALLOW_PROTOCOL=file:https`。
  - **job 子进程能否走 replay**：能。子进程继承 daemon 的 env，`SID_CODE_REPLAY_FILE` 指向 `job.jsonl`（与 A5 同一机制）。
- **运行器**（`tests/smoke/lib/{types,runner}.ts`）：
  - `DaemonStep` 加 `argv`、`env`、`trigger{ready, run}`。trigger 等 daemon.log 出现就绪行后执行一次，然后继续等 `until`。不用固定 sleep 等端口。
  - **两处加固**：daemon 步骤的 `prepare` 抛错，以及 `expect.output` 抛错，都收成用例失败。之前异常会冒出 `runCase`，`run.ts` 整体崩掉，后面的用例全不跑，step summary 也写不出来。B1 端口被占时这两处都会触发。
- 三条变异配方：
  - worker 不起 job，但照样回 202；
  - job 来源被记成 schedule；
  - opened 事件被当成不支持的 action。

覆盖率 23/26 → **24/26**（B1 触发半边入分子）。

**牺牲**：webhook 端口写死 3847（`daemon.ts` 的 `webhookPort ?? 3847`，CLI 没有参数）。本机常驻 daemon 占着 3847 时，本例会红，原因写在失败信息里（prepare 先用 `lsof` 探测端口）。CI runner 上没有常驻 daemon，不受影响。

## 放弃了什么（以及为什么不选）

- **给 daemon 加 `--webhook-port` 参数**：这是为冒烟改产品接口（总纲「不做什么」）。占端口的情况只出现在开发者本机，失败信息能说清原因，不值得为它改 CLI。
- **端口被占时 skip**：本机装着 daemon 的人就永远看不到这个用例变红，而这正是最可能改 daemon 的人。
- **让 worker 改读载荷的 `clone_url`**：这是改产品行为（而且会扩大「载荷可控 → clone 任意地址」的攻击面），不是测试该推动的事。
- **用固定 sleep 等 webhook 端口**：慢机器上会假失败，所以改成等 daemon.log 的就绪行。
- **只断言 HTTP 202**：202 是在 worker 起 job 之前就返回的。变异 1（不起 job 照回 202）证明了，只看状态码会假绿。
