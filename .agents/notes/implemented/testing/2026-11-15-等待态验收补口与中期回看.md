## 放弃了什么（以及为什么不选）

**不修 `zombie_wakeups` 的计算口径。**
方案 §9.8 的定义是「`ScheduledInject{outcome:injected}` 晚于**同 prompt 周期内**
最后一次『清单清零』或收尾 `EndTurnShape`」，`scripts/wait-audit.ts:563-575`
的实现只判「注入前存在任何 `EndTurnShape`」——而唤醒注入本来就发生在模型
结束回合之后（设计和如此），于是每次正常空闲注入都被计成僵尸。
11-12 会话（`20261112-175603-ca8d7e5c`）两次注入的时间线均为
「`EndTurnShape` 10:35:40 → `ScheduledInject` 10:48:21」，属正常流程。
**不改的理由**：要改就得先定义「同 prompt 周期内清单清零」的可操作判据
（`TodoProgressAdvanced{unfinished:0}` + `UserPromptSubmit` 划界），
而方案原文的「或收尾 EndTurnShape」在正常注入下恒真，贸然换判据会引入
比现状更错的数字。改为：在字段注释标注口径限制（本次已补），L6 结论里
附人工核对结果（4 次均为正常注入），后续如需真实僵尸判据单开一项。

**不把 17 项 E2E 全做成 G2 回放用例。**
已有单测覆盖的确定性部分不重复造 G2（CLAUDE.md「防线分层」）；需真实模型的
6 项属 G3/G4，不是贡献者门禁（CONTRIBUTING「贡献者不需要任何 LLM API key」）。

**不补 `T-M1-13/14/22` 的 monitor 专属端到端用例。**
另一份方案（`eab383e5` 会话退出清理 monitor）已补
`packages/cli/tests/app/quit-cleans-tasks.test.ts`、
`exit-signal-kills-monitor.test.ts`、`packages/core/tests/task/monitor-orphans.test.ts`，
T-M1-22 的缺口实际已闭合；T-M1-13/14 的通路层覆盖在 FIX-2d Note 已核对并如实记录。
