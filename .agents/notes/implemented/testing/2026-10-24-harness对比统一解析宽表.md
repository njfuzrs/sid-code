# sid-code 与 Claude Code 同任务对比：口径写死在一个解析脚本里

## 决定了什么

新增 `scripts/harness-compare.ts`，把两边轨迹解析成同一张逐调用宽表（每行一次 LLM 调用），并给出主代理汇总。测试在 `tests/scripts/harness-compare.test.ts`。脚本把以下口径固定下来：

- sid-code 主代理调用取 `raw.jsonl` 的 pair 行，跳过 `type: "request_sent"` 预写行。子代理、fork、标题调用取 `events.jsonl` 的 `BilledRequest`（带 `caller` 的那些）。不带 `caller` 的已在 raw.jsonl 里出现过，不重复计。
- sid-code 只在 index=1 记录 system 和 tools。后续行这两列填 null，表示「没记」，不表示「没变」。
- sid-code 的 system 是转换前的字符串。wire 上的分块长度按 `buildSystemBlocks` 的规则用 `DYNAMIC_BOUNDARY` 还原。
- Claude Code 的 caller 按请求形态判断：tools 为空且带 `output_config.format` 的是标题调用，最后一条 user 文本以 recap 提示开头的是 recap，其余是 main。
- Claude Code 的 `system_hash` 剔除了第 0 块计费头，因为它的版本后缀随调用类型变化。
- 命中率 = Σcache_read / Σ(cache_read + cache_write + input)，只算 main，用累计值。

## 放弃了什么（以及为什么不选）

- **每个维度各自写解析**：不选。P1 有 4 组并行，各写一份解析，口径一定打架。本样本已经出过一次：文档写「剔除标题后 71.0%」，但 recap 调用没剔，严格只算 main 是 71.08%。
- **复用 `trace-digest` / `digest.ts`**：不选。它们只认 sid-code 的轨迹格式，Claude Code 的 claude-trace 格式接不进去。往 core 里加对方格式的解析属于越界。
- **sid-code 一侧也走 claude-trace 抓包**：暂不做。wire 上的 thinking/effort 已经能从 `BilledRequest.thinking_wire/effort_wire` 拿到，断点数能从 `PromptCacheLayout` 拿到，现阶段没有维度需要逐字节的 wire diff。等组 B 要做前缀逐字节 diff 时再评估。

## 拿什么证明它生效了

- `bun test ./tests/scripts/harness-compare.test.ts`：8 pass。
- 变异自证共 4 处，改坏后都变红，之后已恢复：
  - 不跳过 request_sent：3 fail。
  - 去掉 recap 判据：1 fail。
  - 计费头不剔除：1 fail。
  - 不过滤无 caller 的 BilledRequest：2 fail。
- 用真实样本对数：`bun scripts/harness-compare.ts --sid 20261024-215903-c2ee9cd2 --cc f2ecff67-5b4d-4317-a842-079462d35ca1` 的输出为：
  - sid-code：main_hit=71.83%，first_input=42421，tool_use=32。
  - Claude Code：main_hit=71.08%，first_input=40999，tool_use=18。
  - 与对比文档第一部分的 71.8% / 42.4K / 41.0K / 32 / 18 一致。
