# monitor 突发阀用例改断言时序无关不变量，摘掉 CI 上必红的固定省略行数

## 决定了什么

`packages/core/tests/task/monitor-task.test.ts` 的「突发阀停止：触发那一批的行也进冲刷」用例，
把 `expect(lines[0]).toContain(\`前 ${100 - MAX_BURST_FLUSH_LINES} 行已省略\`)`（即固定期望
`前 60 行已省略`）换成了三条与批次时序无关的不变量：

1. 保尾——最后一行 `100` 必须在某条事件里出现（这是「触发那批行没丢」的直接证据）；
2. 一旦发生截断，省略计数自洽——保留的第一行必须是 `omitted + 1`；
3. 截断时保留行数恰好等于 `MAX_BURST_FLUSH_LINES`。

源码零改动（`packages/core/src/task/monitor-task.ts` 未动一行）。

## 放弃了什么（以及为什么不选）

**否决 A：把期望改成 `前 56 行已省略` 之类的实测值。** 换个 runner 又变了。CI 实测同一份代码
三个数字：期望 60、ubuntu 收到 56、macOS 收到 16，说明这个量本身不确定。

**否决 B：放宽成 `expect(lines[0]).toContain("行已省略")` 只验证有截断提示。** 这样会把 D3
修复 3 的验证力全丢掉——「触发那批行被补进缓冲」这个修复如果被回退，断言照样是绿的。
用变异自证确认了这一点：删掉 `pushLines` 里补入那一行后，宽松写法不会红。

**否决 C：让测试确定性地构造「100 行全滞留缓冲」。** `EVENT_BATCH_MS` 是模块常量、没有注入点，
spawn 子进程也注入不了；要加注入点就得改生产签名，为一个测试放宽生产契约不划算。

**为什么原断言本身就不成立**：它隐含「100 行全部滞留在 `pendingLines`，等终态冲刷一次性截断」。
但 `pushLines` 每推进一批行就会挂一个 `EVENT_BATCH_MS` 窗口定时器，`flushBatch` 用
`splice(0)` 取走并经 `admit` 正常投递——慢 runner 上 `printf` 还没走完，前面几批已经被投递走了，
那些行不再进入最终冲刷。于是 `drainAll` 的 `omitted = merged.length - MAX_BURST_FLUSH_LINES`
必然小于 60。这不是实现缺陷，是测试前提错了。

## 拿什么证明它生效了

**① 本机反复跑不红**：`bun test packages/core/tests/task/monitor-task.test.ts -t "突发阀停止"`，
修改前连跑 6 轮全 pass（说明本地快、时序不触发），修改后同样 pass。

**② 变异自证（关键）**：把 `monitor-task.ts` 里 `pushLines` 的补入行
`ctl.pendingLines.push(...lines);`（在 `stopMonitorProcess(taskId, "rate_burst")` 之前那行）
删掉，再跑该用例，得到：

```
error: expect(received).toBe(expected)
Expected: true
Received: false
  at packages/core/tests/task/monitor-task.test.ts:611:55
(fail) D3：暂存行冲刷与终态出口收敛 > 突发阀停止：…（D3 修复 3）
 0 pass / 1 fail
```

失败点正是新断言的第 ① 条（保尾 `100` 不见了），说明它确实守住了「触发那批行不能凭空消失」。
随后从备份还原源码，`git status` 确认 `src` 无改动。

**③ 文件内全量不回归**：`bun test packages/core/tests/task/monitor-task.test.ts` → `35 pass / 0 fail`。

**④ 真实目标**：修的是 PR #694 / #696 上同一个失败的 `test (ubuntu-latest, 1/3)` 与
`test (macos-latest, 1/2)` job，两者 diff 均未触及 `task/`，可确认与这两个 PR 的改动无关。
