# 大数据启动门禁的 afterAll 清理给显式超时，不再走 bun 默认 5s

## 决定了什么

`packages/cli/tests/startup/large-data-startup-gate.test.ts` 的 `afterAll` 显式传 `180_000`。

它原来不传超时，走 bun 的默认 5s（实测默认值 5001ms）。这条 hook 要递归删掉 4 个临时
home 目录：其中 large / upload 两个各含 200MB 大文件，还有 1500 个轨迹目录 × 20 个小文件
（合计约 3 万个小文件、400MB）。macOS(APFS) 上 1s 内删完，ubuntu runner 的磁盘上超过 5s。

后果不是「清理慢一点」，而是**整条测试判红**：PR #521 的 CI 里 7 条子断言全部通过
（`headless` 日志最后一条 07:50:48.108），5.06s 后报
`(fail) 大数据启动门禁… > (unnamed) [5058.67ms]` + `a beforeEach/afterEach hook timed out for this test.`
—— `(unnamed)` 且名字为空正是 hook（非 test）超时的形态，bun 把 `afterAll` 也归到这句措辞里。

## 放弃了什么（以及为什么不选）

- **减少 fixture 体积**：不行。这套 fixture 的体积是被标定过的 —— 文件里记着 C1 变异只 +698ms、
  T1/T2 +353ms。第一版用 400 天前的数据、纯 `aaaa` 正文，变异根本没能让门禁变红，
  缩体积会把真实退化推回噪声里。
- **把清理改成异步 / 并发删**：`afterAll` 返回前一样要删完，解决不了「超时判定」这件事；
  而超时是声明式的一行。并发删还会在慢盘上把 IO 打满，反而影响同批并行跑的其它测试文件。
- **在 hook 里 try/catch 吞掉**：hook 超时不是抛错，是 bun 侧的计时器判定，catch 拦不住。
- **CI 上跳过这条测试 / 重跑等绿**：它挡的是真实不变量（TUI 首帧与事件循环阻塞不随
  `~/.sid-code/` 数据量增长），跳过等于把门禁摘掉。而且这不是随机 flake —— 每次运行都要删
  同样多的东西，只是 macOS 恰好够快。

## 拿什么证明它生效了

三条，都是实测输出：

1. **默认超时探针**（`/tmp` 下的最小用例）：`afterAll` 内 `Bun.sleep(20_000)`、不传超时，
   报 `(fail) … > (unnamed) [5001.23ms]` + 同一句 `a beforeEach/afterEach hook timed out`。
   确认默认值是 5s，与 CI 的 5058.67ms 吻合。
2. **变异自证**：把该文件里的 `180_000` 临时改成 `1`，重跑该门禁，复现出与 CI 完全相同的
   失败形态 —— `(fail) … > (unnamed) [2744.92ms]`，7 pass / 1 fail。
   说明这个参数确实被 bun 采用，不是写了不生效。
3. **恢复后重跑**：`bun test ./packages/cli/tests/startup/large-data-startup-gate.test.ts`
   → 7 pass / 0 fail（46.01s 跑完，清理占秒级，180s 有 ~10 倍余量）。

配套门禁：`bun run typecheck:gate`（66/66，无新增）、`bun run lint`、`bun run format:check` 均通过。

不声称修好了另一个形态：main 上 2026-11-02 07:35 那次 macOS 失败是**首帧差值 159.2ms > 150ms**
的阈值抖动，与本次的 hook 超时是两回事，本 PR 不动它。
