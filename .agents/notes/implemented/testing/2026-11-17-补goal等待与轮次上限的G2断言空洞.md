# 补上 goal 等待 / 轮次上限在 G2 层的两处断言空洞

## 决定了什么

方案 §7.3 对两条 G2 用例列了期望，但落地时都被削弱了，本轮补齐：

1. **`tests/smoke/lib/assert.ts` 的事件断言支持 `a.b` 点号路径。**
   此前 `fieldOf` 只按整键取（`data[key]` → 顶层 `key`），`TurnComplete.goal_limit_exceeded`
   这类**嵌套 payload** 无法用 `where` 表达（`===` 比对象引用恒不等），于是
   「断言字段存在」实际只能断言「事件存在」。先整键后路径，字面量含点的键行为不变。
2. **新增 `tests/smoke/cases/S-goal-wait-achieved`。**
   覆盖方案 §7.3 的第 3、4 条期望与 §7.5 第 1 条：
   等待挂起期间模型调用 **0 次** → 释放后**才有**续跑调用 → 评估器判 `satisfied` →
   `goal.status === "complete"`。此前 `S-goal-wait` 只走到「挂起 + 撞 turns_limited 收尾」，
   「等待之后目标真的达成」这条路径**一条断言都没有**。
3. **`S-goal-turn-limit` 补两条断言**：`TurnComplete.goal_limit_exceeded.source === "turns"`
   恰好 1 条；`BeforeModel` 恰好 3 条（2 轮工作 + 1 轮强制总结）。后者把「第 3 轮工作请求
   没有发出去」从「文件没落盘」升级成「模型调用数没多」。
4. **补 `rejected/` 两份**：D1（不把评估器摊到每轮）、D8（不加 goal 等待放行开关）。
   方案 §5 要求这两条落 `rejected/`，此前论证只写在两份 implemented note 的
   「放弃了什么」段里，检索不到。

## 放弃了什么（以及为什么不选）

- **不改 `S-goal-wait`，而是新增一条用例**。它需要同时改 `replay.jsonl` 与 `case.ts`，
  正好撞上 G2 期望守卫的规则 1（同一 PR 既改夹具又改期望，带标签也不放）。
  更实质的理由是**关注点不同**：`S-goal-wait` 守「等待期不调评估器（不空转）」，
  新用例守「等待结束后能收尾」，合并会让失败归因变糊。
- **不用 `WaitRegistered` 当「等待期」的起点**。实测时间线里 monitor 在 tool_use 阶段
  就注册，而首轮还要再请求一次拿 `end_turn`——用它当起点会把**正常收尾请求**误判成
  「等待期空转」（第一次跑就报了「等待期发生了 1 次模型调用」）。起点改成
  `GoalGateDecision{reason:"waiting"}`（挂起生效那一刻）。
- **不把「等待期 0 次调用」写成事件计数**。计数表达不了时间区间，必须读轨迹按时间戳判，
  所以放在 `expect.output` 里。同理「释放后有续跑」也只能按时间戳判。
- **不让新用例靠撞 `turns_limited` 退出**。`S-goal-wait` 那样做是为了让进程能退出
  （续跑轮被推回会卡死）；本用例要的正是「达成」，所以 `maxTurns=10` + 评估器
  `satisfied` 回放，让 goal 自己收尾。
- **不改 `S-goal-turn-limit` 的夹具**。只动 `case.ts`，避开守卫规则 1；规则 2
  （改已有用例期望需要 `expect-reviewed` 标签）按仓库流程交人工 review。
- **不新增 `S-goal-turn-limit-payload` 独立用例**。与现有用例夹具完全相同，
  多一条只是重复维护；嵌套断言能力加在 `assert.ts` 上，一条用例就够。
- **不把回放数据冒充真实采样**。本机 140 个含等待事件的会话里没有一条
  「goal + 等待 + 续跑 + 达成」轨迹，而且**修复前这条路径根本走不到**。
  按用户 2026-11-15 的原则造数据，但用例头必须注明「按方案期望构造，不是从真实轨迹抄的」。
