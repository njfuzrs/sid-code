## 放弃了什么（以及为什么不选）

- **不把 5 个用例的判据写成「只看 PermissionDecision」**。那会让「权限层把 bash 全拒了」也通过——
  正是 CLAUDE.md 警告的「白名单绿测零调用」形态。所以 B1/B4 都加了文件系统副作用断言（marker 不存在），
  B14 加了 `PostToolUse` 断言（证明工具真跑完，而不只是「放行」）。B14 还额外断言零 deny——
  否则「整个权限层放行一切」也会让它绿。
- **不用方案 §6.3 原文给 B4 设计的「裸仓库形态 + fsmonitor marker」判据**。两条实测否掉了它：
  ① 裸仓库形态下 `git status` 直接报「该操作必须在一个工作区中运行」，fsmonitor 不触发、marker 恒不产生；
  ② 即使换成嵌套真实仓库，第二步的 `git status` 也会被 PR-1 的 git 边界拦下，marker 同样不产生。
  两个方向都让 marker 判据失去区分度，改用「不得出现 `step=5.6` 的 allow」这个决策形态判据，
  marker 保留为纵深防御。**这条已回填方案文档**。
- **不用 `sub_agent` 做 B14 的用例主体**（方案原文如此）。`sub_agent` 的回放要吃掉额外游标（见 X3 的三段式），
  而本用例要证的是「声明式免权限在无头 default 下生效」，`think` + `todo_write` 两个纯记账工具就能证，
  失败时归因也更直接（`sub_agent` 被拒与「子代理内部还有一层权限」两种原因会混在一起）。
- **B3 不按方案原文断 `cd <cwd> && git log` → `step=5.6`**。实测该命令落在 `5.5`
  （走 PR-1 的 git 边界），`5.6` 只对**非 git 只读主体**（`ls` / `cat`）命中。用例按实测把两层分开断言。

## 拿什么证明它生效了

```
$ bun run scripts/smoke/run.ts --source X9…X13
5 例：5 通过，0 失败，0 跳过

$ bun run smoke                      # 全量，含既有 31 例
36 例：36 通过，0 失败，0 跳过（binary）

$ bun run scripts/smoke/mutate.ts X9…X13
5 条变异：5 killed，0 未杀死或已陈旧
```

变异配方逐个验过（这是门禁是否空心的唯一证据）：

- X9 → `readonly-git-boundary.ts` 的 `segmentText` 不再拼回前导赋值：GIT_CONFIG_* 注入被放行，用例红
- X10 → `readonly-compound.ts` 的 `resolveGitRepoTrust` 检查置 false：`cd` 进异仓被放行，用例红
- X11 → 复合判定 `readOnly` 置 false：`cd && ls` 落确认，用例红
- X12 → `setPermissionMode` 不落事件：切了模式但轨迹查不到，用例红
- X13 → `declared.call(tool, input) === false` 改 `return false`：纯记账工具落确认，用例红

其中 X9 的变异点改过一次：最初变异 `isSafeEnvVarName` 后用例**仍然绿**（SURVIVED），
查清原因是 B1 有两层防御、对本用例「值里带空格」的命令形态实际起作用的是 git 边界层那一次复核。
换成边界层后变红。**如果只看「最终 5 killed」而不追查最初那次 SURVIVED，就会留下一个空心门禁。**
