# 子代理病态的造场景台架与量具（G0）

## 决定了什么

修子代理系统的三条曲线（轮次、重复读、报告完整性）之前，先有一把**能在旧二进制上复现病态、
在新二进制上看出差别**的量具，不等日常轨迹积累。台架全部在仓外 `~/Code/person/harness-bench/`
（本 PR 只有这份 Note）：

- **旧臂二进制冻结**：`bin-frozen/sid-code-14c1f0d4`，`--build-info --json` 自证 commit 与 `dirty:false`。
  批 1 的三个 PR（#906 / #907 / #908）都在它之后，所以它是「修之前」的样子。
- **量具 `bin/sa_metrics.py`**：读一个 SID_HOME，按子代理输出方案 §8.4 要的全部原始量
  （轮次、sidechain 轮次差、重复 read、峰值上下文、成本、撞 4096 次数、报告头、截断字数、总结轮 token、
  end_status）。每个指标在文件头写明取数源字段，改口径先改方案。
- **场景包 `bin/sa_build_tasks.py`**：S-A 是 11-16 四个会话 16 个 explore 子代理的**原题**
  （sidechain 首条 user 消息去掉 harness 追加的 `<system-reminder>` 后，与父侧 `sub_agent` 派发原文
  16/16 哈希一致），轮次最长的 4 道各 3 次；S-B 是 6 道「逐项带 file:line 的全量工具清单」长报告题
  + 2 道 `--agents` 注入的 `maxTurns=5` 自定义只读代理。
- **跑道 `bin/run.py`**：新增 `--tasks` / `--jobs` / `--sid-home`，题级 `repeat` / `add_dirs` /
  `extra_args` / `shared_cwd`，以及**派发哈希校验**——父会话里 `sub_agent` 的 prompt 必须逐字等于
  原文，对不上的样本作废重跑（实测 32 个样本里有 2 个被主代理改了标点）。

三个口径上踩出来的判据，都写进了脚本注释：

1. **隔离 home 必须抄迁移水位**。全新 `SID_CONFIG_DIR` 首启会跑「团队默认配置补全」，把模板里的
   `subAgentModels.default=deepseek-flash`、`quota.costLimit=100`、`fallbackModel` 写进 settings.json，
   子代理于是去请求一个隔离配置里不存在的模型（503 `model_not_found`，10 秒就「跑完」）。抄一份
   `state/migrations.json` 过去，水位记着这些键用户已表态过，配置才与真实 home 等价。每个样本跑完
   复查一次 settings.json，出现这些键就停整批。
2. **「两个报告头」要三个口径并用**：行首 `## 发现` ≥2、首行标题复读 ≥2、**续写接缝后 300 字内另起
   行首标题**。只数 `## 发现` 会漏掉两份草稿标题不同的重写（S-B 实测：首份断在「默认启用」后、没有
   `## 发现`，重写那份才有）。三条合起来在 4 个真实会话上恰好认出 §2.2 的那 5 个，另外 11 个零误报。
3. **`maxTurns` 代理的系统提示词要求详尽**。照抄内置 explore（含「保持输出简洁」）时，5 轮里每轮只并行
   1–2 个调用、强制总结轮只吐 2775–3789 token，撞不到 4096，复现不了 §4.1 第 1 条。改成「要求逐项列全、
   鼓励并行检索」的调研代理后，两道都正好 4096、断在半句。真实暴露面本就是用户自定义的代理，提示词由
   用户定，所以改提示词而不是改题面。

## 放弃了什么（以及为什么不选）

- **不等日常轨迹**。方案 §7.1 的理由：批次之间要能立刻对照，攒真实会话按天计，而且攒不出
  `maxTurns=5`、输出上限这些边角场景。
- **不写进仓库 `scripts/`**。台架要换冻结二进制、要落几十个 GB 的合成会话，与发布物无关；仓里只留这份
  Note 指路。
- **S-A 不重新编题**。用原题才能跟 §2.2 的数字直接比；自编题会把「病态是否复现」和「题变没变」混在一起。
- **不改子代理默认提示词来迁就台架**（第 3 条）。改的是台架里那个自定义代理的提示词，产品侧 explore
  一个字没动。
- **不复用真实 `~/.sid-code`**。§2.3 的 11-12 前基线里有一半是旧 harness-bench 合成会话，正是这么来的。

## 拿什么证明它生效了

**量具校准**（真实 4 个会话，`--sessions ... --quiet`）逐项复现 §2.2 的数字：重复读 `781 / 1088`
（71.8%）、sidechain 共缺 18 轮、5 个子代理两个报告头、最长 242 轮、6 个 ≥100 轮、18 次
`recover:max_tokens`。单个子代理成本 `0.03249` 对上文档的 `$0.033`（舍入差）。

**旧臂批次**（`--batch g0-old --sid-bin bin-frozen/sid-code-14c1f0d4 --sid-home homes/g0-old --jobs 4`，
32 样本）复现病态，且比真实会话更重：

- S-A explore（n=23）：轮次 p50/p90/max = **84 / 389 / 430**（真实 78.5 / 200 / 242）、**10 个 ≥100 轮**
  （真实 6）、重复读 **78.1%**（1849 / 2368，真实 71.8%），单个子代理最多 48 次 `recover:max_tokens`、
  峰值上下文 30.7%，成本 p50/p95 = 0.1896 / 0.8498。
- S-B：3 次「两个报告头」；`maxTurns=5` 的两道里 1 道总结轮撞满 4096、断在半句
  （`需读 checkPermissions / validateInput / isReadOnly;`）。
- 最极端的三个样本撞了题级 3600s 墙钟：子代理各跑 **1144 / 1080 / 1119 轮**，重复读
  **96.6% / 95.3% / 96.7%**，同一个文件被反复读 90 多次，一小时不收敛，`SubagentStop` 从未落盘——
  方案 §4.0「子代理没有轮次上限」的极端形态。其中 `SB-opencode` **同一道题跑三次全都不收敛**
  （第二轮在 660 轮时随 `run.py` 进程树一起消失），所以这不是单次采样的偶然。这正是给 `run.py`
  加「超时后按时间窗 + 题面哈希 + 代理类型反查 session_id」兜底的理由：重跑只会再超时一次，
  不捞回来这类样本就永远拿不到数据。
- `ToolResultCleared{stage:stale_clear}` 全批次 381 条，没有一条带 `agent_id`（字段只有 `stage` /
  `cleared` / `saved_chars` / `tool_use_ids` / `ts`）——方案 O1「清理事件不归因到子代理」，修复前恒 0。

判读规则（§7.1.3 三条）开跑前写死在 `bin/sa_g0_judge.py`，结果与逐子代理明细落
`results-g0-old/g0-judge.json`：**终判 `verdict: true`，31 / 32 个样本有效**（唯一作废的
`SA-ayz5g1bqj` 两次重跑派发出的题面字节完全相同——只把一个 `？` 改成 `。`，是确定性改写，
所以永久作废，而不是放宽哈希校验去凑样本数）。详细记录在方案文档 §8.6。

**反查兜底本身有两个坑，第一次用对、重跑之后才暴露**（两个都静默返回 `None` → 样本被二次作废）：
① 时间窗用文件 mtime 且无上界，同一道题重跑三次后三个同哈希会话一起命中，`uniq` 退化成 `None`；
改成只认会话 id 自带的 `hhmmss`。② `samples.jsonl` 的 `start` / `end` 是带 `+00:00` 的 **UTC**，
而会话 id 里的 `hhmmss` 是**本地时间**（`08:46Z` ↔ `164655`），`time.strptime` 解 ISO 串会把偏移量
丢掉当本地时间，UTC+8 上整整错 8 小时。第 ② 条是「拿手写的时间串测全绿、拿 `samples.jsonl` 真实
记录测才红」——**验时间相关的修复必须用真实落盘记录当输入**。变异自证：换回修复前那版，三个时间窗
全部返回 `None`。另外 `run.py` 启动即把源码载入内存，批次跑到一半改脚本对在跑的进程无效，所以补记
走离线的 `bin/sa_fix_timeout_record.py`（只写记账行、不碰轨迹，派发哈希对不上就拒绝）。
