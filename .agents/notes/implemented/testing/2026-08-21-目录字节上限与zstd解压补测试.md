# 目录响应体字节上限（D8）与 zstd 解压路径补测试

`packages/core/src/llm/model-capabilities.ts` 里这两条防线都已实现，但全仓 `.test.ts` 对
`zstd` / `readBodyCapped` / `CATALOG_BODY_MAX_BYTES` **零命中**。按 CLAUDE.md「新增防线的验收
判据不是 build 过 + 单测过，而是真实会话里被触发过」，它们此前是纯声明 —— 上限被改成
`Infinity`、流式循环退回 `arrayBuffer()`、zstd 分支被摘掉，三种情况下全仓测试都是绿的。

## 决定了什么

**8 条用例加进已有文件 `packages/core/tests/llm/model-capabilities-catalog-strategy.test.ts`，
不新建文件。** 该文件已有整套假 fetch 设施与落盘隔离（`:31-63`：`SID_CONFIG_DIR` 指临时目录 +
`__resetCapabilityCacheForTest`），新建文件等于把这套隔离再抄一遍 —— 而抄错的后果是往用户真实
`~/.sid-code/model-capabilities.json` 灌假数据（`model-capabilities.ts:382-385` 记录的那次事故：
2919 条真实数据被抹成 1 条）。

**两个 describe，覆盖三条判据的每一支：**

- **D8 字节上限**（4 条）：`content-length` 声明超限那一支 / 实际流式累加超限那一支
  （`content-length` 缺失 + `content-length` 撒谎报小，两种形态各一条）/ 正常体积正向对照。
- **zstd 解压**（4 条）：真实 `Bun.zstdCompressSync` 压缩体解压成功 / 未压缩明文当 zstd 读 /
  随机坏字节 / `accept` 头是 `*/*` 而非 `application/json`。

**关键设计：超限用例的判据是「上游流被提前中断」，不是「该源被丢弃」。**
这是本次唯一有技术含量的决定，理由见下一节。断言的是 `ReadableStream` 的 `pull` 被拉取次数
落在 `[9, 10]`（远小于声称的 40）且 `cancel()` 回调被调用到。

**不真的分配 32MiB。** 同一个 `Uint8Array` 实例反复 `enqueue`，「160MiB 的流」实际常驻内存
只有 1 个 chunk（实测 rss 增量 2.3MiB）。被测对象是计数与中断逻辑，不是运行时能不能扛住 160MiB。

**生产代码零改动。** 没有发现真 bug；`git diff -- packages/core/src` 为空。

## 放弃了什么（以及为什么不选）

**放弃只断言「超限时该源被丢弃 / 不抛异常」。这是本次最重要的否决，因为它是一个 false gate。**
「超限 → 丢弃」这个结果在流式实现和「先 `arrayBuffer()` 全收进内存再检查」的实现下**都成立**。
实测证据：把 `readBodyCapped` 的流式循环换成 `new Uint8Array(await resp.arrayBuffer())` 之后，
同一个用例里 `r.failed.length === 4` 这条断言**照样通过** —— 唯一红掉的是 `pulled <= 10`
（实测收到 `40`，即整条流被拉干）。只写「被丢弃」等于给「限额白设」发一张绿卡。

**放弃真造一个 32MiB+ 的 buffer 来触发上限。** 它能过，但慢、吃内存，而且**证明力更弱** ——
`arrayBuffer()` 版本同样会在读完之后抛出，一个真 32MiB 的 fixture 分不清两者。
「流被提前 cancel」才是流式限额的**唯一**可观测差异。

**放弃把 `CATALOG_BODY_MAX_BYTES` 从生产代码 export 出来给测试用。**
测试里镜像一份 `32 * 1024 * 1024`：测试要能独立于实现声明「门应该在哪」。
export 生产常量会让「有人把它改成 `Infinity`」这类变异连测试期望值一起改掉。

**放弃用「压缩后比原文小」当 zstd fixture 的前提自证。** 实测这条是**假的**：87 字节的
fixture 压完是 89 字节（zstd 帧头开销）。第一版就是这么写的，直接红了。改成断言 magic bytes
`28 b5 2f fd` —— 那才是「这确实是一个 zstd 帧」的判据，且与载荷大小无关。

**放弃把「流式拉取次数」写成等值断言。** 第一版写 `toBe(9)`（32MiB ÷ 4MiB + 1），实测经
`fetch` + `await` 链路是 **10**：`ReadableStream` 默认 `highWaterMark = 1`，会在我们处理当前
chunk 时预拉一个。这一格差异属于队列预拉、不属于限额逻辑，写死等值只会得到一条脆断言。
改成区间 `[9, 10]` —— 上界 10 仍然远小于 40，区分「中断」与「读干」的能力一点没损失。

**放弃给 zstd 坏数据用例喂「明显不是 JSON 的垃圾」当唯一形态。** 单独一条随机坏字节用例
证明力不足：摘掉 zstd 分支后，垃圾字节走 `JSON.parse` 也会抛，测试照样绿。所以补了
「未压缩的**合法** models.dev JSON」那一条 —— 摘掉分支它会被成功解析、条目进缓存，
于是 `expect(lookupCapability("zstd-plaintext-model")).toBeNull()` 变成解压分支存在的正面判据。

## 拿什么证明它生效了

**变异自证（CLAUDE.md：防线的验收判据是真被触发过）。** 逐个把生产代码改坏、跑一次、改回来。
全程 `cp` 保留原文件，最后 `git diff -- packages/core/src` 验证为空：

| 变异 | 结果 | 被哪条断言抓到 |
| --- | --- | --- |
| ① `CATALOG_BODY_MAX_BYTES = Infinity` | **2 fail** | 声明超限那条（`failed.length` 4→0）+ 流式超限那条 |
| ② 流式循环退回 `new Uint8Array(await resp.arrayBuffer())` | **1 fail** | `pulled <= 10`，实收 **40**（整条流被拉干、`cancelled` 为 false） |
| ③ 摘掉 zstd 分支（`body` 直接当纯文本解析） | **2 fail** | 解压成功那条 + 明文当 zstd 那条 |
| ④ `accept` 恒为 `application/json` | **1 fail** | `accept` 头逐源对照那条 |

⚠ **变异 ② 是这次的重点**，也是最容易写成 false gate 的地方：同一个用例里
`r.failed.length === 4`（「该源被丢弃」）在变异 ② 下**仍然通过**，只有
`pulled <= 10` 红了。这条已写进测试注释，防止下一个人把它「简化」掉。

**落盘隔离实证**（不是「机理上讲得通」）：跑测试前后 `stat` 用户真实缓存文件，
mtime 均为 `Aug 21 10:03:01 2026`、大小 1514012 字节不变；
`packages/core/tests/telemetry/no-real-path-writes.test.ts` 4 pass / 0 fail。

**门禁**（worktree 内已跑过 `bun install`）：

                             16 pass / 0 fail / 72 expect（原 8 条 + 新增 8 条）

**这次的 trade-off（自检第 3 问）**：纯粹加测试，不牺牲任何方向 —— 服务的是「更准」里的
「③ eval / 回归套件」那一层，以及「更安全」的「防线触发率」（把两条 0% 触发的防线变成
真被触发过）。成本是新增约 250 行测试代码与约 0.14s 的选测耗时。
