# P4 长会话内存：同测内串行起两套底座比峰值 RSS 与堆增长斜率（B9 / T8.1c）

## 决定了什么

契约 P4（长会话 RSS 不高于旧底座 1.2 倍）原来挂着「⏳ T8.1」，现在落成 `packages/cli/tests/render-port/rss.test.ts`。
夹具 `fixtures/rss-app.tsx` 把 500 条带样式的多行历史（每条 6 行，含中文）分 20 批灌进 Static，底部动态区每批改一次。
两个判据都要 ≤ 1.2：

- 峰值 RSS 比值（GC 后采样）；
- 堆增长斜率比值 `(heapUsed(500) − heapUsed(0))`：排除固定开销，只看每多一条历史多占多少。

测试自己串行起 legacy 0 / 500、next 0 / 500 四个子进程，不看 `SID_TUI_RENDERER`。

## 放弃了什么（以及为什么不选）

- **两套底座各跑一次、和入库基线比**：同底座跑 3 次，峰值能差 ±7MB，跨机器更大。比值必须同机同时刻采样。
- **n 取 250**：实测 250 条时峰值比值到过 1.20–1.21。原因是 next 的堆有一块约 32MB 的固定开销，0 条时就在、
  不随历史增长（heap 4.6MB vs 36.4MB，很可能是 yoga WASM 线性内存）。历史越短，这块占比越大。
  P4 说的是「长会话」，所以取 500；斜率判据另外把这块排除掉。
- **把阈值做细去抓小泄漏**：见下面的灵敏度。要抓几 MB 级的泄漏，得换成逐帧长跑或堆快照对比，代价是测试变成分钟级，这次不做。

## 拿什么证明它生效了

- 实测峰值 RSS（MB，legacy / next）：100 条 120 / 128，500 条 214–225 / 231–233（比值 1.04–1.09），1000 条 340–352 / 367–384（1.04–1.13）。
  对象数 500 条 50.3 万 / 53.5 万，1000 条 97.1 万 / 103.8 万，两套底座都随历史线性增长，没有看到发散。
- 变异自证：next 的 `onRender` 每帧泄漏约 3MB（整段约 60MB）时**红**；每帧约 300KB（整段约 6MB）时**绿**。
  这条测试防的是「新底座整体多占几十 MB」，不防小泄漏，限制已写进测试头注释和 SPEC。
- `tui:spec`：SPEC 64 条全部有测试（P1 / P4 是最后两条）。
