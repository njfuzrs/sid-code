# G2 用例 A3（PreToolUse hook 拦截）与 A13（团队记忆注入），运行器补 `requests` 与 `repoRoot`

## 决定了什么

质量防线分层专项 M3 的前两条台账落成 G2 用例（tracking issue #618）：

- `A3-pre-tool-use-deny`：项目级 PreToolUse hook（`matcher: "Bash"`）命中 `grep -q 'rm '` 时 `exit 2`。hook 命令、两次 bash 调用的形态都原样取自人工实测会话 `20261105-195723-9bfc240f`。断言四条：未命中那次 `HookExecuted{outcome=success, exit_code=0}`；命中那次 `HookExecuted{outcome=blocking, exit_code=2, decision=deny}`；`PostToolUseFailure.error_head` 逐字等于录制里回灌给模型的拒绝文本；`trash.txt` 内容不变。
- `A13-team-memory-injected`：共享目录里预置一条团队记忆，本地没有 `team-memory/`，即触发清单 A13 的「跨成员」那一步（`20261105-194229-08940a79`）。断言首轮请求的 system 恰好含 1 次「### 团队共享记忆索引（团队 MEMORY.md）」，且段内有对应索引行和摘要前段。一次进程同时守住两段接线：启动期从共享目录拉取，以及本地索引注入 system。

运行器改了两处，都只为这两条用例：

- `RunOutput.requests`：`raw.jsonl` 里各请求的 `request` 字段，按发出顺序排列（`parseRawRequests`）。A13 的判据在 system 上，不在 events 上。
- `SettingsContext.repoRoot`：`teamMemory.dir` 的 schema 要求绝对路径，而用例仓是运行时 `mkdtemp` 出来的。共享目录放在用例仓里，随临时目录一起回收。

## 放弃了什么（以及为什么不选）

- **A13 用「同会话先 save_memory 再问」**：不选。注入是启动期的一次性快照，存记忆的那个会话首轮命中 0（人工实测），要两次进程才能演示，运行器得支持多步用例，成本不值。跨成员那一步一次进程就能覆盖拉取和注入。
- **A13 给团队记忆补一个专门的轨迹事件，再用 events 断言**：不在本 PR 做。这是改产品埋点，不属于写用例。台账已注明 G2 只能证明最终序列化结果。
- **A3 用 `exit 1` 构造反例**：不单独建用例。`exit 1` 是非阻塞告警，第一条变异（`EXIT_BLOCKING` 分支失效）已经覆盖「退出码语义被改」这一类。

## 拿什么证明它生效了

- `make build && bun run smoke`：6 例全部通过（A2/A3/A7/A8/A9/A13），A3 用时 0.4s，A13 用时 0.3s。
- `bun run smoke:mutate -- A3-pre-tool-use-deny`：2/2 killed。`runner.ts` 的 `EXIT_BLOCKING` 分支被改成 `if (false)` 后，blocking 事件剩 0 条。`interpretPreToolUse` 的 `isBlockingDecision()` 失效后，`PostToolUseFailure` 剩 0 条。
- `bun run smoke:mutate -- A13-team-memory-injected`：2/2 killed。`prompt.ts` 不拼团队段，或 `watcher.ts` 启动期不调 `syncTeamMemory`，团队段命中数都变成 0。
- `parseRawRequests` 的单测做了变异自证：把过滤条件改成 `if (obj)` 后变红（14 pass / 1 fail），还原后 15 pass。
- 写用例前用真二进制在隔离目录探针确认过：replay provider 下 `raw.jsonl` 照常落 `request.system`（字符串），共享目录中的条目会被拉进 `config/projects/<slug>/team-memory/`，团队段命中 1。
