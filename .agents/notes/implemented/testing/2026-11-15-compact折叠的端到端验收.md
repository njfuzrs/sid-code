# compact 折叠用 PTY e2e 验收，替代等不到的人工手测

## 决定了什么

方案 §4.3 的唯一未完成项是「用 `sc-dev` 跑连续读十几个文件 + 几条 bash，确认每条一行、
ctrl+o 能看到原文、失败命令正文照常显示」。这条自 2026-11-13 起挂了三天，理由是「需要人在
真实终端里手点」。**它不是数据缺失，而是验收手段选错了**：三项判据都是键盘/屏幕层面的
确定性事实，可以自动化。

新增 `packages/cli/tests/render-port/compact-fold-e2e.test.ts`（PTY 里起 `bootstrap.ts` +
脚本化 mock 模型，10.3s）：

- 临时目录造 12 个 20 行文件（首行埋 `MARKER-FILE-N-CONTENT`）+ 一条成功多行 bash +
  一条非零退出 bash，不依赖真实仓库内容、不调真实模型；
- 折叠态断言：12 条 `read` 卡片各占一行且带「N 行」规模摘要、12 个 marker 一个都不出现、
  成功 bash 的输出正文不出现、失败 bash 的正文可见；
- `ctrl+o`（真实 `\x0f` 按键，不是直接设 `expandLevel`）后断言 12 个 marker 全部可见。

顺带修两处与代码不一致的陈述：官网折叠说明补齐 8 个 compact 工具与 5/1 视觉行阈值
（`website/use/troubleshooting.md`）；`result-display-mode.ts` 的「两个执行器」注释
指向 `query/run-tool-use.ts`（子代理已复用它，`agent/tool-executor.ts` 只做调度）。

## 放弃了什么（以及为什么不选）

- **继续等人工手测**：判据是确定性的，等下去只会在「验收没做」和「文档已 done」之间
  长期挂着。用户明确要求「等不到数据就自己造数据」——这里的正解是把场景**造**出来。
- **写进 `main-screen-shrink-e2e.test.ts`**：那个文件的门禁职责是「整帧重画次数 + 空白块」，
  加折叠断言会让一条 e2e 同时守两类不变量，红了难归因，也容易为了迁就一方放宽另一方。
- **只加整帧渲染测试（`ToolMessage-compact.test.tsx`）**：它直接构造 `expandLevel`，绕过了
  真实按键链路与主循环的档位解析。`ctrl+o` 键位失效、执行器漏传 `result` 这类缺陷
  它永远看不见——这正是 §4.3 要人工点一遍的原因。
- **用 `tests/smoke/` 的 G2 回放**：G2 的定位是「给定模型响应后行为确定」，但它不重放
  终端字节，「卡片占几行」这种屏幕事实只有 PTY + xterm 重放能断言。

## 拿什么证明它生效了

```
$ env -u TERM_PROGRAM ... TERM=xterm-256color bun test ./packages/cli/tests/render-port/compact-fold-e2e.test.ts
[compact-e2e] read 卡片行：⏺ read FILE_1 — 21 行 … ⏺ read FILE_12 — 21 行（12 条）
(pass) 12 个 read + 成功/失败 bash：每条一行、ctrl+o 见原文、失败正文可见 [10343.17ms]
 1 pass / 0 fail / 6 expect() calls
```

真实画面（折叠态）确认了三条判据同时成立：

```
⏺ read FILE_1 — 21 行
…
⏺ bash for i in 1 2 3 4 5 6; do echo OK-BASH-LINE-$i; done — 6 行输出
⏺ bash
  $ echo 'FAIL-BASH-正文必须可见' >&2; exit 1
  ⎿ 命令执行失败（退出码 1）:
    FAIL-BASH-正文必须可见
```

`ctrl+o` 之后 `[compact-e2e] 展开态可见 marker 数 12`（折叠态的对应数字是 0）。

门禁：`affected-tests:run` 8220 pass / 0 fail（651 文件）、`make build` 通过、
`docs:gen-reference --check` 与源码一致、`lint` 0 警告、`typecheck:gate` 无新增错误。
