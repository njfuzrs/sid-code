# 启动门禁等维护子进程改用结果文件做完成信号，不再猜锁

## 决定了什么

`packages/cli/tests/startup/large-data-startup-gate.test.ts` 的 `waitMaintenanceIdle` 换完成信号：

- 旧：`sleep(500)` 后判一次 `state/maintenance.lock` 是否存在，存在就轮询到消失。
- 新：`resetUploadState` 每轮先删 `state/maintenance-result.json`，等它重新出现
  （子进程在 `finally` 里写，`core/maintenance/runner.ts`），再补等锁释放。

顺带给「补传不在主线程」那条断言加了单次值诊断输出（`emptyRuns` / `uploadRuns`）——
中位数会掩盖方差，红的时候要能看出是单次离群还是整组偏移。

## 放弃了什么（以及为什么不选）

- **不放宽 150ms 阈值**：变异形态（补传回到主线程 `gzipSync` 200MB）是 3 秒级阻塞，
  阈值对它有 20 倍余量；抬高阈值会把真回归一起放过去，而且每换一个更慢的 runner
  就要再调一次数字，没有终点。
- **不按平台给不同阈值**：同上，治标且不可迁移。
- **不改成「同 fixture 但关闭上传」的对照组**：那能控制变量（两组都有 200MB traj），
  但要多 3 次 TUI 启动，而 beforeAll 已经有 400s 预算、这套 fixture 在 CI 上跑得并不快。
  先把确定性缺陷修掉，仍红再考虑这条路。
- **不删这条断言**：它是「补传迁入维护子进程」（commit a54d54a4）唯一的回归防护。

## 拿什么证明它生效了

- 修复前的失败形态（CI，同一断言）：
  - main `41648991106` / `test (macos-latest, 2/2)`：`Δframe=224.6 Δblock=78`
  - PR #561 `41656662520` / `test (macos-latest, 1/2)`：`Δframe=351.2 Δblock=94`
  - 两次都是 `Δframe` 超 150 而 `Δblock` 未超 100 —— 主线程没有被阻塞，
    问题在等待不可靠、测量被上一轮 200MB 压缩污染。
- 本机基线（修复前同一份代码）：`[gate] upload first_frame=469.9 max_block=107 | Δframe=28.6 Δblock=-1`，
  7 pass 0 fail —— 说明结构上没有问题，是慢 runner 才暴露的竞态。
- 修复后本机：`[gate] upload first_frame=461.6 max_block=109 | Δframe=-136.6 Δblock=-35`，
  7 pass 0 fail（`Δframe` 为负是因为 empty 组本轮自己抖到 598ms，正说明单次噪声方向不定）。
- 变异自证（门禁仍拦得住「补传回到主线程」）：在首帧前对 trace-upload 组
  `await Bun.sleep(3000)`，结果

  ```
  [gate] upload first_frame=3455.7 max_block=93 | Δframe=2972 Δblock=-23
  error: first_frame 空=[450 / 484 / 623] 上传=[3456 / 3477 / 3454]（中位数差 2972ms）
  Expected: < 150 / Received: 2972
  ```

  6 pass 1 fail —— 门禁按预期变红，且新加的诊断能直接看出是整组偏移。
  ⚠️ 第一次变异试的是「首帧前 gzipSync 200MB traj」，`Δframe` 只有 130ms / 75.6ms，
  **没让门禁变红**：本机 gzip 200MB 的实际耗时远小于秒级，那种变异强度不足以代表
  「补传回主线程」的真实形态。要做变异就用 `sleep` 这种确定性的阻塞。
- 尚未验证的部分（如实记录）：本机跑不出 CI 慢 runner 的竞态，**修复是否消除 macOS CI
  的假阳性要由这个 PR 的 CI 结果回答**。若仍红，下一步按 Note 里「放弃了什么」的第三条
  改成「同 fixture 但关闭上传」的对照组。
