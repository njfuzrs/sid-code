# 启动门禁：macOS 计时断言降级为只报告，补一条结构性门禁

## 决定了什么

`packages/cli/tests/startup/large-data-startup-gate.test.ts` 的四处计时断言（首帧差值、
事件循环阻塞差值、补传首帧、补传阻塞）改为**按平台分档**：`process.platform === "darwin"`
时只打一行 `[gate:report-only]`（带逐轮原始值，不调 `expect`），ubuntu / 本机仍按
150ms / 100ms 阻断。删掉原来 macOS 的 300ms 档与两条「阈值按平台分档」断言，换成
`timingAssertionsBlocking(platform)`，并加一条平台分支断言把两个方向都锁住
（darwin 必须只报告、非 darwin 必须阻断）。

同时新增一条**结构性门禁**「首帧前主进程没调用维护任务入口」，两个平台都阻断，
判据是确定性的 0 而不是阈值：

- `packages/shared/src/utils/startup-profiler.ts` 新增 `profileCounter(name)`：只在
  `SID_CODE_PROFILE_STARTUP=1` 时累加，`first_frame` checkpoint 之后停止累加；
  dump 新增 `counters` 字段，是门禁的取数源。
- 四个入口打点：`cleanupExpiredSessions`（`session/cleanup.ts`）、
  `pruneOldTraceSessions` / `pruneStaleBlankTraceSessions`（`trace/startup-prune.ts`）、
  `prepareUploadFile`（`trace/upload-compress.ts`）。正常启动这三类工作都由维护子进程跑，
  TUI 主进程首帧前对它们的调用次数必须是 0。

## 放弃了什么（以及为什么不选）

1. **继续放宽 macOS 阈值**。已经放宽两次（首帧 150→300、阻塞 100→300），放宽后的实测
   中位数仍有 322~871ms，高于已知真实回归 C1 的 +698ms；再放宽就检不出已知回归，
   门禁只剩「看起来在拦」。
2. **增加轮数（RUNS 3 → 7+）**。每轮起 3 次带 200MB fixture 的 TUI，beforeAll 已占
   400s 预算；且噪声来自共享 runner 负载、本身不平稳，多轮只是摊薄概率，不保证收敛。
3. **失败自动重试**。会把真实回归一起吞掉，还会让「这条门禁到底多稳」不可见。
4. **整条门禁移出 PR 必需检查改 nightly**。ubuntu 侧是有效的阻断门禁，没必要一起降级；
   macOS 降级为只报告后，剩余成本只是「跑一次」。
5. **新增统一 fs 封装层来数首帧前的 stat / readdir / 读字节数**（方案首选的实现方式）。
   实测 `~/.sid-code/` 的数据目录 IO 分散在 session / trace 各模块、各自直接
   `import "node:fs"`，没有可挂的统一封装层；新造一层要改十几个模块的热路径，还会让
   「数 IO」本身成为新的可漂移契约。退而求其次数入口调用次数：判据同样确定性，
   侵入面只有 4 个入口各一行，且 `profileCounter` 在非 profiling 场景是一次布尔判断。

## 拿什么证明它生效了

**基线（未变异）**：`bun test ./packages/cli/tests/startup/large-data-startup-gate.test.ts`
`9 pass / 0 fail`；结构性门禁通过，三种配置每一轮的 `counters` 都是 `{}`；report-only
输出可 grep：

```text
[gate:report-only] 首帧(大−空)：10.599999999999966ms（阈值 150ms，macOS 不阻断）；逐轮 Δframe=[46 / 3 / 11]；first_frame 空=[517 / 435 / 433] 大=[563 / 438 / 443]
```

**变异自证**（每条都是「改坏 → 看到红 → 恢复」，报的是计数而不是耗时）：

| 变异 | 门禁输出 |
| --- | --- |
| C1：`cleanupExpiredSessions` 放回 `initTraceCollector`（首帧前） | `error: 首帧前调用了维护任务入口（空 目录第 0 轮）：{"session-cleanup":1}` |
| T1/T2：`pruneOldTraceSessions` + `pruneStaleBlankTraceSessions` 放回首帧前 | `{"trace-prune":1,"trace-prune-stale":1}` |
| U1–U4：`prepareUploadFile` 放回首帧前 | `{"trace-upload-compress":1}` |
| 平台分支改坏（darwin 也阻断） | `计时断言按平台分档` 红：Expected false / Received true |
| 平台分支改坏（ubuntu 也只报告） | 同上红：Expected true / Received false |
| ubuntu 侧能力（强制 `TIMING_BLOCKING=true` + C1 变异） | `首帧` 红 `Expected: < 150 / Received: 907.4999…`；`事件循环最大阻塞` 红 `Expected: < 100 / Received: 723` |

最后一条同时回答「降级 macOS 有没有把 ubuntu 的检出能力一起削掉」：没有，同一变异在
阻断分支下照红。

**T1/T2 变异第一次没有红**，原因是变异代码走了 `if (config.trace.outputDir)` 判空——
`TraceConfig.outputDir` 是可选项、默认配置只有 `{ enabled: true }`，所以变异体根本没执行。
改用 `sidPaths.trajectories()` 兜底后红。这条记下来是为了说明「门禁绿」必须先确认
变异体真的被执行过，否则是一次假绿。

**macOS 上真实抖动的量级**（同一份代码、git 未改动的基线跑）本机是 Δframe 3~48ms；
CI 上是 322~871ms。说明降级只针对共享 runner，不是把本机也一起放过。
