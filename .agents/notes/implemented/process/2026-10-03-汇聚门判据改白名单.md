# `all-checks-passed` 判据从 failure/cancelled 黑名单改成 success/skipped 白名单

## 决定了什么

`ci.yml` 汇聚 job 的 Verdict 改为：用 `toJSON(needs)` 读全部上游结果，`jq -e 'all(.[]; .result == "success" or .result == "skipped")'`，
不满足即 `exit 1`。`tests/release-flow-contract.test.ts` 把这条 jq 表达式从 workflow 里抽出来，
喂 success / skipped / failure / cancelled / abandoned / 未知取值六种 needs 真跑一遍；`CONTRIBUTING.md` 补一段为什么不许改回黑名单。

**起因（实测）**：PR #148 run 37016782507，macOS runner 容量不足，job「not acquired by Runner」被放弃（steps 为空），
`needs.test.result = abandoned`。旧判据只排除 `failure` / `cancelled`，日志打出 `test=abandoned` 后紧跟「✅ 全部检查通过」，
汇聚门绿、auto-merge 已挂上 —— macOS 一条测试没跑就差点合进 main。

## 放弃了什么（以及为什么不选）

- **在黑名单里补一个 `abandoned`**：只堵已知的那一个值。needs 结果的取值集合不是我们定义的，下一次 GitHub 冒出新值
  还是同样的静默放行。白名单对没见过的值默认拒绝（fail-closed），这是门禁该有的方向。
- **判据改成「全部 == success」**：会把带 `if` 条件被跳过的 job 判成失败，整道门禁卡死 —— 这是原注释 ③ 防的事，`skipped` 必须留在白名单里。
- **继续用 `${{ needs.test.result }}` 逐个点名拼 bash**：新增 job 时要同时改两处，点名漏一个就没人看它的结论。`toJSON(needs)` 自动覆盖 needs 列表。

代价：macOS runner 排不上队时 PR 会红而不是绿，需要人 `gh run rerun --failed`。这是用「更快」换「更安全」，
而换来的正是这道门禁存在的意义 —— 没跑过的测试不能算过。

## 拿什么证明它生效了

- `bun test ./tests/release-flow-contract.test.ts`：68 pass。
- **变异自证**：把判据临时改回黑名单（`.result != "failure" and .result != "cancelled"`）→ `abandoned` 与 `some_future_value` 两条用例变红（2 fail）；恢复 → 68 pass。
- 线上验证留给本 PR 自己的 CI：如果 macOS 再次未被领取，汇聚门应当是红的。
