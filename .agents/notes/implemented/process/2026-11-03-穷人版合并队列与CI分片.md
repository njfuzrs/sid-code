# 个人仓开不了合并队列：用「只更新队首」的 workflow 加 CI 分片顶上

## 决定了什么

两件事放在一个 PR 里，关注点都是「strict 下合并串行化太慢」：

1. **`.github/workflows/pr-auto-update.yml` + `scripts/pr-auto-update.ts`**：在 push main、CI 完成和每 15 分钟时触发，每次只给**一个** PR 做 `gh pr update-branch`。这个 PR 要挂了 auto-merge、处于 BEHIND、检查没红，并且是 auto-merge `enabledAt` 最早的那个。已有 PR 在飞（CLEAN 待合，或 BLOCKED 且检查 pending）时什么都不做。合并本身仍交给 auto-merge 和 ruleset 判定，脚本没有绕过分支保护的路径。
2. **`ci.yml` 的 test job 分片**：用 `bun test --shard=k/N` 拆成 ubuntu 3 片、macOS 2 片，两个平台都仍跑全量。`all-checks-passed` 的 needs 不用改，矩阵展开后仍是 `test` 这一个 job id。

起因（2026-11-03 实测）：一天合入 15 个 PR。全量单测占 test job 的 97%（macOS 547s / ubuntu 506s）。auto-merge 遇到 BEHIND 不会自己 update，开着的 9 个 PR 里有 2 个 BEHIND 挂着等人点。

3. **分片暴露的测试串扰，顺手修掉**：`packages/tui/tests/render-cache.test.tsx` 的 P3 断言读的是进程级全局计数 `renderStats.walked`。分片后它和 `cli/tests/ui/components/{LoadingIndicator,TodoPanel,CoreRendering}` 落在同一片（macOS 1/2）。那几个文件 render 后不 unmount，带 setInterval 动画的实例会一直出帧，被算进计数，导致 n=200 时每帧 7.8～13.3（上限 3），CI 两次 attempt 都稳定变红。修法是给 `renderStats` 加按根节点分账的 `byRoot`（在 `renderer.ts` 写入），断言改读本实例的根节点。

4. **第二处串扰**：`packages/core/tests/query/stall-escalation-loop.test.ts` 依赖进程级任务注册表为空。L2 判据会排除「在等后台任务」的轮次，前面的文件如果留下运行中的任务，L1/L2 就永远不触发。修法是在顶层 `beforeEach` 里补 `clearAllTasks()`。

分片的隐性代价因此值得记一笔：**同进程里的文件组合变了，原本被执行顺序掩盖的共享状态泄漏会冒出来**。这次冒出 2 处，以后调整分片数还可能再冒。处置原则是修测试隔离，不是退回不分片。

5. **PAT 放进 Environment，不放仓库级**：仓库有 write 协作者。同仓分支触发的 workflow 能读仓库级 secret，协作者推一个分支、写个 workflow 就能拿走这个 PAT：之后的操作记录显示为 owner，把人移出仓库后令牌照样能用。job 改为 `environment: {name: pr-auto-update, deployment: false}`，Environment 只允许 main 使用。PAT 权限补上 Workflows，因为 update-branch 要把 main 合进 PR 分支，main 动过 `.github/workflows/` 时没有这个权限会被拒。

## 放弃了什么（以及为什么不选）

- **secret 放仓库级**：理由见上面第 5 点。残余风险是 approvals=0：write 协作者可以自己开 PR 改这个 workflow、自己合进 main，之后就能读到 secret。要堵住需要对 `.github/` 强制 code owner 审批，这是协作规则的取舍，留给维护者决定，本 PR 不动 ruleset。
- **转到 organization 开真合并队列**：这是根治方案，但会改仓库 URL、secrets、镜像和 release 里的 owner，上次迁账号时仓库设置漂移过 4 项。属于不可逆的高风险操作，留给维护者单独决定。`ci.yml` 里的 `merge_group` 预置照旧保留。
- **关掉 strict**：合并前就没有「最新 main + 本 PR」的验证了，语义冲突只能在 main 上发现。在当天的 PR 频率下，main 已经出现过红的 push run。
- **一次 update 全部 BEHIND**：只有第一个能合，其余 N-1 轮 CI 全部白跑。
- **用 GITHUB_TOKEN 做 update**：按 GitHub 文档，GITHUB_TOKEN 触发的 `pull_request synchronize` run 会进入需要批准的状态，队列照样卡在等人。所以改用 fine-grained PAT。
- **检查红了就停住整个队列**（`pr-merge-chain.sh` 的失败即停语义）：那个脚本处理的是一批可能互相依赖的 PR；这里排的是彼此独立的 PR，一个红了不该卡死全仓。
- **PR 上不跑 macOS**：省得最多，但牺牲了「更安全」，macOS 特有问题会变成合入后才发现。分片能拿到大部分收益，又不丢覆盖面。
- **macOS 也分 3 片**：Free 档 macOS 并发上限是 5，而且是账户级共享。auto-update 会让 push main 的 run 和队首 PR 的 run 几乎总是同时在跑，3 × 2 = 6 会排队。

牺牲点：分片多占 runner（每个 run 从 2 个 test job 变成 5 个，公共仓库免费），每片多付约 15s 的启动开销。

## 拿什么证明它生效了

- 本机分片全绿：4 片顺序跑时，shard 1/4 有 2 条计时类用例失败（bash 超时、render-cache n=2000），单跑同两个文件是 `43 pass / 0 fail`，属于本机负载 flake。3 片顺序跑结果见 PR 正文。
- 实际 dry-run：`bun scripts/pr-auto-update.ts --dry-run` 在当时的真实 PR 列表上输出「等待 #551: 已与 main 同步，CI 进行中」，没有去 update 已 BEHIND 的 #555，串行判定正确。
- 变异自证（三处都确认变红后才恢复）：
  - 删掉 macOS 第 2 片 → `test 分片覆盖完整` 红；
  - 命令里混入 `--test-name-pattern` → `ci.yml 用裸 bun test` 红；
  - 去掉「BLOCKED+pending 视为在飞」→ `① 有 PR 已同步 main 且 CI 在跑 → 等待` 红。
- 串扰定位：逐个文件与 render-cache 同进程跑，命中上述 3 个文件。修后 4 个文件同跑结果为 `48 pass / 0 fail`。变异自证：去掉缓存命中条件 `!node.renderDirty` 后，断言变红为 `n=200 Received: 603`；恢复后 `packages/tui/tests/` 为 977 pass。
- stall-escalation：修前本地 `bun test --shard=1/2` 稳定红 5 条，CI 上也是同样 5 条；修后同一命令 `exit=0`；单跑该文件修前修后都是 14 pass。
- 分片**没修**的已知 flake：`large-data-startup-gate` 的「首帧慢不超过 150ms」在 main 上同日已红 6 次，与分片无关，不在本 PR 范围。
- **待合入后验收**（端到端真实指标，代理指标不算数）：
  - 看 PR 的 test 关键路径是否从约 10min 降到约 5min；
  - 看 BEHIND 且挂了 auto-merge 的 PR 是否不再需要人手动 update；
  - 取数用 `gh run list --workflow ci.yml` 的 job 耗时，以及 `pr-auto-update` 的 run 日志。
