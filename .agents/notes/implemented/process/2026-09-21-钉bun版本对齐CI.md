# 钉 bun 1.4.2，消掉「本地 1.3 / CI latest」缝

## 决定了什么

阶段 0 出口是 **0A**：worktree 内独立 bun 1.4.2（不动本机全局 1.3.14）跑无参数
`bun test`，`12044 pass / 1 fail`。那 1 条是
`plan-mode-write-plan-file.test.ts` 相对路径拼到含 `.claude/` 的 cwd 上，
被 safetyCheck 抢先命中——已知环境假失败，不是 spawn 空 stdout。

于是按文档 1A 落地：

- 仓库根 `.bun-version` = `1.4.2`（与 2026-09-21 CI `oven-sh/setup-bun` latest 实测对齐）
- 6 处 workflow 的 `bun-version: latest` 全部改成 `bun-version-file: .bun-version`
- `package.json` `engines.bun` `>=1.0.0` → `>=1.4.2`
- `CONTRIBUTING.md` 不再写「开发用 1.3.x，CI 用 latest」
- 门禁：`tests/build/bun-version-pin.test.ts`（workflow 读文件、零 latest、空集自证 + YAML 解析）
- 探针：`tests/build/bun-test-spawn-stdio.test.ts`（spawn echo 标记；丢掉 stdout 必须红）
- 顺手把 plan-mode 那条相对路径改成显式 workspace 绝对路径，worktree 全量不再被 cwd 误伤

## 放弃了什么（以及为什么不选）

**1B：改 `make test` 避开无参数扫描** —— 否决。阶段 0 在 1.4.2 上无参数路径已经绿，
再改入口会让「刚 clone 敲 `bun test`」和「敲 `make test`」行为分叉，而 CI 注释写明
必须用裸 `bun test`。问题在 bun 版本，不在入口。

**继续 `bun-version: latest`** —— 否决。这正是本地 1.3.14 与 CI 1.4.2 分叉的那条缝。
`latest` 会让下一次 bun 发版再次静默撕开，形态还是「CI 绿、本机 230 红」。

**全局升级本机 bun** —— 本会话不做。用户明确说主工作区另有 CC 在跑，文档也禁止
未征得同意就动全局 bun。worktree 内 `.tools/bun-1.4.2/` 只作验证，不入库。

**按簇修 230 条断言** —— 禁止。单文件 / 显式列表在 1.3.14 上已经绿，那是运行器 bug。
