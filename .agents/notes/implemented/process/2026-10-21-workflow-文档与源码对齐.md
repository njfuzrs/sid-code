# workflow 官网页按源码事实校准 12 处描述

## 决定了什么

`website/extend/workflows.md` 有 12 处与当前实现不符，本次全部按源码改准：

1. `/workflows` 的列举口径：数据源是**进程内 task 注册表**，不是「磁盘上所有 run」；带 runId 也只在内存里匹配，不会回退读 journal。
2. `parallel`/`pipeline` 的错误语义补「闸门错误穿透」例外（预算耗尽 / agent 上限 / run 中止 / 严格 phase 对账失败会让整个调用 reject）。
3. 补并发上限 `min(16, CPU 核数 - 2)` 与 `SID_WORKFLOW_MAX_CONCURRENT`，并说明 item 数超 cap 时墙钟约等于 `ceil(items/cap) × 单链时间`，不是「最慢单链」。
4. `agent({model})` 省略语义：按 **`task` 子代理类型**解析，不是「继承主循环模型」，也与 `agentType` 无关。
5. resume 流程第 1 步：**失败时不返回** `runId`/`script_path`，需先用 `/workflows` 查。
6. 脚本落盘：`{name}` 加载不到自动落盘的 `<名字>-<runId>.js`；参数优先级是 `script_path` > `script` > `name`。
7. 缓存键示例由 `p1/0` 改为 `0p1/0`，并给出分段含义（`<位置序号><p|l|w><分支下标>/<作用域内序号>`）。
8. 确定性守卫补 `Date()` 作为普通函数调用也被禁（原文说「两个硬限制」却列了三条）。
9. 脚本格式校验的归属改为 `sandbox.ts` 的 `parseAndValidateMeta`；`export` 并非强制（正则里可选）、也不要求在文件第一行。
10. 原语列表补 `workflow()`（内联子 workflow）；禁列补 `require`/`eval`（`scanForHardEscapes`）。
11. journal 在 **resume 后会继续增长**（复用同一 runId 继续 append）。
12. 「子代理只能一个个串行或全并行」改为子代理默认并发 20（`SID_SUBAGENT_MAX_CONCURRENT` 可调）。

## 放弃了什么（以及为什么不选）

- **不改代码来迁就文档**。其中 4 条是代码缺陷：`resolveScript` 注释与实现相反、`{name}` 加载不到落盘脚本、失败不回 `runId`、子代理模型解析在 spawn/进程内两路径键不一致。它们已单独登记到 `docs-research/sid-code/bugfixes/todo/20261021-workflow官网核查发现的代码缺陷与文档问题.md`，本次 PR 只让文档与**当前实现**一致。理由：缺陷修复会改行为、需要独立测试与验证；混进来会让这份纯文档 PR 的 review 成本翻倍，也会让「文档描述的是哪个版本的行为」变得不可判断。
- **不按「修好后的行为」写文档**。若按修复后的语义写 `{name}` 与失败返回 `runId`，用户在当前版本照做会直接失败。文档必须描述用户此刻能拿到的行为，缺陷修好后再同步一轮（已在该缺陷文档第四节登记）。
- **不在官网里写「这里是 bug」**。官网是用户文档不是缺陷看板；这层判断留在缺陷文档与 issue，官网只呈现可执行的当前事实。
- **不顺手改其他页面**。`/extend/subagents`、`/use/worktree` 等相邻页未做同轮审计，留给各自的任务，避免混入未核实的改动。
