# `git rm --cached` + gitignore 的文件，会在**切分支/合并**时被 git 从工作区删掉

## 决定了什么

**事故先说清**：本次迁新仓时把 `packages/tui-renderer/src/`（123 文件）与
`packages/cli/src/command/commands/claude-api/reference/`（2 文件）撤销追踪并加进
`.gitignore`，本意是「本地保留、不入库」。结果这 125 个文件**在磁盘上消失了**。

**机理**（复核确凿，不是推测）：

1. 在 `chore/migrate-to-njfuzrs` 分支 `git rm -r --cached` + 提交 `d42cc794` ——
   该提交把这 125 个文件**记录为删除**（`git show --stat d42cc794 --diff-filter=D` = 127 条）；
2. `git switch main`（当时 `main = ce18e19a`，还没有这个删除）→ **文件被 git 恢复**；
3. `git merge --ff-only` 把 main 推进到含删除的提交 → **git 按索引把工作区文件删掉**。

⇒ **`.gitignore` 保护的是"未追踪文件不被 add"，完全不保护"已记录删除的文件不被 checkout 删掉"。**
这两件事在直觉上像同一件，实际毫无关系。

**已做的补救与防线**：

- 125 个文件已从 `ce18e19a` 用 `git checkout ce18e19a -- <两个目录>` 全部取回，
  再 `git rm -r --cached` 撤回索引，恢复成「磁盘有、不追踪、被 ignore」的目标状态；
- **物理备份**：`~/sid-code-untracked-vendor-20260904.tar.gz`（342K，实测包内 125 个文件）。
  这是目前唯一一份**不依赖 git 历史**的副本 —— 一旦将来真做了 `filter-repo`，
  git 历史里这两个目录就没了，**那时这个 tar 包是唯一事实源**。

## 放弃了什么（以及为什么不选）

**① 把两个目录挪到仓库外（如 `~/.sid-code-vendor/`）再 symlink 进来** —— 更彻底，
本次没做：102 个 consumer 走 `@sid-code/tui-renderer` bare specifier，
workspace 解析 + `bun build --compile` 对 symlink 的行为需要单独验证，
不该和「迁仓」这件事混在一次改动里。**留作后续**，它是真正的根治方案。

**② `docs-gen-reference` 改成「按目录是否存在动态过滤」** —— 明确否决。
本机有这个目录、CI 没有，两边会生成**不同的 env 列表**，`--check` 必然在其中一边红。
硬排除（`PKG_SRC_DIRS` 去掉 `tui-renderer`）才能两边一致。

## 拿什么证明它生效了

**恢复本身**：

```
find packages/tui-renderer/src -type f | wc -l              → 123
find .../claude-api/reference -type f | wc -l               → 2
git ls-files packages/tui-renderer | wc -l                  → 4（只剩包根 2 + tests 2）
git status --porcelain | grep -c 'tui-renderer/src'         → 0（被 ignore 覆盖）
tar tzf ~/sid-code-untracked-vendor-20260904.tar.gz | wc -l → 125
make build                                                  → 自检 4 项全过
```

**CI 红的根因与修法**（这是本次连带修的第二个问题）：
新仓首批 4 个 dependabot PR 的 CI **全红**，日志原文：

```
error: --check 应退 0 ... stderr: grep: /home/runner/work/sid-code/sid-code/packages/tui-renderer/src: No such file or directory
```

即 `scripts/docs-gen-reference.ts` 的 `PKG_SRC_DIRS` 扫一个 CI 上不存在的目录。
已从清单移除。

⚠️ **如实记录代价，不写成「无影响」**：我第一次判断是「该目录 env 读取点 0 个」，
**这个判断是错的** —— 当时目录已经被删掉了，grep 扫空目录当然返回 0，
我把「文件不存在」误读成了「内容干净」。恢复后重测，该目录实际有 **6 个只此一处**
读取的变量（`CLAUDE_CODE_COMMIT_LOG` / `CLAUDE_CODE_DEBUG_REPAINTS` /
`CLAUDE_CODE_TMUX_TRUECOLOR` / `CLAUDE_CODE_ACCESSIBILITY` /
`SID_CODE_DISABLE_MOUSE_CLICKS` / `SID_DISABLE_TAB_STATUS`）。
它们**运行时仍生效**（代码编进了二进制），但从此不再出现在 `website/ref/env.md`
（实测该页 158 → 152 个读取点）。这是「代码不入库」的连带代价。

**教训（比上面任何一条都重要）**：**空目录上的 grep 返回 0 命中，与「干净」不可区分。**
判断「某目录是否含 X」之前，必须先断言目录存在且文件数 > 0，否则结论方向可能整个反掉。
