# tsc 基线棘轮门禁：存量 107 处进基线，只拦新增、允许收紧

## 决定了什么

新增 `bun run typecheck:gate`（`scripts/tsc-baseline.ts` + `scripts/tsc-baseline.json`，
`tests/scripts/tsc-baseline.test.ts` 14 条用例），并接进 CI 的 `lint` job
（`.github/workflows/ci.yml` 新增 step「类型检查（只拦新增）」，
所以 `all-checks-passed` 的 `needs` 不需要动）。同时把 `typescript` 锁成
`5.9.3`（`--exact`，此前 devDependencies 里没有它，`bunx tsc` 每次临时拉版本）
并加 `bun run typecheck`（裸 `tsc --noEmit`）作为固定入口。

三条实现决策：

1. **身份键 = 归一化文件路径 + 错误码 + 归一化消息，不含行号和列号。**
   在错误上方插一行代码会让它后面所有错误的行号漂移；带行号的门禁会因此大面积假报，
   然后人就会去绕过它。
2. **比较用计数而不是集合**：基线存 `{ 键: 出现次数 }`，当前次数 > 基线次数即报新增。
   同一文件出现第二个完全相同的错误，集合比较发现不了。
3. **跑 tsc 前临时补齐 `packages/core/vendor/model-catalog-snapshot.json` 占位、跑完即删。**
   该文件是 gitignore 的构建产物（`make build` 生成）：CI 的 fresh clone 上没有它，
   本地跑过 `make build` 则有 —— 缺文件时 tsc 会多报一条 TS2307，于是同一个仓库在
   CI 与本地看到**不同的错误集合**，棘轮必然在其中一边假报「新增」。补的内容是空占位
   （该模块只把文件路径当字符串导出，内容不参与类型检查），被屏蔽的只是「构建产物尚未
   生成」这个纯环境状态，import 路径写错之类的真问题依旧会报出来。

## 放弃了什么（以及为什么不选）

1. **直接把 `tsc --noEmit` 接进 CI** —— 107 处存量错误会让它恒红；恒红的门禁等于没有门禁，
   最后一定被人加 `|| true` 或整条删掉。这正是它此前一直没被接入的原因（`ci.yml` 旧注释
   还写着「当前有 187 个存量错误」，实际已是 107，属文档漂移，本次一并修掉）。
2. **键里带行号** —— 见上，误报率会让门禁失去信任，理由与 `scripts/command-system-gate.ts`
   的棘轮一致。
3. **先清零再接入** —— 清零是漫长的过程，在那之前这条曲线（唯一一条还在恶化的曲线）
   没有任何东西拦着。棘轮让「不再变差」今天就能生效，收紧可以逐步做。
4. **让本地 `make build` 的产物决定基线** —— 基线若按「有快照文件」的环境生成（107 条不含
   TS2307），CI 会立刻报 TS2307 新增。所以基线必须按 CI 环境生成，并由脚本自己把两边对齐
   （决策 3），而不是让执行者去记「我这边环境是哪种」。
5. **`--update-baseline` 允许放宽** —— 放宽等于取消门禁：新增一处错误顺手把数字调高即可全程绿。
   脚本对「新键」或「同键次数变多」一律拒绝（exit 1），只能用 `--init` 无条件重写（仅首次接入用）。

## 拿什么证明它生效了

`bun run typecheck:gate` 三次运行（本地 worktree，tsc 5.9.3）：

```
# 1. 正常状态
类型检查棘轮（tsc 5.9.3）
  当前 107 处错误 / 基线 107 处

✓ 无新增类型错误。
rc=0

# 2. 人工变异：在 packages/core/src/llm/model-catalog-snapshot-embedded.ts 末尾加
#    `const __mutation_probe: number = "s";`
类型检查棘轮（tsc 5.9.3）
  当前 108 处错误 / 基线 107 处

✗ 新增 1 项类型错误：
  - packages/core/src/llm/model-catalog-snapshot-embedded.ts(31,7): TS2322: Type 'string' is not assignable to type 'number'.

  修掉它，不要放宽基线；存量清理后跑 bun run typecheck:gate --update-baseline 收紧。
rc=1

# 3. 撤销那一行（用 Edit 删除，没有用 git checkout）
类型检查棘轮（tsc 5.9.3）
  当前 107 处错误 / 基线 107 处

✓ 无新增类型错误。
rc=0
```

`bun test ./tests/scripts/tsc-baseline.test.ts` → **14 pass / 0 fail**
（含两个方向的变异自证：新增错误必须被数到、行号漂移必须不被数到）。

⚠️ 一条环境差异的如实记录：直接跑裸 `bun run typecheck` 在**没跑过 `make build`** 的
worktree 里是 108 条（多一条 `model-catalog-snapshot-embedded.ts` 的 TS2307），
跑过之后是 107 条；本机主仓还因为历史 `node_modules` 残留一个已不在 lock 树里的
`signal-exit@4.1.0`，把同一条 tui 解析错误显示成另一种形式（TS1192 而非 TS7016）。
基线按 CI 环境（fresh clone、无快照）生成：gate 自身已把快照差异对齐（决策 3），
但**陈旧 node_modules 造成的差异 gate 管不了** —— 主仓跑一次 `bun install`
让依赖树与 lock 对齐即可消除（`bun.lock` 里只有 `signal-exit@3.0.7`）。
