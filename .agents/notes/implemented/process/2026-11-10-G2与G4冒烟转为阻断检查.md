# G2 无头回放冒烟与 G4 TUI e2e 转为阻断检查，先修 G4 运行器的回车时序

## 决定了什么

`.github/workflows/ci.yml` 删掉 test job 里「G2 无头回放冒烟」「G4 TUI e2e」两步的 `continue-on-error: true`，两层从「只报告」改成阻断合并（专项 M2 转正 + M5 转必需）。没有按日历等到原定的 11-21，判据是**样本量**；同一个 PR 里先修观察期唯一一次 G4 失败的成因：

- **G4 运行器回车时序**（`tests/smoke/lib/tui.ts`）：`type` 看到回显后再等 `TYPE_SETTLE_MS`（100ms）才交给下一步。TUI 的 `bufferFastReturn`（`KeypressContext.tsx`）把「距上一个可插入键 ≤ `FAST_RETURN_TIMEOUT`=30ms」的回车当成粘贴里的换行。运行器每 50ms 轮询一次屏幕，TUI 处理文字时只要被拖慢 20ms 以上，回显后紧跟的回车就落进这个窗口。2026-11-09 macOS CI（run 42594411659，main@07bf6ba6）A1-dialog 就这样红了：最后一帧输入框里是「提示词 + 一个空行」，这一轮没提交。
- **新回归测试** `tests/smoke/tui-driver.test.ts`：① 读 `KeypressContext.tsx` 源码字面量，锁 `TYPE_SETTLE_MS ≥ 2 × FAST_RETURN_TIMEOUT`；② 起一个几十行的假 TUI（同样的快速回车判据 + 处理文字时忙等 40ms），走 `type → enter`，断言收到的是提交。没有用真二进制，因为它的这段时序取决于 runner 快慢，复现不稳定。
- **合约测试** `tests/release-flow-contract.test.ts`：新增「G2/G4 冒烟步骤与 test job 都不带 `continue-on-error`」。要降级（总纲 §6「G4 退回非必需」）就得改这条断言，降级在 diff 里看得见。
- **step summary 单测**（`tests/smoke/smoke-lib.test.ts` 的 `renderSummary`）：M2 验收④靠的就是这张表，之前没有测试守。
- `CONTRIBUTING.md` 门禁清单从九道改为十一道（test job 多了 `bun run smoke` / `bun run smoke:tui`）；`types.ts`、`run.ts` 里「观察期 / 转正判据」的过时注释同步改掉。

**牺牲了什么**：用「更快」换「更准」。冒烟只要红一次（包括非代码原因）就会拦住合并；每个 `type` 步骤多 100ms（现有 G4 只有 A1 一例、一个 `type`）。

## 放弃了什么（以及为什么不选）

- **按日历等到 11-21 再转**：两周窗口真正多防的是环境漂移，样本早就够了。G2 394 次 0 失败，按三法则估算失败率 95% 上限约 0.8%，再等 11 天也不会有新信息。环境漂移里能识别出来的只有 runner 镜像更新，而观察窗口首尾的 ubuntu 镜像都是 `20261101.360`，等于这一项也还没检验过。转了之后镜像更新要是真把冒烟弄红，回滚就是加回一行，代价可接受。**重新评估的触发条件**：转阻断后第一次 runner 镜像更新时，冒烟出现非代码原因的红。
- **G4 只在 ubuntu 阻断**（`continue-on-error: ${{ runner.os == 'macOS' }}`）：M5 判据原文只数 ubuntu，可 CI 在两个平台的 shard 1 都跑 G4。只转一半，macOS 上的 G4 就继续处于「红了没人看」的状态。唯一一次 macOS 失败已经查到成因，并在本 PR 修掉了，所以选择补上判据的缺口（两个平台都算），而不是绕开它。
- **不修运行器直接转**：macOS 上 1/66 的已知抖动会变成大约每 66 个 PR 误拦一次。时红时绿的必需检查会养成「红了就重跑」的习惯，比没有门禁更糟。
- **在冒烟环境里关掉或调小 `FAST_RETURN_TIMEOUT`**：这属于「为了上冒烟改产品行为」（总纲「不做什么」），而且 G4 从此测的就不是用户真实走的输入路径了。
- **文字和回车一次写入**：会进同一个读块，被当成多字符文本整段插入（`\r` 归一成 `\n`），结果还是换行。本机对照实验得到的就是和 CI 一样的那一帧。
- **把轮询间隔调短**：回显后回车只会来得更快，更容易落进窗口，方向反了。
- **等一个「TUI 已处理完」的屏幕信号，不用固定等待**：能观测到的只有回显，而「先处理、后回显」正是问题所在。要保证「处理文字 → 处理回车」的间隔，只能在回显之后再等。这里时间本身就是被测对象（产品的 30ms 窗口），和 `pause` 属于同一类例外，运行器文件头已经写明。

## 拿什么证明它生效了

**观察期数据**（`gh run list` 取 ci.yml 的 run，对每个 shard 1 作业用 `gh run view <run> --job <job> --log` 抓 `[PASS|FAIL|SKIP]` 和 `N 例：` 汇总行）：

- G2：2026-11-07 02:12Z 到 11-10 02:58Z，有汇总行的 shard 1 作业 ubuntu 205 个、macOS 189 个，**0 失败**。4 个作业没拿到日志：2 个当时 run 还没结束，2 个下载出错。1 个作业首次拉回来的日志被截断（820KB，没有汇总行），重拉到 1.43MB 后是 `13 例：12 通过，0 失败，1 跳过`。
- G4：ubuntu 从 11-08 16:33Z 起 **71 次连续全绿**；macOS 66 次里失败 1 次（上述 run 42594411659），之后 18 次连续全绿。
- 那次 G4 真失败，jobs API 里的步骤 `conclusion` 是 **success**。这坐实了「`continue-on-error` 下只能看日志」，总纲 §9 里标的「未核实」到此关闭。
- CI 时长（138 个成功的首次尝试 run，jobs API 的步骤时间）：两步合计耗时 ubuntu p50 9s / p95 18s / max 19s，macOS p50 17s / p95 38s / max 51s。把两步从 shard 1 扣掉重算整体耗时，**增量 p50 0s、p95 33s、max 49s**，93/138 个 run 增量为 0（最慢的通常是 macOS shard 2）。都低于 M2 的「p95 +2 min」和 G2+G4 合计「+3 min」上限。
- `bun test ./tests/release-flow-contract.test.ts`（main@c52dfde9）90/90。

**G4 失败成因**：
- 本机对照（只换剧本，用真二进制）：「回车与文字同块写入」得到的最后一帧和 CI 失败帧一致（输入框里是提示词加一个空行）；「只打字」时没有这个空行。
- 端到端复现没成功：本机 10 个 `yes` 压满 CPU 时 6/6 通过，无负载 18/18 通过。所以「CI 那次具体是怎么落进 30ms 窗口的」是从代码路径和帧比对推出来的，不是复现出来的。

**修复与新测试的变异自证**（worktree `sid-code-wt/smoke-blocking`）：
- `tui-driver.test.ts`：基线 2 pass；删掉回显后的等待（退回修复前的运行器）→ 跑 5 次 5 次都红，屏幕是 `NEWLINE gap=10`～`gap=11`，正好是「50ms 轮询 − 40ms 拖慢」；`TYPE_SETTLE_MS` 改成 30 → 下限断言红（`Expected: >= 60, Received: 30`）。还原后 2 pass。
- `renderSummary`：去掉换行压平 / 去掉 skip 原因 / 去掉竖线转义，三种变异各红 1 条，还原后 18 pass。
- 合约断言：G2 步骤加回 `continue-on-error: true`、G4 步骤加表达式形态 `${{ runner.os == 'macOS' }}`、test job 级加回，三种各红 1 条，还原后 91 pass。
- 本 PR 自己的 CI 是转阻断后的第一次实跑：两个平台的 shard 1 上两步都必须真跑且通过，汇聚门 `all-checks-passed` 才会绿。
