# AI 生成代码审查清单

## 何时使用
- PR Review 时
- 用户要求检查代码质量时
- 完成一个 Task 后的自检

## 审查流程

### 第一步：Spec 对齐度审查（核心）

重点不是审查代码写得好不好，而是审查代码是否实现了 Spec 定义的需求：

1. 对照 spec.md 验收标准，逐条检查是否有对应的实现和测试
2. 对照 plan.md 文件变更清单，检查是否有未预期的文件修改
3. 阅读 tasks.md 偏差记录，评估偏差合理性
4. 检查文件变更范围是否在 plan.md 声明的范围内

### 第二步：六种常见问题模式

#### 1. 过度工程化
- 是否添加了不必要的抽象类、工厂模式、策略模式？
- Spec 只要求支持 N 种场景，代码是否设计成支持 10 种？
- 是否有只用一次的 helper/utility 函数？

#### 2. 边界情况处理不足
- 是否处理了 nil/空值？
- 是否处理了空列表、空字符串？
- 是否处理了并发冲突？

#### 3. 错误处理不完整
- 是否只实现了 happy path？
- 错误信息是否足够详细（包含上下文）？
- 是否使用了 `fmt.Errorf("xxx: %w", err)` 包装错误？

#### 4. 测试覆盖不足
- 对照 spec.md 验收标准，每个标准是否有对应测试？
- 是否覆盖了边界情况和错误场景？

#### 5. 性能问题
- 是否有 N+1 查询？
- 批量操作是否使用了批量 API？
- 是否有不必要的重复计算？

#### 6. 安全漏洞
- 用户输入是否经过校验？
- 是否有硬编码的敏感信息？
- 是否有命令注入风险？

### 第三步：文档同步检查

- [ ] 如果修改了模块结构，CLAUDE.md 已更新
- [ ] 如果发现了新的失败模式，failure-modes.md 已更新
- [ ] 如果做了架构级决策，已新增 ADR
