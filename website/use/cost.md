# 成本与用量

读完这页你能做到四件事：

- 看懂 `/cost` 和会话摘要里每个数字的口径，知道哪个是真实总花费
- 判断你的缓存命中率是正常还是异常（**按实测值判断，不套协议族的固定上限**）
- 用四种手段把成本压下来，从改一行配置到换模型
- 给会话设花费上限，超了自动停

::: tip 为什么这页值得读
成本是 sid-code 少数有硬数据支撑的方向。缓存命中率不是玄学——
它直接决定你同一个任务花八分钱还是三毛钱。而这个数就摆在 `/cost` 里，随时能看。
:::

## 快速上手

会话里打 `/cost`：

```text
本次会话花费  $0.1501   5m47s · 主循环 31 次 · 辅助 6 次（本次启动后） · origin-deepseek-v4-1-flash

费用构成
  主循环           $0.0856   57%  ▰▰▰▰▰▰▱▱▱▱
  辅助调用         $0.0645   43%  ▰▰▰▰▱▱▱▱▱▱   ← 占比偏高，见下方明细
    fork:memory-extract 2 次  $0.0335  243k token · 8s
    fork:session-memory-update 3 次  $0.0309  304k token · 15s
    title_generation 1 次  <$0.0001  112 token · 892ms

主循环 token 与单价
  主循环均价 USD/百万 · 来源 网关同步（expr） · 全程空闲时段
  牌价 USD/百万 输入 0.2740 / 命中 0.0055 / 输出 1.0959（高峰价；空闲 ×0.5）
                 token        均价       费用       占比
  输入·未命中         198,709     0.2738     $0.0544  64%
  输入·缓存命中     2,199,936     0.0055     $0.0121  14%
  输出                 17,440     1.0952     $0.0191  22%
  累计发送 2,398,645（flow，每次请求的 prompt 都计入）
  当前上下文 99,126（stock，末次请求；状态栏 ↑ 显示的就是它）

缓存
  命中率 91.7%   省下 $0.5907
  命中下降 4 次（上游波动 4 / 本地 0）
    最近一次 85,120→39,424（-54%）
    证据 system/tools 未变、消息前缀不可判、两次请求间无重试
    → 上游缓存波动（网关或厂商），本地不可控
  本地前缀断裂 1 次（字节级，浪费约 12.8% 字符）

单次请求
  费用 p50 $0.0018 · p95 $0.0101 · 最高 $0.0137（n=31）
    第 3 次  $0.0137  prompt 56,743  命中 7,680
    第 1 次  $0.0101  prompt 43,880  命中 7,680
    第 2 次  $0.0046  prompt 55,553  命中 43,264
  按本进程最近 31 次请求统计（resume 后只含本次启动的部分）

耗时
  API 耗时（主循环）: 2m52s
  辅助调用耗时（逐次累计）: 24s（本次启动后 6 次调用）
  工具耗时: 1m11s

· 会话时长是墙钟：含思考与空闲；API 耗时只算主循环请求，
  子代理与辅助调用不含在内
· 辅助调用耗时是逐次累计：N 次调用各花的时间之和，
  不是它们占据的那段墙钟，不能与上面的 API 耗时直接相加
· 辅助调用 = 标题生成、记忆抽取、权限分类、摘要等，
  不经过主对话但同样计费；其费用/耗时/按用途拆分仅含本次启动后
· 请求数与费用是会话级（resume 后含历史）；
  标了「本次启动后」的辅助调用数字不含 resume 前的部分
· 均价 = 该段费用 ÷ 该段 token（由费用反推，含分时段加权）；
  牌价是当前档位价目，两者不同源，别拿牌价乘 token 对费用
```

> 上面是真实数据：会话级数字（花费 / token / 耗时 / 单次请求分布）来自一次 31 次主循环
> 请求 + 6 次辅助调用的会话（origin-deepseek-v4-1-flash / openai 协议 / 网关同步价），
> 数字取自落盘轨迹逐笔重放；缓存明细（`最近一次 …` 与字节级浪费）取自同机
> `cache-breaks.jsonl` 与 `events.jsonl` 的真实记录（另一段会话，逐笔重放）。
> 各段只在有数据时出现——没有辅助调用就没有「辅助调用」行，没设预算就没有预算行；
> 有模型落到兜底价时，首行下方会多一条黄色警告（那是估算值，不是真实价）。

退出时不用问也会给一份摘要（另一次会话的真实输出）：

```text
Session ID: 20260727-184318-a08fce0c
会话时长: 0.4 分钟
LLM: 4 次请求, 25585 tokens, 平均 5.3s, $0.0529
工具: 3 次调用 (3成功/0失败)
交互: 1 次提示, 4 轮循环
缓存: 命中 71% (71.7k/101.3k)
```

摘要里有两处口径与 `/cost` 不同，别直接横向对比：

- `LLM:` 行的 tokens 是「各模型末次输入之和 + 输出累计」（stock，避免历史被重复计数），
  不是 `/cost` 那条累加口径的 `累计发送`。所以同一次会话里 `25585 tokens` 和 `101.3k` 并存是正常的。
  （`/cost` 的 `当前上下文` 和状态栏的 `↑` 用的也是这个 stock 口径。）
- `LLM:` 行的金额只含 LLM 请求，**不含辅助调用**；含影子调用的完整总花费看 `/cost` 的
  首行 `本次会话花费`（主循环 + 辅助调用，`费用构成` 区拆开列）。

有压缩或自定义指标时，摘要还会追加 `压缩:` / `工具明细:` / `── Harness 指标 ──` 行。

**先看两个数**：首行的 `本次会话花费`（花了多少）和 `缓存` 区的 `命中率 91.7%`（缓存效率）。
第二个数低的时候，第一个数会翻好几倍——`主循环 token 与单价` 区直接告诉你钱花在哪一项上
（上面这次：64% 花在只占 8% 的未命中输入上）。

## 每个数字的口径

新版 `/cost` 是分区账单，这几个数容易看混，逐个说清：

| 字段 | 含义 | 注意 |
| --- | --- | --- |
| `本次会话花费`（首行） | 主对话 **+ 辅助调用**的真实总花费 | 这是你实际要付的钱。`费用构成` 区把它拆成主循环 / 辅助调用两行 |
| `主循环`（费用构成） | 主对话 + 子代理的 LLM 请求费用 | 子代理跑得多时这一行也会涨 |
| `辅助调用`（费用构成） | 标题生成 / 记忆抽取 / 风险分类 / 摘要等影子调用 | 只在 >0 时显示，且按用途逐行列出（`fork:memory-extract` 等）。占比 ≥ 30% 会标黄提示——这行真的花钱 |
| `输入·未命中` / `输入·缓存命中` / `输入·缓存写入` | **互斥三段**（两族协议归一化后拆开，openai 族的「输入」不再和缓存命中混在一起） | 三行加起来 = `累计发送`；费用三行加起来 = 主循环费用。anthropic 族 `缓存写入` 非 0，openai 族恒 0 —— token 为 0 的段**整行省略**（不写一行 `0 0.0000`） |
| `输出` | 全会话累计输出 token（含推理） | 推理 token 另起一行「其中推理」，是输出的一部分，**不另计费** |
| `均价` / `来源` | `均价` 是**该段费用 ÷ 该段 token**（USD/百万，由费用反推，含分时段加权）；`来源` 是入账时记下的价格来源（网关同步 / 注册表 / 兜底价） | 均价**不是牌价**：会话横跨高峰与空闲时，拿牌价乘 token 与费用列差一倍。价格来源后跟时段结论，三态：`全程高峰时段` / `全程空闲时段` / `高峰费用占比 N%`；旧快照或两桶之和与总额不符时写 `时段拆分不可用`，不猜一个值。兜底价是「宁可高估」的估算，首行下方会亮黄警告 |
| `牌价`（紧跟来源行） | 该模型当前档位的价目表：输入 / 命中 / 输出（高峰价，空闲价按倍数派生） | 与上一行是两件事：这一行是「价目表」，上一行是「我实际按什么价结算」。别拿牌价乘 token 去对费用列 |
| `累计发送` | 全会话累计输入 token（**flow 累加口径**） | 多轮会话里这个数会远大于上下文窗口，正常 |
| `当前上下文` | **最后一次请求的完整 prompt**（stock 末次口径） | 和 `累计发送` 是两个口径，必然不等，不是算错了。状态栏的 `↑` 显示的就是这个数 |
| `缓存命中率` | `缓存命中 / 归一化后的完整 prompt` | 分母是三段之和，**不是** `累计发送` 之外随便哪个数。判断标准见下一节 |
| `省下` | 因为命中缓存而少付的金额 | 可能比总花费还大——省下的比花掉的多是常态 |
| `单次请求` | 主循环单次费用的 p50 / p95 / 最高，附最贵 3 次与样本数 `（n=N）` | 用 p 分位不用均值（长尾会拉高均值）。**样本少于 20 时不给 p95**——那时「p95」等于最大值，会让人以为分布很平。**resume 后只含本次启动的部分**（逐次明细在内存里，不落盘） |
| `命中下降 N 次` | token 侧检测器记录的中断次数，括号里按归因拆成「上游波动 / 本地」 | 只在有断裂时显示。上游 = 网关路由或厂商缓存节点，本地改不动；本地 = 前缀/历史被改写、工具顺序变化，能优化。模型变化 / TTL 过期 / 不可判不算进这两类，所以两个数之和可以小于总次数。明细三行：最近一次的前后 token、三条证据（system/tools、消息前缀、有无重试）、结论 |
| `本地前缀断裂 N 次` | 字节侧检测器（逐字符比对前缀）记录的中断次数 + 最近一次浪费的字符比例 | 与上面是**两个独立检测器**：命中 token 还在低位爬升时，字节侧就能看到前缀已被改写。**没采集到数据时整行省略**，不写「0 次」冒充「没有断裂」 |
| `API 耗时（主循环）` | **只算主循环请求**的 API 耗时（已扣人工等待） | 不含辅助调用，也不含子代理 |
| `辅助调用耗时` | 影子调用的耗时之和（**逐次累计**：N 次调用各花时间之和） | 次数与耗时都只覆盖「本次启动后」。它不是这些调用占据的那段墙钟，**不能与 `API 耗时（主循环）` 直接相加**。显示 `—` 表示一次都没采集到耗时，**不是「没花时间」** |
| `工具耗时` | 工具执行耗时之和 | 与 `API 耗时（主循环）` 并列，二者不可相加得到会话时长（后者是墙钟） |
| `作废重发`（有值才显示） | 超时 / 流内错误后重试的次数与白烧 token | 黄色提示——这些请求的响应被丢弃但钱已经花了 |
| `预算`（有值才显示） | 当前花费 / 花费上限 | 只在设了 `--max-budget-usd` 或 `quota.costLimit` 时显示 |

颜色约定：无头模式与管道输出**不带任何 ANSI 颜色**（脚本可以放心 grep）；
真终端里总花费加粗、区标题用品牌蓝、警告用黄、省钱用绿，说明文字全部放面板末尾的注释区。

多模型会话还会按模型分列，`input` 用的是同一套累计口径，
所以「分模型之和」和「上方汇总」是能对上的。

## 缓存命中率：看实测值，不套固定上限

这是最容易误判的一点：**命中率没有一个跨渠道通用的「正常值」。**

2026-11-10 对本机 `~/.sid-code/usage-ledger.jsonl` 的实测
（筛 `provider=openai`、单会话 `promptTotal ≥ 20 万`——太短的会话缓存还没热起来，会把分布拉低）：

| 模型 | 会话数 | 加权命中 | p50 | p90 |
| --- | --- | --- | --- | --- |
| origin-deepseek-v4-1-flash | 473 | **91.4%** | 89.6% | 96.2% |
| glm-5.2 | 157 | 85.5% | 81.0% | 93.3% |
| glm-5.3-uniapi | 51 | 83.8% | 79.8% | 91.3% |
| kimi-k3 | 7 | 81.9% | 80.0% | 85.6% |
| gpt-5.6-luna | 19 | **2.2%** | 0.0% | 0.0% |

openai 协议族的命中率**按厂商和网关差别很大**：主流渠道稳定在 80–95%，
有的渠道几乎为 0（服务端没开缓存，或者网关改写了前缀）。
所以「openai 族结构性上限 60–70%」这个说法已经不成立——那是早期某个模型的样本。
`anthropic` 族走客户端显式写入（`cache_control`），能精确控制缓存边界，
命中率通常更高，但同样没有一个可以拿来考核所有渠道的固定阈值。

`/cost` 现在按**实际数值**给提示，不再按协议族写死上限：

- 命中率 **低于 50%**、且本会话已有 **≥ 5 次请求** → 提示「缓存命中率偏低」，
  并指向 `/cache --breaks` 看本会话每次缓存中断的归因；
- 其余情况不提示。

阈值是渲染层的常量（`LOW_CACHE_HIT_RATE_THRESHOLD` / `LOW_CACHE_HIT_RATE_MIN_REQUESTS`，
在 `packages/cli/src/command/commands/cost/cost-render.ts`，由 `cost.ts` 转出），
**不按模型名分档**：同一族里既有 91% 的渠道也有 2% 的渠道，按族给「正常上限」
只会让前者看到无意义提示、后者被放过。

为什么是 50%：上面实测里正常渠道都在 80% 以上，2% 那种是渠道本身的问题；
50% 既能抓住真问题，又不会误伤正常渠道。

短会话（少于 5 次请求）不提示：缓存还没热起来，前几次请求自然低命中——
取证会话里最贵的 3 次请求正是这前 3 次。

两族协议为什么必须写成两种形状（openai 族的 `输入·缓存写入` 恒为 0 就是那里推出来的），
见 [Prompt Cache：两族协议的分叉](/blog/prompt-cache)。
（该文中的「60–70% 上限」是 2026 年中的样本，本节上表是 2026-11-10 的更新实测。）

::: warning 不要拿 100% 当目标
实测一个单轮会话可以打出 `缓存: 命中 100% (24.6k/24.6k)`——因为输入全部是重复前缀。
这个数很好看但没意义，真实多轮任务的命中率天然会被新增内容拉低。
有参考价值的是**同类任务的命中率趋势**，不是单次绝对值。
:::

### 怎么把命中率提上去

缓存是按**前缀**命中的，前缀一变整段就废。所以核心原则只有一条：
**让稳定的东西待在前面，让变化的东西待在后面。**

| 做法 | 为什么有效 |
| --- | --- |
| 同一个任务留在同一个会话里做 | 换会话等于前缀重建，命中率归零 |
| 别频繁 `/clear` | 同上。想换话题但保留上下文用 `/compact` |
| 项目约定写进 `CLAUDE.md` 而不是每次口述 | 它作为稳定前缀被缓存；口述的内容夹在对话中间，破坏后续前缀 |
| 中途别反复 `/model` 切换 | 换模型等于换缓存空间，前面攒的全不算 |
| 长任务里别插无关的临时问题 | 插进去的内容会让后面每一轮的前缀都变 |

## 跨会话：`/cache`

`/cost` 只看**当前这次会话**。想知道"这周缓存命中率是不是在掉""哪个模型最近老断缓存"，
用 `/cache`——它读的是跨会话的用量账本，不是内存里的当前会话。

数据存在 `~/.sid-code/usage-ledger.jsonl`（每会话一行汇总，按 sessionId 做 upsert：
每轮结束增量落盘、覆盖同会话旧行，不是 append-only，
`packages/core/src/telemetry/usage-ledger.ts`）。所以即使会话关了、机器重启了，历史还在。

### 默认输出：长期命中率与省钱趋势

```text
/cache
```

无参显示长期统计：总命中率（百分比 + 绝对 token 数）、累计省钱（USD）、累计成本
+ 会话数、按模型分列的用量（按命中 token 降序）、各周期命中率的趋势 sparkline
（`▁▃▅▆▇█` 字符图，一眼看出在涨还是在掉；至少有两个周期才显示）。

### 五个参数

| 参数 | 作用 |
| --- | --- |
| `--period day\|week\|month` | 聚合粒度，默认 `day`。`week` 用 ISO 周键、`month` 用年月键 |
| `--model <name>` | 按模型名过滤（精确、前缀或反向前缀匹配） |
| `--breaks` | 显示**本会话**最近 20 条缓存中断记录 + 健康度建议（`packages/core/src/api/cache-detection.ts` 的 `getCacheHealthAdvice()`）。记录只在进程内存里（最多 50 条），进程重启即丢；跨会话历史用 `--history` |
| `--history` | 跨会话缓存中断遥测历史聚合，从 `~/.sid-code/cache-breaks.jsonl` 读，按归因类型计数 |
| `--prune <N>` | 滚动裁剪账本，只保留最近 N 行（账本太大时用） |

### `--breaks`：本会话的缓存退化诊断

**缓存命中率从 90% 掉到 70%，不是 `/cost` 的单次快照能看出来的——你得知道它为什么掉了**。
`--breaks` 给的是**当前进程内**的最近 20 条中断记录（内存环形缓冲最多 50 条），
用来即时解释「刚才那几轮为什么掉」。进程重启即丢；要看跨会话的长期记录用 `--history`。

检测机制（`packages/core/src/api/cache-detection.ts` 的 `CacheBreakDetector`）：每轮请求前快照缓存关键状态
（system prompt hash / 工具 schema hash / 模型 / cache control / beta headers / 消息数 /
工具顺序），响应后比较 `cache_read_tokens` 变化。**下降 > 5% 且绝对值 > 2000 tokens**
才算一次中断（`cache-detection.ts` 的 `DROP_PERCENT_THRESHOLD` / `DROP_TOKENS_THRESHOLD`）——避免正常波动报假警。

10 类归因：模型变化（`model`）、system prompt 变化（`system_prompt`）、工具增删改
（`tools`）、工具顺序变化（`tool_order`）、缓存策略变化（`cache_policy`）、beta headers 变化
（`beta_headers`）、消息数量骤减即 compact 导致（`compact`）、TTL 过期（`ttl_expiry`）、
本地前缀断裂（`prefix_break`）、服务端波动（`server_fluctuation`）。

`--history` 把这些中断落盘到 `~/.sid-code/cache-breaks.jsonl`（append-only），长期聚合，
告诉你"最近哪种归因最频繁"。子代理的缓存中断**独立计**——`MultiSourceCacheDetector`
按 agentId 维护独立基线（`cache-detection.ts` 的 `MultiSourceCacheDetector`），不会把子代理的正常波动算进主会话。

实测这些归因跑出来长什么样、以及为什么"本地前缀 hash 变没变"是最关键的那个判据，
见 [Prompt Cache](/blog/prompt-cache) 的归因分布一节——绝大多数真实中断都是
本地不可控的服务端波动，这个分布本身就是结论：**本地能优化的前缀断裂几乎为零，
所以这里该做的是监测而不是排查**。

::: tip compact 会触发一次中断，但会被抑制
`/compact` 会让消息数量骤减，正常应该报一次中断。但 `notifyCompaction()`
会跳过紧接的那次检测（假阳性抑制），所以 compact 后看到命中率
下降是正常的，不会在 `--breaks` 里报成异常。
:::

## 单会话深度分析：`/insights`

`/cost` 给数字，`/insights` 给**结构化报告**——这次会话到底发生了什么、哪里可能有问题。

```text
/insights              # 分析当前会话
/insights latest       # 分析最近一个会话
/insights 20260728-004217-cc55cf0d   # 分析指定会话
```

别名 `/analyze`。纯本地执行，不调模型（`packages/cli/src/command/commands/insights/insights.ts`），
复用 `packages/core/src/trace/digest.ts` 的 `renderHuman()` 渲染。下面是与
[轨迹采集与可观测](/team/observability) 里 `trace-digest` 同源的**核心结构节选**
（实际报告还会渲染成本结构、Provider 健康、端到端耗时等，且各块按会话数据条件出现）：

```text
━━━ session <id>  [<exitStatus>] ━━━
  模型/API 次数/步骤/耗时/成本/token

用户意图: 1. <prompt>

L0 事实层 (N) — 机器可验证,带出处,不含判断:
  [高] <kind>: <detail>  ⊢ 出处: <file> @<lineRef> = <rawValue>
L1 假设层 (N) — 待验证,先消解证伪条件再采信:
  [中] <kind>: <detail>  ⚖ 证伪条件: <condition>

工具序列 (N 次调用):  · <tool> / ✗ <tool> / ○ <tool>（孤儿调用）
思维链要点:  💭 <thought>
子代理执行:  <N> 个（<M> 成功 / <K> 失败）  执行模式: 串行|并行|混合|单个
```

没有检出异常时，L0/L1 两块会合并成一行 `✓ 未检出异常信号`；
`工具序列` / `思维链要点` / `子代理执行` 同样只在有数据时出现，
子代理失败之外还可能追加 ` / N 未知`。

**它最有价值的设计是 L0/L1 分层**：L0 事实层带出处（`messages.json` 的哪一行 = 什么值），
L1 假设层带证伪条件。它不直接给你"结论是 X"，而是给可验证的事实 + 待验证的假设 +
推翻假设需要看哪里。比如 `exit_status = error` 是事实，但假设层同时给了证伪路径——
查 `messages.json` 的 attribution 会看到实际是正常 end_turn，说明 error 状态不等价于异常终止。

### `/cost`、`/cache`、`/insights` 各管什么

| 命令 | 回答什么 | 数据源 | 范围 |
| --- | --- | --- | --- |
| `/cost` | 这次花了多少钱、缓存命中多少 | 内存当前会话 | 单会话 |
| `/cache` | 缓存命中率长期趋势、是否在退化 | `usage-ledger.jsonl` + `cache-breaks.jsonl` | 全部历史会话 |
| `/insights` | 这次发生了什么、哪里可能有问题 | `trajectories/sessions/<id>/` 轨迹文件 | 单会话深度 |

三者不重复、不替代：`/cost` 看当下花了多少、`/cache` 看长期缓存在不在退化、
`/insights` 看单次会话的决策链与异常信号。时间花在哪、最近是不是变慢了，用 `/perf`，
见[性能与延迟](/use/performance)。

## 设花费上限

单次会话给个硬顶，超了自动停。交互模式和 `-p` 都生效：

```bash
sid-code --max-budget-usd 0.50
```

配置里同时有 `quota.costLimit` 时，**取两者中更严的那个**。上限是只许收紧的语义，
所以团队默认配置的 `100` 不会盖掉你传的 `0.5`，你也没法用参数把团队上限放宽。
`0` 表示「这一侧不限」，不参与比较。

四级预警，按累计花费占上限的比例触发。括号里的百分比是**实测时的实际比例**，
触发阈值是 50% / 80% / 95% / 100%（`packages/core/src/llm/quota.ts`）：

```text
$0.0011 / 0.002  →  [info]     成本已达配额 55%（$0.0011 / $0.0020）
$0.0017 / 0.002  →  [warning]  ⚠ 成本已达配额 85%（$0.0017 / $0.0020），请注意控制用量
$0.0019 / 0.002  →  [critical] ⚠ 成本已达配额 95%（$0.0019 / $0.0020），即将超限！
$0.0025 / 0.002  →  [exceeded] 成本已超出配额（$0.0025 / $0.0020），自动停止
```

到 `exceeded` 就真的终止本轮（消息文本本身不带 emoji，TUI 渲染时两端加 `── … ──`）。

每级只报一次（级别升级才报），不会刷屏。计算基数是**含辅助调用的总花费**，
所以影子调用烧的钱也受这个上限约束，不会绕过去。

::: tip 上限不生效时先查这个
`--max-budget-usd` 与 `quota.costLimit` 取更严的。所以「设了更小的值却没拦住」
只剩一种可能：参数根本没传进去（拼错了、写在了别的子命令后面）。
想放宽上限时，参数是做不到的，要改配置里的 `quota.costLimit`。
:::

团队级的持续管控（每分钟请求数、token 速率、按规则降级）不在这页，
见[配额与成本控制](/team/quota)。

## 把成本降下来的四招

按性价比排序，第一招几乎零成本：

### 一、给子代理配便宜模型

主对话用强模型，子代理干粗活用便宜的。子代理通常做的是搜索、读文件、跑命令这类
不需要强推理的事，用同一个贵模型是浪费。配置见[子代理](/extend/subagents)。

### 二、保住缓存命中率

见上一节。一次会话做完一件事，比来回开新会话省得多。

### 三、控制上下文体积

上下文越长，每一轮的输入 token 越多。`/context` 看当前占用，
长任务到七八成的时候 `/compact` 一次。细节见[上下文与压缩](/use/context)。

### 四、按任务难度换模型

简单任务不需要最贵的档位。`/model` 随时切，不用重启。
还有 `/effort` 调推理档位——低档位输出的 reasoning token 少，也省钱。

### Fast Mode：`/fast`（预留开关）

`/fast` 切换的是 fastMode 偏好——"优先用更快的输出端点/服务档位"。
**如实说明：当前网关未提供对等 fast 能力，开启暂无实际加速效果。**
这是预留开关，等网关支持后无需改命令即可生效
（`packages/cli/src/command/commands/fast/fast.ts`，透传到 `packages/core/src/llm/fallback.ts` 的
`fastMode` 字段，fallback 层标注为「预留，暂未启用」）。

```text
/fast          显示当前开关态 + 能力说明
/fast on       开启（仅当前会话）
/fast off      关闭
/fast on -p    开启并持久化到 settings.json（别名 --persist / save）
```

无参时的真实输出：

```text
Fast Mode: off
注: 当前网关未提供对等 fast 能力，开启暂无实际加速效果（此为预留开关，网关支持后自动生效）。
```

**和 `/effort` 的区别**：`/effort` 控制推理深度（已生效，支持的模型上低档位省 reasoning token），
`/fast` 控制输出端点速度（预留，当前无实际效果）。两者正交——`/effort` 现在就能用，
`/fast` 等网关就绪后才真正生效。无效参数会提示 `用法: /fast [on|off] [-p]`。

`/effort` 有一个前提：模型本身要支持 reasoning 能力，否则命令会拒绝切换并提示；
DeepSeek 这类只认 high 的模型会把 low/medium 钳到 high，低档位不一定真省。

::: tip 为什么不删掉这个预留命令
打了会明确告知"当前无实际加速"，比让命令消失、等网关支持后再突然出现更清楚。
:::

## 常见问题

### 省钱金额比总花费还大，是不是算错了

没算错。`省下` 是「如果这些 token 全按未缓存单价付，会多付多少」。
缓存命中比例高的时候，省下的确实可以超过实际花掉的。

### 总花费和我在网关看到的账单对不上

先看 `费用构成` 区的 `辅助调用` 行。标题生成、记忆抽取、风险分类这些影子调用也算钱，
`/cost` 首行的 `本次会话花费` 是把它们算进去的。如果差得多，用 `/trace` 看这次会话的完整调用清单。

### `--max-budget-usd` 设了但没生效

它和 `quota.costLimit` 取更严的那个，两种模式都生效。所以「设小了却没拦住」
基本只剩参数没传进去这一种可能。反过来，「想用参数把上限调大」是做不到的，
更宽的那个永远不会胜出，要放宽就改配置：

```bash
grep -A3 '"quota"' ~/.sid-code/settings.json
```

### 输入 token 数比模型的上下文窗口还大

正常。`累计发送` 是**全会话累加**，不是单次请求的长度。
四轮会话每轮输入 25k，累加就是 100k，但每一轮实际都在窗口内。
想看单次请求占多大，看 `当前上下文` 或状态栏的 `↑`，也可以直接看 `/context`。

### 想看跨会话的成本趋势

`/cache` 看跨会话命中率与成本趋势（`--period week` 按周聚合），`/trace --health` 看 provider 维度的成功率与延迟。
团队维度的采集见[轨迹采集与可观测](/team/observability)。

### 这些数字能证明"AI 提效了"吗

不能，它们只回答"花了多少"。省下的 token 与省下的工程时间不是一回事——
成本降了，验证侧的负担可能同时在涨，而这一侧本页一个字段都没有覆盖。
为什么会这样、该换成什么指标去看，见
[AI 提效的熵账本](/blog/entropy-accounting)。
