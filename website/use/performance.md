# 性能与延迟

读完这页你能做到三件事：

- 用 `/perf` 看清这次会话的时间花在哪一段
- 用 `/perf --days 7` 判断本机最近是变快还是变慢
- 看懂每个数的口径，不被均值和跨模型汇总骗到

所有数据都在本机：会话轨迹在 `~/.sid-code/trajectories/sessions/`，跨会话索引在
`~/.sid-code/session-index.jsonl`（看单会话时还会读同目录下的 `usage-ledger.jsonl` 核对成本）。
`/perf` 只读这些本地文件，不联网。数据流向见[隐私与数据流向](/use/privacy)。

## 快速上手

会话里打 `/perf`：

```text
77684ab7  glm-5.3-uniapi · 1h52m · 活跃 1h41m · 主循环 160 次调用 · 已结束

结论  慢在模型生成（77%）：thinking 占输出 70%，可考虑降低 effort
      首字等待 19%，网关等模型出字才回响应头（TTFT≈TTFB），分不清是排队还是 prefill
      缓存未命中时首字慢 2.8×
      enter_worktree 失败 23/24 次

时间去哪了                                                   合计 = 活跃时间 1h41m
  等首字节  █████▋                          19%  18m51s
  生成      ███████████████████████         77%   1h18m
  工具      █▎                               4%   4m20s
  其他      ▏                                0%     13s   轮间开销、权限确认

延迟                        P50    P95    P99    n
  首字 TTFT                5.9s    15s    32s  161
    缓存命中               5.8s    13s      —  151   未命中 7 次，P50 16s（慢 2.8×）
  首字节 TTFB              5.7s    15s    32s  161
  单次生成                  10s  2m08s  4m52s  161
  生成速度             33 tok/s   thinking 占输出 70%
  端到端（回车→答复）   1h26m、14m32s  n=2，样本 <5 直接列出 · 另有 1 轮中断（最长 8.7s）

最慢的调用
  #45  7m20s  输出  13,598 tok  首字   15s   5m00s 时触发「慢响应」提示，流一直在推进
  #13  4m54s  输出   9,261 tok  首字  2.2s
  #14  4m32s  输出   8,877 tok  首字  8.4s
  停滞提升 1 次

工具              次数   合计   最长  失败
  bash              77  3m59s  1m07s    10
  enter_worktree    24    19s    19s    23
  edit              27   1.6s  963ms     0
  ...

后台辅助  不计入上面的数字
  记忆 fork  4 次  首字 P50 44s   4 次未完成就被中止（最长 1m00s）
  标题生成   1 次

```

> 示例来自一次 glm-5.3、`effort=max` 的 101 分钟真实会话（3 条用户输入，160 次主循环调用）。
> 当前会话的轨迹还没落盘时，`/perf` 会改看最近一次会话并提示你。

面板从上往下读：

- **第一行**是会话身份：短 id、模型、墙钟、活跃时间、主循环调用次数。会话还在跑时末尾是「进行中 · 截至 HH:MM:SS」，数字是那个时刻的快照（轨迹最多每 30 秒写一次）。
- **结论**直接告诉你慢在哪一段，后面几行是能指回下面数字的补充。黄色的是需要你处理的问题（某个工具大量失败、首字 P95 超过 30 秒）。
- **时间去哪了**把活跃时间拆成四段，四段之和等于活跃时间。
- **延迟**每项给 P50 / P95 / P99 和样本量 n。
- **最慢的调用**看是个别长输出拖慢了，还是普遍慢。
- **工具**按耗时排前 5，带失败次数。
- **后台辅助**是记忆整理、标题生成、子代理这些不在主循环里的调用，单列出来，不混进上面的数字。没有就整段不显示。

终端窄于 80 列时会去掉横条、P99 列和工具「最长」列。无头模式（`sc -p "/perf"`）、输出不是终端或设了 `NO_COLOR` 时不带颜色，结构不变。

## 四个视图

| 用法 | 回答什么 | 数据源 |
| --- | --- | --- |
| `/perf` | 这次会话慢在哪一段 | 当前会话轨迹 |
| `/perf <id\|latest>` | 指定的历史会话 | 该会话轨迹 |
| `/perf --days N` | 近 N 天比前 N 天变快还是变慢 | `session-index.jsonl` |
| `/perf --by-version` | 每个版本的延迟（最近 10 个） | `session-index.jsonl` |

任一视图加 `--json` 输出机器可读结果，方便接脚本或自己的看板。会话视图的 JSON 就是面板背后的报告：
`verdict.primary`（瓶颈：`ttfb` / `gen` / `tool` / `other` / `insufficient`）、`timeSplit`（四段毫秒数与 `activeMs`）、
`latency`（各项分布，n<5 时带 `samples`）、`tools`、`slowest`、`side` 等，字段名即契约。

跨会话视图读索引而不是轨迹目录：轨迹会被自动清理，索引不会，所以几周前的会话照样进趋势
（索引只有显式执行 `/trace --prune-index N` 才会裁剪）。

## 每个数是什么

| 指标 | 口径 | 取数源 |
| --- | --- | --- |
| 首字延迟 TTFT | 发出请求到收到**第一个任意内容**（含思考、工具调用），每次请求单独计，不跨重试累加。**只算主循环**，后台辅助调用（记忆整理、压缩等）和子代理不算在内 | `StreamPhase(first_content).ttft_ms` |
| TTFB | 发出请求到收到响应头 | `StreamPhase(headers_received).ttfb_ms` |
| 生成耗时 | 单次请求从收到响应头到流结束，不含重试。只算主循环；被打断或超时结束的流不算 | `RetryTelemetry(stream_completed).elapsedMs` |
| 生成速度 | 输出 token ÷ 生成耗时累计（与上一行同一组请求）。会话进行中也能算出来。行尾的「thinking 占输出」是推理 token ÷ 输出 token | 轨迹 `output_tokens_per_sec`、`total_reasoning_tokens` |
| 端到端 | 你按回车到最终答复，**含**等你确认权限的时间。被打断（ESC 或上游中止）的轮不算在内 | `TurnComplete.elapsed_ms_since_prompt` |
| 时间去哪了 | 活跃时间（每轮回车到收尾之和，含被打断的轮）拆成四段：等首字节（Σ 主循环 TTFB）、生成（Σ 主循环单次生成耗时）、工具（Σ 主循环工具墙钟）、其他（差值：轮间开销、权限确认等待）。四段之和等于活跃时间。工具只算主循环的调用，子代理内部的工具已经包含在 `sub_agent` 工具自身的耗时里 | `StreamPhase(headers_received)` / `RetryTelemetry(stream_completed)` / `PostToolUse.duration_ms` / `TurnComplete` |
| 后台辅助 | 记忆 fork、标题生成、子代理等非主循环调用的次数与首字 P50。发出后没收到完成事件就结束的记为「被中止」，括号里是最长一次的耗时，接近 1m00s 说明撞了 60 秒上限 | `StreamPhase` / `BilledRequest`（按 `agent_id` / `caller` 分组） |
| 上下文峰值 | 本会话最高一轮的上下文占用 ÷ 模型窗口 | 轨迹 `context_usage_peak_ratio` |

**0.1.616 起口径变了。** 之前 TTFT 和生成耗时里混着后台辅助调用和子代理的请求（后台调用的首字往往要 30 秒以上），P95 偏高；被打断的轮也算进了端到端。所以 `/perf --days` 和 `--by-version` 在对比窗口里含旧口径会话时会提示一行。新旧版本之间的「变快」有一部分只是口径变化。

TTFT 只认可视文本会出错：思考型模型和纯工具调用轮会被系统性高估几十秒。这也是它必须按「首个任意内容」算的原因。

生成耗时从收到响应头开始算。有的网关要等模型开始出字才回响应头，这时大部分等待都落在 TTFT 里，生成耗时会比 TTFT 小很多。这是口径，不是算错。

## 怎么判断慢在哪

面板的「结论」就是按下面这套规则自动给出的。阈值是固定值，不按模型分档：

1. **时间去哪了里占比最大的一段就是瓶颈**。主循环调用不到 5 次时样本不足，不下结论。
2. **生成是瓶颈**：如果 thinking 占输出 ≥ 50%，生成慢主要是思考 token 多，可以降低 `/effort`；否则看生成速度和输出长度。
3. **等首字节是瓶颈**：看 `(TTFT − TTFB) ÷ TTFT` 的中位数。
   - **≥ 50%**：网关先回了响应头，TTFT 里多出来的那段就是模型 prefill，慢在模型。
   - **< 50%（TTFT≈TTFB）**：网关等模型出了第一个字才回响应头，客户端分不清是网关排队还是模型 prefill。用 `/trace --health` 对比不同路由。
   - 缓存未命中时的首字 P50 比命中时高 2 倍以上，会补一句「缓存未命中时首字慢 X×」。
4. **工具是瓶颈**：列出耗时前 2 的工具，用 `/trace` 看具体哪次调用慢。
5. **其他是瓶颈**：时间花在轮与轮之间，多半是等权限确认。
6. 不论瓶颈在哪，某个工具调用 ≥ 3 次且失败率 ≥ 50% 时会用黄色单独提示；首字 TTFT P95 超过 30 秒也会提示（与 `/trace --health` 同一阈值）。

另外两条要自己看：

- **端到端高但时间构成正常**：多半是轮数多。看 `/perf --days` 里的「轮数/会话」。
- **上下文峰值超过 65%**：会话太长，后面每一轮都更慢也更贵。该 `/compact` 或新开会话，见[上下文与压缩](/use/context)。

## 为什么延迟类指标只报分位数

均值会被大多数正常请求稀释，掩盖掉那几次让你等半分钟的慢请求，而慢尾巴恰恰是体感最差的部分。所以延迟类指标（TTFT、生成耗时、端到端）只给分位数，并在每个数后面标样本量 `n`；生成速度和上下文峰值是整段会话的单值，不带 `n`。

样本量很重要。`n=3` 的 P95 就是最大值，写成「P95」会被读成慢尾巴。所以会话视图里：样本少于 5 个时不报分位数，直接列出全部样本；少于 100 个时 P99 显示 `—`（它约等于最大值）。`--days` 视图里，两侧都至少有 5 个样本才会判「改善」或「变差」；样本不够显示「样本不足」，样本够但变化不到 10% 显示 `≈`。

跨会话的 P95 是「每会话 P95 的 P95」。分位数不能求平均：P50 的平均不是平均的 P50。

## 为什么不同模型的 TTFB 不能放在一起比

同一个底层模型走不同网关路由，TTFB 的含义可能完全不同：一条路由在模型开始出字时才回响应头，另一条路由在接单时就先回响应头。

一次实测里，同一个模型的两条路由，`(TTFT − TTFB) ÷ TTFT` 的中位数分别是 87% 和 5%。把它们汇总出来的 TTFB 不描述其中任何一条，却会让人得出「首字节很快」的结论。

所以 `/perf` 只在单个模型内展示 TTFB，跨会话趋势里 TTFT 也单独列出按模型的那几行。混用多个模型时，以按模型的数为准。

## 趋势怎么读

```text
性能趋势 · 近 7 天 vs 前 7 天
  会话数：本期 48 / 上期 62（不含还在跑或崩溃未收尾的会话；中断、报错收尾的仍计入）

  指标                本期              上期              变化
  TTFT P50            5.7s (n=13)       2.2s (n=57)       ▲ 158% 变差 ⚠
  生成速度 P50        无样本            无样本            样本不足
  ...
```

- `▲` / `▼` 是数值方向，「改善 / 变差」才是好坏。延迟变小是改善，tok/s 变大是改善。
- 变化不到 10% 记 `≈`；退步达到 20% 标 `⚠`。
- 「无样本」表示这段时间的会话没有这项数据，不是 0。比如生成速度和工具耗时是新版本才开始写进索引的，旧会话一律无样本。
- 「会话数」只排除没跑到收尾的增量会话（`exit_status=incomplete`，进程崩溃或还在跑）。用户中断（Esc、Ctrl-C、外部 kill）、报错收尾、达到 maxTurns 或预算上限的会话**仍计入**——它们是真实样本，排除会让延迟分位数系统性偏低。
- 成本只统计已计价的会话。网关没回价格的会话成本记为 0，混进来会把中位数压成 $0，看起来像「省了 100%」。
- 先看会话数和 `n`。模型组合变了（比如这周多用了思考型模型），TTFT 变差可能只是换了模型，按模型那几行能分清。

## 还没有的

- **TPOT / token 间隔**：决定打字流畅感，目前没有采集。
- **自动告警**：趋势需要你主动打 `/perf --days` 查看，不会自己推送。
