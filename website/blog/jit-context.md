# JIT 上下文：让 agent 在正确的时刻拿到正确的规则

你在 `CLAUDE.md` 里写了"这个目录下的组件禁止用彩色 emoji"，agent 改完代码，
emoji 还在。你的第一反应大概是"模型不听话"。

多数情况下不是。是那条规则**当时根本不在上下文里**。

模型只能遵守它看得见的东西。规则要生效，得先在这次请求的上下文里出现——
这是一个纯粹的工程问题，和模型能力无关。JIT（Just-In-Time）上下文就是解决
"什么规则、在什么时刻、进不进上下文"的机制。它直接决定你写的规范能不能真正约束模型行为。

这篇把 sid-code 里这套机制拆开讲：两条注入路径各管什么、作用域怎么判定、
为什么"追加式注入"需要一个单一收口，以及一个真实存在过的跨项目规则泄露缺陷。

## 为什么不能"全都塞进去"

最省事的做法是启动时把项目里所有 `CLAUDE.md` 一次读完、全塞进系统提示词。
这条路走不通，有三个各自独立的原因：

**上下文是有限且昂贵的。** 每次请求整个系统提示词都要重新发一遍。大仓里几十份
目录级规范加起来轻松上万 token，绝大多数在当前任务里一条都用不到。这笔钱每轮都在付。

**无关规则会主动干扰模型。** 这不是理论担忧。我们踩过一次真实的：
在 `website/` 目录里做文档任务，上下文里却被塞进了 `src/ui/` 的 TUI 组件规范，
模型连续 6 次在回复里自述"注入的规范与当前任务无关"。它不但没帮上忙，
还占着模型的注意力，让它反复解释自己为什么不用理这些规则。

**规则之间会互相矛盾。** `src/ui/` 要求"状态靠排版不靠颜色"，
`website/` 要求"配色走 theme 变量"——单独看都对，同时出现在上下文里模型就得猜哪条适用。

所以正确的目标不是"尽可能多给规则"，而是**在正确的时刻给正确的规则**。
这就要求机制能回答一个问题：现在这一刻，什么算"相关"？

## 两条注入路径

sid-code 里规则有两条进入上下文的路径，分工明确。

| | 启动加载 | JIT 发现 |
| --- | --- | --- |
| 时机 | 会话启动时一次 | 每轮工具调用后按需 |
| 判定依据 | 你在哪工作 + 你在改什么 | 工具**实际访问**的文件路径 |
| 覆盖范围 | 企业 → 全局 → 用户 → 项目根 → 子目录 → `.claude/rules/` → `CLAUDE.local.md` | 被访问路径向上到项目根的整条目录链 |
| 典型产出 | 项目级约定、全局个人偏好 | 深层目录的局部规范 |

启动加载负责"一定要有的"那部分：项目根的 `CLAUDE.md`、你的全局偏好、企业下发的强制约束。
这些不依赖任何运行时信号，会话一开始就该在。

JIT 负责"用到才给"的那部分。agent 读了 `src/ui/Footer.tsx`，
`src/ui/CLAUDE.md` 这一刻才被发现并注入。没碰过这个目录，这份规范整场会话不出现。

### JIT 的触发面

工具执行完一轮后，harness 检查这批工具访问了哪些路径。文件类工具（`read` / `write` /
`edit` / `grep` / `glob`）的目标路径会被送进 JIT 发现流程。

发现逻辑是"从目标文件所在目录向上走到项目根"，每一级检查这些候选文件名：

```text
CLAUDE.md
.claude.md
claude.md
.claude/CLAUDE.md
.claude/instructions.md
```

读了 `src/ui/components/Footer.tsx`，扫描链是
`src/ui/components/` → `src/ui/` → `src/` → 项目根。链上任何一级有规则文件，都会被拾起。

这里有一条**当前的边界**值得知道：用 `bash` 写文件（`sed`、重定向、脚本生成）
不会触发 JIT——harness 看不出一条 shell 命令碰了哪些路径。
需要目录级规范可靠生效时，让 agent 走 `edit` / `write` 而不是 `bash`。

## `paths:` 作用域：同一份规则，两条路径判定方式不同

规则文件可以在 frontmatter 里声明作用域：

```markdown
---
paths: ["src/ui/**"]
---

# TUI 组件规范

状态变化靠排版表达，不要用彩色 emoji。
```

意思是：这份规范只在处理 `src/ui/` 下的文件时才该出现。

有意思的地方在于，两条路径判定"命中"的方式**必须不同**，因为它们手上的信息不一样。

### JIT 侧：拿真实的活动文件判

JIT 手里有确切信息——`accessedPath` 就是 agent 这一刻真正在读写的文件。
拿它跟 `paths` 直接比：

- 读 `src/ui/Footer.tsx` → 命中 `src/ui/**` → 注入
- 读 `website/index.md` → 不命中 → 跳过

这是 `paths` 语义最干净的一次判定：作用域 = 我此刻正在动的文件。

### 启动侧：没有"活动文件"，得先构造信号

启动时 agent 还没碰任何文件，`accessedPath` 不存在。如果这时候对所有带 `paths:`
的规则一律拒绝，会留下一个真实的坑：**整场会话不触碰该目录的任务**（纯对话、纯规划、
只读代码不改）永远拿不到作用域规则。

所以启动侧自己采集两个信号：

1. **cwd 目录标记**——你在哪个目录启动的，代表"你当前在哪工作"
2. **git 变更文件**——你已经改了什么，代表"你正在改什么"

两个信号各补对方的盲区，缺一个都不行。目录标记只能满足 `dir/**` 形状的规则；
`paths: ["**/*.py"]` 这种按扩展名收窄的作用域，光有目录标记一律不匹配。反过来，
还没开始改文件时只有目录标记能说明你在哪。

这里有个容易踩空的实现细节，用 glob 语义实测一下就清楚：

```text
Bun.Glob("src/ui/**").match("src/ui")   → false
Bun.Glob("src/ui/**").match("src/ui/")  → true    ← 末尾斜杠不可省
Bun.Glob("**/*.py").match("src/")       → false   ← 目录标记满足不了扩展名作用域
```

目录标记必须带末尾 `/`。少这一个字符，整个信号静默失效——不报错、不告警，
只是作用域规则再也匹配不上。

**git 变更还必须按 cwd 收窄**，只取当前工作目录子树内的变更，不是全仓变更。
这正是前面那起"website 里被注入 TUI 规范"事故的修法：这类长期开发的仓库里
`src/ui` 常有未提交改动，若取全仓变更，那份 TUI 规范会在任何目录下都被拉进上下文，
等于换个入口把事故重演一遍。收窄后语义才自洽：**作用域 = 我此刻工作的范围**。

顺带一条设计取向：git 不可用或不在仓库里时，采集结果退回到"仅含 cwd 标记"，
而不是"匹配一切"。作用域机制的目的是收窄注入面，采集失败就应该倒向更保守的那一侧。

## 缓存里的一个细节：为什么"扫过的目录"不能简单记为已扫描

JIT 每轮工具调用都跑，必须去重，否则同一份规则每轮重复注入。
天然的做法是缓存两个集合：已加载的文件、已扫描的目录。

但"已扫描"这个状态和作用域判定放在一起会出问题。看这个序列：

```text
1. 读 src/ui/README.md    → 扫描 src/ui/ → 规则的 paths 未命中 → 跳过
2. 读 src/ui/Footer.tsx   → src/ui/ 已在"已扫描"集合里 → 直接返回
                          → 规则永远拿不到 ❌
```

第一步的"跳过"是对的——`README.md` 确实不该触发 TUI 组件规范。但如果因此把
`src/ui/` 记成"已扫描"，第二步那个**本该命中**的文件就再也没机会拿到规则了。
一次正确的跳过，永久毒化了整个目录。

修法是把两种"没注入"分开：

- **链上所有候选都处理完了** → 登记为已扫描，后续跳过（真的没有新东西）
- **有规则因作用域未命中被跳过** → 不登记，留待下次触达重新判定

对应实现里那个 `hasScopeDeferred` 标记。同理，作用域未命中的文件也不进"已加载"集合——
它没被加载，只是这次不适用。

这类缺陷的共同特征：**去重缓存和条件判定耦合在一起时，"这次不适用"会被误存成"以后都不用看"。**

## 注入是追加式的，所以需要一个单一收口

JIT 注入的实现方式是把规则块**追加到系统提示词末尾**。这个选择带来一个必然的副作用：
任何"覆盖式重建系统提示词"的操作都会把它整体抹掉。

而覆盖式重建的入口不少：`/model` 切模型、`/language` 切语言、`/memory reload`、
`CLAUDE.md` 变更触发的重建……每一个都是 `setSystemPrompt(newPrompt)`。

更麻烦的是**抹掉之后不会自愈**。JIT 的去重集合里已经把那份文件记为"已加载"，
后续再访问同一目录也不会重新注入。规则就此永久丢失，直到进程重启。
用户视角看到的现象是：前半场会话规则好好生效，切了一次模型之后突然不遵守了，
且完全没有任何提示。

修法的关键不是"在 rebuild 里补一次回灌"——那样下一个新增的重建入口还会漏。
正确做法是让**所有**覆盖式写入都只走同一个函数，回灌在那一处完成：

```text
运行时偏好重建（/model、/language）─┐
CLAUDE.md 变更监听                ─┼─→ applySystemPrompt(prompt, reason)
压缩后重建                        ─┘        → 回灌 JIT → setSystemPrompt
```

这是"追加式内容 + 覆盖式重建"这对组合的通用解法：**收口到一个函数，
而不是在每个调用点打补丁。** 补丁的数量会随入口增长，收口的数量恒为一。

不过收口只有在**真的没有旁路**时才成立。写这篇时顺手核对了一遍全部
`setSystemPrompt` 调用点，发现 `/memory reload` 还是裸调的，没走收口——
也就是说这条路径上 JIT 规则依然会被抹掉且不自愈。这正好说明收口模式的
弱点：它把"别漏"的责任从每个入口挪到了"新增入口的人要知道有这个收口"，
少了机制性约束（比如让裸调在类型或 lint 层面不可用），照样会漏。
这条缺陷已登记待修。

回灌本身还得幂等——重复注入同一份规则不但浪费 token，还会让模型看到两份可能已经
不一致的内容。所以回灌前先检查提示词里是否已包含该块。

## 一个真实的跨项目泄露缺陷

JIT 向上扫描时必须在项目根停住，否则会爬到项目外面去。停止条件最初是这样写的：

```js
while (currentDir.startsWith(projectRoot)) {
```

看着没问题，实际有个洞：`startsWith` 是**字符串**前缀比较，不是**路径段**比较。

`/tmp/proj-evil` 确实以 `/tmp/proj` 开头。于是项目根是 `/tmp/proj` 时，
兄弟目录 `/tmp/proj-evil` 被判定为"在项目内"。实测复现：

```text
projectRoot = /tmp/jitbnd/proj
访问        = /tmp/jitbnd/proj-evil/src/a.ts

结果：
--- 新发现的项目上下文 (../proj-evil/CLAUDE.md) ---
# 邻居项目的规则（不应被 proj 加载）
```

注入路径已经显示成 `../proj-evil/CLAUDE.md`——爬出了项目根。

这不是边角情况，触发形态在日常开发里很常见：

- `sid-code` / `sid-code-old`（留了个备份目录）
- `proj` / `proj-worktree`（同级 git worktree，我们自己天天在用）
- monorepo 里的 `app` / `app-legacy`

放大危害的是**用户看不见注入内容**。JIT 是 harness 静默注入的内部上下文，
终端里不显示。泄露了也无从发现——你只会偶尔觉得 agent 行为有点怪。

修法是把判据从字符串前缀换成路径段：

```js
const rootWithSep = projectRoot.endsWith(sep) ? projectRoot : projectRoot + sep;
const isInsideProject = (dir) => dir === projectRoot || dir.startsWith(rootWithSep);
```

`dir === projectRoot` 单独列出是必要的：项目根自己不以 `projectRoot + sep` 开头，
只写后半条会把项目根本身排除掉。

回归测试覆盖四种情形：兄弟目录隔离、项目内不误伤、重复注入幂等、`paths` 作用域生效。
前两条是一对——只测"不泄露"很容易写出一个把所有目录都拒绝的"修复"。

> 顺带一个发现：把 Claude Code 的同段循环逻辑抽出来实测，同样的输入
> （cwd=`/tmp/proj`、读 `/tmp/proj-evil/src/a.ts`）也会把 `/tmp/proj-evil`
> 纳入扫描目录。这是一条上游同样存在的缺陷。

## 一个必须正视的张力：JIT 与 prompt cache 互相冲突

JIT 是"按需追加系统提示词"。prompt cache 是"系统提示词前缀不变才能命中"。
这两件事在方向上直接对立。

sid-code 的系统提示词按一个边界标记切成两区：静态区打缓存断点，动态区（日期、
git 状态这类每次都变的内容）放在边界之后。JIT 注入落在提示词末尾，也就是动态区——
所以它不会击穿整个前缀缓存。但新注入发生的那一轮，动态区内容变了，那部分要重算。

这是个真实的成本，不是零。它换来的是：无关规则不进上下文（省下的是**每一轮**的钱），
以及规则不互相干扰（省下的是模型的注意力）。

值得说清楚的是这个取舍**不是普适最优**。规则文件少且都是项目级无条件规则的仓库里，
启动时一次全量加载、之后前缀完全稳定，反而更省。JIT 的收益随"目录级规范的数量和
分散程度"增长。这也是为什么它是个可关的开关：

```json
{ "jitContext": false }
```

关掉之后，带 `paths:` 的规则只剩启动加载那条路径（靠 cwd 与 git 变更信号判定），
运行时按需发现不再发生。

## 当前的能力边界

这套机制还有几处已知的不完整，说清楚比含糊过去有用：

| 边界 | 具体表现 | 建议 |
| --- | --- | --- |
| `bash` 不触发 | 用 `sed`、重定向、脚本改文件不会触发 JIT 发现 | 需要规则可靠生效时走 `edit` / `write` |
| 子目录规则不被监听 | 文件变更监听覆盖项目根 / 全局 / 企业 / `.claude/rules/`；会话中途改**子目录** `CLAUDE.md`，JIT 仍用首次读到的内容 | 改完子目录规则重开会话 |
| 子代理不走 JIT | 子代理执行工具时不做 JIT 发现，拿不到目录级规范 | 目录规范对子代理关键时，写进项目根 `CLAUDE.md` |
| `glob` 无路径参数 | 只给 pattern 不给 path 时，退化成扫项目根 | 影响不大，但别指望它发现深层规则 |

这些都在推进中。列在这里不是免责声明——是因为**知道边界在哪，你才能绕开它**。
不写出来，用户只会遇到"规则有时候生效有时候不生效"这种最难排查的现象。

## 怎么把规则写对

机制讲完了，落到实操。

**规则放在它约束的代码旁边。** `src/ui/` 的组件规范就放 `src/ui/CLAUDE.md`。
这样它的作用域天然正确，不需要 `paths:` 声明——agent 碰这个目录才注入，
不碰就不出现。目录结构本身就是最好的作用域声明。

**只在跨目录约束时用 `paths:`。** 比如"所有 Python 文件必须带类型标注"这种规则，
没有一个自然的目录归属，就放项目根并声明 `paths: ["**/*.py"]`。

**规则要写得能被检验。** "代码要优雅"没有任何约束力。
"禁止彩色 emoji，状态变化靠排版表达"可以——模型能判断自己有没有违反，你也能。

**规则不生效时，先怀疑它不在上下文里，再怀疑模型。** 排查顺序：

1. 这轮 agent 碰过那个目录下的文件吗？没碰 → JIT 不会发现它，符合预期
2. 规则文件有 `paths:` 吗？拿实际访问的文件路径手动比一下 glob
3. 中途跑过 `/memory reload` 吗？这条路径目前会抹掉已注入的 JIT 规则且不自愈
4. 规则是刚改的吗？子目录规则的变更需要重开会话

四步走完还是不生效，那才轮到"模型没遵守"这个判断。

## 一句话

规则能不能约束模型，取决于它在那一刻是否在上下文里——这是个工程问题，不是模型问题。
JIT 上下文把"什么规则、什么时刻"这件事做成机制，代价是一点缓存开销和几处需要小心
维护的耦合点（去重缓存与条件判定、追加式注入与覆盖式重建）。

这两处耦合的教训比机制本身更通用：**去重缓存碰上条件判定，"这次不适用"容易被
误存成"以后都不用看"；追加式内容碰上覆盖式重建，补丁要打在收口处而不是每个入口。**
