# 分叉处置协议（编排层强制附加，不是本 PR 的任务内容）

> 这一段由 `pr-batch open` **机械附加**在每份任务 prompt 后面，不依赖谁记得写。
> 原来的 prompt 只说「看到别的问题记下来告诉我」—— 那是个死路：
> 「告诉我」之后没有下一步，问题只活在对话里，会话一关就没了。

## 判据：它属于当前这层吗

改到一半发现别的问题时，**先判类别，再动手**：

| 情况 | 处置 |
| --- | --- |
| 是本 PR 范围内的必要部分（不修它，本 PR 的验收判据就过不了） | 就在本 PR 里修，正文说明为什么它属于本 PR |
| 同一文件、但是另一件事 | **开 issue**，不塞进来。见下面的必填格式 |
| 会让本 PR 的验收判据不成立（比如你必须改一个被划为「不能碰」的函数签名） | **停下来问人**。可能要重算分层，那不是你能单方面决定的 |

判「是不是另一件事」需要理解问题，这一步没法机械化，是你的判断。
但**判完之后的归档是机械的**，下面这套格式必须照做。

## 开 issue 的必填格式

**第一行必须是这个 HTML 注释**（`gh issue create --body` 里照原样写进去）：

```
<!-- pr-batch: from=<你的PR id> pr=<你的GitHub PR号> files=<会改的文件,逗号分隔> plan-doc-correction=<被推翻的方案文档小节号，没有就省略> -->
```

真实例子（首次试跑的 #64）：

```
<!-- pr-batch: from=PR11 pr=63 files=packages/core/src/llm/gateway-pricing.ts plan-doc-correction=§6.2 -->
```

四个字段各自的用处，**别省**：

| 字段 | 少了它会怎样 |
| --- | --- |
| `from` / `pr` | `pr-batch derived` 靠「正文指回本批 PR」现查 issue。没有指回就查不到，issue 从编排视野里消失 |
| `files` | 编排靠它算「这个派生问题会不会跟方案文档里**还没做**的 PR 撞上」。⚠️ 只写**你判断会改**的文件，不要把对照用的、引用到的文件写进来 —— 那会制造假阳性，报多了人就不看了 |
| `plan-doc-correction` | 你若在核实中**推翻了方案文档的描述**（不只是「多发现一个问题」），写上被推翻的小节号。没有这个字段，错描述会一直留在文档里骗下一个人 |

**没写 `files` 不会导致失败**，编排会退化成正文 grep 并把结论标成「弱证据」。
但正文 grep 分不出「我要改它」和「我拿它当对照」—— 所以请写。

正文还要有：现象、回源码核出的事实（带 `file:line`）、建议修法、验收判据、
以及一句「来源：PR #<n> 交付时顺手核出，按『一个 PR 一件事』不在那个 PR 里改」。

## 你若推翻了方案文档的描述

这是最有价值也最容易丢的一类发现（#64 就是：方案说两个模块「有同样的问题」，
回源码核完发现是**互补的另一半**，照抄方案会修错方向）。

除了在 issue 里写 `plan-doc-correction=<小节号>`，还要在正文里单独起一节：

```markdown
## ⚠️ 推翻方案文档 §X.Y 的描述

原文说：<照抄原句>
回源码核出：<事实 + file:line + 你跑的命令>
影响：照原文实现会 <具体后果>
```

**不要自己去改方案文档**（它在仓库外，不在你的文件领地里）。
编排侧有 `pr-batch reflow <issue号>` 负责把它变成可粘贴的修正块。

## 最后一步：在 PR 正文里列出派生的 issue

PR 正文写一节「本 PR 派生的问题」，逐条列 `#<n> — <一句话>`。
双向链接（PR → issue、issue → PR）是追溯的唯一途径，两个方向都要有。
