你在为 sid-code 生成面向**用户**的更新日志。

sid-code 是一个命令行 coding agent。它的用户是开发者，但读更新日志时他们关心的是
「装了这个新版本，我用起来有什么不一样」，**不是**「代码里改了哪个符号」。

## 输入

- 本版本号：`{{VERSION}}`
- 提交区间：`{{RANGE}}`
- 本区间的提交清单（hash + 标题，已过滤 bump/Merge 等记账提交）：

```
{{COMMIT_LIST}}
```

## 输出

用 `write` 工具把结果写到：`{{OUTPUT_PATH}}`

**只写这一个文件，不要改动仓库里任何其它文件。** 写完后用一句话说明你保留了几条、
丢弃了几条，不要复述文件内容。

## 硬性规则

1. **先看真实 diff 再动笔。** 对每条你打算保留的提交，先跑
   `git show --stat --format='' <hash>`，必要时 `git show --format='' <hash>` 看正文。
   commit message 可能是**误导性的** —— 它写的是作者当时关心的事，
   不一定是这次改动对用户的实际影响。

2. **只写用户可见的变更。** 纯内部重构、CI、测试、构建脚本、文档改动一律丢弃。

3. **但要反向警惕**：看着像内部改动的，可能对用户有实际影响。依赖升级可能顺带修了 bug；
   一次重构可能真的消除了某个竞态，从而修掉用户遇到的问题。
   判据是**看 diff 的实际效果**，不是看 commit 的类型前缀。

   > 第 2 条与第 3 条的张力是刻意的：只有第 2 条会漏掉「重构顺带修了 bug」这类，
   > 只有第 3 条会把所有内部改动都硬说成用户价值。两条并存，让判据落在「看 diff」上。

4. **写结果，不写实现。** 不要出现函数名、变量名、文件名、符号改名。
   - ✗「update.ts 的 DEFAULT_RELEASE_HOST 升为 DEFAULT_RELEASE_ORIGIN」
   - ✓「下载地址切到新域名，老版本需重新运行 sid-code update」

   例外：**用户会直接敲的东西**该写出来 —— 命令名（`sid-code update`）、
   斜杠命令（`/model`）、配置项名（`subAgentModels`）、环境变量、命令行参数。
   判据是「用户需要照着敲/照着配吗」，而不是「这是不是一个标识符」。

5. **不要复制 commit 前缀**（`feat:` `fix(stream):`），也不要在文案里保留 hash。

   更要紧的是：**不要把 commit 标题原样搬过来。** 每一条都必须是你**重写**的一句话。

   凡是只有本仓库开发者才懂的内部记号，一律不许出现在文案里：
   - 批次/阶段编号：`P0-P3`、`B1-B3`、`G1-G6`、`M2/M4`、「第 4、5 批」、「第 2 轮」
   - 内部方案代号与章节号：`CC §14`、「对齐 CC 缺口」、「审计驱动修复」、「北极星宗旨」
   - 内部工程动作：「死代码清理」、「重构落地」、「双检」、「归因统一」

   这类记号指向的是**项目内部的工作组织方式**，不是用户能感知的变化。
   看到它们，说明你在描述「我们做了哪批活」而不是「用户得到了什么」。

   - ✗「上下文窗口管理对齐 CC §12 缺口修复（P0-P3）」
   - ✓「上下文接近上限时自动压缩，长会话不再中断」
   - ✗「负收益防线审计第 2 轮修复落地（发现 1-6，批次 A/B/C/D/E）」
   - ✓ 拆成具体的几条，每条说清一个用户能察觉的变化；实在说不出就丢弃

   **一条 commit 若你无法说出它对用户有什么变化，就把它放进 `discarded`，不要硬写。**
   宁可少几条，也不要留一条用户读不懂的。这尤其适用于提交数很多的版本 ——
   那种版本里往往有大批内部工程提交，硬凑成条目只会得到一整屏噪音。

6. **一条一句话，越短越好。** 用户是扫读的，能删的字都删掉。
   目标 **40 字以内**；{{MAX_ITEM_LEN}} 字是硬上限，不是目标值 —— 写到 100 字就已经太长了。
   - 一条只讲**一件事**。一句话里塞了两个分号，说明它该拆成两条，或者后半句是实现细节该删。
   - 不要在条目里解释「怎么配」。✗「加一条同模型不同 name 的配置，再设 model_id 指回厂商真名即可」
     ✓「同一个模型可以配多个渠道（如公司网关 + 官方端点）」—— 怎么配是文档的事，
     更新日志只回答「有这个能力了」。
   - 不要把「为什么」写进来。用户要的是「变成什么样了」，不是排查过程。

7. **分组只能用这几个**：{{SECTION_TITLES}}

   分到哪一组，判据是**这条对用户是什么性质**，不是 commit 的类型前缀：

   | 组 | 判据（一句话） |
   | --- | --- |
   | 破坏性变更 | **用户必须动手**，否则升级后会不一样 / 会坏 |
   | 新功能 | 之前**做不到**的事，现在能做了 |
   | 改进 | 本来就能做，现在**更好了**（更快、更省、更好看、噪音更少） |
   | 修复 | 本来**该好用但坏了**，现在好了 |

   - 「重构」「性能」归入「改进」；「文档」「其他」不写。
   - 一个重构若实际修掉了 bug，归入「修复」而不是「改进」。
   - **显示噪音、冗余输出被清理掉 → 「改进」，不是「新功能」**（用户没有获得新能力）。
   - 同一分组只出现一次，把条目合并进去，不要出现两个同名分组。
   - 空分组不要写（宁可整组不出现）。

8. **破坏性变更必须单列**，哪怕只有一条 —— 这是用户升级前最需要看到的一类。

   但**判据严格**：只有「用户必须动手，否则会不一样或会坏」才算。
   - ✓ 配置项改名/移除、命令行参数移除、默认值翻转、旧写法不再被接受
   - ✗ **自动迁移**：程序启动时自己把旧配置改好了 → 这是「改进」，用户什么都不用做
   - ✗ 只影响老版本、装了新版就没事的（那属于「改进」或干脆不写）

   判断口诀：**这条要求用户改点什么吗？** 不要求 → 不是破坏性变更。
   把不需要动手的事放进这一组，会让真正需要动手的那条被淹没。

9. **`highlight` 写本版最值得说的一件事**，一句话，不超过 {{MAX_HIGHLIGHT_LEN}} 字。
   若本版实在没有值得强调的，写 `null`，不要编。

10. **若整个区间没有任何用户可见变更**：`userFacing` 设为 `false`、
    `sections` 设为空数组 `[]`、`highlight` 设为 `null`。
    这是一个**合法结论** —— 不要为了填满而把内部改动包装成用户特性。

11. **不要写任何 URL**（含内网地址、gitlab 地址、IP、端口）。这份文案会发布到公网，
    而你在读 diff 时会看到部署脚本里的内网主机名和 IP —— 一个字都不要抄进文案。
    校验器会拒绝含 URL 的文件。

12. **全部用中文。**

13. **文案里不要用半角双引号 `"`。** 要强调或引用就用中文引号「」。
    半角双引号会**破坏 JSON**（`"行为更符合"只读"预期"` 是非法 JSON），
    整个文件解析失败、这一版的工作全部作废。同理避免文案里出现裸反斜杠 `\`。

14. **`commits` 填你保留下来的提交 hash，`discarded` 填你看过但判断为不写的 hash。**
    两者加起来应覆盖上面清单里的绝大部分 —— 这不是记账，是让后续能查出
    「有没有一整块功能被漏掉」（漏掉是完全静默的，页面看起来很正常，只是少了个功能介绍）。

## 输出 schema

```jsonc
{
  // 必须与文件名里的版本号一致（校验器会比对）
  "version": "{{VERSION}}",
  // 本版一句话亮点；纯内部版本写 null，不要写「无」这种占位文字
  "highlight": "…",
  // false = 本版无用户可见变更。为 true 时 sections 不得为空；为 false 时必须为空
  "userFacing": true,
  // 分组数组；title 只能取上面第 7 条列的受控词
  "sections": [
    { "title": "新功能", "items": ["…", "…"] }
  ],
  // 溯源：保留下来的提交（不渲染到页面）
  "commits": ["3b8b752b"],
  // 看过但判断不写的提交（不渲染到页面）
  "discarded": ["0800dee7"],
  "generatedBy": "sid-code",
  "reviewedBy": "pending"
}
```
