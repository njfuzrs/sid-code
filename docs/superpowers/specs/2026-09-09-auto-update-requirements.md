# 需求澄清文档：自动更新机制

> **需求来源**：微信文件《如何设计并实现一个自动更新机制.txt》（2026-09）
> **对象**：`sid-code` —— coding agent CLI 工具（Bun 编译单文件二进制，自有发布服务器）
> **状态**：已澄清，待实现
> **日期**：2026-09-09

## 1. 背景与现状

本需求是在既有地基上加一层自动化编排。先摆出现有基础设施：

| 需求点 | 现状 |
| --- | --- |
| 检测新版本 | 服务器 `www.sid-code.cc/releases/sid-code/` 已有 `latest.txt`（稳定）/ `beta.txt`（beta）单行版本号指针，`curl` 一次即可拿到 |
| 下载 + 校验 | `install.sh`（由 `scripts/install-template.sh` 生成）已实现：sha256 校验、解压到版本化目录、`--version` 冒烟测试 |
| 原子替换 | `install.sh` 用 `ln -sfn` 临时链接 + `mv -f` 原子切换软链 —— 正在运行的进程持有旧版本目录的二进制，切软链天然不影响它 |
| 手动更新 | `sid-code update` = `curl install.sh \| bash`，刻意复用避免双实现（`packages/cli/src/command/update.ts` 注释有说明） |
| 回滚 | 服务器端 `rollback.sh`（指针回退）；客户端「新版起不来自动回退」尚无 |
| 配置系统 | `settings.json` 已有完整的读取/合并/团队默认值分发机制（`mergeMissingTopLevelKeys`），加一个字段是熟路 |

需求里最难的「安全地替换二进制」已经解决，缺的是自动化的编排层：什么时候查、谁去下载、下载完何时生效、怎么通知、怎么兜底。

## 2. 逐条澄清结论

### 需求 1：检测线上新版本（仅稳定版）

| 子项 | 原文诉求 | 澄清结论 |
| --- | --- | --- |
| 检测目标 | 仅稳定版，不更新到 beta | 自动更新**只读 `latest.txt`**（稳定指针），绝不读 `beta.txt`。spawn 安装子进程时**显式剔除 `SID_CODE_CHANNEL` / `SID_CODE_VERSION` 环境变量** —— 否则用户 shell rc 里残留的 `SID_CODE_CHANNEL=beta` 会被子进程继承，把「仅稳定版」静默破坏（这是澄清过程中发现的真实边界，原文未提及） |
| 1.1 版本比较 | 如何比较 | 编译期内联版本号 `getVersion()` vs `latest.txt` 内容，`x.y.z` 三段数字逐段比较；**严格大于才更新**。`latest.txt` 内容先过 `/^\d+\.\d+\.\d+$/` 格式校验，非法即视为更新源异常、静默退出 |
| 1.2 检查频率 | 多少合适 | **每 24 小时最多一次**（已确认），触发时机为交互会话启动后异步检查，不阻塞启动。频率写死，不暴露配置 |
| 1.3 用户开关 | 默认开启，支持关闭 | **三档**（已确认）：`settings.json` 顶层字段 `autoUpdate: "off" \| "notify" \| "auto"`，默认 `"auto"`；env `SID_CODE_AUTO_UPDATE` 可覆盖（优先级 env > settings > 默认） |

### 需求 2：自动拉取安装（全程后台）

| 子项 | 原文诉求 | 澄清结论 |
| --- | --- | --- |
| 后台安装 | 不需人工介入 | detached 子进程跑现有 `install.sh`（**薄编排层架构**，已确认：TS 只做节流/比较/加锁/spawn/通知，下载、sha256、冒烟、切换全部复用 `install.sh`，不造第二份实现） |
| 2.1 通知用户 | 友好提示 | 主口径：**下次启动时**提示「已自动更新到 vX.Y.Z（原 vA.B.C）」，走 TUI 既有 transient message 通道。会话内实时通知仅在现有通道顺手可用时做，**不为它新建机制** |
| 2.2 下次启动时替换 | 防止破坏正在执行的任务 | **已澄清并获得确认**：现有机制是「解压到版本化目录 + 原子切软链」，正在运行的进程持有旧版本目录的二进制 inode，切软链对它零影响，下次启动自然走新版。原文担忧已被架构天然满足，因此采用「**后台下载完成即原子切换**」语义，不需要额外的 staging 暂存区 |

### 需求 3：边界与异常

| 子项 | 原文诉求 | 澄清结论 |
| --- | --- | --- |
| 3.1 网络类（DNS/重置/中断/代理/TLS） | 全部覆盖 | fetch 5s 超时 + curl `-f --connect-timeout 10 --max-time 600`；失败静默记 state+log，24h 节流即天然退避 |
| 3.2 校验类（哈希不匹配/包损坏/版本号非法） | 全部覆盖 | sha256 校验失败不切软链；版本号格式非法视为更新源异常；签名验证不在当前信任基线（sha256+HTTPS），明示不做 |
| 3.3 安装类（权限/磁盘/路径占用/卸载失败/启动失败） | 全部覆盖 | 失败走子进程 exit 码路径；路径占用由 `mv -f` 原子解决；**旧版本不卸载** —— 版本化目录保留即回滚素材，无此失败形态；新版本启动失败由切换**前**冒烟测试拦截 |
| 3.4 并发类 | 多实例同时更新 | mkdir 锁 + stale 回收（>30min 可回收） + `mv -f` 幂等切换 |
| 3.5 回滚策略 | 新版装后无法启动自动回退 | **能力边界诚实点破**：损坏的二进制内部无法自救。**防线前置**：切换前冒烟测试（`install.sh` 既有）+ 旧版本目录保留使人工回退一条 `ln -sfn` 可完成。这与 npm 等业界同构方案一致，是能力边界而非遗漏 |
| 3.6 降级保护 | 线上版本比当前低不强制降级 | `compareVersions(latest, current) > 0` 才继续，等于/小于一律不动（同时覆盖 beta 用户版本高于 stable 的场景） |
| 3.7 更新源不可用 | 保留当前版本静默失败 | 全链路 try/catch，任何异常不上抛；**连续失败 ≥3 次时提示一次**后计数归零（防止自动更新静默坏死数月无人发现，正是本仓北极星文档「防线全在、调用全 0」的教训） |

### 需求 4 & 5：测试与文档

- **测试**：单测（版本比较/节流/锁/状态机/配置优先级/失败计数）+ 集成（`Bun.serve` 本地 mock 发布源，`SID_CODE_RELEASE_HOST` 指过去跑全链路与失败路径，BIN_DIR 重定向 tmpdir 不碰真环境）。真二进制 e2e 不自动化（CI flake 源，且发布流程第 7 步本来就有人工端到端核验），理由写入设计文档。
- **文档**：website guide 新增「自动更新」页；动了 `packages/core/src/config/` 需重新生成 `website/ref/`（settings 字段页）与 `llms.txt`。

## 3. 范围边界（明确不做什么）

- **不做 Windows 支持**：现有 `install.sh` 链路本身只覆盖 macOS/Linux 5 平台
- **不做增量/diff 更新**：tarball 全量下载，与手动 update 一致
- **不做代码签名**：当前信任基线为 sha256 + HTTPS，签名是独立议题
- **不新建会话内通知机制**：复用既有 transient message 通道
- **不动 beta 通道语义**与 `rollback.sh`
- **不做客户端版本目录自动清理**：与手动 update 保持一致，留作后续独立议题（每次 ~90MB，按现有发版频率每月几 GB，确实需要但不在本次范围）

## 4. 关键决策汇总

| # | 决策 | 替代方案 | 选择理由 |
| --- | --- | --- | --- |
| D1 | 后台下载完即原子切换 | 下载到暂存区，下次启动才切换 | 现有机制天然满足「不打断用户任务」，避免额外 staging 状态 |
| D2 | 每 24 小时最多一次 | 每次启动都查 / 间隔可配置 | npm 等业界惯例，对日更节奏够用，节流本身即退避 |
| D3 | 三档 `off/notify/auto` | 两档开/关 | 企业「只提醒不自动装」场景是常见诉求，多一档成本低价值高 |
| D4 | 薄编排层 + 复用 `install.sh` | TS 原生下载器 | `update.ts` 注释已否决后者，避免长期两份实现同步 |
| D5 | 回滚防线前置 | 切换后自动回退 | 损坏二进制内部无法自救，业界一致做法 |
